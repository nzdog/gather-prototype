# GTC-255 — Team move silently deletes every assignment a person holds

**Status:** Open — unassigned, not started | **Branch:** TBD | **Commit:** [pending] | **Effort:** TBD

*Filed as bookkeeping during [[GTC-188]] (I1), which surveyed the assignment surfaces while
deciding whether the pre-flight could offer assignment. Pre-existing, NOT caused by I1, and
explicitly out of its scope by founder instruction (2026-08-29): "Do not fix the drag-and-drop
assignment deletion or the missing ledger entry. File those as a ticket instead."*

### Scope, one line

`PATCH /api/events/[id]/people/[personId]` deletes every `Assignment` a person holds in the
event whenever their `teamId` changes — recording nothing in the ledger, telling nobody, and
outside any transaction.

### What happens today

The `PATCH` handler in `src/app/api/events/[id]/people/[personId]/route.ts` contains a branch
guarded by `'teamId' in body && teamId !== personEvent.teamId`. Inside it:

1. `prisma.assignment.deleteMany` removes **every** assignment held by that person **across the
   whole event** — not only the ones belonging to the team they are leaving.
2. `prisma.item.updateMany` then sets `status: 'UNASSIGNED'` on **every assignment-less item in
   the event**, not only the items just released.
3. The person's `teamId` is updated by a separate top-level `prisma.personEvent.update`.

The deletion is a defensible enforcement of the same-team rule the assign route applies
(`Person must be in the same team as the item`, specified in `builder-spec-v1.3.3.md` and
reaffirmed by [[GTC-171]]). The problem is not *that* it happens — it is that it happens
invisibly, unrecoverably, and non-atomically.

### Three defects, in severity order

**1. It is a T1 that records nothing.** The only `recordChange` in that file is in the `DELETE`
handler (person removal). A team move can destroy N assignments with no `ChangeSet`, no
`reason`, and no `onAssignmentReleased` — so nobody who lost an item is told, and Kate's
history has no trace of it. Compare the assign route
(`POST /api/events/[id]/items/[itemId]/assign`), which records `MOVE_ASSIGNMENT` /
`DELETE_ASSIGNMENT` and calls `onAssignmentReleased` for exactly this event. Hinge §2 —
"adding a person with an assignment post-send touches someone, so it carries its why" —
applies with equal force to removing one.

**2. It is not in a transaction.** The deletes, the status sweep, and the `personEvent.update`
are separate top-level Prisma calls. A failure between them leaves the assignments destroyed
and the person still on their old team — the exact partial-failure class
`gather-architecture-contract` §7 records, and which the assign route was already fixed for.

**3. The status sweep is unscoped.** `updateMany` over every assignment-less item in the event
is broader than the change that triggered it. Probably self-correcting today, but it does not
use `repairItemStatusAfterMutation` (the definition the assign route uses), so the two paths
can drift.

### How to reach it

The team board (`src/components/plan/TeamBoard.tsx`) calls `onMovePerson`, implemented as
`handleMovePerson` in `src/app/plan/[eventId]/page.tsx`, which PATCHes `{ teamId }`. One drag
of one chip is enough. The click-to-move menu in the same component is a second entry.

### Not in scope

- The same-team rule itself. It is intended product behaviour, specified, and
  [[GTC-171]] deliberately exempted only `TASK` rows from it.
- The auto-assign route, which was changed by [[GTC-188]] under founder Rulings 1-3 on
  2026-08-29 and no longer creates assignments at all.

### Suggested acceptance

- [ ] A team move that releases assignments records them, one `ChangeSet`, with the actor and
      an optional reason — the shape the auto-assign batch used before its item half was
      removed, and the shape `restoreFromRevision` uses.
- [ ] `onAssignmentReleased` fires for each released person.
- [ ] The deletion, the status repair and the `teamId` update run in one transaction.
- [ ] Item status is repaired through `repairItemStatusAfterMutation`, not a hand-rolled
      unscoped `updateMany`.
- [ ] A regression test seeds a person holding items on two teams, moves them, and asserts both
      the ledger entries and that no unrelated item's status changed.
- [ ] `npx tsc --noEmit` clean, build passes, security suite exits 0.
