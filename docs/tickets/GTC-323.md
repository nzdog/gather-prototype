## ⚠ THE POINT, AND IT LEADS THIS TICKET ON FOUNDER INSTRUCTION, 2026-09-19

> **AN SDK'S TYPES TELL YOU THE SHAPE AND NEVER THE VOCABULARY.**

TNZ's twenty-one result codes are **values**, not fields, and **no type declaration would ever have
contained them.** That is why the hard/soft bounce partition is missing from [[GTC-289]] phase 1
*despite both fields being named by the SDK*: `EmailBounce` declares `type` and `subType` and declares
them as bare `string`. The shape was there to read. The vocabulary was not, and could not have been.

**TNZ has four artifacts in `docs/05_ops`:**

- `tnz-restapi-v2.04-docs-2026-09-12.html`
- `tnz-sms-delivery-result-codes-2026-09-12.html`
- plus `tnz-inbound-and-delivery-correspondence-2026-08.md`, the greppable transcription, and
  `tnz-delivery-status-contract-2026-09-12.md`, the contract derived from them.

[[GTC-264]] records why that mattered: until the transcription was filed *"this ticket cited a summary
in GTC-258 and no artifact."* Its Phase 0 produced documentation and nothing else, and it is the
reason GTC-264 could design a twenty-one-value result vocabulary at all — and the reason it found
three discrepancies **between TNZ's own two pages** that reach the parse.

**Resend has none.** A repo-wide search for a Resend document returns nothing in `docs/`. The
provider that sends every magic link, every nudge email, every wrap-up thank-you and — since
[[GTC-189]] slice 5c — every ask, has no contract in the record.

## What three tickets have each paid for it

Each of these carries the same limit, in its own words, and none of them could close it:

1. **[[GTC-189]] slice 4b** — *"The stub models Resend's success envelope from the SDK's TYPE rather
   than from an OBSERVED response. If the real body were shaped otherwise, the code and the stub
   would be wrong together."* It called that *"[[GTC-264]]'s Isolate the wire shape concern, in a
   smaller place and without its machinery"* and said what closes it: the first live send on a
   working key.
2. **[[GTC-189]] slice 5c** — `isRetryableProviderError` matches a **message string**, because
   `SendResult` collapses Resend's error to `error?: string`. The SDK in fact declares
   `ErrorResponse { message; statusCode; name: RESEND_ERROR_CODE_KEY }` with a closed 21-value code
   union, so the predicate is reading prose where a code exists. Slice 6 owns widening it.
3. **[[GTC-289]] phase 1** — the delivery vocabulary is taken from
   `node_modules/resend/dist/index.d.mts`, and the module says so at length. ⚠ **And the one thing
   the poll cannot supply — the hard/soft bounce partition — is exactly the thing a document would
   have given**: the webhook's `EmailBounce` declares `type` and `subType` as bare `string`, so the
   SDK names the fields and enumerates neither.

**The pattern is the one at the head of this ticket**, and these three are what it cost.

## ✅ What IS now observed — [[GTC-289]] phase 2, 2026-09-19

**One live envelope exists in the record now, and it did not need a working key.** A send was made with
a syntactically valid but deliberately invalid SENTINEL key — no credential used, refused at
submission, nothing delivered — and Resend answered:

```
{ statusCode: 401, name: 'validation_error', message: 'API key is invalid' }
```

**Three facts, and the third is the one to keep:**

1. ✅ **The declared `ErrorResponse` shape MATCHES the live body**: three fields, those names,
   `statusCode` a number. Slice 4b's *"the code and the stub would be wrong together"* limit is closed
   **for the failure envelope**. The SUCCESS envelope is still unobserved and [[GTC-247]] still owns
   it.
2. ✅ **`RESEND_401_BODY` in `tests/email-send-result-test.ts` is byte-identical to it.** GTC-265's
   stub was right. ⚠ The executor's first instinct was to write that the stub was *probably wrong*
   because `invalid_api_key` exists — the measurement corrected the correction, and the comment there
   now records both.
3. ⚠ **RESEND ANSWERS AN INVALID KEY WITH `validation_error`.** Not `invalid_api_key`, not
   `restricted_api_key`, not `invalid_access` — all three of which the SDK declares. **So the one
   observed code is filed under a name that does not describe the situation it was returned for.**

**That third fact is this ticket's whole argument, measured.** Phase 2 classified 21 codes by reading
their names, because there was nothing else to read; the single code anybody has seen shows that the
names are a usable guide to *whether to retry* and a poor guide to *why*. The retry decision is
unaffected — both readings are terminal — and any future consumer that wants to tell a host what went
wrong needs this artifact first.

**And the second statusCode question is answered too**, measured in the same phase with a stub whose
body and HTTP line disagreed: `error.statusCode` is **the BODY's**, not the transport's.

## Scope

**Do here:**
- Obtain Resend's delivery-event and error documentation, and **transcribe it into `docs/05_ops`** as
  a greppable artifact, the way `tnz-inbound-and-delivery-correspondence-2026-08.md` was. A link is
  not the deliverable; a link rots and cannot be diffed.
- In particular: the `bounce.type` / `bounce.subType` vocabulary, whether `email.delivered` is
  affirmative or merely the absence of a failure ([[GTC-289]] Unknown 3), and the
  `RESEND_ERROR_CODE_KEY` to HTTP status mapping.
- ⚠ **AND WHAT EACH ERROR CODE ACTUALLY MEANS**, which phase 2 now depends on. Its 21-value
  classification in `src/lib/email-delivery/resend-error-contract.ts` is inference from names, and two
  entries are marked UNCERTAIN in the file itself — `application_error` (retried, on the reading that
  it is provider-side) and `security_error` (terminal, on the reading that it is the request). **A
  document settles both in a sentence each.** Whether `validation_error` is documented as covering
  auth failures is the third thing to look for, since it demonstrably does.
- ⚠ **Record the SDK version the artifact was checked against** — `resend@6.22.0` today — because a
  contract read against one version and a tree running another is the discrepancy GTC-264 found
  between TNZ's own two pages.

**Do not do here:**
- Any code. This produces documentation, as [[GTC-264]] Phase 0 did, and per house convention it
  carries nothing else.
- Any claim from memory. ⚠ **The founder's instruction at GTC-289 was explicit — "do not infer a
  vocabulary from documentation you have not read"** — and this ticket exists precisely because
  inference was declined. Transcribing what is read is the deliverable; summarising what is recalled
  is the defect.

## ⚠ What it does NOT unblock, so it is not mistaken for the key

[[GTC-247]] is a different gap and this does not touch it. A document tells you what the wire says;
it does not let you observe the wire. **Three things need a working key regardless of this ticket:**

- that a real accepted send returns `data.id` at all ([[GTC-189]] slice 4b's open limit);
- which of `id` / `message_id` / `email_id` actually joins a delivery event back to a send
  ([[GTC-289]] phase 1's finding);
- that any of the declared shapes matches the live body.

**So the two tickets are complements, not alternatives.** This one makes the vocabulary knowable; that
one makes the shape observable.

## Unknowns

1. **Whether Resend publish a delivery-result vocabulary at all**, in the way TNZ publish result
   codes. If the bounce `type` and `subType` are documented only as "provider-specific", the
   hard/soft partition may be unobtainable from documentation and need observation — which would make
   [[GTC-247]] the blocker for it rather than this ticket.
2. ✅ **PARTLY ANSWERED FOR THE ERROR HALF:** the 21 error codes ARE declared by the SDK, so that
   vocabulary did not need a document to be enumerated — only to be UNDERSTOOD. The bounce partition
   is the opposite case and stays as Unknown 1 above.
3. **Whether the account's own dashboard is an artifact source.** TNZ's came from correspondence; a
   Resend dashboard may show received events for past sends, which would be observation rather than
   documentation and would belong under GTC-247.
