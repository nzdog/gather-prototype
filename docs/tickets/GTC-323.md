## ⚠ THE POINT, AND IT LEADS THIS TICKET ON FOUNDER INSTRUCTION, 2026-09-19

> **AN SDK'S TYPES TELL YOU THE SHAPE AND NEVER THE VOCABULARY.**

TNZ's twenty-one result codes are **values**, not fields, and **no type declaration would ever have
contained them.** That is why the hard/soft bounce partition is missing from [[GTC-289]] phase 1
*despite both fields being named by the SDK*: `EmailBounce` declares `type` and `subType` and declares
them as bare `string`. The shape was there to read. The vocabulary was not, and could not have been.

Founder ruling on where this sentence belongs:

> GTC-323's REAL POINT — that is the line, and it should lead the ticket rather than sit inside it: an
> SDK's types tell you the shape and never the vocabulary. TNZ's twenty-one result codes are values,
> and no type declaration would ever have contained them. That is why the partition is missing despite
> both fields being named.

⚠ **AND PHASE 2 DEMONSTRATED THE SAME THING FROM THE OTHER SIDE, WITH A MEASUREMENT** — see *What is
now observed* below. The error union's 21 values ARE in the SDK's types, so phase 2 could classify them
all; the one code that has actually been **seen** turned out to mean something its name does not say.
**A declared value is not a documented one.**

### ⚠ AND THE PART THAT DECIDES THIS TICKET'S PRIORITY — IT LEADS ON FOUNDER INSTRUCTION, 2026-09-19

> **THE TWO ENTRIES MARKED `UNCERTAIN` ARE NOT THE RISKY ONES. THEY ARE THE ONES WHOSE RISK WAS
> VISIBLE.**

`application_error` and `security_error` carry warnings in
`src/lib/email-delivery/resend-error-contract.ts` because their names are ambiguous — the executor could
SEE the doubt and wrote it down. **`validation_error`'s name is not ambiguous at all.** It is clear,
ordinary and confident, and it is the one that turned out to describe an authentication failure.

**So the warnings are on the doubts that could be seen, which is the weakest possible guarantee.** The
other nineteen codes are classified by exactly the same method and none of them carries a warning — not
because they are better founded, but because nothing about them looked doubtful. Founder:

> a vocabulary read from names is a guess with a good accent … this is the evidence that the other
> nineteen are no better founded.

## What three tickets have each paid for it

Each of these carries the same limit, in its own words, and none of them could close it:

1. **[[GTC-189]] slice 4b** — *"The stub models Resend's success envelope from the SDK's TYPE rather
   than from an OBSERVED response. If the real body were shaped otherwise, the code and the stub
   would be wrong together."* It called that *"[[GTC-264]]'s Isolate the wire shape concern, in a
   smaller place and without its machinery"* and said what closes it: the first live send on a
   working key.
2. **[[GTC-189]] slice 5c** — `isRetryableProviderError` matches a **message string**, because
   `SendResult` collapses Resend's error to `error?: string`. The SDK in fact declares
   `ErrorResponse { message; statusCode; name: RESEND_ERROR_CODE_KEY }` with a closed 21-value code
   union, so the predicate is reading prose where a code exists. Slice 6 owns widening it.
3. **[[GTC-289]] phase 1** — the delivery vocabulary is taken from
   `node_modules/resend/dist/index.d.mts`, and the module says so at length. ⚠ **And the one thing
   the poll cannot supply — the hard/soft bounce partition — is exactly the thing a document would
   have given**: the webhook's `EmailBounce` declares `type` and `subType` as bare `string`, so the
   SDK names the fields and enumerates neither.

**The pattern is the one at the head of this ticket**, and these three are what it cost.

## ✅ What IS now observed — [[GTC-289]] phase 2, 2026-09-19

**One live envelope exists in the record now, and it did not need a working key.** ONE request, with a
syntactically valid but **deliberately invalid sentinel key** — `re_0000...`, not a credential and not
this environment's key — to a reserved `example.com` address. **Refused at submission with a 401.
Nothing was delivered and nothing could have been.** The script was run once from the scratchpad and
deleted; it is not in the tree. Resend answered:

```
{ statusCode: 401, name: 'validation_error', message: 'API key is invalid' }
```

**Three facts, and the third is the one to keep:**

1. ✅ **The declared `ErrorResponse` shape MATCHES the live body**: three fields, those names,
   `statusCode` a number. Slice 4b's *"the code and the stub would be wrong together"* limit is closed
   **for the failure envelope**. The SUCCESS envelope is still unobserved and [[GTC-247]] still owns
   it.
2. ✅ **`RESEND_401_BODY` in `tests/email-send-result-test.ts` is byte-identical to it.** GTC-265's
   stub was right. ⚠ The executor's first instinct was to write that the stub was *probably wrong*
   because `invalid_api_key` exists — the measurement corrected the correction, and the comment there
   now records both.
3. ⚠ **RESEND ANSWERS AN INVALID KEY WITH `validation_error`.** Not `invalid_api_key`, not
   `restricted_api_key`, not `invalid_access` — all three of which the SDK declares. **So the one
   observed code is filed under a name that does not describe the situation it was returned for.**

### ⚠ AND THAT THIRD FACT IS THIS TICKET'S WORKED EXAMPLE — FOUNDER, 2026-09-19

> ⚠ **THE `validation_error` FINDING SHOULD REACH GTC-323.** The documentation task now has a worked
> example of why it exists: **the one observed code contradicts its own name, so a vocabulary read from
> names is a guess with a good accent.** Two entries are already marked UNCERTAIN by name; this is the
> evidence that the other nineteen are no better founded.

**Read that last clause carefully, because it is the part that changes the priority of this ticket.**
`application_error` and `security_error` are marked UNCERTAIN in
`src/lib/email-delivery/resend-error-contract.ts` because their names are ambiguous — the executor could
SEE the doubt. `validation_error`'s name is not ambiguous at all: it is a clear, confident, ordinary
name, and it is the one that turned out to describe something else. **So the two marked entries are not
the risky ones. They are merely the ones whose risk was visible.** The other nineteen are classified with
exactly the same method and none of them carries a warning, because nothing about them looked doubtful.

**The retry decision survives this** — `validation_error` is terminal under either reading, so no row's
outcome changes — and that is precisely what makes it a good worked example rather than an incident: a
guess with a good accent is not detectable by its consequences until it has some.

**Any future consumer that wants to tell a host WHY a send failed needs this artifact first.** Phase 2's
module says so in its own header, and [[GTC-324]] is the first consumer that will want to.

**And the second statusCode question is answered too**, measured in the same phase with a stub whose
body and HTTP line disagreed: `error.statusCode` is **the BODY's**, not the transport's.

✅ **AND THE METHOD IS WORTH MORE THAN THE FINDING, recorded on founder instruction, 2026-09-19:**

> **A live probe that costs nothing and settles a shape is worth taking, and the restraint is in
> choosing a key that cannot succeed.**

⚠ **Which is also the fence between this and [[GTC-247]].** A key that cannot authenticate has an
outcome space of exactly one shape — a refusal — so no message can escape and no recipient can be
reached. A key that works produces an accepted send, which is a real email to a real address. **That is
why the failure envelope could be observed in passing and the success envelope cannot be**, and why item
3 of *Do here* is still owed to a working key rather than to this ticket.

## ✅ DONE — 2026-09-19. The artifact is `docs/05_ops/resend-error-and-delivery-contract-2026-09.md`

Read and transcribed from four published pages, all on 2026-09-19, against **`resend@6.22.0`**:
`/docs/api-reference/errors`, `/docs/webhooks/event-types`, `/docs/webhooks/introduction`,
`/changelog/email-bounce-details`. The artifact carries the version it was checked against, the
source URLs, and no decisions — where our code classifies a value, the classification stays in the
contract modules.

### What it settles, answered one at a time as the founder asked

- ✅ **THE BOUNCE `type` VOCABULARY — SETTLED.** Three published values with meanings:
  `Permanent` (hard), `Transient` (soft), `Undetermined`. That is the partition [[GTC-289]] phase 1
  could not derive, and **the reason it could not is this ticket's own thesis**: the SDK declares
  `type` and `subType` as bare `string`, so the shape was readable and the vocabulary was not.
  ⚠ **AND IT DOES NOT REACH OUR POLLER.** The partition rides on the WEBHOOK payload; this repo
  reads the POLL, whose `last_event` has one `bounced` member with no type on it. Knowing the
  vocabulary does not by itself let this tree tell a hard bounce from a soft one.
- ✅ **`email.delivered` IS NOT AFFIRMATIVE — SETTLED, and narrower than hoped.** Verbatim:
  *"Occurs whenever Resend successfully delivered the email to the recipient's **mail server**."*
  [[GTC-289]] Unknown 3 is answered: it is a successful handoff to the receiving MTA and says
  nothing about an inbox. `PROVIDER_REPORTS_DELIVERED` was named correctly — *"deliberately about
  who SAID it"* — and `email.complained` corroborates from the other side, published as following
  a successful delivery, which is what slice 7a's mapping already assumes.
- ✅ **`application_error` — SETTLED.** Published at **500**, *"An unexpected error occurred."*
  Provider-side. The contract module read it that way *"from its neighbours"* and warned the entry
  might be wrong; **the inference was right and is now read rather than inferred.** Its `UNCERTAIN`
  marker can come down, citing the artifact. `PROVIDER_FAULT` and the retry stand.
- ⚠ **`security_error` — NOT SETTLED. It is documented nowhere.** It exists in `resend@6.22.0`'s
  declared union and on no published page read here, so `REQUEST_REFUSED` stays an inference and
  its marker stays up.

  ⚠ **AND THAT IS THE SHARPER HALF OF THE PAIR, WHICH IS THIS TICKET'S OWN POINT ARRIVING.** The
  ticket leads on *"the two entries marked UNCERTAIN are not the risky ones — they are the ones
  whose risk was visible."* Reading the documentation settled one and left the other exactly where
  it was. **A document answers the questions it covers, and the residue is not smaller for having
  been looked up.**
- ⚠ **The `subType` VOCABULARY — NOT SETTLED.** The field is documented as existing and carrying
  granular detail; **no enumeration is published.** One value, `Suppressed`, appears in an example
  payload only. Anything built on it would be built on an open set.
- ⚠ **Which id joins a delivery event to a send — NOT SETTLED and not settleable here.** It needs a
  live accepted send, which needs [[GTC-247]]. The two tickets are complements exactly as this
  ticket's scope says.

### ⚠ TWO FINDINGS THE TICKET DID NOT PREDICT

1. ⚠ **THE PUBLISHED VOCABULARY IS SMALLER THAN THE SDK'S UNION, NOT LARGER.** This ticket's thesis
   is that types give the shape and never the vocabulary. Here the vocabulary IS published — and
   **`security_error` and `internal_server_error` are in the SDK's 21-value union and on no
   documented page.** So the containment runs the other way from the bounce case, and **a declared
   value is not a documented one** — which is the same rule stated from its other side, and worth
   having both halves of.
2. ⚠ **NO DOCUMENTED CODE COVERS A WRONG API KEY.** The page has `missing_api_key`,
   `restricted_api_key` and `suspended_api_key`. **There is no published code for a key that is
   simply incorrect** — and the one answer anybody here has ever observed from this provider is
   `validation_error` / 401 / *"API key is invalid"* ([[GTC-189]] slice 5f). That is undocumented
   twice: `validation_error` is published at 400 and 403 and never at 401, and its published
   meanings are field validation and domain verification, neither of which is authentication.
   **The one code this repo has seen is filed under a name that does not describe the situation it
   was returned for, and the page does not connect them.** Recorded as an observation about the
   wire, not as a correction to the provider.

No code. The two contract modules are untouched — including `application_error`'s marker, which
this artifact licenses removing and does not remove. *"This produces documentation, and per house
convention it carries nothing else."*

## ⚠ What it does NOT unblock, so it is not mistaken for the key

[[GTC-247]] is a different gap and this does not touch it. A document tells you what the wire says;
it does not let you observe the wire. **Three things need a working key regardless of this ticket:**

- that a real accepted send returns `data.id` at all ([[GTC-189]] slice 4b's open limit);
- which of `id` / `message_id` / `email_id` actually joins a delivery event back to a send
  ([[GTC-289]] phase 1's finding);
- that any of the declared shapes matches the live body.

**So the two tickets are complements, not alternatives.** This one makes the vocabulary knowable; that
one makes the shape observable.
