## Purpose — read this before anything else

**Opt-out is not unimplemented, and this handler is not the compliance mechanism.**

TNZ detect opt-out keywords themselves, at their layer, and add the number to their own
opt-out list. Subsequent sends to that number fail with `Destination is blacklisted`. The
guest stops receiving messages whether or not Gather ever processes the reply. That is
answer 5 below, and it is the single most important fact in this ticket.

**The handler's job is keeping Gather's local state in sync with TNZ's.** Without it,
Gather does not know the person opted out, and three things stay wrong:

1. **They stay counted as pending.** `getNudgeStatus` in
   `src/app/api/events/[id]/invite-status/route.ts` never consults opt-out at all — with a
   phone number and a chaseable mark it returns `'pending'`.
2. **They still show as awaitable to the host.** `canReceiveSms` on `PersonInviteStatus` is
   `!!person.phoneNumber && !hasOptedOut`, and `hasOptedOut` is read from the `SmsOptOut`
   table via `getOptOutStatuses`. No local row, no opt-out — the host sees a guest they can
   still chase, and the `optedOut` count in both `counts` and `smsSummary` reads zero.
3. **Nudges keep being queued at them, and fail silently.** `checkOptOut` in
   `src/lib/sms/send-sms.ts` reads the same empty table, so `sendSms` proceeds to the
   provider, TNZ rejects the send, and the result is an `SMS_SEND_FAILED` InviteEvent — a
   failure indistinguishable from a network blip, arriving on a schedule, forever.

**A future session must not read this ticket as "opt-out is unimplemented".** The legal
promise is kept by TNZ. What is missing is Gather's *knowledge* of it. Everything scoped
here is state reconciliation and host-facing truthfulness, not the compliance backstop.
Do-Not-Touch Zone 7 remains binding for the same reason it always was.

## TNZ's answers — the factual basis (2026-08-29)

Recorded verbatim in substance. These are the ticket's premises; do not re-derive them from
guesswork about how other providers behave.

1. **Inbound IS supported**, for NZ and Australia.
2. **The sending number is auto-allocated** — a shortcode for NZ mobiles, an Australian
   mobile number for AU. A dedicated shortcode is purchasable if needed.
3. **The MO webhook contract is documented** at
   `https://www.tnz.co.nz/Docs/RESTAPI/?version=2.04#receive-webhook`. It is **distinct from
   the delivery-receipt callback format** — do not assume one shape covers both.
4. **Authentication is a shared secret.** Headers `X-Timestamp`, `X-Sender`, `Authorization`,
   plus `Sender` and `APIKey` repeated in the JSON body. Configured in the TNZ dashboard
   under **Users > API User > API > Reporting**.
5. **TNZ detect opt-out keywords themselves** and add the number to their own opt-out list.
   Subsequent sends fail with `Destination is blacklisted`. **The full message is still
   forwarded to the webhook.**

Answer 5 is what makes this a sync ticket rather than a compliance ticket. Answer 3 is what
makes "point the existing handler at TNZ" wrong. Answer 2 is what makes attribution hard —
see *Flags*.

## Signal

**Expected**

A guest texts STOP. TNZ blacklists the number and forwards the message to Gather's MO
webhook. Gather authenticates the request, resolves which person and which event the reply
belongs to, writes the `SmsOptOut` row and sets `Person.smsOptedOut`, and logs
`SMS_OPT_OUT_RECEIVED`. The host's invite-status view stops counting that guest as
awaitable; the scheduler stops queueing nudges at them.

**Actual**

`POST` in `src/app/api/sms/inbound/route.ts` is a Twilio webhook handler. It parses
`multipart`/`x-www-form-urlencoded` `From` / `Body` / `MessageSid`, performs no
authentication of any kind, and returns `200 OK` to everything including its own catch
block. TNZ will not send it a form-encoded body, will not use those field names, and will
present a header-plus-body shared secret it does not look for. Nothing in the file is
reachable from a TNZ request.

**Smallest failing case**

An AU guest texts STOP. Even if the handler spoke TNZ's format, `normalizePhoneNumber`
returns `null` for `+61412345678` and the handler returns `200 OK` having done nothing.

## Audit at `1cbf014`

### A. What `src/app/api/sms/inbound/route.ts` does today

`POST` runs, in order:

1. `await request.formData()` — reads `From`, `Body`, `MessageSid`.
2. Missing `From` or `Body` → `200 OK`, no action.
3. `normalizePhoneNumber(from)`; `null` → `200 OK`, no action.
4. `isOptOutMessage(body)` from `src/lib/sms/opt-out-keywords.ts` — exact match, trimmed
   and case-folded, against `OPT_OUT_KEYWORDS` (`stop`, `stopall`, `unsubscribe`, `cancel`,
   `end`, `quit`). Non-match → `200 OK`, **message discarded**. There is no storage of
   inbound messages, no reply handling, nothing else consumes an inbound SMS.
5. **Attribution:** `prisma.inviteEvent.findFirst` for the most recent `NUDGE_SENT_AUTO`
   whose `metadata.phoneNumber` equals the normalised number, `orderBy createdAt desc`,
   including the event's `id`, `hostId`, `host.name`. No match → `200 OK`, no action.
6. Finds the `Person` with that `phoneNumber` who is a member of that event.
7. `prisma.smsOptOut.upsert` on `phoneNumber_hostId`, storing `rawMessage`.
8. If a person was found, sets `Person.smsOptedOut` / `smsOptedOutAt`.
9. `logInviteEvent` with type `SMS_OPT_OUT_RECEIVED`.

`GET` returns `200` with the string `SMS webhook endpoint`.

**Authentication: none.** There is no signature check, no shared secret, no allowlist. The
route is not in `middleware.ts`'s `config.matcher` (which covers only `/p/`, `/h/`, `/c/`,
`/api/p/`, `/api/c/`). Anyone who can reach the URL can post a form body and opt an
arbitrary number out of an arbitrary host's sends — provided a matching `NUDGE_SENT_AUTO`
event exists. It is unauthenticated write access to a Do-Not-Touch Zone 7 table.

[[GTC-214]] Ruling 1 is the reason there is no half-measure here: `validateTwilioSignature`
was **deleted, not wired**, and the comment left in `src/lib/sms/twilio-client.ts` says so
and says why. Do not restore it from history.

**Every path returns `200`, including the catch block.** With Twilio that suppressed
retries. With TNZ it means a handler that throws on every request is indistinguishable from
one that works, from TNZ's side and from ours — there is no error signal anywhere except a
`console.error`.

**Also of note:** `/api/sms/inbound` is absent from `route-classifications.json`. That file
holds 79 entries against 102 `route.ts` files under `src/app/api`, so 28 routes are
unclassified and this is one of them. **The absence is staleness, not a ruling** — do not
cite it as evidence the route was assessed and found to need no auth.

### B. Is it Twilio-shaped? Yes. What would have to change

Twilio-shaped in five respects, each of which has to change:

| Today (Twilio) | Required (TNZ) |
|---|---|
| `request.formData()` | JSON body per the MO webhook contract (answer 3) |
| Fields `From`, `Body`, `MessageSid` | TNZ's MO field names — **read the doc, do not guess** |
| No authentication | Verify `X-Timestamp`, `X-Sender`, `Authorization` headers **and** the `Sender` / `APIKey` body fields against the stored shared secret (answer 4) |
| `200` on every path incl. catch | A real status contract per TNZ's retry semantics; a thrown handler must not read as success |
| Doc comment: *"Webhook endpoint for inbound SMS messages from Twilio"* | Accurate, and citing the doc URL |

Two further changes are not format changes but are required by the same rewrite:

- **The `GET` handler** exists for "Twilio's webhook validation". Whether TNZ needs a `GET`
  at all is a question for the doc. If not, delete it rather than leave an unauthenticated
  endpoint answering `200`.
- **Message retention.** Answer 5 says the full message is forwarded even when TNZ has
  already actioned the keyword. Today a non-keyword body is discarded at step 4. Whether
  Gather stores inbound messages is a product question this ticket must *raise*, not settle
  — see *Unknowns*.

**Note the direction of travel.** Because TNZ blacklist at their layer, the handler's
keyword matching is no longer the thing that stops the send. `isOptOutMessage` becomes
Gather's *interpretation* of a message TNZ has already acted on. If the two disagree —
Gather's list is six exact keywords; TNZ's list is theirs and is not documented here — TNZ's
decision wins on delivery and Gather's local state is wrong in whichever direction they
diverge. That divergence is a recorded unknown, not something to paper over by widening
`OPT_OUT_KEYWORDS`.

### C. The phone normaliser — the earlier finding is confirmed at HEAD, and it is worse

`normalizePhoneNumber` in `src/lib/phone.ts` validates through `isValidNZNumber`, whose
pattern is `/^\+64\d{8,10}$/`. Anything not `+64` returns `null`. Measured at `1cbf014`:

| Input | `normalizePhoneNumber` | Note |
|---|---|---|
| `+64211234567` | `+64211234567` | correct |
| `021 123 4567` | `+64211234567` | correct |
| `+61412345678` | `null` | **AU E.164 rejected** |
| `+61 412 345 678` | `null` | AU rejected |
| `61412345678` | `null` | AU rejected |
| `0412345678` | `+64412345678` | **AU local format silently mangled into a bogus NZ number** |

The mangling is the sharper of the two: the leading-`0` branch prepends `+64` before any
validation, so an Australian local-format number does not fail, it becomes a different,
wrong, valid-looking NZ number.

**Why this matters here.** TNZ deliver to AU (answer 1) on an Australian mobile number
(answer 2). `TNZ_COUNTRY_CODES` in `src/lib/sms/send-sms.ts` is `['+64', '+61']`, and
`findDecideByFollowupCandidates` in `src/lib/sms/decide-by-eligibility.ts` deliberately does
**not** call `isValidNZNumber` precisely so `+61` numbers are admitted — its own comment
records this. So Gather sends to AU, and the inbound handler cannot process an AU reply:
step 3 returns `null` and the STOP is dropped on the floor.

Widening the normaliser is **not** in this ticket's scope, and must not be done casually.
`normalizePhoneNumber` has 13 call sites across people, households, contact-info, CSV import
and `reconcileMembers`, plus assertions in `tests/sms-infrastructure-test.ts` and
`tests/moment1-input-test.ts` that pin the current behaviour (`'Non-NZ number returns null'`).
Changing it changes what gets written to `Person.phoneNumber` everywhere. The handler must
therefore either normalise defensively for its own lookup or take TNZ's `From` as already
E.164 — a decision the executor makes with the doc in hand. **File the widening as its own
ticket if it proves necessary.**

### D. How `SmsOptOut` is written today, and by what

The model (`prisma/schema.prisma`): `phoneNumber`, `hostId`, `optedOutAt`, `rawMessage`,
`host` relation to `Person` with `onDelete: Cascade`, unique on `[phoneNumber, hostId]`.
**Opt-out is scoped per host, not per account and not per event.**

**Two production writers, both `upsert`, and neither is reachable in normal operation:**

1. `POST` in `src/app/api/sms/inbound/route.ts` — the handler audited above. Reachable only
   from a Twilio-shaped request, which nothing sends. **Effectively dead.**
2. `manualOptOut` in `src/lib/sms/opt-out-service.ts` — writes `rawMessage: reason || 'Manual
   opt-out'`. **Zero callers.** A repo-wide grep for `manualOptOut` returns only its own
   definition. There is no host-facing UI or API route that opts a number out by hand.

`removeOptOut` in the same file is the only deleter, and likewise has **zero callers**.

**Everything else reads.** `isOptedOut` (called by `nudge-eligibility.ts` and
`proxy-nudge-eligibility.ts`, re-exported by `decide-by-eligibility.ts`),
`getOptOutStatuses` (invite-status), `checkOptOut` and `checkOptOutBatch` in
`src/lib/sms/send-sms.ts`, and direct `findUnique` / `findFirst` reads in the per-person
nudge route and the invite-detail route.

**Conclusion: in production today, nothing writes `SmsOptOut`.** Every consumer reads a table
that only tests populate. `Person.smsOptedOut` is the same story — the inbound handler is its
only writer, while `wrap-up.ts` and `chooseManualNudgeChannel` in
`src/lib/sms/manual-nudge-recipient.ts` gate on it and `PersonInviteDetailModal` displays it.
This ticket is what makes the read side mean something.

## Flags — report, do not solve

These are named so they are not discovered mid-execution and quietly absorbed. If any
becomes load-bearing, **stop** (Stop Condition 5).

### F1 — the shared shortcode: how does a reply find its person and event?

TNZ auto-allocate the sending number (answer 2). A shortcode is **shared**: replies from
every host's guests arrive on one number. The inbound request therefore carries the guest's
number and, at best, Gather's own — it cannot carry which host was being replied to.

**How attribution works today.** Step 5 above: the most recent `NUDGE_SENT_AUTO` InviteEvent
whose `metadata.phoneNumber` matches, newest first. `sendSms` writes that metadata on every
successful send (`messageId`, `provider`, `phoneNumber`, `messageLength`), and the comment at
the top of `src/lib/sms/decide-by-sender.ts` names this as the reason every send must go
through `sendSms` rather than a bespoke path.

**Is there anything else? No.** That heuristic is the only person-and-event resolution
mechanism in the codebase for an inbound message. It has four properties the executor must
weigh with the doc in hand:

- **Newest-wins.** A guest invited to two events by two hosts who replies STOP opts out of
  whichever host messaged most recently. The other host keeps sending — from Gather's point
  of view. TNZ, meanwhile, has blacklisted the number account-wide (F3).
- **It depends on a successful prior send.** `NUDGE_SENT_AUTO` is written in the success
  branch of `sendSms` only. A guest who replies STOP to an *invite* rather than a *nudge*,
  or whose nudge send failed, has no matching row and the handler returns `200` and does
  nothing.
- **It is a JSON-path query on an audit log.** `InviteEvent.metadata` is a JSONB column
  serving as the attribution index for inbound SMS. It is indexed for neither the type nor
  the path being queried.
- **It cannot distinguish a person from a household's shared phone.** Step 6 takes the
  *first* `Person` with that number in that event.

**Not this ticket's to fix.** Report the mechanism, its limits, and whether TNZ's MO payload
carries anything better — a message reference tying the reply to a specific outbound send
would change the answer completely. If it does, that is a new ticket, not a widening of this
one.

### F2 — storing a new shared secret

Answer 4 requires a credential Gather does not have. `TNZ_AUTH_TOKEN` is the outbound Basic
token used by `sendViaTnz`; the MO secret is separate, configured elsewhere in the TNZ
dashboard (Users > API User > API > Reporting), and comprises a `Sender` identity plus an
`APIKey`.

Open, not decided here: how many env vars; naming; whether the `X-Timestamp` header implies a
replay window Gather must enforce and how much clock skew it tolerates; whether the body
`APIKey` and the header `Authorization` are the same secret in two places or two secrets;
what happens on a mismatch (`401` vs silent `200`) and what TNZ do with a `401`.

Note the local precedent and its known weakness: the three cron routes use
`if (CRON_SECRET && providedSecret !== CRON_SECRET)`, so an **unset secret leaves the route
open**. `src/app/api/cron/decide-by-followups/route.ts` documents this as deliberately copied
rather than diverged from, so the fix lands in one ticket — that ticket is [[GTC-220]].
**Do not reproduce that shape here.** An unset MO secret must fail closed. If that argues for
pulling [[GTC-220]] forward, say so and stop; do not fix it in passing.

### F3 — TNZ's blacklist is account-wide; `SmsOptOut` is per-host

TNZ add the number to **their** opt-out list, which belongs to Gather's TNZ account. Gather's
`SmsOptOut` is unique on `[phoneNumber, hostId]`. These are different scopes, and the
mismatch is structural, not a bug in either.

Consequence: a guest who STOPs host A is blacklisted at TNZ for host B's sends too. Gather
will record the opt-out against A, keep showing the guest as reachable for B, and every B
send will fail with `Destination is blacklisted`. Writing one host's row does not make local
state true; it makes it *less* wrong.

Surfaced here because it bears directly on what a correct sync looks like, and because it is
a product decision — does an opt-out in Gather mean "not from this host" or "not from
Gather"? — that this ticket must not make silently by choosing an implementation.

## Unknowns

Four are recorded. **The first is blocking and must be resolved from TNZ's documentation
before any code is written** (Stop Condition 8).

1. **The MO payload shape itself.** Field names, whether `From` arrives as E.164 or local,
   the exact header/body verification order, TNZ's expected response status and their retry
   behaviour on a non-2xx. **Read `https://www.tnz.co.nz/Docs/RESTAPI/?version=2.04#receive-webhook`
   first.** Answer 3 warns it is a different contract from the delivery-receipt callback;
   do not read one and implement the other.
2. **TNZ's keyword list vs Gather's.** `OPT_OUT_KEYWORDS` is six exact, case-folded matches.
   TNZ's list is theirs and is not stated. Where they diverge, TNZ's decision governs
   delivery and Gather's local state is wrong in whichever direction. Do not resolve this by
   widening `OPT_OUT_KEYWORDS` on a guess.
3. **How a blacklisted send actually fails.** `sendViaTnz` treats **any** 2xx as success and
   only tries to parse a `MessageID`. If TNZ signal `Destination is blacklisted` as a 2xx
   with a per-destination error in the body rather than as a non-2xx, `sendSms` logs
   `NUDGE_SENT_AUTO` — **a send recorded as delivered that was never sent**, which would also
   corrupt the F1 attribution index. Worth confirming while the TNZ conversation is open. It
   is `sendViaTnz`'s defect, not this handler's; file it separately if confirmed.
4. **Whether Gather stores inbound messages at all.** Answer 5 says the full message is
   forwarded regardless. Today non-keyword bodies are discarded. Storing guest replies is a
   product and privacy decision with no schema for it — raise it, do not decide it.
