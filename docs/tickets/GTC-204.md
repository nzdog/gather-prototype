## What this ticket does

Epic A (GTC-167 → GTC-202, landed in GTC-200) exercised three practices that aren't yet written
down anywhere a future session would find them before reinventing — or skipping — them: how an
experiment branch actually gets merged (as opposed to built), how a RED state is produced when the
change is a contract replacement rather than a bug, and a naming for the principle that made the
epic's ledger trustworthy in the first place. This ticket adds all three to the skill library, each
pointing at its worked example rather than restating it (`gather-docs-and-writing`'s own rule: the
skills point at the exemplars, they don't replace them).

## Additions

### 1. `gather-change-control` — the experiment-branch merge protocol

New subsection `### The merge protocol (landing an experiment branch)`, appended to the end of the
existing `## The experiment-branch pattern` section (immediately before `## What gates a commit`) —
placed there because it is explicitly the landing half of the pattern already documented above it,
not a separate concern.

Encodes, in order: cold session as reviewer; every gate re-run before reading a line of diff; the
diff read against the governing plan section by section (not file by file); STOP before the first
pick on any unruled divergence; corrections land on the experiment branch as their own ticket,
never mid-merge; gate suite re-run after every pick, checked against each ticket's own recorded
numbers; a byte-identical diff against the experiment tip as the proof (stronger than "zero
conflicts"); the history branch pushed whole and never deleted, with closed tickets kept citing
their experiment-branch hashes rather than being rewritten to trunk hashes.

Worked example cited throughout: **GTC-200** (the merge itself — cold-session review, 87-file diff
read against the A1 plan, byte-identical `git diff experiment/send-lock-ledger HEAD`, chronological
pick-order correction, `experiment/send-lock-ledger` left intact) and **GTC-202** (the two
merge-blocking corrections GTC-200's review forced — proof that "STOP before the first pick" and
"corrections land on the experiment branch" are not hypothetical steps).

### 2. `gather-validation-and-evidence` — RED-first for contract replacement

New subsection `### 3a. RED-first for contract replacement (distinct from bug-RED)`, inserted
between `## 3. The security suite is a contract` and `## 4. Cleanup discipline for DB tests`.

States the inversion explicitly: bug-RED writes a test pinning wrong behaviour and watches it fail
against the current (wrong) code; contract-replacement RED rewrites the assertions to the **new**
contract first and runs them against the **unchanged** code — proving the new assertions actually
distinguish old behaviour from new, before any implementation changes. Sequence: rewrite assertions
→ RED against unchanged code, recorded in its own commit → migrate to GREEN → never fewer tests
than before → for protected (do-not-touch) zones, equal-strength is a ruling obtained explicitly,
not inferred.

Worked example: **GTC-169**'s commit `8d799a4` (security suite rewritten to the send-lock contract,
run against unmigrated code: 38 tests, 29 passed, 9 failed — nine real violations the old suite
couldn't see) migrated to GREEN in `794e0ff` (38/38), suite size 16 → 38 with every removed
assertion replaced at named equal strength.

### 3. `gather-architecture-contract` — the single-definition principle

New `## 11. Single definition — screens consume the server's predicates, never reimplement them`,
appended after section 10 (Known weak points) and before Provenance and maintenance — a new
top-level section rather than a renumber, so no existing section reference in other tickets/skills
shifts.

States the principle (one server-owned definition per predicate; every consumer imports it, never
re-derives it) and why a reimplementation is dangerous (it passes every test on day one, by
construction, and then drifts silently the first time the owning rule changes — the same failure
shape as the FROZEN/`canFreeze()` divergence, GTC-154). Cites `whyTrigger()`/`touchesSomeone()`
(`src/lib/ledger.ts`) and `toLifecycleEvent()` (`src/lib/lifecycle.ts`) as the enforced instances,
and `ReasonPrompt.tsx`'s `useReasonPrompt().ask()` (GTC-202) as the concrete screen that imports
rather than reimplements.

## The §5 rewrite decision

The ticket brief flagged that `gather-architecture-contract` §5 (the EventStatus/FROZEN state
machine) is owed a full rewrite post-Epic-A per GTC-166's original note, and left the choice open:
do it now if it keeps the skill coherent, or add the new principle and leave §5 flagged if a full
rewrite would balloon this ticket.

**Chosen: flag it, don't rewrite it here.** Section 5 currently carries the same level of rigor a
rewrite would need to match — a transition table, the full `canMutate` matrix, gate-by-gate history,
and its own re-verification grep commands. Producing an equivalent for the send-lock/ledger model
means reading `src/lib/lifecycle.ts` and `src/lib/ledger.ts` in full and re-deriving the whole state
model (phases, the ledger's write path, `whyTrigger`'s five triggers, the nudge-predicate inversion)
to the same standard — that is Epic-A-sized verification work in its own right, not a paragraph, and
would have more than doubled this ticket's scope. Section 11 (above) adds the cross-cutting
principle Epic A established now, states plainly that §5 describes the pre-Epic-A model, and leaves
the content rewrite as explicit follow-up work rather than silently stale or silently patched.
