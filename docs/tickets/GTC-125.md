# GTC-125 — Persist plan item order via `Item.displayOrder` — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** de0b31d

### What was found

- GTC-124 left item reorder as UI-only (no `Item.displayOrder` column). On reload, items reverted to creation order.
- `Team.displayOrder` already exists and is populated; `Item` had no comparable column.
- `GET /api/events/[id]/items` sorted by `critical desc, team.name asc, name asc`. `GET /api/events/[id]/teams/[teamId]/items` sorted by `critical desc, name asc`. Neither respected a per-user order.
- 486 items across 62 teams in the current dev database — all needing backfill.

### What was changed

**Schema + migration:**

- Added `displayOrder Int?` to `Item` in `prisma/schema.prisma`, plus composite index `@@index([teamId, displayOrder])` for efficient sorted reads within a team.
- Migration `20260418093439_add_item_display_order` contains:
  1. `ALTER TABLE "Item" ADD COLUMN "displayOrder" INTEGER;`
  2. Backfill via `ROW_NUMBER() OVER (PARTITION BY "teamId" ORDER BY "createdAt" ASC)` — single atomic SQL statement, runs as part of `prisma migrate dev`.
  3. `CREATE INDEX "Item_teamId_displayOrder_idx"`.

**Backfill verification script:** `tests/verify-item-display-order.ts` — counts nulls overall and per team, exits non-zero if any remain. Executed post-migration: 486 items, 0 nulls, all 62 teams clean.

**API — additive, back-compat:**

- `PATCH /api/events/[id]/items/[itemId]` — accepts optional `displayOrder`. Intentionally **not** in the substantive-fields check, so a pure reorder does not flip `source='GENERATED' → 'HOST_EDITED'`.
- `POST /api/events/[id]/teams/[teamId]/items` — computes `max(displayOrder) + 1` within the team and sets it on the new item so "+ Add item" places new entries at end-of-category.
- `POST /api/events/[id]/finalize-plan` — when persisting generated items, seeds `displayOrder` sequentially per category, starting at `max(existing) + 1` so re-running finalize-plan appends cleanly without colliding with prior batches.
- `GET /api/events/[id]/items` — ordered by `team.name asc, displayOrder asc, createdAt asc`. (Team grouping preserved; `critical desc` dropped to honour user-set ordering within a team.)
- `GET /api/events/[id]/teams/[teamId]/items` — ordered by `displayOrder asc, createdAt asc`.

**Client:**

- `Moment2PlanView.PlanItem` gained optional `displayOrder?: number` so the parent can swap values on reorder.
- `mapTeamsAndItemsToPlanCategories` now sorts each team's items by `displayOrder asc` defensively (belt-and-braces vs. the API sort) and carries `displayOrder` through to the mapped item.
- `onAddItem` handler now reads `createdItem.displayOrder` from the POST response and stores it locally.
- `onReorderItem` handler (the behaviour change this ticket exists to deliver): locates the moved item and its adjacent swap target, performs an optimistic local swap that exchanges both items' `displayOrder` values, then fires **two parallel `PATCH`** calls to persist the swap. If either side has no `displayOrder` (shouldn't happen post-backfill but guarded), falls back to renumbering the whole category sequentially.

### Known limitations

- **Swap only, within a single category.** Up/down arrows move by one position; cross-category moves are out of scope (GTC-124 constraint preserved).
- **Last-write-wins under concurrent reorder.** Two clients reordering simultaneously could interleave `PATCH`es and end up in a surprising order. Gather is a single-host app today — flagged for revisit if multi-host editing ever ships.
- **Two round-trips per reorder.** A single batch endpoint (`POST /teams/:id/items/reorder` with an ID array) would be atomic and lower-chatter. Deferred per the ticket's "implementer's call based on slow-network risk" note — parallel `PATCH`es are within the same team and won't reorder each other in practice.
- **`displayOrder` stays nullable.** Tightening to non-null is a follow-up once new writes are confirmed to set it reliably (per ticket suggestion).
- **`critical desc` dropped from `GET /items`.** Previously critical items floated to the top of each team; now they stay in whatever position the user placed them. Intentional — honours user ordering.
