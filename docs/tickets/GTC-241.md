# GTC-241 — Script-seed test events cleanup / reset — CLOSED

**Status:** Closed | **Effort:** Low (dev ergonomics, small surface, no schema, no user-facing changes)

*Note: this ticket was originally numbered GTC-237. That number was already claimed by an
unrelated, substantive stub (`finalize-plan` rerun cascade-destroys host-edited items,
filed during GTC-236) — surfaced and confirmed with the founder before starting. Renumbered
to GTC-241 (next free ticket number); the GTC-237 stub is untouched.*

## Signal

Surfaced by the GTC-137 verification session: `scripts/seed-gtc-133-test-event.ts`
accumulates events with no reset flag. Every run creates another test event; no way to
clean up without manual DB action.

**Expected:** Testing workflow supports repeated seeding cycles cleanly — a `--reset` flag
(or companion cleanup script) that removes previously-seeded events before/after seeding.

**Actual (pre-fix):** every run created another persisted event with no cleanup, cluttering
the dev DB with orphan test events over time.

## Phase 1 — Audit (scripts/seed-gtc-133-test-event.ts)

- **Entities created per run:** `User` (find-or-create by email, not per-run), host `Person`,
  one `Event` (fixed `name: 'GTC-133 Sub-commit (g) Test'`), one `EventRole` (HOST), 6
  `Household` rows, 11 `PersonEvent` rows. Household members without an email get a fresh
  `Person` row created each run (no dedup key for them).
- **Distinguishing marker:** only the hardcoded `Event.name` string — no tag/source field.
  Reliable enough to filter on for deletion.
- **Existing cleanup logic:** none.
- **Cascade check (`prisma/schema.prisma`):** `Household.event`, `PersonEvent.event`,
  `EventRole.event`, `Team.event`, `EventSetup.event` are all `onDelete: Cascade` — no
  `Restrict` relations found on this chain, so deleting the `Event` row cleanly removes all
  dependent rows in one call. `Person` rows are not owned by `Event` (shared across events by
  email lookup) and are intentionally left alone by the reset.
- **Other scripts convention:** `scripts/create-test-event.ts` has an ad hoc inline
  delete-by-known-emails cleanup, not a reusable `--reset` pattern; no existing `--reset`-flag
  convention elsewhere in `scripts/` to match.
- **Landmine found:** one of the events matching the name filter,
  `cmsttnrkj00011ydrkn3jfvue`, is not an accumulated duplicate — it's the `SETUP_DONOR_EVENT`
  hardcoded in `scripts/seed-gtc236-test-event.ts:17`, a standing fixture with a real,
  hand-walked-through `EventSetup` (used to give GTC-236's script-created fixtures realistic
  setup data, since UI event creation is Stripe-gated per GTC-233). It shares the seed
  script's default name only because it originated from an earlier run of this same script
  before being repurposed. A name-only `--reset` filter would have silently deleted it and
  broken `seed-gtc236-test-event.ts`. Surfaced to the founder before implementing; resolved by
  explicit ID exclusion (see Phase 3).

## Phase 2 — Design (confirmed)

**Option A** (recommended and chosen): `--reset` flag on the existing seed script. Bare
invocation unchanged (adds an event, no deletion). `--reset` deletes prior seeded events by
name marker (cascading to Household/PersonEvent/EventRole/EventSetup), reports what was
deleted, then seeds fresh.

## Phase 3 — Implementation

`scripts/seed-gtc-133-test-event.ts`:
- Added `EVENT_NAME` constant (previously an inline string, now shared with the reset query).
- Added `resetSeededEvents()`, invoked when `--reset` is passed: finds and deletes `Event`
  rows named `EVENT_NAME`, excluding `RESET_EXCLUDE_IDS`, and reports the count and IDs
  deleted.
- Added `RESET_EXCLUDE_IDS = ['cmsttnrkj00011ydrkn3jfvue']` — the GTC-236 setup-donor fixture
  — with a comment pointing at `scripts/seed-gtc236-test-event.ts:17` as the dependent.
- No FK-restrict handling needed (Phase 1 audit found none on this chain).

## Phase 4 — Verification

- `npx tsx scripts/seed-gtc-133-test-event.ts` run twice: two events created, no errors.
- `npx tsx scripts/seed-gtc-133-test-event.ts --reset` run against a DB with 4 events named
  `'GTC-133 Sub-commit (g) Test'` (3 accumulated duplicates + the donor): deleted exactly the
  3 duplicates, left the donor (`cmsttnrkj00011ydrkn3jfvue`) untouched, then seeded 1 fresh
  event. Verified via `psql`: 0 orphan `Household`/`PersonEvent`/`EventRole` rows for the
  deleted event IDs.
- `--reset` run a second time immediately after: deleted exactly the 1 event from the
  previous run, donor still untouched — confirms repeatable cycles.
- Final DB state left with exactly 2 events named `'GTC-133 Sub-commit (g) Test'`: the donor
  and one freshly-seeded event.
- Not tested: `Team`/`Item`/`Assignment` cascade paths (this script creates none, so they were
  not exercised — the schema audit in Phase 1 confirms `Team.event` and `Item.team` are also
  `onDelete: Cascade`, consistent with the tested paths).
