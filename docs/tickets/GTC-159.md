# GTC-159 — Household edit silently destroys non-primary member state

> V1/V2 reconciliation campaign — Phase 1 (household data-loss fix).
> Authoritative behaviour established from source (see §Root Cause), not from

## 1. Title and Bug Signal Lock

**Title:** `Plan/Events: editing a household silently wipes non-primary members' team, RSVP and nudge state`

**Expected**
- UI: editing a household (e.g. changing the primary contact's phone) leaves every other member's team assignment, RSVP state and nudge history intact.
- Invariant: a `PUT` that does not change household membership performs zero `PersonEvent` deletions/creations; existing rows are updated in place.

**Actual**
- UI: after any household edit, non-primary members drop off their teams, RSVP resets to PENDING, and (for no-email members) duplicate Person rows accumulate — all with no error shown.
- Invariant: `PUT` deletes every non-primary `PersonEvent` and recreates it, so `teamId`/`rsvp*` are lost, `NudgeLog` cascades away, and `PersonEvent.id`s churn.

**Impact**
- Role: [x] Host [x] Coordinator (assignments break) — All non-primary members affected
- Platform: [x] All
- Environment: [x] Both
- Visibility: [x] Silent failure (PersonEvent count is unchanged — delete N, create N)

**Severity:** [x] High — degrades a core flow (Plan Creation / RSVP-Assignment), silent data loss, workaround is "don't edit households after assigning".

**Smallest Failing Case**
1. [System] Seed an event with a household containing a non-primary member (e.g. Matt, no email); give that member a `teamId` and a `NudgeLog` row.
2. [Host] Enter Moment 1 (`?setup=true`), edit that household, change the primary phone, save (issues `PUT .../households/[householdId]`).
Observe: the non-primary member now has a NEW `PersonEvent.id`, `teamId = null`, `rsvpStatus = PENDING`; the `NudgeLog` row is gone; a duplicate `Person` exists for Matt.

## 5. Ticket Output Contract

### Plan (Executor-Proposed)

**Hypothesis (proven by source read, pending RED):** `PUT` deletes all non-primary
`PersonEvent` rows (`personEvent.deleteMany`) *before* `createMember` runs, so the
`(personId,eventId)` upsert branch already present in `createMember` never matches
— it always falls through to `create`, dropping `teamId`/rsvp and (for no-email
members) minting a new `Person`. `NudgeLog` is lost via `onDelete: Cascade` on the
delete. Root cause is the delete-then-recreate *ordering*, not a missing upsert.

**Minimal Change Set:** reconcile non-primary members by a client-supplied stable
identity (`personEventId`): update matched rows in place, create only genuinely
new members, delete only members actually removed. Remove the blanket
`deleteMany`. Extract this into a testable function.

**Test Strategy:** DB-level tsx regression test (house pattern, à la
`verify-personevent-team-setnull.ts`) targeting the extracted function; RED before
fix, GREEN after; wired as `npm run test:household-edit`.

**Rollback Risk:** client/server payload contract change — if an old client omits
`personEventId`, members are matched by email where possible and otherwise treated
as new; a no-id, no-email member would still be recreated (documented limitation,
mitigated because client+server ship together). The extraction is behaviour-
preserving and guarded by the RED baseline.
