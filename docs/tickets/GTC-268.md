## The sentence that sets the severity

The gate has never failed, and it cannot. Not "it has not found anything
lately" — it is structurally incapable of returning a non-zero exit code
against the file it reads. Its four rules all filter on the contents of a
`securityIssues` string array, and that array is **empty on all 81
entries**. The one rule that does not depend on it looks for
`authType === 'WEAK_PARAM'`, a value **no entry carries**. There is no
edit to the codebase that makes this gate red. There is only an edit to
the JSON.

Meanwhile the same file records eleven routes as `"authType": "NONE"`
with `"authEvidence": []`, and the gate prints
`✓ SECURITY GATE PASSED`. Seven of those eleven were among the nine holes
[[GTC-267]] closed. **The gate was not blind to that exposure. It had it
written down, and passed anyway.**

## Signal

**Expected**
A security gate named in a Do-Not-Touch Zone as *"the security contract
for the API surface"* reads the API surface, determines per exported
method whether a credential is checked before any work is done, and exits
non-zero when one is not.

**Actual**
It opens exactly one file — `route-classifications.json` — and filters
hand-written English strings inside it. It never opens a `.ts` route file.
It has no npm script. Its failure text instructs you to re-run a generator
deleted eighteen months ago and an npm script that has never existed. Its
sibling, `scripts/triage-unknown-routes.ts`, reads a markdown file from a
path it no longer occupies, prints one line of error, and exits 1.

**Smallest failing case**
Delete every guard from every route in the tree, change nothing else, and
run the gate. It prints `✓ SECURITY GATE PASSED` and exits 0.

## What a real scanner would have to parse

The routes are TypeScript. The question a gate must answer is **not**
"does the word `requireEventRole` appear in this file" — that is what
`authEvidence` records today. It is:

> For each exported HTTP method handler, does **every** path from entry to
> a non-refusal response pass a credential check?

That is a reachability property over the control-flow graph of one
function. Stated honestly, here is what it costs.

**What is tractable, and was measured.** A TypeScript AST walk over all
106 route files, resolving exported `GET`/`POST`/`PATCH`/`PUT`/`DELETE`
declarations and scanning each body for guard calls, **runs in 0.20
seconds** and needs no database and no server. `typescript@5.9.3` is
already a devDependency; nothing new is installed. It correctly finds all
134 handlers where the JSON finds 81 files.

**It was controlled, not assumed.** The scan was run against `298b62d`
— the commit before [[GTC-267]]'s fix, where the answer is independently
known — and against HEAD:

```
pre-fix unguarded handlers: 32      HEAD unguarded handlers: 23

CLOSED between the two (10):
  GET /events/[id]/route.ts              GET /events/[id]/items/route.ts
  GET /events/[id]/summary/route.ts      GET /events/[id]/days/route.ts
  GET /events/[id]/conflicts/route.ts    GET /events/[id]/conflicts/dismissed/route.ts
  GET /events/[id]/conflicts/[conflictId]/route.ts
  GET /events/[id]/revisions/route.ts    GET /events/[id]/revisions/[revisionId]/route.ts
  GET /events/[id]/tokens/route.ts

NEWLY unguarded at HEAD (1):
  GET /events/[id]/clone-source/route.ts
```

Exactly [[GTC-267]]'s nine, plus `tokens` whose `?hostId=` branch it
removed, minus the one deliberately-public route it added. A scan that
reported these correctly in both directions is a scan with a control
under it. **A gate whose first run cannot reproduce a known past finding
should not be trusted on a new one**, so this control belongs in the
tool's own test.

### The cases that are hard — stated honestly

**A guard called inside a helper.** Real, and already in the tree.
`handleRequest` in `src/app/api/cron/wrap-up-dispatch/route.ts` and in
`src/app/api/cron/decide-by-followups/route.ts` holds the entire secret
check; the exported `GET` and `POST` are two lines each that call it.
`POST` in `src/app/api/cron/nudges/route.ts` is worse — it delegates to
the exported `GET`. A body-local scan reports all six as unguarded. The
fix is a call-graph walk with a depth bound; one level catches every
instance in the tree today, but the bound is a real limitation and must be
declared, not hidden. **A helper imported from `src/lib/` would defeat a
file-local walk entirely.** There are no such cases today. There is
nothing stopping one tomorrow.

**A guard behind a conditional.** Real, and correct where it occurs.
`GET` in `src/app/api/events/[id]/tokens/route.ts` reaches
`requireEventRole` only in the `else` of `if (token)`; the `if` branch is
itself a full credential check against `prisma.accessToken`. A naive
"guard must precede the first `prisma.` call" rule flags this route —
it was the **only** hit across 134 handlers, and it is a false positive.
So that rule is wrong and must not be shipped. The correct property is
per-path: **every** terminal path either passes a check or returns a
refusal. That needs branch enumeration, not statement ordering.

**A route whose credential is a token, not a session.** The largest
blind spot for any symbol-matching approach.
`POST` in `src/app/api/join/[token]/claim/route.ts` authenticates with:

```
const event = await prisma.event.findFirst({
  where: { sharedLinkToken: token, sharedLinkEnabled: true },
  ...
});
if (!event) {
  return NextResponse.json({ error: 'Invalid or disabled invite link' }, { status: 404 });
}
```

That is a real capability check on a real secret. It is also
**structurally identical to an ordinary lookup**. Nothing about the
syntax distinguishes `sharedLinkToken` from `name`. The same shape
appears in `POST /api/auth/verify` (`prisma.magicLink.findUnique`),
`GET /api/c/[token]/route.ts` (`prisma.accessToken.findFirst`) and the
bearer branch of `GET /api/events/[id]/tokens`. A scanner cannot infer
these; it can only be **told** which columns are credentials —
`sharedLinkToken`, `AccessToken.token`, `MagicLink.token`,
`Session.token` — and then recognise a lookup keyed on one followed by a
refusal. That list is a maintained input, which is the same category of
thing as `route-classifications.json`. The difference, and the only
difference that matters: it is four column names checked against
`prisma/schema.prisma`, not 81 hand-written verdicts.

**Can a regex do this? No.** Not the helper case, not the branch case, and
not the token case. A regex can tell you a symbol appears in a file; it
cannot tell you a function returns before reaching a database. That is
precisely the distance between `authEvidence: ["requireEventRole"]` and
`if (auth instanceof NextResponse) return auth;`.

**What can.** The TypeScript compiler API, already present, at 0.20s for
the whole tree — with three declared inputs rather than one hand-kept
ledger: the guard symbol list, the credential-column list, and the
allowlist below. Its limits (helper depth bound, no cross-file guard
resolution) are small, enumerable, and belong in its own README as
declared blind spots rather than being discovered later by a ticket.

### ⚠ `POST /api/demo/session` — FOUND HERE, THEN REMOVED FROM THIS TICKET

**Found by this investigation and not previously recorded anywhere.** `POST`

**FOUNDER RULING, 2026-09-11 — DELIBERATELY REMOVED FROM THIS TICKET'S
SCOPE AND FILED AS [[GTC-269]], TO BE FIXED BEFORE SLICE 2:**

> *"It is not a gate finding, it is a live auth bypass of the same class as
> GTC-267: no credential, and it mints a 30-day HOST session. GTC-267 closed

## The allowlist

A default-deny rule is only as honest as its exceptions. Below is the
proposed list: **every handler that is public on purpose, with the reason
it belongs.** 23 handlers carry no session or token guard at HEAD. Twelve
are proposed for the allowlist. **Eleven go on a separate list for the
founder to rule on** — this ticket does not decide them.

### Proposed allowlist — public by design (12)

- **`POST /api/auth/magic-link`** — the anonymous entry to the auth flow.
  Requiring a credential to request a credential is incoherent.
- **`POST /api/auth/verify`** — the credential is the magic-link token it
  consumes, checked via `prisma.magicLink.findUnique`.
- **`POST /api/auth/claim`** — anonymous claim request. Returns
  `{ ok: true }` on both "person not found" and "already claimed" to
  prevent enumeration, and rate-limits to 3 per email per 15 minutes.
  Both properties are in the code today and should become assertions.
- **`POST /api/auth/logout`** — acts only on the caller's own `session`
  cookie. Nothing to authorise.
- **`POST /api/billing/checkout`** — creates a Stripe Checkout session
  before any account exists. Payment precedes identity in this product.
- **`POST /api/events`** — the credential is `stripeSessionId`, retrieved
  from Stripe and refused unless `payment_status === 'paid'` (402). A
  verified third-party receipt, not a session.
- **`POST /api/webhooks/stripe`** — the credential is the
  `stripe-signature` header, verified by `stripe.webhooks.constructEvent`
  against `STRIPE_WEBHOOK_SECRET`; 400 on absence or mismatch. Zone 4.
- **`GET /api/events/[id]/clone-source`** — deliberately public, five
  fields, added by [[GTC-267]] with its reasoning in the file header:
  *"it can say nothing a guest invited to the source event does not
  already know, and it cannot name a person, an email, a token, or a
  payment."*
- **`POST /api/join/[token]/claim`** — the credential is the
  `sharedLinkToken` in the path, additionally requiring
  `sharedLinkEnabled: true` and an event in `CONFIRMING` or sent. A
  capability URL is authentication.
- **`GET /api/sms/inbound`** — returns the literal string
  `'SMS webhook endpoint'`. A health check with no data path.
- **`GET /api/templates/gather`** — curated `GATHER_CURATED` templates.
  No PII, no event data, no credential. Public catalogue.
- **`POST /api/events/[id]/households/[householdId]/claim`** — returns
  501 unconditionally; the body is a single `NextResponse.json`. No code
  path to reach. **Allowlisted as dead, not as safe** — if [[GTC-152]]'s
  successor ever revives it, the allowlist entry must be removed in the
  same commit. This is the kind of entry that rots; it should carry an
  expiry note.

### The fail list — NOT allowlisted (10, of which 6 now have a ticket)

**Founder ruling on the allowlist shape, 2026-09-11 — adopted:**

> *"Path, reason, non-session credential if any, and the open ticket that
> disputes it. The directory case makes the argument: intentionally
> unauthenticated and known-problematic must be sayable at once, or they
> cancel out. A bare list of paths is how route-classifications.json
> started."*

So every entry below names its dispute. Was eleven; `POST /api/demo/session`
came out to [[GTC-269]] by the ruling above.

- **`GET,POST /api/cron/nudges`**, **`GET,POST /api/cron/wrap-up-dispatch`**,
  **`GET,POST /api/cron/decide-by-followups`** (6 handlers) —
  **dispute: [[GTC-270]], filed 2026-09-11.** The fail-open
  `if (CRON_SECRET && ...)`: an unset variable disables the check silently.
  **Founder ruling, 2026-09-11: these are a hole and go on the fail list,
  not the allowlist** — *"a guard that guards nothing when it matters
  most."* All three are SMS senders, so an admitted caller spends real
  credit and puts real messages in guests' phones.
  `src/app/api/cron/decide-by-followups/route.ts` names this defect in its
  own header and promises *"the fix lands in one ticket"* — that ticket did
  not exist until now. **Not fixed here; [[GTC-270]] owns it.**
- **`POST /api/sms/inbound`** — **dispute: unfiled; needs a ticket.** No
  Twilio signature verification of any
  kind, recorded in [[GTC-267]]'s *"found in passing"*. It writes
  `SmsOptOut` rows, which is **Do-Not-Touch Zone 7** — opt-out state that
  *"must be respected in all nudge-sending code paths"* and whose bypass
  *"could constitute illegal sending"*. An unauthenticated writer of that
  table is a compliance question, not only a security one.
- **`POST /api/demo/reset`** — **dispute: unfiled; needs a ticket.** Gated
  on `NODE_ENV === 'production'` only;
  on any non-prod deploy it is an unauthenticated
  `prisma db push --force-reset`. Its own doc comment claims *"Requires
  authenticated user AND development environment"* and three lines below
  the code says *"No auth required for demo endpoint in development."*
  Recorded by [[GTC-267]]; unresolved.
- **`GET /api/demo/tokens`** — **dispute: unfiled; adjacent to
  [[GTC-262]].** Hands HOST, COORDINATOR and PARTICIPANT
  access tokens for the demo event to any caller. Same class as the
  directory below, narrowed to three named personas.
- **`GET /api/gather/[eventId]/directory`** — **dispute: [[GTC-262]],
  open.** Public by design and
  classified `PUBLIC` today**, and it is the sharpest illustration of why
  an allowlist entry is not a safety verdict. Its entire payload is people
  paired with access tokens and the URL prefix each token opens.
  [[GTC-256]] phase 3 removed the host's row from it — an exposure where
  one card signed the clicker in as the host — and deliberately did not
  widen. **[[GTC-262]] is open for exactly the same defect on COORDINATOR
  tokens.** So this route is simultaneously on the allowlist and the
  subject of an open High-severity ticket. An allowlist must be able to
  say "intentionally unauthenticated **and** known-problematic" without
  those two facts cancelling out.

**The shape, adopted.** An allowlist entry carries: the handler (method +
file), the reason, the non-session credential if it has one, and the open
ticket that disputes it. The directory is the case that forces the fourth
field — it is genuinely public by design **and** the subject of an open
High-severity ticket, and a list that cannot hold both facts at once will
quietly drop one of them.

**A note the scanner earned.** `GET /api/gather/[eventId]/directory`
selects `token` out of `AccessToken` in order to hand tokens to anonymous
callers. The scanner's first run read that as a credential check and
reported the route *protected by* the very column it gives away. That is
now fixed — detection reads only the `where` clause — and pinned by an
assertion, because **a tool that reads a credential vendor as a credential
checker is worse than no tool.**

## CI

**What runs today.** `.github/workflows/ci.yml`, on `pull_request` and on
`push` to `master`:

```
npm ci → npm run typecheck → npm run format:check
      → npx prisma generate → npx next build → npm audit --audit-level=high
```

`npm audit` carries `continue-on-error: true`. Also present:
`codeql.yml` (push/PR to master/main, plus weekly) and `claude-review.yml`
(PR only).

**It does fire on this branch, contrary to what the trigger list suggests.**
`master` has not moved since 2026-04-10 and the trunk is 309 commits
ahead — but **PR #41 is open** (`feat/moment-one-redesign` → `master`), so
`pull_request` fires on every push. Observed, not inferred:

```
$ gh run list --limit 3
success  ci               feat/moment-one-redesign  pull_request  1m56s  2026-09-11
success  CodeQL           feat/moment-one-redesign  pull_request  1m30s  2026-09-11
success  ci               feat/moment-one-redesign  pull_request  1m39s  2026-09-11
```

**Baseline: ~1m40s–2m per push.** This is the single most useful fact for
this ticket: **there is a live CI pipeline running on every push to the
trunk, and the security gate is not in it.** Adding to it is a
three-line change, not a new pipeline.

**What would have to change, and what it costs.**

- **The static scanner: free, and unconditionally CI-able.** Measured at
  **0.20s** across all 106 route files. No database, no dev server, no
  network. It is *faster than the current gate*, which spends 0.37s
  parsing a JSON file. One step in `ci.yml` after `typecheck`; the added
  wall-clock is inside the noise of a 100-second job. **There is no cost
  argument against this.**
- **`npm run test:security`: needs a database *and* a live server.**
  Measured at **8.3s locally** with both warm. The dependency is split:
  suites 1–9 construct `NextRequest` objects and call handlers in-process
  — those need **Postgres only**. Suite 10 (GTC-267's) uses
  `fetch` against `process.env.SECURITY_TEST_BASE_URL ?? 'http://localhost:3000'`
  — that needs **a running Next server**.

  So it can run in CI, but not for free. It needs a `postgres` service
  container, `prisma migrate deploy`, the seed or the suite's own
  fixtures, then `next start` against the existing build plus a readiness
  wait. **Realistic added cost: 60–90 seconds**, mostly server boot and
  migration, on top of the current ~100s.

  The suite is honest about the dependency and will not pass quietly
  without it — its own probe asserts a guarded sibling answers 401, with
  the rule stated in the file: *"a suite that cannot report its red is not
  a red. If the dev server is down these tests cannot run, so the probe
  FAILS the suite rather than skipping it quietly."* That is the right
  behaviour and it means a half-configured CI job goes red, not green.

**If the full suite cannot go into CI, this can.** The static scanner
needs nothing and catches the entire class [[GTC-267]] was about —
a handler with no credential check — without a database, a server or a
fixture. **Ship the scanner in CI first, and treat the runtime suite as a
second, separately-justified step.** Splitting `test:security` so suites
1–9 run with Postgres alone is a cheaper middle option and is the
recommended second slice.

## Proposal

### The tool — and it replaces the gate

**Recommendation: replace, not sit beside.**

A second gate beside the first means two answers to one question, and the
green one is the one that gets pasted into evidence sections. The existing
gate's only real property — *"no route was added or removed without
someone noticing"* — is subsumed: a scanner that enumerates 134 handlers
from disk gets the count right by construction and cannot drift.

`tests/security-route-gate.ts` (name TBD), which:

1. Walks `src/app/api/**/route.ts` with the TypeScript compiler API and
   enumerates **every exported HTTP method handler** — 134 today, not 81
   files.
2. For each, determines whether every terminal path passes a credential
   check: a guard symbol from a declared list, a lookup on a declared
   credential column followed by a refusal, or a verified third-party
   signature.
3. **Default-deny.** Anything not proven guarded and not on the allowlist
   is a failure, with the handler named and the file and method printed.
4. Exits non-zero on any unexplained handler.
5. Ships with **the [[GTC-267]] control as its own test** — run against
   `298b62d` it must report those nine; run against HEAD it must not. A
   gate whose first act is reproducing a known past finding has earned the
   green it prints.
6. Declares its blind spots in its own header: helper-call depth bound, no
   cross-file guard resolution, and the credential-column list as a
   maintained input.

**What replaces `scripts/triage-unknown-routes.ts`.** Nothing directly.
Its job — sorting UNKNOWN routes by risk — disappears when there is no
UNKNOWN category, because default-deny means every handler is either
proven, allowlisted, or red. **Delete it.** Its risk-substring lists
(`isHighCost`, `isSensitiveRead`, `isAdmin`) are worth keeping as
*prioritisation* of failures — a red on `/tokens` should print above a red
on `/days` — so lift those three arrays into the new tool and delete the
file. It is ~200 lines of unreachable code behind a moved path; keeping it
for reference is what `git log` is for.

### What happens to `route-classifications.json`

**Deleted as an input. Not kept as a record.**

- **As an input it is actively harmful**: it is the mechanism by which a
  route's author certifies their own route, and it is the reason the gate
  cannot fail. The new tool reads the tree.
- **As a record it is false**: 5 phantom entries, 30 missing, 11 entries
  declaring `NONE` on routes that are now guarded, and one `CUSTOM` entry
  describing a `?hostId=` credential path [[GTC-267]] removed. Keeping a
  wrong file next to a right one produces exactly the confusion this
  ticket exists to end.
- **The history is the record.** `git log -- route-classifications.json`
  keeps every version and this ticket cites the ones that matter.

**What survives it.** Two things, promoted to real inputs with real
owners: the **allowlist** (above), and the **credential-column list**
(`sharedLinkToken`, `AccessToken.token`, `MagicLink.token`,
`Session.token`), each checked against `prisma/schema.prisma`.

`docs/05_ops/security/SECURITY_ROUTE_INVENTORY.md` is a separate question
this ticket does not settle: it should either become **generated output**
of the new tool (and therefore always true), or be marked historical. It
must not remain a hand-kept document that a script expects to parse.

- **In (B), not in (A) — three routes allowlisted BECAUSE they carry a
