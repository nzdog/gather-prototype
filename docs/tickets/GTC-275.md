## The shape of it, plainly

This is **not three bugs, and not five. It is a default.**

`prisma.event.findUnique`, `.findMany`, `.update` and `.create` return **every
scalar on the row** unless given a top-level `select`. An `include` does not
narrow anything — it means "all scalars, *plus* these relations", which is the
trap both prior tickets walked into independently. So **every route that returns
an `Event` row inherits the whole row by default**, and will keep doing so, and
each new route will inherit it again on the day it is written.

The history is the argument:

- [[GTC-267]] found it on `GET` and `PATCH` in `src/app/api/events/[id]/route.ts`
  and narrowed **one** route, introducing `EVENT_WIRE_SELECT`.
- [[GTC-271]] found the same default on `GET` in `src/app/api/events/route.ts`
  and narrowed a **second**. `EVENT_WIRE_SELECT` did not fit, so a second shape
  was written — and both were moved into `src/lib/events/wire-select.ts` under
  one stated contract.
- This ticket names **five more**.

Two tickets have now each fixed one instance of a defect that has at least seven.
Fixing a third instance individually would be the same mistake a third time.

**The fix is one contract applied everywhere, not five patches.** Which is why
`src/lib/events/wire-select.ts` existing now matters more than the two routes it
currently serves: it is the place the contract lives. This ticket is the case for
pointing the rest of the surface at it.

This is the read-shape sibling of [[GTC-268]]: that ticket closes the class of
*"the gate cannot see this route"*, this one closes the class of *"the select was
never written"*. Neither is fixed by closing individual holes.

## Signal

**Expected**
A route that serialises an `Event` row names the fields it serialises, the way
`GET`/`PATCH` on `src/app/api/events/[id]/route.ts` and `GET` on
`src/app/api/events/route.ts` now do. The sixteen columns
[[GTC-267]] named — the join credential `sharedLinkToken`, the Stripe block, and
the check-plan telemetry — do not go over the wire.

**Actual**
Five routes hand back the whole row. Two were **driven and confirmed**; three
were **read at HEAD and not driven**. The distinction is kept everywhere below —
see **Evidence**.

**Smallest failing case**
`POST /api/events/<id>/archive` with a HOST session returns 200 and a 63-key
`event` object carrying all sixteen forbidden columns.

### A. DRIVEN — confirmed live, 2026-09-12

Both were exercised in a signed-in browser against the local dev server as
`nigel@mckorbett.co.nz`, on a real event (`cmoxzhkvp00011ybot9q7yo7z`, a
throwaway "GTC-133 Sub-commit (g) Test"). The event was archived and then
restored, so the database was returned to its prior state — 0 archived, 21
events — and the round trip is what produced both measurements.

| Route | Guard | Result |
|---|---|---|
| `POST /api/events/[id]/archive` | `requireEventRole(id, ['HOST'])` | 200, **63 keys**, **16/16** forbidden columns |
| `POST /api/events/[id]/restore` | `requireEventRole(id, ['HOST'])` | 200, **63 keys**, **16/16** forbidden columns |

Both are `prisma.event.update({ where, data })` with no top-level `select`, the
result returned as `NextResponse.json({ event })`. `archive` sets
`archived: true`; `restore` sets `archived: false`. Neither file is longer than
24 lines and neither has any other defect — the guard is present and correct in
both.

### B. READ — verified in source at HEAD `8699344`, NOT driven

Each of these was read in full and the `NextResponse.json` payload traced by
hand. **No request was issued against any of them.** They are listed as findings
because the shape is unambiguous in source, not because anyone observed a
response.

**1. `POST /api/events` — the sharpest of the five**

This is the **sibling handler in the very file [[GTC-271]] just fixed**.
[[GTC-271]] narrowed `GET` in `src/app/api/events/route.ts` and left `POST`
exactly as it found it, because `POST` was outside that ticket's scope.

`POST` creates the event with `tx.event.create({ data: { ...eventData, hostId } })`
— no top-level `select` — and returns it as
`NextResponse.json({ success: true, event })`. The `eventData` object it writes
**sets `stripePaymentIntentId`, `paidAt` and `amountPaid`**, so the route hands
back the Stripe payment intent id it has just written, in the same response, a
few lines later.

That is why it is the sharpest: not because the exposure is the widest — it is
the caller's own payment, see the severity argument — but because it is the
clearest possible demonstration that the default is a default. One file, two
handlers, one of them narrowed last commit and the other still writing a Stripe
credential straight back out. Nobody chose that. Prisma chose it.

**2. `PATCH /api/h/[token]/status`**

`resolveToken(token)` then `resolvedContext.scope !== 'HOST'` → 403, so this is
the host's own link. Inside a `prisma.$transaction`, `tx.event.update({ where,
data: { guestCount } })` with no top-level `select`, returned as
`NextResponse.json({ event: updated })`.

**3. `POST /api/templates/[id]/clone`**

`getUser()` → 401 if absent. `prisma.event.create({ data: {...} })` with no
top-level `select`, returned inside
`NextResponse.json({ eventId, event, scalingApplied, scalingRatio, message })`.
The event is brand new, so the credential and billing columns are `null` at the
moment it is serialised — the **shape** is wrong, the **values** are not yet
populated. Recorded that way rather than inflated.

### C. What is NOT a finding, and why that matters

The sweep initially flagged **21** call sites. **Sixteen were false positives**
and are named here so nobody re-reports them: `confirm-invites-sent` (both the
`[id]` and `h/[token]` variants), `export-text` (both variants), `invite-status`,
`wrap-up`, `generate`, `regenerate`, `regenerate/preview`, `regenerate-plan`,
`finalize-plan`, `setup`, `items/[itemId]/assign`, `conflicts/[conflictId]/
suggest-resolution`, and `h/[token]/confirm-invites-sent`.

Each reads the whole row internally, but serialises **derived fields only** —
`eventName: event.name`, `totalPeople: event.people.length`, and so on. An
internal wide read is not a wire defect. **A pattern match on these files would
report them; reading the payload does not.**

## The sweep method — recorded because it is reusable

This is the part worth keeping. The same method applies to any "does model X leak
on any route" question, and it is the method [[GTC-267]]'s rule demands: **an
empty search result is a claim, and a claim needs a control.**

1. **Prove the detector against a known match, before trusting any absence.**
   The pattern was run first against `prisma.event.findMany` in
   `src/app/api/events/route.ts` — the hit [[GTC-271]] had already confirmed by
   hand. It found it. Only then was any negative result believed.
   *A grep that has never returned a true positive is not evidence of absence.*
2. **Enumerate candidates mechanically, not by eye.** A script walked every
   `prisma.event.*` / `tx.event.*` call in `src/`, matched the call's argument
   object by bracket depth rather than by regex, and extracted its **top-level**
   keys — so a nested `select:` inside an `include:` could not be mistaken for a
   top-level one. Comments were stripped first, so prose mentioning `select`
   could not pass as code. **32** call sites had no top-level `select`.
3. **Narrow by reachability.** Of those 32, **21** bound a variable that appears
   inside a `NextResponse.json(...)` / `Response.json(...)`. The other 11 are
   internal reads and were set aside, listed for the record.
4. **Read every survivor's payload. Do not match on it.** This is the step that
   did the real work: 21 → **5**. The 16 discarded all serialise derived fields.
   No automated check distinguishes `json({ event })` from
   `json({ eventName: event.name })` reliably; a person reading the line does.
5. **Drive what can be driven; label the rest as read.** Two of the five were
   exercised live. Three were not. The ticket says which, and does not blur them.

**32 → 21 → 5, with a control proven first and the last narrowing done by
reading.** The script is not preserved; the method is, and it is cheap to rebuild.

## Severity, argued

**Medium.** The column list would read as High on its own, and it should not be
allowed to.

**What holds it down — say this plainly rather than implying it:**

- **None of the five is [[GTC-267]]'s anonymous class.** That ticket was Critical
  because an event id alone — no session, no token, no credential — reached the
  host's email and then, through `hostId`, the HOST access token. Nothing here is
  reachable without authentication. Three need a session, two need a `HOST`
  `EventRole`, one needs a `HOST`-scope token.
- **No cross-principal exposure on today's guards.** `archive` and `restore` are
  `['HOST']`-only, so the caller already holds the highest role on that event and
  can obtain `sharedLinkToken` legitimately through
  `POST /api/events/[id]/shared-link`. `h/[token]/status` is that same host's own
  link. `POST /api/events` returns the caller their **own** payment intent id,
  moments after they paid for it. `clone` returns a row whose credential columns
  are still `null`.
- So, unlike [[GTC-271]] — which was High precisely because a `COORDINATOR` got
  the join credential — **no principal here currently receives a credential
  belonging to someone else.**

**What keeps it off Low:**

- `sharedLinkToken` is a **declared credential column** —
  `CREDENTIAL_COLUMNS` in `tests/security-route-scan.ts` carries
  `{ model: 'event', field: 'sharedLinkToken' }` — and
  `POST /api/join/[token]/claim` authenticates on it. It is genuinely on the wire
  on the two driven routes. "The recipient could have got it another way" is a
  mitigation, not a contract.
- **The severity is in the default, not in today's reachability.** Every one of
  these is one role-list edit away from becoming [[GTC-271]]. Add `'COHOST'` or
  `'COORDINATOR'` to `archive`'s `requireEventRole` — an ordinary, reasonable
  product change nobody would flag in review — and a Medium becomes a High with
  no edit to the serialiser at all. A defect whose severity is controlled by an
  unrelated line in another file is not a stable Low.
- It is **standing and inherited**. Every `Event`-returning route written from
  here inherits it by default.

Medium is the honest reading: no live cross-principal exposure, a real credential
on the wire, and a class that will keep producing instances until the contract is
applied rather than the holes closed.

## Scope

**Fix here (when it is scheduled — NOT now):**
- The two driven routes: `src/app/api/events/[id]/archive/route.ts` and
  `src/app/api/events/[id]/restore/route.ts`.
- The three read routes: `POST` in `src/app/api/events/route.ts`,
  `src/app/api/h/[token]/status/route.ts`,
  `src/app/api/templates/[id]/clone/route.ts` — each to be **driven first**, then
  fixed. Do not fix a route on the strength of a source read alone.
- `src/lib/events/wire-select.ts` — the contract's home. Decide per route whether
  it reuses `EVENT_WIRE_SELECT`, reuses `EVENT_LIST_WIRE_SELECT`, or needs a
  third shape, and **decide it by reading the caller**, as [[GTC-271]] did. Three
  near-identical shapes with no stated reason would be its own defect.
- `tests/security-validation.ts` — assertions per route, added and never
  weakening, on fixtures where the forbidden columns are **populated**. Suite 13
  (`testSuite13_EventListSelect`) is the template; suite 10
  (`testSuite10_EventReadAuth`) is the original.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding. Two are
adjacent and neither is entered: **Zone 3** (AccessToken & scope) — this changes
what is serialised, never what a token is or how it is minted; **Zone 4**
(Stripe) — `POST /api/events` must have its **response** narrowed, and its
payment verification, idempotency check and `eventData` writes left exactly as
they are. Narrowing the response is not a billing change. Treat any urge to
adjust the Stripe logic itself as a stop condition.

## Unknowns

1. **Whether five is the whole list.** The sweep covered `src/` and the four
   Prisma methods that return rows (`findMany`, `findUnique`/`findUniqueOrThrow`,
   `findFirst`, `update`, `create`). It did **not** cover: rows reaching the wire
   through a helper in `src/lib/` that returns them to a route; `Event` rows
   nested inside another model's `include`; or server components serialising a row
   into RSC payload. Each is a plausible further instance and none was swept.
   Re-run the method in **Sweep method** above, control first.
2. **Whether `POST /api/templates/[id]/clone` can be driven at all.**
   [[GTC-267]] recorded that `POST /api/templates` answers 403 to every caller,
   which is why its clone-source overlay went untested there. If the template
   cannot be created, the clone cannot be exercised, and this finding may have to
   stay source-only. Report it that way rather than claiming a verification that
   did not happen.
3. **Whether a lint rule could hold the contract better than review.** A rule
   banning `include` without a sibling `select` on `prisma.event.*` would catch
   the next instance at write time rather than in a sweep a month later. Not
   scoped, not costed, and possibly noisy against the 11 legitimate internal
   reads. Worth an hour before the fix, not instead of it.
