# GTC-235 — A generated V2 plan cannot be reopened

**Status:** Open — needs scoping when pulled | **Effort:** TBD

*Surfaced by [[GTC-233]] (the V2 route extraction), 2026-08-22. Pre-existing — GTC-233 moved
this code without changing the behaviour, and deliberately did not fix it. Derived from code
at `9ff9f23` plus the GTC-233 working tree.*

## Signal

**Expected:** a host who generated a plan can come back to it. Kate opens her event tomorrow
and sees the plan she approved.

**Actual:** the plan view opens only as the tail of an in-session generation. Navigating to
`/plan/[eventId]/setup` for an event whose plan already exists shows `SetupOpeningScreen`
— the "Ready to start herding" opening — and then Moment 1. There is no path back to the
plan short of generating again, which costs an AI call and replaces the plan.

**Smallest failing case:** generate a plan, reload the page.

## Root cause

`setShowMoment2PlanView(true)` has two call sites in `EventSetupPage`
(`src/app/plan/[eventId]/setup/page.tsx`), and **both are callbacks of
`Moment2Step2Skeleton`** — `onReady` (the normal path) and `onApprove` (a fallback that
GTC-233 repointed at the plan view; its own comment notes it is unused while `onReady`
auto-transitions). Nothing sets the flag on mount.

So the flag is pure session state with no hydration. The route's mount effect loads the
event and `items`; it does not ask whether a plan already exists, and `showSetup`
initialises to `true` unconditionally — see the GTC-233 comment at that `useState`.

Note the data is all there and already fetched by other paths:
`loadMoment2PlanCategories` in the same component builds the categories from
`/api/events/[id]/teams` and `/api/events/[id]/items` with no session state, and
`mapTeamsAndItemsToPlanCategories` is a pure function. The view is reconstructible; nothing
asks it to be.

## Why it matters

**A plan the host cannot reopen is a plan she cannot trust.** The Moment 2 plan view is the
only V2 surface that shows the generated plan; V1's dashboard shows the same rows through a
different lens, but [[GTC-233]] Option 2 deliberately stopped routing V2 events there, and
V2 events now reach V1's URL only by accident.

**It also pushes hosts toward regeneration.** The only way back to the plan view is to walk
Moment 2 again and generate, which consumes one of the ten AI calls and replaces the
existing rows. A navigation bug becomes a data-loss and cost problem.

## Needs scoping when pulled

Candidate directions, not a ruling:

- **Hydrate on mount.** Resolve the entry stage from server state rather than defaulting to
  the opening screen: plan exists → plan view; `EventSetup` complete but no plan → Moment 2
  Step 1; households but no setup → Moment 1; nothing → opening screen. This is the shape
  GTC-233's Phase 2 identified as correct and ruled out of scope, because it changes V2's
  entry behaviour rather than moving it.
- **Or give the plan view its own URL** (`/plan/[eventId]/setup/plan`), self-hydrating via
  `loadMoment2PlanCategories`. GTC-233 originally recommended this two-route split; the
  founder chose the single-route state machine (Decision 1, 2026-08-22) with per-stage URLs
  explicitly deferred: *"If per-stage URLs become needed later, we add them then."* This
  ticket is that later.
- Decide what "already generated" means. `teams.length > 0` is the cheap test but V1 events
  and manually-built plans also have teams; `event.setup` plus teams is narrower.

Whichever is chosen, the entry rule should be one function with a name, not a chain of
conditions inside the component — it will be read by every future Moment.

## Do not touch

All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`. Specifically: do not reintroduce a
query parameter as the stage switch. [[GTC-233]] retired `?setup=true` and the reconciliation
review's section 3 names query-param-as-mode-switch as the pattern being removed. If a URL is
needed, it should be a path segment.
