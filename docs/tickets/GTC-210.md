# GTC-210 — Unguarded wrap-up quiet-hours send

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** a4fa742 | **Effort:** low-medium

*Source: `docs/04_roadmap/moment4-hinge-report-accuracy-audit-2026-08-04.md` — defect 3b,
**CONFIRMED, MEDIUM-HIGH** by the confirmation pass. Live defect, not a doc issue.*

### Scope, one line

The wrap-up / thank-you SMS path has no quiet-hours guard at all, so a host who confirms
wrap-up at 23:00 NZ texts every guest at ~23:10.

### Context

Quiet hours are 21:00–08:00 NZ (`quiet-hours.ts:6-7`). Every other outbound SMS family
respects them. The wrap-up family does not.

**The coverage gap, verified:** `src/lib/sms/quiet-hours.ts` has exactly **two** importers
repo-wide — `nudge-sender.ts:4` and `proxy-nudge-sender.ts:3`. `src/lib/wrap-up.ts` has
**zero** case-insensitive occurrences of `quiet`, `Auckland` or `getHours`.

The thing that looks like a time window is not one. `DISPATCH_DELAY_MINUTES = 10`
(`wrap-up.ts:18`, used at `:162`) is an **age filter** — "only send links created more than 10
minutes ago" — not a time-of-day check. The cron runs `*/10`, 24 hours a day
(`vercel.json:7-10`), and `dispatchPendingWrapUpMessages` (`wrap-up.ts:157`) calls `sendSms`
directly at `:210` with nothing between.

So: press at 23:00 → `WrapUpLink` rows created → cron at ~23:10 finds them older than the
cutoff → texts every guest.

**⚠ This is NOT the quiet-hours arithmetic bug.** The first audit flagged an arithmetic defect
in `getMinutesUntilQuietEnd()` — `getNZTime()` (`quiet-hours.ts:13-19`) returns NZ wall-clock
component values on a shifted absolute instant, and `:78-81` subtracts a real `new Date()` from
it. The confirmation pass **downgraded that to a log-field defect**: every consumer of
`deferredMinutes` / `deferredUntilMinutes` is a log or response field, while the send/skip
decision is the boolean `isQuietHours()` (`:24-30`), which is correct in any server timezone.
No message is sent at the wrong time because of the arithmetic. **This ticket is the missing
guard — the real wrong-send.** Do not fix the arithmetic here; it is a separate, lower-severity
concern.

### The existing convention — find it, match it, do not invent one

Both existing guards are the same shape, at the top of the **batch processor**, not per-message:

- `nudge-sender.ts:114-138` (`processNudges`)
- `proxy-nudge-sender.ts:90-110` (`processProxyNudges`)

```ts
if (isQuietHours()) {
  const minutesUntil = getMinutesUntilQuietEnd();
  for (const candidate of allCandidates) {
    await logInviteEvent({ eventId, personId, type: 'NUDGE_DEFERRED_QUIET',
      metadata: { deferredMinutes: minutesUntil, phoneNumber: candidate.phoneNumber } });
  }
  return { sent: [], deferred: allCandidates.length, deferredUntilMinutes: minutesUntil };
}
```

The deferral is **implicit and durable** — nothing is scheduled. The processor returns having
sent nothing, the candidates remain eligible, and the next cron run outside quiet hours picks
them up. That maps cleanly onto wrap-up: `WrapUpLink` rows simply stay `dispatched: false`, and
the `*/10` cron sends them after 08:00.

**Two traps in the guard's own module:**

1. `isTimeInQuietHours(date)` (`quiet-hours.ts:61-70`) has **zero callers** and is exactly what
   a "add quiet hours to wrap-up" fix instinctively reaches for. The convention uses the
   no-argument `isQuietHours()`. Use the convention.
2. `getNextSendTime()` (`:37-56`) is exported with no external caller and carries the arithmetic
   defect described above. Do not build the guard on it.

**One decision the executor must surface, not assume.** `InviteEventType`
(`schema.prisma:1024-1043`) has `NUDGE_DEFERRED_QUIET` and `PROXY_NUDGE_DEFERRED_QUIET` but
**no wrap-up equivalent**. The guard itself — defer, send nothing — needs no schema change.
Matching the convention's *logging* half would mean adding a `WRAPUP_MESSAGE_DEFERRED_QUIET`
enum value, which is a migration and therefore Stop Condition 7. Report which shape you intend
before writing it; do not silently add an enum value, and do not silently drop the logging.

### Scope

**Fix here:**
- A quiet-hours guard on the wrap-up dispatch path, at `dispatchPendingWrapUpMessages`
  (`wrap-up.ts:157`) — the batch processor, matching where the other two guards sit.
- Deferral must be **durable and implicit**: rows stay `dispatched: false` and are sent by a
  later run. Do not add a scheduler, a delayed job, or a new timer.
- Deferral logging per the convention, if the enum decision above is signed off.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- `sendSms` / `send-sms.ts` / TNZ / Twilio. This is a time guard around the existing call, not a
  change to the carrier.
- The quiet-hours **arithmetic** (`getMinutesUntilQuietEnd`, `getNextSendTime`, `getNZTime`).
  Confirmed as a log-field defect, separate concern, out of scope here.
- `quiet-hours.ts`'s window constants. 21:00–08:00 is the shipped rule.
- GTC-209's dedupe guard. Both touch the wrap-up path; keep the changes separable.

**Behaviour guardrail:** a wrap-up press at a normal hour must behave exactly as it does today —
same recipients, same messages, same ~10-minute dispatch delay. This ticket adds a time guard
and nothing else.

### Dependencies

None. Independent of GTC-209, though both land in the wrap-up path — sequence them, don't merge
them.

### Acceptance

*Built 2026-08-05 on `feat/moment-one-redesign`, landed as `a4fa742`. Boxes reflect
what was actually done. One criterion as originally written was wrong and was superseded — it is
kept below with the correction rather than quietly deleted.*

- [x] A test proves a wrap-up press during quiet hours **defers rather than sends** —
      `tests/wrap-up-quiet-hours-test.ts` (`npm run test:wrap-up-quiet-hours`). At 23:00 NZ and
      again at 03:00 NZ: nothing sent, row still `dispatched: false`, `dispatchedAt` null, not
      marked failed, and no `WRAPUP_MESSAGE_SENT`/`_FAILED` logged.
      **RED with the guard removed: 7 passed, 11 failed** — the link was dispatched and a send
      was logged at 23:00 NZ, i.e. the thank-you fired inside quiet hours. **GREEN: 18/18.**
- [x] The same test proves the deferral is **durable**: the identical row is picked up and
      dispatched exactly once by a later run at 13:00 NZ. No scheduler, no timer — the rows
      simply stay pending, matching how the nudge guards defer.
- [x] A control asserts a dispatch **outside** quiet hours still goes through
      (`deferred === 0`, `total === 1`, row dispatched, attempted exactly once). Without it the
      guard could have "passed" by never dispatching at all.
- [x] ~~**The test pins `TZ` explicitly.**~~ **SUPERSEDED — pinning `TZ` would not have worked.**
      `isQuietHours()` converts to `Pacific/Auckland` internally, so it returns the same answer
      under any `TZ`; pinning it would only have made the test depend on what time CI happened
      to run. **The clock itself is the input instead:** `isQuietHours(now = new Date())` and
      `dispatchPendingWrapUpMessages(now = new Date())` are injectable, in the same shape as the
      existing `isComplete(event, now = new Date())` in `lifecycle.ts`. Both existing
      quiet-hours callers pass nothing and are unchanged in behaviour. Test instants are built
      by probing for a target Auckland hour rather than assuming an offset, so they stay correct
      across NZDT and NZST.
- [x] No real SMS is sent by the test — **and no email either.** The quiet-hours assertions
      return before the dispatch loop. The 13:00 control deliberately enters the loop, so its
      fixture carries **no phone and no email**, routing it to the loop's "No valid contact
      method" branch: row marked dispatched, no provider touched.
      **Why this is called out:** an earlier draft of the fixture had both, and when the
      disabled guard let it through, `sendSms` failed closed (no `TNZ_AUTH_TOKEN`) but the
      **email fallback did not** — a `RESEND_API_KEY` is present in `.env`, so a live Resend API
      call was made to `quiet@example.test` (an IANA-reserved TLD, undeliverable, no real
      recipient). The test now documents this so nobody re-adds an address.
- [x] **No `WRAPUP_MESSAGE_DEFERRED_QUIET` enum value was added, so no migration and Stop
      Condition 7 was never triggered.** The convention's per-candidate `InviteEvent` row is the
      one half not matched: the enum has no wrap-up equivalent and adding one is schema work.
      The deferral is still observable — a `[WrapUp]` console line plus `deferred` and
      `deferredUntilMinutes` on the cron's JSON response, mirroring `processNudges`' return
      shape. Stated in the code comment, not silently omitted.
- [x] `npx tsc --noEmit` 0 · `next build` 0 · `format:check` 0 · **security suite 51/51** ·
      `test:wrap-up` 28/28 · `test:child-exclusion` 18/18 · `test:wrap-up-quiet-hours` 18/18.

**One in-scope deviation from "do not touch", declared:** `getMinutesUntilQuietEnd` and
`getNextSendTime` also gained an optional `now`. This is **not** the arithmetic fix the scope
forbids — the ~720-minute server-TZ offset defect is untouched and is now documented in place.
It was necessary because the guard was checking `isQuietHours(now)` against the injected clock
while reporting the wait from the real one, which the test caught as an inconsistency.
