# GTC-432 - Trimmed checks, and "+64 (0)" stored right

> Filed by Claude Code on 31 Oct 2026. Second of the five household
> save tickets (GTC-431 to GTC-435) on fix/household-save, after
> [[GTC-431]] (02c3791).

## The founder's rulings (31 Oct 2026)

- Item 2 of the fix ticket: "Trim spaces on email and phone before
  checking. First report what the rules currently require for a child's
  email and phone (required or optional) and which formats are
  rejected. Do not loosen anything until I have seen that report."
- After the report: "trim spaces on emails, and fix the '+64 (0)' phone
  case so it stores without the extra 0. Phone rules are otherwise
  unchanged."

## The change

- src/components/plan/Moment1InputForm.tsx: `validateEmail` and
  `validatePhone` move out of the component to module level, exported
  (they use no state), and each checks `value.trim()`. Every caller is
  as it was. buildPayload already trimmed what it sends.
- src/lib/phone.ts, `normalizePhoneNumber`: first of all, a number
  that starts "+640" or "640" (a 0 written straight after the country
  code) drops that one 0. Then the rules run exactly as before.
  Placing it first matters: run after the local-number step, it would
  also have rewritten a "0064 21 123 456" (refused today) into a wrong
  number. Found and moved while building.

## What changes for a person typing

- "+64 (0)21 123 4567", "64 (0)21 123 4567": stored +64211234567, not
  +640211234567 (which no text could reach).
- "+64 (0)21 1234 5678" (an 8-digit 021 mobile): was refused (too long
  with the extra 0); now accepted as +642112345678.
- "+64 (0)123 4567" (no area code): was stored as +6401234567; now
  refused, "Invalid NZ phone number". No real NZ number has that shape.
- A box holding only spaces is now read as empty (as the payload
  already read it), so it no longer stops a Save.
- Nothing else. A differential run of the old and new
  normalizePhoneNumber over 8,840 generated inputs changed results only
  for inputs with a 0 straight after 64.

Found while building: an email box (`type="email"`) hands the page its
value with the spaces at either end already removed (the browser's own
value rule), so on the form's email boxes a trailing space never
reached the check. The rules report (31 Oct) said "kid@example.com " was
refused; that is true of the rule, not of what a person could do in a
browser. The trim makes the rule match what it is given and what is
sent; a visitor sees no change on email.

## Where the phone change reaches

normalizePhoneNumber is shared: the households POST and PUT
(reconcileMembers), host-household, the V1 people routes and batch
import, the guest contact-info route, AddPersonModal, ImportCSVModal,
and src/lib/contact/contact-fix.ts. contact-fix.ts is on tweaks-guard's
protected list (zone 9); its file is unchanged (tweaks-guard green),
but what it stores for a "+64 (0)" mobile is now the right number.
Inbound texts are never normalised (tnz-reply-contract.ts keeps the
sender verbatim), so STOP and opt-out matching cannot move.

gather_demo rows whose stored phone starts "+640" (counts only):

```
before: Person.phoneNumber 0, Person.phone 0 (of 250 people)
after:  Person.phoneNumber 0, Person.phone 0 (of 250 people)
```

Rows already stored as "+640..." are not rewritten.
