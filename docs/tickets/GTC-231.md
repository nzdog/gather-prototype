## Context

Hinge §8 + Moment 4 §8.6: a maybe — or any silence — stays the guest's, held softly, until
Kate reassigns it. When she does, **the system closes the loop with the released guest**.
Releasing them is something the system can do, so it does. This also dissolves the
duplicate-item edge case: nobody arrives with a second dessert.

Today the loop is not closed. `onAssignmentReleased` in `src/lib/ledger.ts` is a placed
no-op with four live call sites. [[GTC-168]] (A2) put the call sites in deliberately — "so
the CALL SITE is decided now, inside the transaction that knows the facts, rather than being
hunted for later". This ticket fills the hook and builds what dispatches from it.

**The ledger already assumes this message exists.** `whyTrigger` in `src/lib/ledger.ts`
justifies T1 firing even at `PENDING` on the grounds that *"Hinge §8 has the system closing
the loop with whoever was released"* — the why-scope rule was written against a notification
that has never been built. Filling the hook makes that reasoning true rather than
anticipatory.

**And the silence is not neutral.** Until the release notice exists, the release path's only
outbound consequence is the *opposite* message — see [[GTC-213]], absorbed into this ticket.

## Founder rulings — settled 2026-08-15. Do not re-open; cite this section.

### Ruling 1 — record-and-sweep, not synchronous dispatch

`onAssignmentReleased` **writes a row**. A separate sweep dispatches it. This is the house
shape — six existing families run this way — and it resolves three of the four guard gaps
that synchronous dispatch could not:

| Guard gap | Why synchronous dispatch fails | How the sweep resolves it |
|---|---|---|
| Quiet hours | The release happens when the host acts, which may be 02:00 | No stamp is written; the next tick after 08:00 NZ picks it up. The house idiom (`processDecideByFollowups`, `processNudges`, `dispatchPendingWrapUpMessages`) |
| Dedupe | Nothing to dedupe against — the assignment row is gone | The record row **is** the dedupe stamp |
| The CHILD check | Needs `eventId`; the hook signature is `(personId, itemId, changeSetId)` and four call sites depend on it | The sweep has `eventId` in scope from the row |

**Costs accepted:** latency between the release and the message, and a fourth cron route.

The fourth gap — that the hook has no `eventId` — is resolved separately: the row itself
needs `InviteEvent.eventId`, which is non-null, so the hook derives it from the item
(`Item → Team.eventId`). That is one lookup inside the hook, not a signature change.

### Ruling 2 — a new `InviteEventType` value, and therefore a migration

Forced. Neither existing value can be reused for the record row:

- **`NUDGE_SENT_AUTO`** feeds STOP attribution. `POST` in
  `src/app/api/sms/inbound/route.ts` finds the most recent `NUDGE_SENT_AUTO` row matching
  the inbound number and opts that number out **of that row's host**. A record row typed
  `NUDGE_SENT_AUTO` would attribute a later STOP to a host who sent nothing — the
  wrong-host opt-out.
- **`NUDGE_SENT_HOST`** feeds the 24h cooldown in `POST` at
  `src/app/api/events/[id]/people/[personId]/nudge/route.ts` (`COOLDOWN_MS`). A record row
  typed `NUDGE_SENT_HOST` would silently `429` the host's next real nudge to that person.
- **No row at all** leaves nothing to dedupe against, which is Ruling 1's whole mechanism.

Stop Condition 7 fires. `type: schema`. See **Migration protocol** below.

*This ruling forecloses reuse and no-row; the arity is settled by Ruling 8 — two values, one
migration. The heading's singular is the wording as first ruled, kept for provenance.*

### Ruling 3 — no link

The message is informational. It carries no token URL. Zone 3 (`AccessToken` & scope) is
untouched by this ticket.

### Ruling 4 — five call sites

The four existing, plus `PATCH` in `src/app/api/events/[id]/people/[personId]/route.ts` —
the team-change branch, where `prisma.assignment.deleteMany` runs (hint: `:70`) and the
person's `PersonEvent` survives. **Verified at `176e9cc`.**

The ledger gap on that same path — it deletes assignments and writes **no** ledger entry —
**files as its own ticket. Surface it; do not fix it here.** Filed as [[GTC-232]].

### Ruling 5 — [[GTC-213]] lands with D3

Latent, not live: nobody was stamped without TNZ. It shares this surface, and it is RED test
7 below.

### Ruling 6 — Gather's voice, not the host's

The message speaks as the system. It **does not name the replacement**. It states the reason
**only when known**. What "known" resolves to is settled by Ruling 7.

## Founder rulings 7–10 — settled 2026-08-15, second pass. Same standing as 1–6.

These answer the questions the first pass left open. The derivations behind them are kept
below (*How rulings 7 and 9 were derived*) because the reasoning is the part that stops them
being re-litigated.

### Ruling 7 — two templates, keyed on structural cause. The host's reason is never quoted.

"The reason, when known" means the **structural cause**, and nothing else:

- **`MOVE_ASSIGNMENT`** — the ask is now someone else's. The item is covered.
- **`DELETE_ASSIGNMENT`** — the ask is withdrawn and the item returns to `UNASSIGNED`.
  Nothing is covering it.

Two templates. No free text on either. A missing changeSet (call site 5) falls to the
`DELETE` shape, which is what actually happened there.

**`AuditEntry.reason` is never quoted to a released person.** This is a Do-Not-Touch
condition on the copy, not a preference — see *Do not touch*, where the reasons are recorded
in full. It is written there rather than only here because **a later executor will read
"include the host's reason" as an obvious improvement**, and the ticket has to say why it
is not.

### Ruling 8 — two new `InviteEventType` values, one migration

`ASSIGNMENT_RELEASED` (written by the hook) and `RELEASE_NOTICE_SENT` (written by the sweep
on success). Ruling 2 forecloses reuse and no-row; this settles the arity.

**Why not one value plus correlation.** The alternative was to write only the record row and
dedupe by looking for the `NUDGE_SENT_AUTO` row that `sendSms` writes on success. It fails
on its own terms: **`sendSms` returns `blocked: 'SMS_DISABLED'` without logging anything at
all.** Both configuration arms return early — the TNZ arm when `TNZ_AUTH_TOKEN` is absent,
the Twilio arm when the Twilio credentials are — before any `logInviteEvent` call. So the
correlation has a hole in exactly the two configurations that matter: **every dev machine,
and production until TNZ answers.** A dedupe that is blind precisely where the system
currently lives is not a dedupe. It also couples this ticket's correctness to another
module's internal logging, which nothing holds still.

`InviteEvent` has no mutable status column — unlike `WrapUpLink`, which carries
`dispatched`/`dispatchedAt` — so an append-only log needs a second row to mark the first one
consumed. That is the mechanism, and it is why the count is two.

### Ruling 9 — a CHILD release sends no message at all

Not to the child, and **not to the household's channel either**.

The household-proxy reading — re-route to the household adult, as `findProxyNudgeCandidates`
does — is **deliberately out of scope, not overlooked.** Recorded so it is not rediscovered
as an oversight:

- The child gate is absolute and precedes everything else. Every finder in the house runs it
  first and skips the candidate outright; none of them substitutes a different recipient at
  that point. Introducing a substitution *inside the child branch* would make this the one
  place where failing the child gate produces a send rather than a skip.
- Proxy re-routing is a **coordination** mechanism — it exists so a household's asks get
  claimed. A release notice is **informational** (Ruling 3: no link, nothing to action).
  Telling an adult that a child no longer holds an item is a different product decision, and
  it has a different recipient, a different template and a different consent story.
- It would need its own RED test. RED test 1 as ruled — "CHILD released → no message" — is
  unambiguous only under this reading.

If the proxy behaviour is wanted later it is a ticket, not a loosening of this one.

### Ruling 10 — freshness ceiling: 48 hours

A record row older than 48 hours is skipped, under a named and counted reason, and never
dispatched. Failures retry until then (the house stamps only on success), bounded also by
`SENT_AND_LIVE`.

48h absorbs a worst-case quiet-hours deferral (~11h) with room to spare, and it is what
stops an aged backlog firing in one burst on the day TNZ goes live.

### The two sites that release an assignment and are deliberately excluded

- **`DELETE` in `src/app/api/events/[id]/people/[personId]/route.ts`** — person removal.
  GTC-211's stated reason (*"a release message there would carry a dead link to a
  non-participant"*) **dissolves under Ruling 3**, since no link is sent. The surviving
  reason is stronger and is the one to record: the recipient's `AccessToken`s and their
  `PersonEvent` are deleted in the same transaction. They are not a participant any more,
  the child gate has no row to read, and "that one's off your list" is the wrong sentence
  for someone who has been removed from the event entirely. **Product decision, not an
  omission.** Telling a removed guest anything is its own ticket, unfiled.
- **`DELETE` in `src/app/api/events/[id]/route.ts`** — whole-event delete. Every
  `PersonEvent`, token and item goes; `InviteEvent.event` is `onDelete: Cascade`, so any
  pending record rows die with the event and the sweep never sees them. Nothing to do, and
  nothing to guard.

### There is no guest-initiated release path

Checked at `176e9cc`. The only participant-facing assignment write is `POST` in
`src/app/api/p/[token]/ack/[assignmentId]/route.ts`, which **updates
`Assignment.response`** and never deletes. A guest declining leaves the row in place at
`response: 'NO'`; a host or coordinator then reassigns, which is site 1 or 3. **All five
call sites are host- or coordinator-initiated.** This is load-bearing for Scoping question A.

## Scope

### Fix here

1. **`onAssignmentReleased` body** (`src/lib/ledger.ts`) — **records, does not send.**
   - Derives `eventId` from `itemId` (`Item → Team.eventId`).
   - Writes one `InviteEvent` row of the new record type, carrying a **snapshot** in
     `metadata`: `itemId`, `itemName`, `priorResponse` (the released person's own last
     answer), `changeSetId`, and the release instant. The snapshot is not redundancy — by
     the time the sweep runs, the assignment is gone and the item may be renamed,
     reassigned again, or deleted. The row must be able to describe a world that no longer
     exists.
   - **This row is a WORK ITEM, not instrumentation.** The distinction decides how it is
     written. `logInviteEvent` in `src/lib/invite-events.ts` catches and swallows its own
     write failures by design — *"instrumentation shouldn't break user flows"* — which is
     correct for a log line and **unacceptable for this write**. Every other row that
     function writes is a record of something that already happened; this one is the only
     record that something still has to happen. **A dropped row is a dropped message with
     no trace**: no retry, no skip count, nothing in the sweep's output, and the guest is
     simply never told. Do not route this write through `logInviteEvent`'s swallow.
   - **It must still not throw into the route.** The hook runs *after* the mutation has
     committed at every call site, so a throw here 500s a route whose write already landed —
     the host is told the reassignment failed when it succeeded. The two requirements are
     compatible and both are mandatory: the failure is caught **here**, at the hook, and
     surfaced loudly (a distinct `console.error` marker at minimum) rather than absorbed
     into general instrumentation noise. A comment records *why* this write is exempt from
     the house logging helper.
   - Widen the third parameter to `changeSetId: string | null` for site 5, which has no
     changeSet ([[GTC-232]]). **This is a widening: all four existing calls compile
     unchanged.** It is not the signature change Ruling 1 rules out.

2. **The sweep** — its own entry point, `now` injectable, following `runDecideByFollowups`'
   shape exactly:
   - `findReleaseNoticeCandidates(now)` — the finder. Reads unconsumed record rows whose
     event is `SENT_AND_LIVE(now)`; applies the child gate, the recipient resolver, opt-out
     and the freshness ceiling; returns `{ eligible, skipped: [{reason, count}] }`.
     Named skip reasons, counted — not silent drops.
   - `processReleaseNotices(candidates, now)` — quiet hours checked **once at the top of the
     batch**, nothing sent, `NUDGE_DEFERRED_QUIET` logged per candidate (existing value —
     read by neither the STOP attributor nor the cooldown). No stamp written, so the next
     tick after 08:00 NZ picks them up unchanged.
   - `runReleaseNotices(now = new Date())` + a `ReleaseRunResult`, mirroring
     `DecideByRunResult`.
   - **Collapse to one message per (person, event) per tick**, and write the terminal marker
     for **every** collapsed row — the `sendDecideByFollowup` rule, for the same reason:
     stamping only the named item leaves its siblings looking undispatched and re-texts the
     same person next tick. Site 5 releases N items in one request and is the case that
     makes this mandatory rather than tidy.

3. **A fourth cron route** — `src/app/api/cron/release-notices/route.ts`, copying
   `src/app/api/cron/decide-by-followups/route.ts` including its `CRON_SECRET` guard **and
   its known weakness** (`CRON_SECRET &&` leaves an unset secret open). Copy it rather than
   diverge: [[GTC-220]] owns that fix across all cron routes and must land in one place.

4. **The recipient resolver — the genuinely new layer.** New module
   (`src/lib/households/recipient.ts` proposed), sibling in spirit to
   `decide-by-eligibility.ts`'s gate stack. Given `(personId, eventId)`:
   1. `PersonEvent` for the pair — `@@unique([personId, eventId])`, a clean 1:1. **A missing
      row is skipped under its own reason and fails closed**, never treated as a null role
      (the `NO_MEMBERSHIP_SKIP_REASON` reasoning in `findDecideByFollowupCandidates`).
   2. **Child gate, absolute, first.** `isMessageableRole(householdRole)` false → skipped
      under `CHILD_SKIP_REASON`.
   3. Direct: `Person.phoneNumber` present → the person is their own recipient.
   4. Otherwise, if `PersonEvent.householdId` is set → `resolveHouseholdChannel`, then load
      that `PersonEvent` **by id from the event, not from `household.members`** (the channel
      may live in another household — §10.7), re-run the child gate on it and **fail closed**
      (`findProxyNudgeCandidates`' precedent — a channel pointing at a CHILD is corrupt data
      and is skipped, never silently downgraded to the primary contact), require its
      `eventId` to match, require a phone.
   5. Otherwise → skipped, "no reachable channel".
   - Opt-out is batched in the finder (the `findDecideByFollowupCandidates` shape) **and**
     re-checked by `sendSms`'s `checkOptOut` against the *recipient's* number. Zone 7 is read
     from, never modified.

5. **Two release templates** in `src/lib/sms/nudge-templates.ts` (Ruling 7) — one for
   `MOVE_ASSIGNMENT`, one for `DELETE_ASSIGNMENT` — each carrying the **mandatory
   ` — Reply STOP to opt out` suffix**. Gather's voice; neither names the replacement
   (Ruling 6); **neither interpolates `AuditEntry.reason` or any other free text**
   (Ruling 7, and *Do not touch*). The only variable content is the item name from the
   record row's snapshot and the event name.
   - Which template fires is re-derived at **send** time — does the item have an assignment
     now? — falling back to the recorded `actionType` when the item has since been deleted.
     The sweep runs later, and an item reassigned at 02:00 can be unassigned again by 08:00;
     what the guest reads must be true when they read it.

6. **Two new `InviteEventType` values + one migration** — `ASSIGNMENT_RELEASED` and
   `RELEASE_NOTICE_SENT` (Ruling 8). See *Migration protocol*.

7. **[[GTC-213]]'s fix.** The `hasResponded` expression inside `findNudgeCandidates`
   (`src/lib/sms/nudge-eligibility.ts`) reads only *remaining* assignments, so deleting an
   assignment flips it back to `false` and re-opens the 48h gate. Fix: `hasResponded` also
   holds when a **release is on record** for that `(person, event)` with a recorded
   `priorResponse` other than `PENDING` — one batched query over the new record rows,
   in the same batching shape the decide-by finder uses for memberships, tokens and
   opt-outs.
   - This covers **both** entry points at once, because both reach `findNudgeCandidates`:
     the 15-minute cron via `runNudgeScheduler`, and the host-authenticated `POST` in
     `src/app/api/events/[id]/trigger-nudges/route.ts` via `findNudgeCandidatesForEvent`.
     GTC-213 is right that the second exists and that the first audit missed it; it needs no
     separate fix.
   - **No backfill.** Releases that happened before this ticket lands left no row and stay
     exposed. The gap closes forward only. Acceptable because the exposure is TNZ-gated and
     has never fired; recorded here so it is not discovered as a surprise.

8. **Correct the false docblock above `onAssignmentReleased`** (`src/lib/ledger.ts`). It
   asserts *"This is the half of frozen-edit's handleReassign that was correct and is
   preserved here rather than reinvented later."* That sentence is false: no send half
   existed. The **call site** is what was preserved. Per GTC-222 rule 3, the replacement
   records *why* and does not assert *what the code does* — the behaviour goes in the tests.
   [[GTC-211]] rules that this must land with the D3 pass rather than as a doc-only fix,
   because a doc-only fix leaves the false sentence in `src/`. Discharged here.

   **And the second docblock in the same file — `whyTrigger`.** It justifies T1 firing even
   at `PENDING` on the grounds that *"Hinge §8 has the system closing the loop with whoever
   was released"*. That is a live rule resting on a mechanism **that has never existed** —

### Do not touch

All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding. Additionally:

- **⛔ DO NOT ADD AN `isSmsEnabled()` GATE. This is a Do-Not-Touch condition, not a style
  note.** [[GTC-214]] (`3eb4c72`) deleted three of them. `isSmsEnabled` in

  scope; every NZ destination routes to TNZ via `shouldUseTnz` in `sendSms`, which checks

  a TNZ-only deployment — the exact defect GTC-214 exists to have removed.
  **`sendSms` owns provider selection.** After GTC-214, `isSmsEnabled` has exactly two
  deliberate call sites (the Twilio arm of `sendSms`, and the `smsConfigured` *report* in
  `runNudgeScheduler`); this ticket adds none.
  **The file family still points wrong 3-to-1 by comment** — an executor reading the
  neighbours for precedent will find more encouragement to add the gate than to omit it.
  Read `runDecideByFollowups`' superseded reason 1, which records this, before copying
  anything.
- **⛔ `AuditEntry.reason` MUST NEVER BE QUOTED TO A RELEASED PERSON.** A Do-Not-Touch
  condition on the copy (Ruling 7), and it is stated at length because **including it reads
  as an obvious improvement.** It is available on the join the sweep already performs, it is
  literally the host's explanation of the thing being messaged about, and a future executor
  will find "the message should say why" a natural completion of Ruling 6. It is not. Three
  reasons, each sufficient on its own:
  1. **It is documented as private.** `RecordChangeParams.reason` in `src/lib/ledger.ts`
     scopes it as Kate's own memory — Hinge §2, *"not compliance — it's her own memory"* —
     and `recordChange` is explicit that it may be absent and must never be demanded. A
     field the product promises never to interrogate anyone for is not outbound copy.
     Quoting it to a third party changes what the host was asked to write, retroactively,
     for every reason already in the database.
  2. **It is unmoderated.** *"Swapped, hers is better"* is a plausible private note and an
     unacceptable text message. Nothing validates, reviews or softens this field, because
     nothing was ever meant to read it aloud.
  3. **It is unbounded.** No length limit, no character-set constraint. Interpolating it
     silently turns a one-segment SMS into an N-segment one, or a Unicode one at 70
     characters a segment (`getMessageInfo` in `src/lib/sms/nudge-templates.ts` computes
     this but nothing gates on it).

  The structural cause (Ruling 7) carries the "why" safely: it is always true, always short,
  and never private. **If a guest-facing sentence is genuinely wanted, it is a new captured
  field with its own UI and validation — a separate ticket, not a read of this one.**
- **`sendSms`, `shouldUseTnz`, `TNZ_COUNTRY_CODES`** (`src/lib/sms/send-sms.ts`) — settled.
  Every send in this ticket goes through `sendSms`; nothing writes to a provider directly.
- **Zone 7 (opt-out).** Read from, never modified. No bespoke send path — `sendSms` writes
  the `NUDGE_SENT_AUTO` row the STOP attributor depends on, and a path that skipped it would
  break opt-out attribution silently (the reason recorded atop `decide-by-sender.ts`).
- **`nudge-eligibility.ts` beyond the one `hasResponded` expression.** The 24h gate, the
  48h clock, the cadence and `findRsvpFollowupCandidates` (a neutralised stub — do not
  revive it, [[GTC-175]] owns that) are untouched.
- **The two bespoke person→channel lookups that already exist** —
  `findProxyNudgeCandidates` and `resolveManualNudgeRecipient`. The new resolver is used by
  D3 only. Consolidating all three is a later ticket; doing it here triples the blast radius
  of a send-path change.
- **`prisma/migrations/`** is Zone 5 — generated by `prisma migrate dev`, never hand-edited.
- **The item's own state.** This ticket sends a message; it does not change item status,
  re-run `repairItemStatusAfterMutation`, or alter what the release routes do.

## How rulings 7 and 9 were derived

Kept because the derivation is what stops the rulings being re-litigated.

### Ruling 7 — "the reason, when known": what the hook can actually see

**What is visible.** The hook receives `changeSetId`, and `recordChange` has already written
the `AuditEntry` rows under it. Joining on `changeSetId` recovers, without any signature
change:

| Fact | Column | What it distinguishes |
|---|---|---|
| Who acted | `actorKind`, `actorId`, `actorName` | HOST / COHOST / COORDINATOR / GUEST / SYSTEM |
| What happened | `actionType` | `MOVE_ASSIGNMENT` (someone else has it) vs `DELETE_ASSIGNMENT` (the ask is gone) |
| Their own last answer | `before.response` | PENDING / YES / NO / MAYBE |
| The why | `reason` | Free text, optional, **never enforced** |
| Was a why owed | `reasonRequired` | T1 fired |

**What is not visible.** At call site 5 there is no changeSet at all ([[GTC-232]]) — cause
and reason are both unknown there, structurally.

**The premise in the brief needs correcting.** The brief distinguishes *"a host-initiated
reassignment"* from *"a guest-initiated drop"* where "the person already knows why".
**There is no guest-initiated drop path** — see the inventory above. The distinction that
actually exists in the data is different, and sharper:

- **`MOVE_ASSIGNMENT`** — the ask is now someone else's. "It's covered" is **true**.
- **`DELETE_ASSIGNMENT`** — the ask is withdrawn and the item returns to `UNASSIGNED`.
  "It's covered" is **false**. Two of the four existing call sites and all of site 5 are
  this shape. A single template built from Hinge §8's line ("all good, the pavlova's
  covered") would state something untrue on the majority of releases.

**And there is a reason not to quote `AuditEntry.reason` to the guest.** That field is
scoped, in the ledger's own documentation, as *Kate's own memory* — Hinge §2: the reason
"is not compliance — it's her own memory", and `recordChange` is explicit that it may be
absent and must never be demanded. Reading it verbatim to a third party repurposes a private
field as outbound copy. It is also unbounded (SMS segments) and unmoderated: *"swapped, hers
is better"* is a plausible private note and an unacceptable text message.

**The three options considered, and the two rejected:**

1. **Structural reason only — two templates keyed on `MOVE` vs `DELETE`. ✅ RULED (Ruling 7.)**
   "Known reason" means the *structural cause*, which is always safe to say and is true at
   every call site. Site 5 and any missing changeSet fall to the `DELETE` shape, which is
   what actually happened there. No private field leaves the ledger. Two short templates.
2. **One conditional template appending `reason` when non-null. ❌ REJECTED.** Cheapest to
   write; publishes a field the ledger promises is private; unbounded length; no moderation.
   The full reasoning is recorded under *Do not touch*, because that is where an executor
   tempted to add it will be looking.
3. **Capture a separate guest-facing sentence at the reassign UI. ❌ OUT OF SCOPE.** Correct
   in the long run — new field, new UI, new validation, and it changes what four routes
   accept on the wire. A ticket, if it is ever wanted.

**Which template fires is re-derived at send time**, falling back to the recorded
`actionType` when the item has since been deleted — scope item 5. The sweep runs later, and
an item reassigned at 02:00 can be unassigned again by 08:00; the recorded action is what
was true then, and the guest reads it now.

### Ruling 9 — the CHILD branch

Derived from the same inventory: every finder in the house runs the child gate first and
**skips**, and none substitutes a recipient at that point. The reasoning for holding the
household-proxy reading out of scope is recorded in full under Ruling 9 itself.

### The ledger gap on the team-change path — filed, not fixed

**Filed as [[GTC-232]]** in this session, as a stub, per Ruling 4. Scope named there: `PATCH`
in `src/app/api/events/[id]/people/[personId]/route.ts` deletes a person's assignments on a
team change and writes no `AuditEntry` — a T1 change that touches someone, invisible to the
ledger, in a route that imports `recordChange` and never calls it. The stub also records the
two adjacent facts found while verifying this ticket's fifth call site (no transaction
around the multi-step mutation; a broad `item.updateMany` in place of
`repairItemStatusAfterMutation`) so they are not re-derived. **Not fixed here.**

## Migration protocol — binding

The database is still coupled to production even with auto-deploy off.

1. **Plan mode at build time.** The migration is designed and approved before it is
   generated.
2. **Stop Condition 7 fires by construction** (Rulings 2 and 8). It is pre-declared here
   rather than discovered mid-build — but the executor still stops and reports the concrete
   migration before running it.
3. **Rehearse against a copy of the production DB before it runs.** Restore a copy, apply,
   confirm `prisma migrate status` clean and **both** enum values present, and record the
   result in Evidence. Two additive enum values are low-risk in principle; "in principle" is
   not the standard this repo uses for a prod-coupled database.
4. No data backfill is required — every existing row keeps its existing type, and both new
   values start unused.
5. **One migration, both values.** Splitting them across two migrations buys nothing and
   leaves a commit in history where the record type exists with no way to mark it consumed.

1. **Real NZ delivery is TNZ-gated.** `sendSms` returns `blocked: 'SMS_DISABLED'` for `+64`
   without `TNZ_AUTH_TOKEN`, which is absent on every dev machine. D3 is built and tested

   seed scripts already violate it. The resolver must not assume `+64`, and must not call
   `isValidNZNumber` (which would reject the `+61` numbers `sendSms` routes to TNZ
   deliberately — `findDecideByFollowupCandidates` records this).
3. **`Person.phone` vs `Person.phoneNumber`.** Two fields, one normalised and one not.
   The resolver reads `phoneNumber` only. Whether `phone` is backfilled and dropped is a
   schema question and is [[GTC-214]]'s recorded non-scope, not this ticket's.
4. **[[GTC-229]] has no file, by design.** [[GTC-214]] references it (inbound signature
   verification) and `docs/tickets/GTC-229.md` does not exist at `176e9cc`. **This is not a
