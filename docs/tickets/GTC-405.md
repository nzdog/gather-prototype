## What a host sees now (Moment 2's edit box)

Pressing "Edit" on a dish in Moment 2's plan opens the edit box as
before: Name, Quantity, Serves, the note, and (on a food dish) the five
marks. Under them, on a DISH, two new boxes:

- "Drop-off place", showing the hint "e.g. the back door" when empty.
- "Drop-off time", showing the hint "e.g. 11am" when empty.

Both are filled from the dish when it has its own place or time. The
note's box is now labelled "Note for the guest" (it was "Notes"); its
hint "Optional" and what it saves are unchanged.

Saving sends the place as `dropOffLocation` and the time as
`dropOffNote` through the host's existing edit route
(`PATCH /api/events/[id]/items/[itemId]`, unchanged), each ONLY when it
changed, so a save that leaves them alone sends exactly what it sent
before. An emptied box sends `null`, which clears it. After the save the
row shows the dish's own drop-off at once ("Drop-off: the back door ·
By: 11am").

A JOB ("Set the tables") gets no drop-off boxes: a job is not dropped
off. That is my reading of "a dish has its own drop-off"; say if a job
should have them too.

How the route treats an empty string, checked: it stores whatever it is
sent (`if (body.dropOffLocation !== undefined) updateData.dropOffLocation
= body.dropOffLocation`), so an empty string would be stored as an empty
string. The screens' `DropOffDisplay` happens to hide an empty string
(it tests truthiness), but the box sends `null` for an empty box anyway,
as the prompt asked, so nothing blank is ever stored by this box. A
stored blank (from older data) is treated as "none", so it never counts
as a change by itself.

## The "why" prompt when a drop-off is edited (reported, not changed)

The route's own rule (GTC-183's why-scope, `whyTrigger` in
src/lib/ledger.ts) counts `dropOffLocation`, `dropOffNote` and
`dropOffAt` as ASK fields: changing them changes what the ask says. So:

- On an event that has been SENT, changing a dish's drop-off place or
  time when the guest holding it has ANSWERED (yes, no or maybe), the
  setup page asks first, with the existing prompt: "You're changing an
  ask someone's already answered." She can write why, skip it, or cancel
  (cancel saves nothing). The why, or "skipped", goes in the change log
  with the change.
- Not yet sent, or nobody holds the dish, or the guest has not answered
  yet (PENDING): nothing is asked; the change just saves.
- Clearing a drop-off counts as a change too (same rule).
- The guest is NOT told: the rule asks the host why and records it, and
  no message goes to the guest from this edit.
- One thing I noticed in passing (not tested): the edit box always sends
  the unit as "CUSTOM", so on an answered dish of a sent event a dish
  whose unit was stored as, say, "TRAYS" may raise the prompt on any
  save, drop-off or not. That is older than this ticket.

The suite's layer P records the rule's answers for a drop-off change.
