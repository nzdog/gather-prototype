# GTC-221 — Triage lint findings surfaced by the eslint-config-next fix

**Status:** Open — unassigned, not started. **Effort:** TBD (needs scoping when pulled)
**Severity:** Low (existing lint findings, not a regression — they were latent while lint was
crashing, not introduced by the fix)

### Context

`eslint-config-next` was pinned to `^16.2.2` against `next@15.5.14` — a major-version mismatch
that made `next lint` crash with a circular-JSON error before it ever reached rule evaluation
(see the eslint-config-next fix commit, this session, 2026-08-06). With the version corrected
to `^15.5.22`, `npm run lint` now runs to completion and surfaces **68 pre-existing errors and
43 warnings** that were sitting underneath the crash the whole time.

Fixing the version also made `next build`'s internal ESLint step run for the first time (it was
previously crashing there too, but the crash was non-fatal to the build, so `npx next build` was
passing vacuously — the linter never actually ran). With the crash fixed, the build started
failing for real on these same 68 errors, so `next.config.js` now sets
`eslint.ignoreDuringBuilds: true` to decouple the build gate from this deferred work.

Breakdown, by rule, from the first clean run:

- `react/no-unescaped-entities` — the bulk of the errors, scattered across `src/components/plan/`
  and `src/components/templates/` (unescaped `'`/`"` in JSX text).
- `react-hooks/exhaustive-deps` — the bulk of the warnings, scattered across the same
  directories (`useEffect`/`useCallback` missing dependencies).
- One config-level finding, not a code finding: `@typescript-eslint/no-require-imports` —
  "Definition for rule ... was not found" at `src/lib/vcard.ts:18`. This is the ruleset itself
  missing a rule definition, not a violation in `vcard.ts`; needs its own diagnosis (likely an
  eslint-config-next/typescript-eslint version-alignment gap, same family as the bug that
  created this ticket).

### Scope

**Fix here:** to be ruled when pulled. This ticket is filing only — the findings are not fixed
as part of it.

**Explicitly NOT a batch auto-fix task.** `react-hooks/exhaustive-deps` in particular requires
per-case judgment: mechanically adding every flagged dependency to a `useEffect`/`useCallback`
array can change when the effect re-runs and introduce new bugs (extra re-renders, refetch
loops, stale-closure fixes that aren't actually needed) rather than fix anything. Each flagged
hook needs to be read and understood individually — is the missing dependency actually safe to
add, does the effect need restructuring, or is the array intentionally incomplete — not swept
with a single lint --fix pass. The `react/no-unescaped-entities` findings are lower-risk
(cosmetic JSX-escaping) and may be reasonable to batch, but confirm that scoping decision
explicitly when this is pulled rather than assuming both rule classes get the same treatment.

### Acceptance

To be defined when scoped. At minimum: a decision recorded on how many of the 68/43 to fix in
this pass vs. defer further, and the `@typescript-eslint/no-require-imports` config gap
diagnosed (root cause, not just suppressed).

**End-state, not open-ended:** `next.config.js`'s `eslint.ignoreDuringBuilds: true` is a
deliberate temporary state, not a silent permanent one. Clearing the findings this ticket
tracks (or explicitly re-ruling that some are staying, e.g. wontfix) is the precondition for
flipping it back to `false` so the build resumes lint-gating for real. Closing this ticket
without flipping the flag back leaves the build vacuously green again — don't do that silently.
