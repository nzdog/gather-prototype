# GTC-221 — Triage lint findings surfaced by the eslint-config-next fix

**Status:** Open — unassigned, not started. **Effort:** TBD (needs scoping when pulled)
**Severity:** Low (existing lint findings, not a regression — they were latent while lint was
crashing, not introduced by the fix)

### Context

`eslint-config-next` was pinned to `^16.2.2` against `next@15.5.14` — a major-version mismatch
that made `next lint` crash with a circular-JSON error before it ever reached rule evaluation
(see the eslint-config-next fix commit, this session, 2026-08-06). With the version corrected
to `^15.5.22`, `npm run lint` now runs to completion and surfaces **68 pre-existing errors and
43 warnings** that were sitting underneath the crash the whole time.

**Update, 2026-08-23 — current count is 56 errors / 43 warnings, not 68/43. Root cause below;
not fixed, per this ticket's own explicit "not a batch auto-fix task" scope.**

During Dependabot triage (GTC-243), re-running `next lint` on `feat/moment-one-redesign` showed
56 errors instead of the 68 recorded above, with warnings unchanged at 43. A lockfile-only fix
(`brace-expansion`/`js-yaml`, unrelated ESLint-toolchain packages) was ruled out first by A/B
testing the vulnerable-vs-patched versions — output was byte-identical either way. To find the
real cause, I checked out commit `b6e6e38` (the exact commit that filed this ticket) in an
isolated `git worktree`, ran `npm install` + `next lint` there, and reproduced **68/43 exactly**
— confirming the original count was accurate and the drift happened afterward, on this branch.

**No `.eslintignore`, `eslintConfig` block, or `next.config.js` `eslint.dirs` restriction exists
at either commit — the linted scope is Next's unmodified default in both runs.** The drift is
not a scope/config change; it's the file set on disk changing:

- **`src/app/demo/review/page.tsx` was deleted** (commit `3eaa2fe`, "docs(GTC-240): drop
  /demo/review page and update guide references"). At `b6e6e38` this file alone carried **13 of
  the 68 errors** (all `react/no-unescaped-entities`) and 1 of the 43 warnings
  (`react-hooks/exhaustive-deps`). Deleting the file deleted its findings — not because the
  underlying JSX text was ever fixed, but because the file it lived in no longer exists.
- **`src/app/plan/[eventId]/setup/page.tsx` is a new file** (commit `06fbeee`,
  "refactor(GTC-233): extract V2 to /plan/[eventId]/setup, retire ?setup=true"), carrying 1 new
  error (`@next/next/no-html-link-for-pages`, an `<a>` tag written in the extracted code that
  should be `<Link>`) and 1 new warning (`react-hooks/exhaustive-deps`).
- **Every other file's findings are byte-for-byte identical** between the two runs — same rule,
  same message, same file — confirmed by a full per-file diff of finding text, not just counts.
  Line numbers shift in three files (`plan/[eventId]/page.tsx`, `plan/events/page.tsx`,
  `plan/new/page.tsx`) purely because unrelated code was added/removed above the flagged lines
  elsewhere in those files (e.g. code moving out to the new `/setup` route); the violations
  themselves are unchanged and unfixed.

**Net arithmetic, exact:** errors 68 − 13 (deleted file) + 1 (new file) = **56**. Warnings
43 − 1 (deleted file) + 1 (new file) = **43** (explaining why the warning count looked
unchanged despite churn underneath it — one warning left, a different one arrived).

**The distinction that matters: this is files no longer linted, not errors fixed.** Not one of
the original 68 errors was resolved in place by anyone reading and fixing the offending JSX.
55 of the original 68 are still sitting in the codebase today, unaddressed, just relocated to
different line numbers or renumbered among the 56. This ticket's own findings (below) are
otherwise unaffected — the `react/no-unescaped-entities` / `react-hooks/exhaustive-deps` /
`@typescript-eslint/no-require-imports` breakdown still holds; `@next/next/no-html-link-for-pages`
should be added as a fourth named category (4 occurrences: 3 pre-existing at the `b6e6e38`
baseline but not individually called out in the original breakdown below, 1 newly introduced by
GTC-233).

**68 → 56 is not a progress metric — do not read it as one.** Zero of the original 68 errors were
fixed in place. 55 remain in the code today, unaddressed. The drop is entirely mechanical: 13
errors left because their file was deleted (GTC-240), and 1 new error arrived from unrelated new
code (GTC-233) — 68 − 13 + 1 = 56. A future reader seeing the count fall should not conclude any
triage or cleanup happened here; none has. The only ticket that changes this number by actually
fixing something is this one, and it hasn't been picked up yet.

**Mechanism note: GTC-233's new violation landed without objection because
`eslint.ignoreDuringBuilds: true` (set in `b6e6e38`) means `next build` does not gate on lint.**
The `<a>` tag in `src/app/plan/[eventId]/setup/page.tsx` that should be `<Link>` was written,
reviewed, and shipped in commit `06fbeee` with nothing in the build pipeline flagging it — the
same silent-pass condition this ticket exists to end. This is the mechanism by which the count
will keep growing, one unnoticed violation at a time, for as long as `ignoreDuringBuilds` stays
`true`. It is not a one-off; expect more of these until the flag flips back to `false` (this
ticket's own end-state condition, below).

No lint errors were fixed as part of this update — this is a count-and-cause correction only,
per this ticket's standing "not a batch auto-fix task" scope.

Fixing the version also made `next build`'s internal ESLint step run for the first time (it was
previously crashing there too, but the crash was non-fatal to the build, so `npx next build` was
passing vacuously — the linter never actually ran). With the crash fixed, the build started
failing for real on these same 68 errors, so `next.config.js` now sets
`eslint.ignoreDuringBuilds: true` to decouple the build gate from this deferred work.

Breakdown, by rule, from the first clean run:

- `react/no-unescaped-entities` — the bulk of the errors, scattered across `src/components/plan/`
  and `src/components/templates/` (unescaped `'`/`"` in JSX text).
- `react-hooks/exhaustive-deps` — the bulk of the warnings, scattered across the same
  directories (`useEffect`/`useCallback` missing dependencies).
- One config-level finding, not a code finding: `@typescript-eslint/no-require-imports` —
  "Definition for rule ... was not found" at `src/lib/vcard.ts:18`. This is the ruleset itself
  missing a rule definition, not a violation in `vcard.ts`; needs its own diagnosis (likely an
  eslint-config-next/typescript-eslint version-alignment gap, same family as the bug that
  created this ticket).
- **[Added 2026-08-23 — present in the original 68, not individually named at the time]**
  `@next/next/no-html-link-for-pages` — 3 occurrences at the original baseline
  (`src/app/demo/page.tsx:436`, `src/app/page.tsx:135`, `src/app/privacy/page.tsx:199`), each an
  `<a>` tag that should be `<Link>` from `next/link`. A 4th occurrence was introduced afterward
  by GTC-233's route extraction (`src/app/plan/[eventId]/setup/page.tsx`) — see the 2026-08-23
  update above.

### Scope

**Fix here:** to be ruled when pulled. This ticket is filing only — the findings are not fixed
as part of it.

**Explicitly NOT a batch auto-fix task.** `react-hooks/exhaustive-deps` in particular requires
per-case judgment: mechanically adding every flagged dependency to a `useEffect`/`useCallback`
array can change when the effect re-runs and introduce new bugs (extra re-renders, refetch
loops, stale-closure fixes that aren't actually needed) rather than fix anything. Each flagged
hook needs to be read and understood individually — is the missing dependency actually safe to
add, does the effect need restructuring, or is the array intentionally incomplete — not swept
with a single lint --fix pass. The `react/no-unescaped-entities` findings are lower-risk
(cosmetic JSX-escaping) and may be reasonable to batch, but confirm that scoping decision
explicitly when this is pulled rather than assuming both rule classes get the same treatment.

### Acceptance

To be defined when scoped. At minimum: a decision recorded on how many of the current 56/43
(originally 68/43 — see the 2026-08-23 update above for why the count moved) to fix in this pass
vs. defer further, and the `@typescript-eslint/no-require-imports` config gap diagnosed (root
cause, not just suppressed). Whoever scopes this next should re-run `next lint` fresh rather than
trusting either number as current by then — this ticket has already drifted once from unrelated
file churn, and will again.

**End-state, not open-ended:** `next.config.js`'s `eslint.ignoreDuringBuilds: true` is a
deliberate temporary state, not a silent permanent one. Clearing the findings this ticket
tracks (or explicitly re-ruling that some are staying, e.g. wontfix) is the precondition for
flipping it back to `false` so the build resumes lint-gating for real. Closing this ticket
without flipping the flag back leaves the build vacuously green again — don't do that silently.
