# GTC-304 — A kind change is a change to the ask, and the ledger does not see it as one

**Status:** Open — filed, not executed. Filed 2026-09-13 | **Branch:** TBD
**Severity:** [ ] Critical [ ] High [x] Medium [ ] Low — **set by the founder, as proposed:**
*"GTC-303 and GTC-304: severity MEDIUM on both, as proposed."* Proposed at filing as Medium; the
frontmatter's `severity` records the set value, and `severity_proposed` keeps the proposal. The
founder: it *"matters more"* than [[GTC-303]].
Escalated (brand/trust risk): [ ] No

**Filed on the founder's instruction**, from [[GTC-302]] *Founder answers — the build*, choice 4:

> Choice 4 — a kind change not counting as a change to what the guest was asked. Wrong the other
> way, and it matters more. Changing a dish to a job changes the sentence the guest receives, from
> "would you bring" to "would you do". On an answered row that is a material change to an ask
> someone has already said yes to.
> File it against the material-change machinery rather than fixing it here — but say in the ticket
> that this is a change to the ask, not a reclassification, because the composer reads kind to
> choose the verb.

**Said plainly, as the founder asked: changing a row's kind is a change to the ask, not a
reclassification.** The composer reads the kind to choose the verb. `whatIsAsked` in
`src/lib/messages/ask-register.ts` says *"bring"* of an `ITEM` and *"do"* of a `TASK` ([[GTC-189]]
answer 6), so a dish made a job turns *"Would you bring the trestle tables?"* into *"Would you do the
trestle tables?"* — and back the other way. On an answered row, the guest said yes to the first
sentence.

---

### Signal

**Expected**
On a sent event, an `EDIT_ITEM` change to `kind` on an answered row fires T4, exactly as a change to
its name does: the flow asks the host for a why, and the ledger records the change as one that touches
someone.

**Actual**
- `kind` is versioned — [[GTC-302]] put it in `TRACKED_ITEM_FIELDS` in `PATCH` in
  `src/app/api/events/[id]/items/[itemId]/route.ts` — but it is **not** in `ASK_FIELDS` in
  `src/lib/ledger.ts`.
- `whyTrigger` in `src/lib/ledger.ts` returns T4 for an `EDIT_ITEM` only when the field is in
  `ASK_FIELDS` and the row has been answered (a response that is neither null nor PENDING). For
  `kind` it returns null whatever the response.
- So `recordChange` writes `reasonRequired: false`, `touchesSomeone` says the change touches nobody,
  and `ReasonPrompt` in `src/components/plan/ReasonPrompt.tsx` — which asks by `whyTrigger` — never
  asks.
- Seen during [[GTC-302]]'s browser walk: `EDIT_ITEM` on `kind`, TASK→ITEM and ITEM→TASK, recorded
  with `reasonRequired` false. That row was unassigned on a DRAFT event, where false is right; the
  answered case is by reading `whyTrigger`.

**Where it belongs — the material-change machinery, as the founder directed.** T4 is [[GTC-196]]'s:
*"an `ASK_FIELD` moved on an answered item"*. The ledger underneath is [[GTC-168]]'s. `ASK_FIELDS` is
documented as *"defined by the spec, not by taste"*, so adding `kind` to it is a reading of the spec,
not a code preference. **A separate question, not answered here:** whether a changed verb should also
RE-ASK the guest, as [[GTC-183]] (F1) is to do for date and venue through `onMaterialChange` in
`src/lib/ledger.ts`. T4 asks the host for a why; it does not tell the guest anything.

**Smallest failing case**
`whyTrigger` on a sent event, for an `EDIT_ITEM` with `field: 'kind'` and
`context.assignmentResponse: 'ACCEPTED'`, returns null. The same change with `field: 'name'` returns
`'T4'`.

**Silent today, twice over.** No edit screen sends `kind` — `EditItemModal`, `ItemEditForm` in
`src/components/plan/Moment2PlanView.tsx` and the coordinator's edit do not — so only the API can
change it. And the pre-flight preview hands composition no kind until [[GTC-189]] slice 3 splits jobs
from dishes, so the verb a guest would read does not follow the kind yet either. Both end: an edit
form offering the toggle makes the change reachable, and slice 3 makes the verb move with it.

**Steps**

true on the name change's.

### Acceptance

Not written. At minimum: on a sent event, a kind change on an answered row fires T4 and the host is
asked for a why, as a name change is; on an unanswered or unassigned row it does not; and the
`[DEFECT GTC-304]` assertion changes with the fix.

---

### Unknowns

1. **The spec reading.** Which passage makes a field an ask field, and whether the verb — not only
   the noun, the quantity and the drop-off — is what a guest *"claimed against"*.
2. **The re-ask.** Whether a changed verb on an answered row also goes back to the guest, and whose
   ticket that is. [[GTC-183]] covers date and venue only.
3. **The asked-but-unanswered row.** `whyTrigger`'s typo rule gives a PENDING row no why. A guest who
   has been sent *"bring"* and not yet replied still read *"bring"*. Whether that is still the typo
   case for a verb is not ruled.
