# GTC-094 — Fix: conflict list flash and stale conflict count after resolution — CLOSED

**Status:** Complete | **Branch:** master | **Commit:** [pending]

### What was found

**Bug 1 — "No conflicts found" flash:**

- `ConflictList` has an empty-state branch at `conflicts.length === 0`. When `hasRunCheck` is true (check has run before) and `conflicts` is momentarily empty during a re-check, the component renders "No conflicts found" for one render frame before new results arrive.
- The `isCheckingPlan` prop was already defined on the `ConflictListProps` interface but was only passed to the second ConflictList instance (expanded modal). The first (hidden dashboard) instance always saw `isCheckingPlan=false`.
- The empty-state branch had no guard for `isCheckingPlan`, so it rendered the "No conflicts found" message even while a check was in progress.

**Bug 2 — Stale conflict count after resolution:**

Investigation of all five ConflictList handlers:
1. `handleResolve` — has `onConflictsChanged?.()` (line 56). OK.
2. `handleDismiss` (used for Ignore) — has `onConflictsChanged?.()` (line 74). OK.
3. `handleDelegate` — has `onConflictsChanged?.()` (line 93). OK.
4. `handleAcknowledgeSubmit` — has `onConflictsChanged?.()` (line 151). OK.
5. `handleAcceptAISuggestion` — has `onConflictsChanged?.()` (line 121). OK.

All five handlers correctly call `onConflictsChanged`. No local optimistic state in ConflictList — it uses the `conflicts` prop directly from the plan page.

The `conflicts` state variable updated by `loadConflicts` (line 510) is the same one read by the Plan Status card count (line 1816 `conflicts.length`). The conflicts API endpoint filters to OPEN/ACKNOWLEDGED/DELEGATED by default (line 37 of conflicts/route.ts), so resolved/dismissed conflicts are correctly excluded on re-fetch.

The root cause of the stale count: `onConflictsChanged` was wired directly to `loadConflicts` but did NOT trigger `setGateCheckRefresh`. The GateCheck and FreezeCheck components rely on `gateCheckRefresh` to know when to re-evaluate their readiness state. Without this trigger, those components showed stale data after conflict resolution actions.

### What was changed

**`src/components/plan/ConflictList.tsx`:**
- Added `isCheckingPlan` guard as the first check in the `conflicts.length === 0` branch. Returns `null` during a check to avoid flashing "No conflicts found". The Check Plan button already shows a spinner, so the user has feedback.

**`src/app/plan/[eventId]/page.tsx`:**
- First ConflictList instance (hidden dashboard): added `isCheckingPlan={isCheckingPlan}` prop.
- Both ConflictList instances: updated `onConflictsChanged` from `loadConflicts` to an inline handler that calls both `loadConflicts()` and `setGateCheckRefresh((prev) => prev + 1)`, ensuring GateCheck/FreezeCheck re-evaluate after conflict resolution.

### Known limitations

- The `isCheckingPlan` guard returns `null` (empty render) during a check. This means if the user was looking at the conflict list area, they see a brief blank space instead of a loading skeleton. This is acceptable because the Check Plan button already shows a spinner with "Checking..." text.
