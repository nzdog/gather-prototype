### ✅ SCOPED 2026-09-30 — FOUNDER RULINGS (in Cowork, one question at a time)

This ticket's two Unknowns, and the reminder cron's health question raised at [[GTC-189]] slice 8b
(the *"ITS HEALTH IS STILL GTC-214's"* note above `runNudgeScheduler` in
`src/lib/sms/nudge-scheduler.ts`), were ruled here before any plan was written. Each ruling is
recorded as asked and as answered.

**Q1 — when should a sending cron report a failed run?** Asked of the three crons this ticket
names (outbound-dispatch, wrap-up-dispatch, decide-by-followups), with four options: per channel;
the whole run, [[GTC-214]]'s rule as `isNudgeRunHealthy` has it; any failure; and setup checked on
every run (which would need a Zone 6 edit, and a job failing every run is switched off by
cron-job.org after 25 failures in a row). The founder chose, verbatim: *"Per channel
(Recommended)"* — *"Fails if it tried to send texts and none got out, or tried emails and none got
out, so broken texting shows up even while emails go fine. Nothing to send: OK. One bad address
among messages that went: OK. A text stopped because texting isn't set up or the live switch is
off counts as not got out. Held back for a reason about the guest or you (an opt-out, your mark, an
answer, a number that isn't valid) never counts. The security test stays as it is."*
- **Unknown 1, answered:** a run is unhealthy when, on either channel, it had sends to make and
  none of them got out. Stops caused by configuration or the live switch count when there was
  something to send; a run with nothing to send stays healthy.
- **Unknown 2, answered:** a `SMS_DISABLED` withholding (no provider, or the live switch off)
  counts as not got out for health. It stays a withholding in the row, terminal, as ruled on
  2026-09-19; only the health reading changes. A withholding for a reason about the guest or the
  host never counts.

**Q2 — the reminder cron, `/api/cron/nudges`.** Asked with the fact stated: since slice 8b it
queues and sends nothing, yet `isNudgeRunHealthy` still fails it whenever no text provider is
configured or the live switch is off, even with nothing to do. The founder chose, verbatim: *"Its
own job (Recommended)"* — *"Reports 'failed' only when it can't line reminders up. Send failures
are the sending job's to report, under the per-channel rule you just chose. Removes an alarm that
would fire every 15 minutes if production ever had no text provider set up. cron-job.org switches
a job off after more than 25 failures in a row (about six hours here), which would stop every
reminder, email ones included."*

**Found while scoping, 2026-09-30 — for the deploy, not for this ticket's code.** Railway does not
read `vercel.json`, so none of its four schedules runs in production; production's crons are
called by an outside scheduler ([[GTC-042]] set up cron-job.org for the nudges cron; [[GTC-220]]
speaks of EasyCron jobs for all three). `/api/cron/outbound-dispatch` ([[GTC-189]] slice 5) is
registered only in `vercel.json`, so no production scheduler calls it yet — and without it nothing
the press queues is ever sent. The founder's [[GTC-270]] undertaking (2026-09-11) to answer "what
calls these" from the platform logs before anything deploys stands. Two deploy steps follow: add
the outbound-dispatch job at every 2 minutes, and turn on the scheduler's failure emails, so this
ticket's failed runs reach the founder. To be recorded in GTC-189's gathered list with this
ticket's commit.

### Signal

[[GTC-214]]'s contract: *a cron that cannot send must not report a healthy run.* The nudges cron
meets it: `GET` in `src/app/api/cron/nudges/route.ts` takes `success` and its status code from
`runNudgeScheduler`'s `ok`, which `isNudgeRunHealthy` in `src/lib/sms/nudge-scheduler.ts`
derives (and which [[GTC-274]] extended to count the live switch being off).

The other three crons do not. Each answers **200 with `success: true`** unless its handler
throws. The failure counts are in the body, but the status and `success` say the run was healthy:

- `/api/cron/outbound-dispatch`: `enrolMiniSends`, `drainOnce` and `pollOnce`. Rejected and
  withheld counts are in the body.
- `/api/cron/wrap-up-dispatch`: `dispatchPendingWrapUpMessages` in `src/lib/wrap-up.ts`, with
  `failed` in the body.
- `/api/cron/decide-by-followups`: `runDecideByFollowups`, with `failed` and `errorCount` in the
  body.

So a production with no provider configured, or with the live switch off, would show three green
crons that sent nothing. A monitor watching status codes would see nothing wrong.

### Constraint to carry into scoping

`tests/security-validation.ts` (Zone 6), suite 12, pins **200** on the valid-secret drives of
wrap-up-dispatch and decide-by-followups. Those drives run only when their preconditions hold, so
there is nothing to send. A fix therefore has to keep a run with nothing attempted healthy, the
way `isNudgeRunHealthy` treats an idle or quiet-hours run, or it needs a founder-approved Zone 6
edit.

## Evidence (Executor-Completed)

**Root cause confirmed**

`handleRequest` in each of `src/app/api/cron/outbound-dispatch/route.ts`,
`src/app/api/cron/wrap-up-dispatch/route.ts` and `src/app/api/cron/decide-by-followups/route.ts`
returned `{ success: true, ... }` with no status on its try path. So a run answered 200 however
many of its sends failed, and only a throw reached the 500. Separately, `runNudgeScheduler` in
`src/lib/sms/nudge-scheduler.ts` took `ok` from `isNudgeRunHealthy({ smsConfigured, live, attempted:
0, succeeded: 0 })`. That read only configuration and the switch, so it failed every run with no
provider or the switch off, although since GTC-189 slice 8b the run sends nothing.

**The fix, as ruled**

- `sendRunHealth` in `src/lib/send-health.ts`: a channel fails when `toSend > 0 && gotOut === 0`;
  the run is `ok` when no channel failed. `tallySend` adds one `GOT_OUT`, `NOT_OUT` or
  `NOT_COUNTED`. `SMS_BLOCK_COUNTS` (a `Record<SmsBlockReason, boolean>`) says `SMS_DISABLED` and
  `SEND_FAILED` count, and `OPTED_OUT` and `INVALID_NUMBER` do not.
- `WITHHELD_COUNTS_FOR_HEALTH` in `src/lib/press/dispatch.ts`, beside `WITHHELD_WHY_IS_TERMINAL`: a
  `Record<OutboundWithheldWhy, boolean>` in which only `SMS_DISABLED` is true (ruling C:
  `NO_LINK` is not). `withholdAndTally` records a withholding and tallies it only when this run
  wrote it. `DrainResult.tally` holds the tick's counts, including the chase rows.
- The wrap-up returns `tally`. `DecideByFollowupResult` gains `channel` and `outcome`, and
  `processDecideByFollowups` and `runDecideByFollowups` return `tally`.
- Each sending route: `success: health.ok`, `{ status: health.ok ? 200 : 500 }`, and a `health`
  field with each channel's counts and `failedChannels`. In outbound-dispatch the verdict is
  computed after the poll's own `try`, from the drain's tally alone.
- `runNudgeScheduler`: `ok` is true on the try path and false in the catch. `isNudgeRunHealthy`
  and its `isLiveSendingOn` import are deleted (ruling B). `smsConfigured` stays, as a report.
