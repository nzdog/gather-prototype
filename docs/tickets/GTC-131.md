# GTC-131 — Extract `<OptionTree>` shared component from GuidedPlanBuilder — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** [pending]

### What was found

The multi-level cascading option-tree mechanic was locked inside
`src/components/plan/GuidedPlanBuilder.tsx` (860 lines). Three pieces of logic
made up the mechanic:

1. **Cascade resolver** — `resolveOptionGroups` (line 340), which reads parent-
   level selections and groups child options by which parent option produced
   them. In the deployed config, the parent is always level index 0 (no
   multi-hop chains exist).
2. **Mutators** — `toggleOption` (line 388) and `setFreeText` (line 403),
   inner closures over `setSelections`.
3. **Per-level rendering** — the option-list + free-text JSX inside
   `renderCategoryScreen` (lines 651–771).

The wizard navigation (overview → category screen → review) is **not** part of
the option-tree mechanic; it is GuidedPlanBuilder-specific UX scaffolding.

Inspection of `src/lib/ai/plan-option-tree-config.json` revealed several
divergences from the API shape proposed in the ticket — the actual config is
the source of truth and was matched verbatim. See **Component API** for the
divergences.

### What was changed

- **Created** `src/components/shared/OptionTree.tsx` (219 lines).
  - Fully controlled (no internal selection state).
  - Renders all levels for one category, stacked vertically. Designed to slot
    into an accordion panel for GTC-133.
  - Cascading visibility via `dependsOn` (flat shape: `Record<parentOption,
    string[]>`) — child levels show options grouped by the parent option that
    surfaced them.
  - Single-select (`multiSelect: false`) and multi-select (default) supported.
    Single-select uses radio inputs; multi uses checkboxes.
  - Free-text input rendered when `level.freeText` is true.
  - `disabled` prop disables every input and dims the surface.
  - Tailwind styling consistent with v2 components (sage/accent palette,
    rounded-lg, hover transitions). No lucide-react icons needed for this
    surface.
  - JSDoc usage example included on the default export.
- **No other files modified.** GuidedPlanBuilder, HostDescriptionModal,
  Moment2Step1Modal, Moment2PlanView, the config JSON, the AI generation
  endpoints, and the EventSetup persistence flow are all untouched.

### Path (a) vs (b) decision

**Chose Path (b)** — leave GuidedPlanBuilder untouched; ship OptionTree as
unused infrastructure.

Reasons:

1. **Behavioural-change constraint.** The ticket explicitly forbids behavioural
   changes to existing code paths. GuidedPlanBuilder's wizard renders one level
   per screen with Next/Previous navigation; the new component renders all
   levels stacked (the shape GTC-133 needs for accordion content). Refactoring
   GuidedPlanBuilder to consume a stacked component would change behaviour.
   The alternative — making OptionTree support both stacked and per-level
   modes via a `mode` prop — adds branches to a component used by exactly one
   consumer today, violating the project's YAGNI guideline.
2. **Clean isolation.** Path (b) keeps the new component small (219 lines vs
   GuidedPlanBuilder's 860) with a single clear shape. GTC-133 can integrate
   it without unwinding wizard-specific concessions.
3. **Verification.** A JSDoc example demonstrates the API. GTC-133 will
   exercise it in production.

Trade-off accepted: the new component is unverified at runtime until GTC-133
integrates it. The cascade and mutator logic are direct ports of
`resolveOptionGroups`/`toggleOption`/`setFreeText` from GuidedPlanBuilder, so
the runtime risk is bounded.

### Component API

Located at `src/components/shared/OptionTree.tsx`.

```typescript
interface OptionTreeLevel {
  question: string;
  breadcrumbLabel?: string;
  options?: string[];
  multiSelect?: boolean;            // default: true (matches existing behaviour)
  dependsOn?: Record<string, string[]>; // flat shape — parent is always level 0
  freeText: boolean;
  freeTextPlaceholder?: string;
}

interface OptionTreeLevelSelection {
  options: string[];
  freeText: string;
}

type OptionTreeSelections = Record<number, OptionTreeLevelSelection>;

interface OptionTreeProps {
  levels: OptionTreeLevel[];
  selections: OptionTreeSelections;
  onChange: (next: OptionTreeSelections) => void;
  disabled?: boolean;
}
```

**Divergences from the API proposed in the ticket** — config field names won:

| Ticket proposal | Actual API | Reason |
|-----------------|-----------|--------|
| `selectionMode: 'single' \| 'multi'` | `multiSelect?: boolean` | Matches config field name. |
| `freeTextEnabled` | `freeText` | Matches config field name. |
| `OptionTreeOption { id; label }` | `string[]` | Config stores plain strings, not id/label objects. Promoting to objects would require config migration out of scope here. |
| `dependsOn: { levelIndex; map }` (wrapped) | `dependsOn: Record<string, string[]>` (flat) | Config uses flat form for all 56 dependsOn instances; no `levelIndex` field exists anywhere in the JSON. Parent is always level index 0. |
| `levels[]` includes a `level: number` field | omitted | Human-numbered duplicate of array index, not used by the component. |

Types `OptionTreeLevel`, `OptionTreeLevelSelection`, `OptionTreeSelections`,
`OptionTreeProps` are all exported.

### Known limitations

- **Single-hop cascade only.** The component reads parent selections from
  level index 0. Every shipped category in `plan-option-tree-config.json`
  follows this pattern (level 2 depends on level 1; level 3 has no
  `dependsOn`). If a future config introduces multi-hop chains (level 3
  depends on level 2), the resolver needs an explicit parent index — the API
  would extend `dependsOn` to a discriminated union without breaking existing
  configs.
- **Type location.** Types live in `OptionTree.tsx` rather than
  `src/lib/ai/types.ts`. Sharing with server-side prompt compilation
  (`compileGuidedPrompt` in `src/lib/ai/generate.ts`) is currently solved by
  duplicate type declarations there — a tidier fix is its own ticket and out
  of scope here.
- **No runtime verification of the new component yet.** Path (b) ships the
  component unused. GTC-133 will exercise it; if integration reveals an issue
  the cost is a small follow-up patch rather than a rollback of GuidedPlan-
  Builder changes.
- **No automated tests.** Per audit, the codebase has no Jest/Vitest config.
  JSDoc usage example is the only static verification.
