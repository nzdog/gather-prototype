# GTC-192 — J1: The screen — person-primary grid

**Status:** Open | **Branch:** TBD | **Commit:** [pending] (filed `e5f6e82`) | **Effort:** xhigh

### Context

Moment 4 spec §3: the four-second contract — closing it, Kate must know (a) is anything mine to
do, (b) is it moving. Green/orange/red as **ownership, not status**. Behind a tap: all actions
(remind, reassign, take over a silence) — looking never becomes operating. The assistant's one
plain message when a critical item is red. Explicitly refused: messaging/chat, countdown, activity
feed, the plan content itself, analytics/response-rate reporting, progress bars or percentages.

§10.8: **the grid is person-primary.** People are the boxes; items live inside the person. A
person holding items in different states shows the **worst colour**, with all items visible on
tap. "Is the lamb covered?" is answered by the badge (J2, GTC-193) and the assistant's message,
not by inverting the grid.

Today: the Moment 4 screen doesn't exist in code at all — confirmed across every territory in the
discovery report. This ticket is the first thing that builds it, so §10.8 fixes the target data
shape before any code is written: a person-keyed read API, not an item-keyed one.

### Scope

**Fix here:**
- A person-keyed read API assembling per-person state from B1's criticality (GTC-170), D1's
  response model (GTC-174), and E1's nudge/colour state (GTC-178).
- The grid itself: person-primary boxes, worst-colour-wins when a person holds mixed-state items,
  all items visible on tap.
- Tap-for-actions: remind, reassign, take over a silence — behind the tap, not on the surface.
- The assistant's one plain critical-red message (banner-class, the only one the surface has).
- Confirm the explicit refusal list is honored: no chat, no countdown, no activity feed, no plan
  content, no analytics, no progress bars/percentages.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The runbook (J3, GTC-194) and the criticality badge's specific rendering (J2, GTC-193) — this
  ticket is the grid shell and colour/data mechanics; J2 layers the badge on top.

### Inherited from D2 (GTC-175) — an expired maybe has no colour yet

D2 landed the maybe's decide-by clock. Per founder ruling (a) of 2026-08-05 it stopped at the
state: **this ticket owns the colour encoding, so D2 did not reach into it.**

Two maybe-related states reach your grid, and they are different colours:

- A **live** maybe is yellow. Hinge §8: "the system can work a maybe — just not with the silence
  machinery", and the item is held softly. It is not a gap, and D1 pinned that.
- An **expired** maybe is red — the clock ran out, which is the same exhaustion semantic red
  already carries. `isDecideByExpired(assignment, item, event, now?)` in `src/lib/decide-by.ts`
  is the predicate; it is pure, client-safe and already tested, so the grid and the server read
  the identical definition rather than two that drift.

Under §10.8's worst-colour-wins rule a person holding one live maybe and one expired maybe shows
red. Coordinate with E1 (GTC-178), which owns the exhausted-silence red the expired maybe joins —
one door, not two.

Also available for a person's row: the decide-by instant itself, via `decideBy(item, event)`. It
is derived, never stored; do not add a column for it.
