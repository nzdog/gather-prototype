## Scope

### 1. The reason prompt — one component, one predicate, from any surface

**The rule the UI asks by must be the server's rule.** `whyTrigger()` in `src/lib/ledger.ts` is
already pure, exported, and client-safe (its only `@prisma/client` import is a type, which erases).
The prompt therefore consumes the *same function the server uses* — no second rulebook. This is the
principle A3c established with `isSentJson`, applied to the why.

**It must never block.** Moment 4 §7 forbids the product demanding justification; §13.1 makes the
reason optional at the server. So Skip is a first-class button that completes the change with
`reason: null`, recorded honestly as `reasonRequired: true, reason: null`. Cancel abandons the
change she has not yet made — that is her choosing not to change something, not the product refusing.

**Copy** — the register is Hinge §2's, verbatim in its example: *"the reason is not compliance —
it's her own memory"*, and *"Why did I reassign the beef?" — "Pete couldn't do it."*

## Evidence — CLOSED 2026-08-04

**Both merge-blockers are closed.** The ledger can now be written to from every surface that can
trigger it, and the epic's data-claims are true.

### 1. The reason prompt — the flow finally asks

`src/components/plan/ReasonPrompt.tsx`. One component, one hook, six surfaces.

**It asks by the server's own rule.** `useReasonPrompt().ask(change, event)` calls `whyTrigger()`
— the exact function `recordChange()` consults. If no trigger fires, it resolves **immediately and
renders nothing**; the host never sees a dialog for a change that owes no why. That containment is
the whole design: there is one definition of "touches someone", and a screen cannot drift from it,
which is precisely how FROZEN got out of step in the first place.

`toLifecycleEvent()` was exported from `lifecycle.ts` so the client parses a serialised event
through the same adapter the JSON predicates use, rather than hand-rolling a second parse.

**Three outcomes, and only one of them is a wall — the one she builds herself:**

| Action | Result |
|---|---|
| **Save note** | change proceeds, `reason` recorded |
| **Skip** | change proceeds, `reasonRequired: true, reason: null` — honestly recorded |
| **Cancel / Esc / backdrop** | the change is abandoned. She has not changed anything, so nothing is owed. |

There is no required field, no validation, no disabled button, and **Skip is not styled as the
lesser choice**. Moment 4 §7: *"never says 'hang on' or demands justification."* An empty note
saves as a skip rather than an empty string, so the ledger never records `reason: ""` — which would
read as an answer.

**The copy**, per trigger, plus the constant footer:

> **Keep a note?**
> *{what is about to happen}*
> This is just for you, later — *why did I reassign the beef?* Nothing is sent to anyone.
> `[ Pete couldn't do it… ]`
> **Skip**  **Save note**

Trigger lines: T1 *"You're moving an ask someone already has."* · T2 *"You're removing someone
who's holding things."* · T3 *"You're deleting something someone's holding."* · T4 *"You're
changing an ask someone's already answered."* · T5 *"You're changing the date or venue."*

**Surfaces wired** — the six that can fire a trigger:

| Surface | Triggers | Site |
|---|---|---|
| Host dashboard — save assignments | T1 | `handleSaveAllAssignments` (one prompt for the batch, one changeSet per request) |
| Host dashboard — edit item | T4 | `handleSaveEditItem` |
| Host dashboard — delete item | T3 | `handleDeleteItem` |
| Host dashboard — Moment 2 plan view | T3/T4 | `onUpdateItem` / `onRemoveItem` |
| `PeopleSection` — remove person | T2 | `handleDeletePerson` |
| `EditEventModal` — date/venue | T5 | `handleSubmit` |
| `EditItemModal` — assign/unassign inside the modal | T1 | its two assign calls |
| `c/[token]` — assign / unassign / delete item | T1, T3 | `handleAssign`, `handleUnassign`, `handleDeleteItem` |

The coordinator page needed `sentAt`/`endDate` added to its `CoordinatorData.event` interface: A3d
put them on the wire but never declared them client-side, so the page could not have used the
predicate even if it had wanted to.

**A batch is one prompt, not N.** `handleSaveAllAssignments` writes several assignments in one
save; the host is asked once and the answer rides every request in that batch. Asking eight times
for one action would be interrogation by volume.

### 2. The person-DELETE reason param

`DELETE /api/events/[id]/people/[personId]` now parses an optional `reason` from its body
(`.catch(() => ({}))`, so a bodyless DELETE still works) and passes it to `recordChange`. It was
the only T-firing route with no way to carry a why — which meant T2, a trigger Hinge §2 names by
name, was structurally unanswerable.

### 3. The §9.3 backfill — applied and measured

`prisma/migrations/20260804.../migration.sql`. **Data-only: four UPDATEs, zero DDL.** Created with
`prisma migrate dev --create-only` (which correctly produced an empty migration, there being no
schema diff) and authored into; no generated SQL was edited, and no schema change was needed —
Stop Condition 12 held.

Written exactly as §9.3 specifies, in its stated precedence:

```sql
-- Event.sentAt is @map("inviteSendConfirmedAt"); clause 1 needs no statement.
UPDATE "Event" SET "inviteSendConfirmedAt" = "frozenAt"
  WHERE "inviteSendConfirmedAt" IS NULL AND "frozenAt" IS NOT NULL;
UPDATE "Event" SET "inviteSendConfirmedAt" = "updatedAt"
  WHERE "inviteSendConfirmedAt" IS NULL AND "status" IN ('FROZEN', 'COMPLETE');
UPDATE "PersonEvent" pe SET "sentAt" = p."inviteAnchorAt" …   -- carried per membership
UPDATE "PersonEvent" pe SET "sentAt" = e."inviteSendConfirmedAt" …  -- where the person predates anchoring
```

**Measured, before → after:**

| Event | `PersonEvent.sentAt` before | after |
|---|---|---|
| Security Test Event (SENT) | 0/4 | **4/4** |
| Security Test Event (SENT-LEGACY) | 0/4 | **4/4** |
| Security Test Event (PAST) | 0/5 | **5/5** |
| Security Test Event (DRAFT) | 0/4 | 0/4 — correct, unsent |
| Henderson Family Christmas 2026 | 0/43 | 0/43 — correct, unsent |

No `Event` row needed either fallback in this database (every sent row already carried
`inviteSendConfirmedAt`, and no row has `frozenAt`), which is why the omission was invisible: the
statements are correct and currently no-ops here, and would not have been on a database with real
frozen history. That is the argument for writing them anyway.

**The known limitation, stated rather than silently fixed.** `PersonEvent.sentAt` is carried from
`Person.inviteAnchorAt`, which is global across events — so a person anchored in another event
carries that anchor here. That is the §8.2 leak, it is [[GTC-178]] (E1)'s to fix, and §9.3 rules
this backfill literally. Clamping it would have invented a rule the plan does not state and hidden
the leak. One row in the dev database takes a carried anchor (the PAST fixture's nudge candidate);
it is that event's own anchor.

**The false comment.** `lifecycle.ts:165` claimed *"a legacy FROZEN event has its `sentAt`
backfilled by this same migration"* — untrue until this ticket, and the comment justified
`SENT_AND_LIVE` carrying no FROZEN shim. It now names the migration that makes it true, so the
SQL-layer/JS-layer asymmetry rests on a fact rather than an assumption.

### 4. Two deletions

**`removePerson()` — deleted, 107 lines out of `workflow.ts`.** Zero callers: the god file removes people through
`PeopleSection`, which calls `DELETE /api/events/[id]/people/[personId]`, and that route does its
removal inline. [[GTC-196]] wired T2 into `removePerson()` *"so every caller inherits it"* — a true
sentence about an empty set. [[GTC-201]] then wired the route that actually runs. Keeping both
would leave two implementations of person-removal, one of them unreachable and quietly divergent —
the same reasoning that removed `canFreeze()` in GTC-154 and `canMutate()` in A3a. **The surviving
implementation is the one the review verified.**

**`TransitionModal`'s freeze-warnings view — deleted, 182 lines out, 26 back.** A3c set `isFreezeTransition =
false`, which made the whole `showFreezeWarnings` branch unreachable: the *"Heads up before you
freeze"* header, the *"Why are you freezing early?"* reason picker, the **"Freeze Anyway"** button
and its `complianceRate < 80 && !freezeReason` disabled gate. A3c's scope said *deleted*; disabling
left a readiness threshold and a justification demand sitting in the tree, one prop away from
rendering. Both are refused outright — Moment 4 §2 (no readiness score, no threshold) and §7 (no
demand for justification). Gone with them: `freezeReason` state, `FREEZE_REASONS`, `freezeWarnings`,
`showFreezeWarnings`, `complianceRate`, the `freeze-check` fetch, and `isFreezeTransition` itself.

The `currentStatus` prop is retained on the contract (its three callers still pass it) but is no
longer read for a freeze decision.

### 5. Suite hardenings

**Suite 8 asserted only half of plan §10.2's nudge metric.** The metric is *"sent event with a live
date yields candidates; complete event yields none — **both** true"*, and [[GTC-169]]'s acceptance
says "verified both ways". Only the negative was asserted. Worse, the positive could not be
asserted from the fixtures at all: no member of the SENT event had a phone or an anchor, so
`findNudgeCandidates()` returned zero from that event whatever the predicate said.

The SENT fixture now carries its own nudge-eligible person, mirroring PAST's. Suite 8 asserts:

- a sent, live event **yields** that candidate — *the inversion working, not merely not-misfiring*
- the past event still yields none
- and the two are the **same shape of person**, so the only difference between them is the event's
  phase. That is what makes the pair an assertion about the predicate rather than about fixtures.

**Suite 9's `isStageKey` exemption was `/status:\s*'FROZEN'/`**, which also matches a real Prisma
filter — `where: { status: 'FROZEN' }` would have been waved through the residue gate as a "stage
key". Narrowed to the object-literal stage-key form and paired with an explicit rejection of
`where`-style comparisons. Self-tested: the gate is run against a synthetic line containing
`where: { status: 'FROZEN' }` and must flag it.
