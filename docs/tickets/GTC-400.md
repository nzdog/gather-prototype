## The finding, in plain English

Before: a host of one event (call it A) could change a dish on someone
else's event (B). The route checked "is this person a host of the event
named in the web address?", and the answer was yes, because she put her
own event A in the address. It then looked up the dish by its id and
changed it, without asking whether that dish was on event A at all. So
with the id of a dish on event B, she could rename it, change its
amount, notes, timing or drop-off, or mark it critical, on B, and the
change was even filed in A's history. A coordinator of A could do the
same.

Now: the route also asks which event the dish is on. If it is not the
event in the address, it answers "Item does not belong to this event"
(400) and changes nothing, writes nothing to the history, before it does
any other work. Deleting a dish already worked this way.

## The sweep (read only, report only; nothing else fixed)

Every route handler under `src/app/api/events/[id]/` with a second id in
its address: 22 files, 27 handlers, all `export async function`.

Check that the second thing belongs to the event in the address:

- The seven conflict handlers (acknowledge, delegate, dismiss,
  execute-resolution, resolve, GET, suggest-resolution): each checks
  `conflict.eventId !== eventId`, answers 403, before any write or AI
  call. execute-resolution also scopes the team and item ids in its
  body to the event.
- Households: DELETE and PUT `[householdId]` check
  `household.eventId !== eventId` (404) before writing. POST `claim` is
  a stub that always answers 501 (no lookup, nothing exposed).
- Items: POST and DELETE `[itemId]/assign` check
  `item.team.eventId !== eventId` (400); DELETE `[itemId]` the same.
  PATCH `[itemId]` is this ticket's fix.
- People: POST `hand-back` (only people on this event's own glance, else
  404); GET and POST `resend` (a PersonEvent for this event, else 404
  NOT_ON_THIS_EVENT); POST `reset-claim` (the lookup requires a
  membership of this event, 404); PATCH `[personId]` (the PersonEvent
  for this event, 404, before the first write).
- Revisions: GET and POST `restore` check
  `revision.eventId !== eventId` (403).
- Teams: GET and POST `[teamId]/items` and DELETE `[teamId]` check
  `team.eventId !== eventId` (400).

DO NOT check (for the founder's ruling; none fixed here):

- POST `people/[personId]/nudge`: the serious one. The person is looked
  up by id alone (`src/lib/sms/manual-nudge-recipient.ts`); the event
  membership may be missing, and every gate on it lets a missing one
  through (the child rule, the host rule, "don't chase"). The route then
  sends the host's own words by text or email to that person. So a host
  of A can send a message from Gather to any person in the database
  whose id she knows. The text opt-out still holds (it is by number);
  the email opt-out is looked up for event A, so an opt-out from B's
  emails is not seen.
- GET `people/[personId]/invite-detail`: the person by id alone; it
  returns the person's name, email, phone and text opt-out to a host of
  any event, given the id. (Their tokens, answers and invite history are
  filtered to the event, so B's activity does not show.)
- POST `people/[personId]/manual-override`: the person by id alone. Its
  write is filtered to this event (nothing of B changes), but it records
  a "marked by hand" row in A's invite log for the outsider and returns
  their name.
- DELETE `people/[personId]`: no 404 for a person not on the event.
  Every write is filtered to this event, so nothing of B changes, but it
  writes a "removed" line in A's history and answers 200.

A coordinator for one team editing another team's dish on the SAME
event, through this route: YES, they can. The route's guard is
`requireEventRole(eventId, ['HOST', 'COORDINATOR'])`, and a sign-in
role (`EventRole`) has no team; nothing in the PATCH limits a
coordinator to her own team. The same holds for the dish DELETE, adding
a dish to a team, and the people PATCH and DELETE. Today it is latent:
nothing in the app creates a COORDINATOR sign-in role (sign-in, event
creation, the demo and the copy make HOST or COHOST only). The
coordinator's link route (`/api/c/[token]/items/[itemId]`) does keep
her to her own team (404 for another team's dish). Not this gap.
