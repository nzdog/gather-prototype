# GTC-232 — STUB: a T1 change that touches people, invisible to the ledger

**Status:** Open — stub, needs scoping when pulled | **Effort:** TBD

*Source: [[GTC-231]] (D3) scoping, 2026-08-15. Founder ruling: surface it, do not fix it
there. Derived from code at `176e9cc`.*

**Filed by `7a062bd`**, alongside [[GTC-231]]. Recorded here rather than in frontmatter
`commit:`, which names the commit that CLOSES a ticket — this one is unbuilt, and a hash
there would read as done ([[GTC-230]]'s convention).

## Signal

`PATCH` in `src/app/api/events/[id]/people/[personId]/route.ts` deletes **every** assignment
a person holds in the event when their team changes:

```ts
// When changing teams, remove all assignments (items must be in same team as person)
await prisma.assignment.deleteMany({ ... })   // hint: :70
```

It writes **no** `AuditEntry`. The route imports `recordChange` from `@/lib/ledger` and calls
it in `DELETE` only. `PATCH` never calls it.

## Why it matters

**The ledger is the version history, not a side log.** [[GTC-168]] (A2): *"VERSIONS ARE
LEDGER ENTRIES. `AuditEntry.sequence` IS the version number"* — a change with no row is a
change with no version. Kate's history silently skips a step in which several people lost
what they had agreed to bring.

**It is a T1 change, and T1 is the trigger that always owes a why.** `whyTrigger` in
`src/lib/ledger.ts` fires T1 on assignment create/move/delete once the event is sent, and
both `assign` routes carry an optional `reason` on the wire for exactly this. `PATCH` accepts
`role`, `teamId`, `name`, `email` and `phoneNumber` — **there is no way to give a reason
here even if the flow asked for one.** That is the same structural shape [[GTC-202]] found
and fixed for the person-removal `DELETE`: *"the only T-firing route with no way to carry a
reason, which made T2 structurally unanswerable."* This is its T1 twin, still open.

**And [[GTC-196]] (A3b) was the pass that was meant to catch it.** A3b wired ~25 mutation
routes into the ledger. This branch was missed — plausibly because the route's headline
action (a team change) is a `PersonEvent` field edit, and the assignment deletion is a side
effect two lines below the validation.

## Two adjacent facts, found while verifying the same branch

Recorded so they are not re-derived. Both are in the same handler; neither is the finding.

1. **No transaction.** `PATCH` runs `assignment.deleteMany`, then `item.updateMany`, then
   `personEvent.update`, then token cleanup, as sequential awaits. A partial failure leaves
   the person's assignments deleted and their team unchanged. This is the same class the
   architecture contract §7 note in `POST` at
   `src/app/api/events/[id]/items/[itemId]/assign/route.ts` was written to fix — that route
   was repaired; this one was not.
2. **A broad status repair in place of the real one.** The follow-up `item.updateMany` sets
   `status: 'UNASSIGNED'` for **every** assignment-less item in the event, not just the ones
   this request released, and bypasses `repairItemStatusAfterMutation` in
   `src/lib/workflow.ts` — the helper every other assignment path uses. Idempotent today;
   it is a second, divergent implementation of the `Item.status` cache rule.

## Interaction with [[GTC-231]] (D3)

D3 adds this handler as its **fifth** `onAssignmentReleased` call site — the branch is the
only release path where `PersonEvent` survives, so the released person is still a
participant and still messageable. Because no changeSet exists here, D3 widens the hook's
third parameter to `changeSetId: string | null`. The message at this site is unaffected
either way: the assignments are deleted and the items return to `UNASSIGNED`, so it takes
D3's `DELETE_ASSIGNMENT` template (GTC-231 Ruling 7), which is what actually happened.

**When this ticket lands, D3 gets the structural cause and `before.response` at that site
for free** — the sweep already joins `changeSetId` to `AuditEntry` for those at the other
four. Nothing in D3 needs changing; a null simply stops appearing.

**Note what D3 will still not take from the ledger: `AuditEntry.reason`.** GTC-231 Ruling 7
makes quoting it to a released person a Do-Not-Touch condition — it is documented as the
host's private memory, and it is unmoderated and unbounded. Adding a `reason` to this route
makes the ledger honest; it does not make the reason guest-facing, here or anywhere.

Not a blocker in either direction, and deliberately so.

## Needs scoping when pulled

Candidate directions, not a ruling:

- Wrap the handler in a `$transaction` and call `recordChange` inside it, last, with one
  `DELETE_ASSIGNMENT` change per released assignment — the `DELETE` handler in the same file
  is the worked example, and `recordChange` must run inside the transaction it describes.
- Accept an optional `reason` on the wire, as both `assign` routes do. Optional and **never
  a 400** — plan §13.1: "required" means the flow asks, never that the server rejects.
- Decide whether the team change itself is also a recorded change (a `PersonEvent` field
  edit) or whether only the assignment deletions are. These are different rows and possibly
  different triggers.
- Repoint the status repair at `repairItemStatusAfterMutation`, or record why it must stay
  broad.
- Check the sibling handlers for the same omission — this was found by grepping
  `assignment.delete` / `assignment.deleteMany`, which returns six sites across four files.

Whether the two adjacent facts ride along or split into their own ticket is a scoping call.
They share one handler and one transaction boundary, which argues for together.

## Do not touch

All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`. Note that this handler also performs
`AccessToken` cleanup and calls `ensureEventTokens` — **Zone 3**. A transaction wrapped
around the whole handler changes the token writes' commit boundary and needs that read
explicitly, not incidentally.
