### Context

[[GTC-312]] unified the two phone columns on the founder's ruling of Unknown 1 — **unify, with the
drop held back.** Committed as `473deba`. After it:

- Every capture path writes `Person.phoneNumber`, normalised.
- Every sender, the chooser and every serialiser read `Person.phoneNumber`.
- `Person.phone` is **written by nothing and read by nothing** — verified structurally by layer W of
  `tests/phone-column-unification-test.ts`, which walks `src/app/api` and `src/lib` rather than
  checking a list.
- The 35 legacy-only rows in `gather_dev` were backfilled; `phoneNumber` populated rose 12 → 47.

So the column is inert, not wrong. That is why this is a separate ticket rather than unfinished work
on GTC-312: **the defect is closed, and what remains is a schema tidy with a precondition of its
own.**

### Scope

**Fix here:** one migration that drops `Person.phone`, and the removal of layer C's control in
`tests/phone-column-unification-test.ts` that currently asserts the column still exists — that
control exists precisely to catch a premature drop, so this ticket is the one allowed to remove it.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`. **Zone 5** — `prisma/migrations/` is never
  hand-edited; this is DDL, so `prisma migrate dev` generates it and the generated SQL stands.
  **Zone 7 is adjacent and must be re-checked**, not inherited from GTC-312: `SmsOptOut` keys on a
  phone number, and GTC-312's check that no opt-out matched a person via the legacy column was made
  against `gather_dev`, not production.
- `PersonEvent.contactMethod` — [[GTC-295]]'s.
- `isValidNZNumber` / `normalizePhoneNumber` — [[GTC-300]]'s.
- `normalisePhone` in `src/lib/vcard.ts` — the second spelling GTC-312 named and deliberately left.
  It reads no column and is not this ticket's.

---

### The precondition, stated as the only thing that matters

**A copy of production must be measured before this migration is written**, and the same copy is
what it is rehearsed against, per the Deploy caveat in `GATHER-BUILD-CONSTANTS.md`. This is the
[[GTC-312]] Unknown 2 that ticket left open:

> **What the 35 rows are.** All are fixture and seed rows in gather_dev, but the write path is live,
> so production may hold rows of the same shape. Not measured — there is no production database in
> reach.

What the measurement has to answer, in this order:

1. **How many production `Person` rows have `phone` set?** If any have `phone` with `phoneNumber`
   NULL, **the backfill has not run there** and dropping the column destroys those numbers.
   GTC-312's backfill migration is committed and runs on deploy, so this should be zero — *should*
   is the word this step exists to replace.
2. **Do any production rows hold BOTH columns with DIFFERENT values?** `gather_dev` had none and the
   populations were disjoint. A production row that disagrees is a number the backfill's `IS NULL`
   guard deliberately did not overwrite, and it is data loss on drop unless it is ruled on first.
3. **Does any `SmsOptOut.phoneNumber` in production match a `Person.phone` that no `phoneNumber`
   matches?** Zone 7. If one does, dropping the column silently stops an opt-out from matching,
   which is the TCPA exposure Zone 7 exists for.

⚠ **This is [[GTC-264]]'s correction applied, and [[GTC-189]] slice 4a's.** A migration that alters
no existing table can call *purely additive* and *harmless* the same sentence. **This one drops a
column from a live table**, so it cannot.

### Unknowns

1. **Is anything outside `src/` reading the column?** Layer W walks `src/app/api` and `src/lib`.
   `scripts/` and `prisma/seed.ts` are outside that walk and are where a fixture writer would live.
   Cheap to check and not yet checked.
2. **Does the drop want a deprecation window?** Prisma has no soft-drop. The alternative is
   `/// @deprecated` in the schema plus a release of separation, which costs a second migration for
   a column nothing reads. Probably not worth it; the founder's call if production holds surprises.
