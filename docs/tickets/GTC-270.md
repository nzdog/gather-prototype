# GTC-270 — The cron guard that disappears when it is not configured

**Status:** Open — **filed, not started. Nothing has been built for this
ticket.** Filed 2026-09-11 | **Branch:** TBD
**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low
Escalated (brand/trust risk): [x] Yes — the widest of the three sends SMS to
real people, and a caller who can trigger it can spend the founder's SMS
credit and put unexpected messages in guests' phones.

**Filed out of [[GTC-268]]**, which classified these six handlers as
`SHARED_SECRET [FAIL-OPEN]` and ruled them a hole rather than an allowlist
entry. Verified against HEAD `e6988e1` on 2026-09-11; every symbol grepped at
that commit (GTC-222 rule).

**Founder ruling, 2026-09-11:** *"The six cron handlers are a hole and go on
the fail list, not the allowlist. `if (CRON_SECRET && ...)` means an unset
variable disables the check silently, which is a guard that guards nothing
when it matters most."*

---

## The ticket the code has been asking for

`src/app/api/cron/decide-by-followups/route.ts` names this defect in its own
header, and names the remedy:

> *"Security: Requires CRON_SECRET header or query param — same shape as the
> two existing cron routes. (The `CRON_SECRET &&` guard means an unset secret
> leaves this open, which is pre-existing behaviour shared by
> /api/cron/nudges and /api/cron/wrap-up-dispatch; **deliberately copied
> rather than diverged from, so the fix lands in one ticket**.)"*

**That ticket was never filed.** This is it. The comment is a deliberate
temporary state without the ticket ID that ends it — the exact pattern
`BUG-TICKET-TEMPLATE.md` names as indistinguishable from a permanent one.
Part of this ticket's job is to make that comment carry `GTC-270` so the
backward link exists whichever way the fix goes.

## Signal

**Expected**
A route protected by a shared secret refuses every caller when the secret is
not configured. A missing secret is a misconfiguration, and the fail-closed
direction for a misconfiguration is "nobody", not "everybody".

**Actual**
All three cron routes carry the same condition, verbatim and identical:

```
if (CRON_SECRET && providedSecret !== CRON_SECRET) {
  console.warn('[Cron ...] Unauthorized access attempt');
  return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
}
```

When `CRON_SECRET` is undefined the left operand is falsy, the branch never
runs, and **every caller is admitted.** The guard is present, reads as
protection, logs an `Unauthorized access attempt` it will never log, and does
nothing.

**Smallest failing case**
Unset `CRON_SECRET` and `curl -X POST http://localhost:3000/api/cron/nudges`
with no credential. It runs the nudge scheduler.

## Evidence

### Six handlers across three files

- `GET` and `POST` in `src/app/api/cron/nudges/route.ts`
- `GET` and `POST` in `src/app/api/cron/wrap-up-dispatch/route.ts`
- `GET` and `POST` in `src/app/api/cron/decide-by-followups/route.ts`

All six are reported by the [[GTC-268]] route scanner as carrying **no session
and no token guard**, with a `SHARED_SECRET` credential flagged `FAIL-OPEN`:

```
  GET    /api/cron/nudges
    SHARED_SECRET [FAIL-OPEN]
    CRON_SECRET compared in a refusal branch
  POST   /api/cron/nudges
    SHARED_SECRET [FAIL-OPEN]
  ... six in total ...
```

That classification is a pinned assertion in
`tests/security-route-scan-control.ts` — *"every cron handler is flagged
FAIL-OPEN (GTC-270)"* — so the state cannot change silently while this ticket
is open.

### Three different delegation shapes, and why that matters here

The check does not sit in the exported handlers. It is reached three
different ways, which is worth recording because it is why a naive scan
reports all six as having nothing at all:

- `handleRequest` in `src/app/api/cron/wrap-up-dispatch/route.ts` holds the
  whole check; `GET` and `POST` are two lines each that call it.
- `handleRequest` in `src/app/api/cron/decide-by-followups/route.ts` — same.
- `src/app/api/cron/nudges/route.ts` has the check inline in `GET`, and its
  `POST` is `return GET(request)`.

**A fix must land in all three.** Changing `handleRequest` in two files and
missing the inline copy in the third would leave `/api/cron/nudges` — the
widest of them — untouched.

### What each one does when it is admitted

- **`/api/cron/nudges`** runs the nudge scheduler and **sends SMS** to event
  participants via TNZ or Twilio. Real messages, real money, real phones.
- **`/api/cron/wrap-up-dispatch`** dispatches pending wrap-up thank-you
  messages. Also SMS.
- **`/api/cron/decide-by-followups`** sends the maybe's decide-by follow-up
  ([[GTC-175]] / D2). Also SMS.

**All three are senders.** This is not a read exposure. The consequence of an
unauthenticated call is messages arriving in guests' phones at a time nobody
chose, and SMS spend against the founder's account. Repeated calls repeat the
sends to the extent the schedulers' own dedupe allows — and the dedupe
windows, not the auth, are then the only limit.

### Zone 7 is adjacent

`GATHER-BUILD-CONSTANTS.md` Do-Not-Touch Zone 7 covers SMS opt-out: opt-out
state *"must be respected in all nudge-sending code paths"* and bypassing it
*"could constitute illegal sending under TCPA/spam regulations."* These routes
are the entry point to those paths. **This ticket does not change Zone 7 and
must not** — the opt-out machinery is believed correct and is separately
asserted in `tests/security-validation.ts` suite 8. The point is only that an
unauthenticated trigger of a send path sits next to a compliance boundary.

### Is the secret set today?

**Not determined for any deployed environment, and deliberately not guessed.**
`CRON_SECRET` is listed as required in `GATHER-BUILD-CONSTANTS.md`'s
environment table, so the intent is clearly that it is always set. **That
intent is exactly what the code does not enforce.** The defect is not "the
secret is missing" — it may well be present everywhere. The defect is that
**nothing tells you if it ever stops being.** A deploy that drops the variable
turns three SMS senders public and produces no error, no warning, and no
failing test.

## Reproduce

**Required state**
- Auth state: **none.**
- Environment: `CRON_SECRET` unset in the running server's environment.
- Multi-actor: [ ] Yes [x] No

**Steps**
1. Start the dev server with `CRON_SECRET` unset.
2. `curl -s -o /dev/null -w "%{http_code}\n" -X POST \
     http://localhost:3000/api/cron/decide-by-followups`
3. Repeat for `/api/cron/wrap-up-dispatch` and `/api/cron/nudges`.

**Observe:** 200 on each, with no credential supplied.

**⚠ USE `decide-by-followups` OR `wrap-up-dispatch` FOR THE PROBE, NOT
`nudges`, AND ONLY AGAINST A FIXTURE WITH NO REAL PHONE NUMBERS.** These
routes send. The reproduction must be done against seeded data whose numbers
are Twilio test values or unreachable, or with the provider credentials unset
so the send layer no-ops. **Confirm which before running step 2** — Stop
Condition 6 in `BUG-TICKET-TEMPLATE.md` covers exactly this ("real-world side
effects possible without safe mode").

**Control, in the same run:** set `CRON_SECRET` and repeat. Each must then
answer 401 without the secret and 200 with it. A 200 with the secret unset
proves nothing on its own — a route that is simply broken also returns
something.

## Scope

**Fix here:**
- The secret comparison in all three files — `handleRequest` in
  `src/app/api/cron/wrap-up-dispatch/route.ts`, `handleRequest` in
  `src/app/api/cron/decide-by-followups/route.ts`, and the inline check in
  `GET` in `src/app/api/cron/nudges/route.ts`.
- The header comment in `src/app/api/cron/decide-by-followups/route.ts` —
  it describes the defect as pre-existing and promises a ticket. Once fixed,
  it must describe what is true; if the fix is deferred, it must name
  `GTC-270`.
- `tests/security-validation.ts` — new assertions, adding and never weakening.

**The shape of the fix.** Fail closed:

```
if (!CRON_SECRET || providedSecret !== CRON_SECRET) {
  return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
}
```

**Recommended, with the cost stated plainly: this breaks local development
for anyone without `CRON_SECRET` in their `.env`.** That is the intended
behaviour and it is the correct trade — the alternative is a guard that is
absent precisely when someone forgot to configure it. `.env.example` should
gain the variable if it is not there, and `GATHER-BUILD-CONSTANTS.md`'s
"Async Trigger Methods" section already documents calling these endpoints
with the secret, so the documented workflow is unaffected.

**One definition, not three.** The comparison is currently copied three times
and the copies have already diverged in shape (two in a helper, one inline).
Extracting it — `requireCronSecret` in a shared module — means the next change
cannot land in two of three. **This is a judgement call for the executor and
is not mandated here**, because a shared auth helper touches the neighbourhood
of Zone 1 and the three call sites are small. If extracted, it belongs beside
the cron routes, not inside `src/lib/auth*`.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding.

- **Zone 7** (SMS opt-out) — not modified. The opt-out predicate and its
  assertions stay exactly as they are.
- **Zone 1** (`src/lib/auth*`, `middleware.ts`) — not modified. A cron secret
  is not a session and its check does not belong in the session guards.

Out of scope: the schedulers themselves (`runDecideByFollowups`,
the nudge scheduler, the wrap-up dispatcher). This ticket changes **who may
trigger them**, not what they do.

## Acceptance

**Test gate** — Severity High: test-first required.

**Assertions**
- [ ] With `CRON_SECRET` **unset**, each of the six handlers refuses (401).
      This is the assertion the ticket exists for.
- [ ] With `CRON_SECRET` **set** and supplied, each of the six answers 200.
      The paired positive control — a refusal alone is also what a broken
      route returns.
- [ ] With `CRON_SECRET` **set** and a *wrong* value supplied, each refuses.
- [ ] All six are covered individually, **including both `POST` delegations**
      (`nudges` POST → `GET`, and the two `handleRequest` pairs). A fix applied
      to two files of three must fail.
- [ ] Both credential channels still work where they are meant to: the
      `Authorization: Bearer` header and the `?secret=` query parameter, both
      documented in `GATHER-BUILD-CONSTANTS.md`.
- [ ] No SMS is sent by any assertion in the suite. Asserted by counting
      message rows, not by trusting that the fixture had no numbers.
- [ ] The [[GTC-268]] scanner no longer flags these handlers `FAIL-OPEN`, and
      `tests/security-route-scan-control.ts` is updated in the same commit —
      **it currently asserts the fail-open state**, and leaving that assertion
      green after the fix would hold the hole open with a passing test.
- [ ] Adjacent flows unaffected: `npm run test:security` still passes; the
      nudge, wrap-up and decide-by suites still pass.

- RED/GREEN output, the set/unset/wrong-value matrix, the commit hash.
