# GTC-270 — The cron guard that disappears when it is not configured

**Status:** BUILT, NOT COMMITTED — filed and executed 2026-09-11, then held
for founder review before commit, per the standing instruction ("Report and
HOLD"). Filed 2026-09-11 | **Branch:** `feat/moment-one-redesign` (from
`e74a21f`)
**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low
Escalated (brand/trust risk): [x] Yes — the widest of the three sends SMS to
real people, and a caller who can trigger it can spend the founder's SMS
credit and put unexpected messages in guests' phones.

**Filed out of [[GTC-268]]**, which classified these six handlers as
`SHARED_SECRET [FAIL-OPEN]` and ruled them a hole rather than an allowlist

**Founder ruling, 2026-09-11:** *"The six cron handlers are a hole and go on

## Signal

**Expected**
A route protected by a shared secret refuses every caller when the secret is
not configured. A missing secret is a misconfiguration, and the fail-closed
direction for a misconfiguration is "nobody", not "everybody".

**Actual**
All three cron routes carry the same condition, verbatim and identical:

```
if (CRON_SECRET && providedSecret !== CRON_SECRET) {
  console.warn('[Cron ...] Unauthorized access attempt');
  return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
}
```

When `CRON_SECRET` is undefined the left operand is falsy, the branch never
runs, and **every caller is admitted.** The guard is present, reads as
protection, logs an `Unauthorized access attempt` it will never log, and does
nothing.

**Smallest failing case**
Unset `CRON_SECRET` and `curl -X POST http://localhost:3000/api/cron/nudges`
with no credential. It runs the nudge scheduler.

## Evidence

### Six handlers across three files

- `GET` and `POST` in `src/app/api/cron/nudges/route.ts`
- `GET` and `POST` in `src/app/api/cron/wrap-up-dispatch/route.ts`
- `GET` and `POST` in `src/app/api/cron/decide-by-followups/route.ts`

All six are reported by the [[GTC-268]] route scanner as carrying **no session
and no token guard**, with a `SHARED_SECRET` credential flagged `FAIL-OPEN`:

```
  GET    /api/cron/nudges
    SHARED_SECRET [FAIL-OPEN]
    CRON_SECRET compared in a refusal branch
  POST   /api/cron/nudges
    SHARED_SECRET [FAIL-OPEN]
  ... six in total ...
```

That classification is a pinned assertion in
`tests/security-route-scan-control.ts` — *"every cron handler is flagged
FAIL-OPEN (GTC-270)"* — so the state cannot change silently while this ticket
is open.

### Three different delegation shapes, and why that matters here

The check does not sit in the exported handlers. It is reached three
different ways, which is worth recording because it is why a naive scan
reports all six as having nothing at all:

- `handleRequest` in `src/app/api/cron/wrap-up-dispatch/route.ts` holds the
  whole check; `GET` and `POST` are two lines each that call it.
- `handleRequest` in `src/app/api/cron/decide-by-followups/route.ts` — same.
- `src/app/api/cron/nudges/route.ts` has the check inline in `GET`, and its
  `POST` is `return GET(request)`.

**A fix must land in all three.** Changing `handleRequest` in two files and
missing the inline copy in the third would leave `/api/cron/nudges` — the
widest of them — untouched.

### What each one does when it is admitted

- **`/api/cron/nudges`** runs the nudge scheduler and **sends SMS** to event
  participants via TNZ or Twilio. Real messages, real money, real phones.
- **`/api/cron/wrap-up-dispatch`** dispatches pending wrap-up thank-you
  messages. **SMS _and_ email.** `dispatchPendingWrapUpMessages` in
  `src/lib/wrap-up.ts` falls back to `sendNudgeEmail` (Resend) when the SMS
  fails, and uses email directly for a link whose `channel` is `'email'`.
  **Founder correction, 2026-09-11:** *"My brief said SMS throughout and that
  was wrong."* An admitted caller therefore reaches the transactional email
  sender as well as the SMS providers.
- **`/api/cron/decide-by-followups`** sends the maybe's decide-by follow-up
  ([[GTC-175]] / D2). Also SMS.

**All three are senders, and one of them sends on two channels.** This is not
a read exposure. The consequence of an
unauthenticated call is messages arriving in guests' phones at a time nobody
chose, and SMS spend against the founder's account. Repeated calls repeat the
sends to the extent the schedulers' own dedupe allows — and the dedupe
windows, not the auth, are then the only limit.

### ⚠ FINDING 2, RAISED TO ITS OWN FINDING BY FOUNDER RULING — the guest-name leak

Found 2026-09-11 during investigation, not present in the ticket as filed.

**Founder ruling, 2026-09-11:** *"All three routes spread a per-recipient
errors array into a 200 body, so an anonymous caller gets full guest names for
every failed send. These are read oracles as well as send triggers. Raise it in
the ticket to its own finding — it is the same class GTC-267 closed, and it is
worse than the trigger half in one respect: the trigger is bounded by stamps
and time gates, and the leak is not."*

**⚠ THE RULING'S PREMISE IS CORRECTED ON ONE ROUTE, AND THE CORRECTION MATTERS
FOR WHERE THE FIX LANDS.** It is two of the three, not all three.

**Founder acknowledgement, 2026-09-11:** *"I said all three leak; wrap-up
returns counts only. Record it."*

Verified per scheduler rather than assumed:

- `runNudgeScheduler` in `src/lib/sms/nudge-scheduler.ts` — **leaks.** Builds
  `errors` from `` `${r.personName}: ${r.error}` `` for the direct family and
  `` `Proxy ${r.primaryContactName}: ${r.error}` `` for the proxy family.
- `runDecideByFollowups` in `src/lib/sms/decide-by-scheduler.ts` — **leaks.**
  `` `Decide-by follow-up ${r.personName}: ${r.error}` ``.
- `dispatchPendingWrapUpMessages` in `src/lib/wrap-up.ts` — **does not leak.**
  Its return shape is `{ sent, failed, total, deferred, deferredUntilMinutes }`
  and carries no `errors` array and no name. The per-link `failReason` is
  written to the `WrapUpLink` row and to an `InviteEvent`, never to the
  response.

The redaction is applied to all three anyway, and that is a decision rather
than an oversight: it makes the three routes put one shape on the wire, it
gives the only route this ticket may safely drive a live assertion to stand on,
and an `errors` array added to the wrap-up dispatcher later is then redacted by
default instead of leaking on the day it lands.

**Founder ruling, 2026-09-11, adopting the executor's reason over the one in
the original instruction:** *"Record your reason for redacting it anyway, which
is better than mine: it gives the one safely-drivable route something live to
stand on, and an errors array added there later arrives already redacted."*

**Why this is its own finding and not a footnote to the first.** The trigger
half of this ticket is bounded: the send stamps (`firstNudgeSentAt`,
`secondNudgeSentAt`, `decideByFollowupSentAt`) and the time gates mean nobody
can make these routes send a message that was not already due. Nothing bounded
the response body. It could be read on demand, repeatedly, and it returned
real guests' full names to a caller with no credential of any kind.

**The fix.** `withoutRecipientNames` in `src/app/api/cron/cron-response.ts`.
The names go to `console.error` at the route, where an operator can act on
them; the wire body carries `errorCount`, which is what a monitor needs. The
schedulers are unchanged — this ticket's Scope puts them out of scope, and the
route is the correct layer to decide what leaves the process.


### Zone 7 is adjacent

`GATHER-BUILD-CONSTANTS.md` Do-Not-Touch Zone 7 covers SMS opt-out: opt-out

### Is the secret set today?

**Not determined for any deployed environment, and deliberately not guessed.**
`CRON_SECRET` is listed as required in `GATHER-BUILD-CONSTANTS.md`'s
environment table, so the intent is clearly that it is always set. **That
intent is exactly what the code does not enforce.** The defect is not "the

## Scope

**Fix here:**
- The secret comparison in all three files — `handleRequest` in
  `src/app/api/cron/wrap-up-dispatch/route.ts`, `handleRequest` in
  `src/app/api/cron/decide-by-followups/route.ts`, and the inline check in
  `GET` in `src/app/api/cron/nudges/route.ts`.
- The header comment in `src/app/api/cron/decide-by-followups/route.ts` —
  it describes the defect as pre-existing and promises a ticket. Once fixed,
  it must describe what is true; if the fix is deferred, it must name
  `GTC-270`.
- `tests/security-validation.ts` — new assertions, adding and never weakening.

**The shape of the fix.** Fail closed:

```
if (!CRON_SECRET || providedSecret !== CRON_SECRET) {
  return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
}
```

**Recommended, with the cost stated plainly: this breaks local development
for anyone without `CRON_SECRET` in their `.env`.** That is the intended
behaviour and it is the correct trade — the alternative is a guard that is
absent precisely when someone forgot to configure it. `.env.example` should
gain the variable if it is not there, and `GATHER-BUILD-CONSTANTS.md`'s
"Async Trigger Methods" section already documents calling these endpoints
with the secret, so the documented workflow is unaffected.

**One definition, not three.** The comparison is currently copied three times
and the copies have already diverged in shape (two in a helper, one inline).
Extracting it — `requireCronSecret` in a shared module — means the next change
cannot land in two of three. **This is a judgement call for the executor and
is not mandated here**, because a shared auth helper touches the neighbourhood
of Zone 1 and the three call sites are small. If extracted, it belongs beside
the cron routes, not inside `src/lib/auth*`.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding.

- **Zone 7** (SMS opt-out) — not modified. The opt-out predicate and its
  assertions stay exactly as they are.
- **Zone 1** (`src/lib/auth*`, `middleware.ts`) — not modified. A cron secret
  is not a session and its check does not belong in the session guards.

Out of scope: the schedulers themselves (`runDecideByFollowups`,
the nudge scheduler, the wrap-up dispatcher). This ticket changes **who may
trigger them**, not what they do.

### ⚠ THE SHAPE WAS DECIDED BY MEASUREMENT, NOT BY TASTE

The ticket left extraction as an open judgement call. It was measured instead,
by calling the scanner's own `analyzeSource` on modified source held in a
scratch file, before a single repo file was touched:

```
if (!CRON_SECRET || provided !== CRON_SECRET)          SHARED_SECRET
two separate ifs                                       SHARED_SECRET x2
if (!isCronSecretValid(CRON_SECRET, provided))         SHARED_SECRET
const denied = requireCronSecret(req); if (denied)...  NO CREDENTIAL OF ANY KIND
```

**Extraction into a shared module blinds the scanner on all six handlers.**
`analyzeSource` follows local helpers within a file and does not follow
imports, so the six would have joined the twelve-strong no-credential list and
`Fail-open credentials: 6 → 0` would have been achieved by the scanner losing
sight of the credential rather than by the credential being fixed — this
ticket's own headline metric, green for the wrong reason. Re-declaring an
unused `const CRON_SECRET` in the route does not buy the verdict back; it is
the `if` condition that is matched.

**Founder ruling, 2026-09-11:** *"Extraction is ruled out by your own
measurement... The pure predicate gives one definition without costing the
verdict, so take that shape — predicate exported, `if` staying in each route
file."* Two branches rather than one condition, on the founder's stated
reason: a misconfigured deployment and an attacker are different events and
only one is an error-level log. Both answer 401 identically on the wire.

### Deployment — recorded, not waited for

**Founder instruction, 2026-09-11:** *"I will answer 'what calls these' myself
from the platform logs before anything deploys. Do not guess it and do not

What the repo settles, and what it does not:

- There is no `railway.json` or `railway.toml`, no `.vercel` directory, no

  CodeQL), and no in-process scheduler in `src/`.

- The deployed snapshot [[GTC-267]] identified as "code from 5 August" is
  `b558825`, which sits on `feat/moment-one-redesign`, not on `master`. All
  three routes exist there and all three carry the identical fail-open guard.
  `master` HEAD is `b28204b` (2026-04-10) and has only two cron routes.
- **Not established, and deliberately not guessed:** whether Vercel
  interpolates `${CRON_SECRET}` into a cron `path`. If it does not, the query
  param arrives as that literal string; the `Authorization: Bearer` channel
  would still carry the credential, because the routes read the header first.
  This needs checking on the platform.

**The coordinated deploy, if something is calling these:**

1. Set `CRON_SECRET` on the platform, and restart or redeploy — the
   module-scope read means a variable added to a running instance has no
   effect until then.
2. **While the guard still fails open**, confirm the caller's credential path
   works: a run that carries the secret and returns 200 proves the channel
   before the channel becomes mandatory.
3. Then land this fix and deploy.

Step 2 is what makes it safe. It is the only window in which the credential
path can be proven without risking a silent outage; after the fix a broken
credential path and a dead schedule look identical from outside. If nothing
calls these, none of it applies.

**[[GTC-267]], [[GTC-269]] and GTC-270 are ONE deploy decision, not three.**
Both earlier tickets recorded that the deployed instance must not be
redeployed until they land, because a redeploy ships their bypasses forward.
Both are fixed on this branch. Whatever redeploy carries this ticket carries
those, and the pre-deploy checklist is theirs plus step 1 above.
