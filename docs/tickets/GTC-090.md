# GTC-090 — AI call cap: 10 calls per event with warning at 3 remaining — CLOSED

**Status:** Complete | **Branch:** master | **Commit:** [pending]

### What was found

- Five AI endpoints identified. On inspection:
  - `generate`, `regenerate`, and `suggest-resolution` make actual Claude API calls and write results to the DB.
  - `regenerate/preview` calls Claude but is **read-only** (no DB writes).
  - `review-items` has **no AI call** — it is a pure CRUD endpoint for marking items as confirmed/unconfirmed.
- The event GET endpoint (`/api/events/[id]`) uses `findUnique` with `include` (no `select`), so all scalar fields including the new `aiCallsUsed` are automatically returned to the frontend.
- AI action buttons live in the plan page header area (Generate Plan and Regenerate Plan) and in ConflictCard (Resolve with AI).

### Decision: regenerate/preview

**Preview calls do NOT count against the cap.** Rationale: The preview endpoint is read-only — it calls Claude to generate a proposed plan but does not write anything to the database. The host may preview multiple times before committing. Only the subsequent `regenerate` call (which applies the changes) increments the counter. However, previews are still **blocked** when the cap is reached to prevent wasted API calls.

### Known limitations

- The counter is per-event, lifetime, and cannot be reset without direct DB intervention.
- The `regenerate` endpoint increments the counter even when using a `preGeneratedPlan` (cached from preview). This is intentional — the preview didn't count, so the commit does.
- No admin UI to view or reset the counter.
