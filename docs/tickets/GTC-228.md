# GTC-228 — Dietary coverage is unverified after plan generation

**Status:** Open — unassigned, not started. **Effort:** To be set at preflight (see below).
**Severity:** To be classified at preflight.

## Problem

Host-ticked dietary needs reach the AI and are usually honoured, but
nothing checks the generated plan against them. Coverage is
non-deterministic run to run, and when a diet is not visibly covered
the host cannot distinguish "handled silently" from "ignored."

This supersedes the E–K scope pass ruling that `detectDietaryGaps` in
`src/lib/ai/check.ts` is a live safety defect for reading legacy
`Event.dietary*`. That ruling assumed guest-supplied dietary answers
were being ignored. Dietary needs are host-entered, at the
`DietaryAccordion` in `Moment2Step1Modal`, as five fixed checkboxes
plus free text. The pre-generation check fires correctly — the
"Needs confirmation" state renders as designed. The defect is the
absence of a POST-generation check, not a misrouted pre-generation
one.

## Evidence — four runs, gather_dev, 2026-08-15

Same seeded event (17 guests, Christmas), varying only the ticks:

| Run | Ticked | Result |
|---|---|---|
| 1 | gluten-free + dairy-free | dairy-free covered and labelled (coconut cream, "for dairy-free guests"). **Gluten-free: nothing.** |
| 2 | vegetarian | covered and labelled — halloumi skewers in Mains, "2 skewers per vegetarian guest" |
| 3 | vegetarian + gluten-free | both covered — halloumi skewers, plus gluten-free crackers. Bread rolls present in run 2 were absent |
| 4 | gluten-free | **nothing labelled.** Bread rolls and standard crackers absent; cheese board served with no crackers |

Vegetarian and dairy-free: reliable across every run they appeared in.
Gluten-free: covered twice, silent twice — same input, different
output.

Runs 3 and 4 show the model IS capable of subtractive handling
(omitting gluten-containing items). It just does not do it
consistently, and never announces it. In run 4 the menu is plausibly
gluten-free already; the host has no way to know that.

## Scope

Post-generation dietary coverage verification:

1. After plan generation, for each ticked diet on the event, determine
   whether the returned plan contains an item addressing it.
2. Where coverage exists, ensure it is visible to the host — the
   serving item should state which diet it serves, as the coconut
   cream and halloumi rows already do.
3. Where coverage is absent, surface it to the host explicitly. A
   correct "this menu is already gluten-free apart from X" is more
   useful than silence, and is the outcome run 4 needed.
4. Free-text "Other dietary needs" is out of scope for automated
   verification — flag for host review rather than attempting a match.

Remedy on failure (re-generate, prompt-repair, or host-facing warning)
is a design decision, not settled here — propose options in the
preflight.

## RED tests

Must fail against unpatched code:
1. Plan generated with gluten-free ticked and no gluten-free item →
   host-visible coverage warning raised
2. Plan generated with vegetarian ticked and only meat mains → warning
   raised
3. Plan generated with a diet ticked AND covered → no warning
4. Determinism: the same ticked set produces a coverage ruling that
   does not vary with generation output wording

## Explicitly out of scope

- Per-person dietary identity. Needs are event-level counts-of-kind,
  not attributable to individuals. (Product ruling, Nigel, 2026-08-15)
- Portion counts per diet — the checkboxes capture whether, not how
  many. Filed separately if wanted.
- All other Epic G work.
- Legacy `Event.dietary*` deprecation — 9+ live consumers, deprecates
  in place.

## Schema

None expected — ticks and generated items both already persist.
Confirm in preflight; if a migration is required, STOP (Stop
Condition 7).

## Effort

To be set at preflight. Larger than the sub-day the scope pass
estimated, because this is a new verification layer, not a repoint.

## Needs a ruling when pulled

*Filed by the executor at ticket-filing time (2026-08-15), verifying citations per
[[GTC-222]]. Not a change to the Problem/Evidence/Scope text above — that is preserved as
given, including the empirical Evidence section, which is not re-derivable. This section is
an additional finding surfaced during citation verification that the Problem section's
"supersedes" claim rests on.*

**The data-flow premise in the Problem section does not hold at HEAD, and a prior ruling on
this exact point is still open, not superseded.**

Traced end to end at HEAD (`6fa38e4`):

- `DietaryAccordion` (`Moment2Step1Modal.tsx:924`) writes only to `EventSetup.dietaryData`,
  via `PUT /api/events/[id]/setup` (`route.ts:199`, `data.dietaryData = body.dietaryData`).
- The live "Generate Plan" action (`handleGeneratePlan` in `page.tsx:936`) calls
  `POST /api/events/[id]/generate`, whose `generatePlan` (`src/lib/ai/generate.ts`) reads
  only the legacy `event.dietaryVegetarian`/`dietaryVegan`/`dietaryGlutenFree`/
  `dietaryDairyFree` integer fields (`generate.ts:484-487,542-546`). It never reads
  `EventSetup.dietaryData` — no reference to `EventSetup` or `dietaryData` exists anywhere
  in `generate/route.ts` or `generate.ts`.
- `detectDietaryGaps` (`check.ts:184`) reads the same legacy `Event.dietary*` fields as
  `generate.ts` — the two are mutually consistent — but neither reads what
  `DietaryAccordion` writes.
- The only route reading `EventSetup.dietaryData` via `readDietaryData()` is
  `finalize-plan/route.ts:148`, which the live Moment 2 "Generate Plan" flow does not call.
- The legacy `Event.dietary*` integer fields are populated by a different, still-live UI —
  `EditEventModal` (`EditEventModal.tsx:183-186`, numeric guest-count inputs), reachable from
  the plan page's "Edit event" action and PATCHed via `/api/events/[id]` (`route.ts:145-148`)
  — not by `DietaryAccordion`.

This is not a new finding. `docs/tickets/GTC-184.md` (**status: open**, G1 — "Reconcile
dietary models") rules the identical point: *"a host's real Moment 2 dietary answer never
reaches conflict detection today."* `docs/04_roadmap/moment4-hinge-report-accuracy-audit-2026-08-04.md`,
row **G-3**, independently re-verified the same claim as **ACCURATE** eleven days before this
ticket's evidence date, citing `check.ts:187,213` by symbol/line at that commit. Neither
document is addressed or refuted by this ticket's Problem section.

The audit also flags (same G-3 row) that `detectDietaryGaps` only ever checks vegetarian and
gluten-free — `Event.dietaryVegan` and `dietaryDairyFree` are dead inputs to it — which is
consistent with this ticket's own Evidence table only ever reporting outcomes for
vegetarian/gluten-free/dairy-free and never vegan.

One point in the accuracy audit is stale and should not be carried forward: it claims
`detectConflicts` has no caller in `src`. That is no longer true — `page.tsx:982`
(`handleCheckPlan`, the host-facing "Check Plan" button) and `page.tsx:1014` (`autoRecheck`)
both call `POST /api/events/[id]/check` today. The route is live and host-triggered; the
question is only which model it reads.

**Practical consequence for scoping this ticket:** the seed scripts that plausibly produced
this ticket's Evidence runs (e.g. `scripts/create-test-fixtures.ts`,
`scripts/test-generate-plan.ts`) set the legacy `Event.dietary*` fields directly, which is
what `generate.ts` actually reads — consistent with the runs' outcomes. But that means the
runs exercise the `EditEventModal`/legacy-field path, not the `DietaryAccordion` path the
Problem section credits as "where dietary needs are host-entered." If the real Moment 2 host
flow (tick boxes in `DietaryAccordion`, click Generate Plan) was exercised instead, current
code suggests the ticks would not reach generation at all — a different and more fundamental
defect than "coverage isn't verified post-generation."

**Not settled here, and it changes this ticket's shape depending on the answer:**
1. Does GTC-184 (open) get executed first — reconciling the two dietary models — with this
   ticket's post-generation verification building on top of the reconciled model? Or
2. Is this ticket's scope quietly relying on the legacy-field path staying authoritative,
   in which case the Problem section's `DietaryAccordion` framing should be corrected before
   an executor is handed the ticket, since building a "post-generation check" on top of a
   pre-generation routing gap verifies the wrong thing?

Recommend ruling before pulling either this ticket or GTC-184.

## Addendum — 2026-08-15, after commit `9b6b287` (reconciliation trace)

The "Needs a ruling when pulled" section above traced the wrong generation entry point.
`handleGeneratePlan`/`/api/events/[id]/generate` is the **V1** path — gated behind
`HostDescriptionModal`, which the code itself comments "never opens on V2 events regardless
of caller (GTC-149)." `Moment2Step1Modal`'s actual "Generate plan →" button
(`handleGenerate`, `Moment2Step1Modal.tsx:429`) calls its `onGenerate` prop, wired at
`page.tsx:2137` to `POST /api/events/[id]/finalize-plan`. `finalize-plan/route.ts:148` reads
`readDietaryData(setup.dietaryData)` — the same `EventSetup.dietaryData` `DietaryAccordion`
writes via `/setup` (`route.ts:199`).

**Corrected finding:** V2 generation honours `DietaryAccordion` ticks. This is now
established by code trace, not only by the Evidence table's four runs. The "practical
consequence" paragraph above — that ticks "would not reach generation at all" on the real
Moment 2 flow — is wrong and superseded by this addendum.

**What does not change:** `detectDietaryGaps`/`detectConflicts` (`check.ts:184-237`) still
reads only legacy `Event.dietary*`, which nothing on the V2 path populates.
[[GTC-184]]'s finding — conflict detection is blind to the real Moment 2 answer — is
confirmed accurate at HEAD and is **not superseded** by this ticket. The Problem section's
framing ("this supersedes the E–K scope pass ruling... assumed guest-supplied dietary
answers were being ignored") mischaracterises what was ruled: the audit and [[GTC-184]] never
claimed generation was blind — only conflict detection. That mischaracterisation is not
corrected in the Problem section itself (committed text, preserved per the filer's
evidence-preservation instruction) but should not be relied on going forward.

**The defect this ticket owns: no post-generation coverage check exists** on the plan
`finalize-plan` actually returns. The four-run non-determinism (gluten-free: 2 of 4 runs
silent, same input) is the *symptom* that exposed this, not the defect itself — a generator
with perfectly reliable coverage and no check would fail exactly the same way the first time
it slipped, later and in front of a guest, with nothing catching it first. The fix is a
check, not a determinism improvement to the model call. This is a different defect from
[[GTC-184]]'s routing gap; see [[GTC-184]] (narrowed 2026-08-15) for how the two are
sequenced.
