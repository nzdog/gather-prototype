# [[GTC-136]] — Plan view headcount display fix — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** [pending]

### What was found

The Moment 2 plan view header rendered "based on 0 guests" because it was reading `event.guestCount` — a separate, optional, host-entered field — instead of computing the actual headcount from the households roster. For events where the host hasn't manually entered a guestCount value (including the seeded test event `cmow49m0l00011yg7w6apsdgg`), `event.guestCount` is `null`, so the prop coerced to `0` via `?? 0`.

The AI plan generation already does the right thing: `src/app/api/events/[id]/finalize-plan/route.ts:115-142` aggregates `totalAdults + totalKids` from `Household` + `members` + `littleCount`, so quantities scale correctly. Only the display prop was wrong.

### Phase 1: Display source

- Render: `src/components/plan/Moment2PlanView.tsx:159` — `based on {guestCount}`
- Prop: `Moment2PlanViewProps.guestCount: number` (line 38)
- Prop supplied at: `src/app/plan/[eventId]/page.tsx:1804` — `guestCount={event.guestCount ?? 0}`
- Source: the `Event` row's `guestCount: Int?` column (`prisma/schema.prisma:17`), populated only by the host editing it on `/h/[token]` (`src/app/h/[token]/page.tsx:339-352`).

### Phase 2: Canonical source

The canonical headcount used everywhere else is an aggregate over `Household` rows:

```
sum over households: 1 (host) + (partner ? 1 : 0) + helpers.length + littleCount + guests.length
```

Used by:
- `src/components/plan/Moment1Summary.tsx:39-41` — drives "X people coming"
- `src/app/plan/[eventId]/page.tsx:1747-1749` — drives `totalPeopleCount` shown on the Moment 1 input form

The plan-generation API (`finalize-plan/route.ts`) computes equivalently from `Household.members` + `littleCount` (it splits adults/kids, but the total matches).

`Event.guestCount` exists in the schema but is *not* maintained as a cache of the household roster — it's a separate host-entered hint and is unrelated to the actual count of people invited.

### Phase 3: Diagnosis

The plan view header was reading `event.guestCount` (an optional, manually-entered field) when it should have been reading the household-aggregate count (the canonical source used by Moment 1's summary and by the plan-generation logic itself). For the seeded test event the host never entered `guestCount`, so the field was `null` → display rendered `0`.

### What was changed

`src/app/plan/[eventId]/page.tsx`:

1. Extended the existing households-fetch effect to also fire when `showMoment2PlanView` becomes true, so that direct entry into the plan view (e.g. after page reload) loads the roster needed for the header.
2. At the `Moment2PlanView` render site, computed `householdsHeadcount` using the canonical Moment 1 formula and pass that as `guestCount`. Falls back to `event.guestCount ?? 0` only when households haven't loaded yet (defensive — pre-fetch effect should always populate by the time the view paints).

No schema changes. No changes to plan-generation or quantity logic.

### Known limitations

- `Event.guestCount` is not kept in sync with the household roster. This ticket does not change that — it just stops the plan view from reading that field. Other UI surfaces that still read `event.guestCount` (the events list at `src/app/plan/events/page.tsx:249`, plus a couple of read-only badges in `src/app/plan/[eventId]/page.tsx`) are unchanged and may show stale values; they're outside this ticket's scope.
- The fallback to `event.guestCount ?? 0` is reachable only in the brief window before the households fetch resolves. If a real event has zero households, the header will show `0 guests`, which is correct.
