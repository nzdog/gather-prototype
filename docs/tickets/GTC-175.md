### Context

Hinge spec §8 + Moment 4 §10.2 (one derivation, two clocks — shared with E3's red-by-time line):
a maybe needs "time to decide," not "did you see this?" — no nudges. The clock is keyed to
**needed-by** (the item's drop-off time where one exists, else the event date), landing far
enough before needed-by for a reassignment to realistically work. **The exact constant is settled
at ticket time with Nigel's sign-off; real-event data will correct it** — this ticket must not
invent a default unilaterally. Near the decide-by, one follow-up in the same voice ("still good
for the pavlova? Kate needs to know by Thursday"). If it passes unanswered, the maybe goes red
through the standard door — the system out of moves. No new machinery beyond this.

### Scope

**Fix here:**
- `decideBy` field on whichever model D1 (GTC-174) lands the maybe state on.
- Derivation logic per the needed-by formula shape; per-item host override.
- Single follow-up message at/near decide-by.
- Red-through-standard-door transition when the clock expires unanswered.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.

  nudge cadence; do not wire it into `nudge-eligibility.ts`'s candidate-finding.

# GTC-175 — D2: Maybe's decide-by clock — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** 59a4afb | **Effort:** high

## What was built

### The constant, and who signed off

`DEFAULT_DECIDE_BY_OFFSET_HOURS = 120` — five days. **Signed off by Nigel on 2026-08-05**,
satisfying Stop Condition 9. Two further numbers were derived from that ruling and signed off
in the same pass:

| Constant | Value | Why |
|---|---|---|
| `DEFAULT_DECIDE_BY_OFFSET_HOURS` | 120 (5 days) | The founder ruling. §10.2's "real-event data will correct it" corrects it here, once. |
| `DECIDE_BY_FOLLOWUP_LEAD_FRACTION` | 0.2 → 24h at the default | §8 puts the follow-up *near* the decide-by and red *at* it, so a lead is genuinely required. A **fraction**, not a second fixed constant: a hardcoded 24h would exceed the entire window the moment Kate sets a 12h offset. |
| `DECIDE_BY_FOLLOWUP_LEAD_FLOOR_HOURS` | 12 | Quiet hours can defer a batch ~11h. A shorter lead could push the message past the very deadline it quotes. |

The host-facing "decide faster" control is **not a fourth number**: it is
`Event.decideByOffsetHours` set to 48. Recorded in that field's schema comment so the J-epic
ticket that builds the control inherits the intent — D2 builds no UI.

### Stored vs derived

Three nullable columns, one migration, no enum add, no backfill:

| Column | Layer |
|---|---|
| `Item.decideByOffsetHours Int?` | override, layer 1 — the one §8 names |
| `Event.decideByOffsetHours Int?` | default, layer 2 |
| `Assignment.decideByFollowupSentAt DateTime?` | the follow-up sent-stamp |

Derived and deliberately **not** stored: the decide-by instant, and the expired state. A stored
instant drifts the moment `dropOffAt` or `endDate` moves — and `endDate` is a
`MATERIAL_EVENT_FIELD`. That is the `Item.status` mistake, and what it would make lie is a
deadline the system had already texted to a guest.

`neededBy()` is byte-identical — verified by regex in `tests/decide-by-clock-test.ts`, not by
eye. No offset was written into it: it is the anchor both clocks share, and baking D2's constant
in would hand E3 a pre-shifted number it could not un-shift.

### The follow-up

A separate module pair (`decide-by-eligibility.ts` / `decide-by-sender.ts`) on its own scheduler
and its own cron route (`/api/cron/decide-by-followups`, `*/15`). It shares the eligibility
**gates** with the nudge machinery — child rule, opt-out, quiet hours — and none of its
**cadence**. `nudge-eligibility.ts`'s candidate-finding is untouched.

Why not a fourth branch of `runNudgeScheduler`: that function early-returns on `isSmsEnabled()`,
which is the **Twilio** predicate, while NZ traffic routes to **TNZ** — D2 would have silently
never fired on a TNZ-only configuration. Loosening that gate is a behaviour change to E1's
machinery, which is not D2's to make. Its single shared `try` also zeroes every sibling's counts
on any one failure, and its `now` is not injectable — fatal for a feature that *is* a clock.

### Six decisions ruled with the schema

1. **Lead** — a fraction of the resolved offset, with the quiet-hours floor.
2. **Born-expired maybes are not chased.** A maybe whose decide-by has already passed gets no
   text. Not an edge case: `Item.dropOffAt` is not host-settable today, so `neededBy()` collapses
   to `event.endDate` for essentially every item, and **any host who sends within five days of
   their event date lands every guest here**. Texting "Kate needs to know by *[last week]*" is
   worse than silence. The state still reads correctly as expired; it simply is not chased.
3. **One message per (person, event)**, naming the earliest-decide-by item, stamping every
   collapsed assignment. Follows from #2 — two maybes by one guest share a decide-by to the
   millisecond, so per-assignment sending meant two near-identical texts 500ms apart.
4. **The stamp is never cleared.** MAYBE → ACCEPTED → MAYBE keeps its stamp and is not texted
   again. "Exactly one follow-up" then holds literally; a duplicate text is a trust failure where
   a missed one is a nuisance. Pinned source-level across all four response writers.
5. **No response timestamp added, and `createdAt` not used** — flagged and rejected as instructed.
   §10.2 keys the clock to needed-by; the expiry predicate reads neither. The one case a
   response timestamp would have helped (a maybe expiring seconds after being tapped) is #2's
   skip rule instead. The two pre-existing `createdAt`-as-`respondedAt` misreports are untouched.
6. **Own module + own cron route** (above).

### Acceptance line 56, amended

Founder ruling (a), 2026-08-05: the "standard door" does not exist — E1 (GTC-178) owns the
exhausted-silence red, J1 (GTC-192) owns the person-grid colour encoding, both open and unbuilt.
Routing to an unbuilt door means inventing one, which that line was written to prevent. D2 ships
the state, tested; the red is theirs. **The linkage is filed in both GTC-178 and GTC-192**, so
neither has to rediscover that the predicate is waiting.

### Two catches worth recording

**`restoreRevision` would have re-texted every maybe in an event.** `workflow.ts` deletes items
(assignments cascade) and rebuilds every `Assignment` with an explicit column list. Omitting
`decideByFollowupSentAt` there means every restored MAYBE reads "never followed up" and the next
15-minute tick texts all of them again. "Exactly one follow-up" is only true if it survives the
revision machinery. The sibling item-create list would likewise have silently reset Kate's
per-item override. Both are pinned by test, not comment.

**No write path existed for either override.** Acceptance line 52 requires a per-item host
override, but neither PATCH route accepted the field — it would have been settable only by
`psql`. Both now accept it with `Int >= 0` validation, deliberately non-substantive so it does not
flip a `GENERATED` item to `HOST_EDITED`.
