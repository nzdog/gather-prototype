## Signal

**Expected**
`tests/demo-endpoints-test.ts` asserts that neither demo handler contains an
environment gate — [[GTC-015]]'s product decision that the demo endpoints must
remain reachable in production. The property is about BEHAVIOUR: does a
`NODE_ENV` test cause a refusal.

**Actual**
It is decided by a regex with a fixed character window, at
`tests/demo-endpoints-test.ts` line 113:

```
const re = /if\s*\([^)]*NODE_ENV[^)]*\)\s*\{?[\s\S]{0,240}?status:\s*4\d{2}/;
```

Three ways a real gate passes it unseen:

- **A local binding.** `const env = process.env.NODE_ENV; if (env === 'production')
  return 404` contains no `NODE_ENV` inside the `if` parentheses. This is exactly
  the shape that defeated `collectEnvGate` in `tests/security-route-scan.ts`,
  measured under [[GTC-273]].
- **The 240-character window.** A gate whose refusal sits more than 240
  characters after the condition — a log line, a metric, a comment — is not
  matched.
- **`[^)]*`** cannot cross a nested parenthesis, so
  `if (isProd(process.env.NODE_ENV))` does not match.

**Smallest failing case**
Move the gate into a local binding. Behaviour is identical; the assertion stays
green and the product decision it exists to hold has been silently reversed.

## Why this is the sharpest example of the species, and why it is only Medium

**[[GTC-269]] named this defect, in this file, in these words:**

> *"A substring match is not a security assertion, and this file is the proof.
> It tests the spelling of the code, not its behaviour."*

It was right, and the fix was a real improvement: the assertion it replaced was
`!content.includes("process.env.NODE_ENV === 'production'")`, which was green
only because of a `(process.env.NODE_ENV as string)` cast added in `a20fbad`
eight months earlier for unrelated reasons. **A regex with a character window is
a smaller spelling test, not a different kind of thing.**

**Two things keep this at Medium rather than High.**

1. **The failure direction is a reversed product decision, not an exposure.** A
   missed gate means the demo endpoints quietly stop being reachable in
   production — [[GTC-015]]'s decision undone without a red. That is a real
   defect and it is not a security hole.
2. **It carries a control, which is more than the scanner's detector had.**
   `POST /api/demo/reset` genuinely has the gate and is asserted to be DETECTED
   as gated in the same run, so the two negatives mean something. That is
   [[GTC-267]]'s rule already applied here.

## Scope

**Fix here:**
- `tests/demo-endpoints-test.ts` — replace the regex with the AST test
  [[GTC-273]] built. `collectEnvGate` in `tests/security-route-scan.ts` now
  resolves `NODE_ENV` through a local binding and requires the branch's own
  DIRECT return to refuse, with a third verdict for a gate it cannot decide.
  **The two files should agree on what a gate is, which was [[GTC-269]]'s
  stated intention** — they agreed on a regex; they should agree on the rule.
- The control on `POST /api/demo/reset` must survive unchanged.

**The question this ticket must answer rather than assume:** whether
`tests/demo-endpoints-test.ts` should import from `tests/security-route-scan.ts`
or duplicate the logic. Importing couples a behavioural test to a static
analyser; duplicating re-creates the divergence. **Recommendation: import
`collectEnvGate`'s decision, exported for the purpose.** One definition of "what
a gate is" is the whole point, and it is the same argument [[GTC-270]] settled
by measurement for `cronSecretAccepted`.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding.
`tests/demo-endpoints-test.ts` does **not** match Zone 6's
`tests/security-*.ts` glob, so this ticket does not need Zone 6 sign-off for
that file — but it does if it exports anything new from
`tests/security-route-scan.ts`.

Out of scope: the demo routes themselves. [[GTC-015]]'s decision stands and
[[GTC-269]] holds the containment.
