# GTC-043 — Remove MOCK_HOST_ID hardcode

**Severity:** Critical
**Status:** Complete

---

## Signal

`MOCK_HOST_ID` with hardcoded value `cmjwbjrpw0000n99xs11r44qh` was used in API calls in three source files. Any real (non-seed) user hitting these paths would get the wrong host identity or a broken response.

---

## Evidence (Executor-Completed)

### Root cause

Three client-side pages used a hardcoded `MOCK_HOST_ID` constant instead of the authenticated user's real host ID:
- `src/app/plan/[eventId]/page.tsx` (4 usages)
- `src/app/plan/settings/page.tsx` (3 usages)
- `src/app/plan/templates/page.tsx` (1 usage as fallback)

### Auth source used as replacement

- **Event page (`plan/[eventId]`):** `event.hostId` from the `GET /api/events/[id]` API response, already loaded into component state.
- **Settings page (`plan/settings`):** `localStorage.getItem('gather_hostId')`, persisted by the event page at `loadEvent()`.
- **Templates page (`plan/templates`):** Same localStorage source (was already using it with query param priority; hardcoded value was only the final fallback).

### Files changed

| File | Change |
|------|--------|
| `src/app/plan/[eventId]/page.tsx` | Removed `MOCK_HOST_ID` constant and comment. Replaced 4 usages with `event?.hostId` / `event?.hostId ?? ''` |
| `src/app/plan/settings/page.tsx` | Removed `MOCK_HOST_ID` constant and comment. Added `hostId` state sourced from `localStorage.getItem('gather_hostId')`. Added empty-hostId guard with redirect to `/demo` |
| `src/app/plan/templates/page.tsx` | Removed hardcoded fallback `setHostId('cmjwbjrpw0000n99xs11r44qh')`. Existing `if (!hostId)` guard handles the empty case |

### Known limitation — follow-up ticket recommended

The settings and templates pages now source `hostId` from `localStorage` (`gather_hostId`), which is written by the event page when it loads. If a user navigates directly to `/plan/settings` or `/plan/templates` without having visited an event page first in that browser session, `localStorage` will be empty and they will see a dead-end guard message.

This is correct behaviour (no wrong ID is ever sent), but the UX is a band-aid. The proper fix is to source `hostId` from the auth session (cookie/token) so it works regardless of navigation order. That change touches the auth/session system (Do-Not-Touch Zone), so it requires a dedicated ticket.

**Recommended follow-up:** GTC-044 — Source hostId from auth session instead of localStorage on settings and templates pages.
