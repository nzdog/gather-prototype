## Why

A guest record (the Person table: name, email, mobile) belongs to no
host. When a host adds a guest, `src/lib/households/capturePerson.ts`
looks for an existing real record anywhere in the database with the
same email and first name, and reuses it. So:

- Host B can be handed the record host A made: B then sees the name,
  email and mobile A stored, B's invitation can go to A's stored
  number, and an edit B makes changes what A sees.
- The email comparison is not plain text. It ignores capitals the way
  a search pattern does, so the characters `%` and `_` in a typed
  address act as wildcards ("any run of characters", "any one
  character"). A typed address can therefore match a stored address
  that differs from it (GTC-411 proved the same on the User table).

A typed address must be compared as plain text, and an existing
record may only be reused when it is already one of the same host's
guests.

GTC-293 Q2 ruled reuse "on this event or another"; it never weighed
other hosts. GTC-465 overrides GTC-293 Q2 across hosts (ruling Q4).

## Severity: high (ruled, Q7)

- Any host or co-host of a real event can be handed another host's
  guest record (name, email, mobile) and can then change it.
- A changed mobile or address moves where host A's own texts and
  emails go.
- It happens with no bad intent too, whenever two hosts invite the
  same person.
- Not critical: it needs a real (paid) event or a co-host role, and
  demo samples cannot reach real people (GTC-392, GTC-441).
- The privacy page says guest details are shared only with service
  providers.

## What the code does (origin/main c4438b7)

- `src/lib/households/capturePerson.ts:64-81`: the match. Email
  "equals, ignoring capitals" (a pattern comparison in Postgres),
  `sampleEventId: null`, then the first name in code. No host or event
  filter on a real event. The typed email is not trimmed (line 60).
- `:82-85` and `:106`: on a match the record is returned unchanged,
  except `:100-105`, which fills the record's first-sent date
  (`inviteAnchorAt`) if it is empty.
- On a sample event (`isDemoEvent`) the match looks only at people on
  that sample (`:68-69`).

The four entry points, and what each passes today:

- add person: `src/app/api/events/[id]/people/route.ts:128`
- CSV import: `src/app/api/events/[id]/people/batch-import/route.ts:111`
- new household: `src/app/api/events/[id]/households/route.ts:233`
- household edit: `src/lib/households/reconcileMembers.ts:325`

Each already passes the event's id and `hostPersonId` read from that
event's own row (`Event.hostId`): `event.hostId` (people, CSV),
`event!.hostId` (households) and `await eventHostId()`, which reads
`prisma.event.findUnique({ where: { id: eventId }, select: { hostId:
true } })` (household edit). So the fix needs no change at any entry
point.

## The change (one file: capturePerson.ts)

1. Trim the typed email (Q8). Keep only candidates whose stored
   address equals the typed one as plain text, after trimming and
   lower-casing, checked in code (as `user-by-email.ts` does).
2. On a real event, look only at people already on one of the event's
   host's real events (`Event.hostId`, Q2), plus the host's own record.
   Samples unchanged. The first-name rule and "the host's own record
   first" unchanged.

No schema change, no migration, no route added or removed, no zone
file, no frozen file.

Two facts found while writing the tests, for the build:

- **A new event gives its host no membership row.** Creating an event
  (`src/app/api/events/route.ts`) writes an EventRole for the host's
  login, not a PersonEvent. The host's PersonEvent comes later (the
  households POST checks `hostHasMembership`). So "the host's own
  record first" must not depend on her being on one of her events:
  the fix must include the host's own record (`Event.hostId`) as a
  candidate. Check H1 holds this.
- **shared-address E3 leans on a record with no event.** E3 makes
  people with the helper and never puts them on the event, then types
  them again. Under ruling Q1 such a record is on none of the host's
  events, so it is not found. See "Question for the founder" below.

## What a removed guest, and the host's own address, do now (step 6)

**A guest removed from all of a host's events, then typed again.** Q9:
they are not found again, so the helper makes a new record holding
exactly what was typed. Removing a guest deletes their membership row
and their links (`people/[personId]/route.ts:432-437`), but not the
record or anything keyed on it. So:

- **A text STOP still holds.** STOPs are kept by number (SmsOptOut),
  and the last send check (`sendSms`) refuses any text to that number,
  whatever the record says. N2 proves this for a new record.
- **An email unsubscribe for that event was lost; Q11 closes it.**
  EmailOptOut is kept per record and per event, so it stays on the
  old record. Before Q11, a guest who had unsubscribed from emails for
  event E, was removed, and was typed again on E came back as a new
  record, and E's emails could reach them again. With Q11 a record
  with an email opt-out on one of this host's real events is found
  again (R1), and an opt-out on another host's event never is (R2). A
  bounce or spam block is kept by address (EmailBlock) and still
  holds.
- Anything else of theirs (links, dish assignments, replies) was
  already removed or stays on the old record.

**A host typing her own email and first name on her own event.** She
is always a candidate (`sameHostScope` includes `Event.hostId`), even
before she is on her own guest list, and the host-first choice is
unchanged, so it is her own record, as before (H1; shared-address F1).
The add-person route then answers "Person is already part of this
event" if she is already on it; the households paths keep GTC-256's
guards. On ANOTHER host's event, the same typing now gives a new
record.
