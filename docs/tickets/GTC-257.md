# GTC-257 — Automated SMS templates pay double for one character

**Status:** Open — unassigned, not started | **Branch:** TBD | **Commit:** [pending] | **Effort:** TBD

*Filed as bookkeeping during [[GTC-187]] (H2), which measured this while removing the same
defect from the ask register. Pre-existing, NOT caused by H2. Following the filing discipline
of [[GTC-256]]: state the consequence, note what closing it would touch, and **propose no
fix** — two of the decisions here are the founder's, not an executor's. No template was
edited by this ticket.*

### Scope, one line

Every automated SMS template in `src/lib/sms/nudge-templates.ts`, and
`buildSmsWrapUpMessage` in `src/lib/sms/wrap-up-templates.ts`, contains an em dash. The em
dash is not in the GSM-7 alphabet, so each message encodes as UCS-2 at **70 characters per
segment instead of 160** — roughly doubling the segment count, and the bill, for one
character of punctuation.

### Signal

**Expected**
A ~200-character nudge bills as 2 SMS segments.

**Actual**
It bills as 3 or 4. The message length is unchanged; only the encoding is.

**Smallest failing case**
`getFirstNudgeMessage` returns a 207-character string containing one `—`. `getMessageInfo`
on that string reports 3 segments. Replace the em dash with a hyphen and the same 207
characters report 2.

### Reproduce

**Required state**
None. Pure functions, no database, no auth, no event.

**Steps**
```ts
import { getFirstNudgeMessage, getMessageInfo } from '@/lib/sms/nudge-templates';

const msg = getFirstNudgeMessage({ hostName: 'Sarah Henderson', eventName: 'Henderson Family Christmas 2026', link });
getMessageInfo(msg);                              // { length: 207, segments: 3, hasUnicode: true }
getMessageInfo(msg.replace(/—/g, '-'));           // { length: 207, segments: 2, hasUnicode: false }
```

**Observe:** identical length, one fewer segment.

### The evidence

Measured 2026-08-29 against a production-shaped participant link (66 characters), event name
`Henderson Family Christmas 2026`. "If em dash removed" substitutes a hyphen and re-measures
through `getMessageInfo`; "other non-GSM-7" is what remains after that substitution.

| Symbol | chars | segments now | if em dash removed | other non-GSM-7 |
|---|---|---|---|---|
| `getFirstNudgeMessage` | 207 | 3 | **2** | none |
| `getSecondNudgeMessage` | 211 | 4 | **2** | none |
| `getProxyHouseholdReminderMessage` | 219 | 4 | **2** | none |
| `getDecideByFollowupMessage` | 173 | 3 | **2** | none |
| `getHostNudgeMessage('direct', …)` | 142 | 3 | **1** | none |
| `getHostNudgeMessage('warm', …)` | 148 | 3 | 3 — no change | 😊 |
| `getHostNudgeMessage('casual', …)` | 129 | 2 | 2 — no em dash | 👋 |
| `getHostNudgeMessage('gentle', …)` | 176 | 2 | 2 — already clean | none |
| `buildSmsWrapUpMessage` | 156 | 3 | **1** | none |

Four of the five nudge templates carry the em dash inside the same substring:
` — Reply STOP to opt out`. `getHostNudgeMessage`'s `direct` variant and
`buildSmsWrapUpMessage` each carry a separate one elsewhere in their prose, and those two are
**tied for the largest ratio in the set — three segments to one**. `buildSmsWrapUpMessage` is
the one of that pair which no ruling below blocks; see "Why the wrap-up is folded in".

The same measurement on [[GTC-187]]'s ask register, before and after removing its em dashes,
on real `Henderson Family Christmas 2026` recipients: 510 characters went from 8 segments to
4, 489 from 7 to 4, 466 from 7 to 3. In every body the em dash was the **only** non-ASCII
character present.

### The multiplier — why this is worse here than it was there

The ask sends **once per person**, at the press.

These do not:

- `findNudgeCandidates` is swept by `/api/cron/nudges` **every 15 minutes**, and
  `DEFAULT_NUDGE_OFFSET_DAYS` in `src/lib/nudge-cadence.ts` is `[4, 7]` — **up to two
  nudges per unresponsive guest, on every event, indefinitely.**
- `getDecideByFollowupMessage` fires once per MAYBE, per item, on every event with maybes.
- `getProxyHouseholdReminderMessage` fires per proxy household.
- `getHostNudgeMessage` fires whenever a host composes one, unbounded.
- `buildSmsWrapUpMessage` is dispatched by `dispatchPendingWrapUpMessages` from
  `/api/cron/wrap-up-dispatch`, swept **every 10 minutes**, once per wrap-up recipient per
  event.

The ask register's fix was a one-off saving on one message per guest. This is a recurring
saving on the machinery that runs forever.

### Two things that need a founder ruling, not a fix

Both are the reason this ticket proposes nothing.

**1. The em dash lives inside the mandatory opt-out suffix — in four of the six templates.**
`getFirstNudgeMessage`, `getSecondNudgeMessage`, `getProxyHouseholdReminderMessage` and
`getDecideByFollowupMessage` carry it as ` — Reply STOP to opt out`. This ruling gates those
four and nothing else: `getHostNudgeMessage`'s em dash and `buildSmsWrapUpMessage`'s are both
in ordinary prose.
`getDecideByFollowupMessage`'s own comment states: *"The ` — Reply STOP to opt out` suffix is
mandatory on every system-sent template and is not a stylistic choice."* Changing the
punctuation inside a string the codebase has declared non-stylistic and compliance-bearing is
not an executor's call, even when the change is one character. SMS opt-out is
Do-Not-Touch zone 7 in `GATHER-BUILD-CONSTANTS.md`; that zone names `SmsOptOut` and
`Person.smsOptedOut` rather than this string, so this is adjacent to the zone rather than
inside it — which is exactly the kind of edge that wants a ruling instead of a judgement
call.

**2. The emoji in the `warm` and `casual` host variants are a deliberate voice choice.**
`HOST_NUDGE_TEMPLATES` in `src/lib/sms/nudge-templates.ts` gives `warm` a 😊 and `casual` a
👋. Emoji are UCS-2 **regardless of punctuation**: as the table shows, removing `warm`'s em
dash changes its segment count not at all, and `casual` has no em dash to remove. These two
variants stay at 70-character segments unless the emoji go, and the emoji are the variant.
Whether that cost is accepted on purpose is a voice decision. Note the asymmetry it creates:
`direct` and `gentle` would become cheap while `warm` and `casual` stay expensive, which is a
pricing gradient across tone — worth seeing before it is chosen.

### Why this is not an unscoped edit from a composition ticket

`src/lib/sms/nudge-templates.ts` is [[GTC-178]] (E1) and [[GTC-179]] (E2)'s deliverable, and
both are closed. [[GTC-187]] builds message composition and has no claim on it; folding this
in there would have been an unscoped change to closed work, and folding it into [[GTC-189]]
would put it on the dispatch path's ticket for no better reason. It is filed separately so
the change carries its own evidence, its own before/after measurement, and the two rulings
above.

### Why the wrap-up is folded in (founder, 2026-08-29)

`buildSmsWrapUpMessage` in `src/lib/sms/wrap-up-templates.ts` carries the identical defect —
an escaped `\u2014` in `Gather — the app they used to organise …` — and was first filed here
as adjacent-but-unclaimed. The founder folded it into this ticket rather than filing it
separately: same defect, same character, same class of change, and two tickets would mean two
things queued behind one conversation.

**⚠ ONE PREMISE OF THAT FOLD-IN IS CORRECTED HERE, AND IT LOOSENS THE TICKET RATHER THAN
TIGHTENING IT.** The fold-in was reasoned partly on both halves waiting on the same
STOP-suffix ruling. They do not. `buildSmsWrapUpMessage` contains no
` — Reply STOP to opt out` substring at all — verified: `grep -n "Reply STOP"` over
`src/lib/sms/wrap-up-templates.ts` returns nothing, and `sendSms` in
`src/lib/sms/send-sms.ts` appends no suffix to anything it sends. Its em dash sits in
ordinary parenthetical prose.

So founder ruling 1 does **not** gate the wrap-up half. Of the two tied-largest ratios in the
table, `buildSmsWrapUpMessage` is blocked by nothing, while
`getHostNudgeMessage('direct', …)` is blocked only by sharing a file with the four templates
ruling 1 does gate. That is an argument for one ticket, not against it — but an executor
picking this up should not wait on ruling 1 for the wrap-up.

### Scope

**Territory, if this is picked up:**
- `src/lib/sms/nudge-templates.ts` — the five automated template functions and
  `HOST_NUDGE_TEMPLATES`.
- `src/lib/sms/wrap-up-templates.ts` — `buildSmsWrapUpMessage`. Folded in by the founder,
  2026-08-29. Note `buildEmailWrapUpMessage` in the same file carries the same character in
  its `body`, and email has no segments, so the cost argument does not reach it — the same
  exemption `askSubject` in `src/lib/messages/ask-register.ts` carries and states.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`, zone 7 (SMS opt-out) especially —
  see founder ruling 1 above.
- `getMessageSegments` and `getMessageInfo`. They are the counter, not the defect, and
  [[GTC-187]]'s `composedCost` in `src/lib/messages/compose.ts` now reads them too.
- The ask register. [[GTC-187]] already fixed it and pins it with a GSM-7 assertion in
  `tests/message-composition-test.ts`.

### Unknowns

- **The counter is not a true GSM-7 check.** `getMessageSegments` tests
  `/[^\x00-\x7F]/` — any non-ASCII character. Real GSM-7 includes `£ é è ù ì ò Ç Ø å Δ § ¿ ä
  ö ñ ü à` and others, so the repo would report UCS-2 for messages a gateway encodes as
  7-bit. For the em dash both agree — it is genuinely absent from GSM-7 — so the measurements
  above hold either way. Whether the counter itself should be corrected is a separate
  question this ticket does not open.
- **Nothing reads the count to make a decision.** `sendNudge` in
  `src/lib/sms/nudge-sender.ts` records `messageSegments` in metadata only. The real bill
  comes from TNZ or Twilio doing their own encoding detection, so the saving is real
  independent of what the counter reports — but the exact per-segment rate on the TNZ account
  is not recorded anywhere in this repo, so the dollar figure cannot be stated here.
- **No test pins any of these templates' encoding.** [[GTC-187]] added a GSM-7 gate for the
  ask register only. Nothing stops an em dash returning to these six.
- **`getDecideByFollowupMessage`'s "mandatory" comment and `buildSmsWrapUpMessage` disagree,
  and this ticket does not settle it.** That comment states the ` — Reply STOP to opt out`
  suffix is "mandatory on every system-sent template". `buildSmsWrapUpMessage` is a
  system-sent template and has no such suffix. Either the comment overstates the rule or the
  wrap-up SMS is missing something it should carry. Noticed while folding the wrap-up in;
  recorded because a reader will otherwise hit the same contradiction. **Not a claim that
  anything is non-compliant** — opt-out STATE is honoured on that path twice over:
  `generateWrapUpLinks` in `src/lib/wrap-up.ts` skips the SMS channel for a person with
  `smsOptedOut`, and `sendSms` in `src/lib/sms/send-sms.ts` checks opt-out before any
  provider work and returns `blocked: 'OPTED_OUT'`. What is absent is the instructional
  suffix telling the recipient how to opt out, and whether that is legally required is not a
  question this repo answers. It is zone-7-adjacent and wants a founder decision, not an
  executor's edit.
