# GTC-206 — restoreFromRevision nulls every PersonEvent.teamId

**Status:** Open — unassigned, not started | **Branch:** TBD | **Commit:** [pending] | **Effort:** TBD

*Filed as bookkeeping during GTC-171 (B2). Pre-existing, NOT caused by B2, and explicitly
out of B2's scope — see "Relationship to GTC-171" below.*

### Scope, one line

`restoreFromRevision` nulls every `PersonEvent.teamId`, leaving nobody on any team after a
revision restore — which the same-team assign gate then reads as "nothing is assignable."

### Context

Restoring a plan revision silently empties every team of its members. The event still has
teams and items, but no `PersonEvent` points at any team, so the host cannot assign anything:
`POST /api/events/[id]/items/[itemId]/assign` rejects every person with
`"Person must be in the same team as the item"` (400).

Nothing errors. The restore reports success, the plan looks intact, and the failure only
surfaces the next time somebody tries to assign an item.

### Verified mechanism

Four steps, each confirmed in code:

1. `restoreFromRevision` deletes every team for the event —
   `src/lib/workflow.ts:887`:
   ```ts
   // Delete current teams
   await tx.team.deleteMany({
     where: { eventId },
   });
   ```
2. `PersonEvent.team` is `onDelete: SetNull` (`prisma/schema.prisma:188`, set by GTC-147's
   migration `20260708005434_change_person_event_team_set_null`). Deleting the teams therefore
   nulls `PersonEvent.teamId` for every member rather than failing.
3. Teams are recreated with **new** cuids and tracked in a `teamIdMap` (old ID → new ID) at
   `src/lib/workflow.ts:916-930`, so even the old ids the memberships pointed at no longer exist.
4. Nothing restores the memberships. The TODO at `src/lib/workflow.ts:919` records that person
   restoration was never implemented:
   ```ts
   // TODO: Revision system - person ID mapping for restored team memberships (Section 9 of build spec)
   // Will need: const personIdMap = new Map<string, string>(); when implementing person restoration
   ```

`teamIdMap` exists and is populated, so the data needed to remap memberships is already in hand
at the point of the gap.

### Why it matters

The same-team gate is load-bearing on both assign routes:
- `src/app/api/events/[id]/items/[itemId]/assign/route.ts:67` — `personEvent.teamId !== item.teamId` → 400
- `src/app/api/c/[token]/items/[itemId]/assign/route.ts:53` — same check against the token's team

`PersonEvent.teamId` is singular (`@@unique([personId, eventId])`, `prisma/schema.prisma:193`),
so a nulled membership is a total loss of assignability for that person, not a partial one.

### Test coverage gap

Test Suite 7 in `tests/security-validation.ts:467-510` exercises `restoreFromRevision` but
asserts only that it does not throw, that a checkpoint revision was created, and that an audit
entry landed. It never asserts membership survival, so this is green today and would stay green.

### Suggested fix direction (not prescriptive)

Rebuild memberships after the team recreation loop using the existing `teamIdMap`: capture each
`PersonEvent.teamId` before the `team.deleteMany` at `:887`, then re-point survivors at the new
team ids. Members whose team is absent from the restored revision have no correct target and
need a ruling — most likely `null` (unassigned) rather than a guess.

### Acceptance

- [ ] A revision restore preserves every `PersonEvent.teamId`, remapped to the recreated team ids.
- [ ] Members of a team that no longer exists in the restored revision are handled by an explicit,
      documented rule rather than incidentally.
- [ ] RED→GREEN test: assign an item after a revision round-trip and assert it succeeds. Must fail
      against unpatched code.
- [ ] `npx tsc --noEmit` clean, build passes, security suite exits 0.

### Relationship to GTC-171 (B2)

B2 relaxes the same-team gate for `kind: 'TASK'` rows only
(`if (item.kind === 'ITEM' && personEvent.teamId !== item.teamId)`), so after B2 a restored event
has an asymmetry worth naming: **task rows stay assignable across the gate, item rows do not.**
That makes this bug more visible, but does not cause it — the item-row behaviour is identical
before and after B2.

Filed rather than fixed in B2 deliberately: it is a pre-existing correctness bug in the revision
system, not part of B2's task-row scope, and prose in a not-in-scope list is where bugs get
forgotten.
