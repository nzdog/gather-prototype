# GTC-220 — SECURITY/HARDENING: Move `CRON_SECRET` from URL query string to a request header

**Status:** Open — unassigned, not started. **Effort:** low
**Severity:** Low (no known exploitation; hardening against plaintext-secret exposure in logs
and third-party config, not an active vulnerability)

### Context

The three cron routes already accept the secret two ways — an `Authorization: Bearer <secret>`
header, or a `?secret=...` query param — and check either against `CRON_SECRET`:

- `src/app/api/cron/nudges/route.ts:16-19`
- `src/app/api/cron/wrap-up-dispatch/route.ts` (same shape)
- `src/app/api/cron/decide-by-followups/route.ts` (same shape, "same shape as the two existing
  cron routes" per its own comment)

The EasyCron jobs are currently configured to call these routes with `?secret=...` in the URL,
not the header. That means `CRON_SECRET` sits in plaintext in two places it doesn't need to:
EasyCron's own job configuration (visible to anyone with EasyCron account access), and Railway's
request logs (URLs are commonly logged in full; headers less so, and `Authorization` in
particular is conventionally redacted by log tooling).

### Scope

**Fix here:**
- Update the three cron routes to read the secret from the `Authorization: Bearer` header only,
  removing the `?secret=` query-param fallback.
- Update the EasyCron job configuration for all three jobs to send `CRON_SECRET` as an
  `Authorization: Bearer` header instead of a URL query param.

**Do not touch:**
- The value of `CRON_SECRET` itself — this is a transport change, not a rotation. (Rotating it
  is a reasonable follow-up given the plaintext exposure to date, but is a separate decision —
  note it, don't fold it in silently.)
- Cron scheduling/frequency, job logic, or any non-auth behaviour of the three routes.
- Any other route's auth pattern — scoped to these three cron routes only.

### Why a ticket, not a drive-by

Touches the auth check on three routes that gate real (if low-value) endpoints, and requires a
coordinated external change (EasyCron config) alongside the code change — if the two land out of
step, the cron jobs 401 until both sides agree on transport. Sequencing (deploy code first with
both header and query accepted, flip EasyCron, then remove the query fallback in a follow-up) is
worth ruling on explicitly rather than assuming a single atomic cutover is safe.

### Acceptance

- [ ] All three cron routes accept `Authorization: Bearer <CRON_SECRET>` and reject requests
      without it (when `CRON_SECRET` is set).
- [ ] `?secret=` query param no longer accepted once the cutover is complete.
- [ ] EasyCron jobs updated to send the header; a live trigger of each job confirmed 200, not 401.
- [ ] No `CRON_SECRET` value appears in any URL, log line, or EasyCron job config after the
      change.

### Stop Conditions

Standard eight from `BUG-TICKET-TEMPLATE.md`. In particular: if EasyCron's UI cannot set a
custom request header on a job (some low-tier cron SaaS plans restrict this), that is Stop
Condition 8 (unknown surfaces during investigation) — stop and report rather than falling back
to a weaker workaround (e.g. encoding the secret differently in the URL).
