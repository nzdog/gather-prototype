# GTC-346 — a 100-send dispatch run, one send at a time, against a 30-second wait

**Status:** Open — a stub, filed 2026-10-01 at [[GTC-335]] on founder instruction (*"at volume, an
outbound-dispatch run of 100 sends, one at a time, can outlast cron-job.org's 30-second wait,
which it may count as a failure"*). Not scoped.
**Severity:** not set at filing — the founder's to set.

---

### Signal

Production's crons are called by an outside scheduler (`GATHER-BUILD-CONSTANTS.md`, *Cron routes*;
GTC-042 set up cron-job.org). cron-job.org waits 30 seconds for an answer and may count a longer
run as a failed one. Since [[GTC-339]] a failed run is what reaches the founder, so a run that is
merely slow would read as broken.

`GET` in `src/app/api/cron/outbound-dispatch/route.ts` calls `drainOnce` with `DRAIN_BATCH` (100),
from `src/lib/press/dispatch.ts`. `drainOnce` takes up to 100 never-attempted rows and up to 100
due for retry, and sends them one at a time: each provider call is awaited before the next. The
same request then runs the delivery poll (`pollOnce`). A few hundred milliseconds per provider
call is enough for a full batch to pass 30 seconds.

### Unknowns

1. The real time per send, by channel, from production logs (TNZ and Resend differ).
2. What the scheduler does with a timed-out run: whether it retries, and whether a retry can
   overlap the run still going (the drain's claim is meant to stop a double send; to confirm).
3. The fix's shape: a smaller batch, a time budget per run, answering before the work finishes,
   or sending in parallel within a provider's limits.
