### Storage — the shape, and which migration

**A nullable column on `PersonEvent`.** The grain is exactly right: one row per (person, event),
`@@unique([personId, eventId])`. The precedent is its neighbour. `PersonEvent.nudgeMark`'s own
docstring makes the argument this ticket would otherwise have to make again:

> ON PersonEvent, NOT Person, and that is the whole point. The mark is a per-EVENT hosting
> judgement: Kate may go gentle on her mother for the wake and not for the birthday. Putting it on
> Person would reproduce exactly the global-for-a-per-event leak that `Person.inviteAnchorAt` and
> `Person.nudge24hSentAt`/`nudge48hSentAt` above are both retained-but-unwritten monuments to.

**Nullable, not a boolean with a default**, for the same reason `nudgeMark` is: *"NULL means NO
MARK — no opinion — and it is not a stored 'normal'."*

⚠ **THE REASON FOR THIS CHANGED ON 2026-09-15 AND THE RECOMMENDATION DID NOT — recorded rather than
silently rewritten.** At ruling AG the argument was that three states were needed: she ticked, she
looked and did not, and **she was never asked**. **Ruling AJ removes the third** — the mini-send
asks too, so nobody is ever unasked. The column is still nullable under **ruling AH**, for a
different reason: **NULL means *follow the event default***, which under AH is the common case and
most rows. A right conclusion resting on a wrong reason is the shape [[GTC-273]] and [[GTC-276]]
are both about, so the correction is on the record.

**And the event-level default needs its own field**, a sibling of `Event.nudgePace` — nullable, per
event, host-set, *"NULL means NOT SET"*. Both should ride slice 4's migration.

**It is NOT part of slice 4's outbound record.** That row describes a message that was sent — event,
membership, kind, channel, provider, provider message id, accepted at, rejected at, why. This is a
standing host decision that exists before anything is sent, one per membership rather than one per
message, with a different lifetime. Putting it there would make an instruction into a property of a
message.

**But it should ride in slice 4's migration.** Slice 4 is *"Schema, alone"*, already scheduled and
already required to be rehearsed against a production copy per the Deploy caveat in
`GATHER-BUILD-CONSTANTS.md`. A second migration for one nullable column buys nothing and costs a
second rehearsal — the same reasoning ruling W recorded for [[GTC-299]]'s third `kind`, *"cheaper to
meet before that migration than after."* **Executor's recommendation, not a founder ruling.**
