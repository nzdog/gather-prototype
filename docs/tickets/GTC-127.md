# [[GTC-127]] — Fix regenerate plan failure: raise maxTokens + audit prompt sizes — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** 9ba5eaa

### What was found

**Root cause (confirmed via pre-[[GTC-127]] server log):** four Claude API calls in the Moment 2 regenerate path had `max_tokens` caps undersized for real-world prompts. Responses hit the ceiling mid-token, tripped `parseClaudeJSON`'s `stopReason === 'max_tokens'` guard ([`src/lib/ai/claude.ts:111-118`](src/lib/ai/claude.ts)), and cascaded 500 → red toast on the client.

| Call site | Old cap | Observed typical output |
|---|---|---|
| `generate-section/route.ts:174` | 1024 | 2900–3250 chars ≈ 950–1080 tokens |
| `finalize-plan/route.ts:205` (gap-fill) | 1024 | same shape as section-gen |
| `finalize-plan/route.ts:239` (dietary coverage) | 512 | ~600–800 chars, boundary-hitting on long flaggedItems |
| `finalize-plan/route.ts:252` (things to consider) | 512 | ~600–900 chars |

Broader maxTokens scan across the codebase surfaced one more small cap — `src/lib/ai/generate.ts:187` `generateExplanation` at 1024. That path is AI conflict-explanation with a mock fallback on error, not part of the Moment 2 regenerate chain. Left as-is; follow-up candidate.

Contributing factor per diagnosis: [[GTC-123]] enriched prompts with NZ-config reference items which both (a) added input tokens and (b) encouraged the model to produce more output items per section. The 1024 cap was adequate pre-[[GTC-123]] and became insufficient after.

### What was changed

**Phase 1+2 — centralised caps and raised them:**

New file `src/lib/ai/token-limits.ts` holds all four ceilings as named `MAX_TOKENS_*` constants with block comments noting the measured range and headroom rationale. The four call sites now import from this file instead of inlining literals.

| Constant | Value | Applied at |
|---|---|---|
| `MAX_TOKENS_SECTION_GENERATION` | 4096 | `generate-section/route.ts:175` |
| `MAX_TOKENS_GAP_FILL` | 2048 | `finalize-plan/route.ts` gap-fill |
| `MAX_TOKENS_DIETARY_COVERAGE` | 1024 | `finalize-plan/route.ts` coverage |
| `MAX_TOKENS_CONSIDERATIONS` | 1024 | `finalize-plan/route.ts` consider |

Claude Sonnet 4.6 supports 64K output tokens; these caps are all comfortably inside the platform limit.

**Phase 3 — measurement script + audit:**

New `tests/measure-moment2-prompts.ts` loads a real event (defaults to Kate's `909a2d6c-…`), reconstructs the exact `householdData`, `dietaryData`, and `generatedData` each AI call receives, then calls the (newly-exported) prompt builders to report input char length and approximate input tokens.

Kate test event results:

```
event:    Kate test event — Christmas — 6 adults + 11 kids — Dairy-free, Vegan

section-gen (mains)       sys  423c  usr  1247c   in  418t / cap 4096t
section-gen (sides)       sys  423c  usr  1718c   in  536t / cap 4096t
section-gen (desserts)    sys  423c  usr  1433c   in  464t / cap 4096t
section-gen (drinks)      sys  423c  usr  1802c   in  557t / cap 4096t
section-gen (setup)       sys  423c  usr  1024c   in  362t / cap 4096t
section-gen (dietary)     sys  423c  usr   381c   in  201t / cap 4096t
gap-fill (mains)          sys   84c  usr   361c   in  112t / cap 2048t
dietary-coverage          sys   72c  usr  5301c   in 1344t / cap 1024t
things-to-consider        sys   70c  usr   316c   in   97t / cap 1024t
```

(The `cap` column is the OUTPUT token ceiling; input tokens are governed separately by the model's 200K context window. The two budgets are independent — the `dietary-coverage` 1344 input tokens vs 1024 output cap is not a conflict, it's just the script using the output cap as a label reference.)

**Tightening decision: none applied.** Per-call rationale:

- **section-gen** input 201–557 tokens — bulk is NZ-config reference items and Kate's wanted/excluded lists. Both are load-bearing for plan quality ([[GTC-123]] introduced them deliberately). Removing or truncating would regress.
- **gap-fill** input 112 tokens — already minimal.
- **dietary-coverage** input 1344 tokens — the `itemList` flatten-all is load-bearing: the model can't judge coverage without knowing what's in the plan. No obvious redundancy.
- **things-to-consider** input 97 tokens — already minimal.

Per assertion 8, the audit happened and no tightening was warranted because prompts were already tight on bulk and the "heavy" parts (reference items, full item list) are necessary for output quality.

**Phase 3 enabling change:** prompt-builder functions were marked `export` in `generate-section/route.ts` and `finalize-plan/route.ts` so the measurement script can import them without duplicating logic. Next.js App Router treats non-handler exports from route files as harmless (only `POST`/`GET` etc. are routed); zero runtime impact.

### Known limitations

- **End-to-end browser verification is user-gated.** Unit-level measurement confirms inputs are sized sensibly and the new caps give 3× headroom over observed peak outputs. A live regenerate on Kate's event after these changes land is Nigel's turn — dev server has hot-reload, so the fix should already be live; a visual confirmation "plan regenerates cleanly, no red toast" from the browser closes this loop.
- **`generateExplanation` at `generate.ts:187` still has `maxTokens: 1024`.** Explicitly out of scope (not in the Moment 2 regenerate chain, has a mock fallback). File a follow-up if conflict-explanation failures appear in logs.
- **Headroom target (25%) is empirical.** If future prompts grow (bigger events, more dietary requirements, richer NZ config), the caps may need another bump. Making the caps named constants means future adjustments are single-line.
- **Prompt audit is a snapshot.** Sizes measured once, against Kate's test event. If event types with different config profiles (e.g. wedding with very long reference lists) behave differently, a fresh audit will be needed. The `tests/measure-moment2-prompts.ts` script accepts an `eventId` argument for easy re-runs.
