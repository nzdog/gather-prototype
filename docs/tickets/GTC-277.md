## Finding 1 — GitHub's alert count must not be used to triage this repo

**GitHub reports 75 open Dependabot alerts (35 high, 35 medium, 5 low).
`npm audit` on this branch reports 13 packages. Both numbers are accurate.
Neither describes this branch's real exposure, and the GitHub one is
dangerously wrong in both directions at once.**

Reproduced live, 2026-09-12, via `gh api repos/nzdog/gather-prototype/
dependabot/alerts?state=open` — 75 alerts, severity split confirmed to the
digit. Every alert's `vulnerable_version_range` was then evaluated with semver
against this branch's installed versions. Result:

- **36 of the 75 are already dead here** — cleared by version bumps that have
  shipped on this branch. `axios` alone accounts for 28 of them ([[GTC-245]]
  moved it 1.15.0 → 1.19.0). Plus `js-yaml` 3, `brace-expansion` 2,
  `form-data` 1, `qs` 1, `follow-redirects` 1.
- **2 more are dead because the package left the tree** — `uuid` (dropped by
  GTC-245 Phase 2b) and `@babel/core` (dropped with the `eslint-config-next`
  downgrade in `b6e6e38`).
- **37 still apply** — 19 high, 15 medium, 3 low; 30 runtime, 7 development.
- **5 advisories live on this branch that GitHub raises no alert for at all**:
  `browserslist` GHSA-c83g-rgw3-j3cx (high), `deepmerge-ts`
  GHSA-ggr8-5vv4-36mx (high), `js-yaml` GHSA-2883-xcg3-v3hh (high), and
  **both Next.js criticals** — GHSA-p293-qw3h-jr36 (unauthenticated RCE on
  Windows-hosted servers) and GHSA-2xp9-vwfh-vxw4 (unauthenticated RCE in the
  Image Optimization API via AVIF).

37 + 5 = **42**, which is exactly `npm audit`'s distinct package-times-advisory
count on this branch. The reconciliation closes with no remainder.

**Stated plainly: GitHub's 75 is 38 alerts too high, and blind to the two most
severe live findings in the tree.** Anyone triaging off that number would be
reading a figure that is half stale and silent on both criticals.

### Why the gap exists

Three effects stack:

1. **Different code.** Dependabot always scores the default branch. The
   default branch is `master`, at `ebc21d9`. This branch is 320 commits ahead
   of the merge-base (`b28204b`) and has **diverged** — `origin/master` is not
   an ancestor of `feat/moment-one-redesign`. Master's lockfile still carries
   `axios@1.15.0`, `js-yaml@4.1.1`, `brace-expansion@1.1.13`, `form-data@4.0.5`,
   `follow-redirects@1.15.11`, `uuid@10.0.0`, `qs@6.15.0` — every one already
   fixed here. GitHub has never seen those fixes.
2. **Different units.** `npm audit` prints one row per *package*; GitHub opens
   one alert per *(package × advisory)*. One `next` row carries 24 advisories.
3. **Different ingestion.** Each surface knows advisories the other does not,
   in both directions — hence the 5 above.

This supersedes [[GTC-243]]'s finding 1, which recorded the same species of
discrepancy (67 vs 26 vs 16) but could not explain it and left it "flagged,
not resolved." It is resolved: effect 1 plus effect 2 plus effect 3, and the
arithmetic closes exactly. GTC-243's recommendation — *"scope tickets against
`npm audit` run directly on the branch being fixed"* — was correct and is
hereby confirmed rather than superseded.

**This gap regenerates forever while `master` is the default branch and
nothing merges into it.** That is a standing decision, filed as [[GTC-279]].

## Finding 2 — `npm ci` was not owed, and running it would have been pure downside

**Correction to the premise this investigation was commissioned under.** The
briefing held that `node_modules` was dated 2 June against a current
`package.json`, so `npm ci` was owed — and that running it was hazardous,
because `npm ci` deletes `node_modules` and wipes the generated Prisma client,
reproducing the failure [[GTC-192]] phase 5 spent an hour on.

**The hazard is real. The premise is false. Nothing was stale.** Recorded here
so the premise is not rediscovered and re-acted on.

- The 2 June dates are **package directory mtimes preserved from tarball
  extraction**. npm does not re-touch a directory whose contents it did not
  change. `node_modules/next` is dated 2 Jun and contained `15.5.14` — exactly
  what the lockfile said.
- `node_modules/.package-lock.json` and `package-lock.json` were both
  lockfileVersion 3 and dated the same minute (12 Sep 11:19).
- Compared entry by entry: 551 lockfile entries, 475 installed, **zero version
  mismatches, zero packages installed that the lock does not name.**
- The 76 lockfile entries absent from disk were checked individually against
  their `optional`, `devOptional`, `os` and `cpu` fields. **All 76 are
  platform-gated or optional** (`@esbuild/linux-*`, `@img/sharp-libvips-*`,
  `@next/swc-win32-*`). **Zero non-gated packages were missing.**
- The Prisma client was present and current; `prisma migrate status` reported
  schema up to date; the security suite passed 148/148 against that tree.

**`npm ci` would have deleted `node_modules`, rebuilt it, wiped
`node_modules/.prisma/client`, and returned a tree identical to the one
already present.** The correct instrument for a staleness question is a
structural lockfile-to-installed-tree comparison, not a directory mtime.

The `prisma generate` step was kept in this ticket's sequence regardless, and
should stay in any future one. `npm install` is incremental and does not
delete the generated client — verified directly here, it survived — but
"should survive" is not a good enough guarantee for a failure mode that has
already cost an hour.

## Finding 4 — reachability, for the 42 advisories cleared or carried

Recorded because count alone hides it, and because [[GTC-244]] left two of
these as open Unknowns.

**Of 42 advisories on this branch before the fix, a plausible path to the
vulnerable code exists for roughly nine, and every one of those is a
denial-of-service or cache-correctness issue on an authenticated-only surface.
Zero confirmed paths to data disclosure, privilege escalation, or code
execution.**

- **GHSA-p293-qw3h-jr36 (critical, Windows RCE) — not reachable.** Railway
  runs Linux containers. The loudest advisory in the set does not apply.
- **GHSA-2xp9-vwfh-vxw4 (critical, AVIF RCE in Image Optimization) — not
  reachable, but by configuration accident rather than design.**
  `next.config.js` declares no `images` block at all, so `/_next/image`
  refuses every external URL. All four `next/image` call sites render
  first-party SVGs from `public/brand/`; Next does not pass SVG through the
  optimizer without `dangerouslyAllowSVG`, which is unset. No upload path
  writes into `public/`. No route under `src/app/api/` returns
  attacker-controlled image bytes. **Nothing on this origin will serve an
  AVIF to the optimizer.** That is not a designed control and should not be
  relied on as one.
- **`sharp` (high, libvips/libheif) — not exercised.** Nothing in `src/`,
  `scripts/` or `tests/` imports sharp; Next's image optimizer is its sole
  consumer, and per the above it never receives attacker-supplied bytes.
  **This answers GTC-244 Unknown 1.**
- **Middleware/proxy bypass advisories (4) — reachable, far smaller
  consequence than the class name implies. This answers GTC-244 Unknown 2.**
  The i18n one (GHSA-36qx-fr4f-26g5) is dead — no i18n config, no Pages
  Router, no `src/pages`. For the other three: **`middleware` in
  `middleware.ts` does not authorize anything.** It sets path-scoped isolation
  cookies for `/p/`, `/h/`, `/c/` and strips the `session` cookie from
  `/api/p/` and `/api/c/`. Authorization lives in the route handlers, via
  `resolveToken` in `src/lib/auth.ts` and `requireEventRole` in
  `src/lib/auth/guards.ts`. Skipping middleware therefore re-opens the GTC-001
  session-collision class; it does not grant entry. Blast radius checked:
  exactly one handler under those prefixes reads the session at all — the
  `GET` export in `src/app/api/p/[token]/route.ts`, which calls `getUser` (`src/lib/auth/session.ts`) only
  *after* `resolveToken` has already returned a valid `PARTICIPANT` scope, to
  offer host-preview. A bypass does not escalate there.
  **Verifying this required no edit to `middleware.ts` (Zone 1).**
- **Unreachable, feature not present:** three SSRF advisories (no WebSocket
  handling; zero `'use server'` directives anywhere in `src/`; no `rewrites`
  in `next.config.js`), three Server Action advisories (same), Cache
  Components DoS (no `cacheComponents`/`dynamicIO`/PPR), `beforeInteractive`
  XSS (no `next/script` usage), CSP-nonce XSS (no nonce usage).
- **`postcss` (vendored in Next) — build-time only.** Processes our own
  Tailwind output. `</style>` XSS and three sourceMappingURL traversal
  variants, none of which see untrusted input.
- **`nanoid` — sizes are never attacker-controlled.** Internal to Next.
- **`qs` — the only one in a genuine request path**, under both `stripe` and
  `twilio`. Both SDKs use it to encode *outbound* bodies; neither parses
  inbound attacker query strings through it. Reachable in principle, not
  exercised in the direction the advisories require.
- **Dev-only (5 packages):** `browserslist`, `js-yaml`, `@humanfs/node`,
  `baseline-browser-mapping`, `postcss-selector-parser`. ESLint and
  browserslist toolchain; none sees user input.

## Finding 6 — method: read the logs, do not count the failures

**This is the transferable part of this ticket. It is method, not result.**

When the 57-script suite was re-run after the change, the headline was
reassuring: same 54 pass, same 3 fail, all 57 exit codes identical. That was
the point at which it would have been natural to stop.

**Six of the passing suites' logs differed textually.** They were diffed rather
than assumed. The differences turned out to be freshly generated fixture cuids
in five of them, and in the sixth — `test:wrap-up-quiet-hours` — a wall-clock
countdown that moved from *"~491 min until send window"* to *"~487 min"*,
which is four minutes of real time elapsed between the two runs and nothing
else. After normalising cuids and timings, **0 of 57 suites differ.**

**"0 of 57 differ after normalising cuids and timings" is a materially stronger
claim than "the same three failed."** The second says the pass/fail boundary
did not move. The first says no assertion text, no test count, and no observable
behaviour moved anywhere in the suite. Only the second claim is available from
the exit-code table; the first requires reading the logs.

**A dependency change is exactly the case where an identical pass count can
hide a changed behaviour.** Nothing in this repo's own code changed — so every
assertion that passed before was always going to pass again unless the
framework underneath it behaved differently. A suite that silently started
exercising a different code path, or stopped exercising one, would keep its
exit code and change its output. The exit-code table cannot see that. The diff
can.

The same reasoning is why `npm run lint` was compared byte-for-byte rather than
by error count — 56/43 matching is weak evidence; byte-identical output is
strong evidence. [[GTC-243]] reached the same conclusion by a different route
when it A/B-tested the lint output against reverted lockfile versions and
found it byte-identical.

**Carry this forward:** for any dependency change, baseline the full suite
*before* touching anything, diff the logs afterwards rather than the counts,
and normalise only what is provably non-deterministic — generated IDs,
timestamps, durations — naming each normalisation. Anything left over after
that is a real difference and must be explained before the change ships.
