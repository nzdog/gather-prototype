### Context

Moment 4 spec §5/§8.2: criticality is decided at the menu, in Moment 2 (the lamb roast, the
birthday cake: critical; two bags of ice: not); the grid shows it as a badge, explicitly "no
float-to-top, no message-only."

Schema fully supports it: `Item.critical`, `criticalReason`, `criticalSource`
(`AI | HOST | RULE`), `criticalOverride` (`NONE | ADDED | REMOVED`). The legacy AI prompt path
(`buildGenerationPrompt`, `PLAN_GENERATION_SYSTEM_PROMPT`) sets it correctly, with the "3-5 items
max, never-critical list" rules documented in `gather-domain-reference`. But the **live** path
(`buildPlanGenerationPrompt` / `finalize-plan/route.ts`, GTC-145/146's single-call architecture)
has no `critical` field in its output schema at all — every AI-generated item defaults
`critical: false`.

Separately, `src/app/c/[token]/page.tsx` (coordinator view) sorts unassigned critical items to
the top of the list — directly contradicting §8.2's explicit ruling, even though the badge
rendering itself is correct in the god file and `h/[token]`.

### Scope

**Fix here:**
- Add `critical`/`criticalReason` to `buildPlanGenerationPrompt`'s output JSON schema and to
  `finalize-plan/route.ts`'s item-creation write.
- Port the "only 3-5 items per plan may be critical, maximum" + never-critical list rules
  (sauces, condiments, bread, drinks, setup, cleanup, side dishes, extra desserts) from the V1
  system prompt into the V2 prompt — check both paths stay consistent per `gather-ai-generation`.
- Remove the float-to-top sort in `src/app/c/[token]/page.tsx`; replace with the badge-only
  rendering pattern already correct in the god file / `h/[token]`.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The V1 prompt path itself (`generate`/`regenerate` routes) — separate concern, not in scope.
- `AI_CALL_LIMIT` values.

### Dependencies

None. Sequenced before J1/J2 (the Moment 4 screen renders this data).

### Acceptance

- [x] `finalize-plan` output includes `critical`/`criticalReason` for AI-generated items,
      following the same 3-5-max + never-critical-list discipline as the V1 prompt.
- [x] `c/[token]/page.tsx` no longer sorts critical items to the top; badge rendering matches the
      god file / `h/[token]` pattern.
- [x] `npx tsc --noEmit` clean, build passes.
- [x] Browser walk: generate a plan via Moment 2, confirm critical items are flagged and the
      coordinator view shows a badge without reordering.

### Stop Conditions

Standard eight from `BUG-TICKET-TEMPLATE.md`.

# GTC-170 — B1: Wire criticality into finalize-plan — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** 4ce7e90 | **Effort:** high

## What was built

**1. Criticality wired through the live single-call path** (`src/lib/ai/prompts.ts`,
`src/app/api/events/[id]/finalize-plan/route.ts`):

- `buildPlanGenerationPrompt`'s system prompt gained a `CRITICALITY` block porting the V1
  prompt's rules verbatim: 3-5 items max across the whole plan, "the event genuinely fails
  without this item," the never-critical list (sauces, condiments, bread, drinks, setup,
  cleanup, side dishes, extra desserts), and "when in doubt, NOT critical." The output JSON
  shape gained `critical`/`criticalReason` fields on each item.
- `finalize-plan/route.ts`'s `SectionResponse` item type gained `critical?`/`criticalReason?`.
  The category-mapping step carries them through with a defensive backfill matching the legacy
  path's behavior (`generate.ts`): a `critical: true` item with no reason gets a default reason
  rather than losing it silently.
- The `Item.create` write now passes `critical`/`criticalReason` — same two fields the legacy
  path writes, no extra fields invented, so downstream consumers (F1/J1) see one consistent
  shape regardless of which generation path produced the item.

**2. Coordinator-view float-to-top removed — at both layers it existed:**

- `src/app/c/[token]/page.tsx`: the custom sort (critical-unassigned → other-unassigned →
  assigned) deleted; `sortedItems` is now just `data.items` in natural order. The two badge
  conditions (`AlertCircle` icon + `CRITICAL` label) had their `!item.assignment &&` gate
  dropped so the badge is unconditional on `item.critical`, matching the god file
  (`src/app/plan/[eventId]/page.tsx`) pattern where the badge persists regardless of assignment
  state (consistent with spec §8.6: "the badge is already on the box").
- `src/app/api/c/[token]/route.ts`: **found during verification, not in the original ticket
  text** — the API itself was pre-sorting `orderBy: [{ critical: 'desc' }, { name: 'asc' }]`
  before the page ever saw the data. Removing only the page's client-side sort would have left
  the float-to-top behavior fully intact, just moved server-side. Changed to
  `orderBy: [{ displayOrder: 'asc' }, { createdAt: 'asc' }]`, matching the natural-order
  convention already used by `src/app/api/events/[id]/teams/[teamId]/items/route.ts` and
  `src/app/api/events/[id]/items/route.ts`.

**Found but explicitly not fixed (out of this ticket's scope):** the identical
`orderBy: [{ critical: 'desc' }, ...]` pattern also exists in
`src/app/api/h/[token]/team/[teamId]/route.ts`, and its page
`src/app/h/[token]/team/[teamId]/page.tsx` has its own client-side critical-first sort — the
same bug class GTC-170 fixed for the coordinator view, contradicting the discovery report's
claim that badge rendering (and implicitly ordering) was "already correct" in `h/[token]`. Not
touched here: the ticket's "Fix here" list named only `c/[token]/page.tsx`, and expanding into
a second page/route pair without a ruling would be scope creep on a `type: build` ticket with
no schema or auth implications forcing an in-band fix. Flagged as a follow-up task instead
(spawned during this session) rather than fixed silently or left unrecorded.
