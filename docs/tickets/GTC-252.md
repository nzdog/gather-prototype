# GTC-252 — Proxy-nudge path has no frequency limiting

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** low (this filing only —
the eventual fix's effort is undetermined; no fix is proposed by this ticket)

**Severity:** [ ] Critical  [x] High  [ ] Medium  [ ] Low
**Escalated (brand/trust risk):** [x] Yes

Filed 2026-08-23 per founder ruling 3 on [[GTC-178]]: the proxy-nudge path stays out of GTC-178's
cadence rework, and its known-broken frequency limiting gets its own ticket. **This ticket
documents the problem and its risk only. It does not propose a fix**, per explicit instruction —
do not begin implementation from this filing alone.

A prior investigation pass over this same gap exists in the `gather-frontier-and-roadmap` skill
("Top nearest work items," item A, "Proxy-nudge frequency limiting"). That note is background
context recorded before this ticket existed — it is not this ticket's ruled scope.

---

### Signal

**Expected**
A household nudged via the proxy/household path is re-nudged only after some bounded frequency
limit — the way direct 24h/48h nudges already are, gated on `Person.nudge24hSentAt`/
`nudge48hSentAt` in `nudge-eligibility.ts`.

**Actual**
`findProxyNudgeCandidates()` in `src/lib/sms/proxy-nudge-eligibility.ts` has no time-based gate
and no frequency check of any kind. Its own doc-comment states this outright: "The Moment 1
redesign removed HouseholdMember-level nudge tracking (proxyNudgeCount, lastProxyNudgeAt,
claimedAt, escalatedAt)... nudge scheduling logic needs redesign in a future ticket."
`src/lib/sms/proxy-nudge-sender.ts` repeats it: "Nudge frequency limiting needs redesign in a
future ticket." Every household with a resolvable, messageable, SMS-opted-in primary contact on
a `SENT_AND_LIVE` event is eligible again on every single cron tick.

**Smallest failing case**
With SMS credentials configured in production: one household with an unresolved item and a
valid NZ-mobile, SMS-reachable, non-opted-out primary contact receives a proxy-nudge SMS every
15 minutes, indefinitely, for as long as the event remains live — with no change in the
household's state between sends.

---

### Reproduce

**Required state**
- `SENT_AND_LIVE` event (per `src/lib/lifecycle.ts`'s predicate — `sentAt` not null, `endDate` in
  the future).
- A household with at least one unresolved/unclaimed item.
- A primary contact resolvable via `resolveHouseholdChannel()` (`src/lib/households/channel.ts`),
  with a valid NZ mobile number, `contactMethod: SMS`, not present in `SmsOptOut`.

**Steps**
1. Seed the state above.
2. Run `runNudgeScheduler()` (or wait for two consecutive 15-minute cron ticks) without changing
   the household's state.
3. Observe `sendProxyNudge()` firing on both runs.

**Observe:** identical proxy-nudge SMS sent to the same household's primary contact on
consecutive runs, with no elapsed-time or count gate preventing it.

**Data setup**
No ticket-specific seed script exists yet. `tests/nudge-provider-gate-test.ts` and
`tests/child-message-exclusion-test.ts` both already exercise `findProxyNudgeCandidates()` and
would be reasonable starting points for a fixture, if and when a fix is scoped.

### Risk (stated plainly)

This has not fired in production only because production currently has no SMS credentials
configured — `isSmsEnabled()`/TNZ config both resolve false, so `send-sms.ts` returns
`blocked: 'SMS_DISABLED'` before any message is actually dispatched. **Restoring SMS
credentials — for any reason, including a fix to something unrelated, or a demo — makes this
live immediately, with zero code change required to trigger it.** The tracking fields that
previously prevented this (`HouseholdMember.proxyNudgeCount`, `lastProxyNudgeAt`, `claimedAt`,
`escalatedAt`) were deleted with no replacement in commit `7606201` ("feat(GTC-101): add
Household model and HouseholdRole enum for Moment 1 redesign") — confirmed via
`git log -S "proxyNudgeCount"`, not inferred from comments. Repeated, unbounded automated SMS to
the same number is TCPA/spam-class legal exposure that exists independently of opt-out
correctness — a recipient who has not opted out can still be sent the same message every 15
minutes forever, which is its own compliance problem opt-out enforcement does not cover.
