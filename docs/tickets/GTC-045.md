### What was found

**Bypass condition (lines 27-40 of `src/app/api/h/[token]/route.ts`):**

```ts
let authStatus: 'unclaimed' | 'requires_signin' | 'authenticated' = 'authenticated';

if (process.env.NODE_ENV !== 'development') {
  const needsClaim = !resolvedContext.person.userId;
  if (needsClaim) {
    authStatus = 'unclaimed';
  } else if (resolvedContext.person.userId) {
    const sessionUser = await getUser();
    if (!sessionUser || sessionUser.id !== resolvedContext.person.userId) {
      authStatus = 'requires_signin';
    }
  }
}
```

The bypass condition is `process.env.NODE_ENV !== 'development'`. The auth status
check runs for **all** values except the literal string `'development'`. This
includes `'production'`, `'test'`, `undefined`, and any other value.

**This is NOT an access control bypass.** The actual access gate at lines 19-23
(`resolveToken` + HOST scope check) runs regardless of NODE_ENV. Without a valid
HOST-scoped AccessToken, the request is rejected with 403. The "bypass" only
affects the `authStatus` field in the response — controlling the UI prompt to
link a user account, not data access.

**NODE_ENV in Railway:** Railway uses Nixpacks for Node.js deployments, which
sets `NODE_ENV=production` by default at both build and runtime. No Dockerfile,
`railway.json`, or `nixpacks.toml` exists in the repo to override this. The
bypass cannot be triggered in the deployed environment.

### What was changed

No changes required. The bypass is correctly gated.
