# GTC-343 — the dispatcher-direct suites, and the exceptions list

**Status:** Open — a stub, filed 2026-09-30 at [[GTC-339]] on founder instruction (the plan's
review, point 2). Not scoped. **Not a deploy precondition unless the founder rules it one.**

---

### Signal

`GATHER-BUILD-CONSTANTS.md` keeps a list of the approved exceptions to "no cron against
`gather_dev`". Since [[GTC-339]] it names the three drives of a cron **route**: test:security's live
layer, `tests/nudge-provider-gate-test.ts` layer D, and `test:cron-health`. Each one either has
preconditions that stop it on any non-zero count outside its own fixture, or restores what it
wrote, or both.

Several suites reach the same machinery without going through a route. They call a dispatcher
directly, against `gather_dev`:

- `drainOnce` in `src/lib/press/dispatch.ts`: `tests/chase-test.ts`, `tests/hand-back-test.ts`,
  `tests/email-block-test.ts`, `tests/email-opt-out-test.ts`, `tests/texts-test.ts` and
  `tests/outbound-drain-test.ts`;
- `dispatchPendingWrapUpMessages` in `src/lib/wrap-up.ts`: `tests/email-opt-out-test.ts`,
  `tests/email-block-test.ts` and `tests/wrap-up-quiet-hours-test.ts`.

Neither dispatcher takes a scope. Each takes **every** pending row in the database, not only the
calling suite's own. So a pending row on a real `gather_dev` board, whether a queued reminder, an
unsent ask or an undispatched thank-you, is claimed and ended by whichever of these suites runs
next. With the live switch off it is withheld or rejected rather than sent, and it cannot be taken
back.

### The check to make, suite by suite

For each suite named above, does it do one of these?

1. **Scope** its dispatcher call to its own fixture.
2. Or **guard** the call with preconditions like [[GTC-339]]'s layer P, so that every count the
   dispatcher would touch outside the fixture is zero, or the suite stops before it drives anything.
   It must then assert restoration by count and by id afterwards.

Only a suite that passes is named in the constants file's exceptions list. Until then that list
names the three cron-route drives only, which was the founder's instruction at GTC-339.

### Unknowns

1. Whether any of these suites already guards its call in a way equivalent to layer P. The
   `outbound-drain` suite, for one, records the rows present before it runs and deletes any others
   it finds afterwards. That is a cleanup of rows it created elsewhere, not a precondition, and it
   deletes rather than asserting.
2. Whether a scope parameter on either dispatcher is the better fix than per-suite guards. It
   would be a change to production code for the sake of tests, which is the founder's to rule.
