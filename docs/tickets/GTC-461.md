## What and why

Facebook could not build a link preview for https://www.gatheringtogether.co.nz. Its Sharing
Debugger reported "Response Code 403" and suggested a robots.txt block. The page loads normally
in a browser.

What was found on 14 Nov 2026 (read-only, before any change):

- **The app answers Facebook with 200.** Railway's HTTP log for the production service shows
  Facebook's own crawler (`facebookexternalhit/1.1`, Meta addresses 173.252.x.x and 69.171.x.x)
  fetching `/` on www and getting 200 at 15:27:46, 15:27:47 and 15:40:27. The 15:40 fetch was for
  a new address (`/?probe=1114`) that the Debugger then still reported as 403.
- **Nothing in the repo or on Railway blocks crawlers.** `middleware.ts` matches only `/p/`,
  `/h/`, `/c/`, `/api/p/` and `/api/c/` and reads no user agent. Nothing in `src` filters by user
  agent. GTC-268's gate is a static scan of API handlers run as a test, not a request filter.
  There was no robots.txt (a 404, which means "allowed"). Railway's Under Attack Mode is off, CDN
  caching is off, and its log has no blocked Facebook request.
- **The bare domain blocks Facebook.** `gatheringtogether.co.nz` (no www) is not on Railway. It
  is on Voyager Internet's shared LiteSpeed hosting (49.50.249.25, name servers
  ns1-ns4.whsl206.com) and only redirects to www. From the founder's computer it answers 302 to
  www, even when the request carries Facebook's user agent. The Debugger, asked for
  `https://gatheringtogether.co.nz/?probe=1115` at 15:41, got 403 and no redirect. So Voyager
  refuses Facebook's addresses.
- **Why www also shows 403 (inference, not proven).** The staging site, the same app on a
  Railway address, previews correctly; there Facebook fetched `/robots.txt` before the page. On
  www, Facebook has not fetched `/robots.txt` from Railway once in the log (which runs from 8 Nov,
  the current deployment), yet it reports 403 and blames robots.txt. The likely reading is that
  Facebook takes its robots.txt answer for www from the bare domain, where Voyager blocks it, or
  from an older saved answer. The founder will test this by running Scrape Again on www after
  this deploys and before Voyager changes anything.

A plain curl with the crawler user agents (Facebook, LinkedIn, X, WhatsApp, Slack) gets 200 on
www, so curl cannot show the fault. The Sharing Debugger is the test.

  `sharePreview(url?)`, which returns the `openGraph` and `twitter` metadata.
- `src/app/layout.tsx`: `metadataBase` is `https://www.gatheringtogether.co.nz` and every page
  gets `sharePreview()`: og:title, og:description, og:image (with width, height and alt),
  og:type `website`, og:site_name `Gather`, and the X card (`summary_large_image`, title,
  description, image). The `<title>` and meta description are unchanged.
- `src/app/page.tsx`: the front page adds og:url `https://www.gatheringtogether.co.nz`.

**og:url on the front page only, not site-wide.** The brief asked for og:url site-wide. A layout
cannot know the page's own address, so a site-wide og:url would name the front page on every
page. Facebook treats og:url as the page's true address, so a shared invite link (`/p/...`,
`/h/...`, `/c/...`) would preview, and open, as the front page. With no og:url a crawler uses the
address it fetched, which is right for every other page.

Not changed: `middleware.ts`, any route, any API handler, auth, `route-classifications.json`, the
security suites. No page or API route is opened to anyone.

- `tests/tweaks-a-test.tsx`: `GTC461_HOME_PAIRS`, this ticket's two insertions into
  `src/app/page.tsx` typed by hand (the two imports around `getUser`'s, and the comment and
  `metadata` line before `LandingPage`), applied after Ticket A's `HOME_PAIRS` in C2, whose label
  now names them. C2 still asks for the whole file byte for byte.
