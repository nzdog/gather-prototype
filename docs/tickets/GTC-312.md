### Signal

**Expected**
One column holds a person's phone number, every writer writes it, and every reader reads it. If a
host can see a number on the screen, Gather can text it.

**Actual — three legs, and the third is the one that makes it a trust problem.**

**1. CODE — one of three capture paths writes the wrong column, unnormalised.**

- `POST` in `src/app/api/events/[id]/people/batch-import/route.ts` creates a `Person` with
  `phone: personData.phone || null` and **never sets `phoneNumber`**.
- The other two paths are correct. `createMember` inside `POST` in
  `src/app/api/events/[id]/households/route.ts` and `POST` in
  `src/app/api/events/[id]/people/route.ts` both write `phoneNumber` through
  `normalizePhoneNumber` in `src/lib/phone.ts`.
- **Every sender reads `phoneNumber`.** `findNudgeCandidates` in
  `src/lib/sms/nudge-eligibility.ts`, `findDecideByFollowupCandidates` in
  `src/lib/sms/decide-by-eligibility.ts`, `chooseManualNudgeChannel` in
  `src/lib/sms/manual-nudge-recipient.ts`, and `ChooserPerson` in
  `src/lib/eligibility/channel-chooser.ts`, whose own field comment says
  *"`Person.phoneNumber`, which every sender reads — never the legacy `Person.phone`."*
- **And batch-import does not normalise**, so even if the column were read, a real CSV carrying
  `021 123 4567` would fail `isValidNZNumber`. The path is host-reachable: `PeopleSection` in
  `src/components/plan/PeopleSection.tsx` posts to it.

**2. DATA — 35 rows, and the two columns are disjoint.**

Measured read-only on 2026-09-15 across all 333 `Person` rows:

- 12 rows have `phoneNumber` set; 9 of those are usable NZ numbers.
- **35 rows have `phone` set with `phoneNumber` NULL.** Every one of the 35 is already in valid
  `+64` form, so every one would be textable if the column were read.
- **No row in the database has both columns set.** They are disjoint populations, which is what a
  write path that chooses one and never the other produces.
- All 35 also carry an email.

**3. DISPLAY — she is shown the unusable number.**

- `GET` in `src/app/api/events/[id]/people/route.ts` serialises `person.phone`, and so does `PATCH`
  in `src/app/api/events/[id]/people/[personId]/route.ts`.
- `CopyPlanAsText` in `src/components/plan/CopyPlanAsText.tsx` and the host view at
  `src/app/h/[token]/page.tsx` both read `p.phone || p.email` for a contact line.

So the number is on her screen, in her printable plan, and in her host view — for a person Gather
will never text.

**Smallest failing case**
Import a CSV with a name, an email and a valid NZ mobile. The person's number appears in the people
list. Query their `Person` row: `phoneNumber` is NULL. No nudge will ever reach that number.

---

### ⚠ Why this is worse under [[GTC-189]] ruling AH than it was before

Ruling AH makes the event-level default *"chase by email when there's no mobile"*, ON. A
batch-imported person **has** a mobile and reads to the product as having none, so he is silently
routed into the email chase — correctly reached, on the wrong channel, with the right channel
sitting in the database unread. Under ruling AI the same person, if he has also opted out of texts,
is refused the exception on the strength of an opt-out against a number nothing was ever going to
use.

**And it corrupts the column ruling C measured.** `createMember` and `POST /people` both set
`contactMethod` / `reachabilityTier` from `person.phoneNumber || person.phone`, so a batch-imported
person is marked `SMS` / `DIRECT` on the strength of a column no sender reads. That is ruling C's
own sentence — *"Such a row says `SMS` and can never be texted"* — now countable at 35.

**Root cause confirmed**

One capture path of **six** wrote `Person.phone`; the other five already wrote `Person.phoneNumber`
through `normalizePhoneNumber` — `POST /people`, `households`, `reconcileMembers` (three sites),
`p/[token]/contact-info`, and `sms/inbound`. ⚠ **The ticket's *"one of three capture paths"* is a
correct diagnosis with a low count.** The write fix is one line.

The 35 rows were reproduced independently before any change: 333 `Person` rows, **12** with
`phoneNumber`, **35** with `phone` alone, **disjoint** — no row with both, which is the signature of
a writer that picks one column and never the other. All 35 already valid `+64`, all 35 also
carrying an email.

⚠ **The normalisation gap is real but is NOT what produced the 35.** `ImportCSVModal` normalises
client-side with the canonical `normalizePhoneNumber` and rejects invalid numbers before posting,
which is exactly why every stored legacy value is well-formed. The route is a guarded API rather
than that modal's private door, so it now normalises too — but the defect that stranded the 35 was
the column, not the format.

**⚠ FINDING 1 — THE FILED SITE LIST AND A MANUAL GREP BOTH MISSED THREE SITES. THE STRUCTURAL WALK
FOUND ALL THREE.**

Layer W of the test walks every `.ts`/`.tsx` under `src/app/api` and `src/lib` rather than checking
a list. It found three legacy reads that neither this ticket's Signal section nor the executor's own
enumeration had:

1. `POST` in `src/app/api/events/[id]/people/route.ts` — `person.phoneNumber || person.phone`
2. `POST` in `src/app/api/events/[id]/households/route.ts` — the same expression
3. `generateWrapUpLinks` in `src/lib/wrap-up.ts` — `person.phoneNumber || person.phone || null`,
   and this one is a **channel choice, not a display**: a thank-you could be routed `'sms'` on the
   strength of a column `sendSms` never sees.

⚠ **Why the manual grep missed number 3 is the part worth keeping.** The grep was piped through
`grep -v phoneNumber` to remove noise — which discarded the one line where **both** columns appear
together, and that is precisely the line where a legacy read hides. A filter that removes the noise
can remove the evidence, and it reports a clean result while doing it. The same shape as
[[GTC-273]] and [[GTC-276]]: the check was wrong in a way that read as an all-clear. `tsc --noEmit`
then caught a fourth — `generateWrapUpLinks` reading a field the type no longer had — which is the
only one no grep would have needed to find.

**⚠ FINDING 2 — THE ASK SPLIT DID NOT MOVE, AND [[GTC-189]]'S SECOND SLICE-5 FINDING IS CORRECTED
BECAUSE OF IT.**
