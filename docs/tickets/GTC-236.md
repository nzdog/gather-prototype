# GTC-236 — Real V2 regenerate — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commits:** backfilled below

## What this became, and why it shrank

The ticket as filed prescribed new `source`/`edited` fields, a schema migration, and a
one-time "seed provenance" flow. **All three were disproven by the Phase 1 audit and dropped
by founder ruling:** `Item.source` (`ItemSource` enum `GENERATED|TEMPLATE|MANUAL|HOST_EDITED`,
non-nullable, `@default(MANUAL)`) has existed since the init migration; `PATCH` on both item
edit routes already flips `GENERATED → HOST_EDITED` on substantive edits; every item in the
dev DB carried provenance. A seed flow had no trigger condition — `source: null` is
structurally impossible. Building as filed would have stood up a second provenance system in
parallel with a live one.

Also corrected during execution, so they are not re-derived: "Moment2Section" (named in one
founder instruction) **does not exist in the tree**; the selective-regeneration branch's real
consumers are the V1 dashboard review flow and `/demo/review` ([[GTC-239]] records this);
and V1's `/regenerate` route is NOT gone — it exists at HEAD and V1's dashboard still calls
it, which is why the new endpoint is a sibling, not a replacement.

## Rulings ledger (founder-decided)

Drop seed flow + migration. Endpoint `POST /api/events/[id]/regenerate-plan`. AI cap **10**
(finalize-plan's value; V1 regenerate still uses 20 — recorded discrepancy). Edit = content
change; `notes` counts — implemented by [[GTC-238]], not here. Marks (Mark for delete) are
client staging: regenerate clears them, never deletes marked items. Both trigger levels.
No confirmation dialog on either trigger (Q2b: an explicit click is the decision; the
unconditional checkpoint is the safety net). Empty-scope refinement (2026-08-22): triggers
stay enabled always — a scope with zero regeneratable items short-circuits server-side
BEFORE the checkpoint and AI call (zero cost, zero writes) and the client explains via
toast. Founder copy said "Unmark items to replace them"; shipped copy is provenance-true
("…every item in this category was added or edited by you") because marks are delete
staging, not keep-marks — unmarking changes nothing about what regenerates. Toasts "Plan regenerated" / "<Category>
regenerated". AI decides replacement item counts (D2) — no count matching. Single call for
plan scope (D3, per GTC-146). Script-seeded fixtures for verification (event creation is
Stripe-gated, GTC-233). Trigger placements and no-confirm approved via question UI.

## What was built

**`buildPlanGenerationInput` in `src/lib/ai/plan-input.ts`** — move-only extraction of
finalize-plan's EventSetup→prompt assembly (dietary three-state read, household headcount,
engaged-categories resolution, task buckets), so generation and regeneration share one input
path. `src/lib/ai/plan-categories.ts` holds the key↔label↔emoji maps as pure data — client
components import it without dragging prisma into the bundle; `plan-input.ts` re-exports.
finalize-plan's route shrank 441 → 236 lines, behaviour identical (verified by a live
generation through it).

**`preservableItems` on `PlanGenerationInput`** in `src/lib/ai/prompts.ts` — optional, so
all existing callers are untouched; absent means the prompt is byte-identical to before.
Renders an "ITEMS ALREADY IN THE PLAN" block: do not output, do not duplicate, count toward
coverage, generate as many or as few new items as fits (D2).

**`POST` in `src/app/api/events/[id]/regenerate-plan/route.ts`** — scope `plan | category`
(`categoryKey` from the canonical key list). Order of operations, each a deliberate
non-copy of a V1 defect: resolve actor via `ledgerActorForUser` (AuditEntry.actorId FKs
Person, not User); **unconditional** `createRevision` checkpoint, abort on failure;
**AI call before any deletion** (V1 clears first — an AI failure there destroys the plan);
then ONE `$transaction`: delete `kind:'ITEM' AND source:'GENERATED' AND isProtected:false`
in scope → map response sections into existing teams by canonical label (create GENERATED
teams only if missing, displayOrder appended after survivors) → sweep empty GENERATED teams
per-team (never an unscoped deleteMany; the cascade would take TASK rows) →
`aiCallsUsed increment` → `recordChange(tx, …, 'REGENERATE_PLAN')` last (the
`restoreFromRevision` worked example). Preservables include `TEMPLATE` in the prompt
context — a deliberate improvement over V1, which spares TEMPLATE items from deletion but
never tells the model they exist. TASK rows are never touched; task-note inputs are zeroed
so the model produces no tasks. No mock fallback (finalize-plan precedent: fail loud, zero
writes). Route-classifications entry added (SESSION, HOST|COHOST).

**UI in `Moment2PlanView` + `EventSetupPage`** — plan-level trigger ("Not quite right?
Regenerate the plan") under the summary header; "↻ Regenerate this category" beside
"+ Add item", rendered only where the team name reverse-maps to a canonical key (custom
categories and task buckets get none — verified live on a custom "Party Games" category);
in-place loading (affected sections pulse, all triggers + footer disabled); marks cleared on
regenerate start (Q2); success/429 toasts; both loaders re-fetched on completion (`items`
backs the GTC-202 assignmentResponse lookup).

**Fixture**: `scripts/seed-gtc236-test-event.ts` — fresh host-owned V2 event with a real
EventSetup (copied from the GTC-133 donor) and two households; `--ai-calls N` flag for the
cap scenario.

## One bug found and fixed during verification

First live invocation 500'd: `AuditEntry_actorId_fkey` — the route passed `auth.user.id`
(User) to `createRevision`, whose audit line FKs **Person**. Fixed by resolving the actor
first (`ledgerActorForUser`) and passing `actor.id` to both the checkpoint and the ledger.
The two failed attempts billed nothing and wrote nothing (failure precedes the AI call,
the deletion, and the increment — the ordering doing exactly what it was designed to do).

## Known limitations

- Category resolution rides on `Team.name === CATEGORY_LABELS[key]`; a renamed category team
  silently loses its per-category trigger (server 404s cleanly).
- The cap check-then-act race is retained (house pattern); the increment is atomic with the
  writes, which V1's is not.
- Notes edits still don't persist or protect — [[GTC-238]], severity high, separate track.
- finalize-plan's own rerun path still cascade-destroys host work on generated teams —
  [[GTC-237]]. This endpoint is the safe alternative; the unsafe path remains reachable via
  Back → Step 1 → Generate.
- Test-fixture residue in dev DB: the GTC-236 fixture event (aiCallsUsed restored to its
  true count of 3) plus an empty custom "Party Games" category on it.
