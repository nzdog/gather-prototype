## Scope (Cowork's findings, checked in the repo at `7837309`)

### What happens

An event is COMPLETE ("PAST" on the stage bar) when `now > endDate`
(`src/lib/lifecycle.ts`, `isComplete`, strict). The forms send the date as a
bare day, "2026-12-25", and the routes store it with `new Date("2026-12-25")`,
which is midnight UTC (`src/app/api/events/route.ts` L163-164;
`src/app/api/events/[id]/route.ts` L137-138; `src/app/api/templates/[id]/clone/
route.ts` L120-121). Midnight UTC on the 25th is 1pm NZ on the 25th in summer
(NZDT, +13) and noon in winter (NZST, +12).

Since GTC-385 a one-day event stores end = start, so a one-day event is over at
1pm on the day of the event. A Christmas lunch, a barbecue at 5pm, an evening
party: each reads PAST on its own afternoon, before or during the event. The
lifecycle header says "the calendar does it" and Moment 4 section 10.1 says the
date passing IS the change; neither says the change should come at lunch time.
Before GTC-385 the same was true of the last day of a multi-day event; GTC-385
made it the common case.

## The options (Cowork's view; the plan weighs them and recommends)

A. Change the rule, not the data (Cowork recommends). An event is over when the
   NZ calendar day that holds its `endDate` has ended. Nothing stored changes,
   no migration, no form change, nothing near Zone 4. In JS: compare `now` with
   the instant that NZ day ends. In SQL there is a clean equivalent that needs
   no per-row sum: the event is live while `endDate >= start of today's NZ day`
   and complete when `endDate < start of today's NZ day` (the NZ day of
   `endDate` is never earlier than today's exactly when `endDate` is at or after
   the instant today began). The two fragments keep their shape, take one
   computed instant instead of `now`, and the JS and SQL rules agree by
   construction. A form event (midnight UTC) then ends at midnight NZ the same
   night; an event seeded at 5:30pm NZ also ends at that NZ midnight.
   Traps to test: the two daylight-saving changeover days (the NZ day is 23 or
   25 hours; 27 Sep 2026 has just passed, April is next), the exact midnight
   instant (strict or not), and the browser clock being in another zone.

B. Change the data: store the end as the end of the day (for example 23:59 NZ)
   when only a day is given. Rejected by Cowork: it needs a data fix for events
   already stored, changes every form and clone path (the post-payment route
   reads the date back from Stripe metadata after the host has paid, Zone 4
   adjacent), moves "Answers by" and every decide-by by a day, and every future
   writer must remember to do it.

C. Leave the rule and only change the words ("Event past" at 1pm). Not a fix.

### The option: A, change the rule and not the data

A, for the reasons Cowork gives, and two more found here: it leaves the
decide-by clock and every "Answers by" date exactly where they are, and
it needs no change to any writer, the Stripe metadata path or the
clone. B would move every decide-by a day and needs a data fix; C fixes
nothing.

The rule, in words: an event is over once the NZ calendar day holding
its stored end has ended. In the code, one function works out ONE
instant, the moment today's NZ day began, and both rules compare the
stored end with it:

```
over (JS, isComplete):        endDate <  nzDayStart(now)
over (SQL, COMPLETE_WHERE):   endDate: { lt:  nzDayStart(now) }
not over (if ever needed):    endDate: { gte: nzDayStart(now) }
```

`endDate < start of today` is exactly "its NZ day is before today": an
instant before today's midnight lies in an earlier NZ day, and one at or
after it lies in today or later. So the event is over AT midnight
(00:00:00.000 belongs to the new day).

differ in names, not in shape):

const NZ_WALL_CLOCK = new Intl.DateTimeFormat('en-US', {
  timeZone: NZ_TIME_ZONE, hourCycle: 'h23',
  year: 'numeric', month: 'numeric', day: 'numeric',
  hour: 'numeric', minute: 'numeric', second: 'numeric',
});

// The NZ wall clock at an instant ("24" read as 0 for old browsers).
function nzWallClock(at: Date) { /* formatToParts -> numbers */ }

// How far NZ's clock is ahead of UTC at an instant (+12h or +13h).
function nzOffsetMs(at: Date): number { /* wall clock - instant */ }

/** The instant today's NZ calendar day began (00:00 in Auckland). */
export function nzDayStart(now: Date = new Date()): Date {
  const w = nzWallClock(now);
  const midnight = Date.UTC(w.year, w.month - 1, w.day);
  const guess = midnight - nzOffsetMs(now);
  // Re-read the offset AT that midnight: on a changeover day the
  // offset at noon is not the offset at midnight.
  return new Date(midnight - nzOffsetMs(new Date(guess)));
}

export function isComplete(event, now = new Date()): boolean {
  return event.endDate.getTime() < nzDayStart(now).getTime();
}

export const COMPLETE_WHERE = (now: Date = new Date()) => ({
  endDate: { lt: nzDayStart(now) },
});

### Daylight saving, and why the JS and SQL rules cannot disagree

The single computed instant is `nzDayStart(now)`, the moment today's NZ
day began, in `src/lib/lifecycle.ts`. It is worked out once, in
JavaScript (Node on the server, the browser on the old dashboard), with
an explicit Pacific/Auckland, and handed to Postgres as a plain value.
Postgres does no time-zone arithmetic for this rule. That matters:
`gather_dev`'s Postgres reports `TimeZone = Pacific/Auckland`, and
production's need not; a rule written with SQL's `now()` or `AT TIME
ZONE` would read differently on the two. Both sides compare the same
`timestamp(3)` column (milliseconds, UTC, as Prisma stores it) with the
same instant, using `<` for over and `>=` for not over. A row cannot
satisfy both or neither.

NZ changes its clocks at 2am (forward, last Sunday of September) and at
3am (back, first Sunday of April), never at midnight, so every NZ day
has exactly one midnight. The changeover days near us:
- Sun 27 Sep 2026, clocks forward: the day runs from 26 Sep 12:00 UTC
  (midnight NZST) to 27 Sep 11:00 UTC (midnight NZDT), 23 hours.
- Sun 5 Apr 2026, clocks back: 4 Apr 11:00 UTC to 5 Apr 12:00 UTC, 25
  hours.
- Sun 4 Apr 2027, clocks back: 3 Apr 11:00 UTC to 4 Apr 12:00 UTC, 25
  hours. The repeated half-hour (2:30am happens twice) falls in that
  day either way.

The trap the sketch avoids: on a changeover day the offset at the
moment asked about (+13 at 1pm on 27 Sep) is not the offset at that
day's midnight (+12). Reading the offset a second time, at the guessed
midnight, corrects it; one correction is enough because the change is
two or more hours from midnight.
