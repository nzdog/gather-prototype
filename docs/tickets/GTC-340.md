# GTC-340 — a stopped email reads red, and a stopped text reads amber

**Status:** Open — a stub, filed 2026-09-29 at [[GTC-274]] on founder instruction, from that
ticket's audit of the send paths. Not scoped. **Not a deploy precondition unless the founder rules
it one.**

---

### Signal

Two sends can stop inside Gather for the same reason, an operator's setting (no provider key, or
[[GTC-274]]'s live switch off), and the board reads them differently.

- **A text:** `sendSms` in `src/lib/sms/send-sms.ts` returns `SMS_DISABLED`. `drainOnce` in
  `src/lib/press/dispatch.ts` passes it to `blockedToWithheld` and records a withholding.
  `WITHHELD_MEANS_UNREACHABLE` in `src/lib/glance/delivery-fact.ts` maps `SMS_DISABLED` to
  `null`, so there is **no red**, and the strip stays amber. That is correct: an operator's failure
  is not a fact about the guest.
- **An email:** `getResendClient` in `src/lib/email.ts` throws on a missing key or, since GTC-274,
  on the switch being off. The sender's `catch` returns `success: false` with no provider code, and
  the dispatcher records a **rejection**. `deliveryFactFrom` reads any `rejectedAt` as
  `NOT_DELIVERED`, which is **red, "never got it"**, and that is a door the resend action offers.

`SendResult`'s own contract says an email failure with no provider code means *"the request never
left the process"*. The board does not read that distinction. So a machine or a production without
a key or the switch shows email guests as red for something the guest did not do.

### Known before GTC-274

This is not new. It is true today on any machine with no `RESEND_API_KEY`. GTC-274 makes it the
behaviour of every non-live machine, which is why it was named there and not fixed.

### Unknowns

1. Whether the fix belongs in the dispatcher (a stop with no code is recorded as a withholding,
   like SMS_DISABLED) or in the reading (`deliveryFactFrom` tells a rejection with no code apart).
2. Whether any existing email rejection with no code, on a real board, was really a provider
   refusal whose code was lost. The [[GTC-265]] and [[GTC-289]] history says no catch block sets a
   code, so no.
