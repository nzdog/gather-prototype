# GTC-218 — Cross-household channel self-heal is single-household-scoped

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** TBD
**Priority: higher than GTC-217** — this is a live correctness/data-integrity hole, not a
resilience gap.

*Spun out of GTC-173 (C2). Confirmed live in code during GTC-173 preflight — see below.*

### Context

The household contact picker (`Household.contactPersonEventId`, GTC-172 / C1, §10.7) is
deliberately **cross-household**: any household's channel can point at a `PersonEvent` belonging
to a *different* household (e.g. Grandma's channel lives in her own household record, not the
grandchild's). `reconcileHouseholdMembers` (`reconcileMembers.ts:320-339`) has a self-heal step
that clears a household's own `contactPersonEventId` if the member it points at has been re-roled
to CHILD — but it only loads and checks **the household currently being edited**:

```ts
const current = await prisma.household.findUnique({
  where: { id: household.id },   // <-- only the edited household
  select: { contactPersonEventId: true },
});
```

**Concretely:** household B's channel picker points at a member of household A. Household A is
edited and that member is re-roled to CHILD (either directly, or via the helper `adultRoled`
toggle flipping off). Household A's own self-heal check runs and finds nothing wrong (A's own
`contactPersonEventId`, if any, is unaffected). Household B is **never checked** — it keeps
pointing at a now-ineligible CHILD.

The eligibility layer fails closed on the read side (`findProxyNudgeCandidates` won't message a
CHILD), so no message is ever sent to the wrong person — but the failure mode is **silent
omission**: household B is quietly dropped from proxy nudges entirely, with no record that its
channel went stale, until someone happens to edit household B itself (which would trigger B's own
self-heal against its *own* `contactPersonEventId` — the same code path, just triggered from the
other side).

### Scope

**Fix here:**
- Extend the self-heal check in `reconcileMembers.ts` (or a caller of it) to also find and clear
  any **other** household's `contactPersonEventId` that points at a member of the household just
  edited, when that member has been re-roled to CHILD. This is application logic against the
  existing `contactPersonEventId` FK (`Household.contactPersonEventId -> PersonEvent.id`) — no
  schema change expected.
- Regression test proving the **cross-household** case specifically (household B's channel
  silently going stale when household A is edited) — the existing self-heal tests, if any, only
  cover the same-household case.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The diff-based upsert matching logic (GTC-159/201) for member reconcile itself — this ticket is
  scoped to the self-heal step, not the reconcile loop.
- `validateChannelTarget` / `resolveHouseholdChannel` in `channel.ts` — their read-time behaviour
  (resolve-then-validate, fail closed) is correct and is not what's broken here; the bug is that
  the write-time self-heal never reaches other households, not that reads are wrong.

### Dependencies

C1 (GTC-172) — introduces `contactPersonEventId` and the self-heal step this ticket extends.
