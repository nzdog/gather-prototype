### Persistence shape change

New shared module `src/lib/dietary.ts` — single source of truth:
- `DietaryStatus = 'unanswered' | 'confirmed_none' | 'confirmed_needs'`; `DietaryData { status, requirements, other? }`.
- `readDietaryData(raw)` — normalizes legacy statusless rows (empty → `unanswered`, populated → `confirmed_needs`) and coerces incoherent stored combinations safety-first (`confirmed_needs` with nothing → `unanswered`; `confirmed_none` with needs → `confirmed_needs`, stated needs win).
- `validateDietaryData(value)` — accepts legacy statusless writes; when status is present, enforces enum + coherence (`confirmed_none`/`unanswered` must carry nothing; `confirmed_needs` must carry something).

`setup/route.ts` imports both; its local two-value interface removed; the validator block now rejects invalid combinations with specific 400 messages.

### UI change

`Moment2Step1Modal.tsx`:
- Local `DietaryData` gains `status`; default `{ status: 'unanswered', requirements: [], other: '' }`; server read goes through `readDietaryData`.
- Accordion: new checkbox **"No dietary needs at this event"** at the top, visually set apart by a divider; ticking it → `confirmed_none` and disables/clears the requirement checkboxes and free-text; unticking → back to `unanswered`. Any requirement tick or other-text → `confirmed_needs`. Status is **derived from content**, never stored independently — invalid combinations are unrepresentable, and removing the last requirement returns to `unanswered` rather than silently becoming "none". Open/close still writes nothing.
- Header indicator while `unanswered`: amber dot + **"Needs confirmation"** beside "⚠️ Dietary requirements"; disappears on either confirmation.
- `AccordionShell`: `stillDeciding`/`onStillDecidingToggle` now optional; the "Still deciding?" affordance renders only when a handler is passed — dietary's dead button is gone. New optional `headerHint` slot. Other accordions unchanged.

### Prompt change (per state)

`prompts.ts` `buildPlanGenerationPrompt` — new required `dietaryStatus` input; the dietary block and the `dietaryCoverage` instruction both branch:
- `confirmed_needs`: `Dietary requirements present: <list>` (GTC-137 pattern unchanged) + per-requirement coverage instruction (unchanged).
- `confirmed_none`: "The host has confirmed there are no dietary requirements at this event. Generate items normally without dietary constraints." + coverage returns an empty array.
- `unanswered`: "The host has not yet confirmed dietary requirements. Do not assume there are none. Include at least one vegetarian option in the mains category as a reasonable default, and prefer naturally-suitable items (e.g. plain vegetable sides) that accommodate common dietary restrictions." + coverage returns exactly one entry `{ requirement: "Dietary requirements not yet confirmed", covered: false }` so the Step 2 coverage panel visibly flags the state.

The legacy `'Dietary requirements present: none'` string no longer exists on any path.
