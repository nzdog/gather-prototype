# GTC-434 - The households POST saves all or nothing

> Filed by Claude Code on 31 Oct 2026. Fourth of the five household
> save tickets (GTC-431 to GTC-435) on fix/household-save, after
> [[GTC-433]] (c8a6432).

## The founder's ruling (31 Oct 2026)

4. "Make 'Save & add another household' write adults and children in
   one transaction, as the other save paths do."
- With the plan: confirm first that nothing inside the new transaction
  sends a text or email or makes a network call; and read every day
  of production's HTTP log Railway keeps for failed household POSTs
  (counts and times only, logs only, no database).

## What happened before (and was proven by the red run)

POST /api/events/[id]/households wrote the Household, then each member
one by one, with no transaction, then the ledger entry in a
transaction of its own. A failure part-way:

- kept the household, its main contact, partner and the children
  before the failing one; the browser said "That didn't save — please
  try again.", and a reload showed the half-household;
- made a retry worse: the same people are found again (address and
  first name, GTC-293) and are already in the first household, so the
  retry made a second household holding only the children not saved
  the first time, with no main contact (uneditable: the PUT answers
  "Primary contact not found in household");
- and a refused contact pick answered 400 only after the household and
  its members existed, so that household was kept too.

## The change (src/app/api/events/[id]/households/route.ts only)

- The household create, every member (`createMember`, which now takes
  the transaction client and passes it to findOrCreateCapturedPerson),
  the contact-picker write and the ledger entry run in one
  `prisma.$transaction`, default timeout, as the PUT does.
- A refused pick throws ChannelValidationError inside it; the catch
  answers the same 400 with the same words, nothing written.
- Unchanged and still before any write: requireEventRole, the demo
  crowd shape, the name, email, kid-name and littleCount checks, the
  host-household-first 409. The reply is read after the transaction.
- Kept inline (no new file): demo-sandbox-b S7 and shared-address G pin
  the route's text.

Checked before building: everything inside the transaction is a
database call or plain code (capturePerson.ts, send-wall.ts'
isDemoEvent read, channel.ts, child-exclusion.ts, ledger.ts writing the
Event and AuditEntry rows, phone.ts). Nothing sends, enqueues or calls
out.

## What she sees now if a save fails part-way

The same as before on screen: "That didn't save — please try again."
beside the Save buttons, the form kept as typed. But the server keeps
nothing, a reload shows the list as it was, and a retry stores the
household once, whole.
