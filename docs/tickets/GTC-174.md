# GTC-174 — D1: Unify the guest response model — one-tap yes/no/maybe

**Status:** Open | **Branch:** TBD | **Commit:** [pending] (filed `e5f6e82`) | **Effort:** max, schema

*Effort level is a proposal from the discovery-report ticket breakdown — run `/effort` manually
before execution.*

### Context

Hinge spec §3 (ruled gap #10 — this is the discovery-gap ruling that materially changed the
original spec's simpler "yes/no/maybe, single tap" framing): **the tap is the item ask, and
attendance is inferred from it.** Yes-to-the-pavlova is yes-to-coming — nobody brings a dessert to
a party they're skipping. A **no** to the item is ambiguous ("can't bring that" vs "can't come"),
so the no path — and only the no path — gets one conditional follow-up in the same interaction:
"no worries — still coming?" Guests with no item assigned receive the attendance-only degenerate
case of the same message. A **maybe** stays purely an item-maybe; attendance is unknown until the
decide-by resolves it (D2, GTC-175). **This supersedes event-level RSVP as a guest-facing
question**: `PersonEvent.rsvpStatus` stops being something guests are asked directly and becomes
derived state.

Today: two independent guest-facing questions exist. `PersonEvent.rsvpStatus`
(`PENDING|YES|NO|NOT_SURE`, asked directly via `PATCH /api/p/[token]`) and `Assignment.response`
(`PENDING|ACCEPTED|DECLINED`, binary, no maybe) — documented as "two different yes/no axes" in
`gather-domain-reference`, which this ticket obsoletes.

### Scope

**Fix here:**
- Extend `Assignment.response` (or a successor field/model) to carry yes/no/maybe.
- Implement the conditional no-follow-up ("still coming?") as part of the same guest interaction.
- Implement the itemless-guest degenerate case (attendance-only message).
- Derive `rsvpStatus` from the item response + degenerate case rather than asking it directly;
  migrate `PATCH /api/p/[token]`'s current direct-RSVP-write behavior to the new derived model.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The decide-by clock itself (D2's territory — this ticket only needs to leave a `maybe` state for
  D2 to attach a clock to).
- Reassignment/release-notification machinery (D3's territory).
