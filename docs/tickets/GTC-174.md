# GTC-174 — D1: Unify the guest response model — one-tap yes/no/maybe

**Status:** Open | **Branch:** TBD | **Commit:** [pending] (filed `e5f6e82`) | **Effort:** max, schema

*Effort level is a proposal from the discovery-report ticket breakdown — run `/effort` manually
before execution.*

### Context

Hinge spec §3 (ruled gap #10 — this is the discovery-gap ruling that materially changed the
original spec's simpler "yes/no/maybe, single tap" framing): **the tap is the item ask, and
attendance is inferred from it.** Yes-to-the-pavlova is yes-to-coming — nobody brings a dessert to
a party they're skipping. A **no** to the item is ambiguous ("can't bring that" vs "can't come"),
so the no path — and only the no path — gets one conditional follow-up in the same interaction:
"no worries — still coming?" Guests with no item assigned receive the attendance-only degenerate
case of the same message. A **maybe** stays purely an item-maybe; attendance is unknown until the
decide-by resolves it (D2, GTC-175). **This supersedes event-level RSVP as a guest-facing
question**: `PersonEvent.rsvpStatus` stops being something guests are asked directly and becomes
derived state.

Today: two independent guest-facing questions exist. `PersonEvent.rsvpStatus`
(`PENDING|YES|NO|NOT_SURE`, asked directly via `PATCH /api/p/[token]`) and `Assignment.response`
(`PENDING|ACCEPTED|DECLINED`, binary, no maybe) — documented as "two different yes/no axes" in
`gather-domain-reference`, which this ticket obsoletes.

### Scope

**Fix here:**
- Extend `Assignment.response` (or a successor field/model) to carry yes/no/maybe.
- Implement the conditional no-follow-up ("still coming?") as part of the same guest interaction.
- Implement the itemless-guest degenerate case (attendance-only message).
- Derive `rsvpStatus` from the item response + degenerate case rather than asking it directly;
  migrate `PATCH /api/p/[token]`'s current direct-RSVP-write behavior to the new derived model.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The decide-by clock itself (D2's territory — this ticket only needs to leave a `maybe` state for
  D2 to attach a clock to).
- Reassignment/release-notification machinery (D3's territory).

### Dependencies

# GTC-174 — D1: Unify the guest response model — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** [pending] | **Effort:** max, schema

## Preflight rulings (taken in plan mode, 2026-08-05)

Three decisions were put to Nigel before any code was written, because each changed the
shape of the contract six downstream tickets build on.

**1. What happens to `rsvpStatus` — RULED: retire it as directly-writable; split stored
fact from derived state.** The framing that decided it: attendance cannot be derived all
the way down. The no-follow-up answer and the itemless answer carry information no item
response encodes, so *something* attendance-shaped must still be stored. The question was
only what. Keeping `rsvpStatus` as a server-recomputed field was rejected because a stored
answer to a derived question is the `Item.status` mistake again
(`gather-architecture-contract` §6): it drifts the moment a write path forgets to repair
it, and what it makes lie is the host's headcount. Repurposing the column under its old
name was rejected because the name would then assert the opposite of the ruling. So:
store only what was genuinely ASKED (`attendanceAnswer`), derive the rest.

**2. Guest-page scope — RULED: mechanism only.** GTC-191 (I4) is explicitly scoped to
rebuild this page's presentation around D1's model plus the post-yes reminder offer. D1
delivers the working model and deletes the superseded flow; it does not pre-empt I4's
screen.

**3. The NOT_SURE forced-conversion nudge — RULED: neutralise now, delete in E1.**
Left alone, a legacy `NOT_SURE` row would keep firing an SMS that contradicts the very
ruling this ticket implements (Hinge §8: a maybe gets no nudges).

## What was built

**`src/lib/attendance.ts`** — new, pure, DB-free, client-safe (its only Prisma import is
a type). Modelled directly on `src/lib/lifecycle.ts`, including the deliberate choice to
make `Attendance` a **TS union, not a Prisma enum** — exactly as `EventPhase` is. There is
no column to add, so no cache can form.

- `deriveAttendance(assignments, attendanceAnswer)` → `PENDING | YES | NO | UNKNOWN`, in
  precedence order: any ACCEPTED → YES (§3's axiom, absolute) → an explicit answer → a
  MAYBE leaves UNKNOWN (§8) → all-DECLINED-unanswered leaves UNKNOWN → else PENDING.
- `isAttendanceAskable(assignments)` — true only for an itemless guest or one who has
  declined everything. This is the server's guard, not a UI convention.
- `parseAssignmentResponse` / `parseAttendanceBody` — the route validators, so the routes
  cannot drift from the model they claim to implement.

`UNKNOWN` and `PENDING` are kept distinct deliberately: D2's clock and E1's cadence must
tell an engaged maybe apart from a silence, which is what Hinge §6 turns on.

**The write paths.** `PATCH /api/p/[token]` no longer takes a guest-supplied
`rsvpStatus`; it takes `{ attending: boolean }`, writes `attendanceAnswer` +
`attendanceAnsweredAt` in a transaction with a `logAudit` line, and **409s when
`isAttendanceAskable` is false**. That 409 is the load-bearing part: without it, "guests
are never asked attendance directly" would be a screen convention the next screen could
break. Both ack routes (`p/` and `c/`) accept MAYBE and return the derived attendance plus
`attendanceAskable`, so the client renders the conditional follow-up "in the same
interaction" (§3) with no second round-trip. `AuditLifecycleAction` gains
`MAYBE_ASSIGNMENT` and `ANSWER_ATTENDANCE`.

**"Exactly one conditional follow-up" needed no new field.** The beat shows while
`isAttendanceAskable && attendanceAnswer === null`. Answering ends it; abandoning and
returning re-presents the *same* unanswered question, not a second one.

**The readers**, all repointed at the derivation: `GET /api/p/[token]`,
`GET /api/h/[token]`, `invite-status` (whose duplicate `rsvp` count block was deleted
rather than kept in sync — two counts of one fact is how they come to disagree), and
`InviteStatusSection`. The wire key `notSure` became `unknown`: not tidying, but because
NOT_SURE meant "maybe I'm coming", which §8 abolishes.

**The union sweep.** Fifteen `'PENDING' | 'ACCEPTED' | 'DECLINED'` sites gained MAYBE with
amber-not-red rendering. The four remaining binary unions are the host manual-override
paths, left binary by design — a host never records a maybe on someone else's behalf.
Both text exporters gained a `~ MAYBE (still deciding)` section; without it, maybes fell
between the `confirmed`/`pending`/`declined` filters and vanished from the printed sheet
entirely. Their wording is deliberately not "needs reassignment" — §8 holds the item
softly, and reassigning is Kate's call (D3), not the sheet's advice.

**The guest page** (`src/app/p/[token]/page.tsx`) is items-first. The RSVP-gate that
asked "Are you coming?" before showing the items is deleted: it asked the guest for the
same decision twice.

**Three predicate rulings pinned in-code**, because each is a place a future reader would
reasonably "fix" the wrong way:

- `computeTeamStatusFromItems` — a MAYBE is **not** a gap (§8: held softly, it stays the
  guest's). The predicate already keyed on DECLINED, so this was correct by accident; it
  is now correct on purpose, with the test named in the comment.
- `checkFreezeReadiness` — a MAYBE **must** block freeze-readiness. Not in tension with
  the above: a maybe is not loose, but neither is it a confirmation.
- `deriveAttendance` — ACCEPTED-outranks-a-stored-NO, documented as unreachable through
  the guest flow, with "do not add precedence machinery for it".

## Migration summary

Three migrations, all generated by `prisma migrate dev` — no generated SQL hand-edited
(Do-Not-Touch zone 5). Every statement was surfaced for sign-off before apply.

| Migration | Contents |
|---|---|
| `20260805051330_gtc174_assignment_response_maybe` | one `ALTER TYPE "AssignmentResponse" ADD VALUE 'MAYBE'` |
| `20260805051343_gtc174_attendance_answer` | `CREATE TYPE "AttendanceAnswer"` + two nullable columns, no defaults |
| `20260805051356_gtc174_backfill_attendance_answer` | two `IS NULL`-guarded `UPDATE`s, zero DDL |

**Why the enum add is isolated.** PostgreSQL 15 permits `ALTER TYPE … ADD VALUE` inside a
transaction but forbids *using* the new value in that same transaction, and Prisma wraps
each migration in one. Isolating it means no later statement can reference `'MAYBE'` too
early. Precedent: `20260414050000_add_child_role_rename_littlecount`.

**Why migration 3 is authored, not generated.** There is no schema diff, so
`--create-only` correctly produced an empty migration to author into — Prisma's own path
for a data migration, and the exact pattern GTC-202 used.

**What the backfill carries, and what it deliberately does not.** `YES` and `NO` in
`rsvpStatus` are real attendance answers guests gave; dropping them would silently
un-answer people who had answered, so they carry across with their timestamps. `NOT_SURE`
is **not** carried, and this changes what those rows mean: their stored "maybe I'm
coming" becomes "attendance undetermined". That is correct under §8 — a maybe belongs to
the item, not the person — and the SQL comment says so, so the decision is visible where
the data moves.

**Condition 1 — proving the backfill moves data.** On the dev database the backfill is a
verified no-op (all 61 `PersonEvent` rows read PENDING), which meant the data-moving path
would otherwise have shipped unexercised. It was exercised before apply, against four
fixtures (YES / NO / NOT_SURE / PENDING), with the migration-2 DDL, the seeded rows and
the migration-3 UPDATEs all inside **one transaction that rolls back** — a stronger revert
than restoring values, and the dev database was never modified:

| fixture | `attendanceAnswer` | `attendanceAnsweredAt` | verdict |
|---|---|---|---|
| YES | `YES` | = source `rsvpRespondedAt` | carried |
| NO | `NO` | = source `rsvpRespondedAt` | carried |
| NOT_SURE | NULL | NULL | not carried (§8) |
| PENDING | NULL | NULL | not carried |

Blast radius 2 of 61 rows; re-running both UPDATEs immediately after changed 0 rows
(idempotent); post-`ROLLBACK` the type and column were both absent and all 61 rows still
read PENDING.

**Retained but unwritten.** `rsvpStatus`, `rsvpRespondedAt`, `rsvpFollowupSentAt` and the
`RsvpStatus` enum are kept for one ticket — the treatment GTC-168 gave
`Person.inviteAnchorAt` — so the backfill stays auditable and the change reverts cleanly.
[[GTC-219]] drops them.

## Carried deliberately, not silently

`sendRsvpFollowupNudge` (`src/lib/sms/nudge-sender.ts`) still contains a write to
`rsvpFollowupSentAt`. It is **unreachable** — its only caller iterates
`findRsvpFollowupCandidates()`, which D1 neutralised to always return `[]`. It is marked
dead in place rather than gutted, because GTC-178 (E1) deletes the finder, the sender and
the template together and a half-removed function would only make that harder to read.

Consequently the schema doc-comment says "no *reachable* path writes these" rather than
"nothing writes these" — the absolute version would have been untrue of the source.

**This is why [[GTC-219]] must land after [[GTC-178]]**, and its ticket says so: dropping
`rsvpFollowupSentAt` while that dead write exists turns dead code into a build failure.
