## The plan (as approved, 23 Nov 2026)

**A. One migration, additive only (Zone 5).**

- `Day` gains `displayOrder`, a whole number, default 0. Sessions are read in
  date order, then by that number, then in the order they were made (their
  id). Every existing Day row reads 0, so existing events keep the order the
  coordinator page already uses, with no host action and no backfill: the
  migration is exactly what Prisma generates.
- A new, empty table `SessionAbsence`: one row means "this person on this
  event is NOT at this session". It holds the person-on-event
  (`personEventId`), the session (`dayId`) and when it was made; one row per
  person per session at most. No rows means "at every session" (ruling A).
  Nothing writes it in this ticket; its writer, in a later ticket, carries the
  belongs-to-this-event check.
- Nothing existing is renamed, retyped or removed.
- Deleting: a removed session takes its rows with it; so does a person leaving
  the event, a deleted person (who leaves every event) and a deleted event
  (its sessions and people go). The database does it (ON DELETE CASCADE on
  both links), so no existing delete code changes.

**B. The session routes**, host and co-host only, like the GET:

- `POST /api/events/:id/days`: create a session (name and date).
- `PUT /api/events/:id/days`: reorder, given the full list of the event's
  sessions.
- `PATCH /api/events/:id/days/:dayId`: rename and/or change the date.
- `DELETE /api/events/:id/days/:dayId`: remove a session; refused (409) while
  it has items (ruling B).

Order of checks: the switch; signed in (401) and host or co-host of this event
(403); the input; the session belongs to this event, for the address and every
id in the list; the write. A date is given as YYYY-MM-DD and stored at
midnight UTC, as the other writers store a bare day. A new session goes last
on its date; a session moved to another date goes last on that date. One
ledger line per change, never asking "why". The words:

- "A session needs a name"
- "That name is too long (100 characters at most)"
- "Give the session's date as YYYY-MM-DD"
- "That session is not on this event" (400)
- "List every session of this event once"
- "Sessions stay in date order"
- "This session still has items. Move them to another session or to the whole
  event first." (409)

**C. "Invites only".** Today `putAwayPlan` (`src/lib/workflow.ts` line 1240)
deletes the event's days, and the plan restore (from line 1028) deletes every
day and makes fresh copies from the saved plan with new ids. With the switch
on, putting the plan away keeps the sessions, and bringing it back keeps each
session still there (same id, its rows), makes again any that is not, and puts
each dish back on its session. With the switch off both run exactly as today.
A restore from the saved plan also keeps each session's place. The old
dashboard's own restore is left as today (a finding for the later tickets).

**D. The switch.** `GATHER_SESSIONS`, read through `isSessionsOn()` in
`src/lib/sessions/switch.ts`; only the exact value `on` is on, read on every
request (as `GATHER_LIVE_SENDS` and `GATHER_DEMO_START`). While it is off each
new address answers as it does today (405 for POST and PUT on `/days`, 404 for
`/days/:dayId`) and reads and writes nothing; it also gates C. Never set in
`.env` or `.env.local`. To turn it on at the release: add `GATHER_SESSIONS=on`
as a variable on the Railway service and deploy (staging first); delete it to
turn it off.

**E.** The days GET sorts by date, then `displayOrder`, then id. Its reply is
otherwise unchanged.
