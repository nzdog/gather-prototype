# GTC-233 — Extract V2 to `/plan/[eventId]/setup` — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign

*Filed under GTC-233 rather than the number on the original brief: `docs/tickets/GTC-153.md`
was already taken by a closed, unrelated ticket (the GATHER-BUILD-CONSTANTS drift fix,
`9eb6069`). Renumbered by founder ruling, 2026-08-22.*

**Surfaced by:** external code review (v1-v2 reconciliation review, section 3 — page
extraction).

## Signal

V1 and V2 shared `/plan/[eventId]`, with `?setup=true` toggling mode inside a single
4,010-line component. Every change to V2 required reasoning about V1 and vice versa, and the
Tier 2 deletes of V1 code were blocked because V2 depended on the same file.

## Phase 1 audit — per-surface classification

The file was one component, `PlanEditorPage`, spanning most of its length. The decisive
finding: **V2's render paths are a contiguous run of early returns that exit before V1's
`return` ever runs.** V1 and V2 were adjacent, not interleaved.

| Region | Lines | Owner |
|---|---|---|
| Imports | 1–73 | 12 V2 / 47 V1, no overlap |
| Moment 2 plan mappers | 74–187 | V2-only |
| `Event`/`Team`/`Item`/`Day`/`Person` interfaces | 188–305 | shared (V1 keeps) |
| `SectionId` + validator | 306–330 | V1-only |
| State / effects / handlers | 331–1767 | ~110 lines V2, rest V1 |
| V2 render block | 1768–2181 | V2-only |
| V1 dashboard render | 2182–4010 | V1-only |

**Zero shared components.** Every one of the 59 imported components was exclusively V1 or
exclusively V2, which resolved two of the ticket's Unknowns: `Moment2PlanView` is V2-only
(it moves; no deduplication), and Moment 1 does not live in `page.tsx` — it is
`Moment1InputForm`, `Moment1Summary` and `HouseholdCardList`, orchestrated by ~110 lines.
No Zustand, no shared context.

**The cut was proved clean before it was made.** Of 36 module- and component-scope symbols
inside the removed ranges, none were referenced by the code that stays. A first pass flagged
seven apparent dangling references (`answer`, `body`, `data`, `res`, `saved`, `list`,
`categories`); all were function-local names coinciding across separate closures.

**The extracted code needed exactly six things from what stays:** `event`, `eventId`,
`toast`, `items`, `loadEvent`, `loadItems`. Ten further apparent dependencies dissolved on
inspection — the `Item` hits were the string literal `targetType: 'Item'`, the `teams` hits
were a mapper parameter and four URL strings, `people` was comment prose, and `error` was
`data.error`/`console.error`/`toast.error`.

### Surprising couplings found

1. **`items` is load-bearing for the ledger.** `Moment2PlanView`'s `onUpdateItem` and
   `onRemoveItem` call `items.find(...)` to read `assignment.response` for the why-scope
   prompt, and the code comments that it relies on `items` being loaded on mount ([[GTC-202]]).
   Omitting that mount call would have left the lookup returning `undefined` and
   `assignmentResponse` silently degrading to `null` — no error, no failing test, a quietly
   wrong ledger entry. The new route loads it explicitly, with the reason recorded at the call.
2. **The event is passed whole to the ledger.** The audit measured `event.<field>` reads and
   concluded four fields sufficed. Typecheck disproved it: `askForReason`/`askForBatchReason`
   take the event and parse it through `toLifecycleEvent`. `SetupEvent` therefore extends the
   exported `SerialisedEvent` from `src/lib/lifecycle.ts` rather than restating
   status/sentAt/endDate.

### Audit question answers

- **Layout:** `src/app/layout.tsx` is the only layout in the app tree. V2's screens are
  `fixed inset-0 z-50` full-viewport overlays that already cover Navigation, so no
  `setup/layout.tsx` was created — one would only have served to remove Navigation, a visual
  change and out of scope.
- **Importers of `page.tsx`:** none in `src/`. Two tests read it by path —
  `tests/invite-status-auth-test.ts` and `tests/batch-import-auth-test.ts` — and both assert
  on V1-only surfaces (`invite-status?hostId`, `PeopleSection` hostId) that stay put. **No
  test changes were needed**, confirmed by the suite passing unmodified.
- **`?setup=true` construction sites:** exactly one, in `src/app/plan/new/page.tsx`. No
  emails, SMS, notifications or API redirects construct it.
- **Middleware / security inventory:** the matcher does not cover `/plan/*`;
  `route-classifications.json` tracks API routes only.

## Phase 2 design

Founder decisions, 2026-08-22:

- **Decision 1 — one route, internal state machine.** `/plan/[eventId]/setup` hosts every V2
  stage. Per-stage URLs explicitly deferred: *"If per-stage URLs become needed later (email
  deep links, etc.), we add them then."* (That later is now [[GTC-235]].)
- **Decision 2 — `window.location.replace`** for the entry redirect.
- **Decision 3 — no redirect** for V2 events reaching the V1 URL.
- **Conflict A — keep the [[GTC-148]]/[[GTC-149]] `event.setup` guards in V1.** Cheap
  insurance; extraction reduces but does not eliminate V2 events reaching V1's URL.
- **Conflict B — fix the events list**, in scope, so V2 events stay reachable.

**No shared module was created.** V2 declares `SetupEvent` and `SetupItem` locally. The
duplication is a few lines and buys the independence the ticket exists to get.

## What moved / stayed / shared

**Moved** to `EventSetupPage` in `src/app/plan/[eventId]/setup/page.tsx` (768 lines): the
Moment 2 mappers including `mapTeamsAndItemsToPlanCategories`, the V2 state flags,
`apiHouseholdToSaved`, the households/channel-candidates effect,
`loadMoment2PlanCategories`, and the V2 render block. Duplicated rather than shared:
`loadEvent`, `loadItems`, and the loading/error guards.

**Stayed:** the V1 dashboard, all 47 V1 imports, `SectionId`, and the 13 `event.setup`
guards. `page.tsx` fell from 4,010 to 3,353 lines. `useCallback` was dropped from its React
import, orphaned when `apiHouseholdToSaved` left.

**Retired:** `?setup=true` in both readers and its one construction site, the URL-cleanup
effect, and the `params.delete('setup')` line plus its KB-003 footgun comment in
`handleChecklistOpenAddPerson`.

**Deliberate reductions:** the V2 approve handlers previously called `loadTeams`,
`loadConflicts`, `setGateCheckRefresh` and `setNextStepDismissed` purely to prime V1's
dashboard before falling through to it. Under Option A the host stays in V2, so these were
dropped — verified safe, as `teams`, `conflicts`, `people` and `days` state are never read
in the extracted code.

## Post-completion landing

Approving the plan previously called `setShowMoment2PlanView(false)` and set nothing else,
falling through every early return into the V1 dashboard — the Option A violation this
ticket had to fix. It now refreshes the event, items and categories and **keeps the host on
the plan view**. `Moment2Step2Skeleton`'s fallback `onApprove` was repointed at the plan view
for the same reason.

## Known limitations

- **A generated V2 plan cannot be reopened.** `setShowMoment2PlanView(true)` has two call
  sites in `EventSetupPage`, and both are callbacks of `Moment2Step2Skeleton` — nothing
  hydrates the flag on mount, so revisiting an event whose plan exists lands on the opening
  screen. Pre-existing; moved unchanged by this ticket. Filed as **[[GTC-235]]**.
- **V2 has no post-plan surface.** "Plan looks good →" now keeps the host on the plan view
  rather than falling through to V1, which is correct per Option A but leaves the button a
  dead end until a V2 post-plan surface exists.
- **V2 events on `/plan/[eventId]` render the V1 dashboard**, by design (Decision 3). The
  guards hide the V1 generate and regenerate pipelines, but the remaining V1 surfaces are
  live against V2 data.
- Two code comments name `?setup=true` when explaining its retirement. No functional
  reference remains.

## V1 → V2 migration follow-ups

V2 has no replacement for these V1 post-plan surfaces; each is a separate ticket:
invites, people management, nudges, freeze, conflicts, share links. Until they exist, a V2
event's only route to them is the V1 dashboard at `/plan/[eventId]`.
