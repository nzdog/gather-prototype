## What this ticket does, in plain English

After she pays, a host who was already signed in used to be sent straight
into setup with no word that the payment worked. Now she first sees a
short "You're all set!" screen with her event's name and one button,
"Start with your people", which takes her into setup, the same place as
before. A host who was not signed in (the sign-in link was emailed) sees
the same new heading and first line on her existing screen; the rest of
that screen is unchanged. Nothing about the payment itself changes.

## The founder's rulings (28 Oct 2026, in Cowork)

- A new "paid" state in src/app/plan/new/page.tsx, shown after the event
  is made and BEFORE she moves on to setup. It says: heading "You're all
  set!", line "Your event " + the event's name in the page's usual quotes
  + " is paid for and ready.", and one button "Start with your people"

```
     Your event "<name>" is paid for and ready.
```

Signed-out payer, after payment (the sign-in link was emailed):

```
old  Payment received

```

The rest of that screen is kept word for word: the amber note when she
is signed in as another address, "We've sent a sign-in link to <address>.
Open it and you'll land straight in your event." (or the red "We couldn't
send the sign-in link" box), the button "Go to sign-in", and "Wrong

Characters: the apostrophe is `&rsquo;` and the quotes `&ldquo;` and


## Refresh and Back, before and after

The new screen would sit on the return address
(/plan/new?session_id=...). A refresh there would run the page again,
call the payment check again, get the server's 409 and show the
paid-before screen ("Payment received ... Sign in with the email you paid
with"), which is the founder's example of worse. So the new screen first
rewrites the address bar to the setup address with
`window.history.replaceState` (no page load, no request; the page the
host sees stays the paid screen). Next 15.5.28 supports this: its own
patch of replaceState keeps the page's tree and only moves the address
(node_modules/next/dist/client/components/app-router.js, the
restoreReducer keeps the tree). The setup page itself already uses the
same call.

Before (measured on the dev server at 0680dfc, scratch proof, the
payment check answered in the browser, setup answered by a stand-in):

- after payment the browser is on /plan/<id>/setup;
- a refresh reloads /plan/<id>/setup; no second payment check;
- Back goes to the page before the payment (the return address was
  replaced, so it is skipped).

After (the same proof on the dev server at 6761488):

- after payment the host sees "You're all set!", her event's line and
  "Start with your people →"; the address bar already reads
  /plan/<id>/setup; nothing was asked of the server for it;
- 4 seconds later the screen is still there (no timer);
- a refresh opens /plan/<id>/setup; no second payment check (one POST in
  all for that visit, as before);
- Back goes to the page before the payment, as before;
- the button opens /plan/<id>/setup; Back from there goes to the page
  before the payment, as before.

So neither a refresh nor Back is worse: ticket C is not a stop. The one
visible difference: while the new screen shows, the address bar reads
the setup address, not /plan/new.
