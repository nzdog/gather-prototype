# GTC-167 — A1: State-machine reconciliation plan (FROZEN → send-lock/ledger/versions)

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** max | **Mode:** Plan mode

---

### Context

`gather-moment-4-spec-v1.md` §7 states plainly: "the current CONFIRMING→FROZEN transition and
FROZEN state need reconciling... The send becomes the lock point; what FROZEN currently models
either collapses into the send or is removed. This is a state-machine change and must be treated
as such (Plan mode, max effort, review step)." The discovery-gap rulings (Moment 4 spec §10;
Hinge spec §2) since resolved every open question in this territory. This is the first ticket of
Epic A, load-bearing for essentially every later epic in the Moment 4 + Hinge breakdown
(`docs/04_roadmap/moment4-hinge-discovery-report.md`).

**This ticket produces a written plan only. No code, no schema migration, no branch work beyond
the plan document itself.** GTC-168 (A2) and GTC-169 (A3) execute what this plan decides.

**Approach accepted in advance:** the eventual implementation (A2 onward) follows the
experiment-branch pattern established by GTC-145/146 (`gather-experiment-methodology`,
`gather-change-control`) — architecture changes of this magnitude do not land directly on
`feat/moment-one-redesign`. This plan's output should include a proposed experiment-branch name
and what "measured" means for a correctness/architecture change (call-site migration count,
regression surface, not item-count-style product metrics).

### What the repo looks like today (from the discovery report — verify before relying)

- `EventStatus` enum: DRAFT, CONFIRMING, FROZEN, COMPLETE (`prisma/schema.prisma`).
- `canTransition`/`canMutate`/`checkFreezeReadiness`/`requireNotFrozen` gate on FROZEN across
  ~30 call sites: routes (`transition`, `frozen-edit`, `wrap-up`, `shared-link`,
  `h/[token]/status`, `join/[token]/claim`, `p/[token]/ack/[assignmentId]`, `c/[token]/items/*`),
  pages (`join/[token]`, `h/[token]`, `h/[token]/team/[teamId]`, `c/[token]`, `p/[token]`),
  components (`SharedLinkSection`, `EventStageProgress`, `FreezeCheck`, `TransitionModal`,
  `InviteStatusSection`, `EditItemModal`, `UnfreezeSection`, `FrozenEditModal`), and 12+ branch
  sites in the god file. Full list in the discovery report, Task 1 §1.
- `frozen-edit/route.ts` already does allow+reason for 3 mutation types, FROZEN-only,
  unconditional reason — narrower and stricter than the ruled model.
- `PlanRevision`/`createRevision` exist but are manual/opt-in; nothing auto-versions per change;
  `GET .../revisions` caps at 5.
- Two unlinked audit systems: `AuditEntry`/`logAudit` (structured) vs `InviteEvent`/`logInviteEvent`
  (the one place a reason is actually mandatory today, in an untyped `metadata` blob).
- `h/[token]/status`'s FROZEN→CONFIRMING "unfreeze" path is exactly the recall/undo the Hinge spec
  now rules out at the mechanism level.

### Scope — questions this plan must answer

1. **Disposition of `EventStatus.FROZEN`.** Collapse into a boolean/timestamp (e.g.
   `Event.sentAt`) vs. retain as a renamed enum value vs. keep FROZEN for historical/read
   compatibility with already-frozen events. Recommend one, with reasoning.
2. **Disposition of `COMPLETE`.** Per §10.1, it survives but becomes calendar-driven (event date
   passing IS the transition — no button). Where does that check run (cron sweep? computed at
   read time?)? How does `wrap-up`'s current hard-requirement of FROZEN status migrate to
   COMPLETE-gated?
3. **The consumer migration sequence.** Take the ~30-site map above and sequence it — likely by
   surface (API routes, guards, UI components, the god file) — for GTC-169 (A3) to execute
   against. Flag any site that looks larger than "swap FROZEN for a send-predicate" (e.g. anything
   currently doing FROZEN-only allow+reason that needs to become always-allow+scoped-reason).
4. **Ledger unification.** `AuditEntry` vs `InviteEvent` — which becomes canonical, or do they
   merge into a new model? How does `PlanRevision` tie in for the "versions ARE the steps"
   requirement (Hinge §2: universal, silent, per-individual-change, complete history always
   reachable — not capped at 5)? Storage mechanics (diffs, dedup) are explicitly this ticket's to
   solve per the spec.
5. **Why-scope rule.** Hinge §2 (ruled gap #2): the why is required only for changes that touch
   someone — reassignment, removal, a quantity someone claimed against, date/venue. Produce a
   concrete, enumerable rule (not a vibe) for which mutation types trigger the reason requirement
   and which don't (a typo fix must NOT be interrogated).
6. **Removal of the FROZEN→CONFIRMING unfreeze path.** Hinge §2: "The old FROZEN→CONFIRMING
   unfreeze path dies with FROZEN in the state-machine reconciliation." What replaces the
   "I made a mistake" recovery case? (Answer per spec: the material-change re-ask machinery,
   Moment 4 §8.5/Epic F — building Epic F is explicitly OUT of scope for A1-A3; this plan only
   needs to confirm the handoff point exists and note the dependency.)
7. **Mini-sends.** Hinge §2 (ruled gap #5): people added post-send get their own clocks
   (nudge cadence, red-by-time) truncated by the event date. Does this require a per-person send
   timestamp distinct from `Event.sentAt`, or can it be derived? Plan must specify the data shape.
8. **Migration and rollback safety.** This changes a heavily-relied-upon status enum with ~30
   consumers. The plan must include a rollback strategy and a recommendation on read-compatibility
   for historical events already in FROZEN/COMPLETE before this ships.

### Do not touch

All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding. This ticket is planning only —
it should not require touching any zone, but if the plan concludes it cannot avoid one (e.g. SMS
send paths for mini-sends), that is Stop Condition 5: stop and report rather than plan around it
silently.

### Acceptance

This ticket is complete when it produces a written plan document (proposed location:
`docs/04_roadmap/` alongside the discovery report, or as this ticket's own body — executor's
call) that:
- [ ] Answers all eight scope questions above with a recommendation and reasoning, not just an
      inventory of options.
- [ ] Sequences GTC-169's (A3) consumer migration by surface.
- [ ] Names the experiment branch and what "measured" means for this change.
- [ ] Lists every sub-decision it could NOT resolve without founder input, explicitly, per the
      Stop-Conditions culture — a plan that guesses past an unknown is worse than one that stops.
- [ ] Does not modify any source, schema, or migration file.

### Stop Conditions

1. `GATHER-BUILD-CONSTANTS.md` missing
2. Cannot produce a recommendation for one of the eight scope questions without founder input —
   document the specific sub-question and await instruction rather than guessing
3. The plan concludes a Do-Not-Touch zone must be modified — stop and report
4. Any required unknown surfaces during planning that isn't covered by the discovery report or
   the two specs
