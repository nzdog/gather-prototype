### /h/ (the host link) - handlers with a second id in the address

- GET `/api/h/[token]/team/[teamId]`. Resolves to the event. CHECKS: the
  team is looked up and refused 404 "Team not found" unless its
  `eventId` is the link's event, before anything about it is answered.
- POST `/api/h/[token]/people/[personId]/manual-override`. Resolves to
  the event. DOES NOT CHECK: it finds the person by id alone. For a
  person of another event it wrote a MANUAL_OVERRIDE_MARKED line in the
  link's event's invite log (with the host's reason) and answered 200.
  (Its assignment write was already limited to the link's event, so no
  answer on the other event moved.)

### /c/ (the coordinator link) - handlers with a second id in the address

- PATCH and DELETE `/api/c/[token]/items/[itemId]`. Resolve to the event
  and the team. CHECK: the item is refused 404 "Item not found" unless
  its team is the link's team (so it is on the link's event too).
- POST and DELETE `/api/c/[token]/items/[itemId]/assign`. Same check,
  same answer.
- POST `/api/c/[token]/ack/[assignmentId]` (the coordinator answering
  their own item). Resolves to the event and the team. DOES NOT CHECK

  for event A could record the coordinator's answer to their own item
  on event B, and the history line ("Declined <B's item>") went into
  event A's history. It is not team-scoped today, by design: a
  coordinator answers their own items on any team of the event (its
  own-row check, GTC-174), and GET `/api/c/[token]` lists them across
  teams.

## The finding, in plain English

A Gather link (the host's, a team coordinator's) opens one event. Two
of the addresses behind those links name a second thing as well, and
trusted it without asking whether it was on the link's event:

- The host link's "mark by hand" (the host saying "they've confirmed")
  took any person's id. For a person of another event it wrote a
  "marked by hand" line, with the host's reason, into the host's own
  event's log about that stranger, and said "done".
- The coordinator link's "my answer" took any of the coordinator's own
  items. Someone who coordinates on one event and is a guest on another
  could answer their item on the other event through the wrong link,
  and the line saying so landed in the wrong event's history.

Neither could send anything, and neither could change another person's
answer. Each now says "not found", exactly as it does for an id that
does not exist.

## What each route did before, and does now

Both now start the same way, right after the link is resolved: one
indexed lookup that asks only "is this thing on the link's event?" and
reads only its id. If not, they answer 404 and stop: the body is not
read, nothing is written, logged or put in any history. Everything
after that line is exactly as it was.

- POST `/api/h/[token]/people/[personId]/manual-override`. Before: for
  a person with no place on the link's event, it read the body, found
  the person by id, moved none of their answers (that write was already
  limited to the link's event), wrote a MANUAL_OVERRIDE_MARKED line in
  the link's event's invite log and answered 200 `{ success: true,
  assignmentsUpdated: 0 }`. Now: 404 `{ error: 'Person not found' }`
  before the body is read. For a person on the event nothing changes.
- POST `/api/c/[token]/ack/[assignmentId]`. Before: for the
  coordinator's own assignment on another event, it read the body,
  recorded the answer on that assignment and wrote the history line
  (ACCEPT/DECLINE/MAYBE_ASSIGNMENT, naming the item) into the link's
  event, and answered 200. Now: 404 `{ error: 'Assignment not found' }`
  before the body is read. For an assignment on the link's event
  (any team of it) nothing changes: the own-row check, the 400 for a bad
  response, the "unchanged, do nothing" path and the write are as
  they were.

One change for things that do not exist at all, reported for
completeness: an id that is not on the event (or does not exist) sent
with a bad body used to get the body's 400; it now gets the 404, as
GTC-401's guards do, because the guard comes before the body is read.

## The answer, copied from which siblings

- manual-override: 404 `{ error: 'Person not found' }`, copied from the
  signed-in sibling `POST /api/events/[id]/people/[personId]/manual-override`
  (GTC-401's guard, itself copied from `reset-claim`). It is also what
  this route already said for a person id that does not exist.
- ack: 404 `{ error: 'Assignment not found' }`, copied from this route's

  not yours to answer."): that one is for a row that is on the event
  and is somebody else's, and this route's own-row refusal is already a
  404.
