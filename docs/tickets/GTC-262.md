# GTC-262 — Unauthenticated endpoints hand out COORDINATOR tokens

**Status:** Open — filed 2026-08-29, not investigated beyond the observation below |
**Branch:** `feat/moment-one-redesign` | **Severity:** High

*Filed out of [[GTC-256]] phase 3, which closed the same defect for the HOST scope and
deliberately did not widen. Founder instruction, 2026-08-29: "File the coordinator token
exposure as its own ticket. Same class, wider scope, unauthenticated endpoint handing out
tokens."*

---

### Signal

**Expected**
An unauthenticated caller holding only an event id, or only a shared invite link, can
obtain at most a PARTICIPANT credential — the thing the shared link exists to give out.

**Actual**
Two unauthenticated surfaces return whatever access token a person holds, preferring
PARTICIPANT but **falling back to COORDINATOR**, together with the URL prefix that opens
it. A coordinator's magic link is therefore obtainable by anyone with the link the host is
told to share with the whole family.

**Smallest failing case**
`GET /api/gather/<eventId>/directory` on an event with a team coordinator returns that
coordinator's token with `tokenPrefix: "c"`.

---

### Scope

**The two surfaces**

| Site | What it does |
|---|---|
| `GET /api/gather/[eventId]/directory` | Unauthenticated, keyed on the event id alone. Builds `tokenMap` with `scopePriority = { PARTICIPANT: 3, COORDINATOR: 2, HOST: 1 }` and emits `{ id, name, token, tokenPrefix }` per person. The `prefixMap` includes `COORDINATOR: 'c'`. |
| `POST /api/join/[token]/claim` | Unauthenticated, takes `personId` from the body. `const anyToken = participantToken \|\| person.tokens[0]`, and when there is no participant token it returns that token with `redirectPrefix` — `'c'` for a coordinator. |

**What GTC-256 already fixed, and why it is not this ticket**

GTC-256 phase 3 closed the **HOST** half of both — by Ruling 5, "her name is not claimable
through the shared link" — and narrowed each fix to the host on purpose. `ADDRESSABLE_PERSON_EVENT`
in `src/lib/eligibility/host-exclusion.ts` excludes the host from the directory query, and
`isHostMembership` refuses her in the claim route. Both carry a comment pointing here.

The coordinator case is **the same class with a wider blast radius**, and closing it is a
decision rather than a filter change: it needs an answer to what the directory is *for*.
The dashboard describes it as "Share this single link with your whole family. Everyone can
click their name to access their personal page" — and a coordinator clicking their own name
and landing in their coordinator view may well be the intent. What is certainly not the
intent is that *anyone else* holding the link can do the same.

**Fix here:**
`src/app/api/gather/[eventId]/directory/route.ts`, `src/app/api/join/[token]/claim/route.ts`.

**Do not touch:**
All Do-Not-Touch Zones in GATHER-BUILD-CONSTANTS.md are binding — Zone 3 (AccessToken &
scope system) covers both files' subject matter. The host exclusions GTC-256 placed in both
routes must survive whatever shape this takes.

---

### Unknowns

1. **Is a coordinator meant to reach their coordinator view from the directory at all?**
   If yes, the fix is not "return PARTICIPANT only" — it is some form of proof that the
   clicker is that person, which the directory has never had for anyone.
2. **Does the same question apply to the PARTICIPANT tokens the directory already hands
   out?** The directory's whole design is that names are self-selected with no
   verification, and the claim endpoint's 409 ("this name has already been claimed") is the
   only friction. That is a deliberate product decision for guests; whether it extends to
   coordinators is the question this ticket asks.
3. **How many events have coordinators today, and is the directory link in real use?**
   Re-measure before choosing a shape.

⚠ Both unknowns are product decisions, not implementation details. Per the house rule an
executor reaching them stops and asks rather than inferring.
