# GTC-262 — Unauthenticated endpoints hand out COORDINATOR tokens

**Status:** DONE — filed 2026-08-29, confirmed and built 2026-09-18 |
**Branch:** `feat/moment-one-redesign` | **Severity:** High

*Filed out of [[GTC-256]] phase 3, which closed the same defect for the HOST scope and
deliberately did not widen. Founder instruction, 2026-08-29: "File the coordinator token
exposure as its own ticket. Same class, wider scope, unauthenticated endpoint handing out
tokens."*

---

### Signal

**Expected**
An unauthenticated caller holding only an event id, or only a shared invite link, can
obtain at most a PARTICIPANT credential — the thing the shared link exists to give out.

**Actual**
Two unauthenticated surfaces return whatever access token a person holds, preferring
PARTICIPANT but **falling back to COORDINATOR**, together with the URL prefix that opens
it. A coordinator's magic link is therefore obtainable by anyone with the link the host is
told to share with the whole family.

**Smallest failing case**
`GET /api/gather/<eventId>/directory` on an event with a team coordinator returns that
coordinator's token with `tokenPrefix: "c"`.

---

### Scope

**The two surfaces**

| Site | What it does |
|---|---|
| `GET /api/gather/[eventId]/directory` | Unauthenticated, keyed on the event id alone. Builds `tokenMap` with `scopePriority = { PARTICIPANT: 3, COORDINATOR: 2, HOST: 1 }` and emits `{ id, name, token, tokenPrefix }` per person. The `prefixMap` includes `COORDINATOR: 'c'`. |
| `POST /api/join/[token]/claim` | Unauthenticated, takes `personId` from the body. `const anyToken = participantToken \|\| person.tokens[0]`, and when there is no participant token it returns that token with `redirectPrefix` — `'c'` for a coordinator. |

**What GTC-256 already fixed, and why it is not this ticket**

GTC-256 phase 3 closed the **HOST** half of both — by Ruling 5, "her name is not claimable
through the shared link" — and narrowed each fix to the host on purpose. `ADDRESSABLE_PERSON_EVENT`
in `src/lib/eligibility/host-exclusion.ts` excludes the host from the directory query, and
`isHostMembership` refuses her in the claim route. Both carry a comment pointing here.

The coordinator case is **the same class with a wider blast radius**, and closing it is a
decision rather than a filter change: it needs an answer to what the directory is *for*.
The dashboard describes it as "Share this single link with your whole family. Everyone can
click their name to access their personal page" — and a coordinator clicking their own name
and landing in their coordinator view may well be the intent. What is certainly not the
intent is that *anyone else* holding the link can do the same.

**Fix here:**
`src/app/api/gather/[eventId]/directory/route.ts`, `src/app/api/join/[token]/claim/route.ts`.

**Do not touch:**
All Do-Not-Touch Zones in GATHER-BUILD-CONSTANTS.md are binding — Zone 3 (AccessToken &
scope system) covers both files' subject matter. The host exclusions GTC-256 placed in both
routes must survive whatever shape this takes.

---

### Unknowns

1. **Is a coordinator meant to reach their coordinator view from the directory at all?**
   If yes, the fix is not "return PARTICIPANT only" — it is some form of proof that the
   clicker is that person, which the directory has never had for anyone.
2. **Does the same question apply to the PARTICIPANT tokens the directory already hands
   out?** The directory's whole design is that names are self-selected with no
   verification, and the claim endpoint's 409 ("this name has already been claimed") is the
   only friction. That is a deliberate product decision for guests; whether it extends to
   coordinators is the question this ticket asks.
3. **How many events have coordinators today, and is the directory link in real use?**
   Re-measure before choosing a shape.

⚠ Both unknowns are product decisions, not implementation details. Per the house rule an
executor reaching them stops and asks rather than inferring.

## Founder rulings — what the directory is for (Nigel, 2026-09-18)

Six, given against a shape proposal, before any code was written.

1. **Unknown 1 — NO.** A coordinator does not reach `/c/` from the directory.
   > "A participant token is an ask, a coordinator token is a job, and the
   > no-verification bargain was struck about the ask. It was never struck about write
   > access to a team's plan."
2. **Unknown 2 — NO, and RECORDED AS RULED rather than left alone.** The participant
   bargain stands.
   > "This narrows the kind of credential, not the bargain, and the directory remains a
   > credential dispenser afterwards with the 409 as its only friction. Say that plainly so
   > nobody reads this fix as having closed something it has not."
3. **The claim route — REMOVE the non-participant branch, not restrict it.**
   > "Restricting leaves the mechanism standing as dead code, and the dead code is the
   > mechanism."
4. **The refusal keys on the membership role, not on token shape.**
   > "Written the token-shaped way it silently stops working the day GTC-294 lands, and
   > nothing would fail. Written the role-shaped way it survives issuance changing
   > underneath it."
5. **Zone 3 — signed off for two items and nothing else.** The scope-emission rule moving
   into one named module and narrowing to PARTICIPANT, and the claim-route refusal on
   `PersonEvent.role`. No schema, no issuance, no `resolveToken`. *"If the build needs any of
   those three, HALT."* It needed none of them.
6. **The ordering stands, on the executor's reason rather than the ticket's** — recorded in
   full under *Why the ordering held* below.

## The confirmation, before the build (2026-09-18)

Driven read-only against the tree and the running app, unauthenticated and with no cookie.
Nothing was minted; the one POST was proved inert by a before/after DB diff. **The finding is
real on both surfaces and WIDER THAN FILED on the entry point.**

**As filed.** `scopePriority` and `prefixMap` in the directory; `participantToken ||
person.tokens[0]` and the prefix ternary in the claim route. Live:

```
GET /api/gather/cmmolxnlm00181yn154x1aylz/directory
  Henderson Family Christmas 2025 — 42 people, 7 with tokenPrefix=c

POST /api/join/NzW0…ZdCk/claim  {"personId":"cmu6laq1x001jrj8upc8jrpkm"}
  HTTP 200 {"participantToken":"6e45ed18…","personName":"Team A Coordinator",
            "redirectPrefix":"c"}
  DB DIFF: NO CHANGE — the redirect branch writes nothing
```

**Scale.** 16 directory rows across 6 events in `gather_dev` emitted a coordinator token.
**9 of the 16 were still inside `expiresAt`** — the other 7 had lapsed. Expiry was doing
unearned work here; it is a 90-day clock on stale seed data, not a control.

**What the credential is worth.** Not a read link. Via `src/app/api/c/[token]/**` a
coordinator token authorises create, `PATCH` and `DELETE` of a team's items and
assign/unassign of people to them, plus `ack`. `middleware.ts` also writes it into a
path-scoped `gather_c_token` cookie on first page visit. No phone or email is in any
coordinator payload — checked; names only.

### Five findings the ticket did not have

1. ⚠ **The entry point is the event id, not the shared link.** The ticket says "anyone with
   the shared family link". The directory never reads `sharedLinkToken`, never checks
   `sharedLinkEnabled`, never checks `Event.status`, and `middleware.ts`'s matcher does not
   name it. Henderson has `sharedLinkEnabled: false` and returned everything anyway. **The
   host's only kill switch does not close this door, and there is no other.**
2. **It serves `DRAFT` and `FROZEN` events alike.** Proved on both.
3. **The claim fallback was order-nondeterministic.** `person.tokens[0]` had no `orderBy`.
   Every reachable case yielded COORDINATOR, so the verdict was unchanged — but *which*
   token leaked was whatever Postgres returned.
4. **The response field name lied.** The body field was `participantToken` carrying a
   coordinator token, and `NameSelectionClient` pushed `/${data.redirectPrefix}/${data.participantToken}`.
5. **The security suite ratified it.** `route-classifications.json` recorded the route as
   `authType: "PUBLIC"`, `authEvidence: ["public directory"]`, `securityIssues: []`.

Findings 1 and 2 are **not fixed here.** On founder instruction they are filed as
**[[GTC-314]]** — a surface with no off switch, keyed on a permanent id, is a different
defect from the one this ticket fixes.

## Evidence (Executor-Completed) — 2026-09-18

### Root cause confirmed

The rule deciding which `TokenScope` an unauthenticated caller may be handed lived in
neither route and in both of them, as four expressions: a `scopePriority` table, a
`prefixMap`, a `||` fallback and a prefix ternary. None of them was the rule; all four were
restatements of an intent nobody had written down. GTC-256 phase 3 had already closed the
HOST slice of each by hand, leaving the mechanism in place and a comment pointing here.

### What the directory is for — answered, because the fix depended on it

It is the **unaddressed path in**: the door for a guest the host has no number for, or who
lost their text. Its bargain is that names are self-selected with no verification, and the
409 is the only friction there has ever been. That bargain was struck about the **ask**. The
fix therefore withholds the **credential** and keeps the **row** — a coordinator is a guest
and belongs in the family's view of who is coming. That is the one place this fix's shape
differs from GTC-256's, which could drop the host's row outright.

### Files changed

**The rule, in one place:**

- `src/lib/eligibility/shared-link-exposure.ts` (new) — `SHAREABLE_TOKEN_SCOPE`,
  `SHAREABLE_TOKEN_PREFIX`, `SHAREABLE_ACCESS_TOKEN`, `isClaimableRole`,
  `UNKNOWN_PERSON_MESSAGE`, `UNKNOWN_PERSON_STATUS`. Sibling in shape to
  `host-exclusion.ts`. The docstring carries why the claim gate reads the role and not the
  tokens, why it is an allowlist, why it does **not** replace `isHostMembership`, and
  ruling 2 verbatim so the unclosed half is not misread as closed.

**The two surfaces:**

- `src/app/api/gather/[eventId]/directory/route.ts` — the token query is narrowed **in SQL**
  via `SHAREABLE_ACCESS_TOKEN`, so a coordinator token never enters the process. The
  `scopePriority` table and the `prefixMap` are **deleted, not narrowed** (ruling 3); with
  one loadable scope there is no priority left to get wrong. The host filter above is
  untouched and its comment now records why it stays host-only.
- `src/app/api/join/[token]/claim/route.ts` — the `!participantToken` redirect branch is
  **removed**, and `person.tokens[0]` with it. A new gate refuses any membership whose
  `PersonEvent.role` is not `PARTICIPANT`, with **404 and the unknown-person wording** —
  byte-identical to the host refusal, so it cannot be used as an oracle for "this `personId`
  coordinates a team here". ⚠ **`isHostMembership` is retained beside it and is not
  optional**: it keys on `Event.hostId`, which catches a host row re-roled to PARTICIPANT
  that the role allowlist would admit.

**The copy — both mitigations, on instruction:**

- `src/app/gather/[eventId]/directory/page.tsx` — the `token: null` branch said *"This person
  does not have access yet. Please contact the host."*, which is false for a coordinator and
  is now the only thing they see. It says:

  > *"No link for {name} in this directory. Coordinators get theirs from the host directly —
  > and so does anyone added since invitations went out."*

  ⚠ **THE CONSTRAINT THAT SHAPED IT, recorded because it is the reason the sentence reads
  indirectly rather than naming the person's situation.** Two populations land on this branch
  and **the payload cannot tell them apart**: a coordinator, whose credential this endpoint
  now deliberately withholds, and a guest whose PARTICIPANT token has not been issued yet
  ([[GTC-189]] records 155 of 232 recipients in `gather_dev` holding none, because the press
  is where they get one). The obvious fix — a flag in the response saying which — would let an
  unauthenticated caller **enumerate who holds write access to this event's teams**. That is a
  smaller disclosure than the token this ticket just closed, and it is the same kind. So the
  marker was not added, and the sentence has to be true of both instead.

  Founder ruling, 2026-09-18, choosing this wording over a shorter alternative: it *"does more
  work — it tells the reader what happens next, and 'anyone added since invitations went out'
  covers the second case honestly. The shorter one says some links go directly without saying
  whose, which leaves a coordinator wondering whether they have been forgotten."*
- `src/app/plan/[eventId]/page.tsx` — the Family Directory card promises "everyone can click
  their name", which is no longer true. It now adds: *"Coordinators are the exception — their
  link opens their team's plan, so it isn't in the shared directory. Send those from the list
  below."* The individual `/c/` links from `listInviteLinks` render directly beneath it.

**The record:**

- `route-classifications.json` — `authEvidence` for the directory is now
  `"public directory — PARTICIPANT tokens only (GTC-262)"`. One line; `authType` stays
  `PUBLIC` because it is. Nothing in `tests/` was weakened.
- `tests/coordinator-token-exposure-test.ts` (new) + `package.json` —
  `npm run test:coordinator-tokens`.
- `docs/tickets/GTC-314.md` (new) — findings 1 and 2, filed rather than folded in.

### Why the ordering held — recorded on instruction

GTC-294's own reason is that issuing coordinators a PARTICIPANT token "moves GTC-262's blast
radius while GTC-262 is still open". True, and the tree makes it sharper: **doing GTC-294
first would have hidden this rather than fixed it.**

⚠ **This stopped being reasoning during the RED run** — see *THE MASKING, MEASURED* above,
where two assertions went green against the unfixed tree for exactly this cause. What follows
is why the masking would not have been temporary.

`scopePriority` preferred PARTICIPANT (3) over COORDINATOR (2). Give every coordinator a
participant token and the 16 `c` rows fall to near zero — the symptom vanishes, the fallback
stays, and the leak becomes conditional on a coordinator *lacking* a participant token. That
condition does not go away. Three named ways it recurs:

1. **`ensureEventTokens` step 3** issues a COORDINATOR token to `team.coordinatorId` whether
   or not that person has a `PersonEvent` row, while step 4 iterates `personEvents`.
   **Measured: one such coordinator exists in `gather_dev` today.** [[GTC-294]]'s own
   acceptance list carries this as unresolved.
2. **Tokens expire at 90 days and nothing renews them.** 8 of 19 coordinator tokens in
   `gather_dev` were already past `expiresAt`. A coordinator whose PARTICIPANT token lapses
   before their COORDINATOR one is back to a `c` emission.
3. **Neither press route calls `ensureEventTokens` today** — [[GTC-189]], verified by grep —
   and 155 of 232 recipients in `gather_dev` hold no PARTICIPANT token. Issuance is neither
   universal nor guaranteed to have run.

A latent leak behind a condition nobody would think to test is worse than the one that was
there. The emission is now decided, so [[GTC-294]] lands on a surface that cannot leak
whatever it is given.

### What [[GTC-294]] inherits

- **A decided emission rule it cannot reopen.** It may mint whatever it likes.
- **A refusal that survives it, proved against it.** The suite mints a PARTICIPANT token for
  the coordinator by hand — GTC-294's shape, simulated — and asserts the claim route still
  returns 404 and still writes nothing. ⚠ **A consequence [[GTC-294]]'s ticket does not
  list:** without this, a POST carrying a coordinator's `personId` would have run the FULL
  claim after that ticket lands, stamping `claimedAt`/`claimedBy` on their token and
  `reachabilityTier: SHARED` + `claimedViaSharedLink: true` onto their membership row, plus a
  `NAME_CLAIMED` invite event — reachable only by a crafted POST, since
  `src/app/join/[token]/page.tsx` lists only `role: 'PARTICIPANT'` and never names them.
- **The forward behaviour, asserted now.** After [[GTC-294]] the directory emits the
  coordinator's PARTICIPANT link with prefix `p`: they reach their own ask from the
  directory, which is what the directory is for, and never the `/c/` job link. The two
  surfaces therefore do different things for a coordinator — the directory hands them their
  ask, the claim route refuses their name — and that is deliberate, because only the claim
  route writes "this guest found themselves on the shared link".
- **The `token: null` copy**, which every coordinator meets in the window until it lands.

### What this deliberately leaves

- ⚠ **Ruling 2, stated plainly so it is not misread:** the directory is **still a credential
  dispenser**. It still hands a working PARTICIPANT token to anyone holding the event id.
  Names are still self-selected with no verification of any kind. The 409 is still the only
  friction, and the directory page does not even pass through it — it routes straight to
  `/p/{token}`. **This fix narrowed the kind of credential, not the bargain.**
- **The door has no off switch and no rotation** — findings 1 and 2, filed as [[GTC-314]].
- **Expired tokens are still published.** The query filters on scope, not on `expiresAt`, so
  a lapsed participant token is still emitted and `resolveToken` then rejects it — the guest
  clicks their name and gets nothing. Pre-existing, not a disclosure, and not this ticket's.
- **`listInviteLinks` still returns every scope** to the host's own plan page. That surface
  is session-authenticated and is the intended way a coordinator gets their `/c/` link.
