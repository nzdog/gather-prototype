### Signal

**Expected**
One fact answers *"has this guest opted out of texts?"*, written in one place and read by every
path that decides whether to text — meaning what [[GTC-229]] F3 and [[GTC-288]] ruled on
2026-09-12: **not from Gather**, account-wide.

**Actual — two facts, three scopes, two sets of readers.**

**`SmsOptOut`** — one row per phone number per host, `@@unique([phoneNumber, hostId])`.
- **Writers:** `POST` in `src/app/api/sms/inbound/route.ts` (upsert; the host is attributed from
  the newest `NUDGE_SENT_AUTO` logged for that number, which `sendSms` logs on every successful
  text); `manualOptOut` in `src/lib/sms/opt-out-service.ts`, zero callers. **Deleter:**
  `removeOptOut`, zero callers.
- **Readers:** `checkOptOut` inside `sendSms` in `src/lib/sms/send-sms.ts` — the send-time gate
  every text passes; `isOptedOut` in `findNudgeCandidates` and `findProxyNudgeCandidates`;
  `findDecideByFollowupCandidates` (its own query); `POST` in
  `src/app/api/events/[id]/people/[personId]/nudge/route.ts` (its own query, falling to email);
  `GET` in `src/app/api/events/[id]/invite-status/route.ts` (`getOptOutStatuses`) and `GET` in
  `src/app/api/events/[id]/people/[personId]/invite-detail/route.ts` (its own query).
  `checkOptOutBatch` has zero callers.

**`Person.smsOptedOut` / `smsOptedOutAt`** — one flag per person, across every event and every host.
- **Writer:** the same inbound `POST`, only when a `Person` holding that number is a member of the
  attributed event, commented *"for UI display"*. **Nothing sets it back to false** —
  `removeOptOut` deletes the row and leaves the flag.
- **Readers:** `resolveManualNudgeRecipient` selects it for `chooseManualNudgeChannel` in
  `src/lib/sms/manual-nudge-recipient.ts`; `selectWrapUpRecipients` carries it into the channel
  choice in `generateWrapUpLinks` in `src/lib/wrap-up.ts`. [[GTC-189]] slice 1's
  `ChooserPerson.smsOptedOut` in `src/lib/eligibility/channel-chooser.ts` takes a boolean of the
  same name and deliberately leaves the choice of fact to its caller (answer 6); it is dark.

**⚠ And a third thing wearing the name.** Both `GET` handlers above return a field called
`smsOptedOut` that is computed from the **table**, and `InviteStatusSection` and
`PersonInviteDetailModal` render it. The `smsOptedOut` the host sees is not the column called
`smsOptedOut`.

**So:** three scopes — per number per host (the table), per person everywhere (the flag), per
number everywhere (the ruling) — and two keys, a phone number and a person.

**Smallest failing case (by reading)**
A guest on two hosts' events replies STOP to host A. The table gains an A row and the flag goes
true. On host B's event the automated paths consult the table, find no B row, and admit the guest
for a text; B's manual nudge and B's wrap-up consult the flag and go by email or skip the text.
**Two answers for one person on one event.** Under the account-wide ruling both should say opted
out.

---

### How they drift apart (by reading)

- **Scope.** The flag is global, the table is per host, the ruling is account-wide.
- **Key.** The flag follows the person when their number changes; the table follows the number to
  whoever holds it next.
- **Clearing.** A row can be deleted; nothing clears the flag.
- **The writer's condition.** The row is written whenever attribution succeeds; the flag only when a
  member of the attributed event holds the number. A STOP whose person is not found writes a row and
  no flag.

### Why it is latent — and why it will not stay latent

- **No live writer of either fact.** [[GTC-229]] audit D records the inbound route as effectively
  dead (Twilio-shaped, and nothing sends it anything) and `manualOptOut` as uncalled. gather_dev,
  measured 2026-09-13: 0 `Person.smsOptedOut` true, 0 `SmsOptOut` rows.
- **It goes live with [[GTC-288]]**, whose TNZ handler writes the opt-out and whose ruled migration
  makes `SmsOptOut` account-wide. That migration fixes the table's scope. It does not, by itself,
  reconcile a flag keyed on a person, or move the readers that consult the flag.
- **And with [[GTC-189]] slices 3, 5 and 8**, each of which passes the chooser a `smsOptedOut`
  boolean and must say which fact it is. That is how answer 6 found it.

### What is already recorded, so it is not re-derived

[[GTC-229]] audit D and [[GTC-288]] name both facts and the inbound handler's write to each, and
[[GTC-288]] rules the table account-wide. **Neither names the flag and the table as competing
answers read by different paths.** That is this ticket.

### Reproduce

**Required state**
- A local database. Two events with different hosts, sharing one guest with an NZ `phoneNumber`.
- Multi-actor: [ ] Yes [x] No — fixture-level.

**Steps**
1. Write what the inbound handler writes for a STOP to host A: an `SmsOptOut` row for
   `(number, hostA)` and `Person.smsOptedOut = true`.
2. Ask the table's gate for host B: `isOptedOut(number, hostB)`.
3. Ask the flag's readers for the same person: `chooseManualNudgeChannel` and
   `selectWrapUpRecipients`.

**Observe:** `isOptedOut` is `false` for host B; `chooseManualNudgeChannel` answers `email`, and
the wrap-up recipient carries `smsOptedOut: true`.

### Scope

**Fix here:**
- Deciding the one fact, and moving every reader named in *Signal* onto it.
- The field name the invite-status and invite-detail routes return.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding. **Zone 7 names both
  `SmsOptOut` and `Person.smsOptedOut`** — explicit approval before any change (Stop Condition 5,
  pre-fired).
- `checkOptOut` inside `sendSms` stays the last gate before a text, whatever the answer.
- [[GTC-288]]'s handler and migration — unless Unknown 1 folds this ticket into them.
- The chooser's signature. It takes a boolean by design (answer 6); its callers change, it does not.
