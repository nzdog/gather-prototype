## Problem

`getCriticalGapCount()` (src/lib/workflow.ts) was dead code with a name/behavior
mismatch:

- Zero callers anywhere in the codebase (re-verified this ticket).
- Named for "critical gaps" but its body counted ALL unassigned items
  (`assignment: null`, no `critical: true` filter).
- Until GTC-156 its doc comment falsely claimed it blocked freeze ("blocking
  freeze (T6)"). GTC-156 corrected the comment, but a corrected comment on an
  uncalled function is still a trap — the function looked load-bearing and
  invited future callers to trust a name that lied about the behavior.

Same species as `canFreeze()` (GTC-154). House position established there:
delete dead code rather than document around it.

## Fix

- Deleted the function and its doc comment (17 lines) from src/lib/workflow.ts.
- Updated the four `workflow.ts:NNN` line references in
  `.claude/skills/gather-architecture-contract/SKILL.md` that shifted up by 17
  as a result (canTransition 243→226, canMutate 265→248, logAudit 289→272,
  runGateCheck 440→423). `checkFreezeReadiness` (107) and the EPIC 4 marker (73)
  sit above the deletion and were unchanged.
- No skill referenced `getCriticalGapCount` by name, so no prose needed updating.

## Zero-callers evidence (pre-deletion)

`grep -rn "getCriticalGapCount" . --include='*.ts' --include='*.tsx'` (excl.
node_modules) returned exactly one hit: the definition at
`src/lib/workflow.ts:225`. No imports, no calls, no tests. All other repo hits
were historical docs under `docs/03_specs/`, `docs/04_roadmap/`, and the GTC-156
ticket — left intact as history.

## Out of scope

If genuine "critical gap" counting is ever needed, that is a new function with an
honest name (e.g. counting `critical: true` items without an ACCEPTED assignment)
under a future ticket — do not resurrect this one.
