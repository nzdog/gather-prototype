# GTC-372 — the clone route treats a User id as a Person id

**Status:** Open — a stub, filed 2026-10-08 on the founder's ruling Q14 at [[GTC-369]]'s plan
(*"stubs at the next free numbers for … C3, the clone route (Q14)"*). C3 in GTC-369. No code now.
Not scoped.
**Severity:** not set — the founder's to set.

### Signal

Found by Claude Code planning [[GTC-369]] (2026-10-08), checking Cowork's evidence that template
clones make the host a team's coordinator. Read at `3b03131`:

- `POST` in `src/app/api/templates/[id]/clone/route.ts` sets `const hostId = user.id`, the signed-in
  `User`'s id, with the comment "Use authenticated user's ID".
- It then compares that with `StructureTemplate.hostId` for a HOST template, looks up
  `prisma.person.findUnique({ where: { id: hostId } })` and answers 404 "Host not found" when there
  is none, and passes the same id on as the new event's host and as each team's `coordinatorId`
  ("Host is initial coordinator"), and to the `QuantitiesProfile` lookup.
- `User` and `Person` are different tables with different ids (`Person.userId` links them). So the
  route 404s for any host whose Person id differs from her User id — every real one — and, where it
  does run, writes a User id into Person-id columns.

`Event.hostId` and `Team.coordinatorId` hold Person ids elsewhere in the tree (the
`coordinatorId: event.hostId` sites in the setup page and the old dashboard, and
`execute-resolution`).

### For the plan (Claude Code's note, not a ruling)

- Resolve the host's Person from the User (`personForUser` in `src/lib/auth/actor.ts`, or the
  user's Person on the template's event) and use its id for the host, the coordinators and the
  template ownership check; check what `StructureTemplate.hostId` actually stores before choosing.
- Measure first: how many `StructureTemplate` rows exist and what their `hostId` points at.
- Not a GTC-369 concern: after GTC-369 a Person id is no longer a sign-in key.
