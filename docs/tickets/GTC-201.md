### Context

[[GTC-196]] (A3b) wired `recordChange()` into every path that can fire a why-scope trigger — T1
through T5 — and deliberately deferred the rest. The ledger is therefore **complete for every change
that touches someone, and incomplete for some that touch nobody.**

That is a coherent place to stop for one ticket and an incoherent place to merge from. "Versions —
universal, silent, per-change" (Hinge §2) is universal across change *types*, not just the
interrogated ones: a host who renames a team or regenerates a plan should find that step in her
history like any other.

**The pattern is settled.** A3b left eight worked examples covering every shape this ticket needs;
none of the work below is a design decision, and any site that turns out to need one is a
stop-and-report.

### The eight worked examples to copy from

| Shape | Reference implementation |
|---|---|
| Single field-scoped edit, host session | `PATCH /api/events/[id]/items/[itemId]` |
| Single field-scoped edit, coordinator token | `PATCH /api/c/[token]/items/[itemId]` |
| Whole-entity create | `POST /api/c/[token]/items` |
| Whole-entity delete with claim context | `DELETE /api/events/[id]/items/[itemId]` |
| Assignment create/move + release hook | `POST /api/events/[id]/items/[itemId]/assign` |
| Assignment delete + release hook | `DELETE /api/c/[token]/items/[itemId]/assign` |
| Multi-field diff via `fieldChanges()` + material hook | `PATCH /api/events/[id]` |
| **Bulk changeSet** (one id, one reason, N entries) | `restoreFromRevision()` in `src/lib/workflow.ts` |
| Domain-function wiring, inherited by every caller | `removePerson()` in `src/lib/workflow.ts` |

Actor helpers: `actorFromToken()` / `SYSTEM_ACTOR` in `src/lib/ledger.ts`, `ledgerActorForUser()` in
`src/lib/auth/actor.ts`.

## Scope — the deferred sites

### 1. The AI generation trio — bulk changeSets

`api/events/[id]/generate/route.ts`, `.../regenerate/route.ts`, `.../finalize-plan/route.ts`

These replace or populate the whole plan, so they take the **bulk** shape: one `PlanRevision`
checkpoint, one `changeSetId`, one reason, N entries. `regenerate` already calls `createRevision` —
keep it, add the ledger.

⚠ **Post-send regenerate is the ruled (a)-now-(c)-later case.** The server allows it and records it;
[[GTC-197]] (A3c) ships the consequence line *"This replaces the plan people have claimed against"*
before the act. **The two must merge together** — allowing the act without the warning ships half a
ruling. Verify A3c's copy is present before closing.

### 2. Person and household paths

| Route | Shape |
|---|---|
| `api/events/[id]/people/batch-import` | Per-person `ADD_PERSON` entries under one bulk changeSet |
| `api/events/[id]/people/auto-assign` | Per-assignment `CREATE_ASSIGNMENT` entries, one changeSet. **T1 fires per entry** — auto-assign post-send touches everyone it assigns |
| `api/events/[id]/people/[personId]/manual-override` | `EDIT_EVENT`-class; versioned only |
| `api/h/[token]/people/[personId]/manual-override` | Same, token actor |
| `api/events/[id]/households` + `.../[householdId]` | Member diffs via `reconcileHouseholdMembers()` |

⚠ `reconcileHouseholdMembers()` still runs **non-transactionally** (discovery report §5, plan §4.4).
`recordChange` requires a `tx`. Wrapping it is the right fix and is in scope; if it resists, that is
a stop-and-report, not a reason to write the ledger entry outside the transaction.

⚠ **auto-assign may be the one genuine surprise here.** If it assigns in bulk post-send, every
assignment is a T1 that owes a why, and there is no natural place for the host to give one. Options
are a single set-level reason, or none with `reasonRequired: true` recorded honestly. **Raise it
rather than choosing silently.**

### 3. Item and conflict paths

`api/events/[id]/teams/[teamId]/items` (create), `.../review-items`, `.../items/mark-for-review`,
`.../conflicts/[conflictId]/execute-resolution`, `api/templates/[id]/clone`.

`execute-resolution` mutates assignments and items to resolve a conflict — check each resolution
class for T1/T3 triggers rather than assuming versioned-only.

### Do not touch

- Guest-side response routes (`p/ack`, `c/ack`, `join/claim`'s response half). They write
  `InviteEvent` by design — Moment 4 §7: responses *"are not the plan changing; they are the plan
  being answered."* Settled in A3b; do not revisit.
- The why-scope rule itself. If a site seems to need a new trigger, that is a spec question — stop.
- UI — [[GTC-197]] / [[GTC-198]].
- All Do-Not-Touch Zones.

### The two flagged items, handled as decisions

**1. `reconcileHouseholdMembers` — IMPLEMENTED (correctness fix).**

It performs six-plus dependent writes — a `Person` update, a `PersonEvent` update, a `Household`
update, then per-member updates, creates and deletes — and ran them as **sequential awaits with no
transaction**. A failure part-way left a household half-reconciled: some members renamed and others
not, some deleted with their replacements never created.

That has been on record as GTC-159's residual risk since July 2026 (discovery report §5). **Wiring
the ledger forced the fix**, because `recordChange` requires a `tx`: an entry that survives a
rolled-back write describes something that never happened. The signature now takes
`Prisma.TransactionClient` and the route wraps it.

**2. `auto-assign` — STOPPED, ruled, then implemented.**

Presented rather than guessed. Ruled option **(a)**: one why for the batch, per-changeSet — N
entries, one `changeSetId`, one reason, each flagged `reasonRequired`. The shape
`restoreFromRevision` and `regenerate` already use.

**Option (c) — a system-authored reason — was explicitly rejected**, and the rejection is recorded at
the call site rather than only in a ticket. The route already computes
`"Even distribution (3 members before assignment)"` per assignment and writing that into `reason`
would have been trivial. It is true, and it is the wrong thing: the ledger is Kate's memory (Hinge
§2 — *"the reason is not compliance — it's her own memory"*), and **a generated string that looks
like an answer makes the gap invisible**. An honest null beats a plausible lie.

### The underneath-thing: UI absence, not server block

Reading the route surfaced something bigger than the reason question: post-send, auto-assign creates
N asks at once — and until mini-send machinery exists, **nobody it asks would ever be told**.

Ruled: **UI absence, not a server block.** The server allows and records it (Moment 4 §7 forbids
hard-blocking the host); the host UI does not offer it on a sent event. Asking someone silently is
worse than not offering the button.

The tombstone at `src/components/plan/PeopleSection.tsx` names its own expiry — [[GTC-189]] (I2, the
press, which owns mini-sends) and [[GTC-178]] (E1, the cadence those clocks run on) — and says
exactly what to delete. **[[GTC-189]] now carries the matching note**, so the dependency is recorded
from both ends and neither side can quietly forget it.

### Found and wired beyond the ticket's list

**The press is now the ledger's first entry.** Both `confirm-invites-sent` routes emit
`SEND_PRESSED`. Moment 4 §7 — *"The audit trail starts at the send"* — so the entry marking the
threshold belongs in the history it opens. Not in the ticket; it fell out of the sweep.

`events/[id]/people/[personId]` DELETE also needed its own T2: it performs its removal inline rather
than calling `removePerson()`, so it did not inherit that helper's wiring.
