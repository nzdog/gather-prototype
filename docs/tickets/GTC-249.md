# GTC-249 — Vegan and nut-allergy dietary categories have no structured coverage check

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** not scoped — this
ticket records a finding and a risk. No fix is proposed here.

### Context

Surfaced as open decision 3 during the [[GTC-184]] Phase 1 audit, split out rather than
resolved by founder ruling (2026-08-23) — see [[GTC-184]]'s "Not settled here" note.

The Moment 2 dietary checklist (`DietaryAccordion` in `Moment2Step1Modal.tsx`) offers five
fixed options: `DIETARY_OPTIONS = ['Vegetarian', 'Vegan', 'Gluten-free', 'Dairy-free', 'Nut
allergy']` (`Moment2Step1Modal.tsx:148`). Of these, only three have a structured field on
`Item` to check coverage against: `Item.vegetarian`, `Item.glutenFree`, `Item.dairyFree`
(`schema.prisma:298-300`). **Vegan and Nut allergy have no corresponding `Item` boolean.** The
only place either could be represented is `Item.dietaryTags` — an unstructured `Json?` column
(`schema.prisma:301`) — and nothing currently reads it for coverage-checking purposes.

**The risk, stated plainly:** a host can tick "Nut allergy" on the Moment 2 dietary
checklist, believing (reasonably — the UI presents it alongside the other four options with no
visible distinction) that the same coverage machinery applies to it as to vegetarian or
gluten-free. No coverage check is possible against it today, structurally, regardless of
whether [[GTC-184]]'s repoint or [[GTC-228]]'s post-generation verification land. A ticked box
implies a check happened. For "Nut allergy" specifically, that gap is safety-relevant, not
merely a UX inconsistency — an allergy is a different risk category from a preference.

**Separate finding, same investigation:** `detectDietaryGaps` in `src/lib/ai/check.ts` has
never read `Event.dietaryVegan` or `Event.dietaryDairyFree` — both are dead inputs to it at
HEAD (only `dietaryVegetarian` and `dietaryGlutenFree` are read, at `check.ts:188` and
`check.ts:214`). Confirmed independently twice: by the [[GTC-184]] Phase 1 audit (2026-08-23)
and, eleven days earlier, by `docs/04_roadmap/moment4-hinge-report-accuracy-audit-2026-08-04.md`
row G-3, which cites the same gate by line (`check.ts:187,213` at that commit). This predates
and is independent of [[GTC-184]]'s repoint — it was already true of the legacy-field version
of the function, and (per [[GTC-184]]'s decision 1) is not something the repoint sets out to
fix, since the repoint targets which *model* is read, not which *categories within it* are
checked.

### Scope

**No fix proposed here.** This ticket exists to record the finding and the risk so it is
visible rather than rediscovered. Do not propose a fix. Do not implement.

A future scoping pass would need to decide, at minimum: whether Vegan/Nut-allergy coverage
should be checked against `Item.dietaryTags` (which would require defining a write-side
convention for that field first — nothing currently writes it in a form a coverage check could
read), whether the checklist UI should visually distinguish checkable from unchecked
categories in the meantime, and how this interacts with [[GTC-228]]'s post-generation coverage
verification (out of scope there too — GTC-228 explicitly excludes free-text and does not
address which of the five categories it covers).

**Do not touch:** nothing is being changed by this ticket.

### Dependencies

None to file this ticket. A future fix would need [[GTC-184]] to have landed first (it
determines which model `detectDietaryGaps` reads at all), but that is a note for the fix, not
a blocker on recording the finding.

### Acceptance

None — this ticket documents a finding, not a change. Acceptance criteria will be written when
a fix is scoped in a future pass.

### Stop Conditions

Not applicable until this ticket is scoped for implementation. When it is, the standard eight
from `BUG-TICKET-TEMPLATE.md` apply, plus: if the fix direction turns out to require writing to

of that field before proceeding (unaudited here).
