**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low

the guest receives a channel the host did not choose.

**Rewritten 2026-08-15**, replacing the stub filed under `audit-2026-08-04`. The stub's
stated reason was false; see *What the stub got wrong*. Scoped by re-derivation from code

## Signal

**Expected**

`sendSms` in `src/lib/sms/send-sms.ts` owns provider selection: `shouldUseTnz` routes
`TNZ_COUNTRY_CODES` (`+64`, `+61`) to TNZ, everything else to Twilio, and each arm checks
only its own provider's configuration. Callers should hand it a destination and let it
decide. A nudge to a valid NZ number should be attempted whenever TNZ is configured,
regardless of whether Twilio is.

**Actual**

Three callers check `isSmsEnabled` from `src/lib/sms/twilio-client.ts` — the **Twilio**
predicate, computed once at module scope from `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`
and `TWILIO_PHONE_NUMBER`. It knows nothing about TNZ. On a TNZ-only deployment all three
refuse to send, and each fails in a different, wrong way:

1. `runNudgeScheduler` in `src/lib/sms/nudge-scheduler.ts` early-returns **before its
   `try` block**, so `findNudgeCandidates`, `processNudges`, `findRsvpFollowupCandidates`,
   `processRsvpFollowupNudges`, `findProxyNudgeCandidates` and `processProxyNudges` never
   run. All three nudge families die together, before any query is issued.
2. `POST` in `src/app/api/events/[id]/trigger-nudges/route.ts` returns
   `400 "SMS is not configured"`.
3. `POST` in `src/app/api/events/[id]/people/[personId]/nudge/route.ts` — **the worst of
   the three.** Its `canSms` expression ANDs *"the number is a valid NZ number"* with
   *"Twilio is configured"*. When Twilio is absent, `canSms` is false and control falls
   through to `sendNudgeEmail` (`src/lib/email.ts`), or to
   `400 "No contact method available"` if the guest has no email address. The host presses
   nudge, receives `{ success: true, contactMethod: 'email' }`, and a guest with a perfectly
   good mobile number gets an email instead. Nothing in the response says the SMS was never
   attempted.

**And the failure is invisible to monitoring.** `runNudgeScheduler` returns
`smsEnabled: false` inside a `NudgeRunResult`, and `GET` in
`src/app/api/cron/nudges/route.ts` spreads that into `{ success: true, ...result }` and
returns HTTP 200. A monitor watching status code or `success` sees a healthy cron that has
sent nothing. The same route reports `success: true` / 200 when `runNudgeScheduler`'s
`catch` fires, too — a caught run-level exception is also reported as healthy.

**Smallest failing case**

With `TNZ_AUTH_TOKEN` set and `TWILIO_*` absent, a host presses "Nudge" on a guest whose
`phoneNumber` is a valid `+64` mobile: the guest receives an email, not a text.

## The invariant, recorded

**`Person.phoneNumber` is `+64`-or-null by construction.** Every production writer routes
through `normalizePhoneNumber` in `src/lib/phone.ts`, which returns `null` for anything
that fails `isValidNZNumber` (`/^\+64\d{8,10}$/`). Five modules, seven write sites:

| Writer | Sites |
|---|---|
| `POST` in `src/app/api/events/[id]/people/route.ts` | 1 |
| `PATCH` in `src/app/api/events/[id]/people/[personId]/route.ts` | 1 |
| `createMember` (inside `POST`) in `src/app/api/events/[id]/households/route.ts` | 1 |
| `PATCH` in `src/app/api/p/[token]/contact-info/route.ts` | 1 |
| `reconcileHouseholdMembers` in `src/lib/households/reconcileMembers.ts` | 3 |

**It is EMERGENT, not enforced.** This is the load-bearing half of the finding:

- **No database constraint.** `Person.phoneNumber` is `String?` in `prisma/schema.prisma`.
  Nothing but developer habit holds the invariant.
- **Two scripts already violate it.** `scripts/seed-rsvp-test.ts` writes
  `phoneNumber: '+12025551234'` — a US number, valid E.164, non-`+64`.
  `scripts/seed-gtc-133-test-event.ts` writes `phoneNumber: '0211234567'` — local format,
  not E.164 at all. Both write through `prisma.person.create` directly, bypassing
  `normalizePhoneNumber`.
- **There is a second phone field, and it is never normalised.** `Person.phone` exists
  alongside `phoneNumber`. `POST` in `src/app/api/events/[id]/people/batch-import/route.ts`
  writes raw user input to it with no normalisation, and sets `reachabilityTier: 'DIRECT'`,
  `contactMethod: 'SMS'` on the strength of it.

Consequence: **an argument of the form "the Twilio branch is unreachable because everything
is `+64`" cannot be made.** The invariant is a convention with two known violators and an
un-normalised sibling field. This is why the fix is *delete the caller-side gates and let
`sendSms` route per destination*, and not *widen them to `isSmsEnabled() || isTnzEnabled()`* —
a widened gate would still be answering the wrong question, just less often.

### Ruling 1 — `validateTwilioSignature` is deleted, not wired

`validateTwilioSignature` in `src/lib/sms/twilio-client.ts` has **zero callers** at

the inbound path belongs to GTC-229, which is blocked on TNZ and will need TNZ's own

"nearly-wired security" is worse than having none: it reads as though the inbound path is
protected.

Recorded so **GTC-225 does not re-decide it.**

### Ruling 2 — the Twilio branch in `sendSms` IS reachable

This answers [[GTC-225]]'s Phase 3 acceptance criterion — *"a recorded conclusion on
whether the Twilio branch in `sendSms` is reachable from any nudge path, derived by tracing
the code"* — and it was permitted to conclude "reachable". It does. **Derived at
`a44aeab`, two live paths:**

1. **Wrap-up.** `generateWrapUpLinks` in `src/lib/wrap-up.ts` selects
   `person.phoneNumber || person.phone` with **no NZ or E.164 gate of any kind**, and

   `Person.phone` is written raw by batch-import (above), any non-`+64` E.164 value there

**Therefore the Twilio arm of `sendSms` stays.** Removing it is a product decision about
whether Gather sends outside NZ/AU at all, not cleanup, and is explicitly out of scope here.

## `smsConfigured` is destination-agnostic — found during execution, then fixed

**Found mid-execution with live evidence, surfaced, and ruled IN by the founder on
2026-08-15: tighten it here rather than defer it.**

`smsConfigured` is `isTnzEnabled() || isSmsEnabled()`: *some* provider is configured. It
does not ask whether the provider that would carry **this run's** traffic is configured.
One configuration slips through:

> **Twilio set, TNZ absent** — every nudge candidate is `+64`, routes to the TNZ arm, and
> fails `SMS_DISABLED`. `smsConfigured` is `true` because Twilio is set, so `ok` is `true`
> and the cron returns HTTP 200 `success: true`.

This is the local dev configuration, so it is observable rather than hypothetical. Live
against the dev server at execution time:

```json
{ "success": true, "ok": true, "smsConfigured": true,
  "candidates": { "eligible24h": 1, "eligible48h": 1 },
  "results": { "sent": 2, "succeeded": 0, "failed": 2 },
  "errors": ["Nudge Candidate Live: TNZ not configured (TNZ_AUTH_TOKEN missing)",
             "Nudge Candidate Live: TNZ not configured (TNZ_AUTH_TOKEN missing)"] }
```

Two candidates, two failures, and a monitor keyed on status code or `success` still saw a
healthy cron — the same failure mode this ticket exists to fix, one layer further in.

**The fix.** `ok` also goes false when the run attempted sends and *every* one failed,
expressed as the pure `isNudgeRunHealthy` in `src/lib/sms/nudge-scheduler.ts`. The three
boundaries that keep it from becoming noise, each asserted:

| Situation | Verdict | Why |
|---|---|---|
| No provider configured | unhealthy | nothing it attempts can succeed |
| Configured, nothing to send | **healthy** | an idle cron is a working cron |
| Configured, every send failed | unhealthy | the hole above |
| Configured, partial failure | **healthy** | one bad number must not flap the alert |
| Quiet-hours deferral | **healthy** | `attempted` counts sends, not candidates — deferring *is* the machinery working |

Same request after the fix, unchanged in every other respect:

```json
{ "success": false, "ok": false, "smsConfigured": true,
  "results": { "sent": 2, "succeeded": 0, "failed": 2 } }      // HTTP 500
```

**Why the verdict is a pure exported function rather than an inline expression.** Provider
configuration is captured at module scope, so any one process can only ever observe one
quadrant of this table — the live cron cannot demonstrate the rule, only one instance of
it. `isNudgeRunHealthy` is the seam where the rule itself is assertable.

TNZ go-live removes this configuration from production. It does not remove it from dev,
where it is exactly what a developer sees.
