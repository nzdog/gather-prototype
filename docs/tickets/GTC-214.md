# GTC-214 — STUB: Delete the caller-side Twilio gate on the nudge paths

**Status:** Open — stub, needs full scoping when pulled | **Effort:** TBD

## ⚠ MOOT UNTIL TNZ GOES LIVE — attach to the TNZ go-live checklist, NOT the current sprint

The TNZ account is **not currently live**. Production has **both** TNZ and Twilio credentials
set, so the gate described below **passes today** and the nudge cron runs. **This is correctness
cleanup, not a live outage.** Do not file it as an incident, do not pull it into the current
sprint, and do not write a production-incident narrative around it — the first audit's
"the nudge cron sends nothing in production" framing asserts an environment state nobody has
observed, and the only readable environment is the opposite configuration.

Attach this to the **TNZ go-live checklist**. It becomes real the moment a deployment is
TNZ-only.

### Scope

The nudge machinery is gated on a **Twilio credential-presence check** while every nudge
recipient is forced to a `+64` number that routes to **TNZ**.

- **The gate:** `src/lib/sms/nudge-scheduler.ts:50` `if (!isSmsEnabled())`. `isSmsEnabled`
  (`twilio-client.ts:23-25`) returns a module-scope boolean computed once at `:9` from
  `TWILIO_ACCOUNT_SID && TWILIO_AUTH_TOKEN && TWILIO_PHONE_NUMBER`. It knows nothing about TNZ.
- **Blast radius is total, not partial.** The `try` block starts at `:60`, so the early return at
  `:51-58` skips `findNudgeCandidates`, `processNudges`, `findRsvpFollowupCandidates`,
  `processRsvpFollowupNudges`, `findProxyNudgeCandidates` and `processProxyNudges`. **All three
  nudge families die together, before any query runs.**
- **It fails silently.** `cron/nudges/route.ts:29-32` returns `{ success: true, ...result }` →
  HTTP 200 with `smsEnabled: false`. Monitoring on status code or `success` sees a healthy cron.
- **The blocker is in the caller, not the sender.** `send-sms.ts:98-105` checks `isTnzEnabled()`
  for a `+64`/`+61` destination and never calls `isSmsEnabled()`. `sendSms` would dispatch to TNZ
  with Twilio entirely unconfigured.

**Three call sites, not one:** `nudge-scheduler.ts:50`, `trigger-nudges/route.ts:24`, and
`people/[personId]/nudge/route.ts:97-101`.

**The fix is to DELETE the caller-side checks, not widen them.** Eligibility already forces
`+64` at every entry — `nudge-eligibility.ts:164` and `:315`, `proxy-nudge-eligibility.ts:103`,
all via `isValidNZNumber` = `/^\+64\d{8,10}$/` (`phone.ts:34-38`). So `send-sms.ts:107`'s Twilio
branch is **structurally unreachable from any nudge path**: these three checks guard a provider
no nudge can ever use. Widening them to `isSmsEnabled() || isTnzEnabled()` would leave a subtler
wrong answer in place. Let `send-sms.ts:98-117` own provider selection — it already does.

**Provenance:** the gate is original to the feature (`b3841a0`, 2026-01-23); TNZ routing arrived
2.5 months later (`01962a9`, 2026-04-09) touching only the constants doc, the ticket,
`send-sms.ts`, `tnz-client.ts` and a test. **The callers were never revisited.** A stale guard
after a provider split.

**Adjacent, same file family, worth folding in:** `.env.example` (55 lines) documents the Twilio
block at `:38-44` and never mentions `TNZ_AUTH_TOKEN`, while `GATHER-BUILD-CONSTANTS.md:210`
lists it as required for production NZ delivery — two tracked files contradicting each other.
And `nudge-scheduler.ts` returning `success: true` with `smsEnabled: false` is its own defect
regardless of the gate.

### Needs full scoping when pulled

This is a stub, and it should **not** be pulled before TNZ go-live. When it is, it needs: a
ruling on whether the three checks are deleted outright or replaced by a destination-aware
check, the `success: true` / `smsEnabled: false` response fix, the `.env.example` / constants
reconciliation, acceptance criteria, and a `/effort` run. Verify the production variable state
at that point rather than trusting this stub's snapshot. **Do not execute from this stub.**
