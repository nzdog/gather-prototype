# GTC-177 — D4: Green-reverting — guest withdrawal reopens the item

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** high

*Effort level is a proposal from the discovery-report ticket breakdown — run `/effort` manually
before execution.*

### Context

Moment 4 spec §8.6: green can un-happen, and it goes straight to Kate. A withdrawn or broken claim
(Sarah's ankle, three days out) reverts red at once, through the standard door — no re-entry into
nudge machinery, no fresh cadence. "This isn't a silence to chase, it's a fact the system can't
fix — it notes it and sends it to her." If the reverted item is critical, the badge is already on
the box and the assistant's message fires.

Today: a guest can flip `Assignment.response` to `DECLINED` via `p/[token]/ack/[assignmentId]`,
but this only updates the field — `Item.status` stays `ASSIGNED`, the item never reopens for
reassignment, and the host isn't specially notified beyond an audit log line. Only a
host-initiated `DELETE` reopens an item today.

### Scope

**Fix here:**
- Wire guest-initiated withdrawal to actually reopen the item (`Item.status` →
  `UNASSIGNED`/equivalent via `repairItemStatusAfterMutation` or D1's successor state).
- Route the reversion directly to the host — not through nudge machinery, per the "standard door."
- Fire the critical-item assistant message if the reverted item is critical (badge already
  present per B1/J2).

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The nudge cadence machinery — explicitly not re-entered per this ruling; do not add a fresh
  cadence for a reverted item.

### Dependencies

D1 (GTC-174).

- [ ] A critical item's withdrawal fires the assistant's one plain message.
