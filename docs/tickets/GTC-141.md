# [[GTC-141]] — Plan view row interaction redesign — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** _(see git log)_

## What was found

`Moment2PlanView` rows had no visible affordances at rest. Of the five
row-level interactions (edit name, edit quantity, reorder up, reorder down,
remove), only quantity edit had any resting affordance — and even that was
only a hover-bg signal. The name-click was invisible (looked like static
text), reorder arrows were `opacity-0 group-hover:opacity-100` (useless on
touch), and remove was buried inside the inline edit form (two clicks deep
and unreachable without first guessing the name-click).

Surfaced during [[GTC-133]] sub-commit (g) browser verification — host couldn't
see how to edit or delete plan items without prior knowledge of the UI.

## What was changed

### Row layout (left → right)

- Item name + serving size stacked vertically (`flex-1 min-w-0 flex flex-col`,
  `break-words` on long names so they wrap rather than truncate).
- Quantity badge — unchanged, still tap-to-edit.
- "Edit" button — always visible, opens the existing inline `ItemEditForm`.
- "Quick delete" button — always visible, immediate single-item removal.
- "Mark for delete" button — always visible, toggles per-row marked state.

### Marked-for-delete state

- First click on "Mark for delete" → row's name, serving size, quantity badge,
  "Quick delete" label, and "Mark for delete" label all get
  `line-through text-gray-400`. Item id is added to `selectedItemIds: Set<string>`
  in parent state.
- "Edit" label deliberately stays un-struck so the edit affordance still reads
  as active on a marked row.
- Second click on the same row → strikethrough removed, id dropped from set.

### Floating bulk-action button

- `fixed right-4 top-1/2 -translate-y-1/2 z-40`, red pill with inline trash SVG.
- Renders only when `selectedItemIds.size > 0`.
- Label: `Delete 1 item now` / `Delete N items now` (plural-correct).
- Click → loops sequentially through `onRemoveItem` for each id (no batch
  endpoint exists), clears selection, toasts `Removed N items.` Disabled
  while the bulk operation is in flight.

### Removed entirely

- Reorder arrows (▲▼) and full prop chain: `handleMoveItem`, `onMoveItem`,
  `isFirst` / `isLast` / `onMoveUp` / `onMoveDown`, the `onReorderItem` prop
  on `Moment2PlanViewProps`, and the 71-line `onReorderItem` handler block in
  `src/app/plan/[eventId]/page.tsx`.
- An earlier checkbox + "Tick items to select for bulk removal" instruction
  line approach (built then replaced once the button-driven model proved
  clearer in browser verification).

### Selection state housekeeping

- Single-item remove (Quick delete or the existing red Remove button inside
  `ItemEditForm`) also drops the id from `selectedItemIds` if present, so
  the floating button counter stays accurate after a single delete.
- Bulk remove clears the whole set.
- Component remount → empty selection (default `useState`).

## Per-session design decisions

- **Reorder removed entirely** — user is on laptop, doesn't need reorder.
  Hidden-by-default `opacity-0` pattern was unsalvageable on touch and the
  use case wasn't strong enough to justify a different reorder mechanism.
- **No instruction line** — button labels (`Quick delete`, `Mark for delete`,
  `Delete N items now`) carry the explanation. The earlier "Tick items to
  select for bulk removal" line was redundant once the buttons replaced the
  checkbox.
- **Name-click stays** as a redundant edit trigger. Costs nothing, helps
  users who land on it.
- **Remove inside `ItemEditForm` stays** as a redundant path (Phase 8
  decision — Option A).
- **Quick delete has no confirmation step**. Draft plans are low-stakes; if
  accidental removal becomes a problem, a future ticket can add a toast-with-
  undo.
- **Strikethrough scope** extends to all of name, serving size, quantity
  badge, "Quick delete" label, and "Mark for delete" label — but **not**
  the "Edit" label, so the edit affordance still reads as active on a
  marked row.

## Browser verification

All scenarios passed:
- Row renders with new layout (name+notes stacked, qty badge, Edit, Quick
  delete, Mark for delete).
- Name and serving size display in full; long names wrap to second line.
- Click "Edit" → inline form opens.
- Click "Quick delete" → item removed immediately.
- Click "Mark for delete" → row's name+notes+qty+Quick-delete+Mark-for-delete
  labels go strikethrough; floating "Delete 1 item now" appears.
- Mark a second row → counter updates to "Delete 2 items now".
- Click "Mark for delete" on a marked row → strikethrough removed, counter
  decrements (button hides at 0).
- Click floating "Delete N items now" → all marked items removed in one go,
  floating button disappears.
- No reorder arrows in DOM.

## Known limitations

- Bulk delete uses N sequential HTTP `DELETE` requests against
  `/api/events/[id]/items/[itemId]`. Slow for large selections but correct.
  No batch endpoint exists; deferred to a future ticket if it becomes a
  performance problem in practice.
