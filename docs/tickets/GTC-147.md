# GTC-147 — Schema fix: PersonEvent.team Cascade → SetNull — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** [pending approval]

**Severity:** Critical (data-loss landmine on every V2 event)
**Surfaced by:** External code review (v1-v2 reconciliation review, section 2 finding upgrade — `docs/v1-v2-reconciliation-review.md`, "one finding the brief missed").

### What was found

`PersonEvent.team` declared `onDelete: Cascade` (`prisma/schema.prisma:170`). Deleting any Team therefore deleted the PersonEvent row of every person placed on it — removing them from the event entirely: household membership, RSVP state, and (via the `NudgeLog.personEventId` cascade) their whole nudge history.

Phase 1 audit found **six** team-deletion call sites, and none relies on the cascade removing PersonEvents:

1. `src/app/api/events/[id]/teams/[teamId]/route.ts:36` — V1 delete-team endpoint. Comment expects only the Item cascade. **Fired the landmine**: deleting a team from the UI silently deleted its members.
2. `src/app/api/events/[id]/route.ts:201` — event-deletion transaction. Deletes PersonEvents explicitly via `tx.personEvent.deleteMany({ eventId })` a few lines later; never depended on the team cascade.
3. `src/app/api/events/[id]/finalize-plan/route.ts:272` — the ticket's trigger. `team.deleteMany({ eventId, source: 'GENERATED' })` on every re-run; never touches PersonEvents.
4. `src/app/api/events/[id]/regenerate/route.ts:94` — deletes empty unprotected teams (members can still reference an "empty" team — items empty ≠ members empty). **Landmine.**
5. `src/app/api/events/[id]/regenerate/route.ts:102` — full-regen path deletes **all** teams for the event. **Landmine on the V1 path too.**
6. `src/lib/workflow.ts:910` — revision restore deletes all teams; team-membership restoration is explicitly unimplemented (TODO at `workflow.ts:942–943`), so nothing recreates or depends on the removed rows.

`PersonEvent.teamId` was already nullable (`String?`, `schema.prisma:154`) — no blocker for SetNull. (Ticket text said `Int?`; the column is a cuid `String?`. Immaterial to the fix.)

RED demonstration (before the change, seeded dev DB): deleting the seeded "Starters & Nibbles" team (7 members) dropped the event's PersonEvents from **43 → 36**; 0/7 preserved.

### What was changed

One relation, `prisma/schema.prisma` (PersonEvent model):

```prisma
// Before:
team  Team?  @relation(fields: [teamId], references: [id], onDelete: Cascade)
// After:
team  Team?  @relation(fields: [teamId], references: [id], onDelete: SetNull)
```

Plus the regression/verification script `tests/verify-personevent-team-setnull.ts` (destructive; run only against a re-seedable dev DB, matching the existing `tests/verify-*.ts` pattern).

Nothing else touched. The `finalize-plan/route.ts:272` deleteMany itself is a separate future ticket (diff-based write pattern, per review section 2(b)).

### Migration

`prisma/migrations/20260708005434_change_person_event_team_set_null/migration.sql`, generated with `prisma migrate dev --name change_person_event_team_set_null --create-only`, reviewed before apply. Contents — one FK constraint swap, no data statements:

```sql
-- DropForeignKey
ALTER TABLE "PersonEvent" DROP CONSTRAINT "PersonEvent_teamId_fkey";
-- AddForeignKey
ALTER TABLE "PersonEvent" ADD CONSTRAINT "PersonEvent_teamId_fkey"
  FOREIGN KEY ("teamId") REFERENCES "Team"("id") ON DELETE SET NULL ON UPDATE CASCADE;
```

Rollback: re-alter the constraint back to `ON DELETE CASCADE` (equally a single statement; no data movement either way).

### Known limitations

- People un-placed by a team deletion are silently unassigned; no UI surfaces "N people lost their team placement." Acceptable per ticket intent (hosts re-place or leave unassigned); a future UX pass could surface it.
- The environment's dev DB was created fresh for this work; the P3005 drift condition documented in GATHER-BUILD-CONSTANTS.md was not present here. On the drifted `gather_dev` instance, apply with `prisma migrate deploy` (single ALTER, safe on live data) rather than `migrate dev`.
