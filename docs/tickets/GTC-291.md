# GTC-291 — the Stripe webhook is classified PUBLIC, and its evidence says nothing

**Status:** Open — **filed on a founder ruling, not yet executed.** Filed 2026-09-12 |
**Branch:** TBD
**Severity:** [ ] Critical [ ] High [ ] Medium [x] Low
Escalated (brand/trust risk): [ ] No — nothing is unguarded. The route is verified; the
record of it is wrong, and a security record that understates a real control is the kind of

**Filed 2026-09-12** during [[GTC-264]] Phase 0, when that ticket needed to choose an
`authType` for a new webhook and found the only in-tree webhook precedent understating
itself. Tree verified at `0dc7be1`.

**⚠ Split out deliberately, on the founder's ruling: "the Stripe entry gets its own

explicitly declines to inherit the understatement. This ticket owns the correction.

---

## The defect

`route-classifications.json` at the repo root records:

```json
{
  "filePath": "src/app/api/webhooks/stripe/route.ts",
  "apiPath": "/api/webhooks/stripe",
  "methods": ["POST"],
  "authType": "PUBLIC",
  "authEvidence": ["webhook endpoint"],
  "securityIssues": []
}
```

**Both fields are wrong, in different ways.**

`authType: "PUBLIC"` says the route has no credential. It has one, and it is verified:
`POST` in `src/app/api/webhooks/stripe/route.ts` reads the `stripe-signature` header,
refuses `400` when it is absent, refuses `400` when `STRIPE_WEBHOOK_SECRET` is unconfigured,
and calls `stripe.webhooks.constructEvent(body, signature, STRIPE_WEBHOOK_SECRET)` inside a
`try`, refusing `400` on a verification failure.

`authEvidence: ["webhook endpoint"]` is not evidence. It states the route's category, not
what guards it. Compare the neighbouring entries, which name mechanisms — `"cookie session
check"`, `"auth flow endpoint (intentionally public)"`.

**The scanner already disagrees with the file, and the scanner is right.**
`npm run security:routes` reports this handler as `SIGNATURE` with the detail
`stripe.webhooks.constructEvent` and the proof `PROVEN`, and
`tests/security-route-scan-control.ts` pins it in `HEAD_VERDICTS` as
`'POST src/app/api/webhooks/stripe/route.ts', false, 'SIGNATURE:PROVEN'`. So the tree holds
two records of this route's authentication and they contradict each other. The hand-written
one is the wrong one.

---

## Why it is worth a ticket rather than a one-line edit

Because it was about to be copied. [[GTC-264]] adds the second webhook this repo has ever
had and went looking for the precedent. Had it followed this entry, the delivery-receipt
endpoint — a shared-secret-authenticated route that fails closed — would have been recorded
`PUBLIC` with the evidence `"webhook endpoint"`, and the file would then hold two
understatements instead of one, with the second citing the first.

That is the same failure shape as the two provenance findings in
`docs/05_ops/tnz-inbound-and-delivery-correspondence-2026-08.md`: a claim that is compact and
quotable travels, and the caution does not travel with it. Here there was no caution at all.

## Scope

**Fix here:**

- The `authType` and `authEvidence` for `src/app/api/webhooks/stripe/route.ts` in
  `route-classifications.json`.

**And one ruling this ticket must get rather than assume.** The available values are
`PUBLIC`, `SESSION`, `TOKEN`, `NONE` and `CUSTOM`. **None of them means "signature".** So the
correction is a choice between two shapes and it should be ruled, not picked:

- **`CUSTOM`**, with `authEvidence` naming the mechanism —
  `"stripe signature verification via stripe.webhooks.constructEvent"`. Consistent with what
  [[GTC-264]] was ruled to use for its own webhook. Requires no schema change to the file.
- **A new `authType` value**, e.g. `SIGNATURE` or `SHARED_SECRET`, matching the scanner's own
  `CredentialKind` vocabulary (`CREDENTIAL_COLUMN`, `SHARED_SECRET`, `SIGNATURE`,
  `THIRD_PARTY_RECEIPT`, `ENV_GATE`). Truer, and it changes the file's value set — so
  whatever consumes that set has to be found first. **Find the consumers before proposing
  this.**

**Explicitly not this ticket:**

- **The Stripe route itself.** It is Do-Not-Touch Zone 4 and it is not broken. This ticket
  changes a JSON record, not a line of the handler.
- **The 25 unclassified routes.** `route-classifications.json` has 81 entries against 106
  `route.ts` files at `0dc7be1`, and neither the three cron routes nor
  `src/app/api/sms/inbound/route.ts` is in it. [[GTC-264]] records that as standing staleness
  and not a ruling. Closing it is its own work and is not smuggled in here.
- **Any change to `tests/security-route-scan.ts` or its control suite.** Zone 6, and they are
  already correct about this route.
