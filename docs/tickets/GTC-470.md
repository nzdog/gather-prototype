## Plan 1 (what the pages show and where Go back goes)

Both pages draw one top bar, drawn by one plain function (a "render
function", as `renderLoadBox` and `renderRow` already are, so the contacts
tests can see through it): src/components/contacts/TopBar.tsx,
`renderTopBar`.

```
<- Your events                                         [ Go back ]
(1) Who's coming?  (2) What's the plan?  (3) ...  (4) ...
Your contacts
Your contacts stay in this browser. Gather only gets ...
```

- "← Your events": the words are STRIP_WORDS.YOUR_EVENTS, a plain link to
  /plan/events, with the same classes as the seven event-screen copies
  (`inline-block text-sm text-gray-500 hover:text-gray-900 underline
  underline-offset-2`). No new word.
- "Go back": a real button (`<button type="button">`), the page's own
  secondary-button style (as "Keep them"), at the right end of the top row,
  drawn from the first paint. Its name for a screen reader is its visible
  words (no aria-label).
- The Moments row is under the top row, only when the address names an event
  (the id rule W18 used). On a phone the four Moments stack, as on the event
  screens. Moment 1 is the current Moment, because every way in from an event
  starts on Moment 1's household form.
- The sample page (SampleContactsNote) draws the link and the button, no
  Moments row, and still reads no address, no storage and makes no request.

Where Go back goes (one rule, `goBackAction` in src/lib/contacts/address.ts,
pure, so it is pinned without a browser):

```
1. The address names an event
     -> that event's household form: backHref, as W18 did
        (/plan/ID/setup?at=people, plus &edit=HOUSEHOLD if she was
        changing one). A full page load, as "Add to this household".
2. Else, the referrer is a page of this site AND the tab has seen
   more than one page
     -> the browser's back (history.back())
3. Else
     -> /plan/events
```

The referrer is the address of the page she came from, which the browser tells
the next page. "A page of this site" means its origin equals ours exactly: a
lookalike such as https://gather.nz.evil.com, a javascript: address, a blank
referrer, or an origin of "null" all fail and fall to rule 3. The menu bar's
links are plain links (full page loads), so the referrer is known when she
comes from the menu bar. No Referrer-Policy is set anywhere. The sample page
never reads an address, so for it rule 1 never applies.

Go back writes no hand-off note, reads no draft and makes no request. The
household form's draft and the hand-off from "Add to this household" behave
exactly as before.

## Plan 2 (the tappable Moments row)

How the pre-flight and the glance board make the row tappable: they pass
`href` doors to MomentArc (an `href` door is a plain link; a `locked` door is
a button that shows its line under the row and goes nowhere). The glance board
and "Who I nudge" call `moment4Doors` (src/lib/moments/strip-hrefs.ts), which
asks the one rule, `stripDoors` (src/lib/moments/strip.ts), with four facts
fixed to true. That is right only because a Moment 4 screen exists after the
plan is held. The contacts page is a Moment 1 screen: she may be anywhere, so
`moment4Doors` cannot be reused as it is.

- strip-hrefs.ts gets one new exported function,
  `momentDoors(eventId, current, facts, blocked?)`, built from the same
  `stripDoors` and the same private `hrefOf`. `moment4Doors` is untouched.
- The six facts `stripDoors` needs are worked out as the setup page works
  them out, from the same rules (`momentTwoBegun`, `hasAnyPlan` in
  src/lib/setup/entry-stage.ts), in src/lib/contacts/strip-facts.ts (pure):
  - host saved: the setup record has begun, or a household member has role
    HOST;
  - a plan exists: `hasAnyPlan([], teamCount)`. Every item belongs to a
    section (see "Proof that every item belongs to a section"), so "any
    section or any item" is exactly "teamCount above zero";
  - approved: setup.planApprovedAt; held: event.status is not DRAFT; sent:
    event.sentAt; invites only: setup.invitesOnly.
- The page loads, from an event only, THREE plain GETs in parallel (a plain
  GET asks only to read: no body, no headers, no second argument):
  GET /api/events/{id}/households (already made before this ticket),
  GET /api/events/{id} (status, sentAt, the setup record) and
  GET /api/events/{id}/summary (teamCount). Before: 1 request from an event;
  now 3, two of them new. With no event, a bad id or nobody signed in: none,
  as before. No new route and no server change; the two new reads are host
  and co-host only, and other screens already make them. The summary was
  chosen over the items or sections lists because it carries eight numbers
  and no guest or coordinator names.
- No ticks (Moment 1's own screens draw none).
- While the reads are in flight, and if any read fails, is refused, throws,
  or the event has no setup record, the row is drawn as a plain display
  (`doors` an empty set: no taps, no words, no error line). MomentArc marks
  the current step for a screen reader only when it is given doors, so the
  empty set is passed on purpose. All or nothing: a half-known fact would send
  her to the wrong place.
- The locks: `momentDoors` calls `stripDoors`, so W6, W7, W8 and the two
  invites-only lines (`NOT_NEEDED`, `NOT_NEEDED_AFTER_PRESS`) come from the
  same rule and the same words as the setup page. Open doors become the same
  addresses the pre-flight uses. The one repeated line is the setup page's
  `blocked` branch (every non-current door becomes locked with that line); the
  setup page is pinned, so it cannot be shared, and a check pins what it
  produces.

### The half-typed household

Today: while she types on Moment 1's household form, the form keeps a copy in
this browser (localStorage, GTC-435), rewritten on every change and when the
page is hidden, for 7 days, per person, event and form (her own household's
step, a new household, or one being changed). Pressing the form's "Your
contacts" link writes the copy at once and, only if that worked, skips the
browser's "Leave site?" question for two seconds. The contacts page never
reads or touches the copy. When she next opens the form it is put back with
"We kept what you typed here earlier. It isn't saved yet." Only a good save,
Cancel or Discard, the form reset, a sign-out or another person signing in, or
7 days remove a copy.

A tap from the contacts page cannot lose it: a tap is a plain link that
removes nothing. What a tap could do is let her move on to Moment 2, 3 or 4
with that household unsaved, so the plan is made without it. The setup page
stops that with its own guard (the strip's other Moments say W9 or W9b and go
nowhere), which lives in the setup page's memory. The contacts page keeps the
guard, with the same ruled words, from what it can know:

- the address has `edit` (she left a household being changed): doors 2 to 4
  are locked with W9b, "Save your changes first, or press Cancel.";
- `form=host` (her own household's step): no extra block, as on the setup
  page (W6 to W8 already lock 2 to 4 while her household is unsaved);
- a plain address (the new-household form): the setup page blocks only if
  something is typed, and the address does not say. So one read asks whether a
  draft is kept for this event's new-household form, through the form's own
  reader: if yes, W9, "Save this household first, or clear what you've
  typed."; if no, the doors are open.

That read is src/lib/contacts/draft-kept.ts (ruling 2 above, amendment A11).
It answers true or false. It reads through the form's own `readDraft`, but
hands it a store that cannot write or remove (`readDraft` itself removes a
stale or malformed entry, so a plain store would break "never removes"). It
never returns what was typed. All three arrivals then match the setup page.

## Proof that every item belongs to a section (done before building)

The first stop condition below needed this. From the schema and the code, 22
Nov 2026, on origin/main 2491795:

- prisma/schema.prisma, model Item: `teamId String` (not optional) with
  `team Team @relation(fields: [teamId], references: [id], onDelete:
  Cascade)`. There is no `eventId` on Item. An item reaches its event only
  through its section.
- prisma/schema.prisma, model Team: `eventId String` (not optional), relation
  to Event with `onDelete: Cascade`.
- The database: in the init migration (20260119083345_init) the Item table has
  `"teamId" TEXT NOT NULL` and the foreign key to Team is `ON DELETE CASCADE`.
  No later migration drops the NOT NULL or the key (every migration that
  touches the Item table was searched for its teamId lines).
- The code: every `item.create` site in src goes through Prisma, which
  requires `teamId`; the database refuses a row without one in any case.
- `GET /api/events/[id]/summary` counts sections as `prisma.team.count({
  where: { eventId } })`.

So an event has an item only if it has a section. The setup page's
`hasAnyPlan(items, teamCount)` ("any section or any item") and "teamCount
above zero" are the same test.
