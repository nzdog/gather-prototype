```prisma
model AuditEntry {
  id             String          @id @default(cuid())
  timestamp      DateTime        @default(now())
  eventId        String
  sequence       Int             // monotonic per event — THE version number
  changeSetId    String          // one request = one changeSet = one human-visible step

  actorId        String?         // NULLABLE — the calendar/cron/system has no Person
  actorKind      ActorKind       @default(HOST)

  actionType     AuditActionType // was untyped String
  targetType     String
  targetId       String
  field          String?         // null for whole-entity create/delete
  before         Json?           // scoped to the changed entity — never the whole plan
  after          Json?

  reason         String?         // nullable BY DESIGN — §13.1, endorsed
  reasonRequired Boolean         @default(false)
  details        String?         // retained for existing rows

  event Event   @relation(fields: [eventId], references: [id], onDelete: Cascade)
  actor Person? @relation(fields: [actorId], references: [id])

  @@unique([eventId, sequence])
  @@index([eventId, timestamp])
  @@index([changeSetId])
}

enum ActorKind { HOST COHOST COORDINATOR GUEST SYSTEM }
enum AuditActionType { /* enumerated from existing logAudit call sites + the new change types */ }
```

Backfill for existing rows: `sequence` assigned by `timestamp` order per event; `changeSetId` =

the existing free-text values.

⚠ `actorId` moving from required to nullable is the only relation change. Audit every read of
`AuditEntry.actor` before applying.

### 2. `src/lib/lifecycle.ts` — new, the single source of lifecycle truth

Nothing else in the codebase may compare `event.status` to `'FROZEN'` or `'COMPLETE'` after A3.

```ts
export type EventPhase = 'DRAFT' | 'CONFIRMING' | 'SENT' | 'COMPLETE';

// Compat shim lives HERE and nowhere else, for the duration of Epic A:
//   isSent = sentAt != null || status === 'FROZEN'
export function isSent(event, now?): boolean;
export function isComplete(event, now?): boolean;      // now > endDate
export function getEventPhase(event, now?): EventPhase;
export function isMiniSend(personEvent, event): boolean; // pe.sentAt > event.sentAt

// Prisma-level equivalents so cron/eligibility filter in SQL, not JS:

export const COMPLETE_WHERE = (now: Date) => ({ endDate: { lte: now } });
```

### 3. `recordChange()` — the single ledger write path

Lives beside `logAudit` in `src/lib/workflow.ts` (or a new `src/lib/ledger.ts`). Requires a `tx`,
exactly as `logAudit` does — plan §7 of `gather-architecture-contract` (multi-table mutations use
transactions) applies unchanged.

Must implement:

- **Sequence allocation** per event, collision-safe under concurrent writes (the `@@unique` is the
  backstop; use a transactional max+1 or a sequence table — executor's call, documented).
- **`changeSetId` grouping** — one call site may emit N field-entries under one id.
- **Bulk changeSets** — one id, one reason, N entries, for the regenerate case (ruling 3).
- **The why-scope rule (T1–T5)** as an exported, unit-testable pure predicate:

  ```ts
  export function touchesSomeone(change: PendingChange, event: Event): boolean;
  export const ASK_FIELDS = ['name','quantity','quantityAmount','quantityUnit',
    'quantityUnitCustom','quantityText','dropOffAt','dropOffLocation','dropOffNote'] as const;
  ```

  | Trigger | Condition (all require `isSent(event)`) |
  |---|---|
  | T1 | Assignment created, moved, or deleted — any `response` value |
  | T2 | Person removed from the event while holding ≥ 1 assignment |
  | T3 | Item deleted while holding an assignment |
  | T4 | An `ASK_FIELDS` value changes where the assignment's `response != PENDING` |
  | T5 | `Event.startDate` / `endDate` / any `venue*` changes |

  **Actor-agnostic** (ruling 2). Explicitly NOT triggers: criticality toggles, description/notes,
  team/day/displayOrder, unassigned items, additions without assignments, guest responses, any
  `ASK_FIELDS` change while the assignment is `PENDING` (**the typo-fix case**), and anything
  pre-send.

- **Never throws or 4xx's for a missing reason** (ruling 4). A reason-less touching-someone change
  is recorded as `reasonRequired: true, reason: null`.

### ⚠ Data-loss incident, 2026-08-03 — and the invalid drift check

**The pre-migration drift check reported "clean" and that result was invalid.** It was run as:

```bash
npx prisma migrate diff --from-migrations prisma/migrations \
  --to-schema-datasource prisma/schema.prisma --shadow-database-url "$DATABASE_URL"
```

Prisma **resets whatever database it is given as the shadow** — drops the schema and replays
`prisma/migrations` into it. Passing the live `DATABASE_URL` therefore (a) wiped `gather_dev` and
(b) made the check compare the migrations against their own fresh replay, so an empty result was
guaranteed regardless of actual drift. **A drift check that resets its own target cannot detect
drift.** The clean result carried no information.

Damage: all 31 tables emptied — 21 events including the Henderson demo and the security fixtures —
and `_prisma_migrations` dropped. No point-in-time recovery available (`archive_mode = off`). Repo
and git were unaffected; no migration had run at that point.

Recovery, in order: `prisma migrate resolve --applied` × 29 rebuilt the migration history **without
dropping anything** (`migrate reset` was refused by Prisma's own AI-agent guardrail, correctly, and
was not needed); `migrate status` then reported "Database schema is up to date!"; `npm run db:seed`
restored Henderson at identical counts; `tests/security-fixtures.ts` restored the security fixtures.
Not recovered: ~19 ad-hoc test events from earlier ticket work, including the 260-item fixture behind
Run 1's upper-bound measurement.

**The honest re-check, post-recovery.** Two read-only forms, neither of which touches the database:

- Before applying, `migrate diff --from-schema-datasource --to-schema-datamodel` returned **exactly
  the intended A2 changes and nothing else** — no pre-existing drift, this time actually measured.
- After applying, `npx prisma migrate status` reports **30 migrations found, "Database schema is up
  to date!"**

The rule is now recorded in `gather-run-and-operate` §3b with this incident as its reason: never pass
a live `DATABASE_URL` as `--shadow-database-url`; use `migrate status`, the read-only
`--from-schema-datasource` direction, or a throwaway `shadow_check` database.

### What was built (scope items 2–5)

**`src/lib/lifecycle.ts`** — the single source of lifecycle truth. `isSent`, `isComplete`,
`getEventPhase`, `isMiniSend`, `neededBy`, plus `SENT_AND_LIVE` / `COMPLETE_WHERE` /
`NOT_YET_SENT_WHERE` Prisma fragments so A3a's cron and eligibility queries filter in SQL rather than
loading every row. Structural `LifecycleEvent` input rather than the full Prisma type, so callers can
pass a narrow `select` and tests need no database.

The FROZEN compat shim lives in `isSent()` and nowhere else — one clause, deleted by [[GTC-199]]
(A4). That containment is what makes plan §9's rollback cost one line.

`isComplete` is strict `>`: an event ends AT `endDate` and is past only beyond it. Asserted in both
directions, including the one-millisecond case. `getEventPhase` puts COMPLETE above SENT so a past
event is over whether or not it was ever sent — which is also what makes A4's data migration safe.

**`src/lib/ledger.ts`** — the write path, and the load-bearing function of the epic.

- `ASK_FIELDS` (9) and `MATERIAL_EVENT_FIELDS` (11) enumerated, not prefix-matched. `ASK_FIELDS` is
  exactly Hinge §3's message contents; enumeration means a future venue-ish column is a decision
  rather than a silent absorption.
- `whyTrigger()` / `touchesSomeone()` — pure, no clock, no I/O, returns *which* of T1–T5 fired.
  The `switch` enumerates every non-triggering `ChangeAction` explicitly rather than defaulting, so
  adding an action is a compile error until someone decides its scope.
- **The T1/T4 asymmetry is the whole of the typo rule** and is documented at the function: T1 fires
  even at `PENDING` because the ask itself is being withdrawn or moved; T4 does not, because nothing
  has been *claimed against* yet. Fixing "Pavolva" before anyone answers is free.
- `recordChange()` — sequence allocation, changeSet grouping, `actorKind`/`actorName`, honest-null
  reason. Requires a `tx`, exactly as `logAudit` does.
- `fieldChanges()` — turns a before/after pair into one change per *actually changed* field, so
  "one entry per changed field" is enforced in one place instead of by 25 routes.

**Sequence allocation, and why it is race-safe.** `recordChange` opens with a write to the `Event`
row, which takes an exclusive row lock for the rest of the transaction; any concurrent
`recordChange` on the same event blocks there rather than racing to read the same `max(sequence)`.
The `@@unique([eventId, sequence])` is the backstop, not the mechanism. Bumping `updatedAt` is also
simply true — the event's plan changed — and nothing reads `Event.updatedAt` (verified: the only
`orderBy: updatedAt` in the codebase is on `HostMemory.patterns`). Documented at the call site:
**`recordChange` must be called last in a transaction**, which keeps lock ordering (items, then
event) consistent across every caller and cannot deadlock. If contention ever appears, the cleaner
form is an atomic `Event.ledgerSequence` counter — deliberately not done here because it is a schema
change and would need its own sign-off.

**`reason` is per-changeSet; `reasonRequired` is per-row.** A set may mix a T1 reassignment with a
non-triggering note edit — the ledger should say which row was owed a why, while the reason itself
belongs to the set because the host gave one answer. Asserted directly.

**Revisions uncapped.** `GET /api/events/[id]/revisions` drops `take: 5` for cursor pagination
(`?limit=`, default 25, max 200; `?cursor=`; `nextCursor` null on the last page; `total` included).
The old cap was not a display default — the API could not return a sixth revision to any caller, so
history older than five steps was unreachable. Hinge §2: "complete history always reachable whatever
the display defaults to." `RevisionHistory.tsx` reads `data.revisions` and is unaffected.
