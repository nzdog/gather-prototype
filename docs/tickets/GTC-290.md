# GTC-290 — Poll TNZ for delivery status

**Status:** Open — **scoped, not designed. Filed to close a structural gap, not to be built
next.** Filed 2026-09-12 | **Branch:** TBD
**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low
Escalated (brand/trust risk): [x] Yes — the gap it closes is invisible by construction. An
account out of credit silences every message Gather sends and produces no delivery webhook

**Filed on a founder ruling**, 2026-09-12, at the close of [[GTC-264]] Phase 0. It exists

## Why this exists — the webhook is incomplete, by TNZ's own table

[[GTC-264]] builds the delivery-receipt webhook. That is the right first move and it is not
the whole channel.

TNZ's SMS delivery result-codes page lists, per value, which mechanisms report it. **Four
states are documented as NOT delivered by webhook:**

- `LinkNotPermitted` — *"SMS message contains a URL that is not on our phishing whitelist"*.
  Channels: Dashboard, Email, GET Poll.
- `CreditHold` — *"The message is held due to lack of available account credit"*.
  Channels: Dashboard, Email, GET Poll.
- `Delayed` — *"The message is queued until the specified Send Time"*.
  Channels: Dashboard, GET Poll.
- `Pending` — *"currently processing and awaiting a delivery result"*.
  Channels: Dashboard, GET Poll. ⚠ **Contested** — the API documentation page lists `PENDING`
  among the webhook `Status` values while the codes page does not. One of the two is wrong.

**`CreditHold` is why this is `high` and not `medium`.** It is not a per-guest failure. An
account out of credit holds **every** message Gather sends, and emits no webhook for any of
them. What Gather would see is: a 200 accept on every send, then nothing, forever. **That is
the exact signature of a healthy send.** Every stamp would be written, every glance would be
green or amber on its nudge-clock, and not one message would have left TNZ.

`LinkNotPermitted` is the same shape at smaller scale and is not hypothetical: Gather's
messages carry links by design — magic links, wrap-up links, the `/p/` participant path. A
URL that falls outside TNZ's phishing whitelist fails the send, and the failure is invisible
to a webhook-only ingest.

**A schema that looks complete while being structurally blind to an account-wide failure is
worse than one that says it is partial.** That is the founder's ruling and it is the reason
this is filed now rather than left as a note in [[GTC-264]].

## What is already known — the contract, read 2026-09-12

Read from the documentation in [[GTC-264]] Phase 0, so this ticket does **not** start with a
blocking unknown about the wire. Recorded in full in the contract record; the load-bearing
parts:

- **Endpoint:** `GET https://api.tnz.co.nz/api/v2.04/get/status/[MessageID]`.
- **Per message, keyed on `MessageID`.** That is the join key Gather already captures on
  every send, via `sendViaTnz` in `src/lib/sms/tnz-client.ts` into `InviteEvent.metadata`.
  **No new correlation key is needed, and no cursor.**
- **⚠ It needs NO new credential.** Authentication is
  `Authorization: Basic <Auth Token>` — described as *"Auth Token value set up"*, which is
  the existing `TNZ_AUTH_TOKEN`. This ticket does **not** consume [[GTC-264]]'s callback
  secret and must not be built as though it does.
- Also required: `Content-Type` and `Accept`, both `application/json; encoding='utf-8'`.
- Responses: `200 OK` on success, `400 Bad Request` on failure.
- **TNZ's own retention guidance:** *"The GET Poll should be configured to timeout after 48
  hours with no result."* That is the stop rule, stated by TNZ.
- Rate limits are **not** stated. See *Unknowns* 1.

### ⚠ The response is a SECOND wire shape, and this is why it was not folded into GTC-264

This is the reason the ruling deferred it rather than adding it to [[GTC-264]]'s phase, and
it must not be re-litigated by an executor who notices the endpoint is "just a GET".

- **Message-level `Status` has its own vocabulary**: `Unknown`, `Pending`, `Delayed`,
  `Completed`, `CreditHold`. Note `Completed`, which appears **nowhere** in the webhook's
  vocabulary.
- Per-recipient `Status` and `Result`, inside a `Recipients` array, use the **webhook**
  vocabulary — `SUCCESS`/`FAILED`/`PENDING` and the twenty-one `Result` values.
- So one response carries **two different `Status` vocabularies at two nesting levels**.
- **`Result` at message level means something else again.** Documented as *"Result of your
  API call (not the result of the message)"* — so a poll can return `Result: "Failed"`
  meaning the poll itself failed, with the message perfectly delivered. Same field name,
  opposite subject.
- Field names differ from the webhook's in ways a shared parser would silently paper over:
  `JobNum` here versus `JobNumber` there; `SentTimeUTC` and `SentTimeUTC_RFC3339` with
  **underscores** here versus `SentTimeUTC-ISO8601` and `SentTimeUTC-RFC3339` with
  **hyphens** there.

**Two vocabularies in one phase is how the fiction gets built.** [[GTC-264]] *Isolate the
wire shape* exists to stop tests passing against a believed shape; giving that phase two
believed shapes at once would defeat it.

### ⚠ And the evidence for this shape is weaker than for the webhook's

Recorded so it is not treated as equally settled. The webhook payload is documented by a
parameter table **and** a literal JSON example, and the two agree. The GET's response is
documented by **tables only**: of the 25 `<pre>` blocks in that section of the saved page
source, 23 are empty — both the "Sample SUCCESS Response" and "Sample FAILURE Response"
bodies are absent from the HTML. **There is no literal example to check the field list
against.** Treat every GET field as DOC-TABLE and none as DOC-EXAMPLE.

## Scope

**Build: a poller that closes the four states the webhook does not send.**

1. **A selection rule.** Which sends get polled, and when. The population is sends with a
   stored `messageId` and no terminal delivery report. The rule is a design question, not a
   given.
2. **A stop rule.** TNZ say 48 hours with no result. Something must stop polling and record
   that it stopped, because "we gave up" and "no report yet" are different facts.
3. **A schedule.** A cron route, following the three existing ones as precedent.
4. **The parse**, behind its own narrow boundary, separate from [[GTC-264]]'s — see the
   second-wire-shape warning above.
5. **Somewhere to put it.** Almost certainly [[GTC-264]]'s delivery-state model, with
   whatever that phase settled. **If it needs a new column this ticket carries a migration
   and that migration is its own phase.**

**Not in scope — the consumers.** Same exclusion as [[GTC-264]]. The stamps are
[[GTC-258]]'s, the glance red is [[GTC-192]]'s, and a `CreditHold` alarm for the operator is
a fifth thing that belongs to neither and is named below.

## What it unblocks, and one thing it does not

- **Delivery state stops having a silent hole.** After [[GTC-264]] alone, "no failure
  reported" has an account-wide cause that cannot be seen. After this, it can.
- **`CreditHold` becomes observable** — which is the precondition for anyone ever alarming
  on it. ⚠ **The alarm itself is not this ticket.** Recording the state is; deciding who gets
  told that the account is out of credit, and how, is an operations question with no owner
  today. Name it, do not build it.
- **The fourth `Result` bucket gets its evidence.** [[GTC-264]]'s amended bucket passage
  puts `CreditHold` and `LinkNotPermitted` in the our-fault-not-the-guest's bucket, which is
  [[GTC-192]]'s to rule. Both arrive only through this channel, so without this ticket that
  bucket is two values short in practice while appearing complete on paper.

**It does not make the channel complete either.** `Unknown` is documented with notification
channels **`N/A`** — reported by no mechanism at all, not even the dashboard. A message whose
status is `Unknown` is unobservable by any means TNZ document. Say so plainly rather than
claiming completeness after this lands.

## Unknowns

1. **Rate limits on the GET.** Not stated anywhere in the documentation. This governs the
   selection rule and the schedule directly: a poller that sweeps every unresolved send every
   fifteen minutes may be fine or may be abusive, and we cannot tell. **Ask TNZ before
   designing the schedule.**
2. **Whether the poll is authoritative over the webhook when they disagree.** If a webhook
   said `SUCCESS` and a later poll says `Pending`, which is true? Not stated. Bears on
   whether poll results overwrite or append.
3. **Whether `Pending` arrives by webhook.** The two TNZ pages disagree (see above). If it
   does, the poller's population is smaller than it looks.
4. **What a poll returns for a `MessageID` TNZ has aged out**, and after how long. The
   48-hour guidance is about our timeout, not their retention.
5. **Whether `Undelivered` can be disambiguated by polling.** It is the one `Result` value
   the documentation cannot bucket. If the poll's `Detail` carries more than the webhook's,
   it might. Unlikely; worth one look at the trial.

## Acceptance — assertions to hold, not a design

- [ ] A poll for a send with a stored `messageId` records the returned per-recipient status,
      distinguishably from a webhook-sourced report.
- [ ] A `CreditHold` response is recorded and is distinguishable from a per-guest failure.
      **This is the assertion the ticket exists for.**
- [ ] A poll for an unknown `MessageID`, and a poll returning `Result: "Failed"` meaning the
      API call failed, are both handled without throwing and without recording a delivery
      failure against the guest.
- [ ] A send that stored no `messageId` — `sendViaTnz` accepting an unparseable 2xx body — is
      never polled, and its absence is recorded rather than retried forever.
- [ ] The stop rule fires, and "stopped polling" is a recorded state, not an absence.
- [ ] The message-level and per-recipient `Status` vocabularies are parsed as the two
      different vocabularies they are, and message-level `Result` is never read as a delivery
      outcome.
- [ ] The poll's assumed shape is recorded in the same provenance form as
      [[GTC-264]]'s, marked DOC-TABLE throughout, with fabricated fixtures built from that
      record.
- [ ] **No test reaches TNZ.** Stop Condition 6 is live and specific.
- [ ] Adjacent flows unaffected: outbound `sendSms`, the three existing cron routes, the MO
      handler, and [[GTC-264]]'s webhook endpoint.

**Test gate** — Severity High: test-first required. RED before any fix, GREEN after, both

## Stop Conditions

Standard eight from `BUG-TICKET-TEMPLATE.md`. Live notes:

- **8 (required unknown):** **not pre-fired**, unusually for a ticket in this family — the
  wire contract was read in [[GTC-264]] Phase 0 before this ticket existed. *Unknowns* 1
  (rate limits) should be asked before the schedule is designed but does not block a parse.
- **7 (schema migration):** fires **only if** [[GTC-264]]'s model needs a new column to
  distinguish a polled result from a pushed one. If it does, that migration is its own phase.
- **6 (real-world side effects):** binding, and **sharper here than in [[GTC-264]]**. This
  ticket makes **outbound** calls to TNZ. A test that polls the live API is a failed test,
  and unlike a webhook endpoint there is no shape of accident that is harmless — a runaway
  poller is a rate-limit incident on a production account.
- **5 (scope expansion):** the consumers are excluded, and so is the `CreditHold` operator
  alarm. If any becomes load-bearing → stop.
- **Sequencing:** [[GTC-264]] must have landed. Per the founder ruling of 2026-09-12 the
  order is [[GTC-264]], [[GTC-258]], [[GTC-229]], [[GTC-288]], then this ticket with
  [[GTC-192]]'s bounce red and [[GTC-289]].
