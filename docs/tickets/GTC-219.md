# GTC-219 — STUB: drop the retired RSVP columns

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** low, schema

### Context

GTC-174 (D1) retired `PersonEvent.rsvpStatus` as a directly-writable field. Hinge §3
(ruled gap #10) supersedes event-level RSVP as a guest-facing question: the tap is the
item ask and attendance is inferred from it, so attendance became derived state
(`deriveAttendance()` in `src/lib/attendance.ts`) and the one genuinely-asked answer
moved to the narrow `PersonEvent.attendanceAnswer`.

D1 left three columns and one enum **retained-but-unwritten** rather than dropping them,
following the precedent GTC-168 (A2) set with `Person.inviteAnchorAt`: keeping them for
one ticket makes the backfill auditable and the change cheap to revert. This ticket is
the second half of that decision. Filing it is what stops "retained for one ticket"
quietly becoming "retained forever".

- `PersonEvent.rsvpStatus` (`RsvpStatus`)
- `PersonEvent.rsvpRespondedAt`
- `PersonEvent.rsvpFollowupSentAt`
- `enum RsvpStatus`

### Scope

**Fix here:**
- Drop the three columns and the `RsvpStatus` enum via `prisma migrate dev`.
- Remove the retained-but-unwritten doc-comment block from `prisma/schema.prisma`.
- Remove the now-vestigial `RsvpFollowupCandidate.rsvpRespondedAt` field
  (`src/lib/sms/nudge-eligibility.ts`) if GTC-178 has not already deleted the type.
- Update the seed/dev scripts that still set `rsvpStatus`: `scripts/seed-rsvp-test.ts`,
  `scripts/check-rsvp-eligibility.ts`, and the `rsvpStatus` fixtures in
  `tests/household-edit-*-test.ts` and `tests/child-message-exclusion-test.ts`.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- `attendanceAnswer` / `attendanceAnsweredAt` — the replacement, not part of the drop.
- The derivation in `src/lib/attendance.ts`.

### Dependencies

- **GTC-174 (D1)** — must have settled; this is its second half.
- **GTC-178 (E1)** — deletes `findRsvpFollowupCandidates()`, `sendRsvpFollowupNudge()`
  and the follow-up template. D1 neutralised the finder to return `[]`, which left one
  DEAD write to `rsvpFollowupSentAt` in `src/lib/sms/nudge-sender.ts` behind an
  unreachable caller. **Dropping that column before E1 lands turns dead code into a
  compile error at best and a runtime failure at worst** — sequence E1 first, or delete
  the write as part of this ticket.

### Pre-flight (do this before writing the migration)

This is a DESTRUCTIVE migration — the first in the D-cluster. Before generating it:

- [ ] Confirm production/staging row counts by `rsvpStatus`. If any `YES`/`NO` rows
      exist whose `attendanceAnswer` is NULL, GTC-174's backfill did not reach them and
      dropping the column **loses a guest's answer**. Re-run the backfill first.
- [ ] Confirm zero `NOT_SURE` rows remain, or accept explicitly that their signal is
      discarded — GTC-174's migration deliberately did not carry them (Hinge §8 abolishes
      the attendance-maybe), so they are the one class of data this drop truly destroys.
- [ ] Take a backup. Zone 5 forbids hand-editing migrations, not backups.

### Acceptance

- [ ] No source file references `rsvpStatus`, `rsvpRespondedAt` or `rsvpFollowupSentAt`.
- [ ] Row-count evidence recorded showing no unmigrated `YES`/`NO` answers were dropped.
