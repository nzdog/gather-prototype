# [[GTC-079]] — Replace Twilio SMS with TNZ — CLOSED

**Status:** Complete
**Branch:** gtc-042-part1-nudge-schema
**Commit:** 01962a9

### What was found

The existing SMS pipeline routed every send through Twilio via
`src/lib/sms/send-sms.ts`, which gated delivery on `isValidNZNumber()` —
effectively accepting only `+64` numbers and then handing them to Twilio.
Twilio does not deliver to NZ, so every NZ SMS (the only kind the system
would accept) failed at the carrier.

Twilio env vars (`TWILIO_*`) are marked OPTIONAL in
`GATHER-BUILD-CONSTANTS.md`; no TNZ client existed. Opt-out enforcement and
`InviteEvent` logging were correct and worth preserving verbatim.

Per TNZ REST API docs (www.tnz.co.nz/Docs/RestAPI):
- Endpoint: `POST https://api.tnz.co.nz/api/v2.04/send/sms`
- Auth: `Authorization: Basic ${TNZ_AUTH_TOKEN}` header only
- Payload: `{ MessageData: { Message, Destinations: [{ Recipient }] } }`
- No NZ-specific compliance text ("reply will be charged" etc.) surfaced in
  the docs reachable during investigation — flagged as a follow-up.

### What was changed

- **`src/lib/sms/tnz-client.ts`** (new) — Thin fetch-based TNZ transport
  exposing `isTnzEnabled()` and `sendViaTnz({ to, message })`. Reads
  `TNZ_AUTH_TOKEN`, posts the documented payload, returns
  `{ success, messageId?, error? }`. Defensive body parsing so a 2xx with a
  non-JSON body is still a success.
- **`src/lib/sms/send-sms.ts`** — Replaced the `isValidNZNumber` gate with an
  E.164 format check plus country-code routing. `+64` and `+61` numbers go
  to TNZ; all other E.164 numbers go to Twilio. Opt-out check runs BEFORE
  the provider-config check so a missing `TNZ_AUTH_TOKEN` can never mask
  an `OPTED_OUT` signal — opt-out is a hard user-level promise that must
  hold regardless of provider availability. `InviteEvent` logging and the
  `SendSmsResult` shape are unchanged. Provider identity is included in
  `NUDGE_SENT_AUTO` / `SMS_SEND_FAILED` metadata for audit.
- **`tests/sms-validation-test.ts`** — Updated Test 2 to reflect the new
  routing: `+1234567890` is now a valid E.164 number routed to Twilio, so
  the assertion accepts either `SMS_DISABLED` (Twilio unconfigured) or
  `SEND_FAILED` (Twilio test credentials reject the bogus number). Added
  Test 2b using `'not-a-number'` to preserve coverage of the
  `INVALID_NUMBER` path under the new E.164-format gate.
- **`GATHER-BUILD-CONSTANTS.md`** — Added `TNZ_AUTH_TOKEN` to the env-var
  table with sourcing note (TNZ Dashboard → Users → API tab). Clarified that
  `TWILIO_*` vars now cover non-NZ/AU destinations only.

### Known limitations / follow-up flags

- **Webhook handler deferred.** No `/api/webhooks/tnz/sms` route was added.
  TNZ will POST delivery status (`Status`, `Result`, `MessageID`,
  `Destination`, `Price`, `SentTimeLocal` with `Authorization`,
  `X-Timestamp`, `X-Sender` headers) to a configured callback URL. Follow-up
  ticket recommended to capture delivery state into `InviteEvent`.
- **NZ compliance text.** TNZ REST docs surfaced during this ticket do not
  explicitly require a "reply will be charged" disclaimer, but the full
  compliance page was unreachable. Worth confirming with TNZ support before
  high-volume production sending. Templates in
  `src/lib/sms/nudge-templates.ts` and `wrap-up-templates.ts` are untouched.
- **Production verification pending.** A live `+64` test send requires
  `TNZ_AUTH_TOKEN` in Railway, which is out of scope for this commit.

### Post-close note — Dependabot alert sweep

While PR #36 was open, GitHub reported two high-severity Dependabot
alerts on `master`, both transitively pulled in via Prisma:

- `defu@6.1.4` — prototype pollution (CVE-2026-35209, GHSA-737v-mqg7-c878)
- `effect@3.18.4` — `AsyncLocalStorage` context leakage (CVE-2026-32887, GHSA-38f7-945m-qr2g)

Neither package is directly imported by app code; both are pulled in
by `prisma → @prisma/config → {c12, effect}`. Real-world exposure in
this codebase is minimal (`effect` runs only during Prisma CLI/config
loading; `defu` doesn't see user input).

**Resolution:** bumped `prisma` and `@prisma/client` from `6.19.2` /
`6.19.1` → `6.19.3` via `npm update`. The caret range in `package.json`
(`^6.19.1`) already accepted this version, so only `package-lock.json`
changed. Post-upgrade lockfile shows `effect@3.21.0` and `defu@6.1.7`
— both above the patched thresholds.

Verification:
- `npm run test:security` → 16/16 passing
- `npm run build` → exit 0 (prisma generate + migrate deploy + next build)
- `npm audit` → 0 vulnerabilities

Prisma v7 upgrade deferred to [[GTC-080]] — Prisma emitted a deprecation
warning about `package.json#prisma` being removed in v7, and v7 has
several breaking changes that require deliberate work.
