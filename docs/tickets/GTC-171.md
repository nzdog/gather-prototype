### Context

Moment 4 spec §6: tasks (day-of choreography — washing, drying, clearing) enter the plan in
Moment 2, alongside the items — "the plan knows the washing-up exists the way it knows the lamb
exists." Ownership lands in Moment 3 — tasks are assigned and claimed through the **same
machinery as items**. One assignment machine, two kinds of rows (items are owed *to* the day;
tasks are owed *during* it).

Today: no `Task` model, no row-kind distinction anywhere in the schema. Day-of choreography exists
only as free text — `EventSetup.setUpData`/`cleanUpData`/`otherJobsOtherData` — and the live AI
schema's category list (`FOOD_CATEGORY_ORDER`) has no Setup/Cleanup slot, so this free text has no
guaranteed path into structured rows today.

### Scope

**Fix here:**
- Schema addition distinguishing item rows from task rows (e.g. a row-type discriminator on
  `Item`, or a shared parent model) that reuses the existing `Assignment` relation unchanged.
- Wire `EventSetup`'s free-text setup/cleanup/other-jobs fields into structured task rows at
  Moment 2 generation time (via `finalize-plan`), consistent with B1's criticality wiring in the
  same route.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The `Assignment` model's core shape — assignments still reference `Person`, never `PersonEvent`
  (the invariant holds regardless of row kind).
- B1's criticality machinery — coordinate, don't duplicate.

# GTC-171 — B2: Task-row data model — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** [pending] | **Effort:** xhigh

## The shape decision

The ticket offered two shapes: a discriminator on `Item`, or a shared parent model. **Chose the
discriminator** — `Item.kind: RowKind`.

The stated tiebreak was Assignment reuse, but that does not discriminate on its own: a parent-model
variant exists that leaves `Assignment` byte-for-byte unchanged (keep the parent named `Item`, move
the ~25 food columns into a child `FoodItem` with `itemId @unique`). Recorded here because a wrong
reason in a decision record is worse than none — the next person would apply the wrong test.

The actual reason is the second half of the tiebreak, *whichever makes the reuse cleanest*:

| | discriminator | parent + `FoodItem` child |
|---|---|---|
| `Assignment` model | untouched | untouched |
| Migration | 1 enum + 1 column, no data movement | 25-column data migration |
| `prisma.item.*` call sites | unchanged by default | every read needs the join taught |
| `createRevision` / `restoreFromRevision` / `PlanSnapshot` | ride along free | three serialisers rewritten |
| Cascade reasoning | one path (`Team → Item`) | two paths to keep in step |

`Item.teamId` is NOT NULL with `onDelete: Cascade` — team lifecycle *is* row lifecycle, and both
`regenerate` and `restoreFromRevision` depend on that cascade. Splitting the row adds a second
lifecycle for zero gain.

## What was built

- **Schema:** `enum RowKind { ITEM TASK }` and `Item.kind RowKind @default(ITEM)`. Nothing else on
  the model changed. `Assignment` untouched — still `itemId @unique` → `Item`, `personId` →
  `Person`, no `PersonEvent`.
- **Generation:** `finalize-plan` now converts `EventSetup.setUpData` / `cleanUpData` /
  `otherJobsOtherData` into structured task rows. A `tasks` array was added to the **same**
  single Claude call (GTC-145 invariant preserved), and the route reads the full persisted
  `{ freeText, stillDeciding }` shape — the previous cast dropped `stillDeciding`, which every food
  category has always honoured and these three never did.
- **Eligibility is enforced server-side**, not in the prompt: a task survives only if its bucket has
  non-empty free text *and* is not `stillDeciding`. A deterministic filter cannot be talked out of
  it by the model.
- **Task teams:** up to three GENERATED teams — Set up (`Domain.SETUP`), Other jobs (`CUSTOM`),
  Clean up (`CLEANUP`) — created only for eligible buckets. `Domain` already carried SETUP and
  CLEANUP, so J3's run-sheet phase grouping came free with no new column.
- **Data shape does the gate work.** Task rows are written non-critical (field omitted → schema
  default) with `quantityState: 'NA'` (existing enum value). That alone keeps them out of
  CRITICAL_GAPS, CRITICAL_PLACEHOLDER_UNACKNOWLEDGED, QUANTITY_MISSING, the summary critical counts,
  the coordinator gap `groupBy`, and `readyToFreeze` — **no code change at any of those sites**.
  B1's criticality prompt block is byte-for-byte unchanged.
- **The assign gate relaxes for task rows only** (`item.kind === 'ITEM' && …`). `PersonEvent.teamId`
  is singular, so a task team can never have members; without this, task rows would have been
  decorative. Same route, same model, same ack path — no second surface. Founder-ruled.
- **Two consequence fixes:** auto-assign builds its distribution only from teams with ≥1 ITEM row
  (otherwise zero-member task teams are the lowest-count targets and strand participants), and
  `detectMissingCoordinators` exempts teams with no ITEM rows (otherwise three permanent conflict
  cards).
- **Filters:** STRUCTURAL_MINIMUM_ITEMS, `summary.itemCount` (with a new `taskCount` alongside), and
  the review-items **GET** exclude tasks. The review-items POST stays unfiltered on purpose —
  filtering it would strand task rows at `userConfirmed: false` forever.
- **Preserves:** both `regenerate` branches and `restoreFromRevision` now keep task rows.
- Step 2 approval preview shows the jobs; `token-limits.ts` header re-checked and updated.

## Migration summary

`20260804045147_gtc171_item_row_kind` — generated with `--create-only`, surfaced for sign-off,
approved, then applied. Contains exactly two statements and nothing else:

```sql
CREATE TYPE "RowKind" AS ENUM ('ITEM', 'TASK');
ALTER TABLE "Item" ADD COLUMN     "kind" "RowKind" NOT NULL DEFAULT 'ITEM';
```

No backfill statement — `DEFAULT 'ITEM'` classifies every existing row, and Postgres adds a
non-volatile default without rewriting the table. No new index: `kind` has two values and every
query filtering it also filters `teamId` or `team.eventId`, already covered by
`@@index([teamId, displayOrder])`.

**Rollback:** `ALTER TABLE "Item" DROP COLUMN "kind"; DROP TYPE "RowKind";`

**Drift:** the P3005 warning in `GATHER-BUILD-CONSTANTS.md` is **stale** — verified, not trusted.
`prisma migrate status` reported "Database schema is up to date!" beforehand, the generated SQL
contained no reset or drift-repair DDL, and `migrate dev` applied without a reset prompt.

## Spawned

**GTC-206** — `restoreFromRevision` nulls every `PersonEvent.teamId`, so nobody is on any team after
a revision restore and the same-team gate reads that as "nothing is assignable". Pre-existing, not
caused by B2, filed rather than fixed: it is a revision-system bug, and prose in a not-in-scope list
is where bugs get forgotten. B2 makes it more *visible* (task rows stay assignable across the
relaxed gate while item rows do not) without changing item-row behaviour either way.
