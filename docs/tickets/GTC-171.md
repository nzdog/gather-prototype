# GTC-171 — B2: Task-row data model

**Status:** Open | **Branch:** TBD | **Commit:** [pending] (filed `e5f6e82`) | **Effort:** xhigh, schema

*Effort level is a proposal from the discovery-report ticket breakdown — run `/effort` manually
before execution.*

### Context

Moment 4 spec §6: tasks (day-of choreography — washing, drying, clearing) enter the plan in
Moment 2, alongside the items — "the plan knows the washing-up exists the way it knows the lamb
exists." Ownership lands in Moment 3 — tasks are assigned and claimed through the **same
machinery as items**. One assignment machine, two kinds of rows (items are owed *to* the day;
tasks are owed *during* it).

Today: no `Task` model, no row-kind distinction anywhere in the schema. Day-of choreography exists
only as free text — `EventSetup.setUpData`/`cleanUpData`/`otherJobsOtherData` — and the live AI
schema's category list (`FOOD_CATEGORY_ORDER`) has no Setup/Cleanup slot, so this free text has no
guaranteed path into structured rows today.

### Scope

**Fix here:**
- Schema addition distinguishing item rows from task rows (e.g. a row-type discriminator on
  `Item`, or a shared parent model) that reuses the existing `Assignment` relation unchanged.
- Wire `EventSetup`'s free-text setup/cleanup/other-jobs fields into structured task rows at
  Moment 2 generation time (via `finalize-plan`), consistent with B1's criticality wiring in the
  same route.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The `Assignment` model's core shape — assignments still reference `Person`, never `PersonEvent`
  (the invariant holds regardless of row kind).
- B1's criticality machinery — coordinate, don't duplicate.

### Dependencies

None directly, but sequenced before J3 (the runbook renders task rows).
