### Context

A3a removed the gates. This ticket makes every mutation carry its story: `recordChange()` (built in
[[GTC-168]]) is wired into every route that changes plan state, and `frozen-edit` — the 499-line
route that did allow+reason for three actions, FROZEN-only, unconditionally — is deleted and
redistributed.

Large diff, low risk: this changes what the system *records*, not what it *permits*.

**A3a and A3b must merge together.** Between them, post-send mutations are allowed but not recorded.
That window exists only between two commits on an undeployed branch (plan §4.3).

### Rulings folded in (Nigel, 2026-08-03)

- **Coordinators — (a):** the ledger is actor-agnostic. Coordinator routes get `recordChange()` on
  the same terms as host routes, with `actorKind: 'COORDINATOR'`. There is no host-only path.
- **Post-send regeneration — (a) now, (c) once F1 exists,** *"with the consequence stated plainly in
  the UI before the act."* This ticket implements (a): regenerate emits one bulk changeSet (one
  `changeSetId`, one reason, N entries) plus one `PlanRevision` checkpoint. The UI warning is
  [[GTC-197]] (A3c); **the copy is specified there and must land in the same merge** — allowing the
  act without the warning would ship half of a ruling.
- **§13.1 required-reason-never-blocks — endorsed.** No route added here may 4xx for a missing
  reason. A touching-someone change without one lands, recorded `reasonRequired: true, reason: null`.

## Scope

### 1. Delete `frozen-edit` and redistribute it

`src/app/api/events/[id]/frozen-edit/route.ts` (499 lines) is removed. Its three actions fold into
the ordinary routes, which gain an optional `reason` field:

| `frozen-edit` action | Destination | Reason? |
|---|---|---|
| `reassign` | `POST`/`DELETE /api/events/[id]/items/[itemId]/assign` | **Yes** — T1 |
| `edit_item` | `PATCH /api/events/[id]/items/[itemId]` | **Only if T4** (`ASK_FIELDS` changed AND `response != PENDING`) |
| `toggle_critical` | `PATCH /api/events/[id]/items/[itemId]` | **No** — Moment 4 §8.3: criticality *"touches nothing else… entirely a host-facing signal."* Today's unconditional reason demand is the contradiction the discovery report flagged. |

Preserve, do not reinvent: `handleReassign`'s two correct halves — capture the why, and notify the
released person. The why becomes `recordChange()`'s `reason`; the release notification becomes a hook
`onAssignmentReleased(personId, itemId, changeSetId)` that [[GTC-176]] (D3) implements. Its
`logInviteEvent(..., metadata.auditType: 'FROZEN_EDIT')` writes are replaced by real ledger entries;
`InviteEvent` keeps `MANUAL_OVERRIDE_MARKED` for genuine channel overrides only.

**Guest-side routes write to `InviteEvent`, not the plan ledger.** Moment 4 §7: responses *"are not

via T1 if it creates an assignment.

Every `recordChange()` call goes inside the route's existing `prisma.$transaction`, per
`gather-architecture-contract` §7. Routes with no transaction today and multi-table writes get one —
notably the household routes (`reconcileHouseholdMembers` still runs non-transactionally, flagged in
the discovery report §5).

### 3. The material-change hook (the F1 handoff)

`PATCH /api/events/[id]` (`route.ts:97,98,111`) is the only route writing `startDate`, `endDate`, or
`venue*`. It currently has **no status gating and no audit logging at all** — this is new server
behaviour, not migration.

Add: T5 detection → `recordChange()` with `MATERIAL_CHANGE`, plus a **no-op hook**
`onMaterialChange(eventId, changeSetId, changedFields)` for [[GTC-183]] (F1) to implement.

**The gap window is real and must be documented, not hidden** (plan §7.3): between this ticket and

### ⚠ Doctrine: the no-undo refusal is INTERIM (Nigel, 2026-08-03)

[[GTC-169]] (A3a) made `restoreFromRevision()` throw on a sent event. **That refusal is the interim
contract, not the end state, and it must not silently harden into doctrine.**

> "Post-send restore is the same species as post-send regeneration (ruled: allow with checkpoint +
> ledger) — a bulk change that must carry a why, not a thing to forbid. When this ticket's wiring
> makes restore recordable, it converts from refused to allowed-as-recorded-changeset, and the suite
> assertion flips with it."

Restore was refused in A3a for one reason only: A3a removed the gate before A3b built the recording,
and an *unrecorded* bulk rewrite of a sent plan is worse than either state. The refusal is scaffolding
around the designed A3a→A3b window, not a product decision.

The conversion is therefore this ticket's, and it uses the same bulk-changeSet mechanism as
regenerate: one `PlanRevision` checkpoint, one `changeSetId`, one reason, one entry per resulting
change. The UI consequence line is [[GTC-197]] (A3c)'s, alongside the regenerate warning, and must
merge with it.

A matching comment sits at the guard itself in `src/lib/workflow.ts`, ending: *"If you are reading
this comment after A3b has landed, the conversion was missed."*

## Evidence — CLOSED 2026-08-03

**The designed window is closed.** Post-send changes are now both **allowed** (A3a) and **recorded**
(this ticket). `recordChange()` went from 0 call sites to 6 routes plus `removePerson` and
`restoreFromRevision`.

### `frozen-edit` deleted; the asymmetry between its three actions IS the ruling

499 lines removed. Redistributed:

| Action | Destination | Reason? |
|---|---|---|
| `reassign` | `POST`/`DELETE .../items/[itemId]/assign` | **Yes** — T1, at any response state |
| `edit_item` | `PATCH .../items/[itemId]` | **Only if T4** — an `ASK_FIELD` moved on an *answered* item |
| `toggle_critical` | `PATCH .../items/[itemId]` | **No** — Moment 4 §8.3 |

The `toggle_critical` line reverses today's behaviour and is the point: criticality *"does exactly
two things (the badge, and the assistant's message at red) and touches nothing else. It is entirely
a host-facing signal, never a guest-facing pressure."* frozen-edit interrogated it. That was the
"stricter than the ruled model" contradiction the discovery report flagged.

`handleReassign`'s two correct halves were preserved rather than reinvented: the why became
`recordChange`'s `reason`; the release notification became `onAssignmentReleased()`, a no-op whose
**call site is now fixed inside the transaction that knows the facts** — [[GTC-176]] (D3) fills the
function, not twenty routes.

### ⚠ Bug found by the new ledger assertion

Sequence allocation broke the moment `logAudit` and `recordChange` coexisted on one event.
`logAudit` writes lifecycle rows with a **NULL** sequence; **Postgres orders NULLS FIRST on DESC**;
so `recordChange`'s max-sequence lookup returned a NULL row, `(null ?? 0) + 1` handed out sequence 1
every time, and the second changeSet violated `@@unique([eventId, sequence])`.

Invisible to [[GTC-168]]'s unit tests, whose fixture event contained only `recordChange` rows — the
two writers never met until this ticket put them on the same event. Fixed with
`sequence: { not: null }`, explained at the call site, and regression-tested
(`ledger-record-change-test.ts`, "a NULL-sequence lifecycle row does not reset the counter").

**This is the argument for the ledger assertion having been added at all.** Asserting only that the
mutation *succeeds* would have shipped a ledger that silently stopped versioning after the first
changeSet per event.

### Restore converted — landed HERE, not deferred

Per the doctrine recorded in `f679665`: A3a's refusal was interim scaffolding around the unrecorded
window, not a product decision. With recording in place it converts to
**allowed-as-recorded-changeSet**: a checkpoint revision first (nothing is lost by moving forward —
Hinge §2), then one changeSet carrying the host's why, identical in mechanism to a post-send
regenerate.

**It landed in this ticket rather than being flagged for the merge.** The wiring made it natural, and
leaving a refusal in place for one more ticket is exactly how scaffolding hardens into doctrine. The
suite assertion flipped with it — Suite 7 is now *"Bulk restore — recorded, not refused"*.

The UI consequence line is [[GTC-197]] (A3c)'s, alongside the regenerate warning, and must merge with it.

### `AuditActionType` enum — not added, and why

A2 deferred this here on the grounds that the writer set would be known once routes were wired. It
now is, and **it is two vocabularies, not one**: `recordChange` writes plan changes (typed by
`ChangeAction`), `logAudit` writes lifecycle lines. Freezing both into a single Postgres enum would
cement that conflation in the schema at exactly the moment `logAudit` is mid-retirement, and needs a
text→enum cast that fails on any historical value outside the enum — a one-way migration risk taken
for something already solved.

The prize was compile-time safety, so `logAudit.actionType` is now a TS union
(`AuditLifecycleAction`). **A typo is a type error today, on both paths, with zero migration risk.**
The Postgres enum belongs with `logAudit`'s retirement, not ahead of it.

### Mini-send clock live

`PersonEvent.sentAt` is written at all four add-a-person sites (`people`, `batch-import`,
`households`, `reconcileMembers`), and **the press stamps every existing member at once** — Hinge §7,
"experientially it is one act". `isMiniSend` = `personEvent.sentAt > event.sentAt`; no extra field.

### The F1 handoff

`onMaterialChange()` fires at `PATCH /api/events/[id]` — the T5 site, which before this ticket had
**no status gating and no audit logging at all**, so a post-send date change left no trace whatsoever.

Stated plainly, as the plan requires: **until [[GTC-183]] (F1) lands, a post-send date change is
recorded but nobody is re-asked.** That is why F1 is a *correctness* dependency of Epic A, not a
later feature. [[GTC-197]] (A3c) ships the sentence that tells the host so.
