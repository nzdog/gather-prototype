# GTC-207 — Confirm and guard child assignment-eligibility

## Why this exists

GTC-172 (C1) established absolute child-MESSAGE exclusion under Moment 4 §10.6: a
CHILD-role person never receives a system message, regardless of contact info,
because they are managed by their parents — the system talks to the parent.
During C1 it was flagged that nothing filters CHILD from being ASSIGNED an item or
task, and that was left out of scope pending a ruling. The ruling: **that is not a
gap. It is the intended design.** A "Kid with a job" is a ~15–16-year-old captured
specifically so they can hold a real task (do the dishes). They are assignable.
They are simply not messaged directly — their parent is.

So the two eligibilities are deliberately different, and must stay different:

| | Message-eligible? | Assignment-eligible? |
|---|---|---|
| CHILD (kid with a job) | **No** — §10.6, parent is messaged | **Yes** — the whole point of capturing them |
| PRIMARY_CONTACT / PARTNER / GUEST | Yes | Yes |

## The actual risk this guards

The risk is now the *opposite* of a hole. A future session, seeing C1's fail-closed
child-message exclusion, could pattern-match "children are excluded" and add a CHILD
filter to assignment eligibility — silently breaking the kid-with-a-job model so a
capturable, jobbable teenager can no longer be given the dishes. This ticket makes
the boundary explicit in code and pins it with a test so that regression can't land
quietly.

## Scope

- **Do NOT add any child filter to assignment eligibility.** Confirm, by reading
  the assignment path, that CHILD-role people are currently assignable and that no
  role gate exists there. If one exists, that is the bug — surface it before
  changing anything.
- Add a short, explicit comment at the assignment-eligibility site (and/or the
  child-exclusion predicate module) stating that the §10.6 message exclusion is
  MESSAGE-ONLY and must never be extended to assignment — the kid-with-a-job is
  assignable by design (ref GTC-207, this ticket).
- Add a RED→GREEN-style guard test: a CHILD-role person WITH a valid assignment
  context CAN be assigned an item/task, and remains assigned after the assignment
  round-trips. This test exists to FAIL if a future change adds a child filter to
  assignment. Pair it with the existing child-MESSAGE-exclusion test so the two
  invariants sit side by side: child not messaged, child IS assignable.

## Explicitly NOT in scope

- Any change to message eligibility (C1 owns that; §10.6 is absolute and untouched).
- Any change to how a child is captured or roled.
- Whether a parent should be notified of a child's assignment — that is a separate
  product question (a child does a job, does the parent get told?). NOT decided here;
  flag if it comes up, do not build it.

- [ ] Explicit code comment records the message-only boundary of §10.6, referencing

- [ ] Guard test: a CHILD-role person can be assigned and stays assigned; the test

## Stop conditions

Standard eight. No migration expected (this is a guard + test, not a schema change) —
if the confirmation reveals a schema change is somehow needed, STOP and surface it,
because that would mean the assumption behind this ticket is wrong.

route (`src/app/api/events/[id]/items/[itemId]/assign/route.ts`), its coordinator-token

own "Flagged, not fixed" note: "Nothing filters CHILD from being *assigned* an item or
