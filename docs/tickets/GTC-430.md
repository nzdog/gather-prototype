## Why

The front page's second button, "See it in action ->"
(src/app/page.tsx, href "/demo"), opens src/app/demo/page.tsx. That
page is a client page. It draws the heading "Gather" and, only when
NODE_ENV is "development", the button "Try it yourself". The sample's
"Create Your Event" page (src/app/demo/new/layout.tsx) is a not-found
anywhere but development. GTC-425's switch GATHER_DEMO_START
(`isDemoStartOn()` in src/lib/demo/start-switch.ts, exact value "on")
closes only the copy-start shape of the API route.

So in production a visitor who taps "See it in action" lands on a page
with a heading and nothing else. Turning the switch on at Railway
would not open the demo either: the page and the sample page are still
development-only (GTC-392's part D is not done).

findings are true as written.

## The choice: a server page and one small client button

The switch is a server-side setting, so the page has to be a server
component to read it (never in the browser, never as a NEXT_PUBLIC
variable). A server component cannot carry the button's `onClick`, so
the button moves, unchanged, into one new client component file:

```
src/components/demo/TryItYourselfButton.tsx   (new, named before it was made)
```

A plain link styled as the button would have been one file, but
existing checks read the button element itself (demo-tweaks D1 and
-2 F1 count `<button>` elements and ban any `<a>`; demo-tweaks D3 and
-2 N12 read the button's `window.location.assign`). A link would turn
D1 and F1 red, and they are not checks of what this ticket replaces.
So the component is the smaller edit by the checks.

The page keeps its two constants (the label and the sample page's
address) and hands them to the button, so the checks that read those
constants in the page stay as they are. The page draws the rendered
button exactly as before (the same markup).

In a production build NODE_ENV is "production", so the condition is
false before the switch is ever read: the page is the heading and the
note, whatever the switch says.
