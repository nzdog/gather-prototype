# GTC-334 — the nudge cron's health still says "is an SMS provider configured"

**Status:** Open — a stub, filed 2026-09-27 at [[GTC-189]] slice 8b's hold, on founder ruling D3:
*"leave it. File a stub that moves send health to the dispatcher."* Not scoped.

---

### Signal

[[GTC-214]] made `/api/cron/nudges` report unhealthy — `ok: false`, HTTP 500 — when no SMS provider
is configured, or when every send it attempted failed: a cron that could not send must not read as
fine to a monitor. `isNudgeRunHealthy` in `src/lib/sms/nudge-scheduler.ts` is that rule.

Since [[GTC-189]] slice 8b the nudge scheduler sends nothing. It queues one `OutboundMessage` row per
reminder, and `/api/cron/outbound-dispatch` (`drainOnce` in `src/lib/press/dispatch.ts`) sends them —
by email as well as by text. So:

- the nudge cron reports unhealthy on a deployment with no SMS provider even when every reminder it
  queued is an email the dispatcher will send; and
- nothing reports it when the DISPATCHER's sends all fail, which is where a send can now fail.

Left as it is by ruling D3, because `tests/nudge-provider-gate-test.ts` pins GTC-214's semantics, and
that suite guards the scheduler slice 8b rewrote.

### The move, named and not designed

Send health belongs to the run that sends: the dispatcher's cron, per channel. The nudge cron's
health becomes "did it queue without error". GTC-214's pinned assertions move with it rather than
being loosened.

### Unknowns

1. What the dispatcher's run should call unhealthy when one channel is unconfigured and the other
   works — the case this environment is in (no TNZ; a Resend key that does not authenticate,
   [[GTC-247]]).
2. Whether any monitor reads `/api/cron/nudges`'s status code today.
