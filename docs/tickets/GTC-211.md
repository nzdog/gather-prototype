### Scope

`GTC-176.md` scopes release notification as **porting a working mechanism** from the deleted
`frozen-edit/route.ts`. There is nothing to port. The deleted route's `handleReassign` wrote one
`logInviteEvent` row and pushed a personId onto a local `const notificationsSent: string[]`,
returned to the client as `notifications: { sent: [...] }` with `failed` a hardcoded literal.
Its complete import list was `next/server`, `prisma`, `requireEventRole`, `logInviteEvent` — no
SMS client, no email client, no carrier of any kind. **A log write named as a send.** This was
re-derived six independent ways (no carrier, helpers followed into their definitions, no
deferred execution, no Prisma hook layer, no InviteEvent-driven dispatch, no client follow-up)
and it holds.

The error has propagated into merged code: `src/lib/ledger.ts:587-588` asserts *"This is the
half of frozen-edit's handleReassign that was correct and is preserved here rather than
reinvented later."* That sentence is false and should be corrected to say the **call site** is
preserved — clear it in the same pass, since a doc-only fix leaves it in `src/`.

**But D3 is NOT greenfield.** The first audit called it *"greenfield SMS work in an opt-out
zone"* and set its "high" effort on that premise; the confirmation pass overturned it. A
complete, directly reusable stack already exists — verified in place:

| Asset | Location |
|---|---|
| `sendSms` — E.164 validation, per-host opt-out, TNZ/Twilio routing, logging | `src/lib/sms/send-sms.ts:45` |
| `sendNudgeEmail` — Resend-backed | `src/lib/email.ts:31` |
| Quiet-hours gate pattern | `src/lib/sms/nudge-sender.ts:114-138` |
| Child gate (§10.6 allowlist) | `src/lib/eligibility/child-exclusion.ts:65` |
| Household channel resolver, cross-household capable | `src/lib/households/channel.ts:46`, `:62` |
| Row-queue + cron dispatcher over `WrapUpLink` | `src/lib/wrap-up.ts:106`, `:157` |
| Household→adult re-routing, fails closed on CHILD | `src/lib/sms/proxy-nudge-eligibility.ts:68-113` → `proxy-nudge-sender.ts:39` |

What D3 actually has to write: one template function; a body for the placed no-op
`onAssignmentReleased` (`src/lib/ledger.ts:590-596`); **one** extra call site at
`people/[personId]/route.ts:70` (the PUT team-change, where `PersonEvent` survives); and a
person→household→channel lookup reusing the existing resolver. That is **wiring an existing
carrier into a placed hook** — materially smaller than the current ticket implies.

Two further corrections for the re-scope:

- **One missing call site, not two.** The other candidate (`people/[personId]/route.ts`, person
  removal) deletes the recipient's `AccessToken`s and their `PersonEvent` in the same
  transaction — a release message there would carry a dead link to a non-participant. That is a
  product decision, not an omission.
- **Real NZ effect is gated on TNZ go-live.** Every nudge-family recipient is forced to `+64`
  (`isValidNZNumber` = `/^\+64\d{8,10}$/`, `phone.ts:34-38`), and `send-sms.ts:98-105` returns
  `blocked: 'SMS_DISABLED'` for `+64` when `TNZ_AUTH_TOKEN` is absent — which it is on every
  dev machine (`grep -c TNZ .env` = 0). D3 can be built and tested now; it will not deliver in
  NZ until TNZ is live. Do not scope it as though shipping it turns messages on.

Related: **GTC-213** (on-demand wrong-nudge) is the argument *for* building D3 sooner — the
population D3 targets is the same one currently exposed to the wrong message.
