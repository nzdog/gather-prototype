# GTC-292 — fixtures clean up rows they cannot prove they made

**Status:** Open — filed, not executed. Filed 2026-09-13 | **Branch:** TBD
**Severity:** [ ] Critical [ ] High [x] Medium [ ] Low
Escalated (brand/trust risk): [ ] No — no production path found and no loss
found. See *Severity, argued*.

**Filed 2026-09-13** from an automated review of a diff that named two files.
Confirmed against the tree at `b3e9f31` on `feat/moment-one-redesign`, and
swept across every file in `tests/` — the list below is the tree, not the diff.

**Same family as the two fixture findings in GTC-192's standing warning** (6c's
fixture that encoded the bug, 6c's walk fixture that was not idempotent). A
proposed third rule is at the end of this ticket; placing it is the founder's

---

### Signal

**Expected**
A test's cleanup removes only rows the test created, or rows reachable from
ids the test captured at creation. Running a test cannot delete a row that
existed before it started, and cannot delete another run's rows.

**Actual**
Cleanup keys on things that are not ownership: a person's name, a shared email
domain, a fixed phone number, or "the first row in the database that matches".

**Smallest failing case**
Remove a household member named "Matt" through the real households edit flow,
then run `npm run test:household-edit` — its cleanup deletes that real Person.

### ⚠ THE SAME FAMILY, FROM THE OTHER END — A FIXTURE THAT CLEANS UP AT THE WRONG TIME

*Added 2026-09-19 on founder instruction, out of a read of `gather_dev`.*

This ticket is about fixtures deleting rows they did not create. **`tests/security-fixtures.ts` is
the mirror image: it deletes rows it DID create, and then leaves a fresh set behind.**

`cleanup()` runs at the **START** of the run — `console.log('Rebuilding fixtures...')`, then
`await cleanup()`, then `generateFixtures()` — so the four `Security Test Event` boards are
**permanent residents of `gather_dev`, re-created on every `npm run test:security`.** The suite's
own comment at its coordinator block says *"this suite leaves nothing behind"*, which is true of
that one user and false of the fixtures.

**WHY IT MATTERS BEYOND TIDINESS, AND IT IS MEASURED:** three of those four events carry
`Event.sentAt` with **zero** `OutboundMessage` rows, so they are **three of the eight events in
[[GTC-322]]'s population** — the boards whose guests slice 8 would chase about an ask nobody
composed. **Running the security suite re-creates a third of that landmine.** It also means any
measurement of "how many legacy pressed events are there" depends on how recently the security
suite ran.

**The rule this adds to the ticket's family:** *cleanup at the start of a run is not cleanup; it is
a reset. A fixture that cannot be told from real data by the NEXT reader has not been cleaned up,
however reliably it is rebuilt.* The fix is the same shape as the rest of this ticket — teardown in
a `finally`, keyed on what the run can prove it made — and it is not made here.

---

### What it costs — specific

**Can something outside `tests/` create a Person with these names?** Yes, and
in exactly the guarded shape. `POST` in `src/app/api/events/[id]/households/route.ts`
and `createNewMember` in `src/lib/households/reconcileMembers.ts` create a
Person from whatever name the host types, `email: null` when none is given.
Removing a member deletes only the `PersonEvent` (the delete loop in
`reconcileMembers`), leaving the Person memberless and emailless — which is
precisely what the guards admit. gather_dev holds 45 such rows today. Also
`scripts/seed-gtc-133-test-event.ts` creates Matt and Charlie (7 of each exist;
all still have memberships, so none are currently in reach).

**What gets deleted if a real person matches.** Verified against the live FK
rules in gather_dev (`pg_constraint`), not the schema file:

- Cascade: `PersonEvent` (none, by the guard), `AccessToken`, `HostMemory`,
  `SmsOptOut` where they are the host.
- Set null: `AuditEntry.actorId` (`actorName` is frozen and survives),
  `InviteEvent.personId`, `SmsDeliveryReport.personId`, `Team.coordinatorId`,
  `Event.coHostId`.
- Restrict: `Assignment`, `WrapUpLink`, `Event.hostId`. Prisma's `deleteMany`
  is one `DELETE`, so **one restricted row aborts the whole statement** —
  nothing is deleted and the test's `finally` throws instead.

So the household tier's realistic victim is a removed household member no screen
shows any more, whose history rows lose their person link. The ledger's
`'Renamed Later'` has no guard, but it is not a plausible real name. Tier 1 needs
no coincidence at all.

**Can two test files delete each other's rows?** Yes, if two run at once.
Nothing in the repo runs them concurrently — `ci.yml` runs no test suites and
the Husky pre-commit runs `lint-staged` only — so this needs two runs started by
hand or by two sessions against one gather_dev.

- Household tests: overlapping names (Matt in two, Charlie in two). A removed
  member is memberless between its removal and its own test's cleanup, so the
  other test's cleanup can delete it. Current assertions read `PersonEvent`, not
  `Person`, so no false result was found from that alone. The sharper case:
  `households/route.ts` and `reconcileMembers.ts` write the Person and its
  `PersonEvent` as separate statements, not one transaction. A cleanup landing
  in that gap deletes a live member mid-request, the `PersonEvent` insert fails
  its FK, and the other test goes red for a reason that is not its own. Narrow,
  unobserved, real.
- `security-fixtures` against the `@test.local` suites: the other suites' hosts
  host events, so Restrict aborts the security cleanup and `test:security` — the
  preflight gate — fails for a reason not its own. A guest with no restricting
  rows is deleted mid-run.
- `ledger-record-change` against itself (two pids): each deletes the other's
  `'Renamed Later'` host, Restrict aborts, and each leaks its own host row.

**No localhost guard.** Of the files above, only `security-fixtures.ts` refuses
a non-local `DATABASE_URL`. The rest would run wherever the variable points.

**Has it already happened?** No evidence found — and the database cannot
supply evidence either way. Checked in gather_dev: 0 of 72 `AuditEntry` rows
with a null actor, 0 of 45 `InviteEvent` rows with a null person, 0 Persons left
with any tier-2 name in reach, 0 ledger test leftovers. But those set-null
traces only appear if the eaten row had history, and the victim shape usually
has none (all 45 current memberless emailless Persons have zero tokens, audit
rows and invites). A cascaded row leaves nothing. gather_dev arrived by pg_dump
from another machine and has no statement log. **This is an absence, and per
GTC-192's standing warning it is not evidence.** Schema-verification Test 5 has
certainly deleted a real row every time it ran; whether it has run on this data
is unknowable.

### Severity, argued

Medium, not escalated. Against High: dev database only, no CI path, no loss
found, and the household tier's guards narrow the victim to rows no screen
renders. Against Low: one fixture deletes a real row by design on every run; a
concurrent run can turn another suite red for a reason not its own, including
the preflight gate; none of the non-security files refuses a non-local
database; and gather_dev is both the measurement base GTC-192's standing
warning depends on and home to the kept GTC-192 demo boards. A fixture that
silently removes rows damages exactly the evidence those rules protect.

### Proposed third rule for GTC-192's standing warning (not yet placed)

> **EVERY FIXTURE DELETES ONLY WHAT IT CAN PROVE IT MADE.**
>
> Clean up by ids captured at creation, or by rows reachable from them — the
> event the fixture created, and the memberships under that event, read before
> they go. Never by a name, a shared email domain, a fixed phone, a fixed id
> another file could reuse, or a `findFirst` over data that was already there.
> Rows the code under test mints are found by walking from the fixture's own
> event, not guessed by what they are called. **The tell is a filter that would
> match a stranger.** And "the suite left nothing behind" is an absence: prove it
> with a decoy that shares the name and survives.

It is the mirror of the idempotency rule. That rule says a fixture must not be
changed by what came before it; this one says a fixture must not change what
came before it. It applies to every suite, not only glance slices, so it
arguably belongs in GATHER-BUILD-CONSTANTS.md under Test Commands, with a
pointer from the GTC-192 warning.
