# GTC-248 — C3: Exclude coordinators from household channel selection

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** low, to reconfirm at
preflight

### Context

Surfaced during GTC-187's Phase 1 audit (message-composition), not by a report or its own
reproduction: `validateChannelTarget` in `src/lib/households/channel.ts` (GTC-172 / C1's
deliverable, already closed) checks only that a candidate channel belongs to the same event and
is not CHILD-role, via `isMessageableRole`. It does not check `PersonEvent.role` at all. A
household's picked channel can therefore resolve to a person whose role is `COORDINATOR`.

`ensureEventTokens` in `src/lib/tokens.ts` never issues a PARTICIPANT-scope `AccessToken` to a
coordinator — its own comment is explicit: "Coordinators do NOT get PARTICIPANT tokens." A
coordinator holds only a COORDINATOR-scope token (`/c/{token}`, a different page entirely). A
household whose channel resolves to a coordinator therefore has no `/p/{token}` for the
guest-side ask/tap flow (GTC-189 / I2, GTC-191 / I4) to link to. Nothing in `validateChannelTarget`
or, so far as this audit went, the picker UI stops a host from choosing a coordinator as their
household's contact — this is a reachable gap, not a hypothetical one.

### Scope

**Fix here:**
- Exclude coordinators (`PersonEvent.role === 'COORDINATOR'`) from valid channel targets in
  `validateChannelTarget`, alongside the existing CHILD exclusion.
- Confirm whether the household-channel picker UI (built under GTC-172) independently needs a
  matching change to stop *offering* coordinators as candidates, rather than only rejecting them
  server-side after the fact — check before assuming the validation-layer fix alone is
  sufficient.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- `resolveHouseholdChannel` itself — it resolves whatever was picked, or falls back to the
  primary contact; the fix belongs in validation, not resolution.
- `isMessageableRole` / `MESSAGEABLE_PERSON_EVENT` (the household-ROLE gate that excludes
  CHILD) — a distinct axis (`PersonEvent.householdRole`) from the one this ticket touches
  (`PersonEvent.role`). Do not conflate the two checks into one.

**Preferred fix (not implemented):** add a `role !== 'COORDINATOR'` condition to
`validateChannelTarget`'s target check, alongside its existing `isMessageableRole` check. Confirm
whether any existing household already has `contactPersonEventId` pointing at a coordinator — if
found, that is a data question (backfill/reassignment), not this ticket's to resolve silently;
flag and stop rather than clear or reassign it.

### Dependencies

GTC-172 (C1, closed) — this fixes a gap in its shipped `validateChannelTarget`.

### Acceptance

- [ ] `validateChannelTarget` rejects a coordinator as a channel target, with an error on the
      same pattern as the existing CHILD rejection.
- [ ] Regression test: a household whose channel is set to a coordinator fails validation (and,
      if the picker UI is touched, cannot be selected there in the first place).
- [ ] Existing CHILD-exclusion behaviour unaffected — confirmed by test, not assumption.
- [ ] `npx tsc --noEmit` clean, build passes, security suite exits 0.
