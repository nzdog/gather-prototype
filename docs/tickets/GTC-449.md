**Where the child-or-adult status lives.**

  PRIMARY_CONTACT, PARTNER, GUEST, CHILD, or empty (empty means an adult added

  `src/lib/eligibility/child-exclusion.ts` (Moment 4 §10.6, "absolute").

- The household routes return members with Prisma `include`, so a new column on
  `PersonEvent` reaches their responses without edits. The pre-flight route

### Contact details Gather will not use — said plainly

Ruling 2 holds a child's number on the child's row while the choice is decide
later, and ruling 15 says that "number" there means contact details: the number
AND the email, under one rule. The rule: **held on the row for decide later,
left out for don't message, never used until the host chooses message.**

**While a child is on decide later, the row holds contact details that Gather
will not use.** The child is stored as CHILD; every gate above treats the row
as a child; nothing that sends, links or counts will read the new marker. The
marker never lets the details be used. It records only that the host has not
settled the question. They are used only if the host chooses message: the row
then becomes an adult (GUEST) by the existing path, and the tick is hers.

What this costs, stated so it is a choice and not an accident: a young person's
number and email are kept that no Gather path will contact. Who can see them:
the host and co-host on the household and pre-flight screens; they are never
published (the directory and links exclude children).

How long they are kept (ruling 17): when the host settles a decide-later child
to "don't message" in the household form, the form blanks the held number and
email, so only a decide-later child holds contact details. One exception
(rulings 33 and 34): if the person has an `EmailOptOut` row on any event, the
server refuses to clear the email and keeps it, and the phone is still
cleared. Which save door and which part of the form does the blanking, and how
the server recognises the settle, is in step S2.3.

What ruling 17's sentence does not reach, said so it is not read as more than
it is: it is true of the flows this ticket builds. It is not true of children
saved before this ticket, nor of a kid row typed with the tick off and Decide
later off, which keep whatever they hold, as today (ruling 19). Stage 2 blanks
nothing except the ruling-17 settle. The founder confirmed this reading
(ruling 31): ruling 17 covers the flows this ticket builds. No backfill.

**In plain words, the blanking can reach another host's guest list (ruling
27).** Gather does not keep one copy of a person per event. When a host types
a row, the person is matched by email address and first name, "on this event
or another" (GTC-293, the ruled trade), and the match is not limited to one
host. So one person record can sit behind rows in several events, including
events run by other hosts. Blanking a decide-later child's email and phone
writes to that shared record. Anyone else's event row that uses the same
person then shows no email and no number for them. If that is another host's
adult guest, that host's guest list has changed, without that host doing
anything. The founder accepted this (ruling 27): it is what the edit door
already does for every edit of a person's details. A test pins the behaviour
(see the tests). One consequence of that sharing is named as its own risk
below (Named risk 1, ruling 30).

### Named risk 1 — an unsubscribed address can be emailed again (30, 33, 34)

Found by reading only, 2026-11-02, at `128b341`. Nothing was run, and no Zone 9
file was touched. The risk is named here. **Ruled: option A1 (ruling 33),
widened to an opt-out on any event (ruling 34)**, which closes it for the
settle path; see "The ruling" at the foot for exactly what that does and does
not cover. The choices as put to the founder are kept below, so the ruling can
be read against them.

**The finding, in plain words.** Yes, it can happen, but only if all four of
these hold:

1. The guest unsubscribed by clicking the link in the email. (A guest who
   reported the email as spam instead is also blocked by address, everywhere,
   and is not exposed: see "What is already safe".)
2. That guest's email address is then removed or changed on their stored
   person record. Any edit through the household edit door can do this.
3. The same address is then typed on a NEW row in the same event where they
   unsubscribed: a new member, an import, a people add. Gather finds no
   person holding that address, makes a new person, and the new person carries
   no unsubscribe. (Typed into the row it came from, the old person gets the
   address back and the unsubscribe still applies.)
4. That event is still sending email to the new row. Before the press it joins
   the press; after the press the late-arrival sweep queues it.

Then Gather emails the address that unsubscribed from that event. The guest can
unsubscribe again from the new email's link.

**The same risk exists today.** Yes. The household edit door already writes a
blank email when a host clears an email box, for any member, a child included.
So the sequence needs no settle and no shared person: one host clears a guest's
email, then types it again on a new row. What this ticket changes is how likely
the steps are. The settle (ruling 17) makes blanking an intended act for every
settle that holds an email. Ruling 27 lets one host's settle land on a person
that another host's event uses, which starts step 2 from outside the event.
Stage 3's picking will make step 3 (a new row made from a pick) routine.

**How an email unsubscribe is stored and checked.**

- Stored: one `EmailOptOut` row keyed by the person and the event
  (`@@unique([personId, eventId])`), with the time and the token that was
  presented. It holds **no address.** It is written by the `POST` handler in
  `src/app/api/unsubscribe/[token]/route.ts` (an upsert on the person and
  event named in the signed token; `readUnsubscribeToken` in
  `unsubscribe-token.ts`, whose token carries a person id and an event id and
  nothing else), and, for a spam report, by the `COMPLAINED` branch of
  `pollOne` in `src/lib/email-delivery/delivery-poll.ts`.
- Checked, by person and event and never by address. `readAskPreview` in
  `ask-preview.ts` loads the event's opted-out person ids once with
  `listEmailOptOutsForEvent` and marks each member with `emailOptedOutFact`;
  `askChannelOf` and `chaseChannelOf` in `channel-chooser.ts` refuse on that
  fact before they look at the address. The press (`pressSend`), the outbound
  drain (`drainOnce`) and the late-arrival sweep (`enrolMiniSends`) all take
  their answer from `readAskPreview`. The other senders ask
  `getEmailOptOut(personId, eventId)`: `dispatchPendingWrapUpMessages` and
  `retryUndeliveredThankYous` (`wrap-up.ts`), `retryUndeliveredFollowups`
  (`decide-by-sender.ts`), `findDecideByFollowupCandidates`
  (`decide-by-eligibility.ts`), `resolveSubject` in `resend.ts`, and the
  by-hand nudge route.
- The one check by address is the provider's block, `EmailBlock`, read through
  `listEmailBlocks` in `email-block.ts` and applied to the address on the
  person's record as it is now.
- So: an unsubscribe is by person and event; a block is by address; a spam
  report writes both (`recordEmailBlock` plus the opt-out); a hard bounce or a
  suppression writes the block only.

**How a person is picked or made when a household is saved.**
`findOrCreateCapturedPerson` in `src/lib/households/capturePerson.ts`, called
for every new row (`createMember` in `households/route.ts`, `createNewMember`
in `reconcileHouseholdMembers`, and the people and batch-import `POST`s):

- With an email: take every person whose email equals it, ignoring capitals (on
  a sample event, only people already on that sample); keep those whose first
  name matches the typed one (the first word, lower-cased); of those take the
  host's own person, else one already on this event, else the lowest id. The
  match is not limited to one host or one event ("on this event or another",
  GTC-293).
- If none is kept, or the row has no email, make a new person. A row without an
  email always makes a new person; phone numbers are not matched.
- An existing row is not matched again. `updateExistingMember` updates that
  row's person in place, by `personEventId`, writing `email: member.email ||
  null` and the phone, so a blank box becomes null on the person.
- Removing a row (the removal loop in `reconcileHouseholdMembers`) deletes the
  membership and not the person, so the person and their unsubscribe stay.

**The sequence, step by step.**

1. The click: the `POST` handler in the unsubscribe route writes
   `EmailOptOut(P, E)` for person P and event E.
2. The blank: `updateExistingMember` sets P's email to null, through the edit
   door (today by a host clearing the box; with this ticket also the settle).
3. The retype on a new row: `createNewMember` or `createMember` calls
   `findOrCreateCapturedPerson`; no person holds the address, so
   `db.person.create` makes P2.
4. The send: `readAskPreview` builds E's opted-out set, P2 is not in it, and no
   `EmailBlock` holds the address; `askChannelOf` returns email; `pressSend`,
   `enrolMiniSends` and `drainOnce` send to the address.

**What is already safe.**

- Texts. The text opt-out is looked up on the phone number across the whole
  account (`SmsOptOut`, read by `readAskPreview` from the roster's numbers), so
  a number blanked and typed again finds its STOP.
- A spam report: it also writes an `EmailBlock` on the address, so the address
  stays blocked whichever person carries it. Bounces and suppressions block the
  address too.
- Another event: an unsubscribe is a no to one event only (GTC-296 ruling 1),
  so a new event was never covered. Nothing is lost there.
- Typing the address into the row it came from.

**What would close it** (the founder's choice; none is decided here; least
change first):

- **A. Refuse to blank where it would leave an unsubscribe behind.** In
  `updateExistingMember` (`reconcileMembers.ts`), skip nulling the email when
  the person has any `EmailOptOut` row. Variants: A1, only on the settle path,
  leaving today's manual clear as it is; A2, on every blank, which closes
  today's path too but changes ordinary edits (a host could no longer clear an
  unsubscribed guest's email); A3, skip on any other membership at all, which
  also closes ruling 27's reach but would rarely blank a returning household,
  because the same person sits in last year's event, so ruling 17 would mostly
  not apply. The phone needs no guard, since its opt-out is on the number.
  Cost: one read and one rule in one file; the form shows blank but the server
  keeps the email, so a reloaded form shows it again, which needs a sentence
  worded (a ruling); item 12 flips. Zones: none edited. A1 and A2 read Zone
  9's table from non-zone code; A3 reads only memberships.
- **B. Check the opt-out by address as well as by person.** The opt-out row
  holds no address and the blanking removes the only copy, so this needs an
  address stored on `EmailOptOut`: a schema change to a Zone 9 model and a
  Zone 5 migration, changes to both writers (the unsubscribe route, `pollOne`)
  and to every reader (`email-opt-out.ts`, `readAskPreview`, the chooser's
  context, wrap-up, decide-by, `resend.ts`, the by-hand nudge), and a backfill
  that cannot recover addresses already blanked. Zones: 9 (read-only) and 5.
  The largest, and not possible without lifting Zone 9.
- **C. Do not blank the shared record: give the child's row its own person
  without details.** It leaves the shared person, its address and its
  unsubscribe untouched, and closes ruling 27's reach as well. But a person
  carries the child's items (assignments), links (tokens) and nudge history,
  which would have to move to the new person, and it reopens GTC-293's identity
  rule. Zones: the Zone 3 neighbourhood (`AccessToken` hangs on the person).
  Large.
- **D. Accept it, as today.** Nothing to build. The risk stays named and open;
  item 12 pins the outcome, so it is a known behaviour and not a surprise.
  Zones: none.

Least change that closes it, as put: A1, then A2. B and C cost far more.

#### The one deploy: what it risks that two deploys would not, and the undo

Said plainly, as ruling 18 asks.

What is the same as with two deploys. The build script runs `prisma migrate
deploy` before `next build` in the same build, so the new code is never built
against a database without the column; if the migration fails, the build stops
and the old deployment keeps serving. The change is additive, so the old code
keeps working beside the column while the build runs.

What one deploy risks that two would not:

1. **No proof of the migration alone in production.** The first of two deploys
   would show, in its build log and in the running app, that the column went on
   cleanly (no lock trouble, no surprise from real data) before any screen read
   it. With one deploy, if something is wrong afterwards, the migration and the
   screens cannot be told apart.
2. **The household save changes in the same press as the schema.** The three
   save doors and the form are the host's capture flow. A fault there reaches
   hosts at once. With two deploys the first would already be proven and the
   second would carry the fault alone.
3. **The rollback target has never run beside the column in production.**
   Undoing the single deploy returns to the code from before this ticket. That
   is safe on paper: the old code ignores the column, and rows marked "yes" are
   still CHILD. But two deploys would have given a middle rung, Stage 1's code,
   proven in production with the column present. S1.4(a) stands in for it on a
   copy; it is not production.
4. **One pull request holds both.** If Stage 2 needs more work, the migration
   waits on the branch with it and cannot be merged ahead. Merging to main does
   not deploy (auto-deploy is off), so waiting is harmless; but a manual deploy
   of main at any moment takes both together.

The same either way: a brief lock on `PersonEvent` while the column is added; a
build that fails after the migration applied (the old deployment keeps serving,
and the column is already there); a stale browser tab, which saves without the
marker and so clears it (the safe direction).

What reduces it (the plan's proposal, not a ruling): S1.4's two checks on the
throwaway copy; deploying away from a press; the founder's own walk after.

How to undo it:

- **The code.** The founder goes back to the last good deployment from
  Railway's Deployments tab, by hand. Railway's documentation (read 2 Nov
  2026; see the Railway checklist) says a **Rollback** reuses that
  deployment's stored image and variables with no rebuild, so no `migrate
  deploy` runs, and that it works only while Railway still holds the image (24
  to 360 hours, by plan). A **Redeploy** runs the build again from the same
  source, which includes `migrate deploy`; if that is from an older commit,
  S1.4(a) shows what `migrate deploy` does with a migration the older code
  does not have. He confirms this in his own dashboard before the press
  (ruling 48). After a Rollback he re-reads `GATHER_LIVE_SENDS`, since no
  build prints the check.
- **The data.** Nothing to undo. The column is "no" by default. Rows saved
  "yes" stay CHILD, so they are never messaged, by the old code or the new;
  their held details stay on the rows, unused, until the code returns. A child
  settled to "message" is a GUEST row, as the tick makes one today.
- **The column.** Left in place. Removing it is a second migration in a later
  deploy, only if wanted, and never an edit of the committed migration (Zone
  5).
- **A failed build.** Nothing new is served; the old deployment continues.
- **What a rollback cannot restore.** Details blanked by the host's own save
  when she settled a child to "don't message" (ruling 17). Nothing in the code
  can put them back.

#### What the code already gives Stage 3 (read 2 Nov 2026 at `128b341`)

This answers ruling 36's confirmation and ruling 44's check.

- **The browser knows who is signed in.** The root layout
  (`src/app/layout.tsx`) reads the session on the server (`getUser` in
  `src/lib/auth/session.ts`) and hands `user.id` to `Providers`, whose
  `ViewerIdContext` carries it to every page; it is null when nobody is signed
  in. Nothing is missing for a per-person key. It is the User's id, not the
  Person's. Signed out, the id is null and the list is not shown; it stays in
  storage and reappears when she signs in again.
- **Why "hidden, not deleted" is a different rule from the household drafts.**
  `sweepDrafts`, run by `Providers` on every page load, deletes every
  household draft that is not the signed-in person's, and all of them when
  nobody is signed in. It only scans keys that start `gather:household-draft:`
  (`DRAFT_PREFIX`), so a separate prefix is never touched, as C7 asks. Said
  plainly: "hidden" means hidden from Gather's screens. It is not protected
  from someone using the same browser profile signed in as her, or the
  browser's own tools; that is what A7 chose.
- **Per-tab storage already has a precedent.** `plan/new/page.tsx` keeps
  `gather_new_event` in `sessionStorage`. It is per tab and goes when the tab
  closes. A new tab does not inherit it, so the hand-off must be a same-tab
  navigation.
- **The saved-draft check can be waited for.** `Moment1InputForm` looks for a
  draft once per opening, in an effect that sets `draftChecked` when it is
  done. A hand-off applied after `draftChecked` equals the form is after the
  check.
- **The form's save check already refuses what ruling 41 leaves to it.**
  `validateEmail` and `validatePhone` run at save for every row, kids
  included: an overseas or malformed number is refused with the form's own
  words, and a named row needs its name. (If a request skipped the form, the
  server would drop an unusable number silently; a pick always goes through
  the form.)
- **Placements can be checked against what is saved.** `GET
  /api/events/[id]/households` already returns the saved households, and the
  setup page uses it.
- **No server change and no new API route is needed.** A new page is a new
  route in Next's sense, but the middleware matches only `/p/`, `/h/` and
  `/c/` pages and the `/api/p/` and `/api/c/` prefixes, so a page elsewhere
  needs no change (Zone 1 untouched); and the security route scan walks
  `src/app/api` only, with all 86 classified routes under it, so a page needs
  no classification (Zone 6 untouched). Ruling 53 confirms that ruling 44 means
  no new API route and that a new page is fine, since A13 and C1 give the
  contacts screen a page of its own (C13).
