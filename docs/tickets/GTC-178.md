### Context

Moment 4 spec §8.3/§10.3: two nudges, days 4 and 7 default (matching the real reply distribution
— first response ~41 min, cluster same-day, day-3 pair, stragglers from day 7 — Hinge §6), on the
**system's own schedule**, not "opened but no response." Criticality does not compress the
cadence — criticality does exactly two things (the badge, the assistant's message at red) and
touches nothing else.

⚠ **Correction (2026-08-27):** the phrase *"opened but no response"* in this paragraph and the
next is **factually wrong** and is retained unedited for the audit trail only. Nothing has ever
been anchored on `openedAt`. See Correction (i) under the 2026-08-27 rulings; the Scope bullet is
corrected in place.

Today: `nudge-scheduler.ts`/`nudge-eligibility.ts`/`nudge-sender.ts` run on **24h/48h
"opened but no response"** semantics — a different mechanism entirely. A third auto-nudge
(`sendRsvpFollowupNudge`, via `findRsvpFollowupCandidates`) force-converts `NOT_SURE` RSVPs at
48h "to force conversion" — this directly contradicts the maybe-state's "no nudges" rule (Hinge
§8) and is doubly obsoleted by D1 (GTC-174) retiring `rsvpStatus` as a directly-askable guest
question in the first place.

### Founder Rulings (2026-08-23)

**Ruling 1 — exhaustion is OUT of this ticket's scope.** The exhaustion counter, the exhausted
predicate, and the host-specified retry count (Moment 4 §4/§8.1's "door") are split into
[[GTC-251]] (E6 — nudge exhaustion and the red door). Rationale: cadence has a testable
definition of done today; exhaustion needs a counter that does not exist, a rule that does not
exist, and a red state on a Moment 4 screen that does not exist and is itself blocked on
[[GTC-192]]'s (J1) own open decisions. Splitting delays nothing real. **This supersedes the
"Inherited from D2" section below where it assigns exhausted-silence-red ownership to this
ticket** — that ownership now belongs to GTC-251; the section is left in place unedited for the
audit trail, with a redirect note added at its head.

**Ruling 2 — the clock fix IS in this ticket's scope.** `nudge-eligibility.ts`'s candidate-finding
switches from reading `Person.inviteAnchorAt` to reading `PersonEvent.sentAt`. Record this as a
**bug fix, not a refactor**: `Person.inviteAnchorAt` is global per-person, so a person who is a
guest at two events shares one clock, and the second event's nudge timing has been wrong since
the day `PersonEvent.sentAt` was introduced without `nudge-eligibility.ts` being updated to read
it. The schema comment on `PersonEvent.sentAt` in `prisma/schema.prisma` already names this
ticket as the fix: "Person.nudge24hSentAt/nudge48hSentAt carry the identical leak and move under
GTC-178 (E1)." **Open and NOT settled by this ruling:** whether the sent-side dedup state
(today `Person.nudge24hSentAt`/`nudge48hSentAt`) also moves off `Person` as part of this ticket,
and if so, to where. See "Storage-question analysis" below — a recommendation is recorded there,
not yet ruled.

**Ruling 3 — the proxy-nudge path stays out of this ticket**, unchanged from the original scope's
"if separate, leave it" below — and its known-broken frequency limiting now has its own ticket,
[[GTC-252]], filed today. No fix is proposed there; the risk is documented and left for a
separate decision.

**Ruling 4 — storage decision: `PersonEvent` columns, not `NudgeLog` (2026-08-23; reverses the
recommendation below).** Do NOT use `NudgeLog`. The sent-side dedup state (Ruling 2's open
question) moves off `Person` onto new columns on `PersonEvent` — the same table the clock fix
already reads (`PersonEvent.sentAt`), same per-event scoping, one write on success. Reasons:
- `NudgeLog` is a schedule-then-fulfil **queue**, not a log — corroborated by GTC-042's own
  wording ("write scheduling **and delivery** records to") and by `WrapUpLink` using the
  identical shape (a required due-time column paired with nullable outcome columns) as a live,
  actively-used queue with its own create-then-update-then-retry flow
  (`src/lib/wrap-up.ts`). This ticket needs a single write on success, not a queue.
- Adopting `NudgeLog` would mean `scheduledFor` duplicating `sentAt` on every write, the
  pending/retry lifecycle the shape implies never actually exercised, and a `nudgeType`/`status`
  vocabulary invented from nothing — no enum, no prior convention, zero production writes to
  that column today.
- **The second-migration argument for `NudgeLog` does not hold up.** [[GTC-251]] needs a
  host-specified *retry count* (Moment 4 §4's "with a retry count she specifies"), which fixed
  sent-timestamp columns — on `Person`, on `PersonEvent`, or on `NudgeLog` as currently shaped —
  cannot express regardless of which table this ticket picks. GTC-251 needs its own storage
  decision either way; avoiding a second migration was never actually achievable through this
  choice.

**Consequence: this is now a schema change, not a read-side-only fix.** Ruling 2 above still
frames the clock fix as reading `PersonEvent.sentAt` without mentioning a migration — that framing
is now incomplete. Adding the sent-dedup columns to `PersonEvent` requires a Prisma migration.
**Stop Condition 7 (DB schema migration required) now applies to this ticket** — see Scope and
Stop Conditions below, both updated accordingly.

**Ruling 5 — the gate question: delete `!hasOpened`, keep `!hasResponded`.** The ticket left open
whether each nudge re-checks opened/responded state or fires on elapsed time alone. Ruled:

- **`!hasOpened` is deleted.** Opening is *behaviour*. Hinge §6 refuses showing the host anything
  a guest did short of deciding — "the screen shows what the system will do, never what the guest
  did short of deciding" — and replaces seen-status with the nudge-clock ("*nudge in 2 days*").
  That promise is only truthful if opening cannot silently cancel it.
- **`!hasResponded` is kept.** Responding is a *decision*, and a decision stops the cadence.

**This adopts the 2026-08-04 accuracy audit's E-1b recommendation IN PART, NOT IN WHOLE.** E-1b
(`docs/04_roadmap/moment4-hinge-report-accuracy-audit-2026-08-04.md`) proposed deleting *both*
gates. Only the opened gate goes. Recorded explicitly so a later reader does not treat the audit
as fully adopted.

Note the asymmetry this removes: today the 24h leg gates on `!hasOpened` and the 48h leg gates on
`!hasResponded`, with no opened-check at all — two legs keyed to different states, which nothing
in the spec or this ticket ever accounted for. After this ruling both legs key to the same state.

**Ruling 6 — the backfill: none. CONDITIONAL, not settled.** The new `PersonEvent` sent-dedup
columns ship with no backfill. Nobody has been messaged, so there is no send history to preserve.

⚠ **This ruling holds on a condition, and the condition is load-bearing.** It is true *because no
live event has had nudges sent* — production has no SMS provider configured
(`isSmsEnabled()`/TNZ both false, so `send-sms.ts` returns `blocked: 'SMS_DISABLED'`). **If real
sends occur before this migration lands, the ruling lapses and must be revisited**, because with
fresh null columns every person past day-4 on a live sent event becomes eligible again on the
next 15-minute cron tick regardless of nudges already sent. That is a re-nudge burst with the
same TCPA/spam shape as [[GTC-252]], reached by a different trigger.

On lapse, the options in preference order:
- **(c) Derive per-`(person, event)` from `InviteEvent` where `type = 'NUDGE_SENT_AUTO'`**
  (written by `sendSms` in `src/lib/sms/send-sms.ts`, carrying `nudgeType` in metadata). Correct
  per-event. Caveat: `logInviteEvent` swallows its own failures by design, so the log is
  best-effort, not authoritative.
- **(a) No backfill, accept the burst** — documented fallback for rows (c) cannot resolve.
- **(b) Copy `Person.nudge24hSentAt`/`nudge48hSentAt` onto every `PersonEvent` of that person —
  REJECTED in all cases.** It would permanently replicate into the new per-event columns the exact
  global leak Ruling 2 exists to fix.

Whoever executes Phase 3 must re-check the condition before running the migration, not assume it.

**Ruling 7 — column names: `firstNudgeSentAt` / `secondNudgeSentAt`.** Ordinal, not timing-based.
[[GTC-179]] (E2) makes the days adjustable (standard/relaxed/off), so a `nudgeDay4SentAt` goes

*event* rather than its timing.

**Ruling 8 — finding C (the mini-send clock never fires): NOT fixed here. Filed as

afterwards"; all four add paths write `event.sentAt` instead, so `isMiniSend = PersonEvent.sentAt

[[GTC-196]] (A3b) owns that semantic. Disposal route is the **pre-launch data cleanup**, not a

**Ruling 9 — finding D (the backfilled cross-event clock): NOT fixed here. Filed as

Person.inviteAnchorAt` where present, so a person in two events can carry the first event's clock

### The proxy determination (Ruling 3, discharged)

Ruling 3 required this ticket to determine whether the day-4/day-7 logic is shared with the
proxy path and to record the answer either way. **Determination: SEPARATE — no shared cadence
code. The proxy path was not touched, and [[GTC-252]] is unaffected.**

`findProxyNudgeCandidates()` in `src/lib/sms/proxy-nudge-eligibility.ts` has **no time gate of
any kind** — no clock, no window, no stamp, nothing to retime. What it shares with the direct
path is four eligibility primitives and no cadence: `SENT_AND_LIVE`, `isValidNZNumber`,
`isOptedOut`, and `isMessageableRole`/`CHILD_SKIP_REASON`. None of them carry timing.

Consequence worth stating plainly for whoever picks up GTC-252: **this ticket did not fix, and
could not have fixed, the proxy path's missing frequency limiting.** The new
`src/lib/nudge-cadence.ts` is reusable there — it is pure and takes a `sentAt` — but which
clock a household nudge should count from is exactly the open storage question GTC-252 records
as undecided, and this ticket has no mandate to settle it.
