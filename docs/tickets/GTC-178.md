# GTC-178 — E1: Rebuild nudge cadence to days 4/7; remove NOT_SURE forced-conversion

**Status:** Open | **Branch:** TBD | **Commit:** [pending] (filed `e5f6e82`) | **Effort:** xhigh

*Effort level is a proposal from the discovery-report ticket breakdown — run `/effort` manually
before execution.*

### Context

Moment 4 spec §8.3/§10.3: two nudges, days 4 and 7 default (matching the real reply distribution
— first response ~41 min, cluster same-day, day-3 pair, stragglers from day 7 — Hinge §6), on the
**system's own schedule**, not "opened but no response." Criticality does not compress the
cadence — criticality does exactly two things (the badge, the assistant's message at red) and
touches nothing else.

Today: `nudge-scheduler.ts`/`nudge-eligibility.ts`/`nudge-sender.ts` run on **24h/48h
"opened but no response"** semantics — a different mechanism entirely. A third auto-nudge
(`sendRsvpFollowupNudge`, via `findRsvpFollowupCandidates`) force-converts `NOT_SURE` RSVPs at
48h "to force conversion" — this directly contradicts the maybe-state's "no nudges" rule (Hinge
§8) and is doubly obsoleted by D1 (GTC-174) retiring `rsvpStatus` as a directly-askable guest
question in the first place.

### Founder Rulings (2026-08-23)

**Ruling 1 — exhaustion is OUT of this ticket's scope.** The exhaustion counter, the exhausted
predicate, and the host-specified retry count (Moment 4 §4/§8.1's "door") are split into
[[GTC-251]] (E6 — nudge exhaustion and the red door). Rationale: cadence has a testable
definition of done today; exhaustion needs a counter that does not exist, a rule that does not
exist, and a red state on a Moment 4 screen that does not exist and is itself blocked on
[[GTC-192]]'s (J1) own open decisions. Splitting delays nothing real. **This supersedes the
"Inherited from D2" section below where it assigns exhausted-silence-red ownership to this
ticket** — that ownership now belongs to GTC-251; the section is left in place unedited for the
audit trail, with a redirect note added at its head.

**Ruling 2 — the clock fix IS in this ticket's scope.** `nudge-eligibility.ts`'s candidate-finding
switches from reading `Person.inviteAnchorAt` to reading `PersonEvent.sentAt`. Record this as a
**bug fix, not a refactor**: `Person.inviteAnchorAt` is global per-person, so a person who is a
guest at two events shares one clock, and the second event's nudge timing has been wrong since
the day `PersonEvent.sentAt` was introduced without `nudge-eligibility.ts` being updated to read
it. The schema comment on `PersonEvent.sentAt` in `prisma/schema.prisma` already names this
ticket as the fix: "Person.nudge24hSentAt/nudge48hSentAt carry the identical leak and move under
GTC-178 (E1)." **Open and NOT settled by this ruling:** whether the sent-side dedup state
(today `Person.nudge24hSentAt`/`nudge48hSentAt`) also moves off `Person` as part of this ticket,
and if so, to where. See "Storage-question analysis" below — a recommendation is recorded there,
not yet ruled.

**Ruling 3 — the proxy-nudge path stays out of this ticket**, unchanged from the original scope's
"if separate, leave it" below — and its known-broken frequency limiting now has its own ticket,
[[GTC-252]], filed today. No fix is proposed there; the risk is documented and left for a
separate decision.

**Storage-question analysis (2026-08-23) — recommendation only, not ruled.** If GTC-251's
eventual per-event nudge count needs its own send records, and this ticket's clock fix writes
new per-send state to close Ruling 2's open question, do the two end up writing the same fact
twice? Recommendation: **no, if this ticket writes its day-4/day-7 sent-dedup directly into the
existing `NudgeLog` model** (`prisma/schema.prisma` — already `personEventId`-keyed, cascade-
deletes with `PersonEvent`, has `nudgeType`/`sentAt`/`status` columns, has an applied migration,
and currently has zero production writers) **instead of adding new boolean/DateTime columns to
`Person` or `PersonEvent`.** A `NudgeLog` row per send (`nudgeType: 'day4' | 'day7'`) makes "has
day-4 already fired" a `NOT EXISTS` query this ticket needs anyway, and makes GTC-251's count a
`COUNT(*)` over the same rows — one source of truth, written once, no second migration when
GTC-251 lands. This also matches the storage location the `gather-frontier-and-roadmap` skill
independently names as a candidate for GTC-252's proxy-path problem, for the same reason.
Recorded here as input to whoever executes this ticket; the founder has not ruled on it.

### Scope

**Fix here:**
- Switch `nudge-eligibility.ts`'s clock source from `Person.inviteAnchorAt` to
  `PersonEvent.sentAt` (Ruling 2 — a bug fix; do not defer this to a later ticket).
- Rework `nudge-eligibility.ts`'s candidate-finding from 24h/48h-since-opened to
  day-4/day-7-since-send (adjustable — the adjustment mechanism itself is E2's territory,
  GTC-179; this ticket only needs to leave the hook for it).
- Remove `findRsvpFollowupCandidates`/`sendRsvpFollowupNudge` entirely — superseded twice over.
- Remove the two orphaned path-2 assertions in `tests/child-message-exclusion-test.ts` when
  deleting `findRsvpFollowupCandidates` (they assert a control IS an RSVP-follow-up candidate,
  impossible once the function is gone).
- Confirm criticality does not alter cadence anywhere in the new logic.
- Exhaustion counting, the exhausted predicate, and the retry-count door are explicitly NOT part
  of this ticket (Ruling 1) — see [[GTC-251]].

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`, especially SMS opt-out logic (Zone 7) —
  gate around it, never through it.
- TNZ/Twilio routing and quiet-hours logic (`send-sms.ts`, `quiet-hours.ts`) — working correctly,
  out of scope.
- The proxy-nudge path (`proxy-nudge-eligibility.ts`/`proxy-nudge-sender.ts`) unless its cadence
  logic is directly shared with the direct-nudge path being rebuilt here — if shared, note it; if
  separate, leave it. Its known-broken frequency-limiting issue is now tracked at [[GTC-252]]
  (Ruling 3), not this ticket's concern.
