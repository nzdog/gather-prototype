### Severity, ruled (Nigel, 2026-09-13)

**Medium, and NOT a blocker on [[GTC-189]]'s press.** The audit first put it forward as a
blocker. The founder dropped it, on this reasoning, recorded in the founder's words:

> I over-rated it: the case I built it on does not happen, because she types Mum and then
> Dad with their own details. The real case is two people who share one address between
> them, which is rarer.

**Dropped from blocker on that reasoning, not on effort.** Still worth the ticket, for two
reasons the founder gave:

1. A person disappearing with no error is bad whenever it happens.
2. The edit path demoting a primary contact into an uneditable household is the worse half.

---

### Signal

**Expected**
Two people captured with one shared email address are two people. Each has a `Person`, each
has a membership, and the household keeps its primary contact.

**Actual — two halves, the second worse.**

- **Create:** the second person is never created. The household saves, and the saved
  household comes back without them. No error.
- **Edit:** the second person is never created, **and the primary contact is demoted** to the
  new row's role. The household is left with no `PRIMARY_CONTACT`, and every later save of it
  fails.

**Smallest failing case**
Edit a household whose primary contact has an email, add a partner with that same address,
and save: no partner is created, the primary contact's `householdRole` becomes `PARTNER`, and
the next save of that household returns 500 *"Primary contact not found in household"*.

---

### The mechanism (as of `b3e9f31`)

`Person.email` is `@unique`, and every capture path finds-or-creates a `Person` by email before
it creates a membership.

**Half 1 — create.** `createMember`, the helper inside `POST` in
`src/app/api/events/[id]/households/route.ts`, runs for the primary contact, then the partner,
then helpers, then guests. For a later member carrying an address already captured,
`prisma.person.findUnique({ where: { email } })` returns the earlier member's `Person`; the
`(personId, eventId)` membership already exists and already has a `householdId`, so
`createMember` returns it unchanged. Nothing is written for the second person and nothing is
reported. A helper (a kid with a job) or a guest disappears the same way.

**Half 2 — edit.** `createNewMember`, inside `reconcileHouseholdMembers` in
`src/lib/households/reconcileMembers.ts`, handles a row added on edit (one with no
`personEventId`). It finds the earlier member's `Person` by the shared address, finds that
member's membership, and — because it is in the same household — writes
`householdRole: role` over it. If the shared address is the primary contact's:

- The primary contact becomes `PARTNER`, `GUEST` or `CHILD`, whichever the new row was. The
  `existing.role === 'HOST'` guard [[GTC-256]] added protects the host only; every other
  household is exposed.
- The household has no `PRIMARY_CONTACT`. `PUT` in
  `src/app/api/events/[id]/households/[householdId]/route.ts` looks one up before reconciling
  and returns **500** *"Primary contact not found in household"* when there is none, so the
  household cannot be edited again.
- `resolveHouseholdChannel` in `src/lib/households/channel.ts` returns null for it unless a
  contact was picked, so `findProxyNudgeCandidates` skips it as *"No primary contact"*.
- If the new row was a helper, the demoted primary is now `CHILD`, and `MESSAGEABLE_PERSON_EVENT`
  excludes the household's adult from every message.

Note [[GTC-256]] recorded the PUT as a 400 on a missing primary. At `b3e9f31` it is a 500.

### The same root, elsewhere

- **Moving an existing member onto an address another `Person` holds.** `updateExistingMember`,
  or the primary contact's own update at the top of `reconcileHouseholdMembers`, writes
  `Person.email`; the unique constraint throws inside the transaction; the `PUT` handler's catch
  returns 500 with the database error's message. Rolled back, so nothing is half-applied — but
  a family cannot record the address they actually share.
- **Across events.** `Person` is global. An address already on another event's `Person` binds
  the new row to that `Person`, and none of the four capture sites updates its name. The name
  typed is dropped and the other event's name shows.
- **`POST` in `src/app/api/events/[id]/people/route.ts`** finds the `Person`, finds the
  membership, and refuses with 400 *"Person is already part of this event"* — not silent, but
  naming the wrong reason.
- **`POST` in `src/app/api/events/[id]/people/batch-import/route.ts`** finds the membership and
  skips the row (*"Skip duplicates silently"*), counting it only in `skipped`.

No capture form or household route refuses a repeated address before any of this runs
(searched 2026-09-13: `Moment1InputForm`, `HouseholdCardList`, both household routes).

---

### What a fix must not break

- **[[GTC-256]]'s host.** Today the email match is what stops the host's own address, typed into
  a guest row, from minting a second `Person`. A second `Person` carrying her address would not
  be caught by `isAddressable` in `src/lib/eligibility/host-exclusion.ts`, which keys on
  `Event.hostId`, and would be sent her own ask. Removing the match needs a guard in its place.
- **The host's household capture.** `src/lib/households/hostHousehold.ts` reads her email from
  her `Person` and never from the client; the fix must keep that.
- **Prisma.** `findUnique({ where: { email } })` compiles only while `email` is unique. Each of
  the four sites changes shape if the constraint goes.
- **[[GTC-159]]'s incident file.** `reconcileMembers.ts` carries the household-edit history;
  keep its diff minimal.

### Reproduce

**Required state**
- A signed-in host of an event, through `scripts/dev-login.ts` (see the local-setup notes).
- An event in any status with at least one household whose primary contact has an email.
- Multi-actor: [ ] Yes [x] No

**Steps — half 2, the worse half**
1. Open the event's households and edit a household whose primary contact has an email.
2. Add a partner. Give them a name and **the primary contact's email address**.
3. Save.
4. Edit the same household again and save.

**Observe:** after step 3, no partner row exists and the primary contact's membership reads
`householdRole: PARTNER`. Step 4 returns 500 *"Primary contact not found in household"*.

**Steps — half 1**
1. Create a new household with a primary contact and an email.
2. Add a partner with the same email. Save.

**Observe:** the household saves with one member.

**Data setup**
Use a fixture event created for the purpose. Per [[GTC-292]], clean up only what the fixture
can prove it made — never by name or shared address.

### Unknowns

1. **Whether the fix drops `@unique` or matches differently** — for instance, within one event
   only, or on address and name together. Two people sharing an address cannot both hold it
   while the constraint stands, so any fix that keeps both people and both addresses removes it.
2. **What a re-entered person should do** — the same person typed twice on one event is the
   case the match was plausibly written for. Not established.
3. **Existing data.** A dropped person leaves no trace, so the number of households already
   affected cannot be counted. A demoted primary can: households with members and no
   `PRIMARY_CONTACT`. Not queried at filing.
4. **Whether the V1 people and batch-import routes are in scope** or split out.
