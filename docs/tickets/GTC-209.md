# GTC-209 — Wrap-up double-send

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** low-medium

*Source: `docs/04_roadmap/moment4-hinge-report-accuracy-audit-2026-08-04.md` — "Found in
passing" defect 1, CONFIRMED by both the audit pass and the independent confirmation pass.
This is a live defect on `master`-lineage code, not a doc-accuracy issue.*

### Scope, one line

`POST /api/events/[id]/wrap-up` has no idempotency guard at any layer, so a host who presses
wrap-up twice sends every guest two thank-you texts.

### Context

The wrap-up press writes `Event.wrappedAt`, then generates one `WrapUpLink` row per guest.
A cron (`/api/cron/wrap-up-dispatch`, `*/10`) picks up undispatched rows 10+ minutes later
and sends each one. **Nothing anywhere checks whether this already happened.**

Four candidate guard layers were checked; all four are absent:

| # | Layer | What is actually there |
|---|---|---|
| 1 | Route | Complete guard list is `requireEventRole(eventId, ['HOST'])` (`wrap-up/route.ts:20`), 404 (`:49`), and `if (!isComplete(event))` → 400 (`:61-66`). `isComplete` is `now > endDate` — **permanently true once past**. `:86-91` writes `wrappedAt` unconditionally, with no `where: { wrappedAt: null }`. |
| 2 | Generator | `wrap-up.ts:131` is a bare `prisma.wrapUpLink.create` — no upsert, no existence check. |
| 3 | Database | `WrapUpLink` (`schema.prisma:1045-1066`) has `token @unique` only. The three `@@index` (`:1063-1065`) are non-unique. No composite on `(eventId, personId)`. Tokens are fresh random per call, so the token index never fires. |
| 4 | Dispatcher | `wrap-up.ts:164-168` selects on `{ dispatched: false, createdAt: { lte: cutoff } }` — no distinct, no groupBy. `:182` iterates **rows, not people**. Two rows = two sends. |

**Why the one plausible accidental breaker does not fire.** `AuditEntry` carries
`@@unique([eventId, sequence])` (`schema.prisma:503`), and `generateWrapUpLinks` is called at
`wrap-up/route.ts:108` — *outside* the transaction at `:85-101`. A unique violation on the
second `WRAP_UP_SENT` insert would therefore have rolled back and prevented duplicates
entirely. It does not fire: `logAudit` (`workflow.ts:387-397`) never sets `sequence` (the
column is `Int?` at `schema.prisma:447`, and `sequence` appears nowhere else in `workflow.ts`),
and the generated index SQL
(`prisma/migrations/20260803042811_gtc168_send_lock_ledger_foundation/migration.sql:35`) has no
`NULLS NOT DISTINCT` — which appears in no migration in the repo. Postgres treats NULLs as
distinct, so unlimited NULL-`sequence` rows coexist. **This conclusion survived a deliberate
attempt to kill it.**

**Reproduction is narrower than "double-click".** Within one page load the second press *is*
blocked — the button carries `disabled={wrapUpLoading}` (`plan/[eventId]/page.tsx:3769`) and
the whole block is hidden once `wrapUpResult?.success` (`:3743`). The double-send needs **a
reload, a second tab, or a direct POST**. It is a reload/multi-tab hazard.

**The UI gate is free today.** `GET /api/events/[id]` uses `include` with no top-level `select`
(`events/[id]/route.ts:26-51`) and applies no `omit`/`$extends`, so `wrappedAt` — an `Event`
scalar — is already in the client payload. `page.tsx:698` `setEvent(data.event)` puts it in
state, where it is currently unused. The UI gates on React state (`wrapUpResult`), not on the
event. Correcting that needs **no API change**.

**The pattern to mirror already shipped.** `confirm-invites-sent/route.ts:51-53` is the same
problem solved correctly:

```ts
if (event.sentAt) {
  return NextResponse.json({ error: 'This event has already been sent' }, { status: 400 });
}
```

### Scope

**Fix here:**
- **Route guard.** Refuse a second wrap-up press for an event that already has `wrappedAt`,
  mirroring `confirm-invites-sent/route.ts:51-53`. This is the load-bearing half.
- **UI gate.** Gate the wrap-up button on `event.wrappedAt` rather than on the `wrapUpResult`
  React state, so a reload or second tab does not re-offer it. No API change required.
- **Generator idempotency and/or a `@@unique([eventId, personId])` constraint on `WrapUpLink`**
  as the race backstop — *shape to be decided by the duplicate-row count below, not assumed.*
  A constraint will fail to apply if duplicates already exist.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- `sendSms` / `send-sms.ts` / the TNZ / Twilio carrier layer. This ticket adds a dedupe guard;
  it changes nothing about how a message is sent.
- The quiet-hours guard on the wrap-up path — that is **GTC-210**, filed separately. Landing
  both is fine; conflating them in one change is not.
- `wrap-up/route.ts:4`'s comment. It reads *"GTC-186 (H1) turns this into a once-only, reviewed
  offer"* — future tense, and therefore **correct** as written. (The audit's claim that this
  comment "claims this route is already once-only" is wrong; verified against the file.)

**Behaviour guardrail:** a correctly-timed *single* press must behave exactly as it does today
— same recipients, same links, same messages, same dispatch timing. This is a dedupe guard, not
a change to the send.

### Dependencies

None. Independent of GTC-186 (H1), which will later rebuild this route as a reviewed offer —
that is a product change; this is a correctness fix that should not wait for it.

### Acceptance

*Built 2026-08-05 on `feat/moment-one-redesign`, uncommitted at time of writing. Boxes reflect
what was actually done; the one open box is deliberate and is explained under it.*

- [x] **BEFORE writing any `@@unique` migration**, count existing duplicate `WrapUpLink` rows.
      Ran read-only against `gather_dev`:
      ```
      WrapUpLink rows total: 0
      Duplicate (eventId, personId) groups: 0
      Events with a WRAP_UP_SENT entry: 0
      ```
      **Clean — but vacuously so, and that is the finding.** The table is empty because nothing
      has ever pressed wrap-up locally, so the query answers nothing about production (Railway,
      not reachable from the dev environment). Treated as "unknown", not "clear".
- [x] **Fix shape chosen: app-level only, constraint deferred.** Route guard + UI gate +
      generator existence check. No schema change, so **Stop Condition 7 was never triggered**.
      Rationale: the only environment whose duplicate count is readable is the one that
      provably has no rows, and a `@@unique` that fails to apply breaks `migrate deploy` on the
      environment that does have them. Deferring trades a narrow race for no deployment risk.
- [x] A test proves a **second wrap-up press does NOT re-send** —
      `tests/wrap-up-double-send-test.ts` (`npm run test:wrap-up-dedupe`). Presses twice at the
      seam the route uses (`selectWrapUpRecipients` → `generateWrapUpLinks`,
      `wrap-up/route.ts:106-108`) and asserts the second press creates zero additional rows.
      **RED against unmodified code: 8 passed, 6 failed** — press 2 duplicated all three guests
      and the dispatcher was queued to send 4 messages instead of 2. **GREEN: 14/14.**
- [x] The same test asserts the **first** press is unaffected — 2 created + 1 skipped, host
      excluded, sms/email/skipped channels each correct. All six press-1 assertions passed in
      the RED state, which is what proves the test was not simply broken.
- [x] A further control asserts a guest added **after** the press still receives exactly one
      link — the dedupe is keyed on `(event, person)`, not on the event. An event-level "already
      done" check would have passed every duplicate assertion above and silently stripped late
      guests, breaking the mini-send model GTC-186 (H1) builds on.
- [x] No real SMS is sent by the test. `dispatchPendingWrapUpMessages` — the only caller of
      `sendSms` — is never invoked; every assertion is on `WrapUpLink` rows and dispatch state.
- [x] The host UI does not re-offer the wrap-up button once `wrappedAt` is set
      (`plan/[eventId]/page.tsx:3752`). `wrappedAt` added to the client `Event` interface; the
      field was already in the API payload, so **no API change was needed**.
      **Not browser-verified** — the offer requires a COMPLETE event plus a host session
      obtainable only through the magic-link flow, the same limitation GTC-172 recorded for the
      household picker. Covered by `tsc` and build instead.
- [x] `npx tsc --noEmit` 0 · `next build` 0 · `format:check` 0 · **security suite 51/51** ·
      `test:wrap-up` 28/28 · `test:child-exclusion` 18/18 · `test:wrap-up-dedupe` 14/14.
- [ ] **CARRIED FORWARD — `@@unique([eventId, personId])` as the race backstop.** Blocked on a
      production duplicate count, not on effort. What remains uncovered by the app-level fix is
      a genuine simultaneous double-POST where both requests read `wrappedAt: null` before
      either writes — milliseconds wide; only a DB constraint closes it atomically. Run the
      count above against production first; if non-empty, plan a cleanup before the migration.

**Known gap, stated rather than papered over:** the route guard itself has **no DB-test
coverage**. Routes behind `requireEventRole` are unreachable from a DB-level test — the same
constraint GTC-172 documented and solved by extracting a seam. The test covers the generator
layer, which is where the duplicate rows were actually created. The guard is verified by
reading, `tsc` and build, and mirrors the already-shipped `confirm-invites-sent/route.ts:51-53`.
