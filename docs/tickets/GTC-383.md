# GTC-383 - walkthrough-batch3 leaves three Person rows behind every run

> Not a deploy precondition and not a walkthrough item. It came out of GTC-381's gate run, when
> `gather_dev`'s Person total rose by three and Claude Code traced it. The founder ruled on it at
> GTC-381's build (Q22), below. It is a test-only ticket: no source file, no migration, no route.

**Status:** Scoped 2026-10-13 by Cowork at `e1d5eaf` (read-only; GTC-381 is pushed, origin level).
**Severity:** not set - the founder's to set.

---

### Where this comes from

GTC-381's gate run left `gather_dev`'s Person total at 470, up three from 467. Claude Code traced it
(read-only) to `tests/walkthrough-batch3-test.tsx` and found it is three rows a run, not three once:
there are now 111 such rows (37 each of Lena Ford, Sam Ford and Nan Ford), one triple per run, from
2026-10-05 to 2026-10-13. None has an email, a phone, a user or an event membership. The three from
the GTC-381 gate run are `cmv4l2xiv0052rj63acq2kcgo` (Lena Ford), `cmv4l2xj10055rj63e7efcd9h`
(Sam Ford) and `cmv4l2xj30058rj6378ypc31b` (Nan Ford). It also found 52 other Person rows with no
links (names like "Kate" and "Nigel") that look like hand testing, not a suite. Those are not
touched.

### Founder ruling (verbatim)

> Q22, 2026-10-13. Asked what to do about the leaked rows. His answer: **"Fix the test's cleanup and
> also remove the 111 rows by id"**. (The options he did not take: the fix alone with the rows left
> for now, which was recommended, and leaving it entirely.)

His word covers the 111 Lena, Sam and Nan Ford rows only, by id, and the suite's own cleanup.

### What the code does today (Cowork, read 2026-10-13 at `e1d5eaf`)

- Test 16p (`tests/walkthrough-batch3-test.tsx` L833) presses "Save & add another household" on the
  fixture's Moment 1. The app's own household save makes the three Person rows (Lena, Sam and Nan
  Ford) and their memberships.
- The suite adds to `created.people` only the people it makes itself (L549 for the host, L601 for
  the guests). The three the app makes are never added.
- `cleanup()` (L1275-1285) deletes the sessions, the events, `created.people` and `created.users`.
  Deleting the event removes the households and memberships, but a Person exists apart from any
  event, so the three stay.
- Z1 (L1264-1270) reads `rows()`, whose Person count is `created.people` only (L724). It cannot see
  the three, so it passes while the leak grows.
- During GTC-381's gate, only this suite grew `gather_dev`'s Person total.

### Cowork's first pass (PENDING the plan)

- Fix the suite so the three are the suite's to clean: after the press in 16p (or before cleanup),
  find the Person rows that have a membership on a fixture event and are not in `created.people`,
  and add their ids to `created.people`, so the existing delete-by-id removes them.
- Make Z1 count by event membership as well, so a leak like this goes red: before cleanup, record
  the people on the fixture events; after it, none of them may remain.
- Removing the 111 existing rows is a one-off, by id, after the suite is fixed and has been run once
  with no growth. It is not a committed script and not part of any suite.

### For the plan

- Is 16p the only press in the suite that makes people through the app? Check every other press and
  every other suite that saves a household, and say whether any other suite can leave Person rows.
- The exact Z1 change, and whether it goes RED against today's leak before the cleanup fix (it
  should: that is the proof the check sees it).
- The one-off removal: the exact selection (see Stops), where the id list is saved, and the recount.
  The list is the 111 rows, plus three more for every batch3 run made before the removal.
- The tests-first order: Z1 red, then the cleanup fix, then green, then one run showing Person
  unchanged before and after.
