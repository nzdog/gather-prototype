## The design

- THE PLAIN TEXT is not changed by one byte. The senders build `text` and
  `headers` exactly as before; the new module only READS the text.
- THE HTML is built by `src/lib/email-design.ts` (new, pure: no
  database, no network, no environment read) from the plain text as
  sent, footer included. An email-safe page: tables for layout
  (`role="presentation"`), inline styles only (no `<style>`, no class),
  a 600px column, a system font stack, no image, no web font, no script,
  nothing fetched, `color-scheme: light` and explicit light colours on
  every part. The button colour is the theme's sage 600, #6B7869 ("sage
  dark", `accent-dark`): white on it is 4.6 to 1; the default sage 500
  #7D8B7A gives only 3.6 to 1.
- PARAGRAPHS as the plain text has them, in order (split at blank
  lines; a single line break stays a line break). A line is split into
  sentences only where the list rule needs it.
- THE BUTTON (ruling 3): when the LAST WORD of the message is exactly one
  link that starts with https:// (or the app's own http://localhost in
  development), with no quote, angle bracket or space in it and no
  second "http" inside it, the HTML shows the sentence before it
  (without the link), then a bulletproof button (a link inside a table
  cell, the colour and padding on the link, 14px by 28px, 17px type)
  reading "Open your invitation", then "Button not working? Copy this
  link: " and the same link as plain text. The href and the shown link
  are the same string. Otherwise: no button, the paragraphs as written.
- THE LIST (ruling 2; the invitation only): only when the ask's own item
  and job names were passed. The item sentence is rebuilt exactly as
  the register builds it (`whatIsAsked` in ask-register.ts, decision
  22's comma, `listOf` imported from it) and must be found in the
  message exactly once, as whole words. That one sentence is replaced
  by "Would you take care of these?" and the bullets, dishes first,
  then jobs. The sentences before it and after it on that line stay, in
  order, as their own paragraphs. Not found once, or no names: no list,
  the text as written. `sendHostVoiced` passes the names only for the
  ask (`label === 'ask'`), so a reminder or follow-up can never draw one.
  A carried child's sentences and the household list lines stay as
  written.
- THE FOOTER (ruling 4): read back out of the plain text. The module
  finds "Don't want emails about this event? PAGE" and the contact line
  at the end, and accepts them only if `withGuestEmailFooter(body, PAGE)`
  rebuilds the text exactly, so it is the page link `guestEmailParts`
  used. In small grey type (12px, #6b7280) under a thin rule: the
  invitation sentence as a link to that page, then "Contact Gather: "
  and the address as a mailto link, built from GATHER_CONTACT_LINE and
  GATHER_CONTACT_EMAIL (no address typed). If the footer cannot be read
  back, there is NO html part: the guest gets the plain text alone, as
  before.
- THE HOST'S TEST (ruling 5): designed by the same pieces with its own
  rule. The stand-in "[Name's own link goes here]" at the end makes a
  button-shaped box with the same words that links nowhere (a span, no
  href); the copy-link line shows the stand-in as it is; the footer
  shows "Don't want emails about this event? [their own link to stop
  these emails]" as plain text and the contact line. With the names
  passed it shows the list, as the guest's email does. A texted guest's
  test has no footer (a text has none): it is drawn as paragraphs only,
  no box, no list. The test still carries no header and no way out.
- SAFETY: every piece of text put in the page is escaped (& < > " '),
  the subject in `<title>` included. The design functions never throw:
  on anything unexpected they return null and the sender sends the
  plain text alone, so the html can never stop or change a send.
- NOTHING ELSE MOVES: who gets which email, when, on which channel; the
  opt-out, the block, the demo stop, the live switch, the result
  handling and the five send calls.

A picture from Chrome is not what Gmail, Outlook or Apple Mail draw. The
page uses what those clients are known to handle: nested tables with
`role="presentation"`, inline styles, `bgcolor` beside `background-color`
on the button cell, a system font stack. Known differences: older
Outlook on Windows (Word's renderer) draws the button square, not
rounded, ignores `max-width` (the column may run wider) and may pad the
button differently; Gmail may turn the copy-link text into a link of its
own; a client in dark mode may still recolour the page despite
`color-scheme: light`.
