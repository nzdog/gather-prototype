# GTC-316 — The press mints a guest link for every child, and the directory publishes it

**Status:** DONE — filed 2026-09-18, built 2026-09-19 | **Branch:** `feat/moment-one-redesign`
**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low
Escalated (brand/trust risk): **proposed yes, the founder's to set.** Nothing here leaks a
child's contact details — the directory already publishes children's names and this does not
change that. What it publishes that is new is a **writable** surface on a child's row, to
anyone holding the event id.

⚠ **DO-NOT-TOUCH ZONE 3** (AccessToken & scope). The defect is in issuance. Surface the shape
and get explicit approval before writing code, in the form [[GTC-256]] phase 3 and [[GTC-294]]
both used.

*Filed on founder instruction, 2026-09-18, during the [[GTC-191]] shape proposal: "File it,
High, before anything else. It is not GTC-191's and it should not ride inside it. Do not fix
it. Do not fold it in."*

**It is the same shape as [[GTC-262]]: a credential that is never sent, but is published
anyway.** GTC-262 found unauthenticated endpoints handing out COORDINATOR tokens nobody had
been sent. This is the same defect one role down — a PARTICIPANT token nobody will ever be
sent, because the child rule forbids sending it, published by the same directory to the same
unauthenticated caller. **And [[GTC-189]] slice 5 is what makes it live**: the press is where
the tokens are minted.

**THE CHAIN, AND IT IS WHY 5f AND NOT EARLIER:**

- The token is minted at **the press** — `ensureEventTokens` is `pressSend`'s first line, and that

### Signal

**Expected**
A child is never a message recipient (Moment 4 §10.6, [[GTC-172]]). A credential that exists
only so that a message can carry it should not be minted for somebody no message will reach —
and if it is minted, it must not be published to an unauthenticated caller.

**Actual**
Every child membership is issued a PARTICIPANT token, and the family directory publishes it.

**1. Issuance keys on the wrong column.** `ensureEventTokens` in `src/lib/tokens.ts`, step 4,
admits a membership on `pe.role === 'PARTICIPANT' && !coordinatorIds.has(pe.personId)`.
`PersonEvent.role` is the event role. **Childness lives on `PersonEvent.householdRole`, which
step 4 never reads.** All 60 CHILD memberships in `gather_dev` carry `role: 'PARTICIPANT'`, so
every one of them is admitted.

**2. The child rule does not catch it, and is not written to.** `isMessageableRole` and
`MESSAGEABLE_PERSON_EVENT` in `src/lib/eligibility/child-exclusion.ts` gate MESSAGING, and that
module says so in terms — *"THIS GATE IS MESSAGE-ONLY. IT MUST NEVER BE EXTENDED TO
ASSIGNMENT."* Nothing sends a child's link, and that part of the model is intact. **The breach
is publication, not messaging.**

**3. The directory publishes it.** `GET /api/gather/[eventId]/directory` is unauthenticated,
keyed on the event id alone, and filters its people on `ADDRESSABLE_PERSON_EVENT` in
`src/lib/eligibility/host-exclusion.ts` — which excludes the host, by `personId` and `role`,
and **nothing else**. It never reads `householdRole`. Its token query filters on
`SHAREABLE_ACCESS_TOKEN` in `src/lib/eligibility/shared-link-exposure.ts`, which is
`{ scope: 'PARTICIPANT' }`. A child's token satisfies it.

**4. The claim route admits them too.** `isClaimableRole` in the same module answers true for
`role === 'PARTICIPANT'`, which every child row is. [[GTC-262]] ruled *"the participant bargain
stands"* — that ruling was made about adults answering their own ask.

**5. The page answers and writes.** `GET` in `src/app/api/p/[token]/route.ts` returns the
child's own assignments, `POST` in `src/app/api/p/[token]/ack/[assignmentId]/route.ts` writes
their `Assignment.response`, and `PATCH` in `src/app/api/p/[token]/route.ts` writes their
`PersonEvent.attendanceAnswer`. All three accept the token as the child's own, because it is.

**Smallest failing case**
An event with one household containing a child who holds an item. Run `ensureEventTokens` — any
path that touches the event does. Load `/gather/<eventId>/directory` unauthenticated. The
child's name carries a working link to a page that answers for them.

### Why this is [[GTC-262]]'s shape and not a new one

[[GTC-262]] closed an unauthenticated endpoint that handed out COORDINATOR tokens to callers
who had never been sent one, and its founder ruling drew the line at what the endpoint *may
publish*: *"a participant token is an ask, a coordinator token is a job, and the no-verification
bargain was struck about the ask."*

A child's token is neither. It is an ask that **may never be asked** — the one case the model
routes through somebody else entirely ([[GTC-189]]'s founder ruling: *"A child's item is
carried in their household contact's message"*). So the bargain GTC-262 preserved does not
cover it: nobody struck a no-verification bargain about a child, because a child was never
supposed to be reachable at all.

The directory fix GTC-262 made is the precedent for the shape of the answer as well as for the
shape of the defect: **it filtered in the query**, so the row never enters the process, rather
than narrowing a mapping downstream. *"Restricting leaves the mechanism standing as dead code,
and the dead code is the mechanism."*

### Unknowns

1. **Withhold, or withhold and revoke?** 3 tokens exist. [[GTC-256]] phase 3 ruled the
   equivalent question for the host — *"revoke, do not merely decline"* — and the reasoning
   transfers, but it is a one-way door on live rows and is the founder's.
2. **Where the gate belongs.** In `ensureEventTokens` (nothing is minted), in the directory and
   claim route (minted but not published), or both. Both is the fail-closed answer and is two
   changes, not one.
3. **Does a child ever need a link?** If [[GTC-191]]'s carried answer is the only way a child's
   row is ever answered by a guest, the answer is no and the gate can be absolute. If a future
   ruling gives an older child their own link, this becomes a policy rather than a bar —
   §10.6's own words ("If a sixteen-year-old should genuinely be messaged directly, Kate roles
   them as an adult at capture") say the escape hatch is the role, not the token.
4. **The interaction with [[GTC-191]], recorded so it is not discovered.** A child's own token
   is, in principle, an alternative way to let a carrier answer for them — hand her the child's
   link. **That shape was considered at GTC-191's proposal and is not the chosen one**: it makes
   a durable credential for someone else's page the mechanism, which is wider than the write it
   authorises. GTC-191's proposal authorises the carried write by re-running `chooseAskRoute`
   instead, and needs no child token to exist. **Closing this ticket does not block that, and
   building that does not close this.**

### ✅ Unknown 1 ruled: WITHHOLD **AND** REVOKE

> *"A token already minted is already published, so withholding alone leaves every child currently
> holding one exposed and fixes only the future. Three exist in gather_dev today and all three are
> lapsed, so the live cost is nil — which is exactly the moment to take a one-way door, not after 5f
> makes it fifty-seven."*

### ⚠ What revoking touches — answered before building, as instructed

The founder's condition was to halt if revoking reached beyond deleting rows that should never have
existed — *"if it needs a sweep, a migration, or anything in issuance beyond the predicate"*. **It
does not**, and the boundary was established from the tree before a line was written:

- **No migration.** It deletes rows. No schema, no `prisma/migrations` entry.
- **No separate sweep.** It is a `deleteMany` inside `ensureEventTokens`, which is **[[GTC-256]] phase
  3's exact shape** — structurally symmetric with the HOST sweep directly beside it and the
  COORDINATOR prune above it. GTC-256's own founder approval was *"scoped to `role: 'HOST'` rows only,
  structurally symmetric with the existing COORDINATOR prune. Nothing wider"*, and this is the same
  sentence one role down.
- **Nothing wider in issuance semantics.** It is not the general PARTICIPANT prune GTC-256 explicitly
  declined — *"a wider change to issuance semantics [that] would need the full security re-audit Zone
  3 requires."*

⚠ **AND IT IS LAZY, WHICH IS THE ONE THING THE RULING'S WORDING DOES NOT ANTICIPATE.** A revocation
that rides issuance only fires when `ensureEventTokens` next runs on that event. **Measured after the
build: the three stale child tokens are still in the database**, because nothing has called issuance
on *GTC-133 Sub-commit (g) Test* since.

**The exposure is nevertheless closed, and that was verified rather than argued.** All three events
probed unauthenticated after the fix:

```
GTC-133 Sub-commit (g) Test | Charlie | expired=true | HTTP 200 | token in payload: false | name in payload: false
GTC-133 Sub-commit (g) Test | Rosie   | expired=true | HTTP 200 | token in payload: false | name in payload: false
GTC-133 Sub-commit (g) Test | Gus     | expired=true | HTTP 200 | token in payload: false | name in payload: false
```

**So the publication half is what closes the exposure and the revocation half is what closes the
rows** — which is why both shipped together rather than either alone. ⚠ **A one-off delete of those
three rows is available and was NOT done**, because it is a data write outside the mechanism and the
founder's condition names a migration as a halt. They are expired, unpublished and unclaimable; say
the word and they go.

### What was built

**Four files, and childness defined once.**

- **`src/lib/eligibility/child-exclusion.ts`** — `isChildMembership` and `NON_CHILD_PERSON_EVENT`.
  ⚠ **Childness as a FACT, deliberately not the messaging gate.** `isMessageableRole` answers *may a
  system message go here*, and [[GTC-207]] fences it as message-only. Neither minting a credential nor
  publishing one is messaging, and the stated reason a child gets no token is **not** "never
  messaged" — it is that the token is *an ask that may never be asked*, which is GTC-316's own ground.
  Two readings of "is this a child" in two modules is the drift this ledger keeps catching, so there
  is one.
- **`src/lib/tokens.ts`** — step 4's predicate gains `!isChildMembership(pe.householdRole)`
  (**withhold**), and a `childRowPersonIds` `deleteMany` sits beside GTC-256's host sweep

  its own.
- **`src/lib/eligibility/shared-link-exposure.ts`** — `isClaimableMembership` (role **and**
  childness) and `SHAREABLE_PERSON_EVENT`. `isClaimableRole` is **kept, not replaced**: the directory
  and `SHAREABLE_ACCESS_TOKEN` still need the role question on its own, and a caller with only a role

- **`src/app/api/gather/[eventId]/directory/route.ts`** — filtered **in the query**, beside

- **`src/app/api/join/[token]/claim/route.ts`** — reads `householdRole` as well as `role`, and its

**Unknown 2 — where the gate belongs — answered BOTH**, which this ticket's own Scope already listed
and which its text called *"the fail-closed answer"*. **Unknown 3 — does a child ever need a link —
answered no** by the model: §10.6's escape hatch is the role, not the token.

### ⚠ THE FINDING — the obvious filter would have silently deleted 99 adults

`child-exclusion.ts` already documented why its gate is an allowlist: *"it sidesteps SQL three-valued
logic. `NOT (col = 'CHILD')` is NULL — not true."* **That warning was read and then measured, and the
measurement is why this is a finding rather than a footnote:**

- **99 of 335 memberships in `gather_dev` have `householdRole: null`.**
- **`{ householdRole: { not: 'CHILD' } }` matches only 176 of 335.**
- 176 + 60 CHILD + 99 NULL = 335.

So the filter any reader would write first **removes 99 ADULTS from the directory and from token
issuance** — every guest with no household. **The fix would have become a worse defect than the one it
closes**, and it would have failed in the direction nobody checks: names quietly missing from a
screen, not an error.

`NON_CHILD_PERSON_EVENT` is therefore an allowlist plus an explicit NULL, the fixture carries an
adult with **no** `householdRole` on purpose, and **layer N asserts across all four touched files that
nobody has written `not: 'CHILD'` or `!== 'CHILD'`** — with a control that the matcher really matches
planted sources.

⚠ **AND THE TWO LISTS ARE KEPT SEPARATE THOUGH THEY COINCIDE TODAY.** `MESSAGEABLE_HOUSEHOLD_ROLES`
and the non-child allowlist are both "the three that are not CHILD", because `HouseholdRole` has
exactly four members. **A fifth member must be classified against both** — it could be unmessageable
and not a child — and keeping them apart is what makes that a decision rather than an inheritance.
