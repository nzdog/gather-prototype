### Signal

**Expected**
`PersonEvent.sentAt` is per-`(person, event)`. Two events containing the same person hold two
independent send clocks. That is the entire reason [[GTC-168]] (A2) introduced the column — the
schema comment says so: *"Person is global, so a person in two events shares one anchor and the
second event's clocks are wrong from the start."*

**Actual**
Migration `prisma/migrations/20260803230610_gtc202_backfill_send_clocks/migration.sql` populates
historical rows from the global field it was meant to replace:

```sql
UPDATE "PersonEvent" pe
SET "sentAt" = p."inviteAnchorAt"
FROM "Person" p, "Event" e
WHERE pe."personId" = p."id"
  AND pe."eventId" = e."id"
  AND pe."sentAt" IS NULL
  AND p."inviteAnchorAt" IS NOT NULL
  AND e."inviteSendConfirmedAt" IS NOT NULL;
```

`Person.inviteAnchorAt` is global per person. So for anyone who was a member of two or more sent
events at backfill time, **every one of their `PersonEvent.sentAt` values was set to the same
instant** — whichever event first anchored them. The second event's row carries the first event's
clock. The fallback statement immediately after (`SET "sentAt" = e."inviteSendConfirmedAt"`) is
correct per-event, but it only fires where the first left `sentAt` still null.

**This was deliberate and documented, not an oversight.** The migration says so in its own words:

> KNOWN LIMITATION, carried deliberately rather than silently fixed: `Person.inviteAnchorAt` is
> global across events (plan §8.2's per-person-for-a-per-event-fact leak), so a person anchored in
> another event carries that anchor here. §9.3 rules this backfill literally; clamping it would
> invent a rule the plan does not state and would hide the leak. **GTC-178 (E1) owns the anchor's
> move.**

⚠ **That deferral to GTC-178 is DECLINED as of 2026-08-27 (Ruling 9).** GTC-178 fixes the *read
path* — `nudge-eligibility.ts` stops reading `Person.inviteAnchorAt` and reads `PersonEvent.sentAt`
instead — which is correct going forward and does nothing for rows already written. Correcting
historical values is a separate act with a separate risk profile, and it is this ticket's.

**Consequences**
1. **A wrong clock is worse than a null one.** A null `sentAt` excludes the row from nudging
   (visible, safe). A *plausible but wrong* `sentAt` produces confidently mistimed nudges — early
   or late by the gap between the two events' send dates.
2. **[[GTC-178]]'s fix does not reach it.** After E1 the cadence reads `PersonEvent.sentAt`
   faithfully; if that value is another event's anchor, the cadence is faithfully wrong.
3. **It is invisible to E1's own test.** A two-event fixture created *after* the backfill writes
   correct per-event clocks and passes. Only rows written *by* the backfill carry the defect.

**Smallest failing case**
1. A person is a member of two events, both sent, with different `Event.sentAt` values.
2. `Person.inviteAnchorAt` holds event A's press time.
3. Both `PersonEvent` rows are backfilled to event A's press time.
4. Read event B's `PersonEvent.sentAt` — it is event A's clock, not event B's.

**Detection query** (run before assuming this ticket is empty):

```sql
SELECT pe."personId", COUNT(DISTINCT pe."sentAt") AS distinct_clocks, COUNT(*) AS rows
FROM "PersonEvent" pe
JOIN "Event" e ON e."id" = pe."eventId"
WHERE pe."sentAt" IS NOT NULL AND e."inviteSendConfirmedAt" IS NOT NULL
GROUP BY pe."personId"
HAVING COUNT(*) > 1 AND COUNT(DISTINCT pe."sentAt") = 1;
```

A person appearing here with events whose own `sentAt` differ is a confirmed instance. This is
suggestive, not conclusive: two events genuinely pressed at the same instant would also match.

### Scope

**Fix here:**
**NOT DETERMINED BY THIS TICKET.** If the pre-launch cleanup does not dispose of it, the candidate
remedy is a corrective data migration setting `PersonEvent.sentAt := Event.sentAt` for rows where
the two disagree and the person holds more than one sent-event membership. That would need its own
ruling, because it overwrites a value some downstream reader may have consumed, and because it
cannot distinguish a leaked anchor from a genuinely simultaneous press.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`, especially Zone 5 (migrations): never
  hand-edit, delete, or reorder `20260803230610_gtc202_backfill_send_clocks`. A correction is a
  **new** migration; the original stays as the record of what was run.
- [[GTC-178]]'s read-path fix — correct and sufficient for rows written from here on.
- `Person.inviteAnchorAt` itself — retained-but-unwritten, dropped by [[GTC-199]] (A4).
