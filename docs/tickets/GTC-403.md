## The finding, in plain English

A Gather link opens one event. Two kinds of request behind the links
trusted a second thing without asking whether it was on that event:

- The guest's Yes / No / Maybe. The guest link checked the item was the
  guest's own (or her child's, whose ask her message carries), but not
  that it was on the event her link opens. Someone invited to two
  events could answer their item on the second event through the first
  event's link, and the history line saying so landed in the wrong
  event.
- A dish's day. The host's dish edit, and the coordinator link's "add a
  dish" and "edit a dish", stored whatever day id was sent. A day from
  another event could be stored on a dish, and its name and date would
  then show on that dish.

Neither could send anything, and neither could change another person's
answer. The guest's answer now says "Assignment not found", as it does
for an item that does not exist. A day that is not on the event is now
refused with "That day is not on this event".

## Part A: the guest link's answer

### What it did before, and does now

POST `/api/p/[token]/ack/[assignmentId]`. Before: for the guest's own
assignment on another event, it read the body, recorded the answer on
that assignment, wrote the history line (ACCEPT/DECLINE/MAYBE_ASSIGNMENT,
naming the item) and a RESPONSE_SUBMITTED invite-log line into the
link's event, and answered 200 with the attendance it derives. Now:
right after the link is resolved, one indexed lookup asks only "is this
assignment's item on the link's event?" and reads only its id
(`assignment.findFirst`, `item: { team: { eventId } }`, the same shape as
GTC-402's coordinator guard). If not: 404 `{ error: 'Assignment not
found' }`, before the body is read and before anything is looked up,
written, logged or sent. Everything after that line is exactly as it
was: an assignment on the link's event (her own, or a carried child's)
gets the answer it got before, and every refusal for one on the event
(the 400 for a bad response, the 403 "That is not yours to answer.",
the re-check inside the write) is unchanged.

The answer is copied from this route's own 404 for a missing assignment
and from the coordinator link's door (GTC-402).

### Can this route send anything?

No. Read, not run: it writes `Assignment.response` and a history line
(`recordAssignmentAnswer`, `src/lib/assignment/answer.ts`, which imports
only the ledger's `logAudit`), and an invite-log line
(`logInviteEvent`). The carried-answer resolver
(`src/lib/eligibility/carried-answer.ts`) only reads (the opt-out and
block lists among them); nothing in the path reaches a sender or writes
an OutboundMessage. The tests count OutboundMessage around every call
anyway. Nothing about opt-out or block changed.

### Who calls it (checked before guarding)

Searched every file under `src/` outside `src/app/api`, and `scripts/`.

- The guest page, `src/app/p/[token]/page.tsx` (`handleResponse`, the
  Yes, No and Maybe buttons on her own items and on a carried child's).
  The ids it sends come from GET `/api/p/[token]`, whose own and carried
  lists are both filtered to the link's event
  (`item: { team: { eventId } }`). So every id it sends is on the event.
- No separate household page calls it; the carried child's items are on
  the same guest page.
- `scripts/gtc192-6e-guest-tap.ts` (a hand-run script, not in the gate)
  finds the assignment's own event first and uses that event's guest
  link. `scripts/test-phase-4.ts` names a conflicts "acknowledge" route,
  not this one.

No caller sends an assignment from another event: no STOP.

## Part B: the dish's day

### How I searched

```
grep -rn dayId src/app/api                 every route that names it
find src/app/api -type d -iname '*day*'    a day id in the address
grep -rnil '\bday(s|Id)?\b' (route.ts)     every route that says "day"
grep "day: {" "days: {" ".day.create|update"
                                           day relation writes
grep "data: body" "...body" "data: {...input"
                                           a body spread into a write
grep "searchParams.get('...day"            a day in the query
grep ".item.create|update|upsert(" src/app/api
                                           every item write, read for
                                           where its day comes from
```

Found, writing a `dayId` from the request body (none from the address
or the query):

- PATCH `/api/events/[id]/items/[itemId]` (the host's edit).
- POST `/api/c/[token]/items` (the coordinator link's create).
- PATCH `/api/c/[token]/items/[itemId]` (the coordinator link's edit).

Found and left alone, because none takes a day id from the request:
GET `/api/events/[id]/days` (reads the event's days); the template
clone (`templates/[id]/clone`, makes the new event's own days and maps
its dishes to them); `restoreFromRevision` (in `src/lib/workflow.ts`,
maps a saved plan's days to the new ones); the AI plan writers
(generate, regenerate, finalize-plan) and conflict resolution, which set
no day from the body; the host's add-dish route
(`POST /api/events/[id]/teams/[teamId]/items`), which does not read a
`dayId` at all (see the flags).

### What each route did before, and does now

All three now start the same way, before anything is built or written:
if a `dayId` is sent and it is not empty or null, one indexed lookup
asks "is there a day with this id on this event?" (`day.findFirst`,
`{ id, eventId }`, reading only its id). If not: 400 `{ error: 'That
day is not on this event' }` and stop. A day id that is not a string
(a number, say) is refused the same way. Everything after is exactly as
it was.

- PATCH `/api/events/[id]/items/[itemId]`. Before: stored the sent day
  as it was, whatever event it belonged to (a ledger line too, the day
  being a tracked field). Now: refused unless the day is on the event in
  the address (which GTC-400 already makes the dish's own event). The
  guard sits right after GTC-400's guard, after the body is read and the
  dish is looked up (it needs the dish's current day), and before the
  update is built.
- POST `/api/c/[token]/items`. Before: made the dish with the sent day.
  Now: refused unless the day is on the event the link opens, right
  after the body is read. There is no current day on a create. Empty or
  null (any value this route already stores as "no day") is not
  checked.
- PATCH `/api/c/[token]/items/[itemId]`. Before: stored the sent day.
  Now: refused unless the day is on the event the link opens, right
  after the body is read (after the route's own "is this dish on my
  team?" check).
- Not checked, by the ruling: clearing the day (empty or null), and, on
  the two edits, a day id equal to the dish's own current day. So an old
  dish whose day is already off its event (from before this ticket) can
  still be edited, as long as the edit sends back the day it has; the
  suite proves it (B(d)).

### What the screens send for a day (so no normal edit is blocked)

- The host's old dashboard edit form (`EditItemModal`, from
  `src/app/plan/[eventId]/page.tsx`) always sends `dayId`: the day picked
  or `null` ("All days"). It starts on the dish's own current day, and
  its list is GET `/api/events/[id]/days`, the event's own days. So it
  sends an event day, null, or the dish's own day: all allowed.
- No other screen sends a `dayId` on the host's edit (the setup page,
  Moment 2 and 3 views and the board send other fields).
- The coordinator page (`src/app/c/[token]/page.tsx`) sends `dayId` only
  when adding a dish: `newItem.dayId || null`, from a list holding only
  the day of the team's first dish (or "Select day...", null). That day
  is on the event unless that dish's own day is already off the event
  (old bad data), in which case the add is now refused with the new
  words (flagged).
- The coordinator page never edits a dish (it only deletes and assigns),
  so nothing calls the coordinator edit with a day today.

No screen sends a day from another event: no STOP.
