#### Item 17 — the event's name throughout, with its details a tap away

Ruling: *"The event’s name"*; and in his words: *"A clickable event name that brings up a pop up
with the rest of the details"*.

Today the event's name shows on Moment 1 (*"Who’s coming to …?"*), its summary, the plan view
(*"Here’s what I’d suggest for …"*), small above the pre-flight's heading, and on the board's top
line. It is not on Moment 2's opening screen, its questions or Moment 3, and nowhere can it be
tapped. The event holds more than its name: its dates, the kind of occasion, a description, a venue
and its times, and the guest count (`Event` in `prisma/schema.prisma`); they are changed in the old
dashboard's Edit Event.

For the plan: where the name goes on the screens that lack it; what the pop-up shows, and its words
(W-lines); whether it only shows the details or lets her change them too; how it opens and closes
on a phone; and the board, where [[GTC-192]]'s rules apply.

### Claude Code's corrections to the ticket

Found while planning, 2026-10-08, and recorded here on the founder's instruction. The ticket above
is left as filed.

1. **C1 — Next's default browser targets here are not Safari 16.4.** Next 15.5.25 targets Chrome 64,
   Edge 79, Firefox 67, Opera 51 and Safari 12 (`node_modules/next/dist/shared/lib/
   modern-browserslist-target.js`); 16.4 is Next 16's floor. Native popover needs Safari 17, Chrome
   114 and Firefox 125, so more browsers lack it than the ticket says, and the fallback matters more.
2. **C2 — Q14's three reads need more than `eventType`.** "Other" needs `eventTypeOther`; the
   pre-flight route's event select lacks `endDate`, the venue, both times and the description; the
   board page's select lacks the venue, both times and the description. The same three reads, more
   fields, no new route.
3. **C3 — W14's Edit Event changes `Event.occasionType`,** the old dashboard's own list. The
   details' Occasion is Moment 2's answer (`EventSetup.eventType`), a different field.
4. **C4 — the list of screens that show the name is off by two.** The opening screen lacks it too;
   "Who I chase" already shows it, small above its heading, like the pre-flight.
5. **C5 — the setup page reads the event once.** On Moment 2's questions and after them, its copy
   does not hold the occasion she has just picked.
6. **C6 — "a native popover, with no hook and no fetch"** holds for the native path; the never-dead
   fallback needs a tap handler, so the details file is a client file with handlers and no hooks,
   an island on the board like `PrintListDoor`. `GlanceBoard` keeps no hooks.

### Two unexpected reds after the change, and the ruling on them (2026-10-08)

written before the run exactly (`test:walkthrough-batch5-words` 50 red, 12 green;
`test:glance-read` the 41 of Q12). After the change:

   server render writes the popover attributes camel-cased (`popoverTarget="event-details-e1"`),
   and the checks looked for lowercase `popovertarget`. Browsers read attribute names without
   regard to case, so every in-browser check passed.
2. **`test:walkthrough-batch3` hung after 16n.** ⚠ *Correction to Claude Code's earlier answer,
   given with the build rulings, that no existing suite relied on the old warning: batch3 did.* On
   the phone it types a household's name, adds a partner, and before the next page empties only the
   name box: that got past the old warning, which read the name alone. Under the new rule the partner
   still differs from what the form opened with, so "Leave site?" came, and its browser had no one
   to answer it. Claude Code stopped the run (exit 143) and removed its fixture by id, counted while
   it existed (`6,5,6,51,71,63,1,1,18,61,8,0,0,0`, aiCallsUsed 0 on all six events; 0 left).

Proposed, tests only: **F1**, the new suite matches the two popover attributes regardless of case;
**F2**, one line in batch3, `chrome.answerLeaveDialogs(true)` after it opens Chrome.
