### FOUNDER RULING, 2026-09-29 — THE SHAPE: ONE LIVE SWITCH (Unknown 1)

Asked in Cowork on 2026-09-29, before execution, as a choice between three shapes. The founder
chose the first. The option, verbatim as chosen:

> **One 'live' switch.** *"Gather only sends for real where a setting says it's live: production.
> Anywhere else, including your Mac, every text and email stops at the last step, whatever keys
> are there, and tests still run in full. Costs one extra setting on Railway, checked at deploy
> (without it production sends nothing). A deliberate live test to your own address means turning
> it on for that one run."*

Declined: *"Tests turn sending off"* (a test written later that forgets the switch could still
send) and *"Tests refuse to run"* (the ambient refusal, which this ticket's Acceptance already
counts as disabling a test, not fixing it).

**Against *Scope*'s three shapes:** this is the provider stub with its polarity inverted. It is not
a test-mode predicate that a suite sets, but a live predicate that only production sets. Without
it there is no real send from any process: a test, a script, or the dev server.

**What the ruling settles:**
- No message leaves any machine or process without the live setting, whatever keys are present.
- The gate is the last step before each provider call. It comes after the opt-out checks, whose
  order in `sendSms` is Zone 7 and load-bearing (Stop Condition 10), and after provider selection
  and configuration, so the outcomes the suites assert today (a `+64` number with no TNZ token is
  `SMS_DISABLED`) still hold.
- A stopped send is never recorded or reported as sent. [[GTC-214]]'s contract stands: a cron
  that cannot send does not report a healthy run.
- Production sets it, and the deploy checks it: without it, production sends nothing.
- A deliberate live send is the setting for that one run, on the founder's word in chat, to his
  own address only.
- The temporary guard in `tests/nudge-provider-gate-test.ts` (`GATHER_ALLOW_LIVE_SMS_TEST`) is
  removed, as this ticket's header says.

**Left to the executor's plan, each as a question with a recommendation:**
- the setting's name and value, and where production's is set and checked;
- what a stopped send records and returns;
- whether any kind of message is exempt (the sign-in link, for one); the ruling names none;
- how each of the four instances in *Evidence* is covered, including the database writes of
  `tests/sms-validation-test.ts` (`InviteEvent` rows, and the `SmsOptOut` upsert and delete on
  Zone 7's table) and `test:security`'s wrap-up drive not waiting on its own precondition
  (Zone 6);
- what changes in `GATHER-BUILD-CONSTANTS.md`: the blanked-keys paragraph for `test:security`'s
  live layer, the `sms-validation-test.ts` line, and the known-failure entry for
  `nudge-provider-gate`.

**Unknown 2 is in scope:** a general audit of every path that can reach a provider, found by what
the code imports and calls (the Resend client, the Twilio client, the TNZ endpoint), not by which
tests exist.

## Signal

**Expected**
A test suite run by `npm run test:*` has no real-world side effects. The repo
already draws this line explicitly: `scripts/test-tnz-sms.ts` is described in
`.claude/skills/gather-run-and-operate/SKILL.md` as *"Sends a REAL SMS — needs
`TNZ_AUTH_TOKEN`; don't run casually"*, and it is the one script excluded from
every sweep for that reason. `BUG-TICKET-TEMPLATE.md` Stop Condition 6 is
"Real-world side effects possible without safe mode (Stripe live mode, real
SMS)."

**Actual**
`tests/nudge-provider-gate-test.ts` invokes the nudge cron handler in-process,
which runs `runNudgeScheduler` against the real `DATABASE_URL`, which calls
`sendSms` for every eligible candidate. There is no fixture isolation, no
provider stub, and no safe-mode flag. It is excluded from nothing.

**Smallest failing case**
Set `TNZ_AUTH_TOKEN` in `.env`, then `npm run test:nudge-provider-gate`. Every
`+64` candidate in the local database that is past a due nudge leg and has no
stamp receives a real message.

## Evidence

### The two call sites

Both in `tests/nudge-provider-gate-test.ts` — section A, the ambient-provider
control, and section D, *"the cron must not report a healthy run when it
cannot send"*:

```
const { GET } = await import('../src/app/api/cron/nudges/route');
const res = await GET(new NextRequest('http://localhost:3000/api/cron/nudges'));
```

`GET` in `src/app/api/cron/nudges/route.ts` calls `runNudgeScheduler` in
`src/lib/sms/nudge-scheduler.ts`, which calls `findNudgeCandidates` and then
`processNudges` in `src/lib/sms/nudge-sender.ts`, which calls `sendSms` in
`src/lib/sms/send-sms.ts`. Nothing on that path is stubbed.

### Why it is currently harmless, and why that is not a control

Three accidents, none of them chosen as a safety mechanism:

- `TNZ_AUTH_TOKEN` is absent from `.env` and `.env.local` on this machine.
- `findNudgeCandidates` filters candidates through `isValidNZNumber` in
  `src/lib/phone.ts`, so every candidate is a `+64` number.
- `shouldUseTnz` in `src/lib/sms/send-sms.ts` routes `+64` and `+61` to the
  TNZ arm, which returns `blocked: 'SMS_DISABLED'` when `isTnzEnabled()` is
  false — before any network call.

So the test is safe here because the ONE provider its candidates can reach is
unconfigured. Configure TNZ — which `GATHER-BUILD-CONSTANTS.md` lists as
*"Required for production NZ delivery"* — and the same command sends.

This is the same species of reasoning [[GTC-270]] and GTC-267 both had to
name: `cuid` non-enumerability contained GTC-267 and was *"an accident of the
id format, not a control."* An absent credential is not a safe mode.

### What [[GTC-270]] changed here, and what it deliberately did not

[[GTC-270]] made the cron routes fail closed, so an uncredentialed in-process
call now returns 401 before reaching the scheduler. This test had to be given
a `CRON_SECRET` to go on testing the provider gate rather than stopping at the
auth guard — which means **anyone who has not set `CRON_SECRET` now gets a
401 instead of a send.**

**That is a side effect and explicitly not a fix.** The test sets the variable
itself, so on any machine the send path is reached exactly as before. The
hazard is unchanged: a configured TNZ plus this command equals real messages.
Recorded here so that a later reader does not mistake GTC-270's incidental
narrowing for the remedy.

### ⚠ SECOND INSTANCE — `tests/glance-actions-test.ts`, found 2026-09-12

**Added by ruling out of [[GTC-265]]'s scope review. Recorded here, NOT fixed
here.** It answers Unknown 2 below, which asked whether any other suite
reaches a live sender the same way. One does, by a different door.

`tests/glance-actions-test.ts` drives `POST
/api/events/[id]/people/[personId]/nudge` **over HTTP** against the dev server
on `:3000`. That server is started by Next, which loads `.env.local` — so it
holds a **real `RESEND_API_KEY`**. Every other suite in the affected set runs
under `tsx`, which does not load `.env.local` and therefore cannot reach a
provider at all.

**⚠ THE MECHANISM IS REAL AND THE EXPOSURE IS NOT — and this is a correction to
the claim as first made.** It was first reported as a suite that *can* cause a
real outbound email. It cannot, as its fixtures stand, and the correction is
recorded rather than quietly dropped. What is real is the crossing: this is the
one affected suite that reaches a live-keyed server process at all.

**Why it cannot send today, and both reasons are accidents rather than
controls.**
Its `guest()` helper creates every person with `phoneNumber:
'+64211234567'`, and the suite creates no `SmsOptOut` rows, so
`chooseManualNudgeChannel` in `src/lib/sms/manual-nudge-recipient.ts` returns
`'sms'` for all of them and the email sender is never reached. The SMS leg
then refuses before touching a provider, because `sendSms` selects TNZ for a
`+64` destination and `TNZ_AUTH_TOKEN` is unset — which is the 502 the suite
asserts, calling it *"the refusal is the PROVIDER's"*.

**Add one email-only guest to that suite and it sends a real email.** Nothing
in the file says so, no assertion holds either containment, and nothing would
fail if someone removed a phone number or a TNZ token appeared in the
environment. A fixture's phone numbers and an absent credential are not a
safety property; they are two coincidences pointing the same way.

**Why this is the same ticket and not a new one:** it is the same defect
class — a `npm run test:*` suite whose safety rests on a provider being
unconfigured rather than on the suite being unable to reach one. This ticket's
Signal is *"A test suite run by `npm run test:*` has no real-world side
effects."* Both instances violate it; whichever of this ticket's three shapes
is chosen must cover both, or must say why it covers only one.

**A difference worth keeping, because it changes the remedy:** the first
instance reaches the sender **in process**, so a provider stub or a fixture
boundary can be applied directly. This one reaches it **across an HTTP
boundary into a separately-configured server process**, where a stub in the
test cannot help. The plausible remedies differ — a sentinel key for the
server under test, a fixture rule that no test person may be email-only, or
an assertion that the channel chooser never returns `'email'` for any fixture
in the file.

## Scope

**Fix here:** the remedy is a judgement call and is deliberately not mandated.
Three shapes, in the order they occur:

- **A provider stub.** Inject the sender, or gate the send behind an explicit
  test-mode predicate that the suite sets. Most direct; touches
  `src/lib/sms/send-sms.ts`, which nothing currently isolates for tests.
- **A dedicated fixture.** Point the test at seeded rows whose numbers cannot
  be delivered to, the way `tests/security-fixtures.ts` scopes the security
  suite. Does not protect a developer's own local data, which is what is
  actually at risk.
- **An ambient refusal.** Have the test assert that no provider is configured
  and abort loudly if one is — turning today's accident into a stated
  precondition. Smallest change, and it converts a silent hazard into a
  refusal, but it makes the test unrunnable exactly where NZ delivery works.

[[GTC-270]] used the third shape inside its own suite 12 and it worked well
there (a canary that refuses to drive senders when the guard is open), which
is weak evidence for it and not a decision.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding.

- **Zone 7** (SMS opt-out) — whatever stub or gate is introduced must sit
  OUTSIDE the opt-out predicate, never through it. `sendSms` re-checks opt-out
  before provider configuration and that ordering is load-bearing.
- **Zone 6** (`tests/security-*.ts`) — this file is not in Zone 6, but a fix
  that reaches into the shared send path will touch suites that are.

Out of scope: what the test asserts. [[GTC-214]]'s contract — a cron that
cannot send must not report a healthy run — is correct and must survive
whatever isolation is introduced. This ticket changes how the test reaches the
scheduler, not what it demands of it.

### Root cause

No process had a way to know it was not production. Every send path called its provider as soon
as a credential was present, so the only thing between `npm run test:*` and a guest's phone was a
credential that happened to be absent. That is an accident, not a control (the ticket's own
words).

### The fix, as ruled

- **`src/lib/live-sends.ts` (new).** `isLiveSendingOn()` is true only when `GATHER_LIVE_SENDS` is
  exactly `on`. It is read at every call and never cached. The module also defines
  `LIVE_SENDS_OFF`, the words every stopped send carries, and `LiveSendsOffError`.
- **The gate is the last step before each provider call**, after the opt-out checks and after
  provider choice and configuration:
  - `sendSms` in `src/lib/sms/send-sms.ts`. Before, the order was: E.164 → provider choice →
    **opt-out (Zone 7)** → provider configuration → network. After: E.164 → provider choice →
    **opt-out (Zone 7, untouched)** → provider configuration → **the switch** → network. A stop
    returns `SMS_DISABLED` with `LIVE_SENDS_OFF` and writes no InviteEvent, as the configuration
    refusal already did.
  - `sendViaTnz` in `src/lib/sms/tnz-client.ts`: after the token check, before the fetch. This
    fences `scripts/test-tnz-sms.ts`, which calls it directly. The script now also refuses by
    name.
  - `getResendClient` in `src/lib/email.ts`: after the client is built (a missing key still throws
    first), then it throws `LiveSendsOffError`. This covers every sender, the claim route in Zone 2
    without an edit, and the delivery poll. Every sender's `catch` reports a stop as
    `success: false` with **no provider code**, which `SendResult` already reads as "never left the
    process".
  - `smsProviderConfiguredFor` answers "live AND configured", so the resend door cannot clear a
    red with nothing sent.
  - `isNudgeRunHealthy` in `src/lib/sms/nudge-scheduler.ts` takes a required `live`. A run that is
    not live is unhealthy, which keeps [[GTC-214]]'s contract.
- **The deploy check** is `scripts/check-live-sends.mjs`, the first step of `build`. Whenever
  `RAILWAY_ENVIRONMENT_NAME` is set, it prints one line with the environment and whether live
  sending is on. It exits 1 on `production` without `on`.
- **No exemptions.** ⚠ **A change on the founder's Mac, recorded as a change:** mail to his own
  address, sign-in links included, has worked there since 2026-09-27 ([[GTC-247]], "the email
  half works in this environment"). It now stops at the switch, which is what the ruling says:
  "every text and email stops". Local sign-in goes through the founder's own tooling
  (`scripts/dev-login.ts`). This also changes what fixing [[GTC-247]] would mean. GTC-247 is not
  edited here.
- **Tests:** `tests/helpers/provider-trap.ts` (new) is the Phase 0 trap copied in full. It traps
  fetch, http and https requests, DNS lookups, net and tls connects, and a proxy wall.
  `liveBehindTrap()` is the only way a test may open the gate, and only behind the walls.
