### What was found
The `/p/[token]` route had no session awareness — it used only `resolveToken()` for PARTICIPANT access tokens. There was no mechanism to detect if the viewer was the event host. The host session is stored via a `session` cookie → `Session` table → `User` → `EventRole` (role: HOST). The `getUser()` helper from `src/lib/auth/session.ts` reads this cookie and returns the authenticated User.

### What was changed
- **`src/app/api/p/[token]/route.ts`** — Imported `getUser` from `@/lib/auth/session`. After token validation, calls `getUser()` to check for an active host session. If the session user has a HOST EventRole for the resolved event, returns a trimmed `isHostPreview` response (person name, event name/id, assigned items) and skips link-open tracking. Non-host viewers fall through to the existing participant flow unchanged.

- **`src/app/p/[token]/page.tsx`** — Added `HostPreviewData` interface and `hostPreview` state. When the API returns `isHostPreview: true`, renders a clean preview card with: checkmark icon, "Link checked, good to send" heading, guest name, event name, list of assigned items (name, quantity, critical badge, day), and a "Back to event" link pointing to `/plan/[eventId]`. No RSVP controls shown. Normal participant flow renders unchanged when `isHostPreview` is absent.

- **`tests/host-preview-test.ts`** — 18-test regression suite covering API response shape, client routing logic, and source code verification (imports, flag presence, render text, tracking bypass order).

- **`package.json`** — Added `test:host-preview` script.

### Known limitations / follow-up flags
- Only detects HOST role, not COHOST. If co-hosts should also see the preview, a follow-up ticket would add COHOST to the EventRole query.
- The `getUser()` call adds one DB query (session lookup) on every participant link load, even for non-hosts. This is lightweight but could be skipped if no `session` cookie is present (micro-optimization, not implemented).
