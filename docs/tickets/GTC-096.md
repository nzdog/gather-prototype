# [[GTC-096]] — Auto-resolve conflicts no longer detected on re-check — CLOSED

**Status:** Complete | **Branch:** master | **Commit:** bdaec0d

### What was found

`saveConflicts` in `src/lib/ai/check.ts` iterated over newly detected conflicts and created, updated, or reopened them — but never resolved conflicts that were no longer detected. When a host fixed an underlying issue (e.g. assigned a coordinator), the next check correctly did not detect that conflict, but the old OPEN conflict record remained in the database untouched and stayed visible in the UI.

### What was changed

**`src/lib/ai/check.ts` — `saveConflicts` function:**

Added a cleanup step at the end of the function, after the existing conflict upsert loop:

```typescript
// Auto-resolve active conflicts that were not detected in this check run
const detectedFingerprints = conflicts.map((c) => c.fingerprint);

await prisma.conflict.updateMany({
  where: {
    eventId,
    status: { in: ['OPEN', 'ACKNOWLEDGED', 'DELEGATED'] },
    fingerprint: { notIn: detectedFingerprints },
  },
  data: {
    status: 'RESOLVED',
    resolvedAt: new Date(),
    resolvedBy: 'system',
  },
});
```

This resolves any active conflict whose fingerprint was not present in the current detection run — meaning the underlying issue no longer exists.

### Known limitations

- Only runs when `saveConflicts` is called (i.e. during a check). If auto-recheck ([[GTC-095]]) is not triggered, stale conflicts persist until the next manual or auto check.
- `resolvedBy: 'system'` is a string, not a Person ID. This is intentional to distinguish auto-resolution from host-initiated resolution in the audit trail.
- If the detection logic has a bug that fails to detect a real conflict, that conflict will be incorrectly auto-resolved. This is mitigated by the existing reopen logic at line 393 which will reopen it on the next successful detection.
