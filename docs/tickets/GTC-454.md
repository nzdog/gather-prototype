# GTC-454 - The demo tally

**Status: built, not committed.** Waiting for the founder's approval to commit. Needs a deploy
(staging first) to take effect.

## What and why

Founder, 5 Nov 2026 (run sheet L1-D3): *"I also want to understand who interacts with the demo
and if they come back for a paid event"*, then *"Option 1 for demo count"*: one line of totals
in the server log, read in Railway, with no database change.

A demo sample is deleted by the hourly clean-up once its NZ day is over (GTC-442), so a morning
report cannot read it. This counts each sample just before the clean-up deletes it. The sample
is finished by then, so this is still listening. Run sheet steps L1-11 to L1-16; this ticket
covers the build (L1-11 to L1-14).

Whether demo visitors come back is answered elsewhere: by asking (Level 2, L2-17 to L2-19) and
by comparing trends (the weekly paid count in GTC-453's report against these log lines).

## What changed

- `src/lib/demo/tally.ts` (new) - `readCopy` reads one sample: counts and yes/no facts only.
  `addReading` and `tallyLine` build the one line per run.
- `src/lib/demo/cleanup.ts` - in `sweepExpiredCopies`, each copy is read just before its
  delete, **outside** its delete transaction, with failures caught (`.catch(() => null)`), so a
  failed read never stops a delete; the copy counts as unread. One `[demo-tally]` line is
  printed after the existing `[demo-cleanup]` line. Nothing else in the file changed.
- `tests/demo-tally-test.ts` (new) - 16 checks.
- `tests/demo-cleanup-test.ts` - one pin widened on purpose, one pin added (see below).
- `package.json` - one line: `test:demo-tally`.

No schema change, no migration, no change to sign-in code, no outside service.

## The line

```
[demo-tally] samples 6; added guests 5; reached M2 4, M3 3, M4 1; guest view 2; saves median 14; deleted by visitor 1; unread 0
```

(Invented numbers.) Printed once per run, hourly, zeros included, so the founder adds up a
day's lines in Railway's Log Explorer by searching `"[demo-tally]"`.

## What a sample saves (checked against the code, 5 Nov 2026)

- **Samples, how far they got: yes.** A sample starts empty (`src/lib/demo/copy.ts`). "Added
  guests" is any person beyond the host. "Reached M2" uses the setup screen's own rules
  (`momentTwoBegun`, `hasAnyPlan` in `src/lib/setup/entry-stage.ts`). M3 is the plan approved;
  M4 is the plan held.
- **Guest view: yes, partly.** The guest view opens a sample guest's own link, and the first
  open stamps `AccessToken.openedAt` (`src/app/api/p/[token]/route.ts`). No demo code
  pre-stamps it. Only first opens count.
- **Saves: yes.** Host rows in the sample's history.
- **Deleted by visitor: a number only.** The clean-up's second pass (GTC-448) counts them; how
  far they got is gone.
- **Pressing send, and errors: no.** Send on a sample writes nothing and the pretend send
  records nothing (`src/lib/demo/pretend-send.ts`); errors go to the server log only. Level 2.

## What it never reads

No name, email, phone, token value, visitor tag, or link-open metadata. Check S2 pins the
tally's selects; D1-D3 pin that the line carries no id, address or name.

## Pins changed on purpose

`tests/demo-cleanup-test.ts` **V3** pins the modules `cleanup.ts` may import, to prove it sends
nothing. It now also allows `@/lib/demo/tally`. A new **V3b** pins that `tally.ts` imports only
`@prisma/client` (types) and `@/lib/setup/entry-stage`, and that `entry-stage.ts` imports
nothing. So the property V3 exists for - the clean-up sends nothing - still holds and is still
pinned. This needs the founder's approval as part of the commit.
