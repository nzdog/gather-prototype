## 2026-09-12 update — the five answers, and the ruling

[[GTC-277]] executed the non-major half of this chain and answered every
open question this ticket carried. Three of the four packages are fixed:

- **`next` 15.5.14 → 15.5.25** — a patch inside the declared `^15.5.12`. This
  is decision point 1's "non-major bump within 15.x" option, taken. It cleared
  22 of `next`'s 24 advisories including **both criticals**.
- **`sharp` 0.34.5 → 0.35.4** — fixed. Accepted despite being a 0.x minor
  because `next@15.5.25` declares `sharp: "^0.34.3 || ^0.35.4"` in its own
  `optionalDependencies`.
- **`nanoid` 3.3.11 → 3.3.19** — fixed.
- **`postcss` — half fixed.** The top-level devDependency copy went
  8.5.6 → 8.5.28. The copy vendored inside Next did not. See Answer 3.

**Answer to decision point 1 (pick a target `next` version):** 15.5.25, taken.

**Answer to decision point 2 (is `next/image` server-side processing
exercised?): NO.** `next.config.js` declares no `images` block at all, so
`/_next/image` refuses every external URL — no `remotePatterns`, no `domains`.
All four `next/image` call sites render first-party SVGs from `public/brand/`,
and Next does not pass SVG through the optimizer without `dangerouslyAllowSVG`,
which is unset. No upload path writes into `public/`. No route under
`src/app/api/` returns attacker-controlled image bytes. **Nothing on this
origin will serve an image to the optimizer that an attacker chose.** This
answers Unknown 1 and de-fangs both the `sharp` advisories and the AVIF RCE
(GHSA-2xp9-vwfh-vxw4) — though note it is a configuration accident, not a
designed control, and should not be leaned on as one.

**Answer to decision point 3 (do postcss/sharp/nanoid resolve with the same
lockfile update?): TWO OF THREE.** This ticket said "verify this rather than
assuming it," and the verification found the assumption two-thirds right.
`sharp` and `nanoid` resolved. `postcss` did not, because
**`next@15.5.25` hard-pins `postcss: "8.4.31"` — an exact pin, not a range.**
Every published 15.5.x was checked; the pin never moves. So
`node_modules/next/node_modules/postcss` stays vulnerable at any point on the
15.x line. `next@16.3.5` pins `postcss: "8.5.23"`, which clears it.

**Answer to Unknown 2 (is the middleware-bypass attack surface reachable given
this app's routing structure?): PARTLY — with far smaller consequence than the
class name implies.** The i18n variant (GHSA-36qx-fr4f-26g5) is dead outright:
no i18n config, no Pages Router, no `src/pages`. For the rest, the decisive
fact is that **`middleware` in `middleware.ts` does not authorize anything.**
It sets path-scoped isolation cookies for `/p/`, `/h/`, `/c/` and strips the
`session` cookie from `/api/p/` and `/api/c/`. Authorization lives in the route
handlers, via `resolveToken` in `src/lib/auth.ts` and `requireEventRole` in
`src/lib/auth/guards.ts`. A bypass therefore re-opens the GTC-001
session-collision class; it does not grant entry. Blast radius checked: exactly
one handler under those prefixes reads the session at all — the `GET` export in
`src/app/api/p/[token]/route.ts`, which calls `getUser` (`src/lib/auth/session.ts`) only *after*
`resolveToken` has returned a valid `PARTICIPANT` scope, to offer host-preview.
A bypass does not escalate there. **This was established without editing
`middleware.ts`, per this ticket's own Do-Not-Touch instruction.**

### THE RULING — NOT NOW on Next 16 (Nigel, 2026-09-12)

**Recorded so it is not reopened casually.**

> A framework major touching routing, middleware and RSC — on an app whose
> middleware carries the Zone 1 session-isolation invariant — to clear one
> moderate and one high in a build-time vendored postcss that only ever
> processes our own Tailwind output. Revisit when Next 16 buys something we
> want, not as a security action.

What the upgrade would additionally drag with it, none of it wanted right now:
`eslint-config-next` must move to 16.x in the same change (anything less
reproduces the circular-JSON crash `b6e6e38` fixed — see [[GTC-243]]);
`next lint` is **removed** in Next 16, so [[GTC-278]]'s flat-config migration
becomes a hard precondition rather than hygiene; and [[GTC-130]] Path B's full
Moment 1 / Moment 2 regression requirement applies.

### What this ticket is now

A single deferred question — **Next 16, yes or no** — currently ruled no, to be
revisited on product need rather than on advisory pressure. The two advisories
it would clear are **2 of the 5 `npm audit` still reports**, and GTC-277
Finding 3 records that those 5 are the correct end state rather than unfinished
work, precisely so nobody reads the number and reaches for
`npm audit fix --force` — which would take this decision silently.

## Context

Four packages from `npm audit` on `feat/moment-one-redesign` form one chain rooted at `next`:

| Package | Prod/Dev | Direct/Transitive | Sev | Notes |
|---|---|---|---|---|
| `next` (installed 15.5.14) | prod, **direct** | — | High | 22 GHSAs known against this package; framework itself |
| `postcss` (installed 8.5.6) | dev, **direct** (also bundled inside `next` at `node_modules/next/node_modules/postcss`) | — | High | XSS + path traversal / arbitrary file read |
| `sharp` (installed 0.34.5) | prod, transitive ← `next` | — | High | Optional image-optimization dep of Next; only exercised if `next/image` server-side processing runs |
| `nanoid` (installed 3.3.11) | prod, transitive ← `next`/`postcss` | — | High | DoS via infinite loop on size 0/negative |

`next`'s 22 known GHSAs cover a mix of vulnerability classes — this is not one bug:
- DoS via Server Components (GHSA-q4gf-8mx6-v5v3, GHSA-8h8q-6873-q5fj)
- **Middleware / Proxy bypass in App Router applications via segment-prefetch routes**
  (GHSA-26hh-7cqf-hhc6) — authorization-adjacent, flagged per the audit's own criteria for
  individual review even though nothing in this repo's own `middleware.ts` is touched
- Middleware/Proxy redirect cache poisoning
- Several more DoS and cache-related entries (full list of 22 GHSA IDs in the raw `npm audit
  --json` output from the triage session)

`sharp`'s advisory (GHSA-f88m-g3jw-g9cj, libvips CVE-2026-33327/33328/35590/35591) is scoped by
its own advisory text to "those processing untrusted input" — real exposure here depends on
whether this app's Next.js image-optimization path (`next/image`) is actually exercised against
attacker-influenced images in production; not confirmed either way in this audit.

**Coupling constraint — do not treat `next` and `eslint-config-next` as independent decisions.**
`eslint-config-next` is pinned to `^15.5.22` specifically because it must track `next`'s major
version (commit `b6e6e38` — see [[GTC-243]] for the full incident). The only currently-installed
route back to `eslint-config-next@16.x` is upgrading `next` itself to a 16.x release — anything
short of that reproduces the circular-JSON ESLint crash b6e6e38 fixed.

**A `next` 16 upgrade is Path B of [[GTC-130]] — do not re-derive that analysis here.** GTC-130
("Align eslint-config-next with installed Next.js major version") already framed this exact
next-vs-eslint-config-next coupling as a two-path decision and is the canonical source for it:
Path A (downgrade `eslint-config-next`, the path `b6e6e38` actually took, without referencing the
ticket) and Path B (upgrade `next` to 16.x, "higher risk... broader scope, but forward-moving,"
with a full regression check on Moment 1 and Moment 2 flows required). GTC-130 is now closed —
Path A shipped, Path B never got attempted or decided against, it just wasn't the path taken. If
this ticket's decision lands on a `next` 16 upgrade, **read GTC-130's Path B section and its
regression-check requirement before scoping that work**; this ticket does not repeat it.

## Scope

**No fix attempted in this ticket.** This ticket exists to force an individual decision before
any of the four packages move, per the triage's own flagging criteria (Next.js/React chain =
largest blast radius, decided individually).

**Decision needed:**
1. Pick a target `next` version. A non-major bump within 15.x clears the DoS/cache-poisoning
   GHSAs without touching the eslint-config-next question. A major bump to 16.x is GTC-130's
   Path B — read that ticket's analysis (risk, regression-check requirement) before choosing it.
2. Confirm whether `next/image` server-side processing is exercised in this app's production
   traffic (determines real-world urgency of the `sharp` advisory specifically).
3. Once a `next` version is chosen, `postcss`, `sharp`, and `nanoid` are expected to resolve as
   part of the same lockfile update (all three are transitive under `next` or bundled inside it)
   — verify this rather than assuming it.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding — in particular, verifying
  the middleware-bypass advisory (GHSA-26hh-7cqf-hhc6) does not require and must not become an
  excuse to touch `middleware.ts` (Do-Not-Touch Zone 1).
- `eslint-config-next` — not to be changed except as a deliberate, explicitly-decided part of a
  `next` 16 upgrade (see GTC-130 Path B above).
