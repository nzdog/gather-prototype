## The founder's rulings (26 Oct 2026, in Cowork)

1. A host whose browser returns to /plan/new?session_id=... AFTER her
   event already exists (a reload, history, a second tab, the "Payment
   received" screen reloaded) no longer sees "Something went wrong" and
   is no longer sent to the home page after 3 seconds. When the server
   answers 409 (payment already used), the page shows:
   - the heading "Payment received" (the existing words);
   - ONE NEW SENTENCE, exactly: "Your event was set up when you paid.
     Sign in with the email you paid with and it will be waiting for
     you."
   - the existing button "Go to sign-in" (to /auth/signin).
   It sends nothing and says nothing else. No timer, no redirect.
2. "Try Again" after a failed creation keeps the receipt. When the
   return page tried to create the event and the failure was a server
   error (a 5xx answer) or a connection failure, "Try Again" tries the
   SAME creation again with the SAME session id (the same POST with the
   same stripeSessionId), through the same screens ("creating", then
   "Payment received" or the error again). It does NOT go to the blank
   form. Where the failure shows the receipt is no use (a 402 "Payment
   wasn't completed", or a 400), "Try Again" goes to the form as it does
   today. The server already refuses a second event for one payment (a
   unique index and a check that answers 409), so a retry after a lost
   answer lands on ruling 1's screen. No new words.
3. "Contact Support" opens mailto:hello@gatheringtogether.co.nz instead
   of mailto:support@gather.app. Nothing else about the buttons or the
   error screen's words changes.

## What a host sees now

- On a second visit to the return address (a reload, Back, history, a
  second tab, the "Payment received" screen reloaded): "Creating your
  event..." for a moment, then a white card with "Payment received",
  the sentence "Your event was set up when you paid. Sign in with the
  email you paid with and it will be waiting for you." and the "Go to
  sign-in" button. It stays there. Nothing else is said and nothing is
  sent.
- After a failed creation: the error screen as before ("Something went
  wrong", the reason, "Try Again", "Contact Support").
- On "Try Again" after a server error or a lost connection: "Creating
  your event..." again, then the same screens as the first try: her
  "Payment received" screen (or setup, if she is signed in as the
  paying address), ruling 1's screen if the event was made after all,
  or the error screen again. The address keeps its session_id.
- On "Try Again" after a 402 or a 400: the blank form on /plan/new, as
  before.
- On "Contact Support": an email to hello@gatheringtogether.co.nz.
- A first visit (no session_id) and a canceled payment (?canceled=true)
  are as before, words and all.

## The server's answers, one by one

Read from src/app/api/events/route.ts at 1b8bfe7 (not edited).

(The page sends `POST /api/events` with `{ stripeSessionId }` only.)

- 402 "Payment required. Missing stripeSessionId." when the body has no
  session id. The page always sends one, so never after a real payment.
  Keeps the receipt: no (goes to the form).
- 402 "Payment not completed" when Stripe says the session is not paid.
  The checkout takes cards only (payment_method_types ['card']) and
  Stripe sends her to the return address only after the card is
  charged, so this does not follow a completed payment; it follows an
  address with an unpaid session id in it. The page shows its own words
  "Payment wasn't completed. Please try again." Keeps the receipt: no.
- 400 "Invalid payment session" when the Stripe lookup throws. That is
  an unknown session id, but ALSO any failure to reach Stripe at that
  moment (an outage, a timeout, a network fault, a rate limit, a key
  problem): the route answers 400 for every lookup failure. So a 400
  CAN follow a real payment. Keeps the receipt: no, as ruled (goes to
  the form). See the flags.
- 400 "No email from Stripe" when the paid session has no email. The
  checkout sets her email and Stripe always collects one, so not
  expected after a real payment. Keeps the receipt: no.
- 400 "Missing event data from payment session" when the session's
  metadata lacks the name or dates. The checkout always writes them (an
  empty end date was closed by GTC-385), so not expected after a real
  payment. Keeps the receipt: no.
- 409 "Payment already used for another event" when an event already
  holds this payment's id. Only ever after a real payment (it is the
  proof one landed). Now ruling 1's screen.
- 500 "Failed to create event" from the route's last catch: the
  database failing on the lookup or the creation; two tabs racing (the
  second's creation hits the unique index on Event.stripePaymentIntentId
  and fails); or a failure AFTER the event is written: the welcome
  email's sign-in row (`prisma.magicLink.create` in sendWelcomeEmail,
  src/lib/email.ts) is written outside that function's own catch, so if
  it throws the route answers 500 though the event exists. All can
  follow a real payment. Keeps the receipt: yes.
- Any other 5xx (a proxy or the host answering 502, 503 or 504, often
  with an HTML page, not JSON): can follow a real payment. Keeps the
  receipt: yes.
- A connection failure (the request never got an answer: offline, the
  server restarting, a timeout): can follow a real payment, including
  one the server finished. Keeps the receipt: yes.
- An answer that arrived but could not be read (a 2xx whose body broke
  off): counted as a connection failure. Keeps the receipt: yes.

Exactly which keep the receipt now: every 5xx, a connection failure,
and an answer lost while it was read. Every 4xx (400, 402, and any
other the route does not send today) goes to the form as before.

What a retry does if the first attempt actually succeeded on the server
but its answer was lost: the server finds the event by the payment's id
and answers 409, so she lands on ruling 1's screen ("Payment received",
the sentence, "Go to sign-in"). No second event is made (the 409 check,
and behind it the unique index). No second email is sent: the 409 path
sends nothing, and the first attempt already sent the sign-in link
(unless its send failed, which the lost answer would have told her).

## What changed in the page (src/app/plan/new/page.tsx, commit 0895827)

- A new page state, 'paid-before', drawn as ruling 1's card (the same
  classes as the existing "Payment received" card and its "Go to
  sign-in" link).

  already used to create an event.", the 3-second timer and
  router.push('/')) is removed.

  the 400s arrives. The catch stores the session id for "Try Again" when
  the flag is still true, and clears it otherwise.
- "Try Again": when the error screen holds a kept receipt, it clears the
  error, shows "Creating your event..." and calls the same creation with
  the same session id. Otherwise it does what it did (to the form).
- "Contact Support": `mailto:${GATHER_CONTACT_EMAIL}`, imported from

  once under src (test:email-contact-line D), in that file; a literal
  in the page would turn that check red.
- creatingRef: unchanged. It stops the effect from starting a second
  creation by itself (React's Strict Mode runs the effect twice in
  development; a re-render). The retry is started by her own press, not
  by the effect, so the guard needs nothing; it stays true after the
  first creation, so the effect still never re-creates on its own.
