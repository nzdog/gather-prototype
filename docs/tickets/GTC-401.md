## The finding, in plain English

Each of these four web addresses names two things: an event and a
person. Each one checked "is the signed-in person a host of the event
in the address?" and then trusted the person part without asking
whether that person was on that event at all. So a host of her own
event (call it A) could put her own event in the address and any
person's id from another event (B):

- The nudge would MESSAGE that person, by text or email, in the host's
  own words, from Gather. The child rule, the "don't nudge" mark and the
  host rule all live on the person's place in the event, so with no
  place on A they were all skipped. The email opt-out was looked up for
  event A, so an opt-out from B's emails was not seen. (The text
  opt-out is by phone number and still held.)
- invite-detail would SHOW that person's name, email, phone number and
  text opt-out.
- manual-override would write a "marked by hand" line about that person
  into A's invite log, and answer with their name.
- The delete would write a "removed" line into A's history and answer
  "done". It removed nothing (every write was already limited to A).

## What each route did before, and does now

All four now start the same way, right after the sign-in check: they
look up the person's place in the event in the address (one indexed
lookup on PersonEvent, reading only its id). If there is none, they
answer 404 `{ "error": "Person not found" }` and stop: nothing is read
about the person, nothing is written, logged, put in the host's history
or sent. Everything after that line is exactly as it was.

- POST `nudge`. Before: for a person not on the event, the route went
  on to the recipient decision, which let them through (no place, so no
  child, host or mark check could fire), then to the cooldown, the
  channel choice, the opt-out reads and the send. Now: refused 404
  before the sample-event check, before the body is read, before the
  recipient decision is called. For a person on the event nothing
  changes: the sample-event 409, the body checks, the child, host and
  mark refusals, the cooldown, the opt-outs, the send and its record are
  all as they were. `resolveManualNudgeRecipient` is not changed.
- GET `invite-detail`. Before: returned the person's name, email,
  phone, text opt-out and status to a host of any event, given the id.
  Now: 404 before the person is read. A member's answer is unchanged.
- POST `manual-override`. Before: wrote a MANUAL_OVERRIDE_MARKED line
  in A's invite log for the outsider and answered 200 with their name
  ("marked as confirmed"). Now: 404 before the body is read and before
  anything is written. A member's answer is unchanged.
- DELETE (the person route). Before: answered 200 and wrote a
  REMOVE_PERSON line in A's history (and touched A's updatedAt), though
  it removed nothing. Now: 404 before the body is read and before
  anything is written. A member is removed exactly as before (including
  the host refusal, 409, for the host's own row).

## The answer, copied from which siblings

GTC-400 sweep as checking. Both answer 404.

- `reset-claim` finds the person only through a place in this event and
  answers `404 { error: 'Person not found' }` when there is none.

Copied: reset-claim's, status and words: 404 `{ error: 'Person not
found' }`. The status is the same in both. The words are reset-claim's
because they are also what three of the four routes already say for an
id that does not exist at all, so a person on another event now looks
exactly like no person: the answer gives no hint that the id is real.

## Does any real screen call one of them for a person not on the event?

No. Searched every caller under `src/` (outside `src/app/api`):

- `PersonInviteDetailModal` calls invite-detail and manual-override,
  and holds `NudgeComposer`, which calls the nudge. It is opened from
  two places on the old dashboard (`InviteStatusSection` and
  `WhosMissing`), both fed by GET `invite-status`, whose people are the
  event's own PersonEvent rows. The host's own row is not clickable.

  rows.
- The only DELETE caller is `PeopleSection` (old dashboard), whose
  people come from GET `/api/events/[id]/people`, the event's
  PersonEvent rows.

So no STOP. The only way a screen now meets the new 404 is a stale
screen, for a person removed from the event since it loaded (before,
the nudge would have gone on regardless).
