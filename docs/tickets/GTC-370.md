# GTC-370 — Moment 2's questions forget a change whose save failed

**Status:** Open — a stub, filed 2026-10-08 on the founder's instruction at [[GTC-367]]'s build
approval. Found by Cowork reading GTC-367's build. No code now. Not scoped.
**Severity:** not set — the founder's to set. **Proposed:** low.

---

### Signal

The founder's words, at GTC-367's build approval (2026-10-08): *"on Moment 2's questions, when a
save fails, the change waiting to be saved is forgotten before the result is checked (leave() in
Moment2Step1Modal.tsx). So the first tap on a way out stays put and the footer says the save failed,
as ruled, but a second tap leaves without saving that change. Generate and the half-second save have
always forgotten it the same way. Found by Cowork reading GTC-367's build."*

### What the code does (read by Claude Code at `2c6e3da`, 2026-10-08)

`src/components/plan/Moment2Step1Modal.tsx` keeps the change waiting to be saved in `pendingRef`.
All three places that save it clear it whatever the save's result:

- `leave()` (GTC-367's ways out: "← Your events", "← Back to the people", the strip), lines 474–478:
  `const saved = await saveToApi(pendingRef.current); pendingRef.current = null; if (!saved) return;`.
  The first tap stays and the footer shows the failure (`saveError`), as ruled at GTC-367 (Q7); the
  second tap finds nothing pending and leaves.
- `handleGenerate`, lines 452–457: the same order. A second press of "Generate plan →" generates from
  the stored answers without the failed change.
- `scheduleSave`, the half-second save, lines 368–370: `saveToApi(pendingRef.current);
  pendingRef.current = null;`, not awaited.

The change stays on screen (it is in the component's state), and every save sends the whole set of
answers, so any later change saves it too. It is lost only when she leaves, or presses Generate,
with no other change in between. Same family as [[GTC-151]] (a save that fails quietly loses what she
chose).

### For the plan

- Keep the change pending until a save succeeds (clear `pendingRef` only on success, in all three
  places), so a second tap retries the save rather than leaving without it.
- A test: a save made to fail (in the browser, the setup route's POST failed), then two taps on a way
  out, the second still stays; and Generate the same.

### Stops

- NOTHING SENDS FOR REAL; no AI call (Generate is never pressed for real: the three safeguards).
- No migration, no new route.
