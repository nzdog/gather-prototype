# GTC-463 - Stop making the device id; the host gets type and time only

**Status: built and gated on `gtc-463-no-device-id` (from `docs/gtc-461-close`, 2e31953), 15
Nov 2026. Committed only on the founder's word; the hash goes in the pull request text (Q6).**

All dates are NZ time (NZDT, UTC+13).

## Why

- When someone claims a name on a shared link, the claim route makes a "device id" from their
  browser text and internet address, and saves it in `AccessToken.claimedBy` and in the
  `NAME_CLAIMED` log row. Nothing reads it to decide anything; the code called it "for audit"
  and "NOT for security".
- `invite-detail` sends the host's browser each guest's newest 20 log rows whole: browser text,
  device id, shared-link token, names, phone numbers. The host's screen draws none of it
  (`PersonInviteDetailModal` declares the list and never uses it).
- The privacy page says none of this (a separate ticket).

## The founder's rulings (15 Nov 2026)

In the founder's words, as given in the planning brief:

- Device id: "Stop making it". New claims store nothing in AccessToken.claimedBy. The column
  stays: dropping it is a migration, which is Zone 5. No old rows to clear: "There are no live
  ones" (my statement, not counted).
- Host's browser: "Yes: send only the event type and time". I give my explicit word to edit the
  invite-detail route, a Zone 7 reader frozen byte for byte by tests/tweaks-guard-test.ts:409,
  and to update that guard's list in the same ticket.
- Zone 3: claimedBy is a field of AccessToken. Writing nothing into it is not issuing,
  validating or scoping a token. I rule that this change is allowed.
- Browser text on a guest-link open: keep storing it as now (p route and c route). Do not change
  those routes.

The plan's questions, answered 15 Nov 2026 (verbatim, the founder's words):

- Q1. "No, leave the frozen file alone". Option A: do not edit invite-status. It will send
  claimedBy as null. No G44 change.
- Q2. "Yes, edit it". My Zone 3 ruling covers reset-claim. Stop reading and logging
  previousClaimBy. Leave its own token write (claimedBy null) exactly as it is.
- Q3. "Yes, delete the line" in PersonInviteDetailModal.
- Q4. "From the GTC-461 docs branch". New branch from docs/gtc-461-close (2e31953). The pull
  request shows two commits.
- Q5. "Yes, correct the wording only" in host-never-messaged-test. Comments only. No change to
  what it checks.
- Q6. "Leave it blank, record it next time". commit: stays blank. The hash goes in the pull
  request text.

## What changes

- `src/app/api/join/[token]/claim/route.ts` (Zone 3, by ruling): reads no request headers,
  makes no device id, writes nothing to `claimedBy` and no `deviceId` into the `NAME_CLAIMED`
  row. The checks, the claim time, the SHARED mark, the log row and the answer are otherwise
  unchanged. The row keeps `sharedLinkToken` and `personName`.
- `src/app/api/events/[id]/people/[personId]/reset-claim/route.ts` (Zone 3, by ruling Q2): no
  longer reads `claimedBy` and no longer logs `previousClaimBy`. Its own token write
  (`claimedAt: null, claimedBy: null`) is exactly as it was.
- `src/app/api/events/[id]/people/[personId]/invite-detail/route.ts` (Zone 7 reader, by the
  founder's word): each log row is read and sent as `type` and `createdAt` only.
- `tests/tweaks-guard-test.ts`: the invite-detail entry (check G45) carries the ruled change by
  the SHA-256 of the file's final text (the [[GTC-442]] kind). The invite-status entry (G44) is
  unchanged (Q1).
- `src/components/plan/PersonInviteDetailModal.tsx`: the unused `metadata` line goes (Q3).
- `tests/coordinator-token-exposure-test.ts`: the claim's happy path now runs in this process;
  the guest control reads the real claim, not a throw.
- `tests/host-never-messaged-test.ts`: two comments corrected, words only (Q5).
- `tests/no-device-id-test.ts` (new) and its script `test:no-device-id` in `package.json`.

Untouched: `src/app/api/events/[id]/invite-status/route.ts` (Zone 7, frozen, G44). After this
ticket it sends `claimedBy: null` for every guest (Q1).

## Not in this ticket

- The privacy page words, the daily visit count, clearing old rows, keying the id with a secret,
  anything about Twilio, any migration.
- The `NAME_CLAIMED` row keeps `sharedLinkToken` and `personName`, and `LINK_OPENED` keeps the
  browser text, in the database. After this ticket neither reaches the host's browser.

## Evidence

- **Root cause.** Not a fault but a ruling. The claim route built a "device id" from the
  guest's browser text and address and kept it in `AccessToken.claimedBy` and the `NAME_CLAIMED`
  row; nothing read it. `invite-detail` sent each guest's newest 20 log rows whole to the host's
  browser, which drew none of them.
- **What the founder ruled, and what proves it:**
  - A claim keeps no device id: S1 S2 S3 (code), P1 P2 (in process), H2 H3 (over HTTP, with
    made-up browser text and address). CONTROLS S6 H1 H4 H5: the claim still refuses, claims,
    marks SHARED and logs NAME_CLAIMED with the shared-link token and the name.
  - reset-claim logs no `previousClaimBy` (Q2): S4, R2. CONTROL R1: the reset still empties
    `claimedAt` and `claimedBy` and logs `CLAIM_RESET` with the name.
  - The host gets each log row's type and time only: S5, D2, D3a-d (no browser text, device
    id, shared-link token or phone number from a log row). CONTROLS D1 D4: every row's type and
    time, newest first, and every other key of the answer as before.
  - invite-status, frozen and left alone (Q1), now sends `claimedBy` as null: T2 (CONTROL T1).
  - The fixture leaves nothing behind: K1.
