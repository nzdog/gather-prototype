and email address, and at the host's own view of the event.

## Signal

**Expected**
`GET /api/events/[id]` answers 401 to a caller with no session and 403 to a
signed-in user with no role on the event, exactly as its own `PATCH` and
`DELETE` already do and exactly as every sibling under `/api/events/[id]/`
does.

**Actual**
It answers **200** to anyone who knows an event id, and returns the whole
`Event` row plus the host's and co-host's id, name and email.

**Smallest failing case**
`curl http://localhost:3000/api/events/<eventId>` with no cookie and no
header returns 200 and the host's email address.

**The sentence that sets the severity:** the chain below needs **no
credential beyond an event id**. Not a stolen session, not a leaked token,
not a guessed password — an event id, which appears in every host dashboard
URL. The only thing that kept this from being trivially exploitable is that
`cuid`s are not enumerable, so an attacker must be given an id rather than
walk the space. That is an accident of the id format, not a control. It is
the single reason this is contained, and it is not a defence anyone chose.

---

## Reproduce

**Required state**
- Auth state: **none**. No session cookie, no bearer token, no header.
- Event state: any. Proven against a `CONFIRMING` event with `sentAt` set.
- Multi-actor: [ ] Yes [x] No — the whole point is that no actor is needed.

**Steps**
1. Start the dev server and note any event id.
2. `curl http://localhost:3000/api/events/<eventId>`
3. Read `hostId` out of the response.
4. `curl "http://localhost:3000/api/events/<eventId>/tokens?hostId=<hostId>"`
5. Take the `scope: "HOST"` token out of that response.
6. `curl http://localhost:3000/api/h/<hostToken>/export-text`

**Observe:** step 2 returns 200 with the host's email; step 4 returns 200
with every access token for the event including the HOST one; step 6 returns
200 with every guest's name, email, assigned item and RSVP status.

### `hostId` is a credential in three routes, not one

Step 2 of the chain works because `GET /api/events/[id]/tokens` accepts a
`hostId` query parameter as authentication, comparing it to `event.hostId`.
That parameter is published by the route in step 1. **A query parameter that
a sibling route hands out is not authentication.**

The same pattern was copied into two more routes, each carrying a comment
saying so — "mirrors /api/events/[id]/tokens/route.ts":

- `GET` in `src/app/api/events/[id]/invite-status/route.ts` — per-person
  nudge stamps and reachability tiers.
- `POST` in `src/app/api/events/[id]/people/batch-import/route.ts` — **a
  write.** An event id yields a `hostId`, and a `hostId` admits an import of
  arbitrary people into the event.

Both proven, each against its own no-`hostId` control:

```
$ curl -s -o /dev/null -w "HTTP %{http_code}\n" \
    ".../api/events/gtc192-phase7-variants/invite-status?hostId=cmmom5428004o1y6hiztga9i4"
HTTP 200
$ curl -s -o /dev/null -w "HTTP %{http_code}\n" \
    ".../api/events/gtc192-phase7-variants/invite-status"
HTTP 401

$ curl -s -w "\nHTTP %{http_code}\n" -X POST \
    ".../api/events/gtc192-phase7-variants/people/batch-import?hostId=cmmom5428004o1y6hiztga9i4" \
    -H "Content-Type: application/json" -d '{"people":[]}'
{"error":"No people provided for import"}
HTTP 400
$ curl -s -w "\nHTTP %{http_code}\n" -X POST \
    ".../api/events/gtc192-phase7-variants/people/batch-import" \
    -H "Content-Type: application/json" -d '{"people":[]}'
{"error":"Unauthorized"}
HTTP 401
```

The `batch-import` probe was deliberately sent with an empty `people` array,
so the proof stops at the body check. Reaching `"No people provided for
import"` proves the auth gate was passed; nothing was written.

### ⚠ A SEARCH THAT FAILS ON QUOTING READS EXACTLY LIKE A SEARCH THAT FOUND NOTHING

Recorded at the founder's instruction, 2026-09-11, in the family of the
standing warning — the same species as *"a suite that cannot report its red is
not a red."*

While sweeping for callers that send `?hostId=`, this ran:

```
grep -rn "hostId=\${" src/
```

It printed nothing, and nothing is what "no callers left" looks like. The
pattern had been mangled by the shell before grep ever saw it, so the sweep
was never performed. A fourth caller was sitting in plain sight:
`handleBatchImport` in `src/components/plan/PeopleSection.tsx`, appending
`?hostId=` to the **write**.

**It was `npm run test:batch-import-auth` that caught it**, by failing on an
assertion about that exact line — a test written for GTC-027 to hold the
opposite contract. The grep was believed; the test was not optional.

The rule this leaves behind: **an empty search result is a claim, and a claim
needs a control.** Before trusting a zero, run the pattern against a string
you know contains a match. Prefer a literal fragment (`batch-import?hostId`)
over anything carrying `$`, `{`, backticks or quotes, since those are what the
shell eats. And where a test can assert the same fact, let the test be the
evidence — a test that fails is louder than a grep that returns nothing.

### Why the `hostId` path existed, and why removing it is now safe

[[GTC-026]] added it for a real reason, recorded in
`tests/invite-status-auth-test.ts`: "the /invite-status fetch sent no
credentials, so requireEventRole called getUser() → null (no session in
token-link flow) → 401 every time."

That justification does not survive step 1 of this ticket. The plan page gets
`event.hostId` from `loadEvent` in `src/app/plan/[eventId]/page.tsx`, which
fetches this very route. Once the route requires a session, only a caller
that already has one can learn `hostId` at all — so any caller still able to
supply the parameter is a caller for whom `requireEventRole` would already
have succeeded. The parameter becomes strictly redundant.

Checked for a session-less path onto `/plan/` and found none. The token
surfaces never link to it; the one link that exists,
`src/app/p/[token]/page.tsx`, renders only in the host-preview branch, which
`GET /api/p/[token]` gates on `getUser` — so it is reachable only with a
session already in hand.

### Middleware does not cover this

`middleware.ts` matches `/p/`, `/h/`, `/c/`, `/api/p/` and `/api/c/` only. It
never sees `/api/events/`, and its job is cookie isolation ([[GTC-001]]), not
authentication. There is no upstream guard to lean on.

## Unknowns — and the blocker behind the one untested path

### `POST /api/templates` 403s for every caller, and that is WHY the overlay is untested

**This is not a passing mention. It is the reason a deliverable in this ticket
could not be verified.**

`POST` in `src/app/api/templates/route.ts` sets `const hostId = user.id` — a
**`User`** id — and then refuses unless `event.hostId === hostId`. But
`Event.hostId` is a relation to **`Person`**, not `User`:

```
prisma/schema.prisma:177
  host  Person  @relation("EventHost", fields: [hostId], references: [id])
```

The two id spaces never coincide. Measured, not assumed: 5 `Person` rows carry
a `userId`, and **0** rows satisfy `Person.id = userId`. So the comparison is
false for every event and every caller, and the route answers 403 to the
event's own host, always:

```
$ curl -s -X POST http://localhost:3000/api/templates \
    -H "Cookie: session=<a valid host session>" \
    -H "Content-Type: application/json" \
    -d '{"eventId":"gtc192-phase7-variants","name":"GTC-267 overlay probe"}' \
    -w "\nHTTP %{http_code}\n"
{"error":"Unauthorized"}
HTTP 403
```

`POST /api/templates` is the **only writer of `StructureTemplate.createdFrom`**
in the tree, and `createdFrom` is the only source of `Event.clonedFromId`
(`clonedFromId: template.createdFrom || null` in
`src/app/api/templates/[id]/clone/route.ts`). So the chain is: no template can
be saved → no clone can carry a source → no event ever gets a `clonedFromId` →
**the reuse overlay cannot fire at all.**

**Say it exactly this way: the clone-source overlay is untested because of a
separate, unrelated bug — not because it is dormant by design.** The data
shape it needs is currently unreachable through any code path, and making it
reachable means fixing a different route in a different ticket.

Not fixed here. It is a different route, a different defect, and nothing to do
with authentication.

### What that leaves untested

- The `/clone-source` **endpoint** was driven and is verified: 200, exactly
  five fields, nothing more.
- The **overlay render** — `fetchSourceData` in
  `src/app/plan/[eventId]/page.tsx` drawing that response — was **not
  exercised**, for the reason above. Reported untested rather than claimed.

## Evidence (Executor-Completed)

**Root cause confirmed**

Three separate faults, one chain. First, nine `GET` handlers under
`/api/events/[id]` never called a guard — `GET` in `route.ts` and in
`summary`, `items`, `days`, `conflicts`, `conflicts/dismissed`,
`conflicts/[conflictId]`, `revisions` and `revisions/[revisionId]`. Two of
them sit in files whose other methods are guarded, which is why the
file-level inventory gate read them as authenticated. Second, `hostId` was
accepted as a credential by three routes — `GET` in `tokens/route.ts`, `GET`
in `invite-status/route.ts`, and `POST` in `people/batch-import/route.ts` —
and the first of the nine published exactly that value to anonymous callers,
so an event id bought the HOST access token and, through it, every guest's
email. Third, both handlers in `route.ts` returned `prisma.event.findUnique`
with an `include` and no top-level `select`, so `sharedLinkToken` (a join
credential), the Stripe columns and the check-plan telemetry were serialised
to whoever asked. The guard closes the reads, the removal kills the chain,
and `EVENT_WIRE_SELECT` narrows what leaves.
