# GTC-216 — STUB: `@@unique([eventId, personId])` on `WrapUpLink`

**Status:** Open — unassigned, not started. Ready to build; unblocked by the production
duplicate-row count below. **Effort:** TBD

*Carried forward from **GTC-209** (`b0c6e8c`), which fixed the wrap-up double-send at the app
level and deliberately did not add this constraint. This ticket is the remaining race backstop.*

### Scope, one line

Add `@@unique([eventId, personId])` to `WrapUpLink` (`prisma/schema.prisma:1045-1066`) so a
guest can hold at most one wrap-up link per event at the database level — but only after
proving production holds no duplicates.

### Why GTC-209 deferred this rather than shipping it

GTC-209's acceptance required counting existing duplicate `WrapUpLink` rows **before** writing
any `@@unique` migration, because a unique constraint will not apply if duplicates already
exist. The count was run read-only against `gather_dev`:

```
WrapUpLink rows total: 0
Duplicate (eventId, personId) groups: 0
Events with a WRAP_UP_SENT entry: 0
```

**Clean, but vacuously so — and that is the whole reason this ticket exists.** The table is
empty because nothing has ever pressed wrap-up locally. The query therefore says nothing about
production, which is the *only* environment that could hold duplicates, and which is not
reachable from the dev environment (Railway; see GTC-214's stub for the deployment notes).

Shipping the constraint on that evidence would have risked a failed `prisma migrate deploy` on
production — trading a narrow in-process race for a broken deployment. The app-level guards
landed instead, and this was split out rather than left as an open box on a closed ticket.

### Precondition — run this BEFORE writing any migration

**Done — production count run 2026-08-05, result clean.** Against **production**, not
`gather_dev`. Query shape from GTC-209 / the audit doc
(`docs/04_roadmap/moment4-hinge-report-accuracy-audit-2026-08-04.md`; note the table is
`AuditEntry`, not `AuditLog`):

```sql
-- Wrap-up: duplicate links?  Run BEFORE writing any @@unique migration.
SELECT "eventId","personId",COUNT(*) FROM "WrapUpLink"
GROUP BY 1,2 HAVING COUNT(*) > 1;

-- Corroborating: did any host ever press wrap-up twice?
SELECT "eventId", COUNT(*) FROM "AuditEntry"
WHERE "actionType" = 'WRAP_UP_SENT' GROUP BY 1 HAVING COUNT(*) > 1;
```

**Result (production, 2026-08-05): zero duplicate `(eventId, personId)` `WrapUpLink` rows.**
Unlike the earlier `gather_dev` count, this result is not vacuous — production has live
wrap-up traffic. Reading the result:

- **Zero rows (this case)** → no cleanup needed. This ticket is exactly "add the constraint",
  and its scope is a one-statement migration. Stop Condition 7 still applies (surface the SQL
  for sign-off before apply) — the count clears the *cleanup* question, not the migration
  approval gate.
- Non-empty was the other branch this precondition was guarding against — did not occur, so
  the cleanup-ruling path below is moot and left in place only as a record of what was checked.

### What this closes that GTC-209 does not

GTC-209 shipped three app-level guards — the route guard on `event.wrappedAt`
(`wrap-up/route.ts`), an existence check in `generateWrapUpLinks` keyed on `(event, person)`,
and a UI gate on the already-serialised `wrappedAt`. Those cover the realistic path: a reload,
a second tab, or a direct POST.

**What remains uncovered is the simultaneous double-POST race** — two requests that both read
`wrappedAt: null` before either writes it, both pass the route guard, and both reach the
generator before either has created a row. The window is milliseconds wide and only a database
constraint closes it atomically; the generator's existence check narrows it but is not atomic
with the insert.

Worth knowing: `WrapUpLink` today has `token @unique` only, and its three `@@index`
(`schema.prisma:1063-1065`) are all non-unique. Tokens are freshly random per call, so the
token index never fires on a duplicate. And the `AuditEntry` composite unique that looks like
it might have caught this does not — `logAudit` never sets `sequence`, and no migration in the
repo declares `NULLS NOT DISTINCT`, so Postgres treats the NULLs as distinct.

### Needs full scoping when pulled

This is a stub. It was blocked on the production duplicate count; that count is now done
(2026-08-05, zero duplicates recorded above) and the ticket is ready to build. When pulled, it
still needs: the migration SQL surfaced for sign-off before apply (Stop Condition 7, per

layer. **Do not execute from this stub — the migration itself is out of scope for whatever
picked up this frontmatter update; it is a separate execution pass.**
