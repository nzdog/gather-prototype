## What was wrong

A User's address is unique letter for letter. Both doors that make a
User from an address looked it up letter for letter too, so
"Nigel@x.com" and "nigel@x.com" were two accounts. A host who paid with
one spelling and signed in with another could land on an empty account
and not see her own events.

## The founder's rulings (27 Oct 2026, in Cowork)

1. Option B-plus for launch: one shared helper finds or makes a User by
   email in this order: (a) trim; (b) look for the EXACT spelling and use
   it if found; (c) otherwise look ignoring capitals, then re-check EVERY
   candidate in code (trim plus lower-case equal) and take the OLDEST by
   createdAt, then id; (d) otherwise make a new User with the trimmed,
   LOWER-CASE address. Prisma's case-blind match may act as a pattern
   match (an underscore as a wildcard), so the code re-check is not
   optional. Two sign-ins at once must not make two Users: if the create
   hits the unique rule, look again and use the winner.
2. When the signed-in address and the paid address differ only by
   capitals or outer spaces, the paid event lands on the SIGNED-IN
   account (its own User, its own Person). No new User or Person. In
   every other case the event lands on the account the helper picks for
   the paid address.
3. New Users are stored lower-case. Old rows are not touched.
4. In a pair of spellings that already exists, the exact spelling still
   opens its own account; a third spelling opens the oldest.
5. The helper lives in src/lib/accounts, NOT src/lib/auth (that folder
   is zone 1 by the letter).
6. The capitals rate-limit gap in magic-link and claim waits until after
   launch. Do not touch those two routes or src/lib/email.ts.
7. One new security suite, three checks (253 to 256).
8. The founder runs the read-only production check himself and will not
   wait for it; nothing in this build changes data.

## What changed

- src/lib/accounts/user-by-email.ts (new): findOrCreateUserByEmail(db,
  email), taking the Prisma client or a transaction. The order is ruling
  1 exactly. Step (d) inserts with "skip a duplicate" (Postgres ON
  CONFLICT DO NOTHING) and then looks again by the lower-case address,
  so a lost race uses the winner's row. A plain create that failed
  would not do inside a transaction: in Postgres a failed statement ends
  the transaction, leaving nothing to look again with. An empty address
  (after trimming) is refused with an error.
- src/app/api/auth/verify/route.ts: lines 61-62 replaced by one call to
  the helper inside the same transaction. The link, its spend, the Person
  claim, the Session and the cookie are unchanged.
- src/lib/events/payment-identity.ts: one new field,
  landOnSessionAccount, true only on SESSION_MATCHES, false on the other
  two. The comment that said the lookup was exact on purpose is
  rewritten to say what is true now. Every other field and value is as
  it was.
- src/app/api/events/route.ts: when landOnSessionAccount is true, the
  event goes on the signed-in User and its own Person; otherwise the
  helper picks the User for the paid address. The comment holding
  "paying $12 and typing a known" is word for word as it was. The
  welcome email, the response and the rest are unchanged.
- One choice made without asking (the founder may be away): a Person
  made by this route now takes its name and address from the User's
  STORED address on BOTH branches (the prompt asked for it on the
  signed-in branch). Before, it took the paid spelling as typed. So a
  Person never disagrees with its own account (for example "Sarah@X.com"
  typed against an account stored "sarah@x.com"). For a brand-new
  account the only difference is lower case and no outer spaces.
