## The premise is CONFIRMED — and the mechanism is worse than the one it named

**TNZ answered on 2026-08-31.** The full answers are recorded in *TNZ's answers* below. The
short of it:

> **A send to a blacklisted number returns 200. The message is ACCEPTED.** The failure arrives
> later, through **status reporting** — TNZ's status GET endpoint or their status webhook — as
> `Status=Failed`, `Result="Destination is blacklisted"`.

The consequent this ticket asserted therefore **holds**: `sendSms` logs `NUDGE_SENT_AUTO` for a
message that was never delivered.

**But the antecedent as originally phrased is false, and that matters more than the confirmation.**
This ticket guessed the failure would be *"a 2xx carrying a per-destination error"* — a wrong
value in a field `sendViaTnz` already reads past. It is not. **The send response carries no
per-destination outcome at all.** There is nothing in the accept response to parse differently,
no field to start reading, no branch to add. `sendViaTnz` is not misreading TNZ's answer; it is
reading TNZ's *only* answer, which is *"accepted"*, and `sendSms` is calling that delivery.

TNZ said this themselves, and it is the sentence to carry forward:

> *"you should be working from delivery results and not assuming the API accepting a message
> means successful delivery."*

**The consequence for the fix.** The original ticket withheld a fix because *"writing a fix before
those answers means writing a guess about a wire format"*. The answers do not unblock a fix here;
they relocate it. The information needed to stop writing a false stamp lives in a channel Gather
does not consume — see *Nothing consumes delivery status* below. That channel is [[GTC-264]], and
**this ticket now depends on it.**

## TNZ's answers — the factual basis (2026-08-31)

Recorded in substance, with TNZ's own words quoted where quoted. Attributed and dated the way
[[GTC-229]] records the 2026-08-29 set. These are premises; do not re-derive them from guesswork
about how other providers behave.

**Against this ticket's four questions:**

1. **What HTTP status does a blacklisted send return?** **200.** The message is **accepted**.
   Blacklisting is not signalled on the send call at all.

2. **If 2xx, which field carries the outcome?** **None on the send response.** The outcome is
   carried by **status reporting** — the status GET endpoint or the status webhook — as
   `Status=Failed` with `Result="Destination is blacklisted"`. TNZ's guidance, verbatim:
   *"you should be working from delivery results and not assuming the API accepting a message
   means successful delivery."*

3. **`Destinations` is an array — is the status per-request or per-destination?**
   **Status webhooks are distributed PER DESTINATION.** There is no batch ambiguity to resolve:
   one destination, one status report. The partial-failure shape this ticket worried about does
   not arise.

4. **Is the same shape used for other per-destination failures?** Implied yes by answer 3 — status
   reporting is the general delivery-outcome channel, of which `Destination is blacklisted` is one
   `Result` value. **Not separately confirmed**, and [[GTC-264]] must read the doc rather than
   inherit that inference. It is recorded here as an inference, not as an answer.

**Note on the unread `Result` field.** This ticket cited, as evidence, that `sendViaTnz` declares
`Result` in its parse type and never reads it. That observation was correct about the code and
wrong about its significance. `Result` **is** TNZ's field name — but it arrives on the *status
report*, not the *send response*. The declared-and-unread field is a vestige pointing at the right
name in the wrong channel. Reading it where it is currently declared would still yield nothing.

## What the code does today, at `5df28ba`

`sendViaTnz` in `src/lib/sms/tnz-client.ts`:

1. `POST`s to `TNZ_ENDPOINT` and reads the body with `await response.text()`.
2. `if (!response.ok)` → returns `{ success: false, error: 'TNZ HTTP <status>: <body>' }`.
   **This is the only failure branch that inspects the response.**
3. Otherwise, parses the body inside a `try` purely to pull a message id —
   `parsed.MessageID ?? parsed.messageID`. A parse failure is swallowed; the comment states the
   intent: *a 2xx without a parseable body is still a success*.
4. Returns `{ success: true, messageId }`.

`TnzSendResult` has three members — `success`, `messageId`, `error`. **There is no delivery-state
member, because there is no delivery state to carry.** The doc comment on `sendViaTnz` says
*"Returns `{ success: true, messageId }` on HTTP 2xx"*, which is an accurate description of a
function whose success means acceptance and is named as though it means sending.

`sendSms` in `src/lib/sms/send-sms.ts` then branches on `result.success` alone:

- `!result.success` → `throw` → caught → `logInviteEvent` with `SMS_SEND_FAILED`, and the function
  returns `blocked: 'SEND_FAILED'`.
- `result.success` → `logInviteEvent` with **`NUDGE_SENT_AUTO`**, metadata `{ messageId, provider,
  phoneNumber, messageLength, ...metadata }`, and returns `{ success: true }`.

A blacklisted destination takes the second path. **Nothing downstream can tell it from a delivery**,
and — now confirmed — nothing ever will, because the correcting signal is never fetched.

### The `messageId` is the handle, and it is written to a place nothing reads

`sendViaTnz` extracts `MessageID` under a comment naming its purpose: *"TNZ returns a JSON body
containing a `MessageID` for delivery tracking."* `sendSms` stores it in `InviteEvent.metadata`.

**A repo-wide grep at `5df28ba` finds no reader of `metadata.messageId`.** It is written by
`sendSms` (into `NUDGE_SENT_AUTO`) and by the manual-nudge route (into `NUDGE_SENT_HOST`,
`src/app/api/events/[id]/people/[personId]/nudge/route.ts`), and returned up the call stack through
`sendNudge`, `sendProxyNudge` and `sendDecideByFollowup` as an unread field. The one handle TNZ
gives Gather for correlating a delivery result back to a send is captured, stored, and never
queried. **That is not a second defect; it is the missing half of this one** — and it is the join
key [[GTC-264]] will need.

## Nothing consumes delivery status — verified at `5df28ba`

This was checked, not assumed, before the claim was recorded. Four searches, four negatives:

1. **No route.** All 104 `route.ts` files under `src/app/api` were enumerated. There is no
   delivery-receipt, DLR, status-callback or message-status route. The only inbound webhooks in the
   tree are `src/app/api/webhooks/stripe/route.ts` and `src/app/api/sms/inbound/route.ts` — and the
   latter is the Twilio-shaped **MO** handler ([[GTC-229]] audit A), which is a different contract
   from delivery receipts, as [[GTC-229]] answer 3 warns.

2. **No poller.** No client, cron route, or library function calls a TNZ status endpoint. The three
   cron routes are `nudges`, `wrap-up-dispatch` and `decide-by-followups`; none fetches a result.
   `src/lib/sms/tnz-client.ts` exports two functions — `isTnzEnabled` and `sendViaTnz` — and the
   `TnzSendResult` interface. Nothing else.

3. **No schema.** `InviteEventType` in `prisma/schema.prisma` has eighteen members and **not one
   names a delivery outcome**: `SMS_SEND_FAILED` is written only in the `sendSms` catch block —
   it is a *send-time* failure, not a delivery-time one. No model stores a provider message id, a
   delivery state, or a delivered-at timestamp.

4. **No red source.** `RED_REASONS` in `src/lib/glance/state.ts` is exactly
   `['DECIDE_BY_EXPIRED', 'REVERSAL', 'EXHAUSTED_SILENCE']`. There is no bounce. This independently
   confirms [[GTC-192]]'s own statement — *"no bounce-red source exists in the tree today (delivery
   receipts are §10.9 / the press)"* — and is why Ruling 14 there is implemented as
   `worst !== 'GREEN'` in `derivePersonState` rather than as a list of red reasons.

**Conclusion: delivery status is not consumed anywhere in Gather.** Acceptance is the only signal
the system has ever had, and every stamp, count and colour is downstream of it.

## What follows — no longer conditional

Three consequences, each traced to a symbol at `5df28ba`. All now hold unconditionally.

### 1. The inbound attribution index is corrupted

`NUDGE_SENT_AUTO` is not only an audit record. `POST` in `src/app/api/sms/inbound/route.ts`
resolves an inbound reply to a person and event by querying for the most recent `NUDGE_SENT_AUTO`
whose `metadata.phoneNumber` matches the sender, newest first. **That query is the only mechanism
in the codebase for attributing an inbound message back to a person** — [[GTC-229]] F1 establishes
this, and a repo-wide grep at `5df28ba` confirms the inbound route is the sole production reader of
the enum value (the only other occurrences are the write in `sendSms`, the explanatory comment atop
`src/lib/sms/decide-by-sender.ts`, and two test files).

A false `NUDGE_SENT_AUTO` is therefore not an inert bad log line. It is a write to the index that
answers *"who is this reply from, and about which event?"* — written **newest first**, so a false
entry outranks every true one before it.

**TNZ's answer 3 to [[GTC-229]]'s follow-ups sharpens this into a direct collision.** TNZ attribute
an inbound reply on the shared shortcode to the **last sent message** to that number. Gather's
index is newest-`NUDGE_SENT_AUTO`-wins. **The two rules agree** — which is the good news, and is
recorded as such in [[GTC-229]] F1. The bad news is that this defect is what makes Gather's copy of
that rule wrong: a blacklisted accept is logged as sent, becomes Gather's "last sent", and TNZ's
genuine last-sent is a different message. The one place the two systems were structurally aligned
is desynchronised by a false stamp.

And the population is exactly the wrong one: the number that gets blacklisted is, by definition,
the number that opted out, so the false successes land on precisely the people the inbound handler
exists to serve.

### 2. Nudge cadence stamps are consumed

`sendNudge` in `src/lib/sms/nudge-sender.ts` writes `PersonEvent.firstNudgeSentAt` or
`secondNudgeSentAt` **only** on `result.success` — its own comment records why: *a send that failed
leaves no stamp and the next tick retries it.* A false success inverts that guarantee. The stamp is
written, the retry never comes, and `getNudgeStatus` in
`src/app/api/events/[id]/invite-status/route.ts` reports `'first reminder sent'` to the host.

### 3. The maybe's single follow-up is spent

`sendDecideByFollowup` in `src/lib/sms/decide-by-sender.ts` stamps
`Assignment.decideByFollowupSentAt` only on success. A maybe gets exactly one decide-by follow-up.
A false success consumes it with nothing sent.

### The other callers — enumerated on conversion

The original filing named `sendProxyNudge` and wrap-up as untraced. All five `sendSms` callers at
`5df28ba` are now listed, so none is discovered mid-fix:

| Caller | Stamp written on success |
|---|---|
| `sendNudge` in `src/lib/sms/nudge-sender.ts` | `PersonEvent.firstNudgeSentAt` / `secondNudgeSentAt` |
| `sendDecideByFollowup` in `src/lib/sms/decide-by-sender.ts` | `Assignment.decideByFollowupSentAt` |
| `sendProxyNudge` in `src/lib/sms/proxy-nudge-sender.ts` | logs `PROXY_NUDGE_SENT`; not traced further |
| `dispatchPendingWrapUpMessages` in `src/lib/wrap-up.ts` | sets local `success = true`; **suppresses the email fallback**, since fallback fires only on `!smsResult.success` |
| `POST` in `src/app/api/events/[id]/people/[personId]/nudge/route.ts` | logs `NUDGE_SENT_HOST`; returns `sentAt` to the host UI |

The wrap-up row is the sharpest of the three additions: a false accept does not merely mis-stamp,
it **cancels the fallback that would have reached the guest by email.**

## Scope

**This ticket is now a defect, but it is NOT yet actionable.** It depends on [[GTC-264]].

The fix cannot be written against the send response, because the send response contains nothing to
read (answer 2). Making the stamps honest requires a delivery-result signal that does not exist in
the tree. **[[GTC-264]] builds that signal; this ticket consumes it.** Attempting the fix first
would mean inventing a local guess at delivery state — the same class of error the original filing
declined to make about the wire format.

**When [[GTC-264]] lands, this ticket owns:**

- The naming and semantics of `sendViaTnz` / `TnzSendResult` — acceptance is not delivery, and the
  type should say so.
- What `sendSms` writes on accept, and what writes the delivered/failed truth afterwards.
- Which of the five callers' stamps move from accept-time to delivery-time, and which legitimately
  stay at accept-time.
- The wrap-up email fallback: whether a delivery failure re-opens it.

**Explicitly not this ticket:**

- The delivery-result ingestion itself — that is [[GTC-264]].
- The inbound MO handler — that is [[GTC-229]].
- The bounce-red source in the glance — that is [[GTC-192]] §10.9 / the press, and it is
  [[GTC-264]]'s data that makes it possible.

**Do not touch:** all Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding.
