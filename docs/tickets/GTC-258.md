## The premise is UNCONFIRMED

**Nobody has observed this.** No TNZ response body has been captured, no blacklisted send has
been made, no log has been read. What follows is a conditional derived by tracing code, and
its antecedent is a question for TNZ.

> **If** TNZ signal `Destination is blacklisted` as a **2xx carrying a per-destination error**
> — rather than as a non-2xx — **then** `sendSms` logs `NUDGE_SENT_AUTO` for a message that
> was never delivered.

The consequent is certain: it follows from the code below, and is verifiable by reading it.
The antecedent is not, and cannot be settled from the tree. **Do not treat this ticket as a
confirmed defect, and do not close it by reasoning about how providers usually behave.**

The phrase `Destination is blacklisted` is TNZ's own, from their answers of 2026-08-29
recorded in [[GTC-229]]. That answer establishes *that* subsequent sends fail. It does not say
*how the failure is transported*, and that gap is this ticket.

## What the code does today, at `6944066`

`sendViaTnz` in `src/lib/sms/tnz-client.ts`:

1. `POST`s to the TNZ endpoint and reads the body with `await response.text()`.
2. `if (!response.ok)` → returns `{ success: false, error: 'TNZ HTTP <status>: <body>' }`.
   **This is the only failure branch that inspects the response.**
3. Otherwise, parses the body inside a `try` purely to pull a message id —
   `parsed.MessageID ?? parsed.messageID`. A parse failure is swallowed; the comment states
   the intent: *a 2xx without a parseable body is still a success*.
4. Returns `{ success: true, messageId }`.

**No branch reads anything from a 2xx body except the message id.** The parse type declares
three fields — `MessageID`, `messageID`, and **`Result`** — and `Result` is **never read**.
Whichever field a per-destination status would most plausibly arrive in is already named in
the type and discarded. That is the whole mechanism: HTTP status is the sole success signal.

`sendSms` in `src/lib/sms/send-sms.ts` then branches on `result.success` alone:

- `!result.success` → `throw` → caught → `logInviteEvent` with `SMS_SEND_FAILED`, and the
  function returns `blocked: 'SEND_FAILED'`.
- `result.success` → `logInviteEvent` with **`NUDGE_SENT_AUTO`**, metadata `{ messageId,
  provider, phoneNumber, messageLength, ...metadata }`, and returns `{ success: true }`.

A 2xx-transported rejection takes the second path. Nothing downstream can tell it from a
delivery.

## What follows if the premise holds

Three consequences, each traced to a symbol. All are conditional on the antecedent.

### 1. The inbound attribution index is corrupted

`NUDGE_SENT_AUTO` is not only an audit record. `POST` in
`src/app/api/sms/inbound/route.ts` resolves an inbound reply to a person and event by
querying for the most recent `NUDGE_SENT_AUTO` whose `metadata.phoneNumber` matches the
sender, newest first. **That query is the only mechanism in the codebase for attributing an
inbound message back to a person** — [[GTC-229]] F1 establishes this, and a repo-wide grep
confirms the inbound route is the sole production reader of the enum value (the only other
occurrences are the write in `sendSms`, the explanatory comment atop
`src/lib/sms/decide-by-sender.ts`, and two test files).

A false `NUDGE_SENT_AUTO` is therefore not an inert bad log line. It is a write to the index
that answers *"who is this reply from, and about which event?"* — and it is written **newest
first**, so a false entry outranks every true one before it.

The interaction with [[GTC-229]] is the reason this was split out rather than left as a
footnote: the number that gets blacklisted is, by definition, the number that opted out, and
the sends that fail are precisely the ones whose false success would land at the top of that
index. If the premise holds, the failure mode is concentrated on exactly the population the
inbound handler exists to serve.

### 2. Nudge cadence stamps are consumed

`sendNudge` in `src/lib/sms/nudge-sender.ts` writes `PersonEvent.firstNudgeSentAt` or
`secondNudgeSentAt` **only** on `result.success` — its own comment records why: *a send that
failed leaves no stamp and the next tick retries it.* A false success inverts that guarantee.
The stamp is written, the retry never comes, and `getNudgeStatus` in
`src/app/api/events/[id]/invite-status/route.ts` reports `'first reminder sent'` to the host.

### 3. The maybe's single follow-up is spent

`sendDecideByFollowup` in `src/lib/sms/decide-by-sender.ts` stamps
`Assignment.decideByFollowupSentAt` only on success. A maybe gets exactly one decide-by
follow-up. A false success consumes it with nothing sent.

`sendProxyNudge` in `src/lib/sms/proxy-nudge-sender.ts` and the wrap-up dispatch in
`src/lib/wrap-up.ts` are the other `sendSms` callers and were not traced for this ticket.

## Why no severity, and why no fix

**No severity is assigned.** Severity would encode a judgement about likelihood that nobody
holds. Assign it when the antecedent is answered.

**No fix is proposed here, deliberately.** The correct handling depends entirely on TNZ's
actual response shape:

- whether a blacklisted destination is a non-2xx at all — in which case there is nothing to
  fix and this ticket closes as *not a defect*;
- if it is a 2xx, which field carries the per-destination status, what its values are, and
  whether it is per-destination or per-request (`Destinations` is an array in the request
  payload `sendViaTnz` builds, so a partial-failure shape is possible);
- whether the same shape covers other per-destination outcomes, making this a general
  response-handling question rather than a blacklist-specific one.

Writing a fix before those answers means writing a guess about a wire format, in the one place
where a wrong guess is invisible: a mis-parsed success looks exactly like the current
behaviour. **This is a question for TNZ, not for the tree.** The tree has already been read;
it says what it says above, and reading it again will not settle the antecedent.

## The question for TNZ

Ask alongside the [[GTC-229]] follow-ups, while that conversation is open:

1. When a send is rejected because the destination is on the opt-out/blacklist, what **HTTP
   status** does the send endpoint return?
2. If it is a 2xx, **which field** of the response body carries that outcome, and what are its
   possible values?
3. `Destinations` accepts an array. If one destination in a batch is blacklisted and others
   are not, what does the response look like — is the status per-request or per-destination?
4. Is the same shape used for other per-destination failures (invalid number, unreachable
   handset), or is blacklisting signalled specially?
