### Scope, one line

On events created through the Moment flow the host has **no `PersonEvent` at all**, and the
person the host captures as themselves during Moment 1 is a **separate `Person` row with no
link back to the host `User`**.

⚠ **THE SCOPE LINE IS TOO NARROW — corrected by the Phase 1 audit, 2026-08-29.** See *Scope
correction* below. This is not a Moment-flow bug. It is an event-creation bug that the Moment
flow adds a second half to.

### The evidence

Measured across every event in the development database on 2026-08-29:

| Event | Path | `PersonEvent` for the host Person | `PersonEvent` with `role: HOST` |
|---|---|---|---|
| Henderson Family Christmas 2026 | V1 seed | 1 | 1 |
| Security Test Event (DRAFT / SENT / PAST / SENT-LEGACY) | V1 | 0 | 0 |

| GTC-236 Regenerate Fixture | **Moment flow** | **0** | **0** |

`PersonEvent` rows for the host `Person` **across all events**: **0**.

⚠ **THAT LAST LINE IS WRONG AS WRITTEN — it is 1, and this ticket's own table above says so.**
Re-measured 2026-08-29: `PersonEvent` rows whose `personId` is any `Event.hostId` = **1**
(Sarah Henderson, on the demo seed). What is genuinely 0 is the count for the two *Moment-flow*
host Persons — "Test Host" and "Security Test Host" — across every event. The same error is
copied into a code comment; see *The wrong comment* below.

Concretely, on `GTC-133 Sub-commit (g) Test`:

- `Event.hostId` → `Person { name: "Test Host", email: "nigel@mckorbett.co.nz", userId: <User> }`.
  That Person has no membership row on this event, or on any event.
- The guest list contains `Person { name: "Kate", email: "kate@example.com", userId: null }`,
  captured through Moment 1 as a household primary contact. Nothing in the data connects Kate
  to the host — not `personId`, not `role`, not `userId`.

Note `Event.hostId` is a **`Person`** FK (`host Person @relation("EventHost")` in
`prisma/schema.prisma`), not a `User` FK. The two identities are joined by `Person.userId`,
which is null on every person the Moment flow captures.

### The consequence, beyond auto-assign

Auto-assign is where this was noticed, and it is the least of it. Auto-assign's host exclusion
was hardened by [[GTC-188]] to resolve the host by three identity paths (`personId`,
`role: HOST`, shared `Person.userId`) and is null-safe and tested — but on a Moment-flow event
**all three paths find nothing, because there is no row to find**.

The general statement: **the host appears in their own event as a stranger, and a duplicate of
them sits in the guest list.** Anywhere the system needs to know which of these people is the
host inherits this:

- **Who not to message.** Nudges, the decide-by follow-up and the proxy path all reason over
  `PersonEvent`. The captured duplicate is an ordinary participant and is a live recipient.
- **Who not to chase.** The per-person `nudgeMark` and the household channel picker
  ([[GTC-172]], [[GTC-179]], surfaced by [[GTC-188]]) offer the host to herself as somebody to
  go gentle on.
- **Whose name goes on the invitation.** The from-whom of a send has two candidate rows and no
  rule distinguishing them.
- **Who is excluded from placement and distribution.** Any current or future "not the host"
  filter, including auto-assign's.
- **Headcount and coverage.** The host is counted as a guest by anything that counts
  `PersonEvent` rows.

### Not in scope, and why this is not small

Closing this is a **Moment 1 capture decision**: it requires ruling how a captured person is
identified as the host — whether the flow creates a membership row for the host, whether the
host is captured as a household member and then linked, what happens to events already in this
state, and what the identity of record is when a `Person` and a `User` disagree. It touches
household capture, which is load-bearing and has its own incident history
(`reconcileHouseholdMembers`, [[GTC-159]], [[GTC-172]]).

**It is a bigger piece than the rest of [[GTC-188]] combined.** No fix is proposed here, per the
founder's instruction on filing.

### Founder rulings — the host's identity (Nigel, 2026-08-29)

*Eleven rulings made across three passes on 2026-08-29, each pass answering what the previous
one's checks turned up. Rulings 1-6 chose the shape; **7-9** closed open question 2 after the
audit reported the delete asymmetry and the role/items collision; **10-11** closed open question
1 and settled the phase ordering. They supersede the filing instruction directly above. **Two**
questions remain deliberately NOT ruled — an executor must stop at those, not interpret them.*

**Ruling 1 — Moment 1 opens with the host's own household.** Of the candidates weighed
(A: write a host `PersonEvent` at event creation; B: link the captured `Person` back to the
host `User`; C: recognise the host at read time and store nothing; D: capture the host as a
household member in Moment 1), **D is ruled.**

*Rationale, recorded because it is the reason and not a preference:* it is the only candidate
that makes the system's picture match reality. **The host is at her own party.** A and C leave
her absent from her own guest list — A adds a row that names her without placing her, C finds
nothing to name. B needs a rule for detecting which captured person is the host, and no such
rule exists: the only automatic candidates are name-matching and email-matching, and
email-matching produces the third state recorded below instead of a link.

**Ruling 2 — the host's household is optional.** Moment 1 offers **"I'm hosting alone"** as an
explicit choice. Taking it makes her a **household of one, not absent** — she is still eating.

The distinction is the whole ruling: "no household" and "a household containing only me" are
different facts, and only the second one survives Ruling 3. A host who declines to name anyone
else must still appear in the headcount, hold items, and be excluded from her own ask.

**Ruling 3 — the host counts in the headcount.**

*Consequence, recorded rather than left to be discovered:* **every existing event's plan was
sized one adult short.** `buildPlanGenerationInput` derives `totalAdults` by counting household
members (`src/lib/ai/plan-input.ts`, the "Headcount from households" block). The host is in no
household, so every plan generated to date fed everyone except the person cooking. This is not
a rounding error in a quantity — it is a missing person in the input the whole plan is scaled
from.

**Ruling 4 — the host may hold items.** She holds them **silently**: they appear on her own
plan rather than arriving as an ask.

This is the ruling that makes Ruling 5 non-trivial. "Holds items but is never messaged about
them" is a combination the system has no existing shape for.

**Ruling 5 — the host never receives her OWN ask.** No invitation, no auto-nudge, no proxy
nudge, no decide-by follow-up, no wrap-up thank-you. Her name is **not claimable through the
shared link**.

⚠ **"IN THE GUEST LIST, COUNTED, HOLDING ITEMS, NEVER MESSAGED" DOES NOT EXIST TODAY.** It is a
new concept, and it must be built as one.

The only existing never-message rule is **the child rule** (Moment 4 §10.6,
`src/lib/eligibility/child-exclusion.ts`). It is deliberately narrow and absolute, and
[[GTC-207]] pins it against exactly this kind of borrowing — the same file's own docstring
forbids importing `MESSAGEABLE_PERSON_EVENT` into any assignment path. **It must not be widened
to carry Ruling 5.** A `CHILD`-role host would also be barred from holding items, which
contradicts Ruling 4, and from being a household channel, which contradicts Ruling 6.

Note also that **`PersonRole.HOST` carries no messaging meaning today.**
`MESSAGEABLE_PERSON_EVENT` reads `householdRole` and nothing else. Giving the host a
`role: 'HOST'` row makes her *findable*; it does not make one send path stop. Ruling 5 must
hold across **all fourteen sites with no host exclusion** enumerated below, not four of them.

**Ruling 6 — the host may be her household's contact, and chooses whether those messages
send.** This is **separate from Ruling 5**. Her own ask is suppressed by *what she is*. Her
household's messages are *a setting she controls*.

**Ruling 7 — the host is always the `PRIMARY_CONTACT` of whatever household she is in.**

This closes the delete-eligibility risk **by construction rather than by guard**:
`reconcileHouseholdMembers` computes `existingNonPrimary` as
`members.filter(m => m.householdRole !== 'PRIMARY_CONTACT')` and the delete loop iterates only
that list, so a primary is updated in place and can never be deleted by an ordinary household
edit. No guard is needed, and none should be added.

*Cost, recorded:* **she cannot join an existing household as a `PARTNER`.** If she is in her
partner's household, **she is the primary and the partner is the partner.**

⚠ *Consequence that promotes Ruling 6 — see "What Ruling 7 does to Ruling 6" below.* A
`PRIMARY_CONTACT` is her household's **default proxy channel**, because
`resolveHouseholdChannel` falls back to the primary on a null pick. Ruling 7 therefore makes
Ruling 6's switch default-ON rather than default-off.

**Ruling 8 — the host's `PersonEvent` carries `role: HOST`.** She gets **no `PARTICIPANT`
token** and **no guest-side page**. She is not being invited, so she does not need one.

This resolves open question 2, which is struck below. It does **not** contradict Ruling 4 — see
Ruling 9.

**Ruling 9 — the host holds items by an explicit toggle she controls.** **Off by default.** The
system never assigns her anything: **the existing rule keeping `role: HOST` out of auto-assign's
`PARTICIPANT` pool stays exactly as it is, unchanged.** She opts in and chooses her own items.
Items she holds appear on **her host view**. She gets no guest view.

*Verified against the code, 2026-08-29 — Ruling 9 needs no eligibility change:*
`POST /api/events/[id]/items/[itemId]/assign` has **no role gate at all**, deliberately
([[GTC-207]] keeps role gates out of that route), so a `role: HOST` row is assignable today.
And `/api/h/[token]` already returns every team's items with their named assignee, so **"appear
on her host view" costs nothing to build.** The one real constraint is team membership, not
role — see the phasing.

**Ruling 10 — the host's `PersonEvent` points at `Event.hostId`'s EXISTING `Person`.** Not a new
`Person` row.

*Rationale:* **the flow knows who is signed in, so there is nothing to detect.** This resolves
open question 1, which is struck below.

*Consequences, from the Phase 1 checks:* `wrap-up.ts`'s path-1 filter (`pe.personId !== hostId`)
and `PeopleSection`'s host badge (`person.personId === hostId`) **both start working for free** —
neither needs a line changed. And `ensureEventTokens` issues her `HOST` token against a row that
now has a membership, instead of against a `Person` with none.

⚠ *Does the third state collapse?* **Its duplicate half collapses completely; its wrong-role
half collapses only once her own row exists.** See the check below — it is sequence-dependent,
and it turned up a demotion path that Ruling 7 does not cover.

**Ruling 11 — Ruling 6's switch is BLOCKING, not a later phase.** It **ships in the same phase
as the host's household, or before it. Never after.**

*The reason is the Phase 1 finding, and it stands:* Ruling 7 makes the host her own household's
proxy channel by default (`resolveHouseholdChannel` falls back to `PRIMARY_CONTACT` on a null
pick, and null is where every household starts), `findProxyNudgeCandidates` has **no member-count
gate**, and so a host hosting alone under Ruling 2 would be texted:

> `<Event>: 1 person in your group hasn't confirmed yet. Can you check in with them? <link>`

about herself.

⚠ **RULING 5 DOES NOT CATCH THIS.** That path reads `householdRole` and **never `role`**, so
Ruling 8's `role: HOST` is invisible to it, and it requires no `PARTICIPANT` token for Ruling 8
to withhold. The never-messaged concept and the household switch are two different mechanisms
and neither substitutes for the other.

#### An observation, NOT a ruling

The host now has **three self-directed switches**: whether she has a household (Ruling 2),
whether her household's messages send (Ruling 6), and whether she holds items (Ruling 9). **All
default off.**

Whether they belong together as one control in Moment 1 or three scattered ones is **a design
question for the build, not settled here.** Recorded so the build sees them as a set rather than
discovering them one at a time.

⚠ One caveat on "all default off": Ruling 7 makes the *messages* switch default **on** in its
current mechanism, because a null channel pick resolves to the primary contact. The switch's
default and the ruling's intent disagree, and that gap is Ruling 6's to close.

### Ruling 6, checked before building — is the switch already the picker?

*Asked by the founder as a pre-condition: is "she chooses whether those messages send" already
expressible as the existing household channel picker, where choosing nobody means the household
gets nothing? Reported, not built.*

**Verdict: half of Ruling 6 already exists; the switch does not. Ruling 6 needs new machinery.**

**What already works — the reference half.** She can be pointed at as a household's channel
today, with no change. `Household.contactPersonEventId` is a `PersonEvent` reference and
`validateChannelTarget` (`src/lib/households/channel.ts`) admits any non-`CHILD` row in the same
event. It is cross-household capable by design. A host captured under Ruling 1 is a valid
target the moment her row exists.

**What does not work — "nobody".** *The picker cannot hold that value.* `contactPersonEventId`
has exactly two states, and neither is "nobody":

| Stored | Means | Resolves to |
|---|---|---|
| a `PersonEvent` id | picked | that person |
| `null` | **not picked** | the household's `PRIMARY_CONTACT`, computed at read time |

`resolveHouseholdChannel` falls back to the primary contact on null. That is not incidental —
it is the property [[GTC-172]] deliberately bought, and the schema docstring records why:
*"NULL means 'not picked' and resolves to the household's PRIMARY_CONTACT at read time. That is
why this ships with no data backfill: the default is computed, not stored."* **Redefining null
as "nobody" would silently mute every household on every existing event** and would destroy the
no-backfill property. The write paths agree: the pre-flight channel PATCH and the households
POST/PUT accept `string | null` only, and `validateChannelTarget` requires a target that exists.

**What comes closest, and why it is not the answer.** Two existing controls *do* suppress the
proxy path, both from [[GTC-179]]:

- `PersonEvent.nudgeMark = DONT_CHASE` on the channel — `findProxyNudgeCandidates` skips the
  household (its Ruling 3).
- `Event.nudgePace = OFF` — suppresses every household on the event (its Ruling 12).

So a host who is her own household's channel could mute it today by marking **herself**
`DONT_CHASE`. That is a coincidence of mechanism, not the control Ruling 6 describes:
`nudgeMark` is *"a hosting judgement about that person"* — an opinion about someone else's
temperament — and it is per-person, so it fires across **every** household she is channel for,
not the one. Overloading it would make the pre-flight offer the host herself under "go gentle
on", which is the precise absurdity this ticket already lists as a consequence.

**Also note the scope of what the picker gates.** Today the channel governs the **proxy nudge
path only** (`findProxyNudgeCandidates`). The ask itself is composed per-recipient, not per
household, and its dispatch is [[GTC-189]]'s and unbuilt. So "her household's messages" is a
smaller surface today than the phrase implies, and will grow when GTC-189 lands.

**Not built, and no shape proposed** — which of the two obvious shapes (a third channel state,
or a household-level boolean) is correct is a decision, not an implementation detail, and it is
not among the eleven rulings.

#### What Ruling 7 does to Ruling 6 — it promotes it to a blocking dependency

*Re-checked 2026-08-29 after Ruling 7. This changes the phasing, so it is recorded here rather
than left in the plan.*

Ruling 7 makes the host **always a `PRIMARY_CONTACT`**. `resolveHouseholdChannel` returns the
primary whenever `contactPersonEventId` is null, and null is the state every household starts
in. **Therefore the host is her own household's proxy channel by default, on every event, with
no pick made.** Ruling 6's switch is not later polish — it is the only thing standing between
Ruling 7 and a live send path.

Worse under Ruling 2. `findProxyNudgeCandidates` has **no member-count gate**: a household of
one is an eligible household, and `memberCount` is simply `1`. The template
(`getProxyHouseholdReminderMessage`) then produces, to a host hosting alone:

> `<Event>: 1 person in your group hasn't confirmed yet. Can you check in with them? <link>`

**She is texted about herself.** Ruling 5 does not stop it — that path reads `householdRole`,
never `role`, so Ruling 8's `role: HOST` is invisible to it and it needs no `PARTICIPANT` token.

Two ways out, neither ruled: Ruling 6's switch defaulting to off for the host, or a member-count
gate on the proxy finder. **A member-count gate is the larger change** — it alters proxy
behaviour for ordinary one-person households too, which is a Moment 4 §10.7 question and not
this ticket's.

⚠ **RULING 11 SETTLES THE PHASING OF THIS, NOT ITS SHAPE.** The switch ships with the household
or before it, never after. *Which* of the two ways out is taken is still undecided and is phase
2's to settle.

### Ruling 10, checked — does the third state collapse?

*Asked by the founder: confirm the reading or correct it. **Confirmed in the half that matters,
corrected in one place, and the check turned up a third thing.***

**Confirmed — the duplicate half collapses completely and unconditionally.** Ruling 10 removes
the possibility of a second `Person` row for the host, so there is never a duplicate to detect,
merge or delete. `Person.email` is `@unique` and the email lookup in `createMember` finds her
existing `Person`, which under Ruling 10 is by definition the right one. The founder's reading
is correct.

**Corrected — the wrong-role half collapses only once her own row exists. It is
sequence-dependent.** `createMember` (households POST) does the email lookup, then:

```
const existing = await prisma.personEvent.findUnique({ where: { personId_eventId: {...} } });
if (existing) {
  if (!existing.householdId) { /* update household fields */ }
  return existing;                    // ← role is NEVER touched here
}
return prisma.personEvent.create({ data: { ..., role: 'PARTICIPANT', ... } });
```

| Sequence | Result |
|---|---|
| Her own household row **already exists** (Rulings 1/2/7/10 have run) | `existing` is found and `existing.householdId` is set, so the branch is a **complete no-op**. `role: HOST` and `PRIMARY_CONTACT` both survive. **Fully collapsed, safely.** |
| Her own row **does not exist yet** — she reaches another household first, or the event was backfilled | `existing` is null ⇒ the `create` runs ⇒ **`role: 'PARTICIPANT'`**. The third state **survives**, now merely against the correct `Person`. |

**So Ruling 1's "Moment 1 *opens* with the host's own household" must be read as a SEQUENCE
GUARANTEE, not just a screen order.** Her row must exist before any other household can be
entered. That is a phase-2 requirement, and it is the whole difference between the two rows
above.

⚠ **And a third thing, which CORRECTS what the previous pass recorded.** That pass said Ruling 7
closes the delete risk by construction and *"no guard is needed and none should be written."*
**That is right about deletion and wrong about demotion, and demotion re-opens deletion.**

`reconcileMembers.createNewMember` — the PUT/edit path, not the POST path above — has a
*different* condition:

```
if (!existing.householdId || existing.householdId === household.id) {
  await prisma.personEvent.update({
    where: { id: existing.id },
    data: { householdId: household.id, householdRole: role, isYoungPerson },   // ← householdRole IS written
  });
}
```

Editing **her own household** makes `existing.householdId === household.id` true. So if her email
appears in that payload's `partner` / `helpers` / `guests` arrays — a form bug, a stale client, or
her typing it into a guest row — **her `householdRole` is overwritten to `PARTNER` / `GUEST` /
`CHILD`.** Her `role: HOST` survives (nothing writes it there), but three things follow:

1. She is now in `existingNonPrimary`, so **the next edit that omits her deletes her row**,
   cascading her `NudgeLog` rows. Ruling 7's protection is gone.
2. The household now has **no `PRIMARY_CONTACT`**, and the PUT route resolves
   `primaryMember = household.members.find(m => m.householdRole === 'PRIMARY_CONTACT')` and
   **400s when it is absent** — the household becomes **uneditable**.
3. `resolveHouseholdChannel` returns null for it, so the proxy finder skips it with
   `'No primary contact'`.

**Therefore one guard IS needed in phase 2, and it guards demotion, not deletion:** the host's
`householdRole` must not be writable to anything but `PRIMARY_CONTACT` (Ruling 7). The POST path
needs no such guard — its condition is `!existing.householdId` alone, so it is already a no-op
for her.

*Related, and worth surfacing rather than leaving as a silent behaviour:* Ruling 7 says she
cannot join an existing household as a `PARTNER`. On the **POST** path that is already enforced
by accident — the attempt is a **silent no-op**, so she would appear to have been added and
would not have been. Whether that should be an error message is a build decision, recorded
below.

### Recorded from the Phase 1 audit (2026-08-29)

*Four findings the ticket did not have when it was filed. Recorded here because each one
changes what closing it means.*

#### Scope correction — this is not a Moment-flow bug

**No event created through `POST /api/events` has ever had a host `PersonEvent`, on either
path.** The split is **paid-creation versus clone-or-seed**, not V1 versus V2.

| Path | Host `PersonEvent` after creation |
|---|---|
| `POST /api/events` — the only production path, V1 and V2 alike | **None.** The transaction writes `User`, `Person`, `Event.hostId` and `EventRole{HOST}`. It makes no `PersonEvent` write at all. |
| `POST /api/templates/[id]/clone` | Yes — `role: 'HOST'`, parked on the first team. |
| `prisma/seed.ts` | Yes — Sarah Henderson is listed with `role: 'HOST'` in the seed data. |

This ticket's own evidence table already showed it: the four Security Test Events are **V1** and
read `0 / 0`. The title and scope line name the Moment flow because that is where it was
noticed. The Moment flow's actual contribution is only the **second** half of the scope line —
the captured duplicate.

*Corollary for Ruling 1:* fixing capture in Moment 1 does not by itself give a V1 event a host
row. Whether V1 gets one is inside open question 3 (backfill) and open question 2 (role).

#### The third state — the host who types her own email

⚠ **PARTLY CLOSED by Ruling 10 — see *Ruling 10, checked* above.** The duplicate half collapses
unconditionally; the wrong-role half collapses only once her own household row exists, which is
why phase 2 carries a sequence guarantee. The description below is the pre-ruling behaviour and
is kept because the backfill decision still has to reason about events already in this state.

The scope line describes two states. There is a **third**, and which one a real host lands in
depends on whether she retypes her account email exactly.

`Person.email` is `@unique`, and `createMember` in the households route does
`findUnique({ where: { email } })` before creating. So if the host enters **her own account
email** as a household primary contact, **no duplicate is created** — her existing host `Person`
is reused and given a `PersonEvent` with `role: 'PARTICIPANT'` and
`householdRole: 'PRIMARY_CONTACT'`.

The result is one person, correctly identified by identity path 1, **wrongly roled**: she holds
both a `HOST` and a `PARTICIPANT` token, is a live auto-nudge recipient, is her household's
default proxy channel, is thanked at wrap-up, and **her name is claimable through the shared
link** (the join page lists `people where role: 'PARTICIPANT'`). Ruling 5 forbids all six.

This state is *worse* than the duplicate in one respect: because path 1 matches, the pre-flight
sets `hostIdentityResolved: true` and **the amber banner that currently warns her disappears.**

#### Zero duplicates exist today — a condition that lapses

*Recorded in [[GTC-178]] Ruling 6's style, because it has the same property: it is true now, it
is load-bearing on the backfill decision, and it can lapse.*

**Verdict: the condition HOLDS. No event in the database has two host records.** Measured
2026-08-29 against `gather_dev`:

| Check | Count |
|---|---|
| Events | 9 |
| Events whose host `Person` has **no** `PersonEvent` | **8** of 9 |
| `PersonEvent` rows whose `personId` is any `Event.hostId` | **1** (Sarah Henderson, demo seed) |
| Guests sharing the host's **name** on the same event | 0 |
| Guests sharing the host's **email** on the same event | 0 |

### Build decisions recorded, NOT made

*Four constraints the checks surfaced. Each is a real choice with more than one defensible
answer, and none is settled by the eleven rulings. Recorded so the build meets them deliberately
rather than discovering them.*

1. **Item choice is bounded by TEAM membership, not role.**
   `POST /api/events/[id]/items/[itemId]/assign` rejects with 400 when
   `item.kind === 'ITEM' && personEvent.teamId !== item.teamId`, and **`PersonEvent.teamId` is
   singular** — one team per person. So Ruling 9's *"she chooses her own items"* is limited to
   items on the one team she is on. Free choice across the plan needs **either a `teamId` write
   alongside the pick, or an exemption from the same-team rule**. *(Task rows — `kind: 'TASK'` —

   question. Three numbers, three answers required.
3. **A backfill must REVOKE stale `PARTICIPANT` tokens, not merely re-role.**

   named as one.
4. **Whether a blocked self-add should say so.** Ruling 7 forbids the host joining an existing
   household as a `PARTNER`; on the POST path the attempt is currently a **silent no-op**, so she
   would appear to have been added and would not have been. Error, or silence, is a UX call.

**The pre-flight recipient list now offers the host to herself under "go gentle on".** Before
phase 2 there was no row to offer. This is cosmetic, involves no send, and is one of phase 3's
four Ruling 5 sites. The blocking consequence — the proxy nudge — is closed by Ruling 6's
switch, which is what Ruling 11 required.

**Existing events are unchanged.** No backfill, and none attempted: phase 5 is gated on open
question 3, and build decision 3 stands — a backfill must **revoke** stale `PARTICIPANT` tokens,
not merely re-role. The route refuses rather than half-doing it: a host `PersonEvent` that
already exists with a non-`HOST` role is a 409 naming phase 5.

**Build decision 4 is unresolved and unchanged.** A blocked self-add is still silent, though
not invisibly so: the route returns the household as saved and the client re-renders from that
response, so a guest row she typed with her own email disappears on save.

**Open questions 3 and 4 remain open.** Nothing here decides the backfill, and the three-path
resolution in `pre-flight/message/route.ts` now resolves on new events but has been neither
extracted nor deleted — which is open question 4, and by the phasing not this ticket's.
