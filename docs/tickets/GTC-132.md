# GTC-132 — Reconcile config keys and backfill missing matrix cells with templates — CLOSED

**Status:** Complete | **Branch:** claude/reconcile-config-backfill-r7roZ | **Commit:** [hash to be filled at commit time]

---

### What was found

1. **Key naming mismatch.** `GuidedPlanBuilder.tsx` defined `ALL_CATEGORY_KEYS` and `FALLBACK_LABELS` using the short keys `sides`, `entree`, `snacks`. The JSON config used the longer keys `sides_salads`, `entree_starters`, `table_snacks`. The two ends never matched, so the JSON's authored content for those three categories was unreachable via the component.

2. **Matrix gaps.** Counted (occasion × category) presence across 10 occasions × 14 canonical categories = 140 cells. **86 cells were populated, 54 were missing.** Gaps are spread across both food and non-food categories — the audit in the ticket description listed only the 5 most-affected categories (furniture_equipment, decorations, activities_entertainment, breakfast_brunch, other), but the executor's full audit also surfaced gaps in `entree_starters` (5), `sides_salads` (6), `drinks_alcoholic` (2), `table_snacks` (2), and `cleanup` (3). Acceptance criterion #5 ("All 140 cells populated") therefore required extending the same template-backfill approach to food categories. Decision documented and applied.

3. **Byte-identical templates already exist** for 7 of the 9 categories with gaps:
   - `entree_starters` (5 instances, 1 unique hash → already a single canonical template)
   - `drinks_alcoholic` (8 instances, 1 unique)
   - `drinks_non_alcoholic` (10 instances, 1 unique — already universal)
   - `table_snacks` (8 instances, 1 unique)
   - `cleanup` (7 instances, 1 unique)
   - `furniture_equipment` (3 instances, 1 unique)
   - `decorations` (5 instances, 1 unique)
   - `breakfast_brunch` (1 instance — trivially canonical)

   Two categories had genuinely varied content across their existing instances and required a template-choice judgment: `sides_salads` (4 unique versions) and `activities_entertainment` (4 unique versions).

4. **`defaultCategories`** is per-occasion (a string array on each `OccasionConfig`). It is the right shape to honour the "universal *availability*, occasion-tuned defaults" interpretation in the ticket. No schema change was needed; defaults left untouched.

### What was changed

**Phase 1 — Key rename (`src/components/plan/GuidedPlanBuilder.tsx`)**

- `ALL_CATEGORY_KEYS`: `'entree' → 'entree_starters'`, `'sides' → 'sides_salads'`, `'snacks' → 'table_snacks'`.
- `FALLBACK_LABELS`: same three keys updated; display values unchanged.
- No other files touched. `src/lib/ai/generate.ts` does not reference these keys directly (it operates on opaque `categoryKey` strings via the `categoryLabels` map). `src/lib/ai/prompts.ts` and `src/components/plan/AcknowledgeModal.tsx` mention the words "sides" / "entree" / "snacks" only inside English prose (placeholders, prompt text), not as category-key string literals. Verified with `grep -n '\\bsides\\b\\|\\bentree\\b\\|\\bsnacks\\b' src/ --include='*.ts' --include='*.tsx'`.

**Phase 4 — Matrix backfill (`src/lib/ai/plan-option-tree-config.json`)**

- 54 missing (occasion × category) cells populated by injecting deep clones of the canonical templates listed above.
- `defaultCategories` arrays: untouched on every occasion (verified byte-identical to git HEAD).
- Existing `categories` entries: untouched on every occasion (verified byte-identical to git HEAD).
- File re-serialized via `JSON.stringify(_, null, 2)` with non-ASCII characters re-encoded as `\uXXXX` to match the original file's escape style. A small amount of unavoidable diff churn comes from a handful of inline string-arrays in the original being expanded to one-element-per-line by the canonical serializer (~24 lines pre-existing; semantically identical).

### Known limitations

1. The `other` template uses the same shape as the `GENERIC_LEVEL` in `GuidedPlanBuilder.tsx` (single level, no options, free-text only). It will render via the existing `<OptionTree>` plumbing without any code change required. If GTC-133 integration discovers a render-time assumption that "other" should behave differently, that's a GTC-133 fix.

2. The chosen `sides_salads` and `activities_entertainment` templates are executor judgment calls. The 4 authored `sides_salads` versions (christmas, bbq_casual, wedding_reception, easter) and 4 authored `activities_entertainment` versions (birthday_kids, baby_shower, engagement_party, anniversary) remain unchanged — only the freshly-backfilled occasions use the chosen template.

3. The "non-food categories" framing in the original ticket Phase 3 was incomplete — food-category gaps also exist (entree_starters, sides_salads, drinks_alcoholic, table_snacks, cleanup). The executor extended the same backfill approach to those categories because acceptance criterion #5 ("All 140 cells populated") explicitly requires it. All food-category template choices are documented above. If a different interpretation was intended ("food gaps stay missing"), reverse via the per-category lists in the matrix.

4. `npm run build` cannot be fully executed in this environment because it runs `prisma migrate deploy` which requires a live Postgres database. The compile half of the pipeline (`next build` → "Compiled successfully in 9.0s") and `npx tsc --noEmit` (exit 0) both pass cleanly, which gives equivalent assurance that no type or compile errors were introduced.

5. UI was not exercised in a browser. Per the ticket's "do not touch the `<OptionTree>` component" constraint and "GuidedPlanBuilder regression check via HostDescriptionModal" line, the regression check here is structural: `ALL_CATEGORY_KEYS` (post-rename) is verified as a perfect superset of every occasion's `categories` keys, and every occasion's `categories` map is verified as a perfect superset of the rename targets. This guarantees no key-lookup failures at render time.
