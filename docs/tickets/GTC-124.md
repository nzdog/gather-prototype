# [[GTC-124]] — Moment 2 Step 2: The editable plan — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** 6b71284

### What was found

- `Moment2Step2Skeleton.tsx` ([[GTC-121]]) already streams the generated plan in category-by-category, then shows a "Plan looks good →" button. The button refreshes event data and exits. The plan was read-only.
- The finalize-plan endpoint (`POST /api/events/[id]/finalize-plan`) persists the generated plan to the Team/Item models using `Team.name` as the category label (e.g. "Mains"), `Item.quantityAmount`, `Item.quantityUnit='CUSTOM'`, `Item.quantityUnitCustom`, `Item.quantityText` (serves), and `Item.notes`. Team emoji is derived from the team name, not stored.
- Existing CRUD endpoints cover update, delete, and create for items and teams — reused as-is, with two minor additions (see below).
- `Team.displayOrder` exists and is set by finalize-plan; `Item` has no `displayOrder` column, so item ordering cannot be persisted.
- `MomentArc.tsx` and `useToast()` are already available for re-use.

### What was changed

**New component:**
- `src/components/plan/Moment2PlanView.tsx` — editable plan view. Collapsible category sections with emoji + name + item count header. Each item row shows name, serving size, and a tap-to-edit quantity button plus reorder arrows (up/down) revealed on hover. Tapping the item name opens an inline edit form (name, quantity + unit, serves, notes) with Save / Cancel / Remove. Per-category "+ Add item" opens an inline add form. "+ Add category" button at the bottom opens a single-input form. Sticky footer has "← Back to event setup" and "Plan looks good →". Unit selector has 17 common units plus a Custom… option. Empty categories show "No items yet."

**Modified components:**
- `src/components/plan/Moment2Step2Skeleton.tsx` — added optional `onReady?: () => void` prop that fires once the staggered reveal finishes. No change to streaming behaviour.
- `src/app/plan/[eventId]/page.tsx` — added `showMoment2PlanView` and `moment2PlanCategories` state; Moment2PlanView render block with handlers that call existing CRUD endpoints; helper `mapTeamsAndItemsToPlanCategories` to turn `GET /teams` + `GET /items` into `PlanCategory[]` with IDs; helper `emojiForCategoryName` to map known category names to emojis (falls back to 📋). The skeleton's `onReady` triggers the load-and-transition flow; skeleton's existing `onApprove` remains as a fallback.

**Endpoint tweaks (minimal, back-compat):**
- `PATCH /api/events/[id]/items/[itemId]` — now accepts `quantityUnitCustom`; added to the substantive-fields check for GENERATED → HOST_EDITED promotion.
- `POST /api/events/[id]/teams/[teamId]/items` — now accepts `quantityUnitCustom` and `quantityText` (previously dropped silently).

### How the skeleton-to-plan-view transition works

1. Moment 2 Step 1 modal's "Generate plan" sets `showMoment2Step2Skeleton=true`, calls `POST /finalize-plan`, and sets `moment2Plan`.
2. Skeleton streams the plan categories in (unchanged).
3. When streaming completes, skeleton fires `onReady`.
4. Parent `onReady` handler calls `loadMoment2PlanCategories()` which fetches `/teams` and `/items` in parallel and maps them to `PlanCategory[]` with database IDs and an emoji derived from each team name.
5. Parent sets `showMoment2Step2Skeleton=false`, `showMoment2PlanView=true`.
6. Moment2PlanView renders; edits go straight to existing CRUD endpoints; local state is patched optimistically for snappy UX.
7. "Plan looks good →" in plan view runs the existing approve path (loadEvent/loadTeams/loadItems/loadConflicts, `toast.success('Plan approved.')`, return to main plan view).
8. "← Back to event setup" returns to `showMoment2Step1`; database edits are preserved.

### How existing CRUD endpoints are reused

| Plan view action | Existing endpoint |
|------------------|-------------------|
| onUpdateItem     | `PATCH /api/events/[id]/items/[itemId]` (reused; extended to accept `quantityUnitCustom`) |
| onRemoveItem     | `DELETE /api/events/[id]/items/[itemId]` (reused unchanged) |
| onAddItem        | `POST /api/events/[id]/teams/[teamId]/items` (reused; extended to accept `quantityUnitCustom` and `quantityText`) |
| onAddCategory    | `POST /api/events/[id]/teams` (reused; coordinator defaults to `event.hostId`, matching existing `handleAddTeam`) |
| onApprove        | existing `loadEvent/loadTeams/loadItems/loadConflicts` flow |
| onBack           | existing `setShowMoment2Step1(true)` |
| onReorderItem    | UI-only — `Item.displayOrder` column does not exist; noted under limitations |

### Known limitations

- **Item reordering is UI-only.** `Item` has no `displayOrder` column and the ticket flagged "no schema changes", so up/down reorder mutates local state only — the order resets on reload. Up/down arrows appear on hover/focus of each item row; the first item's up arrow and the last item's down arrow are disabled.
- **Toast confirmations use the shared 4-second duration.** The ticket specified "fade after 2 seconds"; `ToastContext` is global with a 4s constant. Not changing it to avoid affecting other callers.
- **Drag-and-drop was intentionally swapped for up/down arrows.** The ticket explicitly permitted this fallback ("functional reordering matters more than the specific interaction pattern").
- **Custom category emojis.** User-added categories fall back to 📋 since the schema has no emoji column.
- **Quantity unit mapping on display.** Enum units (`KG`, `G`, `L`, `ML`, `COUNT`, `PACKS`, `TRAYS`, `SERVINGS`) are mapped to display strings (`kg`, `g`, …, `pieces`, …). When the user saves, the unit is written as `quantityUnit='CUSTOM'` + `quantityUnitCustom=<string>` to preserve the raw text.
