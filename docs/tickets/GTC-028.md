Evidence (Executor-Completed)

Root cause confirmed
The "Next" button was `type="submit"`, which triggered `handleSubmit`. That function made a
PATCH API call to save the event before advancing the step. Two failure modes converge:
(1) if any required field (`name`, `startDate`, `endDate`) is empty, HTML5 form validation
silently blocks submission — especially in `overflow-y-auto` scroll containers where browser
validation tooltips cannot scroll into view; (2) even with populated fields, any PATCH failure
leaves the modal on Step 1 with no visible error. The acceptance criteria explicitly requires
Next to work "with valid or empty fields", confirming the fix must not depend on form validation
passing or an API call succeeding. The workaround (clicking the Step 2 tab directly) worked
because those buttons are `type="button"` and call `setStep` directly, bypassing the form submit.

Files changed
- `src/components/plan/EditEventModal.tsx` — Actions section refactored: when `stepLabel && step < 3`, renders a `type="button"` with `onClick={() => setStep(step + 1)}` (no form validation, no API call). "Save Changes" remains `type="submit"`. `handleSubmit` simplified to always `onSave(); onClose()`.
- `tests/setup-modal-next-button-test.ts` — new 14-assertion regression test covering Next button display logic across all step/mode combinations and step advancement.
- `package.json` — added `test:setup-modal-next-button` script.
