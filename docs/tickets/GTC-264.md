## Why this exists

TNZ's answer, quoted in full in [[GTC-258]]:

> *"you should be working from delivery results and not assuming the API accepting a message means
> successful delivery."*

A send returns **200 and the message is ACCEPTED**, including to a blacklisted number. The real
outcome arrives afterwards through **status reporting** — a status GET endpoint or a status webhook
— as `Status=Failed` with a `Result` such as `"Destination is blacklisted"`. Status webhooks are
**distributed per destination**, so there is no batch ambiguity to unpick.

**Gather consumes none of it.** Verified at `5df28ba` and recorded in [[GTC-258]]: no route, no
poller, no schema field, no glance state reads a delivery result. The tree has never had this
signal. Acceptance is the only thing it has ever known, and every stamp, count and colour
downstream is built on it.

This ticket builds the missing channel. **It does not fix the things that are wrong because the
channel is missing** — those are named below as consumers, and each is owned elsewhere.

⚠ **THE SIBLING ON THE EMAIL SIDE IS [[GTC-265]]** (filed 2026-09-01). Together the two are one
sentence — *Gather never checks what actually happened, provider by provider* — but they are not the
same bug and must not be merged. This ticket builds a channel that **does not exist**: TNZ's
delivery results have never reached the tree. GTC-265 reads a value **already sitting in a
variable**: Resend returns its error rather than throwing, and every one of the four call sites
discards it, so a failed email reports success, logs `NUDGE_SENT_HOST`, and starts a cooldown that
then blocks the retry. One is work; the other is an omission. That is why this is a feature at
`high` and that is a bug at `high`.

## Scope

**Build: ingest TNZ delivery results, per destination, and make delivery state readable.**

That is the whole of it. Concretely, the ticket must deliver:

1. **A way in.** Whichever of TNZ's two mechanisms the doc supports and the deployment can use —
   the status webhook, the status GET endpoint, or both. Answer 3 says webhooks are distributed
   per destination; whether the GET is per-message or per-batch is unread.
2. **Authentication on it**, if it is a webhook. See *The auth shape* below — this is not left to
   the executor's taste.
3. **Somewhere to put it.** Delivery state, per sent message, correlated back to the send. **This
   carries schema** — see *Stop Condition 7* below; it fires, and it is expected to.
4. **A read path.** Delivery state becomes the truth its consumers read, in place of the accept
   signal they read today.

**Correlation key — CONFIRMED BY DOCUMENTATION 2026-09-12.** `sendViaTnz` in
`src/lib/sms/tnz-client.ts` already extracts TNZ's `MessageID`, under a comment naming the
reason — *"TNZ returns a JSON body containing a `MessageID` for delivery tracking."* `sendSms`
in `src/lib/sms/send-sms.ts` writes it into `InviteEvent.metadata` as `messageId`. **A repo-wide
grep at `d1577b7` finds nothing that reads it back.**

The documentation settles that this is the right key. On the send side, `MessageID` is an
optional advanced parameter: *"A Message Identifier helps you keep track of each message
(maximum 40 characters, alphanumeric). Use a unique MessageID for each request. If you leave
this field blank, the API will generate a 36-character UUID (v4) for you and include it in the
response body."* `sendViaTnz` supplies none, so TNZ generate one. It is then **echoed back in
both the delivery-status webhook and the SMS-reply webhook** — *"MessageID parameter supplied
when sending your original API call. If you did not supply one, the API generated one for you."*

So the handle exists, is captured on every send, is the documented join key for this ticket
**and** for [[GTC-288]]'s inbound attribution, and has never been read. Whether the metadata
field is the right place to join from or whether the correlation belongs on a proper column is
a design question this ticket answers — but the key itself is already being written.

**➡ The full treatment of `MessageID` is in [[GTC-288]], under *The join key Gather has been
capturing and never reading*.** Read it before designing the correlation here, because the
two tickets join on the same field and **the design this ticket picks is the one [[GTC-288]]
inherits.** If the correlation moves off `InviteEvent.metadata` onto a column, it moves for
both. Three points there bear directly on this ticket:

- The value is written on every TNZ send and read nowhere — [[GTC-258]] calls that *"not a
  second defect; it is the missing half of this one"*, and it is in fact the missing half of
  **three**: this ticket's correlation key, [[GTC-258]]'s correction signal, and
  [[GTC-288]]'s attribution key are the same field.
- It resolves the cross-host ambiguity (H2) and does **nothing** for cross-customer
  interception (H1). Do not let the finding be repeated anywhere as "attribution is solved".
- [[GTC-229]] F1 named the exact condition that would change its answer completely, and this
  is that condition arriving.

⚠ **One gap in the join, and it is this ticket's to handle rather than fix.** `sendViaTnz`
treats a 2xx with an unparseable body as a success with `messageId` left `undefined` — its own
comment says *"a 2xx without a parseable body is still a success"*. Those sends store no join
key, so a delivery result for one cannot be correlated. **Do not fix the send path here**; that
is [[GTC-258]]'s. Handle the unmatched report without throwing, as the acceptance criteria
already require.

⚠ **Supplying our own `MessageID` is NOT this ticket's, and probably nobody's.** The 40-char
alphanumeric limit would let Gather encode its own reference, but TNZ's generated UUID is
already captured and works as a key. Changing what `sendViaTnz` sends is a send-path change.
Named here only so it is not discovered and adopted mid-build.

**Not in scope — the consumers.** Building the channel is not the same as rewiring what drinks
from it. Each consumer is named below with its owner. Wiring any of them here is scope expansion
(Stop Condition 5).

**⚠ NECESSARY, NOT SUFFICIENT — recorded 2026-09-12.** This ticket makes §7's bounce rule

**First, §7's bounce rule is not SMS-only.** §6's ground truth is Kate's Christmas *email*,

no email-bounce ingest ticket** — verified across `docs/tickets/` on 2026-09-12. **Filed as

**Second, §7 needs a taxonomy this ticket cannot supply without the trial.** §7's reasoning
is that *"a bounce is not a silence — it's a dead channel; nudging it sends more messages
into the same void"*, and its door offers *"let the system try again, or take it herself —
ring him, ask his mum, fix the number"*.

**`Destination is blacklisted` is not a dead channel.** It is a live number whose owner
opted out. Colouring it red-on-arrival would be wrong, and every option behind §7's bounce
door is the wrong option for an opt-out — "try again" and "fix the number" both misread what
happened. `Result` values must therefore partition into at least three buckets:

- **dead channel** — §7's bounce, red on arrival;
- **opted out** — opt-out state, and explicitly *not* a §7 bounce;
- **transient** — retryable, and not red at all.

**⚠ AMENDED 2026-09-12 — THE VOCABULARY IS DOCUMENTED, AND THREE BUCKETS ARE NOT ENOUGH.
THERE IS A FOURTH.**

The text above was written believing only one `Result` value had been seen. Phase 0 found
all of them: twenty-one values, with explanations and per-value notification channels, at
`https://help.tnz.co.nz/help/sms-delivery-result-codes`, saved as
`docs/05_ops/tnz-sms-delivery-result-codes-2026-09-12.html`. The full partition is in
`docs/05_ops/tnz-delivery-status-contract-2026-09-12.md`. **It remains [[GTC-192]]'s to
rule; it is proposed, not settled.**

**The fourth bucket is our-fault-not-the-guest's, and it is SEVEN of the twenty-one:**
`Rejected-Duplicate`, `Rejected-Country Blocked-Account Policy`,
`Rejected-Invalid Sender ID`, `Rejected-Message Content Issue`, `LinkNotPermitted`,
`No Permit Record`, `CreditHold`.

**Why it needs its own bucket.** §7's bounce door offers *"let the system try again, or take
it herself — ring him, ask his mum, fix the number"*. **Every one of those seven makes every
one of those the wrong instruction. Nothing about the guest is wrong.** The number is fine,
the guest is reachable, and the fault is ours or TNZ's — a duplicate inside sixty seconds, a
sender id the carrier rejected, a link not on a phishing whitelist, an account out of
credit. Sending Kate to ring him or fix the number for any of them is worse than silence,
because it spends her attention on a problem she cannot see and cannot fix.

**And a fifth case that is not a bucket but cannot be assigned.** `Undelivered` — *"the
carrier responded advising the message failed to send (no defined error reason)"*. It could
be dead channel or transient and nothing in the documentation decides it. **That one still
waits on real traffic**, so the original restraint survives in the one place it must:
**do not model a boolean over `Undelivered`.**

**What the original instruction was right about, and what changes.** *"Do not model a
boolean over a vocabulary you have not seen"* was correct and is now satisfiable — the
vocabulary is documented. But **a documented vocabulary is still not an observed one**, so
[[GTC-192]] must treat the partition as a proposal to be confirmed by the trial, not as a
settled taxonomy. **And it must not colour anything until it has ruled the fourth bucket**,
because a "bounce red" that fires on `CreditHold` tells Kate that a guest is unreachable
when the truth is that Gather has run out of credit.

## The auth shape — OWNED HERE as of 2026-09-12

**Ruled 2026-09-12: this ticket owns the shared-secret verification and its environment
variables. [[GTC-229]] and [[GTC-288]] consume them.**

Both this endpoint and the MO endpoint authenticate against the same TNZ dashboard
configuration — Users > API User > API > Reporting. This ticket lands first, so it builds the
credential handling once and the MO side consumes it rather than building a second path.

**That closes two open questions together.** *Unknowns* 2 below asked whether the MO secret
and the delivery-receipt secret are the same credential; [[GTC-229]] F2 asked whether the
body `APIKey` and the header `Authorization` are one secret in two places or two secrets.
**Both are answered by the example values**, in TNZ's 2026-08-18 answer and confirmed by the
MO documentation read on 2026-09-12: `X-Sender` and body `Sender` carry the same value;
`Authorization` and body `APIKey` carry the same value. One identity plus one secret, echoed
in two places, from one configuration screen.

⚠ **Confirm it at the trial rather than assuming it forever.** The two callbacks being
configured on the same screen is strong evidence they share a credential, but TNZ never said
so in prose. If the trial shows two credentials, this is a configuration change, not a
redesign — provided the credential is not hard-wired to one endpoint.

**The deliverable is therefore:** the env vars, their entry in `.env.example` and in the
Environment Variables table in `GATHER-BUILD-CONSTANTS.md` (which today lists
`TNZ_AUTH_TOKEN` and no callback secret), and a verification path both endpoints can call.

TNZ's inbound authentication scheme, as given on 2026-08-18:

> Headers `X-Timestamp`, `X-Sender`, `Authorization`, plus `Sender` and `APIKey` repeated in the
> JSON body. Configured in the TNZ dashboard under **Users > API User > API > Reporting**.

**Two warnings carry over, and both are binding.**

**⚠ AMENDED 2026-09-12 BY FOUNDER RULING — "the delivery-receipt contract is NOT the MO
contract" WAS WRONG, AND THE INSTRUCTION IS REWRITTEN.**

The text here previously read: *"[[GTC-229]] answer 3 states this explicitly: the MO webhook
documented at `#receive-webhook` is 'distinct from the delivery-receipt callback format — do
not assume one shape covers both.'"* Phase 0 read the documentation and it is one shape.
Source: `docs/05_ops/tnz-delivery-status-contract-2026-09-12.md`, *Finding 1*, against the
saved artefact `docs/05_ops/tnz-restapi-v2.04-docs-2026-09-12.html`.

**There is ONE webhook envelope.** Nineteen fields, same names, same order, same
authentication headers, discriminated by `Type` — `SMS` for a delivery status report,
`SMSReply` for a reply, `SMSInbound` for an unsolicited inbound. `Message` is present only
on the latter two; `ReceivedID` is documented as *"Always blank for Status webhooks"*. And
they are **one subscription**: *"If you are set up to receive Status webhooks, you will also
be receiving SMS Received webhooks."*

**The required structure, ruled:**

- **One documented envelope parser**, shared, built from the recorded contract.
- **Then a `Type` switch.**
- **Then two interpreters that know nothing of each other.**

Two hand-written envelope parsers against one documented envelope is the duplication, not
the separation.

**⚠ WHAT SURVIVES INTACT AND IS STILL BINDING.** The two payloads **MEAN** different things
and must never be conflated. `Status` and `Result` are shared field *names* carrying
different contracts: on a delivery report they are `SUCCESS`/`FAILED`/`PENDING` and one of
twenty-one documented `Result` values; on a reply **both carry `RECEIVED`**. A `RECEIVED` is
a reply. It is not a delivery outcome and must never be recorded as one. The semantic
separation was always the real instruction; only the claim about *shape* was wrong.

**⚠ AND IT OPENS A ROUTING QUESTION THIS TICKET CANNOT CLOSE.** Nothing documents a way to
send the two callbacks to two different URLs. What is documented is one webhook URL per
Sender, overridable per outbound message by `WebhookCallbackURL`, which is per message and
not per callback type. **If TNZ cannot route them separately, this ticket's endpoint and
[[GTC-229]]'s are the same route**, and the *Do not touch* entry below forbidding
`src/app/api/sms/inbound/route.ts` cannot be satisfied as written. Drafted for TNZ
2026-09-12; **it gates Phase 3.**

**The authentication scheme is shared, and that is now documented rather than inferred.**
The same three headers with the same example values appear in both sections, and the
parameter descriptions state the credential *"can configure a unique Sender if required"*
and *"can configure a unique APIKey if required"* — which documents both that sharing is the
default and that divergence is configurable. The ownership ruling's premise holds.

⚠ One correction to the credential's shape: the webhook `Authorization` header carries the
**raw secret** (`Authorization="ta8wr7ymd"`), not `Basic <token>`. Outbound API calls use
`Authorization: Basic <Auth Token>`, which is `TNZ_AUTH_TOKEN` and a different credential.

**⚠ An unset delivery-receipt secret must fail closed.** That requirement stands.

**⚠ CORRECTED 2026-09-12 — the fail-open cron shape this section described is already
fixed.** The text here previously said the three cron routes guard with
`if (CRON_SECRET && providedSecret !== CRON_SECRET)` so an unset secret leaves them open,

- [[GTC-270]] closed the fail-open at `bf06cc1`, status `fixed`. All three cron routes call

**So there is a house precedent to follow rather than a ticket to wait on. Follow
[[GTC-270]]'s shape.**

⚠ **The route scanner will not recognise this ticket's new secret. Verified directly
against `tests/security-route-scan.ts` at `d1577b7`.**

**`SHARED_SECRETS` there is exactly `new Set(['CRON_SECRET'])`** — the only env var the
scanner treats as a shared secret. A new TNZ callback secret is invisible to it as a
credential, whatever shape the check takes. Since this ticket **owns** the credential and

⚠ **`tests/security-route-scan.ts` is Do-Not-Touch Zone 6.** Adding the secret to

**Two structural constraints, verified at `d1577b7`, that bear on where the shared

- **Cross-file resolution is one level and relative-only** — `MAX_MODULE_DEPTH = 1`, its

  import one level away is followed; one reached through the `@/lib/...` path alias is
  **not**. Because [[GTC-229]] consumes this ticket's credential, the placement decided here
  determines whether the scanner can see the check on **both** routes.
- **Local helper depth is bounded** at `MAX_HELPER_DEPTH = 3`.

⚠ **CORRECTION — [[GTC-270]]'s stated reason is superseded and its cited symbol is gone.**
`src/app/api/cron/cron-secret.ts` explains the pure-predicate split by saying [[GTC-268]]'s
scanner *"does NOT follow imports"*, naming `collectSharedSecret`. **That symbol does not
exist at `d1577b7`**, and [[GTC-273]] (`b50dffc`, fixed) has since added one-level
relative-import resolution. The measured outcome [[GTC-270]] records — all six cron handlers
reported as *"no credential of any kind"* — stands as history, and keeping the refusing `if`
in the route file remains the safe shape. **Do not cite `collectSharedSecret` and do not
repeat "does not follow imports" as current.** Read the scanner.

⚠ **The tension with owning the credential.** The *verification* is shared; the *refusal*
must stay visible in each route file. Getting that split wrong either duplicates the
credential — the outcome the ownership ruling exists to prevent — or blinds the scanner.

**A third shape to avoid, from [[GTC-229]] audit A.** `src/app/api/sms/inbound/route.ts` returns
`200` on every path *including its own catch block* — a Twilio-era choice to suppress retries. The
consequence recorded there applies identically here: *"a handler that throws on every request is
indistinguishable from one that works, from TNZ's side and from ours."* A delivery-receipt endpoint
that silently swallows is worse than none, because the surfaces above it would then read
*"delivered"* from an absence.

**`route-classifications.json`** must gain the new route with its real auth type. Note the standing
staleness: 80 entries against 104 `route.ts` files at `5df28ba`, so 24 routes are unclassified.
**Re-counted 2026-09-12 at `0dc7be1`: 81 entries against 106 `route.ts` files, so 25 are
unclassified — the staleness grew.** Neither the three cron routes nor
`src/app/api/sms/inbound/route.ts` is in the file. That is staleness, not a ruling — do not
read an absence there as an assessment.

**⚠ authType — RULED 2026-09-12: `CUSTOM`.** The available values are `PUBLIC`, `SESSION`,
`TOKEN`, `NONE` and `CUSTOM`; there is no shared-secret type. `/api/webhooks/stripe` is
recorded `PUBLIC` with the evidence `"webhook endpoint"`, which understates a
signature-verified endpoint. **Do not inherit that understatement, and do not fix it here** —
the Stripe entry's correction is [[GTC-291]]. This route is `CUSTOM`, with the evidence
naming the predicate it calls.

**⚠ Parse failure answers 5xx — RULED 2026-09-12.** A payload the endpoint cannot parse is
answered non-2xx in the 5xx range, never 200 and never 4xx. The reasoning is the retry
contract: TNZ retry a failed webhook every five minutes for up to 24 hours, so a 5xx buys a
24-hour window in which the contract can be corrected and the report still lands, where a
4xx discards it permanently. **The retry window is the mechanism that survives a contract we
got wrong**, and this ticket's central risk is exactly that. The cost is up to 288 retries
per message while the fault stands, which is the correct noise for a fault that must not be
silent. Auth failure stays `401`.

## Isolate the wire shape — RULED 2026-09-12

**Every acceptance assertion in this ticket is a fabricated-payload assertion. Not one of
them requires reaching TNZ.** That is deliberate and it is what makes the ticket buildable
without the subscription. It is also the ticket's central risk: **we would be asserting
against a shape we believe rather than one we have seen.** If the believed shape is wrong,
every test passes against a fiction and the surfaces above are confidently wrong rather than
merely silent — the exact failure this ticket exists to end.

**Requirement: the wire-shape assumption must be isolated and recorded, so the trial
corrects one place.**

- The parse from TNZ's payload into Gather's delivery state must live behind one narrow
  boundary. Everything downstream reads Gather's shape, never TNZ's.
- The assumed shape must be written down — field names, types, the status vocabulary as far
  as it is known, and which parts are documented versus inferred. A reader at trial time
  must be able to diff belief against reality without reading the implementation.
- Fabricated test payloads must be built from that recorded shape, so that correcting the
  shape breaks the tests **loudly** rather than leaving them passing against a fiction.

**This is the difference between a build that survives the trial and one that has to be
redone.** The same reasoning that makes the fabricated-payload approach acceptable makes
this requirement non-optional.

## This ticket does not design it

**Deliberately.** The design questions are real and the doc answers most of them; guessing them
before reading it is the error [[GTC-258]] declined to make about the send-response wire format,
and the same reasoning applies with more force here, because a mis-parsed delivery report would
make the surfaces confidently wrong rather than merely silent.

**Not decided here, and not to be decided by an implementation choice made in passing:**

- **Webhook or poll or both.** A webhook is push and needs authentication and a retry contract; a
  GET is pull and needs a schedule and a cursor. Different failure modes, possibly both wanted.
- **Where delivery state lives.** A column on an existing model, a new model, or an `InviteEvent`
  type. Note that `InviteEventType` at `5df28ba` has eighteen members and none names a delivery

- **What the states are.** `Status=Failed` and `Result="Destination is blacklisted"` are two of

- **Retention and privacy.** How long delivery results are kept, and whether a `Result` string is
  stored verbatim. [[GTC-229]] *Unknowns* 4 raises the parallel question for inbound message bodies

- **Whether a delivery failure feeds opt-out state.** `Destination is blacklisted` is evidence the

  Inferring a local opt-out from a delivery failure would write into Do-Not-Touch Zone 7 on an
  inference. **Raise it; do not do it.**

## Phase 1 findings — the two schema decisions that changed on Phase 0's evidence

Recorded here on a founder ruling rather than only in the schema comments,
because both are reasoning that outlives this model.

### 1. `reportedAt` would have been a lie

The proposal carried a `reportedAt DateTime` column, filled from TNZ's timestamp.
**Phase 0 found there is no report timestamp in the envelope.** All three of TNZ's
timestamps — `SentTimeLocal`, `SentTimeUTC-ISO8601`, `SentTimeUTC-RFC3339` — are the time
the **message was sent**. Nothing in the payload carries the clock of the report itself.

So the column is `providerSentAt` (TNZ's, the send) and `receivedAt` (ours, the arrival).

**The durable part: a column whose name asserts a fact the data cannot support is worse
than a missing column, because nothing ever contradicts it.** A missing column is felt the
first time someone needs it. A mis-named one is read correctly by every query, reported
confidently on every screen, and is wrong in a way that produces no error — which is the
same failure this whole ticket exists to end, one layer down. `reportedAt` filled from a
send time would have made the acceptance-to-outcome gap ([[GTC-264]] *Unknowns* 5, which
bears on which stamps [[GTC-258]] moves) measure exactly zero, forever, and look right.

### 2. No unique constraint on `providerMessageId`

The proposal weighed `@@unique([providerMessageId, destination, status, result])` for
idempotency. It is an index only.

TNZ retry a failed webhook every five minutes for up to 24 hours, and
`PENDING`-then-`SUCCESS` appears possible, so duplicates and multiple reports per message
are both expected rather than exceptional.

**The durable part: a unique constraint over an unobserved vocabulary turns a wrong belief
into SILENT DATA LOSS, while an index turns it into duplicate rows, which are
recoverable.** The asymmetry is the whole argument. If the dedupe key is wrong, the
constraint silently discards reports that differ in a way we did not anticipate, and the
loss leaves no trace; the index keeps both rows and a reader can collapse them later.
**And idempotency in the handler is correctable without a migration**, where a constraint
is not. This is the same restraint as *"do not model a boolean over a vocabulary you have
not seen"*, applied to the schema rather than the enum.

### 3. The measurement that settles the `InviteEventType` option

The ticket argued from structure that the join key is *"buried in a JSONB column with no
index for that path"*. Measured on the rehearsal database, 50,000 rows in each table,
`EXPLAIN (ANALYZE, BUFFERS)`:

- `SELECT * FROM "SmsDeliveryReport" WHERE "providerMessageId" = $1`
  → **Index Scan**, 4 shared buffers, **0.038 ms**.
- `SELECT * FROM "InviteEvent" WHERE metadata->>'messageId' = $1`
  → **Seq Scan**, 963 shared buffers, **5.216 ms**, 50,044 rows removed by filter.

**And the shapes differ, not just the numbers: the sequential scan grows with the table
and the index scan does not.** At 50,000 rows it is ~137x on time and ~240x on buffers; at
a million it is worse by the same mechanism. That is the argument against storing delivery
state as an `InviteEventType` member, measured rather than asserted.

## Phase 2 findings — the split, the false positives, and what RED proved

### 1. The file split, and why it is better than the instruction it deviates from

**Recorded as such on a founder ruling, 2026-09-12.** The instruction was one
module, `src/lib/sms/tnz-delivery-contract.ts`. Phase 2 built two:

```
src/lib/sms/tnz-webhook-envelope.ts     the SHARED envelope — [[GTC-288]] imports this
src/lib/sms/tnz-delivery-contract.ts    the delivery interpreter — this ticket only
```

**The reason is the envelope ruling itself, not a preference.** A shared module
named after one of its two consumers invites the second consumer to write its own.
Had the shared envelope parser lived in a file called `tnz-delivery-contract.ts`,
[[GTC-288]]'s executor would have had to write
`import { parseTnzWebhookEnvelope } from './tnz-delivery-contract'` — and the file
name would have told them, correctly, that they were in another ticket's
territory. The reasonable response to that signal is to write a second parser,
which is precisely the outcome the ruling exists to prevent.

**The durable part: putting the boundary in a FILENAME rather than a comment is
what makes the next executor MEET it rather than read it.** A comment is advice
that has to be found and believed. An import path is encountered whether or not
anybody reads the header. The first version of this instruction failed because a
caution sat beside a fact and did not travel with it; a filename travels with
every use.

**And the corollary, which is where the actual line sits.** `Message` — the reply
body — is part of the SHARED envelope type on purpose. Leaving it out would force
[[GTC-288]] to extend the type before it could parse a reply, which is the first
step back toward the second parser. So the line is **not** "the delivery module
cannot SEE the reply body". It is **"the delivery module never READS it"**. Three
consequences, each asserted:

- The contradiction warning for `Message` arriving on a `Type=SMS` envelope is
  raised in the **envelope** module, so the delivery module contains no access to
  the field at all. The first draft read `envelope.Message` in the delivery module
  and the suite failed it correctly.
- That warning reports **presence, never content**.
- A reply refusal carries the classified kind — so Phase 3 can route it onward
  rather than drop it — and carries none of the message.

### 2. Two false-positive assertions, and the rule they yield

**⚠ THIS IS THE SAME FAMILY AS [[GTC-277]] FINDINGS 6, 7 AND 8, IN A NEW PLACE,
and it is recorded here at the founder's instruction for that reason.** Finding 8
records a mutation that reported nothing for two possible reasons, and the trap
beside it — an assertion matching `/resend|email|send/i` that was satisfied by the
Resend SDK's own log line, so *"the third-party library's logging stood in for the
application's"*. Same species: **an assertion satisfied by something other than
the thing it was written to check.**

Both instances here were source-grep assertions that fired on the modules' own
**prose**:

- `/\b(RED|AMBER|GREEN|colour)\b/`, asserting the module forecloses no glance
  colour, matched this phase's own `PHASE 2 RED STUBS` comment.
- `/\bSmsOptOut\b/`, asserting the delivery module carries no reply vocabulary,
  matched a `note:` string whose entire content is a **prohibition** against
  touching `SmsOptOut`.

**Both were the dangerous direction.** Each would have gone GREEN the moment the
prose changed — the first when the RED-stub comments were deleted at the end of
the phase, the second on any rewording of the note — **passing for a reason
unrelated to the property, and silently re-breaking on any future comment using
the word.**

> **A source-grep assertion about CODE must not read PROSE. And naming a
> prohibition is the opposite of the defect: a comment that forbids a thing is
> evidence the thing is absent, not present.**

**The fix, in two parts.** A `codeOnly()` helper strips block comments, and line
comments only where `//` does not follow a colon so that URLs inside strings
survive — string literals are deliberately KEPT, because a foreclosed colour or an
import specifier would appear as one. And the reply-vocabulary check was narrowed
from *"the name appears anywhere"* to *"the field is accessed, or the opt-out
machinery is imported"*: `/\.Message\b|\[['"]Message['"]\]|from '\.\/opt-out|OPT_OUT_KEYWORDS/`.

**⚠ AND THE MUTATION CHECK IS WHAT MADE THE LOOSENING SAFE RATHER THAN MERELY
SMALLER.** Narrowing an assertion to stop a false positive can easily narrow it
past the true positive as well, and a suite that then goes green proves nothing —
which is [[GTC-277]] Finding 8's whole point. So all three source-grep assertions
were mutation-checked after the narrowing, and **[[GTC-277]] Finding 8's own rule
was followed: the edit was verified to have landed before its result was read**,
by diffing the module against its pre-mutation copy afterwards.

Each mutation was caught by exactly the assertion that should catch it, with one
failure and no collateral:

- add `function leak(e: TnzWebhookEnvelope) { return e.Message; }` → L7 fails, 1 failure
- add `const bad = 'RED';` → L8 colour fails, 1 failure
- add `export function isDelivered(): boolean` → L3 fails, 1 failure

Module byte-identical to its pre-mutation state afterwards, verified by `diff`.

### 3. Layer 9 passed at RED, and that is the most valuable thing in the run

The fixture factory is the mechanism GTC-264 *Isolate the wire shape* requires:
fabricated payloads built FROM the recorded shape, so that correcting the shape
breaks the tests loudly. **That is a TYPE property, and no runtime assertion can
observe it by running code.** Layer 9 therefore generates two probe files and runs
`tsc` on each:

- **the control** — an override naming a real field (`MessageID`) must typecheck,
  and does;
- **the rename** — an override naming a field that does not exist (`MessageIDD`)
  must fail, and does, and the error names the offending key.

**The control is what makes the negative test mean anything.** Without it, a probe
that failed for an unrelated reason — a bad import path, a compiler flag, a
missing dependency — would satisfy "the rename fails" and the suite would report
a working correction mechanism that did not exist.

**It passing at RED is the point.** At RED there was no parse at all, so layer 9
proved the correction mechanism worked *before there was anything to correct*. The
requirement is not that the tests pass; it is that a corrected field name cannot
leave them passing. That property is verifiable independently of the parse, and
verifying it first is what makes the rest of the phase safe to build.

**⚠ THE LIMIT, STATED, BECAUSE AN OVERCLAIMED GUARANTEE IS WORSE THAN A NARROW
ONE.** The mechanism has two halves. The first is total: the wire type is
*derived* from `ENVELOPE_PROVENANCE`, so the record cannot drift behind the type —
renaming a field in the record renames it in the type, everywhere, unavoidably.
**The second half is not total.** It relies on TypeScript's excess-property check,
and **that fires on object LITERALS only.** A test that assembled its override
into a loosely-typed variable first, and passed the variable, would compile
against a stale key and go green against a fiction.

Every override in `tests/tnz-delivery-contract-test.ts` is a literal, so the
property holds today. **It is a property of how the tests are written, not one the
compiler enforces on their behalf** — so a future suite that builds overrides
dynamically forfeits it, and would need a different mechanism rather than
inheriting this one.
