# GTC-264 — Ingest TNZ delivery results

**Status:** Open — **scoped, not designed.** Filed 2026-08-31 | **Branch:** TBD
**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low
Escalated (brand/trust risk): [x] Yes — the surfaces this feeds currently tell the host that
messages were sent which were never delivered. Three separate consumers are wrong, or absent, for
want of this one signal.

**Filed on TNZ's answers of 2026-08-31**, recorded in [[GTC-258]]. Tree verified at `5df28ba`;
every symbol cited was checked against that commit (GTC-222 rule 5). Line numbers appear only as
parenthetical hints.

---

## Why this exists

TNZ's answer, quoted in full in [[GTC-258]]:

> *"you should be working from delivery results and not assuming the API accepting a message means
> successful delivery."*

A send returns **200 and the message is ACCEPTED**, including to a blacklisted number. The real
outcome arrives afterwards through **status reporting** — a status GET endpoint or a status webhook
— as `Status=Failed` with a `Result` such as `"Destination is blacklisted"`. Status webhooks are
**distributed per destination**, so there is no batch ambiguity to unpick.

**Gather consumes none of it.** Verified at `5df28ba` and recorded in [[GTC-258]]: no route, no
poller, no schema field, no glance state reads a delivery result. The tree has never had this
signal. Acceptance is the only thing it has ever known, and every stamp, count and colour
downstream is built on it.

This ticket builds the missing channel. **It does not fix the things that are wrong because the
channel is missing** — those are named below as consumers, and each is owned elsewhere.

---

## Scope

**Build: ingest TNZ delivery results, per destination, and make delivery state readable.**

That is the whole of it. Concretely, the ticket must deliver:

1. **A way in.** Whichever of TNZ's two mechanisms the doc supports and the deployment can use —
   the status webhook, the status GET endpoint, or both. Answer 3 says webhooks are distributed
   per destination; whether the GET is per-message or per-batch is unread.
2. **Authentication on it**, if it is a webhook. See *The auth shape* below — this is not left to
   the executor's taste.
3. **Somewhere to put it.** Delivery state, per sent message, correlated back to the send. **This
   carries schema** — see *Stop Condition 7* below; it fires, and it is expected to.
4. **A read path.** Delivery state becomes the truth its consumers read, in place of the accept
   signal they read today.

**Correlation key.** `sendViaTnz` in `src/lib/sms/tnz-client.ts` already extracts TNZ's
`MessageID`, under a comment naming the reason — *"TNZ returns a JSON body containing a `MessageID`
for delivery tracking."* `sendSms` in `src/lib/sms/send-sms.ts` writes it into
`InviteEvent.metadata` as `messageId`. **A repo-wide grep at `5df28ba` finds nothing that reads it
back.** The handle exists, is captured on every send, and has never been used. Whether that
metadata field is the right join key or whether the correlation belongs on a proper column is a
design question this ticket answers — but the key itself is already being written.

**Not in scope — the consumers.** Building the channel is not the same as rewiring what drinks
from it. Each consumer is named below with its owner. Wiring any of them here is scope expansion
(Stop Condition 5).

### 1. Honest sent-stamps

Every cadence stamp in the tree is written at accept-time on the strength of `result.success`:

| Stamp | Written by |
|---|---|
| `PersonEvent.firstNudgeSentAt` / `secondNudgeSentAt` | `sendNudge` in `src/lib/sms/nudge-sender.ts` |

reports `'first reminder sent'` to the host on their strength.

**Owner: [[GTC-258]]** — which of these move to delivery-time, which legitimately stay at

## The auth shape — inherited from [[GTC-229]], not invented here

If the ingest is a webhook, TNZ's inbound authentication scheme is already documented in
[[GTC-229]] answer 4, gathered on 2026-08-29:

> Headers `X-Timestamp`, `X-Sender`, `Authorization`, plus `Sender` and `APIKey` repeated in the
> JSON body. Configured in the TNZ dashboard under **Users > API User > API > Reporting**.

**Two warnings carry over, and both are binding.**

**⚠ The delivery-receipt contract is NOT the MO contract.** [[GTC-229]] answer 3 states this
explicitly: the MO webhook documented at
`https://www.tnz.co.nz/Docs/RESTAPI/?version=2.04#receive-webhook` is *"distinct from the
delivery-receipt callback format — do not assume one shape covers both."* [[GTC-229]] warns its own
executor not to read one and implement the other; the same warning applies here in the mirror
image. **Read the delivery-receipt documentation.** Whether the *authentication* scheme is shared
between the two callbacks even though the *payload* is not is an unknown below, not an assumption.

**⚠ Do not copy the fail-open cron pattern.** The three cron routes guard with
`if (CRON_SECRET && providedSecret !== CRON_SECRET)`, so **an unset secret leaves the route open**.
`src/app/api/cron/decide-by-followups/route.ts` carries a comment recording that this was
*"deliberately copied rather than diverged from, so the fix lands in one ticket"* — that ticket is
[[GTC-220]]. [[GTC-229]] F2 says of the same shape: *"Do not reproduce that shape here. An unset MO
secret must fail closed."* **The same holds for this endpoint.** An unset delivery-receipt secret
must fail closed. If that argues for pulling [[GTC-220]] forward, say so and stop; do not fix
[[GTC-220]] in passing.

**A third shape to avoid, from [[GTC-229]] audit A.** `src/app/api/sms/inbound/route.ts` returns
`200` on every path *including its own catch block* — a Twilio-era choice to suppress retries. The
consequence recorded there applies identically here: *"a handler that throws on every request is
indistinguishable from one that works, from TNZ's side and from ours."* A delivery-receipt endpoint
that silently swallows is worse than none, because the surfaces above it would then read
*"delivered"* from an absence.

**`route-classifications.json`** must gain the new route with its real auth type. Note the standing
staleness: 80 entries against 104 `route.ts` files at `5df28ba`, so 24 routes are unclassified.
That is staleness, not a ruling — do not read an absence there as an assessment.

## This ticket does not design it

**Deliberately.** The design questions are real and the doc answers most of them; guessing them
before reading it is the error [[GTC-258]] declined to make about the send-response wire format,
and the same reasoning applies with more force here, because a mis-parsed delivery report would
make the surfaces confidently wrong rather than merely silent.

**Not decided here, and not to be decided by an implementation choice made in passing:**

- **Webhook or poll or both.** A webhook is push and needs authentication and a retry contract; a
  GET is pull and needs a schedule and a cursor. Different failure modes, possibly both wanted.
- **Where delivery state lives.** A column on an existing model, a new model, or an `InviteEvent`
  type. Note that `InviteEventType` at `5df28ba` has eighteen members and none names a delivery
  outcome — `SMS_SEND_FAILED` is a *send-time* failure written in the `sendSms` catch block, and
  must not be quietly overloaded to mean a delivery-time one.
- **What the states are.** `Status=Failed` and `Result="Destination is blacklisted"` are two of
  TNZ's values. The full set is unread. Do not model a boolean over a vocabulary you have not seen.
- **Retention and privacy.** How long delivery results are kept, and whether a `Result` string is
  stored verbatim. [[GTC-229]] *Unknowns* 4 raises the parallel question for inbound message bodies
  and declines to settle it; the same restraint applies.
- **Whether a delivery failure feeds opt-out state.** `Destination is blacklisted` is evidence the
  number is on TNZ's list — which is account-wide, while `SmsOptOut` is per-host ([[GTC-229]] F3).
  Inferring a local opt-out from a delivery failure would write into Do-Not-Touch Zone 7 on an
  inference. **Raise it; do not do it.**

## Unknowns

**The first is blocking (Stop Condition 8) and must be resolved from TNZ's documentation before any
code is written.**

1. **The delivery-receipt contract itself.** Payload shape, field names, the status vocabulary, how
   a report correlates to a send (`MessageID`? something else?), the authentication order, TNZ's
   expected response status and their retry behaviour on a non-2xx. **Distinct from the MO contract
   — read the delivery-receipt documentation, not the receive-webhook page.**
2. **Whether the MO shared secret and the delivery-receipt secret are the same credential.**
   [[GTC-229]] F2 already has this open for MO — *"whether the body `APIKey` and the header
   `Authorization` are the same secret in two places or two secrets"* — and it now has a second
   axis. Affects how many env vars, and their naming.
3. **The status GET endpoint's shape.** Per-message or per-batch, its rate limits, and whether it
   returns anything the webhook does not. Answer 3 covers webhooks; the GET was not asked about
   separately.
4. **Whether a delivered receipt exists, or only failures.** If TNZ report success as well as
   failure, "delivered" becomes an affirmative state; if only failures arrive, absence of a failure
   is the only positive signal there will ever be — a materially different thing to build a green
   on, and a materially different thing for [[GTC-192]] to colour.
5. **Timing.** How long after acceptance a status report arrives, and therefore whether a stamp can
   wait for it or must be written provisionally and corrected. This bears directly on
   [[GTC-258]]'s choice of which stamps move.

## Acceptance — assertions to hold, not a design

- [ ] An authenticated delivery report for a known `MessageID` is recorded, and readable.
- [ ] An **unauthenticated** report is rejected and records nothing.
- [ ] With the secret env var **unset**, the endpoint **fails closed** (contrast the cron shape).
- [ ] A handler that throws does **not** read as success to TNZ or to us.
- [ ] A report for an unknown or already-recorded message is handled without throwing and without
      double-writing.
- [ ] A `Status=Failed` / `Result="Destination is blacklisted"` report is distinguishable from a
      send-time failure — it must not be conflated with `SMS_SEND_FAILED`.
- [ ] Adjacent flows unaffected: outbound `sendSms` routing, the nudge scheduler, wrap-up dispatch,
      the decide-by follow-up sweep, and the MO handler.

**Test gate** — Severity High: test-first required. RED before any fix, GREEN after, both pasted
into Evidence. **Stop Condition 6 is live and specific: a test that reaches TNZ is a failed test.**
Drive the endpoint with fabricated delivery-report payloads only.

## Stop Conditions

Standard eight from `BUG-TICKET-TEMPLATE.md`. Live notes:

- **8 (required unknown):** **pre-fired.** Unknown 1 blocks. The delivery-receipt contract must be
  read before code.
- **7 (schema migration):** **fires, and is expected to.** Storing delivery state carries schema.
  Per house convention the phase that carries the migration carries nothing else, and per the
  Deploy caveat in `GATHER-BUILD-CONSTANTS.md` the migration must be rehearsed against a copy of
  the production database before any deploy carries it. Stop and report the migration first.
- **6 (real-world side effects):** binding. No test may reach TNZ. Fabricated payloads only. Note
  that a live probe is *less* informative than it sounds — a blacklisted send returns 200 like any
  other, so the probe only shows anything once a status report lands.
- **5 (scope expansion):** the three named consumers are the excluded work, not the deliverable.
  Rewiring a stamp, adding a `RED_REASON`, or hardening the cron shape are each someone else's
  ticket. If any becomes load-bearing → stop.
