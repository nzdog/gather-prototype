## Why this exists

TNZ's answer, quoted in full in [[GTC-258]]:

> *"you should be working from delivery results and not assuming the API accepting a message means
> successful delivery."*

A send returns **200 and the message is ACCEPTED**, including to a blacklisted number. The real
outcome arrives afterwards through **status reporting** — a status GET endpoint or a status webhook
— as `Status=Failed` with a `Result` such as `"Destination is blacklisted"`. Status webhooks are
**distributed per destination**, so there is no batch ambiguity to unpick.

**Gather consumes none of it.** Verified at `5df28ba` and recorded in [[GTC-258]]: no route, no
poller, no schema field, no glance state reads a delivery result. The tree has never had this
signal. Acceptance is the only thing it has ever known, and every stamp, count and colour
downstream is built on it.

This ticket builds the missing channel. **It does not fix the things that are wrong because the
channel is missing** — those are named below as consumers, and each is owned elsewhere.

⚠ **THE SIBLING ON THE EMAIL SIDE IS [[GTC-265]]** (filed 2026-09-01). Together the two are one
sentence — *Gather never checks what actually happened, provider by provider* — but they are not the
same bug and must not be merged. This ticket builds a channel that **does not exist**: TNZ's
delivery results have never reached the tree. GTC-265 reads a value **already sitting in a
variable**: Resend returns its error rather than throwing, and every one of the four call sites
discards it, so a failed email reports success, logs `NUDGE_SENT_HOST`, and starts a cooldown that
then blocks the retry. One is work; the other is an omission. That is why this is a feature at
`high` and that is a bug at `high`.

## Scope

**Build: ingest TNZ delivery results, per destination, and make delivery state readable.**

That is the whole of it. Concretely, the ticket must deliver:

1. **A way in.** Whichever of TNZ's two mechanisms the doc supports and the deployment can use —
   the status webhook, the status GET endpoint, or both. Answer 3 says webhooks are distributed
   per destination; whether the GET is per-message or per-batch is unread.
2. **Authentication on it**, if it is a webhook. See *The auth shape* below — this is not left to
   the executor's taste.
3. **Somewhere to put it.** Delivery state, per sent message, correlated back to the send. **This
   carries schema** — see *Stop Condition 7* below; it fires, and it is expected to.
4. **A read path.** Delivery state becomes the truth its consumers read, in place of the accept
   signal they read today.

**Correlation key — CONFIRMED BY DOCUMENTATION 2026-09-12.** `sendViaTnz` in
`src/lib/sms/tnz-client.ts` already extracts TNZ's `MessageID`, under a comment naming the
reason — *"TNZ returns a JSON body containing a `MessageID` for delivery tracking."* `sendSms`
in `src/lib/sms/send-sms.ts` writes it into `InviteEvent.metadata` as `messageId`. **A repo-wide
grep at `d1577b7` finds nothing that reads it back.**

The documentation settles that this is the right key. On the send side, `MessageID` is an
optional advanced parameter: *"A Message Identifier helps you keep track of each message
(maximum 40 characters, alphanumeric). Use a unique MessageID for each request. If you leave
this field blank, the API will generate a 36-character UUID (v4) for you and include it in the
response body."* `sendViaTnz` supplies none, so TNZ generate one. It is then **echoed back in
both the delivery-status webhook and the SMS-reply webhook** — *"MessageID parameter supplied
when sending your original API call. If you did not supply one, the API generated one for you."*

So the handle exists, is captured on every send, is the documented join key for this ticket
**and** for [[GTC-288]]'s inbound attribution, and has never been read. Whether the metadata
field is the right place to join from or whether the correlation belongs on a proper column is
a design question this ticket answers — but the key itself is already being written.

**➡ The full treatment of `MessageID` is in [[GTC-288]], under *The join key Gather has been
capturing and never reading*.** Read it before designing the correlation here, because the
two tickets join on the same field and **the design this ticket picks is the one [[GTC-288]]
inherits.** If the correlation moves off `InviteEvent.metadata` onto a column, it moves for
both. Three points there bear directly on this ticket:

- The value is written on every TNZ send and read nowhere — [[GTC-258]] calls that *"not a
  second defect; it is the missing half of this one"*, and it is in fact the missing half of
  **three**: this ticket's correlation key, [[GTC-258]]'s correction signal, and
  [[GTC-288]]'s attribution key are the same field.
- It resolves the cross-host ambiguity (H2) and does **nothing** for cross-customer
  interception (H1). Do not let the finding be repeated anywhere as "attribution is solved".
- [[GTC-229]] F1 named the exact condition that would change its answer completely, and this
  is that condition arriving.

⚠ **One gap in the join, and it is this ticket's to handle rather than fix.** `sendViaTnz`
treats a 2xx with an unparseable body as a success with `messageId` left `undefined` — its own
comment says *"a 2xx without a parseable body is still a success"*. Those sends store no join
key, so a delivery result for one cannot be correlated. **Do not fix the send path here**; that
is [[GTC-258]]'s. Handle the unmatched report without throwing, as the acceptance criteria
already require.

⚠ **Supplying our own `MessageID` is NOT this ticket's, and probably nobody's.** The 40-char
alphanumeric limit would let Gather encode its own reference, but TNZ's generated UUID is
already captured and works as a key. Changing what `sendViaTnz` sends is a send-path change.
Named here only so it is not discovered and adopted mid-build.

**Not in scope — the consumers.** Building the channel is not the same as rewiring what drinks
from it. Each consumer is named below with its owner. Wiring any of them here is scope expansion
(Stop Condition 5).

**First, §7's bounce rule is not SMS-only.** §6's ground truth is Kate's Christmas *email*,
and §7's illustration — *"twelve are away, two bounced"* — is drawn from it. [[GTC-265]] is
fixed, but it closed only the **send-time** half: its own *Unknowns* 3 records that it does

that delivery receipts do not exist in the tree and ingesting them is a feature. **There is
no email-bounce ingest ticket** — verified across `docs/tickets/` on 2026-09-12. **Filed as
[[GTC-289]].** This ticket makes the SMS half of §7 possible; [[GTC-289]] is the other half.

**Second, §7 needs a taxonomy this ticket cannot supply without the trial.** §7's reasoning
is that *"a bounce is not a silence — it's a dead channel; nudging it sends more messages
into the same void"*, and its door offers *"let the system try again, or take it herself —
ring him, ask his mum, fix the number"*.

**`Destination is blacklisted` is not a dead channel.** It is a live number whose owner
opted out. Colouring it red-on-arrival would be wrong, and every option behind §7's bounce
door is the wrong option for an opt-out — "try again" and "fix the number" both misread what
happened. `Result` values must therefore partition into at least three buckets:

- **dead channel** — §7's bounce, red on arrival;
- **opted out** — opt-out state, and explicitly *not* a §7 bounce;
- **transient** — retryable, and not red at all.

**We have seen exactly one `Result` value and it belongs to the middle bucket.** *Unknowns*
4 below — "the full set is unread" — is precisely what §7's colour rule waits on, and that
vocabulary is learned only by watching real failures. **Do not model a boolean over a
vocabulary you have not seen, and do not let [[GTC-192]] colour one until the partition is
known.**

## The auth shape — OWNED HERE as of 2026-09-12

**Ruled 2026-09-12: this ticket owns the shared-secret verification and its environment
variables. [[GTC-229]] and [[GTC-288]] consume them.**

Both this endpoint and the MO endpoint authenticate against the same TNZ dashboard
configuration — Users > API User > API > Reporting. This ticket lands first, so it builds the
credential handling once and the MO side consumes it rather than building a second path.

**That closes two open questions together.** *Unknowns* 2 below asked whether the MO secret
and the delivery-receipt secret are the same credential; [[GTC-229]] F2 asked whether the
body `APIKey` and the header `Authorization` are one secret in two places or two secrets.
**Both are answered by the example values**, in TNZ's 2026-08-18 answer and confirmed by the
MO documentation read on 2026-09-12: `X-Sender` and body `Sender` carry the same value;
`Authorization` and body `APIKey` carry the same value. One identity plus one secret, echoed
in two places, from one configuration screen.

⚠ **Confirm it at the trial rather than assuming it forever.** The two callbacks being
configured on the same screen is strong evidence they share a credential, but TNZ never said
so in prose. If the trial shows two credentials, this is a configuration change, not a
redesign — provided the credential is not hard-wired to one endpoint.

**The deliverable is therefore:** the env vars, their entry in `.env.example` and in the
Environment Variables table in `GATHER-BUILD-CONSTANTS.md` (which today lists
`TNZ_AUTH_TOKEN` and no callback secret), and a verification path both endpoints can call.

TNZ's inbound authentication scheme, as given on 2026-08-18:

> Headers `X-Timestamp`, `X-Sender`, `Authorization`, plus `Sender` and `APIKey` repeated in the
> JSON body. Configured in the TNZ dashboard under **Users > API User > API > Reporting**.

**Two warnings carry over, and both are binding.**

**⚠ The delivery-receipt contract is NOT the MO contract.** [[GTC-229]] answer 3 states this
explicitly: the MO webhook documented at
`https://www.tnz.co.nz/Docs/RESTAPI/?version=2.04#receive-webhook` is *"distinct from the
delivery-receipt callback format — do not assume one shape covers both."* [[GTC-229]] warns its own
executor not to read one and implement the other; the same warning applies here in the mirror
image. **Read the delivery-receipt documentation.** Whether the *authentication* scheme is shared
between the two callbacks even though the *payload* is not is an unknown below, not an assumption.

**⚠ An unset delivery-receipt secret must fail closed.** That requirement stands.

**⚠ CORRECTED 2026-09-12 — the fail-open cron shape this section described is already
fixed.** The text here previously said the three cron routes guard with

**So there is a house precedent to follow rather than a ticket to wait on. Follow
[[GTC-270]]'s shape.**

⚠ **`tests/security-route-scan.ts` is Do-Not-Touch Zone 6.** Adding the secret to

**Two structural constraints, verified at `d1577b7`, that bear on where the shared

⚠ **CORRECTION — [[GTC-270]]'s stated reason is superseded and its cited symbol is gone.**

## Isolate the wire shape — RULED 2026-09-12

**Every acceptance assertion in this ticket is a fabricated-payload assertion. Not one of
them requires reaching TNZ.** That is deliberate and it is what makes the ticket buildable
without the subscription. It is also the ticket's central risk: **we would be asserting
against a shape we believe rather than one we have seen.** If the believed shape is wrong,
every test passes against a fiction and the surfaces above are confidently wrong rather than
merely silent — the exact failure this ticket exists to end.

**Requirement: the wire-shape assumption must be isolated and recorded, so the trial
corrects one place.**

- The parse from TNZ's payload into Gather's delivery state must live behind one narrow
  boundary. Everything downstream reads Gather's shape, never TNZ's.
- The assumed shape must be written down — field names, types, the status vocabulary as far
  as it is known, and which parts are documented versus inferred. A reader at trial time
  must be able to diff belief against reality without reading the implementation.
- Fabricated test payloads must be built from that recorded shape, so that correcting the
  shape breaks the tests **loudly** rather than leaving them passing against a fiction.

**This is the difference between a build that survives the trial and one that has to be
redone.** The same reasoning that makes the fabricated-payload approach acceptable makes
this requirement non-optional.

## This ticket does not design it

**Deliberately.** The design questions are real and the doc answers most of them; guessing them
before reading it is the error [[GTC-258]] declined to make about the send-response wire format,
and the same reasoning applies with more force here, because a mis-parsed delivery report would
make the surfaces confidently wrong rather than merely silent.

**Not decided here, and not to be decided by an implementation choice made in passing:**

- **Webhook or poll or both.** A webhook is push and needs authentication and a retry contract; a
  GET is pull and needs a schedule and a cursor. Different failure modes, possibly both wanted.
- **Where delivery state lives.** A column on an existing model, a new model, or an `InviteEvent`
  type. Note that `InviteEventType` at `5df28ba` has eighteen members and none names a delivery
  outcome — `SMS_SEND_FAILED` is a *send-time* failure written in the `sendSms` catch block, and
  must not be quietly overloaded to mean a delivery-time one.
- **What the states are.** `Status=Failed` and `Result="Destination is blacklisted"` are two of
  TNZ's values. The full set is unread. Do not model a boolean over a vocabulary you have not seen.
- **Retention and privacy.** How long delivery results are kept, and whether a `Result` string is
  stored verbatim. [[GTC-229]] *Unknowns* 4 raises the parallel question for inbound message bodies
  and declines to settle it; the same restraint applies.
- **Whether a delivery failure feeds opt-out state.** `Destination is blacklisted` is evidence the
  number is on TNZ's list — which is account-wide, while `SmsOptOut` is per-host ([[GTC-229]] F3).
  Inferring a local opt-out from a delivery failure would write into Do-Not-Touch Zone 7 on an
  inference. **Raise it; do not do it.**

## Unknowns

**The first is blocking (Stop Condition 8) and must be resolved from TNZ's documentation before any
code is written.**

1. **The delivery-receipt contract itself.** Payload shape, field names, the status vocabulary, how
   a report correlates to a send (`MessageID`? something else?), the authentication order, TNZ's
   expected response status and their retry behaviour on a non-2xx. **Distinct from the MO contract
   — read the delivery-receipt documentation, not the receive-webhook page.**
2. **~~Whether the MO shared secret and the delivery-receipt secret are the same
   credential.~~ COLLAPSED 2026-09-12** into *The auth shape* above, together with
   [[GTC-229]] F2. One identity plus one secret, echoed in headers and body, from one
   configuration screen — evidenced by the example values in TNZ's 2026-08-18 answer and the
   MO documentation. Confirm at trial; it is a configuration change if wrong, not a
   redesign.
3. **The status GET endpoint's shape.** Per-message or per-batch, its rate limits, and whether it
   returns anything the webhook does not. Answer 3 covers webhooks; the GET was not asked about
   separately.
4. **⚠ Whether a delivered receipt exists, or only failures. THE HIGHEST-RISK ASSUMPTION
   BEING DEFERRED TO THE TRIAL — asked of TNZ 2026-09-12, outstanding.**

   If TNZ report success as well as failure, "delivered" becomes an affirmative state. **If
   only failures ever arrive, absence of a failure is the only positive signal there will
   ever be.**

   That is not a gap in knowledge, it is a different product statement. **Green on the
   glance would mean "no failure reported yet" rather than "it arrived"** — and the host
   reading that screen is being told something materially weaker than §7 implies, in a
   product whose stated purpose is to end wondering. [[GTC-192]] would be colouring an
   absence and calling it an arrival.

   It also decides whether this ticket can offer an affirmative delivered state at all, or
   only a failure record with an implied-success complement. That shapes the schema, so it
   shapes the migration.

   **Escalated above the other unknowns deliberately.** The others leave gaps; this one can
   force rework of the stored model and can quietly mislead a host if assumed the wrong way.
   If TNZ answer before the build starts, build to the answer. If they do not, **record the
   assumption explicitly under *Isolate the wire shape* and make it correctable.**
5. **Timing.** How long after acceptance a status report arrives, and therefore whether a stamp can
   wait for it or must be written provisionally and corrected. This bears directly on
   [[GTC-258]]'s choice of which stamps move.

## Acceptance — assertions to hold, not a design

- [ ] An authenticated delivery report for a known `MessageID` is recorded, and readable.
- [ ] An **unauthenticated** report is rejected and records nothing.
- [ ] With the secret env var **unset**, the endpoint **fails closed** (contrast the cron shape).
- [ ] A handler that throws does **not** read as success to TNZ or to us.
- [ ] A report for an unknown or already-recorded message is handled without throwing and without
      double-writing.
- [ ] A `Status=Failed` / `Result="Destination is blacklisted"` report is distinguishable from a
      send-time failure — it must not be conflated with `SMS_SEND_FAILED`.
- [ ] Adjacent flows unaffected: outbound `sendSms` routing, the nudge scheduler, wrap-up dispatch,
      the decide-by follow-up sweep, and the MO handler.
- [ ] A report whose `MessageID` matches no stored send is handled without throwing —
      including the case where the send stored no `messageId` at all because `sendViaTnz`
      accepted an unparseable 2xx body.
- [ ] **The assumed wire shape is recorded in one place**, marked documented-versus-inferred,
      and the fabricated test payloads are built from that record — so correcting the shape
      breaks the tests loudly rather than leaving them green against a fiction.
- [ ] **The credential verification is callable by the MO endpoint too**, not wired to this
      route alone. [[GTC-229]] consumes it; if it cannot, the ruling has been missed.
- [ ] The `.env.example` entry and the Environment Variables table in
      `GATHER-BUILD-CONSTANTS.md` are both updated. That table today lists `TNZ_AUTH_TOKEN`
      and no callback secret.
