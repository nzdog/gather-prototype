## ⚠⚠ THE THREE PAYLOAD TRAPS — none of these will fail loudly

**Read these before writing a line. Each one produces a handler that parses cleanly,
returns 200, and is wrong.** Shared field names across different contracts is the class this
codebase keeps getting caught by; here it appears three times in one payload.

**TRAP 1 — `Destination` carries the GUEST's number, not ours.**
The field named for a destination on the way out is the **sender** on the way in. It is
documented as E.164. A handler that reads `Destination` as "the number we sent to" will
resolve every reply to the wrong end of the conversation. There is no `From` field in this
contract.

**TRAP 2 — the body is `Message`, not `Body`.**
The Twilio-shaped handler at `src/app/api/sms/inbound/route.ts` reads `From` and `Body`
(audit A step 1). **Neither name exists in TNZ's contract.** Both silently yield
`undefined`, and audit A step 2 then returns `200 OK` having done nothing — a handler that
looks like it is working and discards every STOP it receives.

**TRAP 3 — `Status` and `Result` are the delivery-receipt vocabulary, reused.**
Here they carry the value `RECEIVED`. [[GTC-264]] will see the same two field names carrying
`FAILED` and one of twenty-one documented `Result` values. **Same names, different
contracts.**

**⚠ AMENDED 2026-09-12 BY FOUNDER RULING. The instruction was "do not build one parser for
both". That is rewritten, and the reason it was wrong is instructive.**

This trap previously said the similarity was *"precisely what TNZ warned about in their
2026-08-18 answer 2"*, and concluded *"a shared parser is the failure mode, not the
tidy-up"*. Phase 0 of [[GTC-264]] read the documentation.
**There is ONE webhook envelope.** Nineteen fields, same names, same order, same
authentication headers, and **one subscription** — verbatim: *"If you are set up to receive
Status webhooks, you will also be receiving SMS Received webhooks."* The discriminator is
`Type`: `SMS` is a delivery report, `SMSReply` is a reply to one of ours, `SMSInbound` is an
unsolicited inbound. `Message` is present only on the latter two, and `ReceivedID` is
documented as *"Always blank for Status webhooks"*.

**And TNZ never made the claim.** It came from Nigel's own question 2, which stated the
delivery-receipt field names as *"already known"* and the MO contract as *"assumed
different"*; TNZ answered that question with a bare URL. The correspondence record flagged
that provenance at the time and the flag was inherited past anyway. The finding is recorded
as its own lesson in `docs/05_ops/tnz-inbound-and-delivery-correspondence-2026-08.md`.

**The required structure, ruled:**

- **One documented envelope parser**, shared with [[GTC-264]], built from the recorded
  contract in `docs/05_ops/tnz-delivery-status-contract-2026-09-12.md`.
- **Then a `Type` switch.**
- **Then two interpreters that know nothing of each other.** This ticket owns the reply
  interpreter. [[GTC-264]] owns the delivery interpreter.

Two hand-written envelope parsers against one documented envelope is the duplication, not the
separation.

**⚠ WHAT SURVIVES INTACT AND IS STILL BINDING — and it is the whole point of the trap.** The
two payloads **MEAN** different things and must never be conflated. **A `RECEIVED` is a
reply. It is not a delivery outcome and must never be recorded as one**, and a `FAILED` is
not an inbound message. The shared field names are a shared *envelope*, never shared
*meaning*. Sharing the envelope parse is correct; sharing an interpretation is the defect
this trap exists to prevent.

**⚠ AND ONE OPEN QUESTION THAT MAY MERGE THIS TICKET'S ROUTE WITH [[GTC-264]]'s.** Nothing
documents a way to send the two callbacks to two different URLs — what is documented is one
webhook URL per Sender, overridable per outbound message by `WebhookCallbackURL`, which is
per message and not per callback type. If TNZ cannot route them separately, then
`src/app/api/sms/inbound/route.ts` receives delivery reports too, and this ticket's parse
must hand anything that is not `SMSReply`/`SMSInbound` to [[GTC-264]]'s interpreter rather
than dropping it. **Drafted for TNZ 2026-09-12; it gates [[GTC-264]] Phase 3 and it gates
this ticket's route shape.**

**And the fourth thing, which is not a trap but is the reason the first two matter:** every
one of those failures returns `200`. Audit A records that every path in the current handler
returns `200` including its own catch block. Until [[GTC-229]] lands, a wrong parse is
indistinguishable from a working one from TNZ's side and from ours.

## `MessageID` — the join key Gather has been capturing and never reading

**This is the ticket's central design change. It resolves [[GTC-229]] F1, and it is the
reason this ticket is buildable rather than blocked.**

TNZ's MO payload carries `MessageID`, documented as *"MessageID parameter supplied when
sending your original API call. If you did not supply one, the API generated one for you."*
It is echoed back in **both** the delivery-status webhook and the SMS-reply webhook. On the
send side it is an optional advanced parameter: *"If you leave this field blank, the API will
generate a 36-character UUID (v4) for you and include it in the response body."*

**So an inbound reply names the outbound message it answers.** Attribution does not have to
be guessed.

### 1. Gather has been capturing it on every send, and reading it nowhere

`sendViaTnz` in `src/lib/sms/tnz-client.ts` supplies no `MessageID`, so TNZ generate one.
`sendViaTnz` reads it off the send response under a comment naming its purpose — *"TNZ
returns a JSON body containing a `MessageID` for delivery tracking"* — and `sendSms` in
`src/lib/sms/send-sms.ts` writes it into `InviteEvent.metadata` as `messageId`.

**A repo-wide grep at `d1577b7` finds no reader of the stored `metadata.messageId`.** Every
occurrence in the tree is a write, a type declaration, or a pass-through up the call stack:
`sendSms`, the manual-nudge route at
`src/app/api/events/[id]/people/[personId]/nudge/route.ts`, `sendProxyNudge`,
`sendDecideByFollowup`, and the two interface declarations. **The value has been written on
every TNZ send since the transport went in and has never once been read back out.**

[[GTC-258]] records this under *The `messageId` is the handle, and it is written to a place
nothing reads*, and calls it *"not a second defect; it is the missing half of this one"*.
**That reading is now confirmed and enlarged: it is the missing half of three tickets** —
[[GTC-258]]'s correction signal, [[GTC-264]]'s correlation key, and this ticket's
attribution key are the same field.

⚠ **The email side declined the same capture, and that decision now has evidence against
it.** [[GTC-265]] *What was deliberately NOT done* records that `sendNudgeEmail` does not
return `messageId` — **a deliberate omission ruled 2026-09-12** — because Resend's `data.id`
*"changes what the audit trail contains, and that is its own decision"*, noting that the
nudge route already reads `sendResult.messageId` for its `InviteEvent` metadata *"where
email sends record `undefined` today"*. That restraint was right on the evidence then
available. **The SMS side now shows what such an id is for: it is load-bearing, not
decorative.** Not this ticket's to act on — it is [[GTC-289]]'s, which lists exactly this as
something it must establish.

### 2. It resolves H2 and does NOTHING for H1

**Say this plainly wherever the finding is repeated. It does not close the shared-shortcode
problem.**

- **H2 — two Gather hosts message the same guest — CLOSES.** The reply names the message, so
  it names the host and the event. No heuristic, no ambiguity, and no dependence on Gather's
  own record of what was sent last.
- **H1 — another TNZ customer's message intervenes — UNTOUCHED.** The reply is attributed to
  that customer, so **no webhook reaches Gather at all.** There is no `MessageID` to read
  because there is no payload. That is an absence indistinguishable from a guest who simply
  did not reply, and **no handler behaviour helps.** A dedicated shortcode is the only thing
  that closes it, and it is unpriced and outstanding.

**Anyone reading this section as "attribution is solved" has read it wrong.** What is solved
is attribution *of the replies we receive*. Whether we receive them is H1, and H1 is
unchanged by anything in this ticket.

### 3. [[GTC-229]] F1 anticipated its own unblocking

Worth pointing at, because it is why this arrived as a resolution rather than a surprise.
F1 named the exact condition under which its answer would change:

> *"Report the mechanism, its limits, and whether TNZ's MO payload carries anything better —
> a message reference tying the reply to a specific outbound send would change the answer
> completely. If it does, that is a new ticket, not a widening of this one."*

**It does, and this is that new ticket.** F1 also instructed that the handler *"must not
attempt to compensate for a false stamp"* — and joining on `MessageID` is not compensation,
it is declining to consult the corruptible index at all.

### What follows for sequencing

**The handler reads TNZ's answer rather than re-deriving it.** Audit A step 5 today queries
for the most recent `NUDGE_SENT_AUTO` whose `metadata.phoneNumber` matches, newest first.
That heuristic agrees with TNZ's last-sent rule, but it is a guess at an answer TNZ are
already giving.

**And it weakens the corruption link to [[GTC-258]].** A handler that never consults the
newest-wins index cannot be misdirected by a false entry in it. The sequence makes that safe
for the case that matters: a guest is not blacklisted until they STOP, so the **first** STOP
is a reply to a message that really was delivered, resolved before any false stamp for that
number exists. The false stamps accumulate afterwards, where inbound attribution no longer
looks.

⚠ **This is a reason not to wait for [[GTC-258]]; it is not a reason to think [[GTC-258]] is
less of a defect.** Its other consequences — a consumed nudge cadence stamp, a spent
decide-by follow-up, a suppressed wrap-up email fallback — are untouched, as is the host
being told a reminder was sent to a guest who received nothing.

**Two residual gaps in the join, both real:**

- `sendViaTnz` treats a 2xx with an unparseable body as success with `messageId` left
  `undefined` — its own comment says *"a 2xx without a parseable body is still a success"*.
  Those sends store no join key, and a reply to one cannot be resolved by `MessageID`. **Do
  not fix this here** — it is a change to the send path, and outbound is [[GTC-258]]'s.
  Report it and handle the miss (see *Settled: attribution failure* below).
- Whether TNZ attribute to the last *accepted* or last *delivered* message is unstated. It
  bears only on a second or later inbound message from an already-blacklisted number.

**Whether the newest-wins query is retained as a fallback** when `MessageID` does not
resolve is a design question this ticket answers. It is a real option and it is not
obviously right: the fallback is exactly the index [[GTC-258]] corrupts, so falling back to
it re-imports the problem `MessageID` avoided.

## ⚠ AFTER [[GTC-189]] SLICE 5, THE JOIN KEY LIVES IN A TABLE — AND THAT RETIRES THE SCAN RATHER THAN EXTENDING IT

*Filed 2026-09-19 on founder instruction, out of [[GTC-189]] slice 5c's shape proposal, where a
stopgap was ruled and this was named as the fix. Recorded as scoped work and not as a note.*

**The section above resolves attribution by `MessageID` and says the handler should read TNZ's
answer rather than re-derive it. Slice 5 changes WHERE that id is stored, and the change makes the
design cheaper than it was when this ticket was written.**

`OutboundMessage` landed at [[GTC-189]] slice 4a (`cb9ca01`). It carries, per recipient:

- `providerMessageId` — *"Resend's `data.id` for EMAIL; TNZ's `MessageID` for TEXT. The same name
  and the same meaning as `SmsDeliveryReport.providerMessageId`"* — and it is **`@@index`ed**,
  named in the schema as *"the join slice 6 runs on every inbound bounce"*.
- `channel`, an enum, so a reply can be resolved to the channel it answers.
- `personEventId`, a foreign key to the membership — which reaches `Person.phoneNumber` and
  `Event.hostId` in one join.
- `eventId`, denormalised and single-written, so the host is one hop away.

**So this ticket's join stops being a JSON-metadata scan and becomes a row lookup.** Today Audit A
step 5 reads `InviteEvent.metadata` with `{ path: ['phoneNumber'], equals: … }`, newest first —
an unindexed JSON path query over a log table, standing in for a foreign key. After slice 5 the
same question is `OutboundMessage.findFirst({ where: { providerMessageId } })`, on an index built
for it, returning the membership and the event directly.

### ⚠ AND IT DISSOLVES A VOCABULARY PROBLEM SLICE 5c ONLY PAPERED OVER

Slice 5c's dispatcher sends the ask. `sendSms` writes `NUDGE_SENT_AUTO` **unconditionally**, inside
itself, and `InviteEventType` has no member for an ask being sent — so the ask's text send writes
a ledger row saying a nudge was sent, at the press, before any nudge exists.

**The founder ruled the stopgap on 2026-09-19: leave it, record the falsity at the call site, and
file the fix here.** The measurements that carried it, reproduced so this ticket does not have to
re-derive them:

- The ask is **231 EMAIL to 1 TEXT** across 232 recipients, so a press writes **one** false row
  today — though it grows with [[GTC-189]] slice 8, which is text-first, and with [[GTC-312]]'s 35.
- **`NUDGE_SENT_AUTO` has ZERO rows in `gather_dev`.** No successful SMS has ever been sent in this
  environment, so the newest-wins attribution has never once worked here and nothing live depends
  on it either way.
- [[GTC-189]] decision 27 already makes `OutboundMessage` **the** record of a send — *"what was
  sent, to whom, on which channel, and what came back. Not the words."* The `InviteEvent` is
  therefore carrying **only** the STOP attribution, as a side effect of `sendSms`.

**The fix is this ticket's, and it is a subtraction.** Once attribution reads
`OutboundMessage.providerMessageId`, the ask does not need an `InviteEventType` member at all,
because nothing is reading the log row for attribution any more. **A new enum member would have
been a migration bought to feed an index this ticket is retiring** — which is why the stopgap was
ruled rather than the member.

### What this ticket must decide with it

- **Does the retained fallback — the newest-wins scan, still open above — now read
  `OutboundMessage` instead of `InviteEvent.metadata`?** It could: `personEvent -> person ->
  phoneNumber` gives the same "last message to this number" question against a table with foreign
  keys instead of a JSON path. That is a better fallback than the one this ticket was weighing, and
  it still re-imports [[GTC-258]]'s corruption if the ordering key is an acceptance stamp rather
  than a delivery fact. **Not decided here.**
- **The residual gap above is unchanged and now has a second home.** `sendViaTnz` treats a 2xx with
  an unparseable body as success with `messageId` undefined; slice 4a's schema records the same
  nullability on `providerMessageId` and calls it *"load-bearing rather than defensive"* for exactly
  this reason. So a send can be accepted and permanently unjoinable in **both** stores, and the
  miss-handling this ticket settles has to cover both.
- ⚠ **ORDERING.** Nothing here unblocks this ticket: it still depends on [[GTC-229]] for the door.
  What changes is that the work inside it is smaller once [[GTC-189]] slices 5c and 5d have written
  `providerMessageId` on a real accepted send — which, per slice 5a's evidence, **cannot happen in
  this environment until [[GTC-247]] is resolved.** So the table exists, the index exists, and the
  column is empty until a provider accepts something.

## RULED — opt-out is account-wide, not per-host

**Ruled 2026-09-12.** This was [[GTC-229]] F3, which was "report only". It is now decided.

**An opt-out in Gather means *not from Gather*, not *not from this host*.**

**The argument that carries it:** TNZ's blacklist belongs to the account. A per-host opt-out
therefore leaves every other host sending messages that are **guaranteed to fail**, while
`canReceiveSms` on `PersonInviteStatus` goes on reporting the guest as chaseable. That is
the board lying to the host, which is the failure the invite-status screen exists to avoid.

A second argument points the same way: attribution can be wrong (H1), and a *wrong* per-host
opt-out is worse than a *right* account-wide one.

**⚠ THIS CARRIES SCHEMA — STOP CONDITION 7 FIRES.**

`SmsOptOut` at `d1577b7` is:

- `phoneNumber String`, `hostId String` — **required**, with a required relation to `Person`
  via `host` and `onDelete: Cascade`.
- `@@unique([phoneNumber, hostId])`, plus indexes on each.

Account-wide opt-out cannot be expressed in that model. The required `hostId` and the
composite uniqueness both encode the per-host assumption.

**Per house convention the phase that carries the migration carries nothing else**, and per
the Deploy caveat in `GATHER-BUILD-CONSTANTS.md` the migration must be rehearsed against a
copy of the production database before any deploy carries it. **Stop and report the
migration before writing it.**

Note also that this is a **Do-Not-Touch Zone 7** model and a Zone 5 migration. Both are
binding. The ruling above is the explicit instruction that releases the change; it does not
release anything else in either zone.

## SETTLED — attribution failure must not be a silent discard

**Ruled 2026-09-12. This was to be settled, not deferred.**

**Silently discarding a compliance signal is the current behaviour by accident rather than
by decision.** Audit A step 4 discards any non-keyword body, and steps 3, 5 and 6 each
return `200 OK` having done nothing — on an unparseable number, on no matching prior send,
and on no matching person. None of those was chosen; they are what a Twilio-shaped handler
happened to do. That is the sentence this ticket exists to make false.

**The settlement, in three parts:**

1. **The opt-out is recorded on the phone number, always — attribution or not.** This is
   the compliance-critical write and it must never be skipped because a join failed. A STOP
   whose `MessageID` resolves to nothing is still a STOP.
2. **The person and event linkage is best-effort.** Join on `MessageID`. When it resolves,
   link the opt-out to the person and event and log `SMS_OPT_OUT_RECEIVED` as today. When it
   does not, record the opt-out with the linkage explicitly marked unresolved, so it is
   visible as unreconciled rather than absent.
3. **Nothing is dropped on the floor without a decision having been made about it.** Every
   path that today returns `200` and does nothing must either act, or record why it did not.

**And notice what makes part 1 possible.** It is the account-wide ruling above. Once the
opt-out is keyed on the phone number rather than `[phoneNumber, hostId]`, **an unattributed
STOP becomes writable** — there is no host to resolve, so failing to resolve one stops being
fatal. The account-wide ruling and the silent-discard problem have the same fix. They should
land in the same migration, and they are the reason Stop Condition 7 fires once rather than
twice.

**What remains a genuine product decision, and is NOT settled here:** whether Gather stores
inbound message *bodies* that are not opt-outs. TNZ forward the full message regardless
(answer 4). Today those are discarded at audit A step 4. Storing guest replies is a product
and privacy decision with no schema for it — **raise it, do not decide it.** After this
ticket it is the only thing still being discarded, and it is discarded on purpose pending
that decision.
