# [[GTC-044]] — Settings/Templates: hostId sourced from localStorage fails on direct navigation

**Severity:** Medium
**Escalated:** No

---

### Signal

**Expected**
Navigating directly to `/plan/settings` or `/plan/templates` (e.g. via
bookmark, shared link, or browser back/forward) loads the page with the
correct host identity, regardless of prior navigation history.

**Actual**
Both pages read `hostId` from `localStorage` key `gather_hostId`, which
is only written when the event page (`/plan/[eventId]`) loads. If a user
has not visited an event page in the current browser session, localStorage
is empty and the pages show a dead-end guard ("No host session found" /
"Loading templates...") with no way to recover other than manually
navigating to an event.

**Smallest failing case**
Clear localStorage. Navigate directly to `/plan/settings`. Page shows
dead-end message instead of loading settings.

---

### Reproduce

**Required state**
- Authenticated host user
- Empty localStorage (no prior event page visit in session)
- Multi-actor: No

**Steps**
1. Clear `gather_hostId` from localStorage (or use fresh incognito session)
2. Navigate directly to `/plan/settings`
3. Observe: "No host session found. Please open an event first."
4. Navigate directly to `/plan/templates`
5. Observe: "Loading templates..." indefinitely

---

### Scope

**Fix here:**
- `src/app/plan/settings/page.tsx` — replace localStorage lookup with
  auth session source
- `src/app/plan/templates/page.tsx` — replace localStorage fallback with
  auth session source
- Potentially a shared hook or utility if the pattern is reused

**Do not touch:**
All Do-Not-Touch Zones in GATHER-BUILD-CONSTANTS.md are binding.
The auth/session system itself should not be modified — the fix should
*read from* the existing session/cookie mechanism, not change how sessions
are created or managed.
