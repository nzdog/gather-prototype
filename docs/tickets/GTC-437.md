# GTC-437 - The cron secret stays out of the dev server log

> Filed by Claude Code on 31 Oct 2026, at the founder's request, after
> GTC-432's run. Not built.

## What happens

`test:security` (tests/security-validation.ts) drives two cron routes
on the live dev server with the REAL secret from .env.local in the
query string:

```
tests/security-validation.ts:1709  GET /api/cron/wrap-up-dispatch?secret=<real>
                                   (the "?secret= channel" positive control)
tests/security-validation.ts:1854  GET /api/cron/decide-by-followups?secret=<real>
                                   (the response-body LEAK check)
```

Next's dev server logs every request line with its query string, so
each run writes the secret into the dev log twice (GTC-432's run: two
lines, masked afterwards), and Next's trace file under .next can hold
it too (GTC-412/413's lesson). Runners have masked the log and deleted
.next after the fact. Nothing else does this: test:cron-send-health and
test:nudge-provider-gate pass `?secret=` only to a route called inside
the test's own process (a `NextRequest`, no HTTP), which writes no
server log; the other suites' `?secret=` values are made-up wrong ones.

## Proposed fix (stops it at the source; no masking needed)

Only tests/security-validation.ts changes. No route, no secret
handling in src, no other suite.

1. The LEAK check (line 1854) sends the real secret in the
   `Authorization: Bearer` header instead of the query string. The
   route reads the header first; the request line then carries no
   secret, and Next never logs headers. The check still asks the same
   question of the same 200 body.
2. The "?secret= channel" positive control (line 1709) keeps proving
   that channel, but in the suite's own process: it imports the
   wrap-up-dispatch route's GET and calls it with a `NextRequest`
   whose URL carries `?secret=<real>`, the pattern
   cron-send-health and nudge-provider-gate already use. Same
   precondition as today (no undispatched WrapUpLink, no text retries;
   GTC-274), so it still sends nothing. No request reaches the dev
   server, so nothing is logged. The Bearer positive control stays
   live over HTTP (its secret is in a header).
3. A new static check in the same suite: no `fetch(` in tests/ builds
   a URL holding the real secret (`?secret=` with `serverSecret` or
   `process.env.CRON_SECRET`), with a control proving the detector
   finds a written sample. Wrong, made-up secrets in URLs stay
   allowed.

## Protected zone

tests/security-* is a tweaks-guard PROTECTED path (zone 6): the working
folder, the index and HEAD must each hold it exactly as 21a9577 does.
So this ticket also gives the entry a ruled `plus` (GTC-426's
mechanism) in a commit of its own, or the founder rules another way.
Effort is medium for that reason; the edit itself is small.

## Proof (proposed)

- Red before: on a guarded dev server, run test:security and count
  dev-log lines holding the secret (counted, never printed): 2.
- After: the same run gives 0 such lines and 0 in .next, with
  test:security still 256 of 256 or more (the new static check added),
  and both positive controls still green.
- Break proof: put a `?secret=${serverSecret}` fetch back in a scratch
  copy; the new static check goes red.

## Not proposed here (for the founder)

The cron routes accept the secret two ways, the header and
`?secret=`. Production's scheduler (EasyCron, 27 Oct 2026) sends the
header. Retiring the `?secret=` channel in the routes would close the
same leak for any hosting log that records query strings. That is a
change to src/app/api/cron and its own ticket.
