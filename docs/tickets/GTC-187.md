# GTC-187 — H2: Dual-voice message architecture

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** medium

*Effort level is a proposal from the discovery-report ticket breakdown — run `/effort` manually
before execution.*

### Context

Moment 4 spec §8.4: the thank-you's voice is Gather's by default; Kate can override to her own, or
mix. The mix reuses the Hinge message's architecture **in reverse register**: Gather's specific
gratitude does the systematic work (*thanks for the pavlova*), with room for Kate's line where she
wants one — "the journey's first message and its last are the same instrument." Kate's review pass
before send stands regardless.

Hinge spec §5: the outgoing ask has three movements, seam deliberately visible — (1) Kate speaks
first, fully hers; (2) the handover, Kate introduces Gather; (3) Gather takes over in its own
voice. The guest can tell whose words are whose, and that's the design.

Building this composition pattern once and using it for both the ask (I2, GTC-189) and the
thank-you (H1, GTC-186) avoids two divergent implementations of the same seam-visible idea.

### Scope

**Fix here:**
- A shared message-composition component/service implementing the three-movement pattern
  (author's-line / handover / system's-voice), with per-movement authorship
  (Kate-only / Gather-only / mixed) configurable per use.
- Support both directions: ask-register (Kate's ask, then Gather's roadmap) and thank-you-register
  (Gather's gratitude first, Kate's line optional) — per §8.4's "reverse register" framing.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The actual send/dispatch mechanism — that's I2's (the ask) and H1's (the thank-you) territory;
  this ticket builds message composition, not delivery.

### Dependencies

None — should land before or alongside I2 (GTC-189) so it isn't built twice.

### Acceptance

- [ ] One shared composition service/component handles both the ask and the thank-you's
      three-movement structure.
- [ ] Kate's review-before-send is enforced regardless of voice configuration (the no-show must
      not get "thanks for coming" — §8.4's explicit example).
