# GTC-281 — The payment with nowhere to land

**Status:** Open — **filed, not started.** Filed 2026-09-12 out of
[[GTC-280]]'s investigation. **Branch:** TBD
**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low

## Signal

**Expected**
A completed payment produces the thing that was paid for, whether or not the
payer's browser survives the round trip. The `checkout.session.completed`
webhook exists for exactly this.

**Actual**
Event creation happens **only** in the browser. `useEffect` in
`src/app/plan/new/page.tsx` watches for `?session_id=` on the return from
Stripe and calls `createEventWithPayment`, which posts to `/api/events`. If
the browser never gets back — tab closed, phone dies, network drops, redirect
blocked, back button pressed — the charge has settled at Stripe and **nothing
at all exists in Gather.** No `Event`, no `User`, no `Person`, no row of any
kind. There is no orphan to reconcile from inside the product. The only record
is in the Stripe dashboard.

`POST` in `src/app/api/webhooks/stripe/route.ts` is the mechanism that exists
to cover this, and it does nothing.

**Smallest failing case**
Complete a checkout in Stripe test mode and close the tab before the redirect
resolves. Query for an `Event` with that `payment_intent`. There is none, and
there never will be.

## Evidence

### The webhook, verbatim at `a3927ab`

The verification half is real and correct: it requires the `stripe-signature`
header, requires `STRIPE_WEBHOOK_SECRET`, and calls
`stripe.webhooks.constructEvent` inside a try/catch that answers 400 on
failure. Then:

```
switch (event.type) {
  case 'checkout.session.completed': {
    // Note: Event creation happens via POST /api/events, not here
    break;
  }

  case 'payment_intent.succeeded': {
    break;
  }

  case 'payment_intent.payment_failed': {
    break;
  }

  default:
}
```

Three empty breaks and a bare `default`. **The verification is real; the
handling is a comment.**

### The scanner cannot see this, and that is worth recording

`npm run security:routes` reports the handler as:

```
  POST   /api/webhooks/stripe
    SIGNATURE
    stripe.webhooks.constructEvent
```

That verdict is true and tells you nothing about whether anything happens
afterwards. It is the same category of gap [[GTC-280]] recorded against
`THIRD_PARTY_RECEIPT` on `POST /api/events`: a credential classification
describes the door, not the room. Not a scanner defect — a limit of static
classification, recorded so nobody reads `SIGNATURE` as "handled".

### It used to do something

Git shows this handler once called `syncSubscriptionFromStripe`
(`src/lib/billing/sync.ts`). `scripts/verify-ticket-2.4.ts` still asserts
against that name in three places. The per-event payment rewrite emptied the
handler and did not replace what it did.

`syncSubscriptionFromStripe` is exported and has **no caller anywhere in
`src/`** — verified by grep. Two consequences, and the second belongs to this
ticket only as context:

- The webhook is not merely under-used; it is disconnected.
- Nothing writes a `Subscription` row, so `POST /api/billing/portal` and
  `POST /api/billing/cancel` both answer 404 for every caller. Recorded in
  [[GTC-280]] §4. **Not this ticket's to fix** — the per-event model may
  simply not want subscriptions, and that is a product question.

### The client-side guard doing the webhook's job

`creatingRef` in `src/app/plan/new/page.tsx` exists to stop React Strict Mode
double-invoking `createEventWithPayment`. It is a `useRef` in a browser. The
actual idempotency is the `existingEvent` check in `POST` in
`src/app/api/events/route.ts`, keyed on `stripePaymentIntentId` — which is the
right key and is already in place. Recorded because the fix below reuses it
and should retire the ref.

## Reproduce

**⚠ STOP CONDITION 8 APPLIES.** This completes a card payment. Local Stripe is
in test mode (`STRIPE_SECRET_KEY` in `.env.local` begins `sk_test`, checked
without printing the key), so the money is not real.

**Required state**
- Stripe CLI forwarding: `stripe listen --forward-to
  localhost:3000/api/webhooks/stripe`, with the printed `whsec_…` set as
  `STRIPE_WEBHOOK_SECRET` for the session.
- Auth state: none.

**Steps**
1. Start at `/plan/new`, fill the form, submit.
2. At Stripe, pay with `4242 4242 4242 4242`.
3. **Close the tab before the redirect completes.**
4. Confirm in the Stripe CLI output that `checkout.session.completed` fired
   and the webhook answered 200.
5. Query `Event` for that `payment_intent`.

**Observe:** step 4 shows a 200 from a handler that did nothing; step 5
returns no rows. The charge is settled and Gather holds no record of it.

**Writes:** one Stripe test-mode PaymentIntent and Charge. **Nothing local** —
which is the finding.

## Scope — PROPOSED, not ruled

**Preferred shape: make the webhook the creator.**

- `checkout.session.completed` creates the event idempotently, keyed on
  `payment_intent` — the same key the `existingEvent` check in `POST`
  `/api/events` already uses, so the primitive is chosen and does not need
  inventing.
- The browser's return becomes a redirect into an event that already exists,
  or a short poll while the webhook lands. `POST /api/events` becomes an
  attach-and-continue rather than a create, or is retired.
- `creatingRef` in `src/app/plan/new/page.tsx` retires with it.

**Alternatives, recorded and ranked below the preferred shape:**

- **A reconciliation sweep.** A cron route listing paid Checkout Sessions with
  no matching `Event`, creating or refunding. Cheaper to write; leaves a
  window in which the host has paid and sees nothing. If taken, it is a fourth
  cron route and inherits [[GTC-270]]'s fail-closed `CRON_SECRET` contract —
  do not copy an older cron route's shape.
- **Log and alert only.** Not a recovery path; a place to put one later.

**Zones**

- **Zone 4 — Stripe integration. TOUCHED BY THE LETTER, not merely by intent.**
  `src/app/api/webhooks/stripe/route.ts` is named in the zone. Sign-off
  required and not held. This is the ticket [[GTC-280]] deliberately did not
  reach into.
- **Zone 5 — migrations.** Should not be needed. If the preferred shape wants
  a status column on `Event`, Stop Condition 9 fires.
- **Zone 6 — additive assertions only.**

## Why this waits on [[GTC-280]]

The ordering runs one way only, and it is the reason this ticket is filed
rather than merged into that one.

**A webhook has no browser, no cookie and no session.** It cannot authenticate
the payer, ever, under any design. So a webhook-created event can only ever be
created **unbound** — attached to an address, with no credential returned.

That is precisely the rule [[GTC-280]] is being fixed to establish:

> A payment may CREATE an event and ATTACH it to an address. It may never, on
> its own, return a credential for an account.

Rule [[GTC-280]] first and this ticket inherits a rule it satisfies trivially,
because a webhook has no way to break it. Land this one first and it must
invent an identity-binding rule of its own, in a second place, with no session
to check against — which is how the hole [[GTC-280]] closes reopens somewhere
nobody is looking.

**Founder ruling, 2026-09-12:** *"Your ordering argument is the reason it
waits: a webhook has no browser, no cookie and no session, so it can never
authenticate anyone and must create unbound — which is this ticket's rule
arriving from the other side. Rule this first and the webhook inherits it.
File only."*

## Acceptance — sketch, to be completed when this is scheduled

**Test gate** — severity High: test-first required.

**Assertions**
- [ ] A `checkout.session.completed` delivery for a paid session with no
      corresponding `Event` creates exactly one `Event`.
- [ ] **Delivering the same event twice creates exactly one `Event`** —
      Stripe retries, and an at-least-once delivery guarantee is the whole
      reason `payment_intent` is the key.
- [ ] The webhook-created event is **unbound**: no `Session` row, no cookie,
      no credential of any kind returned. This is [[GTC-280]]'s invariant
      restated on the second creation path, and it must be asserted here
      rather than assumed from there.
- [ ] The browser-return path and the webhook path racing produce one event,
      not two.
- [ ] A delivery with a bad signature still answers 400 and creates nothing —
      the existing behaviour, asserted so the fix cannot weaken it.

## Unknowns

1. **Whether the browser path should be retired or kept as a fast path.**
   Keeping both means two creation paths and a race; retiring the client path
   means a poll or a wait on the success screen. Product decision.
2. **What the host sees while the webhook is in flight.** Stripe delivery is
   usually sub-second but is not guaranteed.
3. **Whether any charge has already been lost.** Answerable only from the
   Stripe dashboard, which the founder holds. Worth checking before this is
   scheduled: it decides whether this is a latent defect or an outstanding
   debt to a real person.
