### Follow-up 2 (read only): can a three-date event get the one-day line?

Not from its dates. The Sessions card picks its line in one place
(`src/components/sessions/Moment1Sessions.tsx`, lines 92 to 94 and 243):
it counts the dates from the event's first to its last date, each read as
its NZ calendar day (GTC-479's date rule), and shows "Is this more than
one meal? ..." when there is more than one. The invitation's "from ... to
..." line reads the same two dates the same way, so for one reading of an
event's dates the two never disagree.

It can show the one-day line on a 25 to 27 Dec event in one way: the
card reads the event's dates once, when it first draws, and again only
after an action on the card itself. It does not read them again when the
dates change elsewhere (the Edit event box on the plan page, another tab,
a page the phone restores from memory). An event first made as one day
and then given its range keeps the one-day line until the page is
reloaded. (An end before the start would also give it, but the edit route
refuses dates that run backwards.) Nothing is fixed here.

## The plan (as approved, 26 Nov 2026)

**A. The one call is told the sessions.** With the switch on and sessions
on the event, `buildPlanGenerationInput` reads them (sorted by GTC-479's
order) and the user prompt gains one block. Each session has a short
label of its order (S1, S2, ...), its name, its date (left out when the
name is only the date), and how many are coming, with the adults and
children (the founder's change A below). The AI gives every dish a
"session": a label, or "whole". It never sees a database id. The label is
read back after trimming and in capitals ("s2 " is S2); "whole" is the
whole event; anything else, or nothing, is the whole event and counted.
The system prompt does not change.

The block, word for word, as the code builds it for fixture 2 below:

```
SESSIONS (this event has more than one meal; plan each one):
- S1: Christmas Eve dinner, Thu 24 Dec, 9 coming (5 adults, 4 children)
- S2: Christmas lunch, Fri 25 Dec, 17 coming (11 adults, 6 children)
- S3: Christmas evening, Fri 25 Dec, 15 coming (9 adults, 6 children)
- S4: Boxing Day brunch, Sat 26 Dec, 13 coming (7 adults, 6 children)
- S5: Boxing Day dinner, Sat 26 Dec, 15 coming (9 adults, 6 children)

How to plan the sessions:
- Every item gets a "session": the label of the session it is eaten
  at (S1 to S5), or "whole" for something bought once and used
  across sessions (a stock of drinks, ice, snacks to graze on). Use
  no other value.
- Size each item for its own session's headcount, not the whole
  event's.
- Kate's selections are for the event as a whole: put each where it
  fits best (the main roasts at the main meal), not at every session.
- Each session should make sense on its own as a meal of its kind. A
  lighter session (a brunch, a leftovers dinner) needs fewer, simpler
  items than the main meal. The plan size guidance is for one main
  meal.
- Never list the same item twice in one session. List an item in two
  sessions only if it is really eaten at both; prefer a note
  ("leftover ham from S2") to buying the same thing again.
- Cover each dietary requirement at every session that has a meal.
- A session with 0 coming gets no items.
```

How it varies, all in the code: "(S1 to S5)" reads "(S1)" for one
session and "(S1 or S2)" for two; "1 adult", "1 child" in the singular;
the example says "S1" when there is only one session. When the event's
households name no one (its count then comes from its guest count), no
session carries a count and the two headcount lines ("Size each item
..." and "A session with 0 coming ...") are left out. The headcounts are
counted from the same people as the event's totals (named people, kids by
role CHILD, each household's little ones), less those marked as not at the
session; the adults and children are given only when they add up to
`sessionHeadcounts`' figure for that session, else the one number alone.

The reply's one new field (only while the block is in the prompt), on
each item after `dietaryTags`:

```
"session": string           // S1 to S5, or "whole" — see SESSIONS above
```

The reply to the screen gains one small object, only when sessions were
in the prompt: finalize-plan's `plan.sessionDraft` and regenerate-plan's
`sessionDraft`, each `{ "sessions": 5, "unplaced": 0 }`. A dish that
matched no session writes one server log line naming the call, the event
and how many (missing, unknown, gone).

**B. The write.** Each drafted dish is written with its session, in the
same one transaction as today (`applyPlanSections`). Inside it, the
event's sessions are read again: a dish whose session was removed while
the AI answered goes on the whole event, counted ("gone"). What a redraft
may replace (`disposableItemWhere`) does not change. Jobs stay on the
whole event.

**C. regenerate-plan**, both scopes, gets the block from the same
function; the rows it keeps are described with their session label ("S2,
Mains: Glazed ham (4 kg)").

**D.** Switch off, or on with no sessions: no new query, no block, no new
key; the prompt, the rows and the reply as before. Proved against main's
own code in the new suite.

**E.** The cap stays 16384 unless a measured reply passes 13,107 tokens
(the largest that leaves 25 per cent headroom). It can go no higher than
21,333 (the library's limit); a reply needing more than about 17,000 is a
stop, not a raise.

**F.** Tests never call the AI: the AI library's call is replaced by
canned replies inside the suite's own process.

**The decisions** (ruled below): 1, each session its own small menu
sized to its own headcount, from Moment 2's one set of answers, no new
questions; 2, drinks, ice and nibbles on the whole event, bought once,
plates and napkins stay reminders; 3, the jobs on the whole event; 4,
nothing redrafts by itself, Regenerate picks up changed sessions; 5, no
special case for the sample copy; 6, W0, no new words; 7, 14 real calls.

**W0, no new words.** The option kept for the gate, if any measured run
has a dish that fits no session (the founder's ruling 6):

- W1: "1 dish didn't fit a session, so it's under Whole event. You can
  move it."
- W2: "{n} dishes didn't fit a session, so they're under Whole event.
  You can move them."

**Source:** `src/lib/ai/plan-input.ts`, `src/lib/ai/prompts.ts`
(`buildPlanGenerationPrompt` and its new block only),
`src/lib/ai/plan-write.ts`, `src/app/api/events/[id]/finalize-plan/route.ts`
and `src/app/api/events/[id]/regenerate-plan/route.ts`. No new source
file, no route, no migration. Zone 8: one script line in `package.json`.
Near zone 1 only in that the routes' sign-in call is unchanged.

**Tests:** a new suite `tests/sessions-drafting-test.ts`
(`test:sessions-drafting`, gate position 204). Four older checks moved,

S1 (names `src/lib/ai/plan-input.ts` as the nineteenth reader of the
