# GTC-212 — STUB: Re-derive GTC-206's fix (INVESTIGATION, not a fix ticket)

**Status:** Open — stub, needs full scoping when pulled | **Effort:** TBD

*Source: `docs/04_roadmap/moment4-hinge-report-accuracy-audit-2026-08-04.md` — GTC-206
**REVISED**. The mechanism is real; **the ticket's stated fix cannot work.***

### Scope

GTC-206's *mechanism* is confirmed: `restoreFromRevision` deletes every team
(`workflow.ts:942-944`), `PersonEvent.team` is `onDelete: SetNull` (`schema.prisma:195` — a real
Postgres action, confirmed in the migration DDL, not Prisma emulation), teams are recreated with
fresh cuids (`workflow.ts:978`), and **nothing repoints the memberships** — `workflow.ts` contains
zero case-insensitive occurrences of `personevent`, and the route does nothing after the call.

**The ticket's proposed fix cannot work.** GTC-206 says `teamIdMap` means *"the data needed to
remap memberships is already in hand at the point of the gap."* Three independent reasons that
is false:

1. **The snapshot has no members.** `createRevision`'s capture (`workflow.ts:809-824`) includes
   `coordinator` and `items` but **not** `members` — though the relation exists
   (`schema.prisma:122`).
2. **The live values are already destroyed.** `teamIdMap` is declared at `workflow.ts:973` and
   populated at `:991` — **49 lines after** the delete at `:942` that nulled them.
3. **The key is wrong.** `teamIdMap` is keyed by *snapshot* team ids; a pre-delete
   `PersonEvent.teamId` points at *current* ids. After any prior restore these diverge and the
   remap silently drops every membership.

**Worse, and unfiled:** the "Checkpoint before restore" (`workflow.ts:919`) uses the same
members-less capture, so the comment at `:903` — *"nothing is lost by moving forward"* — is
untrue for team membership. **The loss is not undoable by restoring the checkpoint.** That puts
the root cause in `createRevision`, not `restoreFromRevision`: it cannot restore what was never
recorded. Any real scope must include both. (Also: assignments *are* restored while memberships
are not, producing a state the same-team assign gate would itself reject.)

**GTC-206's own citations have drifted** and will mislead whoever picks it up — it cites
`workflow.ts:887`, `:916-930`, `:919` and `schema.prisma:188`; the current locations are `:942`,
`:973-991`, `:974` and `schema.prisma:195`. Re-verify every line before quoting it.

**What remains unprovable without a live DB:** that a real restore leaves zero non-null `teamId`
(the DDL and code path are unambiguous, but **no test has ever executed this path**), and whether
any user has hit the resulting 400. Repro requires a **scratch database** — it mutates data. A
read-only production check settles whether this is latent:

```sql
SELECT "eventId","createdAt" FROM "AuditEntry" WHERE "actionType" = 'RESTORE_REVISION';
-- then, per eventId:
SELECT count(*) FILTER (WHERE "teamId" IS NOT NULL) AS on_a_team, count(*) AS total
FROM "PersonEvent" WHERE "eventId" = '<id>';
```

Zero rows on the first query closes GTC-206 as latent.

### Needs full scoping when pulled

**This is an INVESTIGATION ticket. It deliberately carries no acceptance criteria for a fix.**
Writing fix acceptance against an un-re-derived mechanism is precisely what made the original
GTC-206 unbuildable — its acceptance was written around a `teamIdMap` remap that cannot work.

When pulled, the work is: re-derive the correct fix from current code (starting from
`createRevision`'s capture, not `restoreFromRevision`'s replay), establish repro on a scratch
DB, run the latency check above, and **then** file a scoped fix ticket with acceptance criteria.
Correct or supersede GTC-206's stale citations in the same pass. **Do not write a fix from this
stub.**
