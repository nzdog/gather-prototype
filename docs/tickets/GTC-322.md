## The state

**`Event.sentAt` has been written since [[GTC-169]] (A3a) by a press that sent nothing.** That press
locked the plan, stamped every `PersonEvent.sentAt` ([[GTC-196]] / A3b), set the invite anchors and
wrote `SEND_PRESSED`. It dispatched no message, because no dispatcher existed — [[GTC-189]] slice 5
is what built one.

So an event pressed before slice 5 is in a state the new model has no name for:

- `Event.sentAt` **set** — the plan is locked and the board treats it as sent.
- `PersonEvent.sentAt` **set for everyone**, by the `updateMany` slice 5a deleted.
- `OutboundMessage` rows: **none.** The table did not exist until slice 4a.
- And **nothing will ever create them.** Slice 5e's `enrolMiniSends` deliberately requires an event
  the new press has written ask rows for, because *a mini-send is a send after a send, and a legacy
  pressed event never sent — so there is nothing for a late arrival to be late to.*

**Measured in `gather_dev`, 2026-09-19:** 8 events carry `sentAt`. All 8 have zero ask rows. 109
`PersonEvent` rows carry a `sentAt` that no provider acceptance ever produced.

---

## ⚠ Why it is a question and not a fix

**Because the obvious fix is the defect slice 5e just closed.**

Slice 5e's sweep, keyed on `sentAt` alone, treated every recipient of every such event as a late
arrival and enrolled them. On its first run that created **20 rows across four real boards** — three
security-test events and `GTC-192 replay — arrival`, a seeded demo board — and the dispatcher claimed
and attempted a send for all 20. Nothing was delivered, and the two reasons were **a broken Resend key
and reserved email domains. Both luck.**

**So "just enrol them" is exactly what was tried by accident, and it was wrong.** On a real deployment
it is every guest of every previously-pressed event invited a second time, from a lock they were told
was final — against a press ruled ONE ACT, NO RECALL (Hinge §2, ruled gap #1).

## ⚠ FOUR FINDINGS, EACH MEASURED IN A ROLLED-BACK TRANSACTION, 2026-09-19

The probe wrote all 86 rows inside `$transaction`, read the eight boards from inside it, and threw
to roll back. `OutboundMessage` held 0 rows before and 0 after. That is Zone 5's rehearsal
technique — *"probe behaviour in transactions that are rolled back"* — applied to a data change.

### ⚠ 1. THE BACKFILL DOES NOT STOP THE CHASE, WHICH IS THE RULING'S OWN STATED REASON

`findNudgeCandidates` filters `PersonEvent.sentAt: { not: null }` and **nothing in `src/lib/sms/`
reads `OutboundMessage` at all.** Measured in the probe: after all 86 rows are written, **109
`sentAt` stamps are still set.** So slice 8 chases exactly the same people it would have chased
before.

**The record is repaired and the defect is not.** To stop the chase, shape 3 has to do one of two
further things, neither of which is ruled:

- **clear the 109 `PersonEvent.sentAt` stamps** — which is consistent with ruling G (*the clock
  starts at provider acceptance*, and none happened) and with [[GTC-321]]'s shape 2 ruling of the
  same day (*record the contact, start no clock*), but is a second data change on live rows that
  three surfaces read; or
- **teach the chase to consult the outbound record**, which is slice 8's and a different ticket's.

⚠ **This is the measurement-attributed-to-the-wrong-cause family, caught before the fix rather than
after:** the ticket's own framing said backfilling the rows answers the slice 8 exposure, and it
does not. The rows and the stamps are two different assertions and only one of them is being
repaired.

### ⚠ 2. SHAPE 3 CANNOT BE "DATA ONLY, NO SCHEMA", BECAUSE THERE IS NO HONEST CHANNEL

`OutboundMessage.channel` is a **non-nullable enum of two**, and its docstring says what it means:
*"EMAIL or TEXT, decided by `chooseAskRoute`/`chooseChaseRoute` at the press and then stored."* For
a legacy row **no chooser ever ran**, so every available value asserts a routing decision that was
never taken:

- `EMAIL` by convention is the value the founder refused by name at [[GTC-325]] — *"a column saying
  EMAIL about a person with no channel is the false-sentence family, and this ledger has caught it
  four times."*
- *The channel the chooser would answer today* is the same false sentence with a subtler
  provenance: it dates a decision to a press that did not make it.

**The honest value is NULL, and NULL does not exist until [[GTC-325]]'s ruled migration lands.**
⚠ **So GTC-325's nullability is a precondition of this ticket, and the build order 322-then-325 is
the wrong way round.** The probe wrote `channel: 'EMAIL'` to measure the BOARD consequence, which
is channel-independent; it is not what the migration may write.

### ⚠ 3. THE BACKFILL FLIPS `enrolMiniSends`' PREDICATE ON ALL EIGHT EVENTS

That sweep keys on *an ask row exists* precisely to refuse these events — *"an event with `sentAt`
and no rows was pressed by machinery that did not send."* **After the backfill they all have ask
rows.** Measured: the events the sweep would consider go from **1 to 8**.

✅ **And it would enrol ZERO of them** — because the backfill's population is exactly the sweep's
population, so every recipient it would consider already has a row. **That is a property of the two
predicates being identical, not a safety margin.** If they ever differ by one person, the cron
sends that person a real invitation from an event pressed months ago — which is the incident slice
5e already had once, at 20 rows across four real boards.

**So the backfill and `enrolMiniSends` must read ONE predicate**, called from one place, rather
than two spellings that agree today.

### ✅ 4. THE BOARD DOES NOT MOVE — AND IF IT IS MADE TO, IT IS 18 PEOPLE AND NOT 109

Measured both ways in the rolled-back probe:

- **As built (`PREDATES_SENDER` maps to `null`): 0 of 8 boards move.** No strip changes colour.
- **If the code mapped to a red: 6 of 8 boards move and 18 people go from *with Gather* to *needs
  you*.** Not 109, and the reason is slice 7a's own design: the delivery branch sits BELOW the
  three response branches, because *an answer is proof the ask arrived*. **95 of the 118 people on
  those boards have already answered**, so a delivery failure cannot redden them. Only the 18 who
  have not answered move, plus the 5 already red stay red.

⚠ **AND THE COLOUR CANNOT BE CHOSEN WITHOUT CHOOSING A MECHANISM.** The mapping `Record`'s value
type is `'UNREACHABLE' | null`, so a withholding may say *nowhere to send* or say nothing:

- **`UNREACHABLE`** gives the red, with the why-line *"nowhere to send"* — **false** of people who
  hold live addresses. Refused rather than deferred.
- **Widening the `Record`** so a withholding may also mean `NOT_DELIVERED` gives the red with
  *"never got it"*, which is **true** of them — 7a named that reason for three mechanisms because
  they are *"one fact to the host: it did not arrive"*, and never-sent is a fourth of the same
  kind. It changes the shape of a mapping [[GTC-325]]'s scope reserves to a ruling.
- **`null`**, as built: the record is repaired and no strip moves.

⚠ **AND A RED HERE OPENS SLICE 7b's DOOR ON 86 PEOPLE.** `doorOffered` is true for both reds, so
red puts a one-press *"send it again"* on 86 guests across eight legacy boards — three of them
security-test events and two seeded demo boards ([[GTC-192]]'s). One press would send a real
invitation from an event pressed months ago. **That may be exactly the affordance a host wants for
these people; it is not a side effect a record repair should acquire unruled.**

**Built in the order the findings gave, which the founder ruled over the one first given:**

1. ✅ **[[GTC-325]] first** — `OutboundMessage.channel` nullable, applied (`9dd4648`). Nothing here
   was writable honestly before it.
2. ✅ **One predicate, shared.** `askRowPopulation` in `ask-preview.ts`, asked by `pressSend`,
   `enrolMiniSends` and this backfill. The two-step rule — *would the press message them*, then
   *do they hold a link* — was spelled three times; `pressWillMessage` was shared and the split
   built on it was not, and it is the split that decides who gets a row.
3. ✅ **The colour is `null`** — shipped at `214403f`, on the founder's ruling that a red would put
   a one-press *"send it again"* on 86 guests across eight legacy boards.
4. ✅ **The 109 stamps are cleared**, in the same transaction as the rows.
5. ⚠ **`scripts/backfill-gtc322.ts` — WRITTEN, REHEARSED, NOT RUN against `gather_dev`.**

### ⚠ IT IS A SCRIPT AND NOT A MIGRATION, WHICH IS A DEPARTURE FROM THIS REPO'S PRECEDENT

`gtc202_backfill_send_clocks` and `gtc312_backfill_phone_number` are each one `UPDATE` authored
into a migration Prisma generated empty. **Half of this could be written that way and half could
not.** The stamp clearing is expressible exactly — the script prints the SQL on every run, and the
suite asserts the printed predicate matches the executed one. **The row population is not:** who
gets a row is `chooseAskRoute`'s answer, a ladder over household roles, picked contacts, mute
switches, the host exclusion, two opt-out facts and a phone predicate. **A SQL approximation of the
chooser is a second definition of the chooser**, which is the shape this ticket set has spent a
week refusing. Both halves run in one transaction, which is what *"in the same migration"* was for.

### ⚠ THE DRY RUN FOUND THE DESIGN WAS WRONG, AND THAT IS THE FINDING OF THE BUILD

It was written to write rows for the `ready` population only — the people holding a link. The dry
run showed **only 20 of the 86 hold a PARTICIPANT token; the other 66 read `AT_PRESS`.**

**Writing rows for the 20 alone is worse than doing nothing.** All eight events would gain ask
rows, which **flips `enrolMiniSends`' event predicate** from refusing them to considering them —
and the sweep would then find 66 people with no row, count them `awaitingLink`, and **wait for a
token.** The moment [[GTC-316]] mints one, the sweep enrols them and the drain sends **66 real
invitations from events pressed months ago.**

⚠ **That converts a closed door into a door held shut by a missing token** — a new exposure created
by the repair itself, and the same incident slice 5e already had once at 20 rows. Corrected: the
row population is the whole intended set. A row for an `AT_PRESS` membership invents no routing
decision, because `PREDATES_SENDER` claims nothing about routing — it says the event predates the
press, which is equally true of somebody who never held a link.

- ✅ **`findNeverAttempted` returns 0 of them.** Every row is born withheld; nothing can send.

- ✅ **0 of 8 boards move.** Every summary is identical before and after, because

- Clone dropped. `gather_dev` still holds 0 outbound rows and 109 stamps.

## The three shapes, and none is obviously right

1. **Leave them.** Their guests are never messaged by Gather. The host either already told them by
   hand — which is what the old press's two buttons said she had done, and which [[GTC-321]] is about
   — or they were never told at all. Nothing sends, nothing surprises anybody, and the board goes on
   claiming they were sent to.
2. **Re-press them deliberately**, as a one-off, per event, with the host's hand on it. Honest about
   what is happening and it needs a surface — she is pressing a second time on an event whose lock
   says once.
3. **Backfill the rows as already-finished**, so the model is consistent and nothing sends: an
   `OutboundMessage` per recipient, `withheldAt` set with a why naming this ticket. The board stops
   lying about a send that never happened, the chase stays off them, and **nothing is delivered.**

⚠ **Shape 3 is the executor's lean and it is NOT a recommendation**, because it writes a row asserting
a withholding that no gate produced, and `withheldWhy` is documented as carrying OUR reason for not
sending — which here would be *"this event predates the sender"*. That may be exactly right or it may
be putting a false sentence in a column separated from `providerError` specifically to keep it true
(ruling AN). **That is the founder's call and it is the whole of this ticket.**

## ⚠ What makes it more than tidiness — AND WHY IT IS HIGH

**`PersonEvent.sentAt` is set for 109 memberships that no provider ever accepted**, and ruling G makes
that column mean *"this person's provider accepted their message."* So on every legacy event the column
means something it was never true of.

The consequence is not hypothetical: `findNudgeCandidates` filters `sentAt: { not: null }` and anchors
the whole cadence on it. **So the chase is live on those events, counting from a send that never
happened** — and slice 8 will chase those guests about an ask they were never sent, unless this is
ruled first.

⚠ **THAT IS WHY IT IS HIGH, AND IT IS THE WHOLE OF THE SEVERITY ARGUMENT.** Nothing is wrong for a
guest today, because nothing chases anybody — slice 8 is unbuilt. **The defect is fully formed and
waiting.** On the day slice 8 lands, `findNudgeCandidates` will read 109 memberships whose `sentAt`
says a provider accepted a message, and chase those people — by text or email, twice — about an ask
that was never composed, never sent, and whose contents Gather does not have.

**So this must be ruled BEFORE slice 8, not before a deploy.** A ticket that reads as housekeeping
gets scheduled after the thing it blocks, which is exactly the failure this note exists to prevent.
⚠ **`type` was changed from `chore` to `bug` for the same reason** — the word at the top of a ticket
is the first thing that decides when it is read.

⚠ **WHETHER IT IS A FORMAL PRECONDITION OF SLICE 8 IS NOT CLAIMED HERE**, and no `blocks` edge is
asserted. [[GTC-296]] carries one for that slice by an explicit ruling; this ticket has been raised to
High and re-framed but not ruled, and adding the edge would be the executor deciding an ordering. It
is named as reaching slice 8 so the question is unavoidable when slice 8 is scoped.

⚠ **AND THE POPULATION IS NOT SMALL RELATIVE TO THE DATABASE:** 109 of 335 memberships — roughly a
third of every membership in `gather_dev` — carry a `sentAt` that ruling G's definition makes false of
them.
