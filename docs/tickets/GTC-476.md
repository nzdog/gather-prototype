# GTC-476 - Multi-day events: the scoping

The scoping was read-only and was done before this file existed. This file is
the record of it. It holds the founder's rulings for the whole multi-day build,
word for word, as written into GTC-477's brief on 23 Nov 2026.

The scoping found three faults that sit under every later change. GTC-477 fixes
them first (Q14).

## The founder's rulings on multi-day (23 Nov 2026), verbatim

```
MY RULINGS ON MULTI-DAY (23 Nov 2026)
- Q1: several sessions per day (lunch and dinner on the 25th). The
  screens say "session".
- Q2: one AI call drafts all sessions, now, as a measured experiment.
- Q4: who comes to which session ships together with sessions.
- Q8: a dish's decide-by counts back from its own session's date.
- As recommended by the scoping: Q3 one invitation for all
  sessions; Q5 still one $25 event; Q7 sessions named on a card on
  Moment 1's summary; Q9 an item may have no session ("whole
  event"); Q10 sessions survive "invites only"; Q11 a date change
  keeps sessions and flags those outside the range; Q12 a shared dish
  splits only within one session; Q13 changing a dish's session
  counts as changing the ask; Q14 fix the three faults first; Q15
  template dates later, its own ticket.
- The build order: GTC-477 these faults; GTC-478 foundation (one
  migration for the Day order column and per-session attendance,
  Day write routes, the switch that hides session screens until
  release); GTC-479 Moment 1; GTC-480 Moments 2 and 3; GTC-481 guest
  answers per session; GTC-482 drafting; GTC-483 release.
```

## The founder's ruling on the order (26 Nov 2026), verbatim

Given in GTC-483's brief. It changes the last two steps of the build order above
(GTC-482 drafting, then GTC-483 release): the release now comes first.

```
MY RULING ON THE ORDER (26 Nov 2026)
GTC-483 (this release) goes before GTC-482 (drafting all sessions in
one AI call). Hosts get multi-day with today's drafting: the plan
drafts as it does now and the host moves dishes into sessions
herself. GTC-482 follows as an upgrade. Record this in GTC-476.md
too.
```

## The founder's rulings for GTC-482 (26 Nov 2026), verbatim

Given in GTC-482's brief, for that ticket.

```
- One call stays one call. Never one call per session, never a
  second call to sort dishes into sessions. If the measurements say
  one call cannot do it well, the answer is to stop and tell me, not
  to add a call.
- The repo's experiment method makes adoption its own ticket. For
  speed, adoption rides this ticket and this branch, after my word at
  the decision gate below. Record that as a dated exception.
```

The dated exception (26 Nov 2026): for [[GTC-482]] only, the adoption
step of the experiment method (gather-experiment-methodology, step 7:
"Adoption is its own ticket") rides GTC-482 and its branch
`experiment/gtc-482-sessions-drafting`, after the founder's word at its
decision gate. Every other experiment keeps adoption as its own ticket.

## The three faults it found (fixed in GTC-477)

```
1. The item-create POST (src/app/api/events/[id]/teams/[teamId]/
   items/route.ts) never reads a day, so a day picked when adding an
   item is thrown away. Accept dayId, with exactly the
   belongs-to-this-event check the item edit route already does
   (security suite part GTC-403). Extend GTC-403's checks to the
   create route; weaken none.
2. The coordinator page's day list (src/app/c/[token]/page.tsx,
   around line 921) offers only the first item's day. Offer every
   Day of the event, in date order, plus "All days" for none. Say
   where the page gets the event's days, and whether the coordinator
   route already returns them. If it does not, adding them to that
   route's reply is allowed; no new route.
3. src/lib/ledger.ts says dayId "never reaches a guest", but the guest
   page shows the day. Make the day an ask field (Q13). Say in the
   plan exactly what changes for a host after the send: which edits
   will now ask "why", and confirm that nothing new is sent (the
   notify hooks are empty today).
```
