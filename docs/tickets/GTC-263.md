# GTC-263 — The three-path host resolution survives, and one site only runs path 1

**Status:** Open — filed 2026-08-29 out of [[GTC-256]] phase 5 | **Severity:** Medium
**Branch:** `feat/moment-one-redesign`

*Filed on closing [[GTC-256]]. Its open question 4 asked whether the three-path host
resolution survives Ruling 10. **It does** — the investigation is recorded there. This ticket
carries what that answer leaves: an unblocked extraction question, and one real gap.*

---

### Signal

**Expected**
"Whoever the host is, they are not a recipient of their own ask" holds wherever it is checked.

**Actual**
It is checked three different ways in three places. Two sites resolve the host by three
identity paths; a third uses one of them. Under the sequence below, the one-path site messages
the host.

**Smallest failing case**
A host who is also captured as a guest under a second `Person` row, then claims that name
through the magic-link flow, is a wrap-up thank-you recipient on her own event.

---

### What GTC-256 established, so this ticket does not re-derive it

**The three paths do NOT collapse.** GTC-256 Ruling 10 pins the host's `PersonEvent` to
`Event.hostId`'s existing `Person`, which makes **path 1** (`personId === Event.hostId`)
resolve on every event created after its phase 2. It does not retire paths 2 or 3.

**Path 3 catches a row the other two cannot, and the route to it is shipped.**
`POST /api/auth/verify`'s claim branch does

```
await tx.person.update({ where: { id: personId }, data: { userId: user.id } });
```

— an **unconditional** link, with no check for another `Person` already carrying that
`userId`. `Person.userId` has only `@@index([userId])`, no `@unique`. So one human can become
two `Person` rows sharing one `User`: signed up as the host (Person A), separately captured as
a guest (Person B), then claiming B.

Proven against the database on 2026-08-29, not inferred:

```
BEFORE the claim   path 1: A(host)   path 2: A(host)   path 3: A(host)              union 1 row
AFTER the claim    path 1: A(host)   path 2: A(host)   path 3: A(host), B(claimed)  union 2 rows
```

**Path 2 is largely a cache of path 3.** Nothing creates a `role: 'HOST'` `PersonEvent` whose
`personId` differs from `Event.hostId` — the clone route and the seed both write it *for*
`Event.hostId`, and nothing writes a `PersonEvent` for `Event.coHostId` at all. The only
producer is auto-assign's own promotion write, which promotes rows found by paths 1 and 3.

---

### The two things this ticket carries

**1. The extraction question, now unblocked.** `src/app/api/events/[id]/pre-flight/message/route.ts`
declined to extract the resolution into a shared helper on two grounds: it would edit GTC-188's
closed deliverable, and GTC-256 might delete the need entirely. **The second ground is
discharged** — the need is permanent. The first stands. Two copies of a security-shaped
predicate, plus a third partial one, is now a standing duplication rather than a deliberate
wait. The comment in that route has been updated to point here.

Sites: `resolveHostMemberships`-shaped blocks in
`src/app/api/events/[id]/people/auto-assign/route.ts` and
`src/app/api/events/[id]/pre-flight/message/route.ts`.

**2. ⚠ `selectWrapUpRecipients` runs path 1 only — and that is a real gap.**
`src/lib/wrap-up.ts` filters `pe.personId !== hostId`. GTC-256 phase 3 recorded this as
"CLOSED by Ruling 10", which is true *for the host's own row* and not for the second row path 3
finds. Under the claim sequence above, **the host receives a wrap-up thank-you addressed to her
guest identity** — which GTC-256 Ruling 5 forbids outright ("no wrap-up thank-you").

Unreachable in current data — `Person` rows sharing one `userId` measured **0** on 2026-08-29 —
so this is latent, not live. It becomes reachable the moment the claim flow is used by someone
who is already a host.

*Note the asymmetry that makes this the sharp end:* the auto-nudge and decide-by finders are
closed by the PARTICIPANT-token gate (GTC-256 Ruling 8), which the second row would **not**
pass. Wrap-up has no token requirement — `WrapUpLink` denormalises the contact details at
creation — so it is the one send path where the second row is live.

---

### Scope

**Fix here:**
`src/lib/wrap-up.ts` (`selectWrapUpRecipients`), and whichever module the extraction lands in.

**Do not touch:**
All Do-Not-Touch Zones in GATHER-BUILD-CONSTANTS.md are binding — Zone 2 (magic-link auth)
covers `POST /api/auth/verify`, which is where the duplicate originates.

⚠ **Do not "fix" this by adding `@unique` to `Person.userId`.** That is a schema change with a
migration on a column that already has non-unique data semantics elsewhere, and it would make
the claim flow throw rather than link. Whether one `User` may own several `Person` rows is a
model question, not a constraint to bolt on — see the unknowns.

⚠ **`src/lib/eligibility/host-exclusion.ts` is MESSAGE-ONLY** (GTC-256 Ruling 5) and
`src/lib/assignment/same-team.ts` is its assignment-side counterpart. If the extraction lands
near either, the boundary in `tests/child-assignment-eligibility-test.ts` is binding.

---

### Unknowns

1. **Should one `User` be able to own several `Person` rows at all?** If the answer is no, this
   is an auth-flow bug and the three paths collapse after all. If yes, path 3 is permanent and
   the extraction is the whole of the work. **Do not decide this by inference** — it reaches
   Zone 2.
2. **Does `personForUser` (`src/lib/auth/actor.ts`) pick the right row when two exist?** It is
   `findFirst` with **no `orderBy`**, so the answer is non-deterministic. GTC-256 recorded this
   as a residual it could not reach; path 3's survival makes it reachable.
