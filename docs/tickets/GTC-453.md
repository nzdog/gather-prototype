# GTC-453 - Listening report, Level 1

**Status: built and committed (b96ce73), approved by the founder 5 Nov 2026.** Not deployed; it needs no deploy.

## What and why

The founder wants to look at finished gatherings, almost every day at the start, and feel they
know how Gather is working for people. The principles, in the founder's words: *listening, not
watching*, and *no one is in the picture*. The question to answer: *where is the biggest
friction point?*

Level 1 answers it from times Gather already saves. Nothing new is recorded. This ticket is one
read-only report script the founder runs from their own computer. It is run-sheet steps L1-1 to
L1-10; this ticket covers the build (L1-1 to L1-7).

## Decisions it follows (founder, 5 Nov 2026)

  sections. A, planning finished: the invitations are sent; a draft with no host save for 14
  days and nothing sent is "stopped". B, gathering finished: its NZ day has ended (the app's own

## How a host save is placed in a Moment

Host saves are `AuditEntry` rows with actorKind HOST or COHOST.

- Before `EventSetup.planApprovedAt`, by what changed: Event, PersonEvent, Household are
  Moment 1; Item, Team, PlanRevision, Conflict are Moment 2. Anything else (for example an
  Assignment before approval) is counted as "fits no Moment", never guessed.
- From plan approved to the hold (`Event.transitionedToConfirmingAt`): Moment 3.
- From the hold to the send (`Event.sentAt`, column `inviteSendConfirmedAt`): Moment 4.
- After the send: after-send changes. A legacy FROZEN event with no sentAt counts as sent at
  frozenAt, as `isSent` in `src/lib/lifecycle.ts` does.

The targetTypes written in code today (by literal) are Item, Assignment, PersonEvent, Event,
Team, Household, PlanRevision, Conflict. All but Assignment are mapped before approval.

## Known limits, said plainly

- **Stalls are estimates.** A host who looks and leaves without saving is invisible. Level 2's
  step log is what sees that.
- **"Time to everyone sorted" is an estimate**, labelled as one. A gathering counts as sorted
  when no assignment is PENDING and every invited person has answered. The time is the latest
  guest reply (the board's own reply actions, `src/lib/glance/rewind.ts`, plus RSVP and
  attendance stamps) minus the send.
- **Reply time** uses `PersonEvent.sentAt`, which since GTC-189 is each person's provider
  acceptance, so it measures from when the message was accepted, not from the press.
- **It loads every non-demo gathering** and their host saves in one read. Fine at today's
  size; if it ever gets slow, narrow the queries to the window.

## How the founder runs it

Staging first, then production. From the repo folder. Every command names the environment
(`-e`) and the service (`-s`), so it never runs against whatever the folder happens to be linked
to. Replace `<APP_SERVICE>` with the name of Gather's app service in Railway, and
`<LAUNCH_DATE>` with the launch date written as YYYY-MM-DD.

The standard daily run, staging then production:

```
railway run -e staging -s <APP_SERVICE> npx tsx scripts/listening-report.ts --exclude ~/gather-test-gatherings.txt --cutoff <LAUNCH_DATE>
railway run -e production -s <APP_SERVICE> npx tsx scripts/listening-report.ts --exclude ~/gather-test-gatherings.txt --cutoff <LAUNCH_DATE>
```

A baseline, reading everything since the start (add `--since 2020-01-01`):

```
railway run -e staging -s <APP_SERVICE> npx tsx scripts/listening-report.ts --since 2020-01-01 --exclude ~/gather-test-gatherings.txt --cutoff <LAUNCH_DATE>
railway run -e production -s <APP_SERVICE> npx tsx scripts/listening-report.ts --since 2020-01-01 --exclude ~/gather-test-gatherings.txt --cutoff <LAUNCH_DATE>
```

What the options do:

- `--since` sets where the reading window starts: only things that happened from that NZ day
  onwards (a send, a draft stopping, a gathering ending) are counted. Left out, it is the start
  of yesterday, NZ time.
- `--cutoff` leaves out whole gatherings that were created before that NZ day, however recent
  their activity, so test gatherings from before launch never count.
- The difference: `--since` chooses *which period* to report on; `--cutoff` chooses *which
  gatherings* are allowed into any report at all.
- `--exclude` names a file on the founder's computer (never in the repo) listing test
  gathering ids, one per line, copied from the address bar (`/plan/<id>/...`). Lines starting
  `#` are notes.

### Reaching the database from a home computer

`railway run` passes the chosen environment's settings into the command, including the
database address, without showing it. Railway databases are private by default (Railway's
PostgreSQL guide, checked 5 Nov 2026), and an app service's `DATABASE_URL` normally points at
the private address, which only works inside Railway's network. If so, the commands above stop
with a connection error code from a home computer, and nothing is read.

The repo has no record of how GTC-369's script reached production (its ticket says only that it
was never run against production by the builder), so this is untested.

Options, none of them enabled by this ticket, each the founder's decision:

1. **Public Access on the database** (Railway: the database service, Settings, Networking,
   Public Access). This creates a TCP proxy and a `DATABASE_PUBLIC_URL` variable on the database
   service. Railway bills network egress through the proxy, and it opens the database to the
   internet behind its password. The report can then use that address without it ever being
   shown, because the swap happens inside Railway's own command:
   ```
   railway run -e staging -s <DATABASE_SERVICE> sh -c 'DATABASE_URL="$DATABASE_PUBLIC_URL" npx tsx scripts/listening-report.ts --exclude ~/gather-test-gatherings.txt --cutoff <LAUNCH_DATE>'
   ```
   The single quotes matter: they keep the address out of the founder's own shell and screen.
2. **Run it inside Railway's network** instead of from home, for example from a shell on the
   running app service if the founder's Railway plan and CLI offer one. Not checked here.
3. **Leave it** until one of the above is chosen. The script is safe to keep: it reads nothing
   unless it can connect and the database confirms read-only.
