# GTC-208 — Unauthenticated SMS test-send route reaches a real TNZ send — CLOSED

## Why this exists

Flagged incidentally during the GTC-172 preflight, two tickets ago, and left
unactioned pending its own ticket. `src/app/api/sms/test-send/route.ts` appeared
to have no auth guard, take a caller-supplied `to` number, and reach a real SMS
send (TNZ). If still true, any unauthenticated caller can trigger an arbitrary
SMS send through Gather's account — cost exposure, abuse potential (spam/TCPA-
class risk, the same family SMS opt-out logic in do-not-touch zone 7 exists to
guard against), and a route invisible to the security suite's route-
classification gate if it was never added to `route-classifications.json`.

## Scope — VERIFY BEFORE FIXING

Before changing anything, confirm the exposure still holds (it may have been
closed since the C1 preflight flagged it):

- Read `src/app/api/sms/test-send/route.ts` in full. Confirm there is genuinely
  NO auth guard on the POST, that the `to` number is caller-supplied, and that
  it reaches a real SMS send (TNZ).
- Confirm the route is absent from `route-classifications.json`.
- If EITHER is already handled — a guard exists, or it's already classified —
  STOP and report. The exposure may already be closed; the fix shape changes.

## Decision gate — surface, do not decide

Once the exposure is confirmed live: is this a shipped feature or a leftover
dev/test utility? The name "test-send" suggests a dev tool. Look at how it's
reached, whether anything in the app calls it, and whether it reads like
production surface or a leftover. Report which it looks like and STOP for a
ruling on guard-vs-remove BEFORE writing the fix. Do not assume guard; do not
assume remove.

## Scope — after the ruling

- **If GUARD:** add the auth check by matching how sibling SMS/admin routes
  protect themselves — the existing convention (session / admin-only /
  event-role, whichever fits). Do NOT invent a new auth mechanism. Add the
  route to `route-classifications.json` with the correct classification.
- **If REMOVE:** remove the route and confirm nothing in the app references it.
- Either way: add a test asserting an unauthenticated POST is rejected and does
  NOT reach a real send — RED against current unguarded code first, GREEN after
  the fix. (If REMOVE, the test asserts the route is gone / 404s.)
- Do NOT change what the route does when correctly authorised — this is an
  access fix, not a behaviour change to the send.

## Explicitly NOT in scope

- Any change to SMS send behaviour for authorised callers.
- Any change to SMS opt-out logic (zone 7) or nudge eligibility.
- Inventing a new auth mechanism — match an existing sibling convention only.

## Guardrails

- No real SMS sent during testing — assert the send is BLOCKED, don't exercise
  a live send. If confirming the exposure requires proving a send would fire,
  prove it by reading the code path, NOT by actually sending.
- No migration expected. If a migration seems needed, STOP.

  into a real feature.
- Ruling: **REMOVE**. Guarding would keep a real-SMS-send route in the
  production surface permanently for a caller that doesn't exist.
