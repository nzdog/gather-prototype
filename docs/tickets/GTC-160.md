# GTC-160 — Client personEventId wiring (completes GTC-159) — CLOSED

> **Handoff ticket for a Sonnet session.** GTC-159 fixed the server seam
> (`reconcileHouseholdMembers`) but its benefit reaches no-email members
> (kids, partners — the common case for a family-event app) only once the
> client sends each member's `personEventId`. This ticket is the completion
> of GTC-159, not polish. Zero frontier cost — executable on a cheap model.

## Why this is the real completion
`PUT /api/events/[id]/households/[householdId]` now reconciles non-primary
members by `personEventId`. If the client omits it:
- members **with email** are still preserved (matched via the
  `(personId,eventId)` upsert branch in `createNewMember`);
- members **without email** (Matt/kids) fall through to create → the old
  PersonEvent is then deleted as "removed" → team/rsvp/nudge loss persists
  for exactly the population most events care about.

The GET `/api/events/[id]/households` response **already returns** each
member's PersonEvent id as `member.id` (verified) — no server GET change
needed. This is pure client plumbing.

## Scope — the wiring sites (all in the client)
1. `src/app/plan/[eventId]/page.tsx` — `apiHouseholdToSaved`: capture the
   PersonEvent id for each non-primary slot (`partnerMember.id`, each helper
   `m.id`, each guest `g.id`) into a new `personEventId` field.
2. `src/components/plan/HouseholdCardList.tsx` — `SavedHousehold`: add
   `personEventId?: string` to `partner`, `helpers[]`, `guests[]`.
3. `src/components/plan/Moment1InputForm.tsx` — `Moment1PersonInput`: add
   `personEventId?: string` to `partner`, `helpers[]`, `guests[]`.
4. `Moment1InputForm.tsx` edit-mode init: when populating the form from
   `editingHousehold`, thread each member's `personEventId` into the form's
   internal per-member state (the local `GuestForm.id` is a UI key, NOT the
   PersonEvent id — keep them separate).
5. `Moment1InputForm.tsx` — `buildPayload()`: include `personEventId` for
   partner/helpers/guests when present (edit mode). Add-new keeps it absent.
6. Route body types are already done in GTC-159 (`HouseholdMemberInput.personEventId`).

Primary contact needs NO id — it is matched server-side by `householdRole`.

## Evidence (Executor-Completed)

**Root cause confirmed:** already established by GTC-159's source read and
restated in the skill correction below — the pre-fix bug was the
`deleteMany`-before-`createMember` ordering, not a missing upsert. This
ticket's job was purely to close the remaining client-side gap: the payload
GTC-159's server contract accepts (`personEventId`) was never sent, so
no-email members (the common family-event case) still lost team/RSVP/nudge
state on every edit.

**Found, not specified:** the six-site spec (Scope, above) didn't cover
clearing `partnerPersonEventId` on form reset / partner removal. Without it,
this sequence corrupts state: edit a household with an existing partner
(`partnerPersonEventId` set) → remove that partner in the form → add a
*different, brand-new* partner without saving in between → save. The stale
id from the removed partner would still be sitting in
`partnerPersonEventId` and get sent on the new partner's payload, so the
server's `reconcileHouseholdMembers` would match the new partner's name
against the *old* partner's `PersonEvent` row and silently overwrite the
wrong member — the exact class of bug this ticket exists to close, just
reintroduced through the new field. Fixed by clearing
`partnerPersonEventId` in both the partner-remove handler and `resetForm()`
(the diff labeled "4d" during implementation). Recorded here as a defect
the spec missed, not as incidental plumbing, so it's findable if the same
gap shows up in the helpers/guests arrays later (those are safe today only
because removing a `GuestForm` entry drops its `personEventId` along with
the rest of the object — there's no equivalent standalone id variable to
go stale).
