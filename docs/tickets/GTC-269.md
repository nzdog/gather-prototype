## ⚠ READ-VERIFIED, NOT DRIVEN — AND THAT IS A DELIBERATE GAP

**Nothing in this ticket has been executed against a running server.** The
evidence below is the route's source at `e6988e1`, the presence of the row it
depends on, and a single non-mutating probe proving the path resolves.

The reason is specific, and it is not caution for its own sake: **driving
this endpoint creates a real credential.** One `POST` writes a `User`, an
`EventRole` with `role: 'HOST'`, and a 30-day `Session` row, and returns a
live session cookie. [[GTC-267]] had to devote a headed paragraph to
explaining one such row it left behind on purpose, so that a later auditor
finding an unexplained 30-day host session dated the same day as a
critical-severity auth ticket did not reasonably assume the worst. **This
ticket will not create a second one unasked.**

Founder instruction, 2026-09-11: *"File GTC-269 with what you have —
read-verified, not driven, and say so. Do NOT drive it."*

**A live proof is one command and takes one second.** It is written out under
*Reproduce* so that whoever executes this ticket can run it deliberately,
with the cleanup already specified. It has not been run.

## Signal

**Expected**
An endpoint that creates an authenticated session requires a credential to do
so — a verified magic link, as `POST /api/auth/verify` does. Failing that, it
is unreachable outside development.

**Actual**
`POST` in `src/app/api/demo/session/route.ts` takes **no body, no token, no
header and no session.** It resolves one event by literal name, upserts a
`User`, upserts an `EventRole` with `role: 'HOST'`, creates a `Session` with a
30-day expiry, sets the `session` cookie, and returns `200` with the event id.

Its own doc comment reads:

> *"Safe for production: scoped to the demo event and demo user only."*

**The scoping half of that sentence is true. The production half is not
enforced by anything.**

**Smallest failing case**
`curl -X POST http://localhost:3000/api/demo/session -i` with no cookie and
no header returns 200 and a `Set-Cookie: session=...` valid for 30 days.

## Evidence

### The handler, verbatim at `e6988e1`

`POST` in `src/app/api/demo/session/route.ts`. There is no guard call of any
kind in the file — no `getUser`, no `requireEventRole`, no `resolveToken`.

```
// Ensure EventRole (HOST) exists
await prisma.eventRole.upsert({
  where: { userId_eventId: { userId: user.id, eventId: event.id } },
  update: {},
  create: { userId: user.id, eventId: event.id, role: 'HOST' },
});

// Create Session (30-day expiry) — same pattern as verify/route.ts
const sessionToken = randomBytes(32).toString('hex');
const expiresAt = new Date(Date.now() + 30 * 24 * 60 * 60 * 1000);

await prisma.session.create({
  data: { userId: user.id, token: sessionToken, expiresAt },
});

(await cookies()).set('session', sessionToken, {
  httpOnly: true,
  secure: (process.env.NODE_ENV as string) === 'production',
  sameSite: 'lax',
  maxAge: 30 * 24 * 60 * 60,
  path: '/',
});
```

Its comment says *"same pattern as verify/route.ts"* — and that is exactly
the problem. `POST` in `src/app/api/auth/verify/route.ts` reaches this same
block **after** consuming a magic-link token via `prisma.magicLink.findUnique`.
This route reaches it after consuming nothing.

### There is no environment gate

The only `NODE_ENV` reference in the file is the cookie's `secure` flag:

```
$ grep -n 'NODE_ENV' src/app/api/demo/session/route.ts
75:      secure: (process.env.NODE_ENV as string) === 'production',
```

**That is a cookie transport flag, not a gate.** Compare `POST` in
`src/app/api/demo/reset/route.ts`, which does have one:

```
if (process.env.NODE_ENV === 'production') {
  return NextResponse.json({ error: 'Not Found' }, { status: 404 });
}
```

`demo/session` has no such branch. The route runs in every environment where
the code is deployed and the event row exists.

**Independently confirmed by machine**, not only by reading: the route scanner
built in [[GTC-268]] slice 1 classifies every handler's credentials and
reports this one as the only mutation in the tree with nothing at all —

```

    no credential of any kind
```

— where `POST /api/demo/reset` is reported `ENV_GATE` and
`POST /api/webhooks/stripe` is reported `SIGNATURE`. That verdict is a pinned
assertion in `tests/security-route-scan-control.ts`, so it cannot quietly
change while this ticket is open.

### ⚠ FINDING 2, RAISED TO ITS OWN FINDING BY FOUNDER RULING — the session clobber

Found 2026-09-11 during execution, not present in the ticket as filed.

**Founder ruling, 2026-09-11:** *"The clobber is not hygiene, it is a live
product bug: a signed-in host is two clicks from the homepage to being
silently signed out of their own account and into the demo. It is the most
likely of these to have actually bitten someone."*

The cookie this route sets is named `session` at `path: '/'` — **the same
cookie a real login uses**, written by `POST` in
`src/app/api/auth/verify/route.ts` and by `POST` in
`src/app/api/events/route.ts`. Setting it unconditionally replaces whatever
was there.

The path is two clicks and needs no error on anyone's part:

1. A signed-in host loads `/` . The homepage renders the "See it in action →"
   link **unconditionally** — in `src/app/page.tsx` the first CTA branches on
   `user` and the demo link does not — so it is offered to signed-in users.
2. They click "Open Planning Dashboard →" on `/demo`
   (`handleOpenDashboard` in `src/app/demo/page.tsx`).
3. Their own session cookie is gone, replaced by the demo account's. They are
   signed out of their own event and into the demo, with no indication that it
   happened.

**This is distinct from finding 1 and would survive any of the three filed
options.** Environment-gating the route would leave it fully live in
development. Deleting the route would remove it by accident rather than by
decision.

Unlike the credential-scope finding, this one has a plausible history of
actually firing: it needs no attacker, only a host who clicked the demo link.

### What the session reaches

**⚠ THE TICKET AS FILED UNDERSTATED THIS, and the correction is the reason the
fix is shaped the way it is.** Filed text: *"**Scoped to the demo event**,
which is the containment and the whole of it."* That is false, and it was
false at filing time.

`requireEventRole` in `src/lib/auth/guards.ts` keys on `userId` **and**
`eventId`, and every `EventRole` read site in `src/` does the same — checked
individually: the guard, `canEditEvent` in `src/lib/entitlements.ts`, the
host-preview branch in `src/app/api/p/[token]/route.ts`, and the viewer lookup
in `src/app/plan/[eventId]/glance/page.tsx`. **Nothing in the tree treats a
HOST `EventRole` as a broader credential.** That part of the filed story
holds.

The breadth is not in the `EventRole`. It is in the `Session`. `getUser` in
`src/lib/auth/session.ts` resolves the cookie to a whole `User` with no event
scoping at all, so the containment depends entirely on that user's role set —
and **nothing in the route bounded it.** Measured on the local database,
2026-09-11, before the fix:

```
User sarah.henderson@demo.gather  (cmmolypsj004c1y6hnvyldumv)
  HOST  cmmolxnlm00181yn154x1aylz   Henderson Family Christmas 2025
                                    isDemo = true
  HOST  cmow49m0l00011yg7w6apsdgg   GTC-133 Sub-commit (g) Test
                                    isDemo = FALSE
```

The amplifier is `GET` in `src/app/api/events/route.ts`, which takes a bare
session with **no** event role and returns every event the user holds any role
on — so the holder need not even know an event id. Both of those events carry
a HOST `AccessToken` (demo: 1 HOST, 8 COORDINATOR, 35 PARTICIPANT over 43
people, 37 with an email; GTC-133: 1 HOST, 14 PARTICIPANT over 15 people, 8
with an email), so the chain runs on into [[GTC-267]]'s step 6.

**Why the role set grew, which is the part that makes this structural rather
than a one-off:** `Event.hostId` points at the **`Person`** "Sarah Henderson",
who also hosts the GTC-133 test event, and the claim branch in `POST`
`src/app/api/auth/verify/route.ts` creates an `EventRole` for **every** event
where `hostId === personId`. A demo credential tied to that Person inherits
her whole hosting history and grows with it.

**Driven, not inferred.** The RED run of suite 11 printed it:

```
✗ the minted session reaches EXACTLY ONE event, and it is the demo event
  Error: status 200; reaches 2:
    cmow49m0l00011yg7w6apsdgg "GTC-133 Sub-commit (g) Test" isDemo=false
    cmmolxnlm00181yn154x1aylz "Henderson Family Christmas 2025" isDemo=true
```

**Severity holds at Critical, for a different reason than filed.** Not "it
mints a host session" but "it mints a user session whose reach nothing in the
route bounds". No real personal data was reachable — everything on both events
is seeded or test data, `@example.com` and `@demo.gather`, no phone numbers —
exactly as [[GTC-267]] recorded. The mechanism was not contained.

`Session` + `EventRole(HOST)` is the credential `requireEventRole` accepts.
Everything [[GTC-267]] closed by requiring a session is open to a caller
holding this one — `GET /api/events/[id]`, `/items`, `/people`, `/tokens`,
and through `/tokens` every access token on the event. **Scoped to the demo
event**, which is the containment and the whole of it.

## ⚖ THE RULING — recorded before any code was written

**Founder ruling, 2026-09-11, verbatim on the substance:**

> *"The defect is not that the route lacks a credential. It is that it hands
> out a credential wider than the thing it is demoing and then documents the
> narrow version. GTC-015 made a product decision — a stranger can click 'try
> the demo' — and that decision stands. What does not stand is a session whose
> reach nothing in the route bounds, and which grows on its own as a Person's
> hosting history grows."*

**None of the three options below was taken as written.** The option taken is
a **narrowed option 2**: keep the endpoint reachable by anyone, and make the
credential it hands back match what its own comment claims. Four changes, all
in the route file plus its caller and tests.

Why not the three as filed, each rejected on a specific ground and not on
taste:

- **Option 1 (environment-gate)** is a revert of [[GTC-015]]. That commit
  (`f6e4b41`, 2026-03-08, "enable demo APIs in production") removed this exact
  gate deliberately and rewrote the doc comment in the same diff. It would
  cost the deployed planning-dashboard demo, leave the bypass on every
  non-production deploy, and fix neither of the two defects actually found —
  the cross-event reach and the session clobber. It would also have turned
  `tests/demo-endpoints-test.ts` red on an assertion whose failure message
  instructs the reader to take the gate back out.
- **Option 2 as filed (require a credential)** trades the product for the
  property. A stranger clicking "See it in action" is the homepage's second
  CTA.
- **Option 3 (delete it)** is not viable, and this answers Unknown 3 below.
  `/plan/[eventId]` needs a real `Session` plus `EventRole`: it is a client
  component with no server guard, and after [[GTC-267]] every API it calls —
  `/api/events/[id]`, `/teams`, `/days`, `/conflicts`, `/items`, `/people`,
  `/tokens`, `/invite-status` — requires `requireEventRole`. Without a session
  the page renders and every fetch 401s. Token links reach `/h/`, `/c/` and
  `/p/`, which are different surfaces. Option 3 does not repoint the dashboard
  demo; it deletes it.

**Zone sign-off, given explicitly and narrowly:**

- **Zone 2 — signed off, narrowly.** *"Changing what this route WRITES into
  Session, User and EventRole is not touching Zone 2. The zone protects the
  schema, the auth routes, and magic-link generation, expiry and consumption."*
  None of `prisma/schema.prisma`, `src/app/api/auth/` or the magic-link path
  was touched. Verified in the diff.
- **Zone 1 — signed off for the cookie-clobber fix only, and only in the route
  file.** `src/lib/auth*` and `middleware.ts` untouched. The cookie's name
  (`session`) and path (`/`) are unchanged. Verified in the diff.

**The three options as originally filed** are kept below verbatim, because the
reasoning that rejected them only makes sense against what they said:

1. **Environment-gate it**, matching `demo/reset`: return 404 when
   `NODE_ENV === 'production'`. Smallest change, preserves the demo flow
   locally, and makes the doc comment true instead of aspirational. **It does
   not make the endpoint safe — it makes it unreachable where it matters.**
   Any non-production deploy keeps the bypass.
2. **Require a credential.** Put the demo behind the same magic-link exchange
   as every other session, or a `DEMO_SECRET`. Correct, and it changes the
   demo's user experience — a stranger clicking "try the demo" is the point of
   the page.
3. **Delete it** and have `/demo` use the existing token links from
   `GET /api/demo/tokens`, which already hands out demo personas. Removes the
   session mint entirely; needs a check that no surface depends on a real
   `Session` for the demo host.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding. Two are
directly adjacent and neither may be modified:

- **Zone 1** (session & cookie management, `src/lib/auth*`, `middleware.ts`) —
  this route writes a `Session` row and sets the `session` cookie by hand
  rather than through a shared helper. **Fixing it must not change the cookie
  naming or scoping logic**, which was a hard-won fix (GTC-001).
- **Zone 2** (magic-link auth flow, `src/app/api/auth/`, and the `MagicLink`,
  `Session`, `User` models) — if option 2 is chosen, the demo must **use** the
  existing flow, not alter token generation, expiry or consumption.

Out of scope: `POST /api/demo/reset` and `GET /api/demo/tokens`. Both are
unauthenticated, both are recorded on [[GTC-268]]'s list awaiting a ruling,
and neither mints a session.

**Root cause confirmed**

Three faults in one handler, and only the first was in the ticket as filed.

First, the credential was wider than the route's own claim. The route minted a
`Session` for the `User` linked to the demo `Person` (`person.userId`), and a
`Session` is a bearer credential for a whole `User` — `getUser` applies no
event scoping. Because the claim branch in `POST`
`src/app/api/auth/verify/route.ts` creates an `EventRole` for every event
where `hostId === personId`, that user's role set grows with the demo
Person's hosting history, and had already grown to two events, one with
`isDemo: false`. `GET` in `src/app/api/events/route.ts` enumerates that set
for a bare session, so the holder did not even need an event id.

Second, the cookie clobber — finding 2 above. `session` at `path: '/'`, set
unconditionally, replacing a real host's login.

Third, the lookup was `findFirst` on `name` alone with no `orderBy`.
`Event.name` has no uniqueness constraint, so a real event sharing the demo
name could be the row resolved, and its host's `Person` would then be handed
an `EventRole` and a live session.

**Files changed**

- `src/app/api/demo/session/route.ts` — the fix, all four changes:
  - `DEMO_SESSION_EMAIL` (`demo-session@demo.gather`), a dedicated account
    **never linked to a `Person`**, replacing the `person.userId` lookup. This
    is the change that makes the doc comment true: an account with no `Person`
    link cannot inherit event roles. The old `sarah.henderson@demo.gather`
    user is left in place and untouched; the route simply stops using it.
  - `DEMO_SESSION_MAX_AGE_SECONDS = 2 * 60 * 60`. **Two hours, chosen and
    stated.** Reasoning: the dashboard walkthrough plus the three token views
    is well under an hour of reading, two hours absorbs an interruption, and
    it expires the same afternoon rather than standing for a month. It is one
    constant, used for both the `Session.expiresAt` and the cookie `maxAge`,
    so the two cannot drift.
  - `eventRole.deleteMany({ where: { userId, eventId: { not: event.id } } })`
    before the upsert — the invariant **enforced on every call**, not merely
    true at creation. If anything ever grants this account a role elsewhere,
    the next demo session revokes it rather than handing it out.
  - the cookie-presence check, returning **409** with its own explanatory
    `reason`, and `isDemo: true` on the `findFirst`.
  - the doc comment rewritten to say what the route does, including that it
    is deliberately uncredentialed and why.

**⚠ THE PRESENCE CHECK IS DELIBERATELY NOT `getUser()`, and the reason is the
scanner**

The clobber check reads the cookie's presence and does not resolve it. That
looks like the lazy choice and is the opposite.

`getUser` is in `SESSION_GUARDS` in `tests/security-route-scan.ts`, and
`guardResultIsChecked` counts a guard whose result reaches a variable that an
`if` later tests. `const user = await getUser(); if (user) { return 409 }`
satisfies both, so the scanner would have reported this handler **GUARDED**
while it remained callable by anyone with no credential at all. That is
precisely the false positive [[GTC-268]]'s scanner exists to prevent, and
buying a flattering verdict with a false one is not a trade worth making.
Looking the token up instead — `prisma.session.findUnique({ where: { token } })`
— trips the same wire from the other side: `{ model: 'session', field: 'token' }`
is a declared `CREDENTIAL_COLUMN`, and the handler already returns 4xx
somewhere, so it would have been reported as carrying a credential it does not
check.

Presence only. No guard symbol, no credential column, verdict unchanged and
**true**.

**⚠ ONE ASSERTION IS REPORTED UNASSERTED RATHER THAN CLAIMED — the `isDemo`
filter**

M4 removed `isDemo: true` from the lookup and the suite stayed 100/100. The
filter is in the fix, by founder ruling, and it is correct. **It is not proved
by a red.**

Why it cannot be, stated rather than worked around: the route resolves with
`findFirst` and no `orderBy`, so which of two same-named rows is returned is
Postgres heap order — in practice the older row, which is the demo one. A
decoy cannot be made to win deterministically. Suite 11 does create a decoy
event with the exact demo name and `isDemo: false`, and asserts the route
still resolves the demo row, but that assertion passes with or without the
filter on this data. It is labelled in the suite as a **forward regression
guard, not a reproduced red**, and it is real as that: once the filter is on
the lookup, no non-demo row can be resolved whatever the ordering.

**Founder ruling, 2026-09-11 — accepted as reported, and the label is the
point.** *"A forward regression guard that cannot be shown a red is worth
having and worth labelling as what it is. Do not manufacture a decoy that wins
by heap order; that would be a test that passes for a reason nobody
controls."*

So no decoy was engineered to win. The alternative on the table was to force
the unfixed route to resolve the decoy by exploiting insertion order, and it
was rejected: a green that depends on Postgres returning rows in a particular
sequence is a green nobody can reason about, and it would have been reported
as a reproduced red when it was nothing of the kind.

**⚠ `tests/demo-endpoints-test.ts` WAS A LOADED GUN IN THE FILE BEING EDITED**

Founder ruling, 2026-09-11: *"A green test whose failure message instructs the
reader to reintroduce a vulnerability is not an adjacent problem, it is a
loaded gun in the file you are editing."* Narrowed in this commit, not its
own.

It asserted `!content.includes("process.env.NODE_ENV === 'production'")` on
both demo routes, with the failure message *"Route still returns 404 in
production — guard must be removed"*. Written by [[GTC-015]] in the same
commit that removed the gate, to hold that decision — which is still correct.
How it held it was not.

**A substring match is not a security assertion**, and this file is the proof.
It tests the spelling of the code, not its behaviour. The route's cookie flag
reads `(process.env.NODE_ENV as string) === 'production'` — a cast added in
`a20fbad` on 2026-02-21, which **predates** GTC-015 and has nothing to do with
gating. That cast is the only reason the substring failed to match and the
only reason the suite was green. Delete the cast, change no behaviour
whatsoever, and the assertion fails.

It also asserted the absence of a mechanism rather than the presence of a
property: "no NODE_ENV string anywhere in this file" forbids every future use
of `NODE_ENV` in these routes, gating or not.

What it asserts now: that neither demo handler contains a refusal branch keyed
on the environment — a `NODE_ENV` test in an `if` whose body returns a 4xx.
That is the same shape `collectEnvGate` in `tests/security-route-scan.ts`
looks for, so the two files now agree on what a gate is. A `NODE_ENV`
reference that is not a refusal is correctly ignored. Comments are stripped
first, because both routes now carry headed comments that quote the gate whose
absence they are explaining — reading a tombstone as the thing itself is the
mistake `readCode` exists to prevent in [[GTC-267]].

**And it gained a control it did not have.** Two assertions that a regex found
nothing prove nothing, because a regex that never matches anything also finds
nothing — [[GTC-267]]'s rule that an empty search result is a claim, and a
claim needs a control. `POST /api/demo/reset` **does** carry the gate and is
now asserted to be detected as gated in the same run. That control passes, so
the two negatives above mean something.
