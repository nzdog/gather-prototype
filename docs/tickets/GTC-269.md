## ⚠ READ-VERIFIED, NOT DRIVEN — AND THAT IS A DELIBERATE GAP

**Nothing in this ticket has been executed against a running server.** The
evidence below is the route's source at `e6988e1`, the presence of the row it
depends on, and a single non-mutating probe proving the path resolves.

The reason is specific, and it is not caution for its own sake: **driving
this endpoint creates a real credential.** One `POST` writes a `User`, an
`EventRole` with `role: 'HOST'`, and a 30-day `Session` row, and returns a
live session cookie. [[GTC-267]] had to devote a headed paragraph to
explaining one such row it left behind on purpose, so that a later auditor
finding an unexplained 30-day host session dated the same day as a
critical-severity auth ticket did not reasonably assume the worst. **This
ticket will not create a second one unasked.**

Founder instruction, 2026-09-11: *"File GTC-269 with what you have —
read-verified, not driven, and say so. Do NOT drive it."*

**A live proof is one command and takes one second.** It is written out under
*Reproduce* so that whoever executes this ticket can run it deliberately,
with the cleanup already specified. It has not been run.

## Signal

**Expected**
An endpoint that creates an authenticated session requires a credential to do
so — a verified magic link, as `POST /api/auth/verify` does. Failing that, it
is unreachable outside development.

**Actual**
`POST` in `src/app/api/demo/session/route.ts` takes **no body, no token, no
header and no session.** It resolves one event by literal name, upserts a
`User`, upserts an `EventRole` with `role: 'HOST'`, creates a `Session` with a
30-day expiry, sets the `session` cookie, and returns `200` with the event id.

Its own doc comment reads:

> *"Safe for production: scoped to the demo event and demo user only."*

**The scoping half of that sentence is true. The production half is not
enforced by anything.**

**Smallest failing case**
`curl -X POST http://localhost:3000/api/demo/session -i` with no cookie and
no header returns 200 and a `Set-Cookie: session=...` valid for 30 days.

## Evidence

### The handler, verbatim at `e6988e1`

`POST` in `src/app/api/demo/session/route.ts`. There is no guard call of any
kind in the file — no `getUser`, no `requireEventRole`, no `resolveToken`.

```
// Ensure EventRole (HOST) exists
await prisma.eventRole.upsert({
  where: { userId_eventId: { userId: user.id, eventId: event.id } },
  update: {},
  create: { userId: user.id, eventId: event.id, role: 'HOST' },
});

// Create Session (30-day expiry) — same pattern as verify/route.ts
const sessionToken = randomBytes(32).toString('hex');
const expiresAt = new Date(Date.now() + 30 * 24 * 60 * 60 * 1000);

await prisma.session.create({
  data: { userId: user.id, token: sessionToken, expiresAt },
});

(await cookies()).set('session', sessionToken, {
  httpOnly: true,
  secure: (process.env.NODE_ENV as string) === 'production',
  sameSite: 'lax',
  maxAge: 30 * 24 * 60 * 60,
  path: '/',
});
```

Its comment says *"same pattern as verify/route.ts"* — and that is exactly
the problem. `POST` in `src/app/api/auth/verify/route.ts` reaches this same
block **after** consuming a magic-link token via `prisma.magicLink.findUnique`.
This route reaches it after consuming nothing.

### There is no environment gate

The only `NODE_ENV` reference in the file is the cookie's `secure` flag:

```
$ grep -n 'NODE_ENV' src/app/api/demo/session/route.ts
75:      secure: (process.env.NODE_ENV as string) === 'production',
```

**That is a cookie transport flag, not a gate.** Compare `POST` in
`src/app/api/demo/reset/route.ts`, which does have one:

```
if (process.env.NODE_ENV === 'production') {
  return NextResponse.json({ error: 'Not Found' }, { status: 404 });
}
```

`demo/session` has no such branch. The route runs in every environment where
the code is deployed and the event row exists.

**Independently confirmed by machine**, not only by reading: the route scanner
built in [[GTC-268]] slice 1 classifies every handler's credentials and
reports this one as the only mutation in the tree with nothing at all —

```
  POST   /api/demo/session
    no credential of any kind
```

— where `POST /api/demo/reset` is reported `ENV_GATE` and
`POST /api/webhooks/stripe` is reported `SIGNATURE`. That verdict is a pinned
assertion in `tests/security-route-scan-control.ts`, so it cannot quietly
change while this ticket is open.

### The dependency it needs exists

The route resolves `DEMO_EVENT_NAME = 'Henderson Family Christmas 2025'`. That
row is present in the local dev database:

```
$ npx tsx -e "... prisma.event.findFirst({ where: { name: 'Henderson Family Christmas 2025' } })"
demo event row: cmmolxnlm00181yn154x1aylz
```

### The route is mounted — proven without triggering the write

```
$ curl -s -o /dev/null -w "GET /api/demo/session -> HTTP %{http_code}\n" \
    http://localhost:3000/api/demo/session
GET /api/demo/session -> HTTP 405
```

A `405 Method Not Allowed` proves Next resolved the path and found a route
module exporting `POST` and not `GET`. **A 404 would have meant the route was
not mounted.** This probe writes nothing.

### What the session reaches

`Session` + `EventRole(HOST)` is the credential `requireEventRole` accepts.
Everything [[GTC-267]] closed by requiring a session is open to a caller
holding this one — `GET /api/events/[id]`, `/items`, `/people`, `/tokens`,
and through `/tokens` every access token on the event. **Scoped to the demo
event**, which is the containment and the whole of it.

### Production exposure — the same shape as GTC-267's, recorded the same way

**There is no real personal data on the deployed instance.** Per [[GTC-267]],
verified there and not re-verified here: the deployed instance has no branch
connected, has not deployed in five weeks, and runs code from 5 August. The
demo event is seeded, not real. **Railway is handled by the founder and this
ticket takes no deploy action.**

**Recorded as a note only, and it is the same note [[GTC-267]] left:** the
instance must not be redeployed until this lands, because a redeploy ships
this forward onto whatever data is there by then.

**Unverified and stated as unverified:** whether the demo event row exists on
the deployed database. If it does not, the route 404s there today. That is an
accident of seeding, not a control — exactly as `cuid` non-enumerability was
the accident that contained [[GTC-267]].

## Scope

**Fix here:**
- `POST` in `src/app/api/demo/session/route.ts` — the decision below.
- Its caller, if the chosen fix changes the contract: the `/demo` page.
- `tests/security-validation.ts` — new assertions, adding and never weakening.

**The decision this ticket needs, and it is the founder's, not the
executor's.** Three options, in the order they are recommended:

1. **Environment-gate it**, matching `demo/reset`: return 404 when
   `NODE_ENV === 'production'`. Smallest change, preserves the demo flow
   locally, and makes the doc comment true instead of aspirational. **It does
   not make the endpoint safe — it makes it unreachable where it matters.**
   Any non-production deploy keeps the bypass.
2. **Require a credential.** Put the demo behind the same magic-link exchange
   as every other session, or a `DEMO_SECRET`. Correct, and it changes the
   demo's user experience — a stranger clicking "try the demo" is the point of
   the page.
3. **Delete it** and have `/demo` use the existing token links from
   `GET /api/demo/tokens`, which already hands out demo personas. Removes the
   session mint entirely; needs a check that no surface depends on a real
   `Session` for the demo host.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding. Two are
directly adjacent and neither may be modified:

- **Zone 1** (session & cookie management, `src/lib/auth*`, `middleware.ts`) —
  this route writes a `Session` row and sets the `session` cookie by hand
  rather than through a shared helper. **Fixing it must not change the cookie
  naming or scoping logic**, which was a hard-won fix (GTC-001).
- **Zone 2** (magic-link auth flow, `src/app/api/auth/`, and the `MagicLink`,
  `Session`, `User` models) — if option 2 is chosen, the demo must **use** the
  existing flow, not alter token generation, expiry or consumption.

Out of scope: `POST /api/demo/reset` and `GET /api/demo/tokens`. Both are
unauthenticated, both are recorded on [[GTC-268]]'s list awaiting a ruling,
and neither mints a session.
