# GTC-237 — Re-running generation ate Kate's edits, silently — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign
**Shipped in one commit with [[GTC-235]]** — see that ticket's "Why these are one change".

*Filed from [[GTC-236]]'s Phase 1 audit, 2026-08-22, as a stub. Scoped and executed
2026-09-12.*

## Signal

**Expected:** regenerating replaces the model's draft. Anything Kate wrote, edited, or a guest
has answered survives.

**Actual:** the rerun path of `POST` in `src/app/api/events/[id]/finalize-plan/route.ts`
dropped prior AI output at TEAM level — `team.deleteMany({ where: { eventId, source:
'GENERATED' } })`. `Item.team` is `onDelete: Cascade` and `Item.teamId` is non-nullable, so
**every item on a generated team died with it regardless of `Item.source` or `isProtected`**,
and every `Assignment` cascaded after.

**Smallest failing case:** generate → edit any item (or add one) → Back to Step 1 → Generate
again. The edit is gone; no error, no ledger note of the loss beyond the bulk record.

**Measured blast radius** on the development database at execution time: five V2 events with
260, 86, 68, 53 and 24 items on generated teams. On the last of those, **all 24 items carried
an assignment** — one rerun would have destroyed 24 live commitments between the host and her
guests.

## Root cause

`Item.source` and `isProtected` exist for exactly this and were simply not consulted at item
level. Three witnesses: V1's `clearPlanForRegeneration` in `src/lib/workflow.ts` uses precisely
`source: 'GENERATED', isProtected: false`; [[GTC-236]]'s `regenerate-plan` uses the same
predicate plus `TEMPLATE`; and the item PATCH maintains `source` for no other purpose than
letting a regeneration tell disposable output from owned rows.

`finalize-plan` *did* reason about provenance — its comment read "We only delete teams whose
source is GENERATED to preserve any teams Kate added by hand" — but one level too high. Host
state accumulates on exactly those generated teams: the item PATCH flips `GENERATED →
HOST_EDITED` in place, and `POST .../teams/[teamId]/items` files `MANUAL` rows into whichever
team she is looking at, which after generation is a generated one. Deleting a team can never be
the way a regeneration clears items.

Two further absences: no `PlanRevision` checkpoint (so nothing to restore, and the V1 revision
UI is hidden on V2 events by the `!event.setup` guards anyway), and no transaction (so a
failure part-way through the create loop left the previous plan gone and the new one half-built).

## Founder rulings, 2026-09-12

**Ruling 1 — an accepted item is not disposable, whatever its source.** An item a guest has
said yes to is a promise between two people; provenance records who drafted the row, and a
reply outranks a draft. "Has an assignment whose response is not `PENDING`" joins the preserve
set.

⚠ **"NOT PENDING" IS DELIBERATE AND WIDER THAN "SAID YES".** `DECLINED` and `MAYBE` preserve
the row too. Do not narrow this to `ACCEPTED` thinking you are tightening a loose rule:
replacing a declined item deletes the evidence that someone said no, and the host needs to see
that and re-home the item. The screen exists to show her where the plan stands, not to tidy
away the parts that went badly.

**The shape — fix the delete in place. Do NOT reroute Step 1's Generate to `regenerate-plan`.**
It looks like the smaller change and is not: `regenerate-plan` is food-only and never
reproduces `TASK` rows, and Step 1 is the only place the set-up / clean-up / other-jobs free
text can change. Rerouting would trade a loud data-loss bug for a quiet wrong-answer one —
Kate edits her jobs, presses Generate, and the jobs silently do not change.

**No stopgap.** The one-guard version (409 on a rerun, relabel the button) costs her the jobs
text, and the real fix ships now rather than later.

**Canonical-first team naming.** The two routes disagreed: `finalize-plan` preferred the
model's label and fell back to the canonical map, `regenerate-plan` preferred the canonical
map. Canonical wins, because find-or-create keys on this string — model-first is exactly what
produces a second team of nearly the same name on a rerun, and a naming rule that depends on an
AI returning the same string twice is not a rule. Recorded here because the disagreement was
real and someone will otherwise re-derive it from the losing side.

## The fix

**`src/lib/ai/plan-write.ts` — NEW.** The write phase, shared. `plan-input.ts` is the input
half of the same seam: [[GTC-236]] pulled the prompt assembly out so both routes build through
one code path. This is the output half, pulled out for the same reason and one more.

**The one more is testability, and it is the stronger argument.** Before this module the only
way to exercise what a regeneration does to the database was to run a route that spends one of
an event's ten Claude calls. A High-severity data-loss path that costs money to assert does not
get asserted, and this one never was. `applyPlanSections` takes a sections array, so a test
hands it a fabricated payload and reads rows back.

Exports:

- `disposableItemWhere` — the predicate. Two tests, not one: provenance (`source`,
  `isProtected`) **and** reply (`assignment` absent or `PENDING`).
- `applyPlanSections` — delete disposables in scope, find-or-create each team by canonical
  label, append after survivors rather than restarting `displayOrder` at 1.
- `sweepEmptyGeneratedTeams` — per-team deletes, never an unscoped `team.deleteMany`; the
  cascade would take `TASK` rows, the trap [[GTC-171]] already recorded.
- `planCategoryLabel` / `planCategoryEmoji` — canonical-first for the label because
  find-or-create keys on it; model-first for the emoji because nothing does.

**The rerun carve-out this ticket asked for, stated rather than implied:** first generation is
unchanged to the row. Its deletes are no-ops on an event with no generated rows, and the
checkpoint is written only when `priorItemCount > 0`, so a first generation still produces no
`PlanRevision`. The carve-out needs no branch beyond that one condition.

**`finalize-plan`** now resolves its actor up front, checkpoints before anything destructive on
a rerun, and runs the food phase, the task phase and the sweep inside one `$transaction`. The
task loop stays here rather than moving into `applyPlanSections`, which is food-only — what it
shares is `disposableItemWhere`, so a job Kate wrote or edited survives a rerun exactly as an
item she wrote or edited does. The sweep runs once after both phases, so a team emptied by the
food phase and refilled by the task phase is not deleted and recreated in between.

**`aiCallsUsed` stays OUTSIDE the transaction, deliberately.** The call has been made and
billed by the time that line runs; a write-phase rollback must not refund it, or a repeatable
failure becomes a free loop through the cap. ⚠ `regenerate-plan` does the opposite — it
increments inside its transaction — and this ticket did not change it. The difference is real
and is not an oversight; whichever way it is settled should be settled in one place, on its own
ticket, for both routes at once.

### `regenerate-plan` inherits the predicate

Ruling 1 originally ring-fenced `regenerate-plan` as file-don't-fix. The extraction overtook
that: a shared helper whose whole purpose is that there is only one answer cannot be
parameterised to let one caller keep the wrong one without building a deliberate defect into
it. Founder ruling, 2026-09-12: **inherit.** The change makes that route strictly more
conservative — it deletes fewer rows and never more — so the blast radius of being wrong is
zero rows lost. [[GTC-284]] owns proving it and writing the copy that explains it.

Its `preservedItems` query is now the exact complement, `NOT: regenerableWhere`, so nothing can
fall into the gap between two independently-written predicates and end up neither replaced nor
described to the model.

## The assertion that was wrong, and the rule it produced

**One of the RED assertions was wrong rather than the code, and finding that out is the
strongest thing test-first did on this ticket.**

The assertion read: *"an item on a MANUAL team is untouched."* It was written before the fix,
out of the same instinct that produced the bug — that a row's fate follows from the team it
sits on. Under the old team-level delete it was true, because only generated teams were
deleted. Under an item-level predicate it is false, and it should be.

**THE RULE, in its own words: a row is protected by its own provenance and its own reply,
never by the provenance of the team it sits on.** Asking "whose team is this?" is the
team-level mistake. It is the mistake the original `team.deleteMany` made at the scale of a
whole plan, and the mistake this ticket's own test reproduced in miniature one file away —
which is how much pull the wrong frame has, and why the rule is written down here rather than
left to be inferred from the predicate.

### The behaviour change this produced was FOUND, not decided

The delete widened from "items on generated teams" to "disposable items anywhere on the
event". A `GENERATED`, unanswered, unprotected row sitting on a team Kate made by hand is now
replaced, where before it survived.

**That change was surfaced by the failing assertion, not chosen in advance.** It is not in the
founder rulings of 2026-09-12, not in the ticket as filed, and not in the implementation shape
that was signed off. The predicate was written to satisfy Ruling 1; the test then asked a
question nobody had asked; the answer disagreed with the assertion; and the rule above is what
settled which of the two was wrong. Had the test been written after the fix it would have been
written to match the code, and this would have shipped unexamined.

The case is real rather than theoretical: `regenerate-plan` finds teams by canonical label, so
a team she named "Mains" genuinely does receive generated rows. Two assertions now stand where
the wrong one was — her own `MANUAL` row on her own team survives, and an unanswered
`GENERATED` row is replaced even there.

## Evidence

**Root cause confirmed:** `team.deleteMany({ where: { eventId, source: 'GENERATED' } })` in
`POST` in `src/app/api/events/[id]/finalize-plan/route.ts`, combined with
`Item_teamId_fkey ... ON DELETE CASCADE` and `Assignment_itemId_fkey ... ON DELETE CASCADE`
from the init migration. Provenance was read at team level; the cascade then overrode the
item-level fields put there to stop exactly this.

**Files changed**
- `src/lib/ai/plan-write.ts` — NEW. `disposableItemWhere`, `applyPlanSections`,
  `sweepEmptyGeneratedTeams`, `planCategoryLabel`, `planCategoryEmoji`.
- `src/app/api/events/[id]/finalize-plan/route.ts` — actor resolved up front; `createRevision`
  on a rerun; the write phase moved into one `$transaction` over `applyPlanSections`, the task
  loop and the sweep; the task delete now uses the shared predicate.
- `src/app/api/events/[id]/regenerate-plan/route.ts` — delete-and-recreate and the sweep
  replaced by the shared helpers; `preservedItems` expressed as the exact complement.
- `tests/plan-write-preserve-test.ts` — NEW, and `package.json` script
