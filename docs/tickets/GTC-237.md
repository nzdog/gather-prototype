# GTC-237 — STUB: re-running generation eats Kate's edits, silently

**Status:** Open — stub, needs scoping when pulled | **Effort:** TBD

*Source: [[GTC-236]] Phase 1 audit, 2026-08-22. Founder ruling: file, do not fix there.
Derived from code at `cfa6845`.*

## Signal

The rerun path of `POST` in `src/app/api/events/[id]/finalize-plan/route.ts` deletes prior
AI output at TEAM level: `prisma.team.deleteMany({ where: { eventId, source: 'GENERATED' } })`
(hint: ~311, the GTC-145 idempotency comment). `Item.team` is `onDelete: Cascade` and
`Item.teamId` is non-nullable — so **every item on a generated team dies with it, regardless
of `Item.source` or `isProtected`**, assignments cascading too.

Host state accumulates on exactly those teams: the item PATCH routes flip
`GENERATED → HOST_EDITED` in place, and `POST .../teams/[teamId]/items` adds `MANUAL` items
into whatever team Kate is looking at — which after generation is a GENERATED one.

**Smallest failing case:** generate → edit any item (or add one) → Back to Step 1 → Generate
again. The edit/addition is gone; no error, no ledger note of the loss beyond the bulk record.

## Why it matters

The V1 regenerate path got this right (`clearPlanForRegeneration`: item-level predicate
`kind:'ITEM' AND source:'GENERATED' AND isProtected:false`, then a guarded empty-team sweep).
The V2 rerun path predates the same care. Until [[GTC-236]] ships, this rerun is Kate's ONLY
regenerate on V2 events — the destructive path is the default path.

## Needs scoping when pulled

Candidates, not a ruling: adopt item-level clearing in finalize-plan's rerun (mirror
`clearPlanForRegeneration`, mapping new output into surviving teams); or route the rerun
through [[GTC-236]]'s `regenerate-plan` semantics; or gate the Step-1 re-generate behind the
new endpoint entirely. Whichever is chosen, the ticket's Do-Not-Touch on initial-generation
behavior needs an explicit carve-out for the rerun branch.
