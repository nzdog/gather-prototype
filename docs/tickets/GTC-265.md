# GTC-265 — Resend errors are never inspected

**Status:** Open — **filed, not started.** Filed 2026-09-01 | **Branch:** TBD
**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low

## The sibling — read [[GTC-264]] beside this

**Together they are one sentence: Gather never checks what actually happened, provider by

| | SMS | Email |
|---|---|---|
| Ticket | [[GTC-264]] | **this one** |
| What is trusted | the provider **accepted** the message | the SDK call **did not throw** |
| What is never read | TNZ's delivery result (`Status=Failed`, `Result="Destination is blacklisted"`) | Resend's returned `error` object |
| Consequence | a blacklisted number reads as delivered | an invalid key reads as sent |

**They are not the same bug and must not be merged.** GTC-264 builds a **missing channel** —
delivery receipts do not exist in the tree, and ingesting them is a feature. This one reads a value
**already sitting in a variable** that the code throws away. That is why this is a bug at `high` and
that is a feature: one is work, the other is an omission.

## Signal

**Expected**
When Resend rejects a send, the caller learns it: `sendNudgeEmail` in `src/lib/email.ts` returns
`{ success: false }`, `POST /api/events/[id]/people/[personId]/nudge` answers 502 as it already does
for the SMS leg, no `NUDGE_SENT_HOST` is logged, and no cooldown starts.

**Actual**
Nothing is sent and the host is told it was. Measured 2026-09-01 against the configured
`RESEND_API_KEY`:

```
resend.emails.send(…) →
  {"data":null,"error":{"statusCode":401,"name":"validation_error","message":"API key is invalid"}}
```

**The Resend SDK RETURNS its error rather than throwing it.** `sendNudgeEmail` awaits the call inside
a `try`, never looks at the result, and returns `{ success: true }`. The route then:

1. answers **200**;
2. calls `logInviteEvent` (`src/lib/invite-events.ts`) to write **`NUDGE_SENT_HOST`**, with
   `contactMethod: 'email'`;
3. starts the 24-hour window that `COOLDOWN_MS` in that route enforces — so **the retry of a message
   that never left is refused with 429** for a day.

The host's surface says `Reminded.` The audit trail says it was sent. Neither is true.

**Smallest failing case**
With any invalid or revoked `RESEND_API_KEY`, nudge an email-only guest. The UI reports success and
an `InviteEvent` of type `NUDGE_SENT_HOST` appears.

**⚠ WRONG IN ANY ENVIRONMENT, NOT A DEV-CREDENTIALS ISSUE.** [[GTC-247]] records that no provider
authenticates in local dev, and that is what made this visible — but the defect is not about the key
being wrong. A **production** key revocation, a suspended domain, a rate limit, a bounce rejected at
submission, or a Resend outage all arrive by the same door: a returned `error`, unread. Production
would report every one of them as sent.

**Contrast, from the same walk: the SMS leg is honest.** `sendSms` in `src/lib/sms/send-sms.ts`
returns `{ success: false, blocked: 'SMS_DISABLED' }`, the route answers **502**, and **no**
`NUDGE_SENT_HOST` is written. The two legs of one route disagree about whether a failed send is a
failure.

| Leg | Provider result | Route | InviteEvent | Cooldown |
|---|---|---|---|---|
| SMS | `{success:false, blocked:'SMS_DISABLED'}` | **502** | none | not started |
| Email | `{data:null, error:{401,…}}` | **200** | `NUDGE_SENT_HOST` | **started** |

## Scope

**Fix here:**
- `src/lib/email.ts` — **all three senders**: `sendNudgeEmail`, `sendMagicLinkEmail`,
  `sendWelcomeEmail`. Each awaits `resend.emails.send` and discards the returned object.
- `src/app/api/auth/claim/route.ts` — a **fourth** call site, calling `getResendClient()` and
  `emails.send` inline with the same omission.

⚠ **The founder's stated scope was `sendNudgeEmail` alone. Widening it to four sites is recorded
here rather than done quietly**, because the other three are the identical omission in the same
file and fixing one would leave the ticket's own reasoning false. If the widening is unwanted, cut
it to `sendNudgeEmail` — but say so, because the auth path is the more serious of the two.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding.

⚠ **STOP CONDITION 5 FIRES BY DESIGN ON TWO OF THE FOUR SITES.** `sendMagicLinkEmail` and
`src/app/api/auth/claim/route.ts` are **Do-Not-Touch Zone 2** (magic-link auth flow) — the sole
authentication mechanism. The executor must stop and obtain explicit approval before changing
either, and must not fold that approval into the nudge fix.

⚠ **AND DO NOT "FIX" THE ENUMERATION PROTECTION WHILE YOU ARE IN THERE.** Both auth routes return a
generic `{ ok: true }` on failure **on purpose**, so an attacker cannot use the response to learn
which addresses exist. That is correct and must stay. The gap there is not the response shape — it
is that **the server does not know either**: nothing is logged, nothing alerts, and the only signal
that a user was silently locked out is the user saying so. The fix for those two sites is a
server-side record, not a changed status code.

## Acceptance

**Test gate** — severity High: **test-first required.**

The RED test is cheap and does not need a live provider: the senders take their client from
`getResendClient`, so a test can drive them against a stub that returns Resend's own failure shape
(`{ data: null, error: { statusCode: 401, name: 'validation_error', message: 'API key is invalid' } }`)
and assert the caller's behaviour. **Assert on the returned SHAPE, not on a thrown exception** — the
whole defect is that nothing throws.

**Assertions**
- [ ] `sendNudgeEmail` returns `{ success: false }` and surfaces Resend's message when `error` is
      non-null.
- [ ] `POST /api/events/[id]/people/[personId]/nudge` answers **502** on that path, matching the SMS
      leg's existing behaviour on the same route.
- [ ] **No `NUDGE_SENT_HOST` `InviteEvent` is written for a failed send** — this is the assertion
      that matters most, because the row is what makes the cooldown refuse the retry.
- [ ] **The cooldown does not start**, so an immediate retry is not 429.
- [ ] A SUCCESSFUL send is unchanged: 200, one `NUDGE_SENT_HOST`, cooldown starts. A fix that
      reports every send as failed passes four of the five above.
- [ ] Adjacent flows unaffected: the SMS leg of the same route (`sendSms`, still 502 with no log);
      `test:host-nudge`; `test:nudge-provider-gate`; `test:security`; the glance suites
      (`test:glance-actions` asserts the surface reports whatever the route reports, in both
      directions).
- [ ] If the auth sites are approved and included: a failed magic-link send is **recorded
      server-side**, and the route's response to the caller is **byte-identical** to the success
      case.

## Unknowns

1. **Where a failed auth send should be recorded.** `InviteEvent` is scoped to an event and a
   person; a magic-link failure has neither. A log line may be the whole of it, or it may want a
   row somewhere. Unresolved, and it is the reason the auth sites are separable from the nudge fix.
2. **Whether a failed nudge should be recorded at all**, rather than merely not recorded as sent.
   `sendSms` writes `SMS_BLOCKED_INVALID` and `SMS_BLOCKED_OPT_OUT` rows for its own refusals, so
   there is a house precedent for a negative record — but no `EMAIL_FAILED` type exists in the
   `InviteEventType` enum, and adding one is schema. **If that is wanted, Stop Condition 7 fires.**
   Not adding one is a complete fix for everything above.
3. **Whether Resend distinguishes "rejected" from "accepted then bounced".** This ticket only closes
   the first. If a message accepted at submission can still fail later, that is the email half of
   [[GTC-264]] and it is a different ticket again — do not scope-creep into it here.
