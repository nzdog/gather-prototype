# GTC-205 — Host team-detail float-to-top fix — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** e0eb07d | **Effort:** low

## Context

GTC-170 (B1) removed the coordinator view's (`c/[token]`) critical-first
float-to-top at both the client-sort layer and the API `orderBy` layer, per
Moment 4 spec §8.2: "Critical items in the grid — RESOLVED: badge... No
float-to-top, no message-only." During that ticket's verification, the
identical dual-layer pattern was found in the host team-detail view
(`h/[token]/team/[teamId]`) and its API route — contradicting the discovery
report's claim that this view was "already correct." It was explicitly
flagged as out of scope for GTC-170 (a `type: build` ticket naming only
`c/[token]/page.tsx`) and spawned as a follow-up task instead of fixed
silently. This ticket is that follow-up.

**Spec check:** §8.2 rules on "the grid" generically ("badge... visible in
the grid. No float-to-top, no message-only") — it does not carve out a
different rule for the host's read-only team-detail grid versus the
coordinator's. No other spec section (§8.3, §8.6) distinguishes host vs.
coordinator item ordering. Treated as the same rule GTC-170 already applied.

## Scope

**Fix here:**
- Remove the client-side critical-first sort in
  `src/app/h/[token]/team/[teamId]/page.tsx`.
- Remove the `orderBy: [{ critical: 'desc' }, ...]` pre-sort in
  `src/app/api/h/[token]/team/[teamId]/route.ts`.
- Confirm the badge renders unconditionally on `item.critical` (it already
  did — no `!item.assignment &&` gate existed on this page, unlike the
  coordinator view GTC-170 had to un-gate).

**Do not touch:** coordinator view (`c/[token]`) or the generation path —
GTC-170 owns those and they're closed. `PersonEvent` records. Any
Do-Not-Touch Zone in `GATHER-BUILD-CONSTANTS.md`.

## What was built

**`src/app/h/[token]/team/[teamId]/page.tsx`** — the sort that put
unassigned-first then critical-first then alphabetical was deleted;
`sortedItems` is now `data.items` in natural (API) order:

```diff
- const sortedItems = [...data.items].sort((a, b) => {
-   if (!a.assignment && b.assignment) return -1;
-   if (a.assignment && !b.assignment) return 1;
-   if (a.critical && !b.critical) return -1;
-   if (!a.critical && b.critical) return 1;
-   return a.name.localeCompare(b.name);
- });
+ const sortedItems = data.items;
```

**`src/app/api/h/[token]/team/[teamId]/route.ts`** — the `Item.findMany`
`orderBy` changed from `[{ critical: 'desc' }, { name: 'asc' }]` to
`[{ displayOrder: 'asc' }, { createdAt: 'asc' }]`, matching the natural-order
convention `c/[token]`'s API route now uses (GTC-170) and its siblings
(`.../items/route.ts` routes).

The badge markup (`AlertCircle` icon + `CRITICAL` label, both gated only on
`item.critical`) was already unconditional on this page — the coordinator
view's `!item.assignment &&` gate that GTC-170 had to drop never existed
here. No change needed for that half of the pattern.
