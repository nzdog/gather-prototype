# GTC-315 — The 90-day expiry nothing renews, and the dead link it publishes

**Status:** Open — filed 2026-09-18, not started | **Branch:** TBD
**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low
Escalated (brand/trust risk): **yes, on the second half.** The first half is an internal
gap. The second half is a guest tapping their own name on a link their host sent them and
landing on nothing.

⚠ **DO-NOT-TOUCH ZONE 3** (AccessToken & scope). Renewal is token issuance. Surface the
shape and get explicit approval before writing code, in the form [[GTC-256]] phase 3 and
[[GTC-294]] both used.

*Filed out of [[GTC-294]] on founder instruction, 2026-09-18: "FILE WAY 2. Its second half
earns it: the directory filters on scope and not on expiresAt, so a lapsed ask is
published, resolveToken rejects it, and a guest clicks their own name and gets nothing.
That is guest-facing and it is a dead link rather than an internal gap."*

This is **way 2 of the three** [[GTC-262]]'s evidence named as ways a coordinator ends up
without a working ask. [[GTC-294]] fixed way 1 and named 2 and 3 as out of scope rather
than leaving them to be discovered. Way 3 remains unfiled and is [[GTC-189]]'s.

---

### Signal

**Expected**
A link a host has sent to a guest keeps working for as long as the event is live. If it
cannot, the guest is not shown it.

**Actual**
Two separate defects that compound, and the second is the one that reaches a guest.

**1. Nothing renews.** `ensureEventTokens` in `src/lib/tokens.ts` sets
`expiresAt` to 90 days at creation, and **every branch in it only creates a MISSING row**.
No branch refreshes `expiresAt` on a row that already exists — `tokenExists` finds the row
and the loop moves on. So the clock starts at first issuance and never restarts, however
many times the function runs afterwards.

**2. The directory publishes the lapsed ones anyway.**
`GET /api/gather/[eventId]/directory` narrows its token query on **scope** —
`SHAREABLE_ACCESS_TOKEN` is `{ scope: 'PARTICIPANT' }` — and **not** on `expiresAt`. So a
lapsed token is emitted with `tokenPrefix: 'p'`, the page renders it as a working link,
`resolveToken` in `src/lib/auth.ts` then rejects it, and the guest gets nothing. They are
not told the link is old; they are shown their own name and handed a dead one.

**Smallest failing case**
An event whose tokens were issued more than 90 days ago. Load its directory
unauthenticated, click any name.

**Measured — 2026-09-18, `gather_dev`**

```
scope        total  past expiresAt  no expiry
HOST             8              2          0
COORDINATOR     19              8          0
PARTICIPANT     71             49          0
```

**49 of 71 participant tokens are already lapsed**, and every one of them is still
published by the directory to anyone holding the event id.

⚠ **AND [[GTC-294]] ADDED ROWS TO THE AFFECTED POPULATION.** That ticket issues every
`role: 'COORDINATOR'` membership a PARTICIPANT token — 16 memberships across 6 events in
`gather_dev`, which will be minted by ordinary traffic rather than a migration. Those
tokens start a 90-day clock that nothing will restart, and they are emitted by the same
unfiltered directory query. GTC-294 named this and deliberately did not fix it; it is
this ticket's.

---

### Why the expiry is not currently doing the work it appears to

[[GTC-262]] found this while measuring something else and recorded it:

> **9 of the 16 were still inside `expiresAt`** — the other 7 had lapsed. Expiry was doing
> unearned work here; it is a 90-day clock on stale seed data, not a control.

That is the shape of the whole problem. The expiry column looks like a security control and
behaves like an accident: it neither reliably closes an old credential (nothing prunes the
row, nothing stops it being published) nor reliably keeps a live one working (nothing
renews it). **Both directions fail, and they fail toward different harms** — a lapsed token
is a dead link for the guest, and a *published* lapsed token is a dead link the system
actively hands out.

### Scope

**Where it lives:**
- `src/lib/tokens.ts` — `ensureEventTokens`, the `expiresAt` assignment and every branch
  that skips an existing row.
- `src/app/api/gather/[eventId]/directory/route.ts` — the token query, and
  `src/lib/eligibility/shared-link-exposure.ts`'s `SHAREABLE_ACCESS_TOKEN`, which is the
  one place the rule about what may be published now lives ([[GTC-262]]).
- `src/app/gather/[eventId]/directory/page.tsx` — the `token: null` branch and its copy,
  if the answer is to withhold rather than to renew.
- `src/lib/auth.ts` — `resolveToken`, which is the thing doing the rejecting. **Read only
  unless the shape requires otherwise; [[GTC-262]] and [[GTC-294]] both left it untouched
  and said so.**

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding. Zone 3 covers both
  halves of this and is entered under approval only.
- [[GTC-256]]'s HOST revocation and the COORDINATOR prune in `ensureEventTokens`. Neither
  is about expiry and neither is widened here.
- [[GTC-294]]'s step 4b. A coordinator's ask is issued; whether it is *renewed* is this
  ticket's, and it is the same question for every scope.
- The claim route's refusal. It keys on `PersonEvent.role` and expiry is not a role.

---

### Unknowns — all three are product decisions, not implementation details

1. **Renew, or lengthen, or drop the expiry?** Three different answers with three different
   risk profiles. Renewing on every `ensureEventTokens` call means a token's life is a
   function of how often the host opens her plan page, which is not a policy. Lengthening
   moves the cliff without removing it. Dropping `expiresAt` makes every issued credential
   permanent, which is a real widening on a surface [[GTC-262]] ruling 2 confirmed is
   **still a credential dispenser** — it hands a working PARTICIPANT token to anyone holding
   the event id, with the 409 as its only friction.
2. **Should the token's life be tied to the EVENT rather than to a clock at all?** The
   natural boundary is `Event.endDate`: an ask is meaningless after the day it was about,
   and `SENT_AND_LIVE` in `src/lib/lifecycle.ts` already expresses "this event is still
   live" for the chase finders. A token that expires with its event needs no renewal and no
   arbitrary 90.
3. **What does the directory show for a guest whose token has lapsed?** Withholding it
   lands them on the `token: null` branch, whose copy [[GTC-262]] wrote under a constraint
   that still applies: it must be true of more than one population, because a marker
   distinguishing them would let an unauthenticated caller enumerate who holds write
   access. That copy currently reads *"No link for {name} in this directory. Coordinators
   get theirs from the host directly — and so does anyone added since invitations went
   out."* ⚠ **[[GTC-294]] already removed one of that sentence's two audiences.** If lapsed
   guests are added to it, it needs re-reading rather than inheriting.

⚠ Per the house rule an executor reaching any of these stops and asks rather than
inferring.

### Stop Conditions

Standard eight from `BUG-TICKET-TEMPLATE.md`, plus:

9. **Do not resolve unknown 1 or 2 by inference.** They are what the ticket is for.
10. **Do not fix the publication half and call the renewal half done, or the reverse.**
    They compound, and either alone leaves a guest with a dead link — withholding without
    renewing means a lapsed guest silently loses their row's link, and renewing without
    filtering means the rows already lapsed stay published until someone opens the plan
    page.
