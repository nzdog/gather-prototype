the fix's effort is undetermined; no fix is proposed here)

### Signal

**Expected**
`PersonEvent.sentAt`'s own schema comment (`prisma/schema.prisma`, on the `sentAt` field):

> GTC-168 (A2): THIS person's send clock — the mini-send anchor (Hinge §2, gap #5). Set to
> `Event.sentAt` at the press; **set to `now()` for anyone added afterwards**, so their nudge
> cadence and red-by-time run from THEIR send date, truncated by the event date.
> `isMiniSend = PersonEvent.sentAt > Event.sentAt` — no extra field.

**Actual**
The predicate is built and correct. **The data shape it tests for is unreachable.**

`isMiniSend(personEvent, event)` exists at `src/lib/lifecycle.ts` — exported, pure, and pinned by
`tests/lifecycle-predicates-test.ts` Suite 5, which asserts among others:

```
'person sent after the press → mini-send',  isMiniSend({ sentAt: LATER }, sentEvent) === true
```

That assertion passes on a hand-built object. **No production write path can produce it.** All
four post-press add paths write `event.sentAt` — the *original press time* — not `now()`:

| Path | Written |
|---|---|
| `POST /api/events/[id]/people` (`src/app/api/events/[id]/people/route.ts`) | `sentAt: event.sentAt ?? null` |
| `POST /api/events/[id]/people/batch-import` | `sentAt: event.sentAt ?? null` |
| `POST /api/events/[id]/households` | `sentAt: event!.sentAt ?? null` |
| `reconcileHouseholdMembers` (`src/lib/households/reconcileMembers.ts`), reached from `PUT /api/events/[id]/households/[householdId]` | `sentAt: sentAt ?? null`, where `sentAt` is the caller's `event.sentAt` |

Each carries the comment *"GTC-196 (A3b) — THE MINI-SEND CLOCK GOES LIVE"* or a pointer to it, so
the intent is explicit and the implementation contradicts it. `POST /api/join/[token]/claim`
mentions mini-sends in a comment but writes no `sentAt` at all — a claimant keeps whatever their
`PersonEvent` already had.

**So `isMiniSend` returns false for every row the application can create.** It has no production
caller today either — the only reference outside comments is its own unit test. The unit test is
green; what it proves is that the function is correct, not that the state exists.

**Consequences**
1. **A late-added person is instantly past their nudge windows.** Under [[GTC-178]]'s day-4/day-7
   cadence, someone added on day 6 has a `sentAt` six days old, so both nudges become eligible on
   the next 15-minute cron tick — two SMS in immediate succession to someone invited minutes ago.
2. **The walk's own example is the failing case.** Hinge §2, gap #5: *"a Bob added three days out
   may pass straight to Kate's line"* — the arithmetic that was supposed to make that fall out
   with no special case does not run.
3. **A live tombstone is waiting on a condition that cannot currently become true.**
   `PeopleSection.tsx` hides Auto-Assign on a sent event because "until the mini-send machinery
   exists, nobody it asks would ever be TOLD," and says to delete the condition when GTC-189 and
   GTC-178 land. GTC-178 alone will not satisfy it.

**Smallest failing case**
1. Press send on an event (sets `Event.sentAt` and stamps every existing member).
2. Six days later, add one person via `POST /api/events/[id]/people`.
3. Read that person's `PersonEvent.sentAt` — it equals `Event.sentAt` (six days old), not `now()`.
4. `isMiniSend(personEvent, event)` returns false. Under GTC-178's cadence they are immediately
   day-4 *and* day-7 eligible.

### Scope

**Fix here:**
**NOT DETERMINED BY THIS TICKET.** Candidate directions, none ruled: (a) the four add paths write
`now()` when `event.sentAt` is already set, per the schema comment; (b) the schema comment is
amended to match the code and `isMiniSend`'s meaning is re-derived; (c) the pre-launch data
cleanup disposes of it, per the founder ruling. Which is right is a product question about what a
late-added guest's clock should mean — [[GTC-196]]'s or [[GTC-189]]'s to settle, not this filing's.

Note for whoever scopes the fix: `isMiniSend` has **no production caller**, so changing the writes
alone would alter cadence behaviour for late-added people with no reader to validate it against.
Scope the reader and the writer together, or neither.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- [[GTC-178]]'s cadence rework. That ticket's Ruling 8 explicitly declines this fix; it reads
  `PersonEvent.sentAt` as it finds it.
- The `Event.sentAt` press stamping itself (both `confirm-invites-sent` routes) — that half is
  correct: the press genuinely is one act for the whole existing cohort (Hinge §7).
- `isMiniSend` and its Suite 5 assertions in `tests/lifecycle-predicates-test.ts` — the predicate
  is not what is broken. Do not weaken the test to match the reachable data.

Contained today by two facts, **neither of which is a property of this code**: the database holds

`blocked: 'SMS_DISABLED'` before anything is dispatched. Restoring SMS credentials *and* having
real late-added guests makes the immediate double-send real with no code change required. Same
containment shape as [[GTC-252]]; it should not be mistaken for a fix.
