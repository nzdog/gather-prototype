# GTC-289 — Ingest email delivery results

**Status:** Open — **scoped, not designed. Filed to close a named gap, not to be built next.**
Filed 2026-09-12 | **Branch:** TBD
**Severity:** [ ] Critical [ ] High [x] Medium [ ] Low
Escalated (brand/trust risk): [x] Yes — but deferred. The Hinge spec's bounce rule is written
against email and there is no email bounce signal anywhere in the tree. The glance cannot go
red for a dead email channel because nothing can tell it one exists.

**Filed 2026-09-12**, on a gap found while rescoping [[GTC-229]] and [[GTC-264]] against the
TNZ correspondence. Tree verified at `d1577b7` (GTC-222 rule 5).

---

## Why this exists — it was named by another ticket and declined

[[GTC-265]] *Unknowns* 3 says it outright:

> **Whether Resend distinguishes "rejected" from "accepted then bounced".** This ticket only
> closes the first. If a message accepted at submission can still fail later, that is the
> email half of [[GTC-264]] and it is a different ticket again — do not scope-creep into it
> here.

**This is that ticket.** It was correctly declined there and correctly filed here.

[[GTC-265]] is fixed. What it fixed is the **send-time** half: `resend.emails.send` returns
its error rather than throwing, and all four call sites discarded it — `sendMagicLinkEmail`,
`sendNudgeEmail` and `sendWelcomeEmail` in `src/lib/email.ts`, plus an inline call in
`src/app/api/auth/claim/route.ts`. A failed email reported success. That is closed.

**What is still open is everything that happens after submission succeeds.** An email that
Resend accepts can still bounce. Nothing in the tree ever learns that it did.

## The gap, verified

A tree-wide search at `d1577b7` for `bounce`, `delivery-receipt`, `DLR`, `deliveryStatus`,
`deliveredAt` and `statusCallback` across `src/` and `prisma/schema.prisma` returns **zero
hits**. Independently:

- **No route.** The only inbound webhooks in the tree are
  `src/app/api/webhooks/stripe/route.ts` and `src/app/api/sms/inbound/route.ts`. There is no
  Resend webhook endpoint.
- **No schema.** `InviteEventType` has eighteen members and **not one names a delivery
  outcome**, for either channel. [[GTC-265]] *Unknowns* 2 records that no `EMAIL_FAILED`
  type exists and that adding one is schema.
- **No red source.** `RED_REASONS` in `src/lib/glance/state.ts` is exactly
  `['DECIDE_BY_EXPIRED', 'REVERSAL', 'EXHAUSTED_SILENCE']`. There is no bounce, from either
  channel.

## Why it matters — §7's bounce rule is written against EMAIL

This is the part that makes the gap worth a ticket rather than a note.

The Hinge spec §7 (`docs/03_specs/gather-hinge-spec-v1.md`) states the rule:

> **Bounces are red on arrival.** A bounce is not a silence — it's a dead channel; nudging it
> sends more messages into the same void. The system is out of moves *immediately*, so the
> ask goes red at once, transparently: she sees exactly what's going on — *twelve are away,
> two bounced.*

And §7 again, on why the distinction is load-bearing:

> **The colours know the difference.** Never-reached (red at once) can never be mistaken for
> reached-and-quiet (amber, with its nudge-clock). No silence gets nudged into a void for
> days and goes red for the wrong reason.

**§6's ground truth is Kate's Christmas email**, sent 8:58am, with replies at 9:39, 9:50 and
10:48. The illustration §7 reasons from — *"twelve are away, two bounced"* — is an email
send. **The spec's bounce rule is drawn from the email channel, and the email channel is the
one with no delivery signal at all.**

[[GTC-264]] makes the **SMS** half possible. This ticket is the other half. Without it, §7's
rule is implementable for the channel it was not written about and not for the channel it
was.

## What this ticket must establish first

**Mirroring Moment 4 §10.9's instruction shape**, which is how [[GTC-264]] was born: *"Its
ticket's first task: investigate TNZ delivery-receipt capability. If webhooks exist, wire
them."*

**This ticket's first task: investigate Resend's delivery-event capability.** Specifically,
and before any design:

1. Whether Resend report asynchronous delivery events at all, and by what mechanism.
2. The event vocabulary — and in particular whether a **hard bounce** (dead channel) is
   distinguishable from a **soft bounce** (transient) and from a **complaint** or
   **suppression** (a live address that does not want mail). This is the same partition
   [[GTC-264]] must make for TNZ's `Result` values, and it matters for the same reason.
3. How an event correlates back to a send. [[GTC-264]] has `MessageID` captured on every
   send and never read; the email path has no equivalent recorded anywhere — **verify
   whether the four senders retain any provider id at all.** [[GTC-265]] made them inspect
   the result; whether they *keep* an id from it is a separate question and is this ticket's
   to answer.
4. Authentication on the callback, if it is a webhook.

**Do not design against a guessed contract.** That is the error [[GTC-258]] declined to make
about TNZ's send-response wire format, and [[GTC-264]] carries the same restraint. It
applies here with equal force.

## What it would unblock

- **§7's bounce rule for the email channel** — the channel the rule was written about.
- **[[GTC-192]]'s bounce red, for email.** [[GTC-192]] Ruling 14 is implemented as
  `worst !== 'GREEN'` in `derivePersonState` rather than as a list of red reasons, precisely
  so that *"a reason list would need extending by every future red source"*. A bounce red is
  displaced correctly the day it exists — for either channel. **Owner remains [[GTC-192]]**
  for the red source itself; this ticket supplies the data and does not add a `RED_REASON`.
- **The email fallback's honesty.** `dispatchPendingWrapUpMessages` in `src/lib/wrap-up.ts`
  uses email as the fallback when SMS fails. A fallback that can itself fail silently after
  acceptance is a fallback with an unmeasured failure rate.

## Ordering — deliberately NOT next

**This ticket is filed to close a named gap, not to be built now.** Recorded so the sequence
is explicit rather than implied:

1. [[GTC-264]] — the SMS delivery channel, and the shared credential.
2. [[GTC-258]] — the stamps made honest.
3. [[GTC-229]] — MO authentication.
4. [[GTC-288]] — MO parse and opt-out sync.
5. **This ticket, and [[GTC-192]]'s bounce red** — last, and both gated on a delivery-result
   vocabulary that only a live trial produces.

**The argument for filing it now rather than later** is that §7's rule reads as implementable
once [[GTC-264]] lands, and it is not. Leaving that unrecorded invites someone to build the
bounce red on SMS data and believe §7 is satisfied.

## Unknowns

1. **Everything in *What this ticket must establish first*.** All four items block design.
2. **Whether the email path retains a provider message id.** [[GTC-264]]'s join key was
   already being captured by accident. There is no reason to assume the same luck here.
3. **Whether "delivered" is affirmative or merely the absence of a failure.** The same
   question [[GTC-264]] *Unknowns* 4 escalates for SMS, and it has the same consequence: if
   only failures are reported, a green on the glance means *"no failure reported yet"*
   rather than *"it arrived"*. **Whatever answer each provider gives, the glance must not
   present two different meanings behind one colour.** If SMS and email differ on this, that
   is a product question, and it is bigger than either ticket.

  authenticate, which is tracked under [[GTC-247]].

  [[GTC-264]]'s SMS channel, [[GTC-192]]'s red source, and the wrap-up fallback's behaviour
  are each named and excluded. If any becomes load-bearing → stop.
