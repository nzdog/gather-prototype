## Why it matters — §7's bounce rule is written against EMAIL

This is the part that makes the gap worth a ticket rather than a note.

The Hinge spec §7 (`docs/03_specs/gather-hinge-spec-v1.md`) states the rule:

> **Bounces are red on arrival.** A bounce is not a silence — it's a dead channel; nudging it
> sends more messages into the same void. The system is out of moves *immediately*, so the
> ask goes red at once, transparently: she sees exactly what's going on — *twelve are away,
> two bounced.*

And §7 again, on why the distinction is load-bearing:

> **The colours know the difference.** Never-reached (red at once) can never be mistaken for
> reached-and-quiet (amber, with its nudge-clock). No silence gets nudged into a void for
> days and goes red for the wrong reason.

**§6's ground truth is Kate's Christmas email**, sent 8:58am, with replies at 9:39, 9:50 and
10:48. The illustration §7 reasons from — *"twelve are away, two bounced"* — is an email
send. **The spec's bounce rule is drawn from the email channel, and the email channel is the
one with no delivery signal at all.**

[[GTC-264]] makes the **SMS** half possible. This ticket is the other half. Without it, §7's
rule is implementable for the channel it was not written about and not for the channel it
was.

## ✅ INVESTIGATION DONE 2026-09-19, AND THE MECHANISM IS THE POLL — THIS REVERSES THIS TICKET'S STATED SHAPE

*Read this before the section below, which the investigation answers and partly overturns.*

**This ticket assumed a webhook.** *"Then the webhook route, verification, and idempotent storage
keyed on the provider id"* — because a bounce ingest usually is one. **Founder ruling, 2026-09-19,
taking the poll instead:**

> THE POLL FIRST. `last_event` is a closed twelve-value union that exists in this tree today; the
> webhook's bounce detail is two untyped strings that need a live trial to learn. The poll needs no
> public URL, no signature scheme, no third `SHARED_SECRETS` entry and no pinned-count change, and it
> runs on the cron pattern slice 5c already built. Worse latency, better everything else — and the
> board is not a real-time surface.
>
> Record that this reverses GTC-289's stated shape and why: the ticket assumed the webhook because
> that is what a bounce ingest usually is, and the poll turns out to be the mechanism whose vocabulary
> we actually have.

**BOTH MECHANISMS EXIST**, established from `resend@6.22.0`'s shipped declarations at
`node_modules/resend/dist/index.d.mts`:

- **POLL** — `resend.emails.get(id)` answers `GetEmailResponseSuccess`, whose **`last_event` is a
  CLOSED union of twelve**: bounced, canceled, clicked, complained, delivered, delivery_delayed,
  failed, opened, queued, scheduled, sent, suppressed.
- **WEBHOOK** — `resend.webhooks.create({ endpoint, events })` returns `{ id, signing_secret }`;
  `resend.webhooks.verify({ payload, headers: { id, timestamp, signature }, webhookSecret })` returns
  a typed `WebhookEventPayload`. The signature scheme is **Standard Webhooks**
  (`standardwebhooks@1.0.0`, already an SDK dependency), headers `webhook-id` / `webhook-timestamp` /
  `webhook-signature`, and replay protection is inside the library — a route must not re-implement it.
  `WebhookEvent` has 19 members, eleven of them email.

### ⚠ WHAT THE POLL STILL CANNOT ANSWER — recorded plainly on founder instruction

> Whether `delivered` is affirmative or merely no-failure-yet is Unknown 3 and the poll does not
> settle it. Neither does it give the hard/soft partition, since `last_event` has one `bounced` member
> with no type beside it. So **the poll gets the fact of a bounce and not its kind** — record that
> plainly, because §7's red-on-arrival rule needs the fact and its door needs the kind.

- **UNKNOWN 3 IS UNSETTLED.** `last_event: 'delivered'` is what the provider reported, not what
  happened to the message, and nothing in the SDK's types says which. So the interpreter's kind is
  `PROVIDER_REPORTS_DELIVERED` and **there is no exported boolean claiming arrival** — asserted.
- **THE HARD/SOFT PARTITION IS NOT AVAILABLE FROM THE POLL.** One `bounced` member, no type beside
  it. The webhook's `EmailBounce` does carry `{ message; subType; type }` — **and all three are bare
  `string` in the SDK; it names the fields and enumerates nothing.** So the partition needs the
  webhook AND an observation, and the vocabulary is [[GTC-323]]'s to obtain.
- **THE CONSEQUENCE, STATED:** Hinge §7's *"bounces are red on arrival"* needs **the fact**, and the
  poll supplies it. Ruling U's bounce door — *send again to the same address* versus *edit it* versus
  *send to the phone* — needs **the kind**, because the first action is right for one kind of bounce
  and useless for another. **So §7 becomes implementable for email and ruling U's door does not.**

### ✅ NO HARD/SOFT PARTITION IS ASSERTED, IN ANY PHASE — ruled

> That is the thing to refuse to invent, and your reason is the ruling: a wrong partition turns a
> transient bounce into a permanent red, and §7's rule is the thing being implemented.

### ⚠ THE ID JOIN IS UNVERIFIED, AND IT IS THE FINDING OF THE INVESTIGATION

This ticket's establish-first item 3 asked whether the email path retains a provider id. **It does** —
[[GTC-189]] slice 4b stores the send's `data.id` into `OutboundMessage.providerMessageId`. But:

- the **poll** answers with `id` **and** `message_id`;
- the **webhook** payload's `BaseEmailEventData` carries `email_id` **and** `message_id`;
- **neither of the event shapes has a field called `id`.**

`id` / `email_id` is the obvious match and `message_id` reads like the RFC 5322 header. **That is
inference and phase 1 does not build on it.** Both are carried through, unlabelled as the join key.
Slice 4b already recorded the cost of getting it wrong: *"a value that is not the provider's would
match nothing and read as a LOST BOUNCE rather than as a send that never happened."*

⚠ **AND IT IS THE SINGLE THING MOST LIKELY TO FAIL SILENTLY ON THE DAY A WORKING KEY EXISTS — IN THE
DIRECTION THAT LOOKS LIKE NOTHING HAPPENED.** Recorded on founder instruction, 2026-09-19.

**Every other unknown in this ticket announces itself.** An unrecognised `last_event` is flagged. A
malformed poll response is refused with a reason. A missing field is a red. A 22nd error code does not
compile. **A join on the wrong field returns zero rows, and zero rows is exactly what a quiet week looks
like.** Nothing distinguishes *no bounces arrived* from *every bounce failed to match* — not a log, not
a count, not the board.

**So the first live poll must verify the join explicitly — one accepted send, one poll, the two ids
compared — BEFORE any board reads a bounce off it.** That is one step, it costs nothing, and it is the
difference between a silent partial outage and a working feature. [[GTC-247]] is what makes it possible;
the note is in the module so the person doing it cannot miss it.

### ✅ `isRetryableProviderError` — WIDEN `SendResult`, AND IT IS THIS TICKET'S

> YES, widen `SendResult`. Your finding is that the predicate reads a string because a string is all
> it is given, and `resultOf` throws away a closed 21-value union and a status code. That is slice 6's
> to make, not slice 5's to revisit: slice 6 is the ticket that needs the distinction, and slice 5's
> own evidence already names the string match as owed.

The SDK declares `ErrorResponse { message: string; statusCode: number | null; name:
RESEND_ERROR_CODE_KEY }`, and `RESEND_ERROR_CODE_KEY` is a **closed 21-value union**:
`invalid_idempotency_key, validation_error, missing_api_key, restricted_api_key, invalid_api_key,
not_found, method_not_allowed, invalid_idempotent_request, concurrent_idempotent_requests,
invalid_attachment, invalid_from_address, invalid_access, invalid_parameter, invalid_region,
missing_required_field, monthly_quota_exceeded, daily_quota_exceeded, rate_limit_exceeded,
security_error, application_error, internal_server_error`.

**So the change is upstream of the predicate**: `resultOf` in `src/lib/email.ts` keeps `name` and
`statusCode` on `SendResult`, the dispatcher stores them, and `isRetryableProviderError` in
`src/lib/press/dispatch.ts` reads the code instead of matching prose. On the declared vocabulary the
retryable set is `rate_limit_exceeded`, `internal_server_error` and `application_error`; the
auth-terminal set slice 5c's guard exists for is `missing_api_key`, `restricted_api_key`,
`invalid_api_key` and `invalid_access`.

⚠ **NOT BUILT IN PHASE 1**, which was scoped as the envelope and the interpreter. It is a later phase
of this ticket, and it touches `src/lib/email.ts` and `dispatch.ts` rather than this ticket's own new
module — recorded against [[GTC-189]] slice 5c as well, so the owed string-match is findable from
both ends.

✅ **BUILT AS PHASE 2, 2026-09-19 — see *Evidence (phase 2)*.** Founder ruling: it went BEFORE the
migration, *"because a shipped predicate known to be reading the wrong field should not wait behind a
migration and a rehearsal."*

⚠ **AND ONE SENTENCE ABOVE WAS NOT BUILT AS WRITTEN: "the dispatcher STORES them".** It does not. A
column for the code is a migration, the widening was ruled to carry no schema, and `providerError`
stays the provider's words verbatim with no code prefix. **So the DECISION gets the code and the RECORD
does not** — a column is a candidate for this ticket's migration phase and is not assumed here. The
phase 2 suite fences both halves: `prisma/schema.prisma` has no such column, and `recordRejection`'s
own body does not mention one.

## What this ticket must establish first

**Mirroring Moment 4 §10.9's instruction shape**, which is how [[GTC-264]] was born: *"Its
ticket's first task: investigate TNZ delivery-receipt capability. If webhooks exist, wire
them."*

**This ticket's first task: investigate Resend's delivery-event capability.** Specifically,
and before any design:

1. Whether Resend report asynchronous delivery events at all, and by what mechanism.
2. The event vocabulary — and in particular whether a **hard bounce** (dead channel) is
   distinguishable from a **soft bounce** (transient) and from a **complaint** or
   **suppression** (a live address that does not want mail). This is the same partition
   [[GTC-264]] must make for TNZ's `Result` values, and it matters for the same reason.
3. How an event correlates back to a send. [[GTC-264]] has `MessageID` captured on every
   send and never read; the email path has no equivalent recorded anywhere — **verify
   whether the four senders retain any provider id at all.** [[GTC-265]] made them inspect
   the result; whether they *keep* an id from it is a separate question and is this ticket's
   to answer.
4. Authentication on the callback, if it is a webhook.

**Do not design against a guessed contract.** That is the error [[GTC-258]] declined to make
about TNZ's send-response wire format, and [[GTC-264]] carries the same restraint. It
applies here with equal force.

### ✅ THE FIRST OBSERVED RESEND ENVELOPE IN THIS REPO

Measured with a syntactically valid but deliberately **invalid sentinel key** — no credential used,
refused at submission, nothing delivered, one request:

```
{ statusCode: 401, name: 'validation_error', message: 'API key is invalid' }
```

1. ✅ **The declared shape matches the live body.** Three fields, those names, `statusCode` a number.
   Slice 4b's *"the code and the stub would be wrong together"* limit is closed for the FAILURE
   envelope; the success envelope is still unobserved and [[GTC-247]] still owns it.
2. ✅ **`RESEND_401_BODY`, the stub GTC-265 wrote, is byte-identical to it.** ⚠ The executor first
   wrote into that file that the stub was *probably wrong* because `invalid_api_key` exists. The
   measurement corrected the correction, and the comment now records both directions.
3. ⚠ **RESEND ANSWERS AN INVALID KEY WITH `validation_error`** — not with any of the four codes whose
   names are about keys. **So the one code anybody has seen is classified `REQUEST_REFUSED` here, by
   its own name, and its observation was an AUTH failure.** Kept as-is: the code plainly covers request
   validation too, and reclassifying a general code on one sighting would be worse than a coarse kind.
   Both kinds are terminal, so the decision is identical either way.

⚠ **THE CONSEQUENCE, AND IT IS THE FINDING OF THIS PHASE: A KIND MUST NEVER BE SHOWN TO A HOST AS A
REASON.** The provider demonstrably reuses one code for two unrelated situations. The names are a
usable guide to *whether to retry* and a poor guide to *why*. [[GTC-323]] is what closes it, and it now
leads with that point on founder instruction.

**And a second measurement, from the mismatch stub** (body says 429, HTTP line says 500): the SDK's
`error.statusCode` is **the BODY's**. Nothing in this repo had ever read that field, and the retry's
second reading depends on it.

### ⚠ What it changes in this environment: NOTHING OBSERVABLE, said plainly

The observed envelope is `validation_error` / 401, which is `REQUEST_REFUSED` by the code and was
already terminal by the message (`/api[ _-]?key/`). **So no row's outcome changes today.** The
widening's value is that the answer stops depending on the provider's prose — and the proof is
therefore a mutation table and an observed shape, not a behavioural difference anybody can point at.
Stated so nobody reads the green suites as a demonstration that the retry got better.
