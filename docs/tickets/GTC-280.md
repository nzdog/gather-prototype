## Signal

**Expected**
A payment proves that money moved. Authentication proves who is asking. A
route that returns a session cookie for an account that already exists
requires the second, as `POST` in `src/app/api/auth/verify/route.ts` does —
it mints only after consuming a magic-link token sent to that address.

**Actual**
`POST` in `src/app/api/events/route.ts` treats a paid Stripe Checkout Session
as both. It retrieves the session, requires `payment_status === 'paid'`, reads
`stripeSession.customer_details?.email`, looks that address up in the `User`
table, and — whether the row was found or created — writes a `Session` with a
30-day expiry and sets the `session` cookie at `path: '/'`.

`POST` in `src/app/api/billing/checkout/route.ts` sets no `customer_email`, so
the address in `customer_details` is whatever the payer typed into Stripe's
own form. Nothing anywhere checks that the payer controls it.

**Smallest failing case**
Pay $12 through `/plan/new` and type a known host's address into Stripe's
email field. The browser returns to `/plan/new?session_id=…`, the page fires
`POST /api/events`, and the response carries `Set-Cookie: session=…` valid for
30 days for that host's `User`.

## 1. What exactly is the credential today

Traced through the two handlers, in order.

**What the route treats as proof of identity:** the string at
`stripeSession.customer_details.email`, on a Checkout Session whose
`payment_status` is `paid`.

**What that string actually proves:** that somebody completed a NZ$12 card
payment and typed that text into a form field. Nothing else.

The distinction is the whole bug, so state it flatly:

> **A Stripe receipt is a bearer proof of PAYMENT. It is being spent as a
> bearer proof of IDENTITY. Those are different claims, and only one of them
> was verified.**

Stripe's `customer_details.email` is a self-declared field in Checkout. Stripe
does not send a confirmation to it, does not require a click on it, and does
not represent it as verified. It is used to address a receipt. When
`customer_email` is not supplied on the Checkout Session — and `POST` in
`src/app/api/billing/checkout/route.ts` does not supply it — that field is a
free-text box the payer fills in.

Three checks stand between an anonymous caller and the cookie, and none of
them is an identity check:

- `if (!stripeSessionId)` → 402. A shape check.
- `stripe.checkout.sessions.retrieve(...)` in a try/catch → 400. Proves the
  id exists in this Stripe account.
- `stripeSession.payment_status !== 'paid'` → 402. Proves money moved.

Then the lookup:

```
let user = await tx.user.findUnique({ where: { email } });
if (!user) {
  user = await tx.user.create({ data: { email } });
}
```

`findUnique` on `User.email` is the entire binding. If the row exists, the
route adopts it. There is no branch that distinguishes "this account is new"
from "this account belongs to someone who has been using Gather for months",
and no branch that asks whether the caller can read the mailbox.

**The route's own header comment says so out loud:**
`// POST /api/events - Create new event (requires payment, no auth needed)`.
That comment is true. It describes a route that creates events. It was written
before the same handler also began returning a session for a pre-existing
account, and nobody noticed that "no auth needed" had stopped being a
description of the input and become a description of the output.

**The scanner already named it, in its own vocabulary.** `npm run
security:routes` (the [[GTC-268]] slice-1 scanner) classifies this handler:

```
  POST   /api/events
    THIRD_PARTY_RECEIPT
    Stripe checkout session retrieved and verified
```

`THIRD_PARTY_RECEIPT` is exactly right, and the word *receipt* is exactly the
problem. A receipt is an adequate credential for the thing it is a receipt
for — creating one paid event. It is not a credential for an account. That
verdict is pinned in `tests/security-route-scan-control.ts` as
`['POST src/app/api/events/route.ts', false, 'THIRD_PARTY_RECEIPT:PROVEN']`,
and the control file's own comment records [[GTC-268]]'s allowlist reason for
the route as *"it refuses unless `payment_status === 'paid'`"*. That reason
was accepted on the strength of what the route creates. It was never tested
against what the route returns.

### ⚠ FINDING 2 — the "new account" branch is not safe either

The founder's framing is *"an existing host's email address"*, and that is the
sharp case. But the `if (!user)` branch is the same defect with the damage
deferred.

Pay with an address that has no `User` yet, and the route creates the `User`,
creates a `Person` named `email.split('@')[0]`, and mints a 30-day session on
it. When the real owner of that address later signs in, `POST` in
`src/app/api/auth/verify/route.ts` does `user.findUnique({ where: { email } })`
and resolves to **the same row**. She joins an account a stranger already holds
a live session on, and there is no way for her to see that or end it (see
finding 4).

Recorded as its own finding rather than folded in, because a fix that only
guards the `user` branch closes the loud half and leaves this one open.

### ⚠ FINDING 3 — the cookie clobber, [[GTC-269]]'s finding 2 in a second route

`POST` in `src/app/api/events/route.ts` sets `session` at `path: '/'`
unconditionally:

```
response.cookies.set('session', sessionToken, { ... path: '/' });
```

That is the same cookie a real login uses, written by `POST` in
`src/app/api/auth/verify/route.ts`. [[GTC-269]] filed this exact shape as a
live product bug in `POST /api/demo/session` and fixed it there with a
cookie-presence check returning 409. **The identical shape in this route was
not in that ticket's scope and is still here.**

It needs no attacker. A host who is signed in as A, and who mistypes or
autofills a different address at Stripe, is silently signed out of A and into
B, with the event she just paid for attached to B. Both accounts now exist,
each holds part of her history, and nothing in the UI says what happened.

### ⚠ FINDING 4 — the victim cannot revoke it

`POST` in `src/app/api/auth/logout/route.ts` deletes exactly one row, keyed on
the caller's own cookie value. There is no session list, no "sign out
everywhere", and no `session.deleteMany` anywhere in `src/` — verified by
grep. A host who learns her account has been taken has no in-product action
that ends the other session. It stands for its full 30 days unless someone
deletes the row directly in the database.

This is why the 30-day lifetime matters more here than it did in
[[GTC-269]], where the fix could simply shorten it.

## 2. How discoverable is a host's email address

**Answer, stated plainly: not from the product. And that is the only thing
containing this.**

The lookup is on `User.email`. Swept for any surface that returns it, or any
`Person.email`, to a caller without a session or an access token:

- **`GET /api/gather/[eventId]/directory`** — the shareable family directory,
  unauthenticated and keyed on the event id alone. It returns names and access
  tokens and **no email addresses at all**. It also excludes the host: the
  `where` clause composes `ADDRESSABLE_PERSON_EVENT` in
  `src/lib/eligibility/host-exclusion.ts`, which bars both `Event.hostId` and
  any `role: 'HOST'` row, filtered in SQL. [[GTC-256]] ruling 5 put it there
  and `tests/host-directory-exposure-test.ts` holds it.
- **`GET /api/c/[token]`** — the coordinator view, and the widest thing an
  unauthenticated caller can reach today, because the directory hands out
  COORDINATOR tokens ([[GTC-262]], open). Its host block returns
  `{ name: hostToken.person.name }` and nothing else. Name, no address.
- **`GET /api/p/[token]`** — no host email in the payload.
- **The nine `GET /api/events/[id]…` reads** — closed by [[GTC-267]]. All now
  behind `requireEventRole`. The `?hostId=` parameter that made them a chain
  is gone from all three routes that honoured it.
- **`GET /api/events/[id]/host-household`** — the one route in the tree that
  selects `host: { select: { … email … } }`, and it calls
  `requireEventRole(eventId, ['HOST','COHOST'])` before it does.
- **Outbound mail** — `sendMagicLinkEmail`, `sendWelcomeEmail` and
  `sendNudgeEmail` in `src/lib/email.ts` all send `from: EMAIL_FROM`. No
  `replyTo`, no host address in any header or body.
- **Account-existence oracles** — deliberately absent. `POST` in
  `src/app/api/auth/magic-link/route.ts` returns `{ ok: true }` for every
  input including the error path, with a comment saying why. `POST` in
  `src/app/api/auth/claim/route.ts` does the same for a missing person, an
  already-claimed person and a rate-limited caller. Neither can be used to
  confirm a guess.

**So a stranger cannot get there from Gather.** They must arrive already
knowing the address, and Gather offers no way to test a guess short of paying
$12 — which is destructive, self-announcing (see below) and single-use.

**This narrows who can do it. It does not make it obscure.** The address is
ordinary personal information: a host's email is known to her guests, her
family, her employer, her mailing lists, and anyone who has ever received an
invitation from her. The population that both knows a host's address and might
want to read her event — who is coming, what everyone is bringing, every
guest's email and phone — is not strangers on the internet. It is people
around her. Requiring the attacker to know the victim selects *for* the people
best placed to do harm with it, not against them.

**This is the same shape [[GTC-267]] recorded and it should be read the same
way.** There the containment was that `cuid`s are not enumerable — "an accident
of the id format, not a control. It is the single reason this is contained, and
it is not a defence anyone chose." Here the containment is that Gather happens
not to publish host addresses. Nobody designed that as a barrier, no test holds
it, and [[GTC-262]] is open evidence that the unauthenticated surface is still
being narrowed rather than settled.

**Severity holds at Critical**, on the mechanism and the reach, and the
discoverability finding is recorded as the mitigating fact it is rather than
argued away. The ticket should not be read as "anyone can take any account".
It should be read as "anyone who knows a host's email can buy her account for
$12, and nothing in the product stops them or tells her how to stop it."

**One detection signal exists, and it is an accident.** `sendWelcomeEmail` in
`src/lib/email.ts` is already called on this path with the Stripe address, so
the victim receives *"Your event '<name>' is ready!"* for an event she did not
create. It is fire-and-forget with a `.catch()` that only logs, and per
[[GTC-265]] (open) a Resend failure reports success — so it is a signal that
may or may not arrive, addressed to someone with no way to act on it. Worth
having; not a control.

## 3. The second address — `gather_prefilled_contact`

**What it was for.** Introduced by [[GTC-FM2]] (`02244d2`, 2026-04-07), the
guest-to-host wrap-up conversion. `GET` in `src/app/start/[token]/route.ts`
resolves a `WrapUpLink` and redirects to `/plan/new` with the guest's known
`name`, `email` and `phone` as query params. Those were parked in
sessionStorage under `gather_prefilled_contact` with the comment *"Persist
pre-filled contact for use after payment"*. [[GTC-047]] (`11389af`) later
promoted the three values into real form fields and rewrote the write in
`startCheckout` to read from `formData`, recording it as *"preserving
downstream compatibility"*.

**When it stopped being read: it never was.** This corrects the premise in the
brief. `git log -S 'gather_prefilled_contact' --all` returns exactly two
commits, both of which write it; `git log -S "getItem('gather_prefilled_contact')"
--all` returns nothing at all. There is one call site in the tree,
`startCheckout` in `src/app/plan/new/page.tsx`, and it is a `setItem`. The key
was written for a downstream consumer that was never built. Five months later
[[GTC-047]] preserved compatibility with a reader that did not exist.

Two consequences, and the second is why it belongs in this ticket:

- **The form lies.** Name, Email and Phone are collected on `/plan/new` — and
  are the only three fields on that form without a `required` attribute — and
  all three are discarded. The event's `Person` is named
  `email.split('@')[0]` from the Stripe address, so a host who typed "Sarah
  Richardson" is filed as "sarah". The `ref` referral token is discarded with
  them, so wrap-up conversion attribution never lands anywhere.
- **It is the second address.** She types her address into Gather's form, and
  then a different form at Stripe decides who she is. Two inputs, one
  ignored. That is not merely wasted UI: it is the mechanism by which an
  honest host ends up with two accounts, and it is the same gap the attacker
  walks through deliberately.

**Is the fix to use it or to remove it? Use the value; remove the key.**

Removing the fields is wrong — [[GTC-FM2]]'s conversion flow depends on
arriving with contact details in hand, and Moment 1 needs her name. Keeping
the sessionStorage key is also wrong: a browser-side parking spot for an
identity value is what let this drift unnoticed for five months, and it is not
a channel the server can trust anyway. The value should travel in the request
body to `POST /api/billing/checkout` and onto the Checkout Session as
`customer_email`, where Stripe echoes it back in `customer_details` and the
server reads it from a place it can verify came from its own request. Delete
`gather_prefilled_contact` in the same change, and delete it rather than
repointing it, so no second parking spot survives.

Note what this does and does not achieve — see the ⚠ under the fix. Passing
`customer_email` removes the *accidental* second address. It does not remove
the *deliberate* one.

## 4. What the 30-day mint reaches

`getUser` in `src/lib/auth/session.ts` resolves the cookie to a whole `User`
with no event scoping whatsoever. So the reach is the reach of that account,
and nothing in `POST` in `src/app/api/events/route.ts` bounds it — the same
structural point [[GTC-269]] had to correct itself on.

**Measured, not inferred.** Read-only against the local database, 2026-09-12:

```
Session rows: 27   User rows: 6
  demo-session@demo.gather      roles=1   sessions=0
  gtc192-glance@example.com     roles=2   sessions=2
  nigel@mckorbett.co.nz         roles=21  sessions=24
  sarah.henderson@demo.gather   roles=2   sessions=0
  security-test@gather.test     roles=4   sessions=1
  test-gtc129-host@example.com  roles=0   sessions=0
```

A session minted for `nigel@mckorbett.co.nz` reaches **21 events**. Across
those 21:

```
distinct people: 144  |  with email: 84  |  with phone: 3
access tokens on those events: 24 PARTICIPANT, 2 HOST
```

Email domains across those 144, addresses withheld: `example.com` 53,
`gmail.com` 18, `outlook.com` 6, `xtra.co.nz` 6, `mckorbett.co.nz` 1. The 30
non-test addresses sit almost entirely on one event, *"Testing generation new
thing"*. **Whether those are real people or realistic seed data is not
something this ticket can determine and it is not asserted either way** —
[[GTC-267]] recorded the deployed instance as carrying no real data, but that
was about Railway, not about this laptop. It is the founder's database and the
founder's call. Recorded because severity depends on it.

**What the credential opens, route by route.**

Enumeration first, and it needs no event id:

- `GET` in `src/app/api/events/route.ts` takes a bare session with no event
  role and returns every event the user holds any role on. This is the
  amplifier [[GTC-269]] identified. [[GTC-271]] narrowed its wire shape; it
  did not narrow who may call it.

Then, per event, `requireEventRole(eventId, ['HOST','COHOST'])` in
`src/lib/auth/guards.ts` succeeds on every one of the 21, opening:

- Everything [[GTC-267]] closed — `/api/events/[id]`, `/summary`, `/items`,
  `/days`, `/conflicts`, `/revisions`, `/people`, `/teams`.
- `GET /api/events/[id]/tokens` — every `AccessToken` on the event. These are
  the wide ones: they are bearer credentials for the `/h/`, `/c/` and `/p/`
  surfaces, they are not tied to the session, and **they do not expire when
  the session does.** A caller who spends five minutes with the minted session
  walks away with 26 credentials that outlive it.
- Through a harvested HOST token, `GET /api/h/[token]/export-text` — every
  guest's name, email, assigned item and RSVP status, which is
  [[GTC-267]]'s step 6 reached from a different direction.
- `GET /api/events/[id]/glance`, `/invite-status`, `/pre-flight` — per-person
  nudge stamps, reachability tiers and the host's own operational view.

Writes, not only reads:

- `PATCH` and `DELETE` on `/api/events/[id]` — edit or delete any of the 21.
- `POST /api/events/[id]/people/batch-import` — insert arbitrary people.
- `POST /api/events/[id]/trigger-nudges` — guarded by
  `requireEventRole(eventId, ['HOST'])` and it **sends real SMS** through TNZ
  or Twilio to the event's guests. This spends the founder's SMS credit and
  puts unexpected messages in third parties' phones, which is the same harm
  [[GTC-270]] escalated its severity on.
- `POST /api/events/[id]/wrap-up` — dispatches thank-you messages by SMS and
  email to every guest.
- `POST /api/events/[id]/shared-link`, `/transition`, `/freeze-check`,
  `/regenerate` — the whole lifecycle.

Account-wide, outside any event:

- `GET`/`PATCH` on `/api/memory`, `/api/memory/patterns`,
  `/api/memory/settings` — all keyed on `user.id` from the bare session.
  Host memory, learned patterns, defaults, and the learning and
  aggregate-contribution consent flags, which are readable and writable.
- `/api/templates` and `/api/templates/[id]/clone` — bare session.

**Billing is reachable but currently empty, and the distinction matters.**
`POST /api/billing/portal` and `POST /api/billing/cancel` accept the minted
session, so on paper it reaches a Stripe Customer Portal session — payment
methods and invoice history. Both then require a `Subscription` row with a
`stripeCustomerId`, and **nothing in the running app writes one**:
`syncSubscriptionFromStripe` in `src/lib/billing/sync.ts` is exported and has
no caller in `src/` (the webhook that used to call it is now empty — see §5).
So both answer 404 today. Recorded as reachable-but-inert rather than as safe,
because the day a `Subscription` row appears, this becomes a route to a real
host's card details with no other change.

**Summary sentence for the record:** the mint is not a credential for the
event that was paid for. It is a credential for a person — every event they
host, every guest on those events, every access token, their message-sending
capability, their host memory, and their billing surface — and it lasts 30
days with no way for them to end it.

## 5. The lost payment — and where it belongs

**Confirmed.** Event creation happens only in the browser. `useEffect` in
`src/app/plan/new/page.tsx` fires `createEventWithPayment` when it sees
`?session_id=` on the return from Stripe. If the browser never returns — tab
closed, phone dies, network drops, redirect blocked, back button — the charge
has settled at Stripe and **nothing at all exists in Gather.** No `Event`, no
`User`, no `Person`, no row of any kind. There is no orphan to reconcile from
inside the product; the only record is in the Stripe dashboard.

`POST` in `src/app/api/webhooks/stripe/route.ts` is the mechanism that exists
precisely to cover this, and it does nothing. It reads the body, requires the
`stripe-signature` header, requires `STRIPE_WEBHOOK_SECRET`, calls
`stripe.webhooks.constructEvent` — and then:

```
case 'checkout.session.completed': {
  // Note: Event creation happens via POST /api/events, not here
  break;
}
case 'payment_intent.succeeded': { break; }
case 'payment_intent.payment_failed': { break; }
default:
```

Three empty breaks and a bare default. The verification is real and correct;
the handling is a comment. The scanner reports it `SIGNATURE`, which is true
and tells you nothing about whether anything happens afterwards. Git shows
this handler once called `syncSubscriptionFromStripe` — `scripts/verify-ticket-2.4.ts`
still asserts against that name — and the per-event rewrite emptied it without
replacing what it did.

**Recovery path.** Three shapes, in the order I would rank them:

1. **Make the webhook the creator.** `checkout.session.completed` creates the
   event idempotently, keyed on `payment_intent` — the same key the existing
   duplicate check in `POST /api/events` already uses, so the idempotency
   primitive is already chosen. The browser's return becomes a redirect into
   an event that already exists, or a short poll. This is the standard Stripe
   pattern: the webhook is the source of truth, the redirect is only UX. It
   also fixes the double-invoke guard (`creatingRef`) currently doing that job
   in React.
2. **A reconciliation sweep.** A cron route lists paid Checkout Sessions with
   no matching `Event` and creates or refunds. Cheaper to write, keeps a
   window in which the host has paid and sees nothing.
3. **Log and handle by hand.** Not a recovery path; a place to put one later.

**Does it belong in this ticket? No — its own ticket, filed at the same time,
and this one must be ruled on first.** Three reasons, and the third is the
load-bearing one:

- Different defect class. This ticket is about who a payment authenticates.
  That one is about whether a payment is delivered at all. Neither reproduces
  the other and neither test would catch the other.
- Different zone posture. Shape 1 edits
  `src/app/api/webhooks/stripe/route.ts`, which is Zone 4 **by the letter** of
  `GATHER-BUILD-CONSTANTS.md`, not merely by intent. It deserves its own
  sign-off, its own Stripe-CLI preflight (`stripe listen --forward-to
  localhost:3000/api/webhooks/stripe`) and its own idempotency proof.
- **Order matters and it only runs one way.** A webhook has no browser, no
  cookie and no session — it can never authenticate the payer, so it can only
  ever create an event *unbound*, which is exactly the shape this ticket is
  proposing. Rule this one first and the webhook ticket inherits a rule it can
  satisfy trivially. Land the webhook ticket first and it must invent an
  identity-binding rule of its own, in a second place, which is how the hole
  reopens somewhere nobody is looking.

Filed as [[GTC-281]]. Recorded here so the link exists whichever way both go.

**⚠ THIS HALF IS NOT THE SECURITY FIX, AND IT MUST NOT BE MISTAKEN FOR ONE.**
`customer_email` is populated from the request body, so a caller who skips the
form and posts directly to `/api/billing/checkout` still chooses the address.
It removes the *accidental* second address and the two-account drift. It
leaves the *deliberate* one exactly where it is. Half 2 is the fix; half 1 is
what makes half 2's error messages honest.

### Half 2 — a receipt may create an event, never adopt an account

The rule, stated once and testable as written:

> A payment may CREATE an event and ATTACH it to an address. It may never, on
> its own, return a credential for an account.

Four branches in `POST` in `src/app/api/events/route.ts`, in order:

**Branch 1 — a valid session whose `User.email` matches the checkout email.**
She is already authenticated; the receipt adds nothing and takes nothing away.
Create the event, create the `EventRole`, **set no cookie** (hers is live),
return the event, redirect to `/plan/<id>/setup`. Zero friction, zero new
credential.

**Branch 2 — a valid session for a *different* `User`. RULED.** Attach the
event to the paid address, leave the existing session untouched, and say so —
*"You're signed in as a@… but you paid as b@…. Your event is attached to b@…
and we've sent a sign-in link there."* The founder's reason, recorded because
it is the constraint and not merely the choice: *"moving someone's event under
them is no better than moving their session."* So neither is done silently.
Today's silent switch (finding 3) is what must not survive.

**Branch 3 — no session, and the address already has a `User`.** This is the
bug. Create the event, attach the HOST `EventRole` to that `User`, **mint no
session**, and send a sign-in link to the address. This is not a refusal to
serve her — the event is created, paid, and hers. It withholds the shortcut,
not the goods.

**Branch 4 — no session, and no `User` exists at that address. RULED: the same
handshake.** The invariant is one sentence — *"`POST /api/events` never sets a
session cookie"* — one assertion, one code path, and it closes finding 2
rather than accepting it. The founder's reason: *"a route with one branch that
mints and three that do not is a route someone will later simplify in the
wrong direction."* **There is no alternative branch 4. The fallback variant is
withdrawn and must not be reintroduced by an executor who finds the dependency
inconvenient.**

**⚠ [[GTC-265]] IS A HARD BLOCKER ON THIS TICKET AND THE DEPENDENCY WAS TAKEN
DELIBERATELY.** The uniform branch makes an email the only door for every new
host at the moment they have just paid. `sendWelcomeEmail` and
`sendMagicLinkEmail` in `src/lib/email.ts` both `await
resend.emails.send(...)` **without inspecting the returned `error` object** —
that is [[GTC-265]], filed High and open. Today a silent Resend failure means
she pays and is told to check an inbox nothing was sent to.

**[[GTC-265]] lands first.** Founder ruling, 2026-09-12: *"Take the dependency
rather than the variant… If GTC-265 turns out to be larger than filed, HALT
and tell me rather than falling back to the variant."*

**⚠ AND ONE PART OF [[GTC-265]] IS NOT OPTIONAL FOR THIS TICKET.** That ticket
offers to cut its own scope back to `sendNudgeEmail` alone if the widening to
four call sites is unwanted. **That cut would leave this ticket blocked.** The
site this ticket depends on is whichever sender carries the post-payment link
— `sendWelcomeEmail` today — and it is one of the three [[GTC-265]] offers to

[[GTC-265]] executor can build to it:

> The sender **returns** its result and **does not decide** what to do about a

If the failure handling is decided inside the sender rather than returned to

already present for a different user. That is finding 3, and it is

### What the honest host actually experiences

The founder's constraint is the one thing that must not be got wrong: *"A host
who legitimately pays for her second event must still get in."* Spelled out.

**Sarah, second event, signed in — the common case, and it gets faster, not
slower.** The "New Event" buttons live on `/plan/events`
(`src/app/plan/events/page.tsx`, two of them) and in `Navigation.tsx`, and
`src/app/page.tsx` sends a signed-in user to `/plan/events` rather than
`/plan/new`. She is already authenticated when she starts. Her email field is
prefilled from her session and read-only, captioned *"signed in as
sarah@…"*. Stripe shows the same address, uneditable. She returns straight to
`/plan/<newId>/setup`. **She sees no new step and no email**, and she can no
longer create a second account by mistyping at Stripe.

**Sarah, second event, signed out — new laptop, or the 30 days lapsed.** She
types her address, pays, and lands on: *"Payment received. Your event
'Christmas 2027' is ready. We've sent a sign-in link to s•••@example.com — it
expires in 15 minutes."* With a Resend button and a plainly worded *"wrong
address?"* that routes to support rather than silently rebinding. She clicks
the link in her inbox and lands on `/plan/<id>/setup`. **One extra click, on a
device where she was not signed in — the same click she would need to open any
of her existing events from that device.**

**She is not locked out even if that email fails**, and this is the sentence
that makes the trade acceptable: the `Event` and the `EventRole` are already
written and attached to her `User`. `/auth/signin` is a second door to the
same place, and `/plan/events` will list the event the moment she is in. The
fix withholds a shortcut, never the event.

**Sarah, first event.** Under the recommendation, identical to the signed-out
case. Under the branch-4 alternative, exactly as today.

**The attacker.** Pays $12 with Sarah's address. The event is created and
attached to Sarah. He receives no cookie and no link. Sarah receives an email
naming an event she did not create. **He is out twelve dollars and has bought
her a free event.**

### Four things this ticket deliberately does NOT propose

Recorded so the founder can see they were considered and rejected on grounds,
not overlooked:

- **Refusing the payment when the address already has an account.** It
  punishes the honest returning host, and it turns checkout into an
  account-existence oracle — the exact thing `POST /api/auth/magic-link` and
  `POST /api/auth/claim` both contort themselves to avoid.
- **Auto-refunding the attacker.** It removes Sarah's only detection signal
  and hands a stranger a way to churn her billing record.
- **A short-lived session instead of a 30-day one.** [[GTC-269]] took that
  shape and was right to, because the account there was a bounded demo
  account. Here the account is a real host's, and a two-hour impersonation is
  still an impersonation.
- **Scoping the session to the event that was paid for.** `Session` has no
  event scoping, and adding it is `prisma/schema.prisma` plus `src/lib/auth*`
  — Zones 1, 2 and 5, and a far larger ticket than this one.
