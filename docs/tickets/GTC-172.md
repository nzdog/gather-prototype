# GTC-172 — C1: Household contact picker + absolute child exclusion

**Status:** Open | **Branch:** TBD | **Commit:** [pending] (filed `e5f6e82`) | **Effort:** max, schema

*Effort level is a proposal from the discovery-report ticket breakdown — run `/effort` manually
before execution.*

### Context

Hinge spec §10.7 (Moment 4 §10.7): the recipient control is a **household contact picker** —
"who should Gather talk to for this household?" — defaulting to the primary contact, any adult
addable, **cross-household capable** (Grandma's channel may live in another household), which
requires channel to be a **Person reference, not a boolean**. One decision per household, not a
matrix — Moment 1 stays light.

Moment 4 §10.6: the child rule is a **hard constraint, absolute, in those words** — a CHILD-role
person never receives system messages regardless of contact info on their record; their channel
is always an adult via the picker; a genuinely-messageable teenager must be explicitly roled as an
adult at capture, never inferred from phone presence. §10.6 names the current code directly:
"Current code contradicts this — CHILD with contact info derives a direct reachability tier;
fixing it is a hard requirement of the recipient-model ticket. No future session may soften this."

Today: `Moment1InputForm.tsx` captures name/email/phone only. `reachabilityTier`/`contactMethod`
are auto-derived from contact-info presence — a system inference, not a host judgement toggle. A
`CHILD`-role person with their own phone/email gets `reachabilityTier: DIRECT` today and can be a
direct SMS recipient — the exact contradiction §10.6 names.

### Scope

**Fix here:**
- Schema for a per-household channel reference — cross-household capable, a `Person` reference
  (not a boolean) — captured at Moment 1.
- Hard-exclude `CHILD`-role people from message eligibility **at the eligibility-check layer**,
  not just the capture UI, so it cannot be bypassed by contact-info presence on the record. This
  is the hard requirement §10.6 names explicitly — do not soften it, do not make it a default that
  can be silently overridden by data presence.
- An explicit adult-roling path at capture for a genuinely-messageable teenager (a hosting
  decision Kate makes deliberately, never a system inference).

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- `littleCount` (pure headcount, unaffected by this ticket).
- The `ReachabilityTier` enum itself — still useful for signal-quality assessment, just not the
  recipient decision going forward.

# GTC-172 — C1: Household contact picker + child exclusion — CLOSED

**Status:** Complete | **Branch:** feat/moment-one-redesign | **Commit:** 63764d1 | **Effort:** max

## The contradiction this closed

Not a new feature — a live contradiction §10.6 names in the code, verified present before any
change was made:

- `reconcileMembers.ts:81-85` (`reachabilityFor`) and `households/route.ts:157-165` derive
  `reachabilityTier: DIRECT` from phone/email presence for **every** role, CHILD included.
- `nudge-eligibility.ts:66` filtered on `phoneNumber: { not: null }` with **no role filter**. The
  query roots on `Person` while `householdRole` lives on `PersonEvent`, so the loop had no role
  data to filter on even if it had wanted to.
- A `CHILD` with their own phone was therefore a live SMS recipient.

**The discovery report understated the surface.** It named two eligibility files; **five**
recipient-selection paths had no role filter. Verified in code, not trusted:

| # | Path | Role filter before C1 |
|---|---|---|
| 1 | `nudge-eligibility.ts:66` `findNudgeCandidates` | none (Person-rooted; role not selected) |
| 2 | `nudge-eligibility.ts:235` `findRsvpFollowupCandidates` | none (role on the queried row) |
| 3 | `proxy-nudge-eligibility.ts:38` `findProxyNudgeCandidates` | incidental only — targets `PRIMARY_CONTACT` |
| 4 | `wrap-up/route.ts:104` → `wrap-up.ts:52` | none — filtered only `personId !== hostId` |
| 5 | `people/[personId]/nudge/route.ts:50` | none — Person loaded straight from the URL |

A CHILD with a phone received the wrap-up thank-you SMS. Acceptance box 2 says *every*
message-eligibility query, so all five are covered.

## What was built

- **One predicate, five call sites.** `src/lib/eligibility/child-exclusion.ts` exports
  `MESSAGEABLE_PERSON_EVENT` (a Prisma `where` fragment) and `isMessageableRole`, mirroring the
  `SENT_AND_LIVE` pattern in `lifecycle.ts`. Spread into SQL at every path, with a JS re-check in
  each loop so loosening the query cannot silently reopen the hole.
- **Allowlist, not `{ not: 'CHILD' }`.** `PRIMARY_CONTACT | PARTNER | GUEST`. It **fails closed** —
  a future `HouseholdRole` is non-messageable until added deliberately — and sidesteps SQL
  three-valued logic, where `NOT (col = 'CHILD')` is NULL, not true, for a NULL role.
- **NULL is explicitly messageable.** `people/route.ts` and `batch-import` create PersonEvents that
  never set `householdRole`. A naive negation would have silently stopped nudging every
  directly-added adult — no error, just no messages.
- **`reachabilityTier` deliberately unchanged**, per scope. A CHILD with a phone genuinely has
  DIRECT *signal quality*; it is simply no longer the recipient decision. This is also what makes
  the test meaningful — the subject keeps phone, email and DIRECT and is excluded anyway.
- **Contact picker (§10.7).** `Household.contactPersonEventId` → `PersonEvent`, cross-household
  capable, `ON DELETE SET NULL`. `resolveHouseholdChannel` returns the pick, else the primary
  contact — NULL means "not picked", so the default is **computed, not stored**, which is why the
  migration needs no backfill and pre-picker households behave correctly.
- **Resolution and validation are separate on purpose.** `resolveHouseholdChannel` returns a picked
  CHILD rather than falling back; `findProxyNudgeCandidates` then skips the household outright. A
  silent fallback would message somebody the host never picked and hide the corruption for as long
  as it existed.
- **Adult-roling (§10.6).** `adultRoled` on a helper row stores `householdRole: GUEST` instead of
  CHILD. It is a *payload* input, never a stored flag — there is no "child but messageable" state,
  because that is exactly the soft override §10.6 forbids. Off by default, never pre-ticked, never
  inferred from a phone number. `isYoungPerson` carries the kid-with-a-job fact for **display
  only**, so a re-roled teenager still renders in the helpers list instead of silently reappearing
  among the guests on reload.
- **Two behaviour-preserving extractions** (`selectWrapUpRecipients`, `resolveManualNudgeRecipient`)
  — both routes sit behind `requireEventRole` and were unreachable from a DB-level test, the same
  problem and the same solution as GTC-159's `reconcileHouseholdMembers` seam.

## Migration summary

`20260804082756_gtc172_household_contact_channel` — generated with `--create-only`, surfaced for
sign-off, approved, then applied. Four statements:

```sql
ALTER TABLE "Household" ADD COLUMN     "contactPersonEventId" TEXT;
ALTER TABLE "PersonEvent" ADD COLUMN     "isYoungPerson" BOOLEAN NOT NULL DEFAULT false;
CREATE INDEX "Household_contactPersonEventId_idx" ON "Household"("contactPersonEventId");
ALTER TABLE "Household" ADD CONSTRAINT "Household_contactPersonEventId_fkey"
  FOREIGN KEY ("contactPersonEventId") REFERENCES "PersonEvent"("id")
  ON DELETE SET NULL ON UPDATE CASCADE;
```

Both columns additive; nullable or defaulted, so existing rows are untouched and Postgres adds the
boolean default without a table rewrite. No backfill — deliberately, since the picker's default is
computed at read time, and a hand-written backfill would have meant editing migration SQL (zone 5).

Adding a second Household↔PersonEvent relation makes the existing one ambiguous to Prisma, so
`household`/`members` gained an explicit `@relation("HouseholdMembers")`. Prisma derives FK
constraint names from table+column, so this emitted **no DDL** — predicted in the plan and
confirmed by the generated SQL matching line-for-line.

**Rollback:** drop the FK and index, then both columns.

**Drift:** the P3005 warning in `GATHER-BUILD-CONSTANTS.md` is **stale** — verified, not trusted.
`prisma migrate status` reported "Database schema is up to date!" (32 migrations) beforehand, and
`migrate dev` applied with no reset prompt.
