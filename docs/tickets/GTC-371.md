### Signal

Found by Claude Code planning [[GTC-369]] (2026-10-08), reading `POST` in
`src/app/api/auth/verify/route.ts` and `src/app/auth/verify/page.tsx` at `3b03131`.

A magic link is a bearer credential with nothing tying it to the browser that asked for it. Anyone
can get a valid link for their own address (`POST /api/auth/magic-link`) and send it to someone
else. Opening it runs the sign-in page's effect, which posts the token to verify; verify mints a
`Session` for the SENDER's account and sets the `session` cookie in the OPENER's browser, replacing
any session she already had. She is then working in the sender's account: an event she creates, or
pays for, is the sender's.

[[GTC-369]] limits where such a link can land (Gather's own pages only) and stops it claiming anyone;
it does not stop the sign-in itself. That is this ticket.

### For the plan (Claude Code's note, not a ruling)

- Shapes seen elsewhere: tie the link to the browser that asked for it (a short-lived cookie set
  when the link is requested, checked at verify), or ask before switching accounts when a different
  session is already present ("You're signed in as A; continue as B?").
- The nav already shows the signed-in address, which is a partial signal, not a defence.
- Zone 1 (the session cookie) and Zone 2 (the magic-link flow): every step comes back to the
  founder.

### Stops

- NOTHING SENDS FOR REAL. Tests write their own sign-in links straight into the database.
- Zones 1 and 2: plan first, every step to the founder.
