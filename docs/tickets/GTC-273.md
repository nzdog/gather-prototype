## Signal

**Expected**
`collectSharedSecret` in `tests/security-route-scan.ts` reports `failOpen` for
a handler whose shared-secret check is disabled when the secret is unset. The
property is about the CONDITION'S BEHAVIOUR — "does an unset secret make this
refusal unreachable" — not about how the condition is typed.

**Actual**
It reports `failOpen` only when the condition is a `&&` whose **left operand
is the bare identifier**:

```
let failOpen = false;
if (
  ts.isBinaryExpression(cond) &&
  cond.operatorToken.kind === ts.SyntaxKind.AmpersandAmpersandToken &&
  ts.isIdentifier(cond.left) &&
  cond.left.text === secret
) {
  failOpen = true;
}
```

Any other spelling of the same defect passes. It is the same species of fault
[[GTC-269]] named in `tests/demo-endpoints-test.ts`: *"A substring match is
not a security assertion... It tests the spelling of the code, not its
behaviour."* This is an AST match rather than a substring match, which makes
it look stronger and does not make it so.

**Smallest failing case**
Move the secret out of the condition into a local and the flag disappears:

```
const s = CRON_SECRET;
if (s && provided !== s) { return 401; }
```

## Evidence — four rewrites, all genuinely fail-open, none flagged

Every one of these leaves the endpoint open to any caller when `CRON_SECRET`
is unset, exactly as the shape [[GTC-270]] removed did. Verdicts are the
scanner's own, printed by `analyzeSource` against the
`decide-by-followups` route source with only the condition line replaced:

```
if (process.env.CRON_SECRET && p !== process.env.CRON_SECRET)
  -> SHARED_SECRET                 NOT FLAGGED
const s = CRON_SECRET; if (s && p !== s)
  -> NO CREDENTIAL OF ANY KIND     NOT FLAGGED
if (Boolean(CRON_SECRET) && p !== CRON_SECRET)
  -> SHARED_SECRET                 NOT FLAGGED
if (CRON_SECRET != null && p !== CRON_SECRET)
  -> SHARED_SECRET                 NOT FLAGGED
```

**The second one is the worst and deserves naming separately.** Assigning the
secret to a local does not merely lose the fail-open flag — the handler drops
out of the credential classification entirely and reports **"no credential of
any kind"**, because `collectSharedSecret` matches `\bCRON_SECRET\b` against
the condition text and a local named `s` does not contain it. A reviewer
reading that report sees an unguarded handler where there is a broken guard,
and a default-deny gate sees a handler with nothing to allow-list.

**The control, so the negatives above mean something.** The detector was fed
the exact shape GTC-270 removed, in the same run, and it fired:

```
if (CRON_SECRET && provided !== CRON_SECRET)
  -> SHARED_SECRET [FAIL-OPEN]     FLAGGED
```

That control now lives in the suite as a permanent assertion —
*"[CONTROL] the FAIL-OPEN detector still fires on the shape GTC-270
removed"* in `tests/security-route-scan-control.ts`, added by [[GTC-270]]
precisely because "no handler is flagged FAIL-OPEN" is also what a broken
detector reports. [[GTC-267]]'s rule: an empty search result is a claim, and
a claim needs a control.

## Why this is not urgent, stated so nobody reads it as worse than it is

- **[[GTC-270]]'s own fix is unaffected.** The six cron handlers went
  `FAIL-OPEN 6 → 0` and every one still reports `SHARED_SECRET`, so they did
  not fall off the classification. That change is real and pinned.
- **The behaviour is not held by this detector anyway.** Suite 12 of
  `tests/security-validation.ts` drives all six handlers with the secret
  deleted before the module loads and requires 401 from each. A rewrite from
  the table above would turn that suite red whatever the scanner said.
- `SHARED_SECRETS` currently contains one entry, `CRON_SECRET`, and the three
  cron routes are its only consumers.

**Why it is High anyway:** [[GTC-268]] slice 2 is a default-deny gate in CI.
The moment a gate decides what to admit from `failOpen`, a false negative
stops being a cosmetic report line and becomes a merge that should not have
happened.

## Scope

**Fix here:**
- `collectSharedSecret` in `tests/security-route-scan.ts` — widen the
  fail-open determination from one AST shape to the property. Sketch, not a
  mandate: resolve the secret through a local `const` binding before testing
  the condition; treat `Boolean(x)`, `x != null` and `x !== undefined` as the
  same truthiness test as a bare `x`; match `process.env.CRON_SECRET` as well
  as an identifier initialised from it.
- `tests/security-route-scan-control.ts` — one control assertion per shape in
  the table above, each asserting it IS flagged. A detector that has never
  fired on a shape is not a detector for that shape.

**The harder question, recorded rather than answered:** every widening above
is another spelling. The property is "is the refusal unreachable when the
secret is absent", and the shapes are unbounded. A scanner that decides this
structurally will always be behind. Whether the right answer is a wider
matcher, a conservative rule (any `&&` in a shared-secret condition is
suspect until proven otherwise), or a declared limit with the behaviour held
by a behavioural suite, is a judgement for [[GTC-268]] slice 2 and is not
pre-empted here.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding. Zone 6
covers `tests/security-*.ts`, which is both files above — this ticket needs
explicit Zone 6 sign-off before it starts, the way [[GTC-270]] did.

Out of scope: the cron routes. They are fixed, and this ticket is about the
instrument that measures them.

### The evaluator, and the two designs it refuted before it worked

Recorded because each was a wrong design that looked right, and both were found
by running it rather than by reasoning about it.

1. **The first version treated every unresolvable call as undecidable.** Since
   `request.headers.get('authorization')` is unresolvable, it reported UNPROVEN
   on **all seventeen fixtures and all six real handlers** — Stop Condition 9 in
   its purest form. The attacker CHOOSES the header, so those branches are
   existential: if some path reaches the work, the attacker can reach the work.
2. **The second reported UNPROVEN on correct code** because
   `if (result.errors.length > 0)` stands in the cron bodies AFTER the guard has
   decided. Fix: explore both branches of an undecidable condition and JOIN — if
   both agree the opacity did not matter. The fixture in suite 6 carries an
   opaque post-decision condition on purpose, so that fix stays held.

A third, smaller: returning UNPROVEN on sight of any loop or `switch` reported
a correct guard as undecidable because an unrelated `for` preceded it. The test
is now whether the construct can return, throw, or reassign something the
decision reads.

The founder's instruction was that the full scan output must be identical

**FIRST HALT — six movements.** No guard verdict moved (106 files, 134
handlers, 111 guarded, 23 unguarded, all identical; `guardProof` 111 PROVEN / 23
REFUTED / 0 UNPROVEN). What moved:

- `GET /api/c/:token` and `GET /api/p/:token` gained `CREDENTIAL_COLUMN`. True
  detections — the old rule tested `^prisma\.\w+\.find\w+$` on the callee text
  and both routes write it across two lines, so **a line break defeated it.**
  But the lookup is analytics ("Track first link open") and the route's
  credential is `resolveToken`.
- `POST /api/auth/logout` gained `CREDENTIAL_COLUMN [UNPROVEN]`
  (`prisma.session.delete({ where: { token } })`), moving the no-credential
  count 12 → 11. It authorises nothing — [[GTC-268]]'s own allowlist reason.
- `GET /api/h/:token` gained `ENV_GATE [UNPROVEN]`. Its
  `if (NODE_ENV !== 'development')` sets a field; it gates nothing.
- `GET /api/h/:token` and `GET /api/p/:token` listed `getUser` under "Guards
  CALLED but not CHECKED", 0 → 2 handlers. `getUser` there computes an
  `authStatus` field; both routes are guarded by a PROVEN `resolveToken`.
- At `298b62d`, unguarded 32 → 34 and the closed set 10 → 12.

**Rulings, 2026-09-12, all three as recommended:**

- **Movements 1-3 — the lookup's RESULT must gate a refusal.** A result
  consumed by `.then()` or `.catch()`, or never tested, is not a credential
  check. **This is not tuning to the tree: it is the same "witness must refuse"
  test already applied to guards, applied consistently**, and it keeps every
  capability gained — aliased client, `update`-keyed credential, `OR`/filter
  rejection, multiline callee. The attribution point is what carries it: on the
  `/c/` and `/p/` routes **the label is TRUE and the attribution is WRONG**, and
  at slice 2 a misattributed credential becomes an allowlist entry. *"A true
  statement pointed at the wrong check is not a lesser error than a false one;
  it is the one that survives review."*
- **Movements 4-5 — UNPROVEN means "looks like the thing, cannot decide", never
  "is not the thing".** *"UNPROVEN is for a thing whose verdict you cannot
  reach, not for a thing that is not the kind of thing being verdicted. An `if`
  whose branch contains no return is not a gate. A guard symbol computing a
  field is not a guard being ignored."* Printing either under "a guard that
  cannot refuse anyone" asserts a defect that is not there — and a gate that
  cries wolf gets hollowed out by allowlist entries, the failure mode already
  visible in this tree where `GET /api/gather/:eventId/directory` sits on the
  proposed allowlist AND under open High-severity [[GTC-262]].
- **Movement 6 — KEEP IT AND RE-PIN.** 32 becomes 34; the closed set becomes
  GTC-267's ten plus `invite-status` and `people/batch-import`, with the
  `?hostId=` reason recorded beside it. At `298b62d` both have
  `requireEventRole` in the `else` of `if (hostIdParam)` — branch-nested, the
  other branch being the mechanism [[GTC-267]] removed as a bypass — and
  unconditional at HEAD. **The retired rule called them guarded at both
  commits: a THIRD false positive of the old guard rule, found by the control
  commit rather than by anyone looking.** **Suppressing it would mean choosing a
  weaker guard rule to protect a number.**

**SECOND HALT — a seventh movement, and the control was too weak to see it.**
After 1-5, one assertion still failed: `POST /api/auth/verify` moved
`CREDENTIAL_COLUMN` from PROVEN to **UNPROVEN**. The suite-8 table compared
credential KINDS only, so it passed while a proof moved — **a control that
cannot see a movement is the same failure as a gate that cannot fail.** The
table now pins kind AND proof.

The finding itself is real and the retired rule answered it by accident.
`POST /api/auth/verify` refuses an unknown, expired or used magic-link token
with `Response.json({ success: false, error: 'invalid' })` **at HTTP 200**. The
only 4xx in the handler is line 13's `status: 400` for a MISSING token in the
request body — a different branch and a different question. `refusesSomewhere`
matched the whole function text, so it **borrowed that unrelated 400.** Nothing
distinguishes a 200 carrying `success: false` from a 200 carrying data without
knowing the body convention, and teaching the scanner that convention would be
another spelling test of exactly the kind this ticket removes. **So it stays
UNPROVEN, pinned by name.** It needs a slice-2 ruling: an allowlist entry
carrying this reason, or a route that refuses with a 401. It is on
[[GTC-268]]'s proposed allowlist today with the reason *"the credential is the
magic-link token it consumes, checked via `prisma.magicLink.findUnique`"* — the
check is real; the scanner's ability to confirm it is what is not.

### ⚠ THE SLICE-2 RULING ON `POST /api/auth/verify`, AND THE REFUSAL THAT EARNED IT

**Founder ruling, 2026-09-12 — recorded as a slice-2 precondition against
[[GTC-268]] so slice 2 inherits it rather than rediscovering it: the allowlist
entry carries the reason explicitly. The route is NOT changed to refuse with a
401.**

> *"The check is real — a magic-link token consumed through `findUnique`, with
> unknown, expired and used all refused. What is missing is the scanner's
> ability to confirm it, and changing a working auth route's response shape to
> satisfy a static analyser is the tail wagging the dog. The allowlist exists
> precisely for 'genuinely fine, provably so by a human and not by the tool',
> and an entry whose reason names the unprovability is worth more than a 401
> added to make a report tidy."*

**And the refusal that produced the finding, recorded at the founder's
instruction as the decision this slice most turns on.** The obvious fix was to
teach the scanner that `success: false` in a returned body means refusal. That
was refused, and the reason is now blind spot 6 in
`tests/security-route-scan.ts`:

> Encoding that would be a BODY CONVENTION, and nothing distinguishes a 200
> carrying `success: false` from a 200 carrying data except that convention.
> **It is another spelling test of exactly the kind this ticket exists to
> remove. A rule that reads one codebase's JSON idiom is not more behavioural
> than a rule that reads one `&&`; it is the same mistake with a wider
> vocabulary.**

This is the shape of the whole ticket in one decision. The defect was never
that the matchers were too narrow — it was that a matcher was standing where a
verdict belonged. Widening the vocabulary would have hidden the same defect
better.
