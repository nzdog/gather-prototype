# GTC-273 — The detector that only catches one spelling

**Status:** Open — **filed, not started. Nothing has been built for this
ticket.** Filed 2026-09-11 | **Branch:** TBD
**Severity:** [ ] Critical [x] High [ ] Medium [ ] Low
Escalated (brand/trust risk): [ ] Yes [x] No — this is a hole in the
instrument, not in the product. Nothing ships to a user through it. It is High
because [[GTC-268]] slice 2 is a default-deny CI gate, and a gate that trusts

**Found during [[GTC-270]]'s execution**, 2026-09-11, and the provenance is

variable."*

## Signal

**Expected**
`collectSharedSecret` in `tests/security-route-scan.ts` reports `failOpen` for
a handler whose shared-secret check is disabled when the secret is unset. The
property is about the CONDITION'S BEHAVIOUR — "does an unset secret make this
refusal unreachable" — not about how the condition is typed.

**Actual**
It reports `failOpen` only when the condition is a `&&` whose **left operand
is the bare identifier**:

```
let failOpen = false;
if (
  ts.isBinaryExpression(cond) &&
  cond.operatorToken.kind === ts.SyntaxKind.AmpersandAmpersandToken &&
  ts.isIdentifier(cond.left) &&
  cond.left.text === secret
) {
  failOpen = true;
}
```

Any other spelling of the same defect passes. It is the same species of fault
[[GTC-269]] named in `tests/demo-endpoints-test.ts`: *"A substring match is
not a security assertion... It tests the spelling of the code, not its
behaviour."* This is an AST match rather than a substring match, which makes
it look stronger and does not make it so.

**Smallest failing case**
Move the secret out of the condition into a local and the flag disappears:

```
const s = CRON_SECRET;
if (s && provided !== s) { return 401; }
```

## Evidence — four rewrites, all genuinely fail-open, none flagged

Every one of these leaves the endpoint open to any caller when `CRON_SECRET`
is unset, exactly as the shape [[GTC-270]] removed did. Verdicts are the
scanner's own, printed by `analyzeSource` against the
`decide-by-followups` route source with only the condition line replaced:

```
if (process.env.CRON_SECRET && p !== process.env.CRON_SECRET)
  -> SHARED_SECRET                 NOT FLAGGED
const s = CRON_SECRET; if (s && p !== s)
  -> NO CREDENTIAL OF ANY KIND     NOT FLAGGED
if (Boolean(CRON_SECRET) && p !== CRON_SECRET)
  -> SHARED_SECRET                 NOT FLAGGED
if (CRON_SECRET != null && p !== CRON_SECRET)
  -> SHARED_SECRET                 NOT FLAGGED
```

**The second one is the worst and deserves naming separately.** Assigning the
secret to a local does not merely lose the fail-open flag — the handler drops
out of the credential classification entirely and reports **"no credential of
any kind"**, because `collectSharedSecret` matches `\bCRON_SECRET\b` against
the condition text and a local named `s` does not contain it. A reviewer
reading that report sees an unguarded handler where there is a broken guard,
and a default-deny gate sees a handler with nothing to allow-list.

**The control, so the negatives above mean something.** The detector was fed
the exact shape GTC-270 removed, in the same run, and it fired:

```
if (CRON_SECRET && provided !== CRON_SECRET)
  -> SHARED_SECRET [FAIL-OPEN]     FLAGGED
```

That control now lives in the suite as a permanent assertion —
*"[CONTROL] the FAIL-OPEN detector still fires on the shape GTC-270
removed"* in `tests/security-route-scan-control.ts`, added by [[GTC-270]]
precisely because "no handler is flagged FAIL-OPEN" is also what a broken
detector reports. [[GTC-267]]'s rule: an empty search result is a claim, and
a claim needs a control.

## Why this is not urgent, stated so nobody reads it as worse than it is

- **[[GTC-270]]'s own fix is unaffected.** The six cron handlers went
  `FAIL-OPEN 6 → 0` and every one still reports `SHARED_SECRET`, so they did
  not fall off the classification. That change is real and pinned.
- **The behaviour is not held by this detector anyway.** Suite 12 of
  `tests/security-validation.ts` drives all six handlers with the secret
  deleted before the module loads and requires 401 from each. A rewrite from
  the table above would turn that suite red whatever the scanner said.
- `SHARED_SECRETS` currently contains one entry, `CRON_SECRET`, and the three
  cron routes are its only consumers.

**Why it is High anyway:** [[GTC-268]] slice 2 is a default-deny gate in CI.
The moment a gate decides what to admit from `failOpen`, a false negative
stops being a cosmetic report line and becomes a merge that should not have
happened.

## Scope

**Fix here:**
- `collectSharedSecret` in `tests/security-route-scan.ts` — widen the
  fail-open determination from one AST shape to the property. Sketch, not a
  mandate: resolve the secret through a local `const` binding before testing
  the condition; treat `Boolean(x)`, `x != null` and `x !== undefined` as the
  same truthiness test as a bare `x`; match `process.env.CRON_SECRET` as well
  as an identifier initialised from it.
- `tests/security-route-scan-control.ts` — one control assertion per shape in
  the table above, each asserting it IS flagged. A detector that has never
  fired on a shape is not a detector for that shape.

**The harder question, recorded rather than answered:** every widening above
is another spelling. The property is "is the refusal unreachable when the
secret is absent", and the shapes are unbounded. A scanner that decides this
structurally will always be behind. Whether the right answer is a wider
matcher, a conservative rule (any `&&` in a shared-secret condition is
suspect until proven otherwise), or a declared limit with the behaviour held
by a behavioural suite, is a judgement for [[GTC-268]] slice 2 and is not
pre-empted here.

**Do not touch:**
All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md` are binding. Zone 6
covers `tests/security-*.ts`, which is both files above — this ticket needs
explicit Zone 6 sign-off before it starts, the way [[GTC-270]] did.

Out of scope: the cron routes. They are fixed, and this ticket is about the
instrument that measures them.
