reporting error by a prior session — it was read accurately off a real GitHub surface. The
problem is that GitHub itself reports two different counts, seconds apart, and neither has been
reconciled:**

- **GitHub's push-time hook** (fires on every `git push` to this repo) reports **67
  vulnerabilities — 32 high, 31 moderate, 4 low — on the default branch.** Confirmed live during
  the push that landed the first four tickets in this triage (2026-08-23): the exact same 67 /
  32 / 31 / 4 printed to the terminal, unprompted, on a routine push.
- **GitHub's Dependabot alerts API** (`gh api repos/.../dependabot/alerts`), queried seconds

- **`npm audit` on `feat/moment-one-redesign`** (the working branch) returns **16** (11 high,

**Two GitHub-owned surfaces disagree with each other on the same repository, moments apart. The
push banner is not a one-off — it appears on every push and will keep asserting 67 regardless of
what the Alerts API says.** Neither GitHub surface should be treated as authoritative until this
discrepancy is explained (possibilities not yet investigated: the push banner may be a cached or
differently-scoped rollup — e.g. counting closed/fixed alerts, or double-counting per manifest

directly on `feat/moment-one-redesign`, per the original reasoning below — that number is the
only one of the three that was reproduced by directly inspecting the installed dependency tree
rather than reading a summary line from a UI or hook.**

## Context

Two of the 16 advisories `npm audit` reports on `feat/moment-one-redesign` are pure
`package-lock.json` re-resolutions with no `package.json` change and no production impact:

- **`brace-expansion`** 1.1.13 → needs ≥1.1.18 (GHSA-3jxr-9vmj-r5cp, GHSA-mh99-v99m-4gvg,
  GHSA-rgw5-rvv9-x895 — DoS via exponential/unbounded expansion). Chain:
  `eslint-config-next@15.5.22` → `eslint-plugin-import@2.32.0` (already latest 2.x, declares
  `minimatch: ^3.1.2`) → `minimatch@3.1.5` (already latest 3.x, declares
  `brace-expansion: ^1.1.7`). That range already permits 1.1.18 — brace-expansion released
  1.1.14 through 1.1.18 without minimatch ever moving off the 3.x line. The 1.1.13 pin in the
  lockfile is stale, not range-constrained.
- **`js-yaml`** 4.1.1 → needs ≥4.3.1 (GHSA-h67p-54hq-rp68, GHSA-52cp-r559-cp3m,
  GHSA-5p4m-2wfm-xmqj — quadratic-complexity DoS via merge-key/alias chains). Chain:
  `eslint-config-next@15.5.22` → `eslint@9.39.2` (satisfies eslint-config-next's own peer
  range unchanged) → `@eslint/eslintrc@3.3.3` (declares `js-yaml: ^4.1.1`). js-yaml 4.3.1
  exists and satisfies that same range. Same story — stale pin, not a range constraint.

Both packages are pulled in solely through the ESLint/TypeScript-ESLint devDependency toolchain.
Neither appears anywhere in `dependencies` (production); both are transitive under
`eslint-config-next`, which is itself a `devDependency`. `npm ls brace-expansion --all` /
`npm ls js-yaml --all` confirm each has exactly one resolution path in the tree, with no other
tool (build, runtime, or test scripts) depending on either package independently.

**`eslint-config-next` itself must not move.** It was deliberately downgraded from `^16.2.2` to
`^15.5.22` in commit `b6e6e38` ("fix: correct eslint-config-next mismatch; decouple lint from
build gate", 2026-08-06). Reason, from the commit message: `eslint-config-next` had been pinned
to `^16` against `next@15`, which crashed ESLint with a circular-JSON error that Next treated as
non-fatal — so `next build` was exiting 0 *without the linter ever running*, and `next lint` was
outright broken. The downgrade made lint execute again; the same commit set
`eslint.ignoreDuringBuilds: true` to keep the now-functioning linter's 68 pre-existing errors
(tracked in [[GTC-221]]) from gating the build. Bumping `eslint-config-next` back to a `^16` line
would reintroduce the exact crash b6e6e38 fixed, unless paired with an actual Next.js 16 upgrade
— see [[GTC-244]] and [[GTC-130]] ("Align eslint-config-next with installed Next.js major
version," filed before b6e6e38, recommended the same downgrade as its "Path A"). GTC-130 has
since been closed, citing b6e6e38 as the commit that executed it — see that ticket for the full
reconciliation note.
