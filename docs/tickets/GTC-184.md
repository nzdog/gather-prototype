# GTC-184 — G1: Repoint dietary conflict detection at the GTC-150 model

**Status:** Open | **Branch:** TBD | **Commit:** [pending] (filed `e5f6e82`; narrowed
2026-08-15 per the [[GTC-228]] reconciliation) | **Effort:** to reconfirm at preflight —
narrowed from "max" now that per-person capture and the legacy-model-fate decision are both
removed. **`type: schema` and Stop Condition 7 (schema migration) do not apply — settled by
founder ruling, 2026-08-23; see below.**

*Effort level is a proposal — run `/effort` manually before execution.*

### Context

Two dietary models coexist on `Event`/`EventSetup`:
- GTC-150's three-state model (`unanswered|confirmed_none|confirmed_needs`) on
  `EventSetup.dietaryData` — well-built, event-scoped, and (per [[GTC-228]]'s reconciliation
  trace, 2026-08-15) correctly consumed by generation: `finalize-plan/route.ts:148` reads it
  via `readDietaryData()`.
- A legacy model on `Event` itself: `Event.dietaryStatus`
  (`UNSPECIFIED|NONE|SPECIFIED` — different enum, different names) plus
  `Event.dietaryVegetarian/Vegan/GlutenFree/DairyFree` int counts.

`src/lib/ai/check.ts`'s `detectDietaryGaps()` reads the **legacy** counts, not GTC-150's
model. Confirmed still accurate at HEAD by [[GTC-228]]'s trace (`check.ts:184-237`; nothing
on the live V2 path ever writes `Event.dietary*`): a host's real Moment 2 dietary answer
never reaches conflict detection today. This is the one part of this ticket's original scope
that generation does not already solve on its own.

### Scope

**Fix here:**
- Repoint `check.ts`'s `detectDietaryGaps()` at the GTC-150 model (`EventSetup.dietaryData`
  via `readDietaryData()`) instead of the legacy `Event.dietary*` counts.
- Legacy model's fate: **deprecate in place** — ruling adopted from [[GTC-228]] (9+ live
  consumers; not a clean empty-column drop). Not re-litigated here.

**Do not touch:**
- All Do-Not-Touch Zones in `GATHER-BUILD-CONSTANTS.md`.
- The dietary three-state values themselves (`unanswered`/`confirmed_none`/`confirmed_needs`)
  — proven and working, not being redesigned.
- Generation's consumption of dietary data (`finalize-plan`) — already correct per
  [[GTC-228]]'s trace; nothing here should touch it.

**Out of scope:**
- **Per-person dietary capture at Moment 1 — ruled out, not deferred.** Dietary needs are
  event-level counts-of-kind; counts are sufficient to verify coverage. Per-person identity
  would only be required for portioning or for telling an individual guest which dish is
  theirs — a different product. (Product ruling, Nigel, 2026-08-15.)
- Wiring `finalize-plan` to consume per-person data — moot, since per-person capture is
  ruled out above.
- The host-facing coverage warning/labelling UX — owned by [[GTC-228]], which depends on
  this ticket landing first.

### Founder ruling — the V1 fallback (Nigel, 2026-08-23)

Resolves open decision 1 from the GTC-184 Phase 1 audit (the V1 fallback). No other open
decision from that audit is resolved by this ruling.

- No fallback. `detectDietaryGaps` in `src/lib/ai/check.ts` reads `EventSetup.dietaryData`
  only — it does not branch on `event.setup` presence to preserve legacy-count behaviour for
  events that have no Moment 2 setup row.
- Rationale: all events currently in existence are old test/seed events, not a live production
  population with real V1 dietary data at stake. There is no live V1 population whose dietary
  check would regress from this change.
- This rationale is time-bound, not an architectural claim. If real V1-only events with
  populated `Event.dietary*` fields and no `EventSetup` row ever exist in the live population,
  this ruling should be revisited — the reasoning it rests on will no longer hold.

### Founder ruling — guest count in the conflict message (Nigel, 2026-08-23)

Resolves open decision 2 from the GTC-184 Phase 1 audit (guest count in the host-facing
conflict message). No other open decision from that audit is resolved by this ruling.

- Drop the guest count. The three-state model carries no headcount, so the message states the
  category only.
- Current wording, verified at `fc29ce0`: `"Event has ${event.dietaryVegetarian} vegetarian
  guest(s) but no vegetarian items in the plan."` (`detectDietaryGaps`, `check.ts:204`) and
  `"Event has ${event.dietaryGlutenFree} gluten-free guest(s) but no gluten-free items in the
  plan."` (`check.ts:230`).
- Proposed wording: `"Event has a vegetarian requirement but no vegetarian items in the plan."`
  and `"Event has a gluten-free requirement but no gluten-free items in the plan."` Titles
  (`'No Vegetarian Options'` / `'No Gluten-Free Options'`) are unaffected.
- `guestCount` is dropped from the emitted `ConflictData` for these two conflict types.
  `currentCoverage`/`minimumNeeded` (0/1) are unaffected — they are not guest counts.

### Founder ruling — free-text 'other' needs (Nigel, 2026-08-23)

Resolves open decision 4 from the GTC-184 Phase 1 audit (free-text 'other' needs). No other
open decision from that audit is resolved by this ruling.

- Ignored, explicitly. `detectDietaryGaps` does not attempt to match `DietaryData.other` free
  text against the item list — no automated verification is possible against unstructured
  text.
- Stated here so the exclusion isn't silently absent from scope: `other` is read by generation
  (`readDietaryData`, consumed at `finalize-plan/route.ts:148`) but is not read by conflict
  detection.

### Founder ruling — schema migration (Nigel, 2026-08-23)

Resolves open decision 5 from the GTC-184 Phase 1 audit (whether Stop Condition 7 applies).

- Confirmed not required. This is a read-side change against an existing `Json?` column
  (`EventSetup.dietaryData`) already populated by the live Moment 2 flow. Stop Condition 7
  does not apply.
