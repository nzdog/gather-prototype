# GTC-443 - The start limit

> Filed by Claude Code on 1 Nov 2026 as a stub, from the plan for
> GTC-392 parts C and D and the founder's rulings that day. Branch
> feat/demo-public from origin/main at df782c4. Planned, not built.

## Scope

The per-visitor start limit becomes hard to fake with a header, kept
across deploys, and atomic. The global limits (30 an hour, 150 a day,
100 AI calls a day) are what bound the cost. The header, as ruled on
Q13: X-Real-IP is read first, else X-Forwarded-For. Which end of
X-Forwarded-For is read is not decided; it is decided after the
staging check. So this ticket ships one small function that picks the
entry (the choice is then a one-line change) and one log line per
start saying whether X-Real-IP was there and how many X-Forwarded-For
entries came, counts only, never a value. No header at all skips the
per-visitor limit only. The count comes from the database: the last 8
of each copy address's 32 hex characters are a keyed hash of the
visitor's address (HMAC-SHA256, key derived from CRON_SECRET with a
fixed label). The first 24 stay random, and no IP is stored. The
in-memory map goes. The three counts and the six-row write run in one
transaction under `pg_advisory_xact_lock(392002)`. New suite
test:demo-start-limit (about 16); its "spoofed first XFF ignored"
check waits on the end chosen.
