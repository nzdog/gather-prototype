# GTC-247 — Local dev environment has no working SMS send path — OPEN

**Status:** Open | **Branch:** TBD | **Commit:** [pending] | **Effort:** low (credential/config
only — no code change expected)
**Severity:** Low (dev-environment gap, not a production issue; not caused by any code change)
**Escalated (brand/trust risk):** No

**Filed from:** GTC-245 Phase 2a smoke testing, 2026-08-23.

---

## Signal

**Expected:** The Twilio-routed SMS send path (`sendSms` → `twilio-client.ts` → `twilio` SDK)
can be smoke-tested locally against Twilio's live API using the credentials configured in this
environment's `.env`.

**Actual:** The configured `TWILIO_ACCOUNT_SID` / `TWILIO_AUTH_TOKEN` fail Twilio's own
authentication. A real request reaches Twilio's API, is correctly formed and sent, and Twilio
returns a structured `Authenticate` (401) error — not a transport failure, an auth failure.

**Smallest failing case:** Run `npx tsx tests/sms-validation-test.ts` (Test 2, the repo's
existing safe pattern — routes the syntactically-valid but unassigned `+1234567890` US number
to Twilio). Result: `[SMS] Failed to send to +1234567890 via Twilio: Authenticate` →
`{ success: false, blocked: 'SEND_FAILED', error: 'Authenticate' }`.

---

## Reproduce

**Required state:** None beyond the existing dev DB (any event with at least one person works;
the test script finds one automatically).

**Steps:**
1. `npx tsx tests/sms-validation-test.ts`
2. Observe Test 2's result.

**Observe:** `Authenticate` error from Twilio, not a successful send and not a transport-level
failure (no `ECONNREFUSED`, no TLS error, no malformed-request error — the round trip completed
and Twilio's API replied).

**Data setup:** None needed; the existing dev DB already satisfies the script's requirements.

---

## Evidence this predates and is unrelated to GTC-245

Cited from [[GTC-245]]'s Phase 2a evidence (2026-08-23): the same test was run immediately
after re-resolving `axios`/`follow-redirects`/`form-data`/`qs` in `package-lock.json`
specifically to smoke-test that fix. The `Authenticate` response is itself the proof the
dependency bump did not break anything — a broken HTTP client fails at the transport layer
(connection refused, TLS handshake failure, malformed request, unparseable response); an
`Authenticate` response requires the request to have been correctly built, sent, and the
response correctly parsed back into a structured error. The failure is Twilio rejecting the
*credentials*, not this app's HTTP stack rejecting anything. Nothing in GTC-245's diff touches
`TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, or any credential-handling code.

---

## Effect

The Twilio/axios send path — the one exercised by every non-NZ/AU SMS this app sends — **cannot
currently be smoke-tested to a successful send in this local environment.** Round-trip/transport
verification is possible (as GTC-245 did); dispatch verification is not, until the credentials
are fixed.

**Separately, and not caused by the same issue: TNZ is also untestable locally, for a different
reason.** No `TNZ_AUTH_TOKEN` is set in this environment's `.env` at all (not present, not just
invalid). TNZ is NZ/AU's SMS provider (`GATHER-BUILD-CONSTANTS.md`) and — per [[GTC-079]], the
ticket that added it — uses its own thin fetch-based client (`src/lib/sms/tnz-client.ts`), not
the `twilio` SDK and not `axios` at all. This is a wholly separate gap from the Twilio auth
failure above; the two aren't the same root cause and fixing one won't fix the other.

**Net effect: neither of the two SMS send paths this app uses (`twilio-client.ts` for non-NZ/AU,
`tnz-client.ts` for NZ/AU — the paths that between them cover every destination this app sends
to) currently has local smoke-test coverage to an actual successful dispatch.** Both can be
exercised up to the point of provider rejection (Twilio: auth failure; TNZ: `SMS_DISABLED`,
provider not configured at all) and no further.

---

## Scope

**Fix here:** Not this ticket. This ticket documents the gap; resolving it means either:
- Twilio: obtain/rotate valid Twilio credentials for this environment (Test Credentials from
  the Twilio Console are the safer choice per `GATHER-BUILD-CONSTANTS.md`'s own guidance — they
  accept API calls but don't send real SMS).
- TNZ: obtain a `TNZ_AUTH_TOKEN` (TNZ Dashboard → Users → API tab, per
  `GATHER-BUILD-CONSTANTS.md`) and add it to `.env`.

Both are credential/environment actions outside an executor's authority — **do not attempt to
fix or acquire credentials as part of this ticket.** Whoever holds the Twilio/TNZ accounts needs
to action this.

**Do not touch:** `src/lib/sms/*` — the code is not implicated; this is purely a local
environment configuration gap. Do-Not-Touch Zone 7 (SMS opt-out logic) is not relevant here but
noted per convention.
