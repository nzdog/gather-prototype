## Signal

**Expected:** All three of this app's outbound send paths — Twilio SMS, TNZ SMS, and Resend
email (the magic-link auth delivery mechanism) — can be smoke-tested locally against their real
provider APIs using the credentials configured in this environment's `.env`.

**Actual:** None of the three currently authenticate or are even configured. Three distinct
failures, three distinct providers:

| Path | Credential | Result |
|---|---|---|
| Twilio SMS (non-NZ/AU) | `TWILIO_ACCOUNT_SID` / `TWILIO_AUTH_TOKEN` | `401 Authenticate` — Twilio rejects the credentials |
| TNZ SMS (NZ/AU) | `TNZ_AUTH_TOKEN` | Not present in `.env` at all — not invalid, simply absent |
| Resend email (magic-link auth delivery) | `RESEND_API_KEY` | `401 validation_error: "API key is invalid"` — Resend rejects the credential |

**Smallest failing case, per path:**
- Twilio: `npx tsx tests/sms-validation-test.ts` (Test 2, the repo's existing safe pattern —
  routes the syntactically-valid but unassigned `+1234567890` US number to Twilio). Result:
  `[SMS] Failed to send to +1234567890 via Twilio: Authenticate` →
  `{ success: false, blocked: 'SEND_FAILED', error: 'Authenticate' }`.
- TNZ: any send to a `+64`/`+61` number returns `SMS_DISABLED` — `TNZ not configured
  (TNZ_AUTH_TOKEN missing)`.
- Resend: call `sendMagicLinkEmail` with a real, DB-persisted `MagicLink` token (not the
  fabricated-token `scripts/test-email.ts`, which can't prove the auth step). Result:
  `[Resend API Error]: { status: 401, error: { statusCode: 401, name: 'validation_error',
  message: 'API key is invalid' }, path: '/emails' }`.

---

## Consequence

**No send path — SMS or email — can currently be verified end to end in this local
environment.** All three can be exercised up to the point of provider rejection (transport
layer proven working in every case — see Evidence below) and no further; none can prove an
actual successful dispatch.

**The magic-link auth path is the one that matters most here, and it has zero local delivery
coverage.** Magic-link email (via Resend) is this app's *sole* authentication mechanism
(`GATHER-BUILD-CONSTANTS.md` Do-Not-Touch Zone 2). Right now, nobody working in this local
environment can confirm — by actually receiving an email and using the link — that a fresh
magic link authenticates correctly. The auth *logic* itself (`/api/auth/verify`, token
lookup/expiry/consumption) is unaffected and untouched by any of this; what's missing is the
ability to close the loop with a real send.

## Evidence this predates and is unrelated to any dependency work

Cited from [[GTC-245]]:

- **Phase 2a** (twilio/stripe branch, 2026-08-23): the Twilio test above was run immediately
  after re-resolving `axios`/`follow-redirects`/`form-data`/`qs` in `package-lock.json`,
  specifically to smoke-test that fix. The `Authenticate` response is itself proof the
  dependency bump didn't break anything — a broken HTTP client fails at the transport layer
  (connection refused, TLS handshake failure, malformed request, unparseable response); an
  `Authenticate` response requires the request to have been correctly built, sent, and the
  response correctly parsed back into a structured error.
- **Phase 2b** (resend branch, 2026-08-23): same shape, same conclusion. The Resend test above
  was run immediately after re-resolving `resend` (6.7.0 → 6.22.0, dropping `svix`/`uuid` from
  the tree) specifically to smoke-test that fix. A `401 validation_error: "API key is invalid"`
  is Resend's API correctly receiving, parsing, and rejecting the request on credential
  grounds — again transport-layer proof the bump didn't break the HTTP path, and again not
  something either dependency change touches: neither diff comes near `RESEND_API_KEY`,
  `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`, `TNZ_AUTH_TOKEN`, or any credential-handling code.

TNZ's absence is a separate, third root cause again: no `TNZ_AUTH_TOKEN` is set at all (not
invalid, just never provisioned locally), and TNZ uses its own thin fetch-based client
(`src/lib/sms/tnz-client.ts`, per [[GTC-079]]), not `axios` — GTC-245 never touched its path
either way.

the values in this local environment could be *old* credentials that were deliberately
invalidated elsewhere, rather than credentials that were simply never valid or expired
naturally. This is speculative and **explicitly unverified** — I checked `git log` for any

rotation incident on record in this repo (`7984652`, `GTC-220`) is about `CRON_SECRET` and URL
plaintext exposure, a different secret and a different concern, and doesn't establish this
hypothesis one way or the other. Recording it here only so whoever has account access checks it
as one possible explanation, not as something already established.

## Open question — is the Twilio credential item even worth fixing?

**Findings only below — no conclusion on whether Twilio should be removed, and nothing removed.**

**Why Twilio exists at all:** TNZ is the SMS provider for NZ/AU because Twilio does not deliver
to NZ numbers (`GATHER-BUILD-CONSTANTS.md`, [[GTC-079]]). Twilio predates that decision —
introduced `2026-01-23` (`3736a76`, "add SMS infrastructure with Twilio integration (Phase 4)"),
originally the *only* SMS provider, intended for NZ numbers too. TNZ was added
`2026-04-09` (`01962a9`, [[GTC-079]]) specifically because Twilio couldn't reach NZ; that same
commit *repurposed* Twilio as the fallback for non-NZ/AU destinations rather than removing it.

**What calls it, and whether each path is reachable in production:**

| Caller | Pre-filters to NZ/AU only? | Twilio reachable via this path? | Wired to |
|---|---|---|---|
| Manual/host-triggered nudge (`chooseManualNudgeChannel` in `manual-nudge-recipient.ts`, GTC-214) | Yes — uses `isValidNZNumber()`; non-NZ falls to email or 'none' before `sendSms` is ever called | **No** | `POST /api/events/[id]/people/[personId]/nudge` (live route) |
| Automatic scheduled nudge (`nudge-eligibility.ts`) | Yes — `isValidNZNumber()` gates candidates before `sendSms` | **No** | `nudge-scheduler.ts` → cron `/api/cron/nudges` |
| Proxy nudge (`proxy-nudge-eligibility.ts`) | Yes — same `isValidNZNumber()` gate | **No** | `proxy-nudge-sender.ts`, called from the same scheduler |
| Decide-by-clock follow-up (`decide-by-eligibility.ts`, GTC-175) | **No — deliberately not.** Code comment: "E.164 validity and provider routing are `sendSms`'s job — deliberately not `isValidNZNumber`, which rejects the +61 numbers `send-sms.ts` routes to TNZ on purpose." Only checks "has a phone number." | **Yes** | `decide-by-sender.ts` → cron `/api/cron/decide-by-followups` (live route) |
| Wrap-up thank-you message (`wrap-up.ts`, GTC-209/210) | **No** — any phone number with `!smsOptedOut` gets channel `'sms'`, calls `sendSms` directly, no country check anywhere in the file | **Yes** | `wrap-up/route.ts` (host-triggered) and cron `/api/cron/wrap-up-dispatch` — both live routes |

**`isSmsEnabled()` (the Twilio-configured predicate) has exactly 2 call sites** total in the
codebase, confirmed by `tests/nudge-provider-gate-test.ts` (GTC-214, assertion `E`): inside
`send-sms.ts`'s own Twilio arm, and the scheduler's health-report line — which GTC-214 also
fixed from being a hard gate (`!isSmsEnabled()` used to kill *all* nudges, including TNZ ones,
on a TNZ-only deployment) to a non-blocking report. Neither call site is dead.

**Does Twilio's non-NZ/AU role predate the TNZ decision?** The *code path* (Twilio existing at
all) predates TNZ by about 11 weeks. But the two callers that actually reach it today — decide-
by-clock (GTC-175) and wrap-up (GTC-209/210) — both landed `2026-08-05`, about four months
*after* GTC-079 added TNZ, and decide-by-eligibility's own code comment shows the non-NZ-gate
choice there was deliberate, not inherited. The two callers that *don't* reach Twilio (manual
nudge, automatic/proxy scheduled nudge) were deliberately narrowed to NZ/AU-only, also after
TNZ existed.

**Net: Twilio is reachable from two live, recently-built, currently-wired production code
paths (wrap-up, decide-by-clock), and unreachable from three others (manual nudge, scheduled
nudge, proxy nudge) by deliberate design.** This does not read as legacy/orphaned code — it
reads as an intentional, currently-maintained split between NZ/AU-only paths and
any-destination paths. Not concluding from this whether the credential item should be fixed,
removed, or left as-is — recording only what the code actually does, per instruction.

**Fix here:** Not this ticket. This ticket documents the gap; resolving it means, per path:
- **Twilio:** obtain/rotate valid credentials for this environment (Test Credentials from the
  Twilio Console are the safer choice per `GATHER-BUILD-CONSTANTS.md`'s own guidance — they
  accept API calls but don't send real SMS).
- **TNZ:** obtain a `TNZ_AUTH_TOKEN` (TNZ Dashboard → Users → API tab, per
  `GATHER-BUILD-CONSTANTS.md`) and add it to `.env`.
- **Resend:** obtain/rotate a valid `RESEND_API_KEY` (resend.com/api-keys).

All three are credential/environment actions outside an executor's authority — **do not attempt
to fix, guess, or acquire credentials as part of this ticket.** Whoever holds the
Twilio/TNZ/Resend accounts needs to action this.

**Do not touch:** `src/lib/sms/*`, `src/lib/email.ts` — none of this code is implicated; this is
purely a local environment configuration gap. Do-Not-Touch Zone 2 (Magic-Link Auth Flow) and
Zone 7 (SMS opt-out logic) are not directly relevant (nothing here touches token/session logic
or opt-out enforcement) but noted per convention given the paths involved.

## ⚠ WHAT TO EXPECT WHEN THE KEY WORKS — CARRIED FORWARD FROM [[GTC-323]], 2026-09-19

*Added on founder instruction, out of the Resend documentation read, because this is the ticket
whoever holds a working key will be standing in.*

> **NO DOCUMENTED ERROR CODE COVERS A WRONG API KEY, AND THE ONLY ENVELOPE THIS REPO HAS EVER
> OBSERVED IS PUBLISHED AT NEITHER THAT STATUS NOR THAT MEANING.**

Resend's published error page covers a **missing** key (`missing_api_key`, 401), a **restricted**
one (401 and 403) and a **suspended** one (403). **There is no published code for a key that is
simply incorrect.**

What this environment actually answers, measured at [[GTC-189]] slice 5f on 2026-09-19:
**`validation_error` / HTTP 401 / "API key is invalid"**. That is undocumented twice over —
`validation_error` is published at 400 and at 403 and never at 401, and its published meanings are
field validation and domain verification, neither of which is authentication.

⚠ **THE EXPECTATION TO CARRY, WHICH IS WHY IT IS HERE RATHER THAN IN GTC-323:**

> **Whoever gets a working key should expect the documentation to be WRONG about failures, not only
> silent about them.**

Silence is the easy case — you observe the value and write it down. This is the other one: a
published page that describes a code's meaning, and a live wire that returns that code for
something else entirely. **A failure envelope that matches the documentation is the thing to
verify, not the thing to assume**, and the first live send is the only chance to check it cheaply.

Full transcript, with the version it was read against:
`docs/05_ops/resend-error-and-delivery-contract-2026-09.md`.

## Acceptance

Not applicable until credentials are resolved (a founder/account-holder action). When picked
up, per path:
- Twilio: a real successful send confirmed via Test Credentials/sandbox numbers, never a real
  recipient number in automated runs.
- TNZ: `npm run test:tnz-sms` confirms a real successful send (per [[GTC-079]]'s own evidence
  pattern — a live delivery to a known test recipient, confirmed by the recipient).
- Resend: a real magic-link email received and its link successfully authenticating a session
  — the specific gap this ticket exists to close, given it's the sole auth mechanism.

⚠ **AND THREE THINGS THAT ONLY A WORKING RESEND KEY CAN SETTLE, NAMED HERE SO THEY ARE CHECKED ON THE
DAY IT WORKS** — added 2026-09-19 out of [[GTC-289]] phases 1 and 2:

1. **That an accepted send returns `data.id` at all.** [[GTC-189]] slice 4b stores it and has never
   seen one.
2. ⚠ **WHICH id JOINS a delivery event back to a send.** The poll answers `id` and `message_id`; the
   webhook carries `email_id` and `message_id`; the send returns `id`. **This is the single thing most
   likely to fail silently, in the direction that looks like nothing happened** — a join on the wrong
   field returns zero rows, and zero rows is what a quiet week looks like. One accepted send, one poll,
   the two ids compared, before any board reads a bounce off it.
3. **That the SUCCESS envelope's declared shape matches the live body.**

✅ **The FAILURE envelope no longer needs this ticket.** Observed 2026-09-19 with a deliberately invalid
sentinel key — no credential, nothing delivered: `{ statusCode: 401, name: 'validation_error', message:
'API key is invalid' }`. The declared `ErrorResponse` shape matches the live body exactly, and ⚠ Resend
answers an invalid key with `validation_error` rather than with any of the four codes whose names are
about keys. [[GTC-323]] carries what that means.
