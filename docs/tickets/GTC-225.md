# GTC-225 — Remediate defective citations in unbuilt stubs

**Status:** Open — unassigned, not started. **Effort:** High.
**Model when pulled:** Opus, xhigh reasoning. This is re-derivation from code, not editing —
the failure mode is accepting a plausible-looking coordinate, which is exactly what produced
the defect.
**Gated on:** [[GTC-222]] (closed, `9bccf42`). The convention must exist before anything is
re-cited against it.
**Not purely a docs ticket.** Phase 1 unblocks a schema migration; Phase 3 asks a live code
question about SMS reachability and carries a privacy-disclosure finding attached to TNZ
go-live. Both may spawn fix tickets. Scope accordingly.

*Source: [[GTC-222]] scope item 5, the read-only sweep of GTC-209–221. That sweep reported;
this ticket repairs.*

### Why this is not part of GTC-223

[[GTC-223]] is documentation accuracy — a stale registry entry misleads a reader. This is a
**migration ticket carrying coordinates that land on enum bodies while marked ready to
build**. A schema repair must not sit behind a docs ticket in anyone's queue. Deliberately
separate; do not merge them.

### What the sweep found

9 of 13 sibling stubs carry a defective citation; 51 of 243 citations no longer resolve; 19
land on a different named construct. Full table in [[GTC-222]]. This ticket acts on the
subset that is still unbuilt, in risk order.

**Note on form:** the line numbers below are quoted as *evidence of a defect*, not used as
addresses. Quoting a broken citation is not making one. Every replacement this ticket writes
must be a symbol per [[GTC-222]], including its fifth rule — **verify the name exists at
HEAD**, which is how [[GTC-211]]'s non-existent `PUT` survived review.

### Phase 1 — [[GTC-216]] (do this first)

A one-statement schema migration, **`status: open`, marked "Ready to build; unblocked"**. Both
its citations are wrong, and both point into enum declarations. Verified at `ae4d6ce`:

| GTC-216 says | Claims it is | Actually at that range | Real location |
|---|---|---|---|
| `prisma/schema.prisma:1045-1066` | `model WrapUpLink` | `enum SnapshotPhase` (1046), `enum TemplateSource` (1050), `enum PatternConfidence` (1062) | `model WrapUpLink` — line 1129, ~84 lines below |
| `schema.prisma:1063-1065` | `WrapUpLink`'s three `@@index` | the `HIGH`/`MEDIUM`/`LOW` members of `enum PatternConfidence` | the three `@@index` inside `model WrapUpLink` — 1147–1149 |

An executor adding `@@unique([eventId, personId])` at the cited coordinates edits an enum
body. Prisma will reject it, so this fails loudly rather than silently — but it fails on a
ticket whose entire content is one statement, whose precondition is already satisfied
(production duplicate count run clean 2026-08-05), and which is therefore the most likely of
the nine to be picked up cold by someone trusting the coordinates.

The displacement source is [[GTC-174]]/[[GTC-175]] growing `prisma/schema.prisma`. The same
~84-line shift invalidated schema coordinates in [[GTC-209]] and [[GTC-210]] simultaneously.

**Do:** re-cite `model WrapUpLink` and its indexes by symbol. Re-confirm the `@@unique`
statement is still the right one-liner against the current model. Leave the precondition
evidence and the deferral rationale untouched — they are sound.

#### GTC-214 is re-derivation, not documentation repair

**The question is whether the Twilio branch is genuinely unreachable from any nudge path.**
That is a code question with a real answer, and the answer is not known. This phase must be
permitted to conclude **"reachable"** and spawn a fix ticket. Scoping it as "correct the
citations in GTC-214" pre-commits to the answer being "unreachable" and is wrong.

What is already established: GTC-214 argues unreachability because *"these three checks"*
force `+64` at every entry — `nudge-eligibility.ts:164`, `:315`, and
`proxy-nudge-eligibility.ts:103`. **Only two of the three survive.** D1 neutralised
`findRsvpFollowupCandidates` in `src/lib/sms/nudge-eligibility.ts` to
`return { eligible: [], skipped: [] }`, taking the `:315` check with it; the function remains
as a stub. The stated reason is therefore false as written.

The conclusion may still hold on the survivors — two live `+64` gates plus a finder that now
returns nothing cannot obviously admit a non-`+64` recipient. **That is what needs
establishing, from the code, not assumed from the ticket.** Trace every path that reaches the
Twilio branch in `sendSms`, not only the ones GTC-214 enumerated.

Stop Condition 9 applies: if the branch is reachable, report and file — do not fold a
behavioural fix into a citation-repair ticket.

#### Cross-reference: the privacy-page disclosure

The [[GTC-176]] (D3) preflight found that the subprocessor list under "Who We Share It With"
in `PrivacyPolicy` (`src/app/privacy/page.tsx`, the Twilio `<li>` at :98 as of `5e318c7`)
names **Twilio** as the SMS subprocessor. **TNZ appears in no `.tsx` in the repo.** Twilio's
only mention in any `.tsx` is that one line.

**These two findings resolve together, and whoever pulls GTC-214 needs both in view:**

| If the Twilio branch is… | Then the disclosure is… |
|---|---|
| **reachable** | coherent — Twilio really is an SMS subprocessor, and the fix is in code |
| **dead** | a **pre-launch disclosure fix** — the page names a provider that sends nothing, and omits TNZ, which will send everything to NZ |

Neither outcome is a documentation tidy-up. One is a live code defect; the other is a privacy
disclosure that is wrong about who handles user phone numbers.

**Timing makes this sharper.** GTC-214 is attached to TNZ go-live — it is the ticket that will
be picked up *at the moment SMS becomes live in NZ*. That is precisely when the privacy page
stops being a draft and starts being a representation to users about where their data goes.
The disclosure question cannot be deferred past the event that makes it matter.

Correcting the disclosure is **not** in this ticket's scope. Surfacing it to whoever pulls
GTC-214, so it is not discovered after go-live, is.

### Phase 4 — closed tickets: annotate only

[[GTC-209]] (14 defective, 5 wrong-symbol) and [[GTC-210]] (12 defective, 6 wrong-symbol) are
**closed**. [[GTC-222]]'s "Out of scope" bars retro-citing closed tickets, and that stands.

**Add a dated stale-as-of-HEAD annotation at the top of each. Do not touch the filed text
below it.** An annotation records that the coordinates no longer resolve as of a given
commit; it does not rewrite them. That distinction is the whole of this phase — a closed
ticket is a record of what was believed at close, and editing its body destroys that.

[[GTC-215]] is also closed, but its drift is factual (a count of skills mentioning P3005), not
positional. Annotate on the same basis if it is touched at all; it overlaps [[GTC-223]] and
should not be repaired twice.
